DDD 领域模型

领域驱动设计（Domain-driven design）是一种通过将实现连接到持续进化的模型来满足复杂需求的软件开发方法。

DDD 核心思想是通过领域驱动设计方法定义领域模型，从而确定业务和应用边界，保证业务模型与代码模型的一致性。

领域驱动设计是一种由域模型来驱动着系统设计的思想。

  • 一种解决复杂系统的建模与分析方法
  • 将业务概念和规则转为对象和对象的属性行为
  • 通过封装、继承和多态降低业务复杂性
  • 不是数据库表结构的映射，而是对业务逻辑、规则、流程的建模。
  • 包含实体、值对象、聚合、领域服务、领域事件等元素。

举个例子：在一个电商系统中，“订单”不是一个简单的 Order 表，而是一个包含下单、支付、取消、发货等行为和状态流转逻辑的复杂对象。

DDD 分层架构的核心思想是每层只能与位于其下方的层发生耦合。领域层是系统的心脏，所有业务规则和逻辑都封装在此。基础设施层为领域层提供技术支撑，但领域层不直接依赖基础设施——通过仓储接口实现依赖倒置。

五层架构

原则：每层只能与位于其下方的层发生耦合。

分层架构可以简单分为两种，即严格分层架构和松散分层架构。在严格分层架构中，某层只能与位于其直接下方的层发生耦合，而在松散分层架构中，则允许某层与它的任意下方层发生耦合。

  • 降低了系统的性能。因为增加了中间层，可以通过缓存机制来改善。

  • 可能会导致级联的修改。这种修改尤其体现在自上而下的方向，可以通过依赖倒置来改善。

层级职责划分

  • 领域层domain（核心业务层）

    • 领域对象：实体对象、值对象、聚合、聚合根 （充血模型：业务方法在实体对象里，负责维护实体自身的生命周期和状态）
    • 领域服务：接口服务，业务的具体实现（围绕实体）：商品服务、电子围栏、订单服务、运单服务、
    • 领域仓储：持久化的细节隐藏，减少领域层对基础设施层的依赖（需要使用到基础设施层，包括DB、Feign调用等）

  • 应用层（业务逻辑层）

    • 应用服务：调用和组合领域层的服务，不包含任何业务逻辑（简单除外），只是组合模型业务（类似模块化）
    • 数据转换：接口参数DTO的简单校验，以及DTO和实体值对象的数据转换
    • 事件订阅：管理多个消息主体
    • 消息订阅：多个微服务间协作解耦的异步实现方式

  • 基础设施层

    • 数据库、缓存、消息队列、配置
    • 对外隐藏技术实现细节，提供粗粒度的数据输出服务
    • 数据库操作：领域层传递的是数据对象，在这里可以按数据表的实现方式进行拆分实现
    • 防腐层（外部API）：隔离业务，防止污染业务代码，可通过代理或适配器实现转换

  • 用户接口层（表现层）

    • 面向服务间API调用，WEB接口
    • 身份认证和权限验证
    • 限流和熔断服务
    • VO和DTO数据转换

  • 简单查询不涉及业务，是可以直接从应用层穿透到PO查询，不需要经过domain层

  • DTO是不能存在于domain层的，DDD设计不认为DTO是业务对象，entity才是

战略设计 vs 战术设计

DDD 分为两大阶段：战略设计（Strategic Design） 确定业务边界，战术设计（Tactical Design） 实现业务逻辑。

维度 战略设计 战术设计
关注点 业务领域划分、限界上下文、上下文映射 聚合、实体、值对象、领域事件、仓储
输出物 领域全景图、上下文映射图、核心子域识别 代码模型（实体类、值对象、领域服务）
常用工具 Event Storming、业务用例分析 JPA/MyBatis、状态机、事件总线
典型问题 “订单状态的业务归属哪个上下文？” “Order 应当是聚合根还是实体？”

限界上下文（Bounded Context） 是 DDD 的基石——每个上下文拥有自己的通用语言（Ubiquitous Language），同一个"订单"在销售上下文、物流上下文、财务上下文中含义各不相同。上下文之间通过 上下文映射（Partnership、Shared Kernel、Customer-Supplier 等）协同工作。

限界上下文与上下文映射

限界上下文是 DDD 中最重要也最容易被忽略的实践。它将庞大复杂的业务领域拆解为一个个语义内聚、边界清晰的子领域，每个子领域拥有独立的通用语言（Ubiquitous Language）。

在电商系统中，典型的限界上下文划分如下：

上下文映射关系

关系类型 含义 电商示例
防腐层（ACL） 下游上下文主动建立翻译层，保护自身领域模型不被上游污染 销售上下文通过 ACL 调用库存上下文
开放主机服务（OHS） 上下文对外提供公共 API，供其他上下文集成 支付上下文提供 PaymentService API
发布语言（PL） OHS 使用的、被双方理解的通信协议 销售与支付间的事件 DTO
共享内核（Shared Kernel） 两个上下文共用部分领域模型 销售上下文与定价上下文共享 Money 值对象
跟随者（Conformist） 下游完全跟随上游模型，不做转换 报表上下文直接复用订单上下文的数据模型
分离方式（Separate Ways） 两个上下文完全独立，不产生依赖 审计上下文与所有上下文仅通过 MQ 异步通信
客户-供应商（C-S） 上游提供服务，下游按合同使用 物流上下文为销售上下文提供物流能力

上下文映射是微服务拆分的重要输入——一个限界上下文通常映射为一个微服务，但并非绝对。当上下文内部聚合间存在强事务依赖时，应保持在同一服务内。

订单建模示例

完整Github项目

  1. DDD 分层模型：

用户接口层（Interface / API 层）：提供 REST 接口，接收外部请求。

应用层（Application 层）：编排领域服务，处理用例逻辑，如“创建订单”。

领域层（Domain 层）：包含核心业务逻辑，如 Order 聚合根、领域事件、状态机、仓储接口等。

基础设施层（Infrastructure 层）：实现仓储接口、防腐层、外部服务调用、事件发布等。

  1. 防腐层（Anti-Corruption Layer, ACL）：

用于与外部系统（如库存服务）交互，避免领域模型被外部污染。

在基础设施层实现，通过 ACL 将外部模型转换为内部领域模型。

  1. 事件与状态机：

使用领域事件（如 OrderCreatedEvent, OrderPaidEvent）表达领域内发生的重要事情。

使用状态机（如 OrderStateMachine）管理订单状态的合法流转（如：待支付 -> 已支付 -> 已发货 / 已取消）。

实体 vs 值对象判断指南

原则：需要身份标识且有生命周期变化的对象 → 实体；仅描述属性且不可变的 → 值对象。

判断维度 实体（Entity） 值对象（Value Object）
身份标识 有唯一 ID（orderId、customerId） 无 ID，靠属性值判断相等性
可变性 可变更（状态从 PENDING → PAID） 不可变（Money.add() 返回新实例）
生命周期 有独立生命周期（创建 → 变更 → 删除） 无生命周期，随所属实体一起持久化
相等性判断 通过 ID 判断（equals 基于 orderId） 通过所有属性判断（equals 基于 amount + currency）
典型例子 Order、Customer、Product Money、Address、Coordinates、Email
复用方式 单独引用（order.customerId） 值复制（多个 Address 实例，值相同即相等）
持久化 独立数据表，有主键 嵌入到实体的表结构中（如 order.shipping_address 字段）
修改方式 order.setStatus(PAID) Money newMoney = oldMoney.add(amount)

决策口诀：问自己"这个对象换了属性值还是同一个东西吗？"是 → 实体；否 → 值对象。例如：一个订单改了收货地址还是原来那个订单（实体）；一张 100 元钞票换成两张 50 元就不再是原来那张钞票了（值对象）。

领域事件（Events）

领域事件是 DDD 中实现最终一致性和跨聚合通信的核心机制。当聚合根的状态发生重要变更时，它发布一个事件，其他聚合或上下文通过订阅该事件做出响应——这种模式将"动作"与"反应"解耦，保证了聚合边界的封装性。

设计原则：

  • 事件名称必须使用过去时态（OrderPaidEvent 而非 PayOrderCommand），表示"已经发生的事情"，而非"想要做的事情"

  • 事件应包含足够信息让消费者独立处理（如 OrderPaidEvent 包含 orderId + amount），避免消费者回查发布者的状态

  • 事件通常设计为不可变对象（final 字段 + No-arg 构造 + 全参构造），一经发布不可更改

  • 同一次事务内发布的事件应统一收集（order.getEvents()），在事务提交后一次性发布，确保"发布或不发布"与"成功或失败"保持一致

在电商场景中，领域事件的典型用途如下：

事件 发布者 典型消费者
OrderCreatedEvent 订单聚合根 库存服务（预留库存）、通知服务（发送下单成功短信）
OrderPaidEvent 订单聚合根 物流服务（生成运单）、积分服务（增加消费积分）、会计服务（记录收入）
OrderShippedEvent 物流上下文 订单服务（更新状态）、通知服务（发送发货提醒）
OrderCancelledEvent 订单聚合根 库存服务（释放库存）、支付服务（发起退款）
OrderRefundedEvent 支付上下文 订单服务（状态变更）、财务服务（记账）

领域服务（Service）

处理跨聚合或跨上下文的复杂逻辑：

仓储接口（Repository）

仓储（Repository）是 DDD 中连接领域层和基础设施层的桥梁。它提供**类似集合（Collection-like）**的访问接口，让领域层能够以面向对象的方式管理聚合的生命周期，而无需关心底层是 MySQL、Redis 还是 MongoDB。

为何接口定义在领域层，实现放在基础设施层？

这是**依赖倒置原则（DIP）**的典型应用：

  • 领域层定义 OrderRepository 接口——这是领域层的"需求声明"：“我需要一个能保存和查找订单的存储机制”

  • 基础设施层实现 JpaOrderRepository 或 MyBatisOrderRepository——这是技术细节：“我用 JPA 来满足这个需求”

  • 领域层不依赖基础设施层，基础设施层依赖领域层定义的接口

这种隔离带来的好处：更换持久化技术时，领域模型完全不需要修改。比如从 JPA 换到 MyBatis，或从 MySQL 迁移到 TiDB，只需修改基础设施层的实现类。

注意：仓储接口的方法签名应使用领域语言（如 findByCustomer），而非数据库语言（如 queryByCustomerIdWithJoin）。仓储屏蔽了底层存储细节，让领域层保持纯净。

工厂封装（Factory）

当聚合根的创建涉及复杂校验或跨多个对象的初始化时，直接 new Order() 或调用静态工厂方法可能不足以表达业务意图。此时引入 Factory 模式将创建逻辑集中管理。

Factory 与领域服务的区别：

  • Factory 专注于对象的创建——它接收简单参数，返回一个完整构造的聚合根，内部封装了所有创建时的校验和初始化逻辑

  • 领域服务 专注于跨越多个聚合的操作编排——它协调多个聚合或外部服务完成一个业务流程

在电商场景中，OrderFactory 负责将购物车中的商品转换为订单项、校验用户状态、计算初始金额，并返回一个处于 PENDING 状态的完整订单。应用层不需要知道这些细节，只需调用 OrderFactory.createFromCart(...) 即可。

何时需要 Factory？ 当创建逻辑满足以下任一条件时：① 需要校验多个外部输入的有效性 ② 创建过程涉及多个领域对象的组合 ③ 创建后需要执行额外的初始化步骤（如发送 OrderCreatedEvent）

聚合设计的原则与常见陷阱

聚合（Aggregate）是 DDD 中最核心也最容易出错的概念。一个设计良好的聚合能保证业务一致性和事务边界清晰，而一个糟糕的聚合会导致性能问题、并发冲突和难以维护的代码。

聚合设计五大原则

  1. 聚合越小越好，但不能太小

    • 聚合应围绕业务一致性边界定义，而不是"一个表对应一个聚合"
    • Order + OrderItem 是一个合理的聚合（一次下单必须同时保存订单头和行项）
    • Order + User 不应在同一个聚合（订单创建不要求用户信息同时变更）

  2. 通过根实体访问所有内部对象

    • 外部只能通过聚合根（order.ship(), order.cancel()）修改内部状态
    • 禁止外部直接获取 OrderItem 引用后修改（order.getItems().get(0).setQuantity(10) 是反模式）
    • 聚合根负责转发所有写操作并校验一致性边界

  3. 一次事务只修改一个聚合

    • 跨聚合的事务一致性通过最终一致性 + 领域事件补偿，而非分布式事务
    • 例如：订单支付后通过 OrderPaidEvent 通知库存扣减，而非在同个事务中锁定库存
    • 使用 Saga 或 TCC 模式保证跨聚合的最终一致性

  4. 引用其他聚合只通过「ID」而非对象

    • Order 不应持有 User 对象引用，应持有 customerId（值对象）
    • 如需 User 数据，通过领域服务查询（应用层编排）
    • 避免将整个聚合图加载到内存中

  5. 边界内强一致性，边界外最终一致性

    • 聚合内的所有状态变更必须在同一次数据库事务内完成
    • 聚合之间的状态同步通过异步事件实现
    • 这是 DDD 对 CAP 理论的实践回答：聚合内部 CP，聚合之间 AP

典型反例：设计一个巨大的 OrderAggregate 包含 Order、OrderItem、Payment、Shipment、Invoice —— 看起来"完整"，实际上每次操作都要加载整个对象图，导致严重的性能瓶颈和并发冲突。正确的做法应拆分为四个独立聚合，通过领域事件协调。

事件驱动的订单状态机设计

  • 订单的状态流转不再由"硬编码 if-else"控制，而是通过 监听领域事件 触发状态变更。

  • 使用 状态机（State Machine） 模型来管理 OrderStatus 的合法转换。

  • 所有状态变更由 领域事件驱动，保证逻辑集中、可追溯、可扩展。

事件处理器（Event Handlers）

事件处理器是将领域事件与业务反应连接起来的纽带。每个事件处理器监听一类领域事件，当事件发生后执行对应的业务操作——典型的反应包括调用状态机变更状态、通知仓储持久化、发布跨服务消息等。

设计原则：

  • 单一职责：每个事件处理器只处理一种事件类型。OrderPaidEvent 的处理逻辑不应与 OrderShippedEvent 混在一起

  • 幂等性：由于事件可能重复投递（如 Broker 宕机重试），事件处理逻辑应保证多次执行与一次执行效果相同。实践中可通过检查订单当前状态实现幂等：“如果订单状态已经是 PAID，忽略重复的 OrderPaidEvent”

  • 失败隔离：事件处理器中的异常不应影响其他事件的派发。推荐在每个处理器中 independently catch 异常，避免一个事件处理失败阻塞后续事件

Spring 事件机制 vs 消息队列：@EventListener 适用于同进程内的事件处理（事务边界内），而如果事件的消费方在另一个微服务或需要异步持久化保证，应使用消息队列（Kafka/RocketMQ）来发布事件。实践中通常结合两者：领域事件先通过 Spring Event 在进程内同步处理，同时由基础设施层将事件转发到 MQ 供下游服务消费。

支持事件溯源

事件溯源（Event Sourcing）是 DDD 的一种高级模式：不存储聚合的当前状态，而是存储所有发生过的事件，当前状态由事件序列重放（Replay）得到。

与常规仓储的区别：

  • 常规仓储：orders 表中存储订单的当前快照（status = PAID, totalAmount = 99.00），更新时直接覆盖

  • 事件溯源：order_events 表中存储事件的有序序列（OrderCreatedEvent → OrderItemAddedEvent → OrderPaidEvent），查询订单时从空状态开始依次应用所有事件

事件溯源的优势：

  • 完整的审计追踪：每个事件都记录了"谁在什么时间做了什么"，天然满足金融审计合规要求

  • 时间旅行：可以回溯到任意历史时间点，查看当时的订单状态，对排查问题极有价值

  • 事件驱动的自然架构：存储的就是事件本身，无需额外将状态转换为事件

代价：

  • 查询当前状态需要重放事件，事件量大时性能下降（可通过快照 Snapshot 优化）

  • 事件 Schema 的演进需要兼容性设计（如 Protobuf/Avro + Schema Registry）

  • 删除数据困难（ GDPR 合规场景下需要"抵消事件"而非物理删除）

事件溯源并非适用于所有场景。对于需要高查询性能和即时的当前状态视图的业务（如实时报表、Dashboard），使用常规仓储 + 领域事件的组合方式更合适。事件溯源最适合审计要求严格、需要完整变更历史的业务领域（如金融交易、合规记录）。

防腐层的核心价值：当支付宝的 AlipayCallback 数据结构发生变化时，只需修改 AlipayAclAdapter 与 PaymentEventMapper，领域层的 Order 聚合根和状态机逻辑完全不受影响。这就是 DDD 所说的"保护领域模型的纯洁性"。

防腐层通常包含三个职责明确的组件：外部 DTO（接收外部数据）、ACL 适配器（校验和转发）、事件映射器（将外部格式转换为领域事件）。下面以支付宝支付回调为例逐一说明：

  1. 外部支付回调 DTO（来自支付宝）

    支付宝回调的原始数据结构。这是外部系统的"语言"，不能直接进入领域层。注意字段命名是支付宝的规范（trade_no、out_trade_no），与我们的领域模型完全不同——这正是需要防腐层翻译的原因。

  2. 防腐层适配器（ACL Adapter）

    适配器是防腐层的入口——它接收外部请求，执行安全校验（如签名验证），然后将数据交给映射器转换为领域事件。一个好 ACL 适配器应做到：即使外部系统彻底重构，适配器的内部逻辑变化也不会扩散到领域层。

  3. 事件映射器（Mapping Logic）

    映射器负责翻译——将支付宝的"方言"（TRADE_SUCCESS、TRADE_CLOSED）翻译为领域内通用的"普通话"（OrderPaidEvent、OrderRefundedEvent）。这是防腐层中最核心的转换逻辑，也是当外部系统接口变更时最需要关注的地方。

    为什么不直接把 AlipayCallback.tradeStatus 传给领域层？ 因为支付宝的状态枚举（TRADE_SUCCESS）是外部概念，领域层不应感知它的存在。映射器负责这个"从外部到内部"的语义转换，确保领域模型只理解自己的语言。

应用层（Service）

应用层是 DDD 分层架构中的"指挥者"，它负责：

  1. 接收输入：从接口层接收 DTO 或 Command 对象

  2. 编排领域逻辑：调用领域层的一个或多个聚合根、领域服务完成业务操作

  3. 管理事务：控制事务边界（@Transactional），确保聚合内的一致性

  4. 发布事件：将聚合根收集的领域事件发布到事件总线

应用层与领域层的核心区别：应用层不包含业务规则，它只是"知道做什么"（比如"下单需要创建订单并扣库存"），而"具体怎么做"（比如"订单的状态机是什么样的"、“扣库存的规则是什么”）由领域层负责。应用层更像是胶水代码，它把领域对象粘合起来完成一个用例。

注意：应用层的 Service 方法通常对应一个完整的用例（Use Case），每个方法应当只做一件事。如果 Service 方法越来越长，说明该方法的逻辑可能应该下沉到领域服务或拆分为多个用例。

接口层（Controller）

接口层是系统的边界，负责处理 HTTP 请求和响应。在 DDD 分层中，接口层的职责非常明确：

  1. 协议转换：将 HTTP 请求（JSON/XML）转换为应用层能够理解的 Command/DTO 对象

  2. 基础校验：参数校验（@Valid、@NotNull）、身份认证、权限控制

  3. 调用应用层：将转换后的 Command 交给应用层 Service 处理

  4. 响应封装：将应用层返回的结果封装为 HTTP 响应（ResponseEntity）

接口层不允许包含任何业务逻辑——业务规则必须封装在领域层。例如，Controller 不应该判断"订单状态为 PENDING 才能支付"，这是 Order.pay() 方法内部的事情。

分层职责边界：

  • Controller：HTTP 协议 + 参数校验（能收什么）
  • Application Service：用例编排 + 事务（做什么）
  • Domain：业务规则校验 + 状态变更 + 事件发布（怎么做）

每一层都只能调用其紧邻下方的层——Controller 不直接调用 Repository，Application 不直接访问数据库。

CQRS 与 DDD 结合

CQRS（Command Query Responsibility Segregation）将读写操作分离为不同的模型——命令端（Command） 接收写请求，经过领域模型处理；查询端（Query） 直接读取数据，绕开复杂的领域对象。

CQRS 是 DDD 的天然搭档，尤其在复杂业务场景下解决以下痛点：

  1. 读写负载不对称：写操作经过聚合根严格校验（如订单状态机、库存锁定），读操作只需要简单的数据展平。将两者混在同一个模型中，要么查询性能差（因为穿越领域层），要么领域逻辑被查询优化冲淡。

  2. 查询形态各异：订单详情页需要 Order + Items + Address 的嵌套结构；订单列表页只需要 orderId + status + totalAmount 的扁平结构；订单报表页需要按时间、金额、状态多维聚合。一个聚合根无法同时满足多种查询需求。

  3. 读模型可自由优化：查询端可以直接使用 JOIN、投影查询、甚至引入读库（Read Replica）或搜索引擎，不影响领域模型的封装性。

CQRS + DDD 的典型分层

注意事项：CQRS 增加了系统复杂度，不是所有场景都需要。对于简单的 CRUD 场景，一个模型兼顾读写更高效。仅当读写逻辑差异明显时才引入 CQRS。

DDD 在微服务拆分中的落地策略

DDD 的限界上下文是微服务拆分的最理想输入。一个限界上下文对应一个微服务，但落地时需考虑以下因素：

拆分原则

原则 说明 电商示例
按业务能力拆分 每个微服务负责一个完整的业务领域 订单服务、支付服务、库存服务、物流服务
按变更频率拆分 变更频率不同的逻辑放入不同服务 促销规则每周调整 → 独立为定价服务
按数据所有权拆分 每个服务拥有自己的数据存储，不共享数据库 订单服务用 MySQL，支付服务用 TiDB 保证分布式事务
按团队结构拆分 遵循康威定律，匹配团队边界 订单团队负责 Order 相关的所有服务

  1. Event Storming：业务专家和技术团队一起贴便签，识别领域事件（Event）、命令（Command）、聚合（Aggregate）

  2. 限界上下文识别：将事件归类到不同的业务边界内，形成上下文地图

  3. 服务映射：每个限界上下文映射为一个微服务（如果上下文中聚合间存在强事务依赖，可保持在同一服务）

  4. API 设计：下游服务通过 OHS（开放主机服务）+ ACL（防腐层）与上游服务交互

  5. 独立部署：每个服务独立 CI/CD、独立数据库、独立伸缩

  6. 可观测性：通过分布式追踪（Jaeger/Zipkin）串联跨服务调用链

过渡策略：绞杀者模式

从单体到微服务不建议"大爆炸式重构"。推荐绞杀者模式（Strangler Fig Pattern）：

  1. 在单体旁边新建微服务，处理新需求
  2. 通过反向代理（如 Nginx）将新请求路由到微服务，旧请求仍由单体处理
  3. 逐步将单体功能迁移到微服务，直到单体可以退役

关键原则：先拆分变更最频繁且边界最清晰的模块（如商品服务），积累经验后再拆分核心模块（如订单服务）。

DDD vs 传统 CRUD 对比总结

维度 传统 CRUD（贫血模型） DDD（充血模型）
核心设计 数据表驱动，Service 层包含所有逻辑 领域模型驱动，业务规则封装在聚合根内
实体状态 纯数据容器（Getter/Setter），无行为 状态变更通过业务方法控制（如 order.pay()）
业务规则 分散在 Service 层，难以复用 集中在领域层，聚合根统一校验
数据一致性 依赖数据库事务保证 聚合根内部一致 + 领域事件驱动最终一致
外部耦合 直接调用外部 API，与外部模型耦合 通过防腐层隔离，领域模型纯净
变更影响 改表结构需改 Service 层 改业务规则只需改聚合根，隔离性好
适用场景 简单 CRUD、报表查询、管理后台 复杂业务逻辑、强规则校验、高复杂度领域
团队要求 熟悉 ORM + SQL 即可 需领域建模能力、学习周期长

选型建议：DDD 并非万能银弹。一个纯增删改查的管理后台使用 CRUD 更加高效，但当业务逻辑复杂到一定程度（如订单状态机、支付对账、库存管理），DDD 的充血模型能显著降低长期维护成本。
