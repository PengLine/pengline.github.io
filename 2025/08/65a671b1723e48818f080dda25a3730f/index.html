Redis 过期数据的删除和淘汰策略

发表于2025-08-26|更新于2026-09-06
|DBRedis
|浏览量:

过期清除策略

redis针对设置过期时间的key，所使用的清除策略有主动和被动两种方式。

flowchart TD
    A[Redis 启动] --> B{客户端访问某个 key?}
    B -- 是 --> C{该 key 已设置过期时间?}
    C -- 是 --> D{当前时间 > 过期时间?}
    D -- 是 --> E[立即删除该 key
（惰性删除 Lazy Expire）]
    D -- 否 --> F[正常返回 key 的值]
    C -- 否 --> F

    B -- 否 --> G{后台周期性任务触发
（默认每秒 10 次）}
    G --> H[随机采样一批设置了过期时间的 key
（默认 20 个）]
    H --> I{采样中发现过期 key?}
    I -- 是 --> J[删除所有过期 key]
    I -- 否 --> K[本次扫描结束]

    J --> L{过期 key 占比 > 25%?}
    L -- 是 --> M[立即再次执行定期删除
（避免堆积）]
    L -- 否 --> N[等待下一次周期任务]

    E --> O[内存释放]
    F --> P[业务逻辑继续]
    K --> Q[继续监听客户端请求]
    M --> H
    N --> Q

    style J fill:#e8f5e9,stroke:#4caf50
    style M fill:#fff8e1,stroke:#ff9800

被动检测

被动检测，也称惰性删除。

放任键过期不管，每次从键空间中获取键时，都检查取得的键是否过期，如果过期就删除该键，否则就返回该键值。

被动方式对于那些永远不会再访问的 key 并没有效果。不管怎么，这些 key 都应被过期淘汰，所以 Redis 周期性主动随机检查一部分被设置生存时间的 key，那些已经过期的 key 会被从 key 空间中删除。

sequenceDiagram
    participant Client as 客户端
    participant Redis as Redis Server
    participant KeySpace as 键空间 (keyspace)
    participant Expires as 过期字典 (expires)

    Client->>Redis: GET mykey
    Redis->>Expires: 检查 mykey 是否在 expires 中？
    alt 存在过期时间
        Expires-->>Redis: 返回过期时间 T
        Redis->>Redis: 判断当前时间 > T ?
        alt 已过期
            Redis->>KeySpace: 从 keyspace 删除 mykey
            Redis->>Expires: 从 expires 删除 mykey
            Redis-->>Client: 返回 nil
        else 未过期
            Redis->>KeySpace: 从 keyspace 获取 mykey 的值
            Redis-->>Client: 返回 value
        end
    else 无过期时间
        Redis->>KeySpace: 直接获取 mykey 的值
        Redis-->>Client: 返回 value
    end

主动检测

  • 定时删除：在设置键过期时间的同时，创建一个定时器 timer。让定时器在键的过期时间来临时，执行对键的删除操作。

    这种方式最精确也最消耗 CPU：每个设置过期时间的 Key 都要维护一个定时器，过期键很多时定时器数量庞大，且创建/销毁定时器本身有开销。因此 Redis 并未采用"定时删除"，而是选择下面的定期删除作为主动检测手段。

  • 定期删除：每隔100ms就对数据库进行一次随机抽查，删除里面的过期键。至于要删除多少过期键，以及要检查多少个数据库，则由算法决定。比如Redis每秒执行10次下面的操作：

    1. 从带有生存时间的 key 的集合中随机选 20 进行检查。
    2. 删除所有过期的key。
    3. 如20里面有超过25%的key过期，立刻继续执行步骤1。

    为什么是“随机采样”而不是“全量扫描”？

    Redis 的过期字典（expires）可能包含数百万个 Key，全量扫描会阻塞主线程。随机采样 20 个 + 比例控制（>25% 继续），将单次主动删除的 CPU 开销限定在可控范围内：既保证过期 Key 不会大量堆积，又不会因清理任务阻塞正常请求。

flowchart TD
    A[Redis 启动后台定时任务] --> B{每秒执行 10 次
（由 server.hz 控制）}
    B --> C[从 expires 字典中
随机抽取 20 个带过期时间的 key]
    C --> D{遍历这 20 个 key}
    D --> E{当前 key 已过期?}
    E -- 是 --> F[从 keyspace 和 expires 中删除该 key]
    E -- 否 --> G[保留该 key]
    F --> H
    G --> H
    H{是否遍历完 20 个?}
    H -- 否 --> D
    H -- 是 --> I{本次扫描中
过期 key 占比 > 25%?}
    I -- 是 --> J[立即再次执行本流程
（继续清理）]
    I -- 否 --> K[等待下一次周期任务]

数据淘汰策略

Redis 的内存淘汰机制（Eviction Policy）是指当 Redis 的内存使用量达到设定的最大值（通过 maxmemory 配置）时，选择哪些数据被删除以释放空间来存放新数据的策略。

由于redis定期删除是随机抽取检查，不可能扫描清除掉所有过期的key并删除，一些key由于未被请求，惰性删除也未触发。

同时存在未设置过期时间的key，这样redis的内存占用会越来越高。此时就需要内存淘汰机制。

淘汰算法

Redis 的淘汰算法有4种：

  • random（随机）：随机选择被淘汰的 Key，实现最简单

  • TTL（将要过期）：选择剩余生存时间最短的 Key 淘汰

  • LRU（最近最少使用，Least Recently Used）：淘汰最久未被访问的 Key

  • LFU（最不经常使用，Least Frequently Used，4.0+）：淘汰访问频率最低的 Key

flowchart LR
    subgraph LRU 最近最少使用
        LRU1[按访问时间排序
淘汰最久没碰过的] --> LRU2[适合: 幂律分布/热点缓存]
    end
    subgraph LFU 最不经常使用
        LFU1[按访问频率计数
淘汰频率最低的] --> LFU2[适合: 防缓存污染/低频突发访问]
    end
    subgraph TTL 最快过期
        TTL1[按剩余生存时间
淘汰最快过期的] --> TTL2[适合: 临时数据优先级管理]
    end
    subgraph Random 随机
        RD1[随机抽取淘汰] --> RD2[适合: 数据访问均匀场景]
    end

LRU vs LFU 的关键差异：

  • LRU 只看"多久没访问"——一个 Key 历史上被访问 1000 次，但最近 1 分钟没被碰，就可能被 LRU 淘汰；
  • LFU 看"整体访问频率"——上述 Key 的访问频率高，会继续保留，反而淘汰那些"刚被访问过一两次但从未热过"的 Key。

典型场景：某明星热搜 Key 短时间被刷 10 万次，之后不再有人访问。LRU 会认为它"很新"而保留很久（缓存污染）；LFU 会因 10 万次频率给它较高初始计数，但配合频率衰减机制，最终也能正确淘汰它。

淘汰策略

Redis 支持8种淘汰策略（maxmemory-policy 可取值）：

  1. noeviction（默认）：不清除数据，只返回错误，会导致浪费掉更多内存（DEL 命令和其他的少数命令例外）

  2. allkeys-lru：从所有的数据集（server.db[i].dict）中挑选最近最少使用的数据淘汰

  3. allkeys-lfu：从所有数据集（server.db[i].dict）中挑选访问频率最低的数据淘汰（4.0+）

  4. allkeys-random：从所有数据集（server.db[i].dict）中任意选择数据淘汰

  5. volatile-lru：从已设置过期时间的数据集（server.db[i].expires）中挑选最近最少使用的数据淘汰

  6. volatile-lfu：从已设置过期时间的数据集（server.db[i].expires）中挑选访问频率最低的数据淘汰（4.0+）

  7. volatile-random：从已设置过期时间的数据集（server.db[i].expires）中任意选择数据淘汰

  8. volatile-ttl：从已设置过期时间的数据集（server.db[i].expires）中挑选将要过期的数据淘汰，ttl值越小越优先被淘汰

flowchart TD
    A[客户端发起写操作：SET, HSET, LPUSH等] --> B{当前已用内存大于等于 maxmemory?}
    
    B -- 否 --> C[直接执行写入 返回 OK]
    
    B -- 是 --> D{maxmemory-policy 配置为何值?}
    
    D -->|noeviction| E[拒绝写入 返回错误： OOM command not allowed when used memory > 'maxmemory'.]

如果没有设置 expire 的key, 那么 volatile-lru, volatile-random 和 volatile-ttl 策略的行为, 和 noeviction基本一致。

一般来说:

​ 设置 expire 会消耗额外的内存, 所以使用 allkeys-lru 策略, 可以更高效地利用内存 。

​ 如果某个命令导致大量内存占用(一个很大的set), 在一段时间内, 内存的使用量会明显超过 maxmemory 限制。

策略选择建议

策略使用规则：

  • 如果数据呈现幂律分布，也就是一部分数据访问频率高，一部分数据访问频率低，则使用 allkeys-lru。如果分为热数据与冷数据, 推荐使用 allkeys-lru 策略。 如果不确定具体的业务特征, 那么 allkeys-lru 是一个很好的选择。

  • 如果数据呈现平等分布，也就是所有的数据访问频率都相同，则使用 allkeys-random，即读写所有元素的概率差不多。

策略 适用场景
allkeys-lru 通用场景，最常用。如果你的数据访问模式大致符合幂律分布（即一部分数据访问频率高，另一部分低），或者你不确定该用什么策略，选这个通常不会错。
allkeys-lfu 你希望数据的访问频率对淘汰决策影响更大时。例如，一个key即使刚被访问过，但如果它历史上只被访问过一两次，而其他key被访问过成百上千次，那么它仍然可能被淘汰。
volatile-ttl 你希望通过设置不同的TTL来主动管理数据的优先级，并且希望Redis优先淘汰那些快要过期的“临时”数据，保留那些TTL很长的核心数据。
volatile-lru / volatile-lfu 你希望将 Redis 既用作缓存（有过期时间），又用作持久存储（无过期时间）。这样能保证永久数据不会被淘汰，只淘汰缓存数据。
allkeys-random / volatile-random 所有数据被访问的概率都差不多，没有明显的热点数据。
noeviction 不推荐用于缓存场景。适用于你希望数据永不被删除，并且内存足够或由应用层处理写失败的情况。

过期删除对主从复制与持久化的影响

理解了上述删除机制后，一个面试高频问题随之而来：从库会不会自己删除过期键？RDB/AOF 里会残留过期键吗？

结论先行：Redis 集群中，过期键的删除动作只发生在主库，从库永远被动等待主库的删除指令；而持久化文件则按“是否过期”在生成与载入两个阶段分别过滤。

主从复制：删除动作只发生在主库

sequenceDiagram
    participant M as 主库 Master
    participant S as 从库 Replica
    participant C as 客户端

    Note over M: 惰性删除 / 定期删除
发现 key 已过期
    M->>M: 删除过期 key（释放内存）
    M->>S: 传播 DEL key 命令
    S->>S: 执行 DEL 删除本地 key

    Note over C,S: 从库被读到“已过期但尚未收到 DEL”的 key 时：
    C->>S: GET key
    S-->>C: 返回 nil（键已逻辑过期，不可见）
但不主动删除，等待主库 DEL

关键设计点：

  • 删除指令由主库产生：无论是惰性删除还是定期删除，主库每删除一个过期键，都会在命令传播阶段向所有从库发送一条 DEL，同时追加写入 AOF；

  • 从库不做“主动删除”：从库自身的读请求即使命中过期键，也只返回 nil 而不删除（键对读不可见）。若从库各自随意删除，将与主库的删除产生时序冲突，可能导致主从不一致；

  • 为什么从库还需要过期时间：主库 DEL 命令可能因网络延迟晚于客户端对从库的读取到达，从库需要依据本地保存的过期时间判断“逻辑过期”，避免返回脏数据。

特殊场景：若从库提升为主库（故障转移），它身上“已过期但未被删除”的键将由新主库的惰性/定期删除机制继续接管清理，不会造成内存永久泄漏。

RDB：生成过滤，载入区分主从

阶段 处理逻辑
生成 RDB 遍历数据库时跳过已过期的键（expires 字典中判定已过期的 key 不写入文件），因此 RDB 中不会保存已过期数据
主库载入 载入时再次过滤：已过期的键直接丢弃，不载入内存
从库载入 不做过滤，原样载入所有键（含已过期键）——因为从库删除动作依赖主库的 DEL，若载入时就丢弃，可能导致与主库状态不一致

AOF：删除即追加，重写即过滤

  • 运行期追加：键被惰性/定期删除时，Redis 会向 AOF 追加一条 DEL 命令，保证 AOF 重放后与内存状态一致；

  • AOF 重写：基于当前内存数据重建 AOF 文件时，已过期的键不会写入新文件。

启发：理解这套机制有助于排查两类线上问题——

  1. 从库内存持续增长：检查是否有大量“只被从库读到过、但主库删除命令积压”的过期键堆积（配合 INFO replication 观察同步延迟）；
  2. 重启后内存异常：若使用 RDB 恢复且从库全量载入，短暂的内存峰值属于正常现象，主库 DEL 同步后会自动回落。
