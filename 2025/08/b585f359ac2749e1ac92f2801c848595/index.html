docker-compose 安装脚本大集锦

发表于2025-08-27|更新于2026-09-07
|DevOpsDocker
|浏览量:

本地开发、测试环境里最“烦人”的不是写代码，而是搭中间件：装 Nacos 要配数据库、起 Kafka 要解决监听器、部署 ES 集群要处理安全配置……每个组件都有自己的启动姿势，换台机器就得重来一遍。而 docker-compose 把“镜像 + 端口 + 环境变量 + 数据卷”声明成一份 YAML，一条 up -d 就能复现一套完整环境，已经成为本地开发与交付验证的事实标准。

本文汇总了日常开发与中小型生产环境中常用的 10 组中间件 compose 编排脚本，每组都同时给出单机版与集群版两种形态，并针对部署中真实踩过的坑（监听器配置、网段冲突、安全开关与 Token 的矛盾、数据目录挂载丢失等）给出说明与修正，可直接复制、按需裁剪。

几点通用提醒

  1. 文中 YAML 顶部的 version: '3.x' 字段已被 Docker Compose V2 忽略（仅为兼容旧版保留），删除不影响运行。
  2. 所有相对路径卷（./data/...）都以执行 compose 的目录为基准，脚本与数据目录建议固定存放；重装前先备份对应数据目录。
  3. 宿主机端口若被占用，直接改 ports 左侧宿主机端口即可（右侧容器端口勿动）。
  4. 生产环境建议把镜像 tag 从 latest 固定为具体版本，避免漂移。

Nacos

单机模式（Standalone）

单机模式使用内嵌 Derby 数据库，适合本地联调；数据保存在容器内，容器销毁即丢失，不适合承载任何正式环境（集群模式见下节，必须外置 MySQL）。

启动后访问：http://localhost:8848/nacos 默认账号密码：nacos / nacos

集群模式（Cluster）

集群版必须外置 MySQL（5.7+ / 8.0）承载配置与注册数据，且需要先初始化官方 SQL 脚本。

  • 3 个 Nacos 节点（v2.x 集群需 ≥3 个节点才能完成 Raft 选主，节点数保持奇数更稳）

  • 1 个 MySQL 8.0（持久化配置、服务注册与鉴权数据）

  • Nginx（可选，做 8848 负载均衡与健康检查；本文省略，客户端可直连任一节点，Nacos 客户端内置故障转移）

初始化 SQL 从哪来：Nacos 发行包 conf/ 目录下的 mysql-schema.sql（随版本发布，官方文档亦提供）。先在 MySQL 中执行建表，再把它改名为 init.sql 放入下方 ./data/mysql/init.sql——MySQL 容器首次启动时会自动执行该目录下所有 .sql 文件（仅首次，数据卷已存在则跳过）。表结构必须与 Nacos 镜像版本严格对应。

  • 访问任意节点：

    • http://localhost:8848/nacos
    • http://localhost:8849/nacos
    • http://localhost:8850/nacos

  • 默认账号密码：nacos / nacos

RocketMQ

RocketMQ 5.x 拆分为三个进程协同工作，读懂职责后脚本便一目了然：

  • namesrv（9876）：注册中心，维护 Broker 地址与主题路由，无状态、可水平扩展；

  • broker（10909/10911/10912）：消息的存储与读写主体（10911 主服务、10909 VIP 通道、10912 主从同步）；

  • proxy（8081）：5.x 新增的无状态接入层，向客户端提供 gRPC/HTTP 协议，remoting 老协议客户端仍直连 Broker。

Kafka

单机版（KRaft 模式）

背景：Kafka 3.3+ 进入 KRaft 时代，用内置 Controller 取代 ZooKeeper 管理元数据，单机部署不再需要额外起 ZK。示例采用 Confluent 镜像（cp-kafka），环境变量以 KAFKA_ 前缀注入其 server.properties；注意该前缀约定与 bitnami 镜像的 KAFKA_CFG_ 不同，二者不要混写。

Mosquitto（MQTT）

MQTT 是面向 IoT / 机器对机器场景设计的轻量消息协议：报文头部极小（最小控制报文仅 2 字节）、支持 QoS 0/1/2 三级可靠性、断线重连与遗嘱消息等机制，非常适合带宽受限、网络不稳定的设备链路。本节提供 Eclipse Mosquitto（最轻量的开源 Broker）的 compose 编排与配置。

三种 QoS 怎么选：QoS 0（最多一次）适合遥测类丢得起的数据；QoS 1（至少一次）默认选择，可能重复但绝不丢失，业务侧需幂等；QoS 2（恰好一次）开销最大，仅在金融类强一致场景使用。

SkyWalking

完整组件：OAP Server（11800 gRPC 数据上报 / 12800 HTTP 查询接口）+ SkyWalking UI（8080）+ Elasticsearch（存储层）。应用侧只需在启动命令挂载 javaagent 即可自动上报链路数据。

接入说明：应用接入时在 JVM 启动参数追加 -javaagent:/path/to/skywalking-agent.jar -Dskywalking.agent.service_name=your-app -Dskywalking.collector.backend_service=<宿主机IP>:11800（agent 从 SkyWalking 发行包获取，版本尽量与 OAP 一致），随后访问 UI：http://localhost:8080 查看拓扑与调用链。

存储提示：OAP 的 SW_STORAGE=elasticsearch 对应 ES 7.x；若改用 ES 8，需升级 OAP 至支持 ES 8 的版本并补充 SW_STORAGE_ES_*（用户名/密码/SSL）相关变量，否则启动报错。

Prometheus

一套完整的监控告警栈包含四类角色，compose 中一一对应：

  • 采集层：Prometheus 本体（9090）+ node_exporter（9100，主机指标）+ cadvisor（8080，容器指标）+ pushgateway（9091，接收短生命周期任务的指标推送）；

  • 存储与查询：Prometheus 内嵌 TSDB，数据落在 ./data/prometheus/data；

  • 可视化：Grafana（3000）；

  • 告警：Alertmanager（9093），接收 Prometheus 规则触发的告警并做分组/抑制/路由分发。

集群版

基于 Docker Compose 的 Redis 集群（3 主 3 从，共 6 个节点）配置示例

至少 3 个主节点才能完成故障转移的多数派选举，通常搭配 3 个从节点（共 6 节点）实现高可用。本节配置全部通过命令行参数注入，不需要 redis.conf。

本文以单机 Docker 为场景（客户端与容器同机）；若跨多台物理机部署，需把每处 cluster-announce-ip 改为对应宿主机实际 IP。

  • 6 个节点均公布 127.0.0.1 作为 announce IP（客户端从宿主机经端口映射访问）；从其他机器访问时，把 6 处 127.0.0.1 统一改为宿主机实际 IP，保持所有节点一致。

  • 每个节点暴露两类端口：客户端端口 700x 与集群总线端口 1700x（gossip 与故障转移走总线端口，必须一并公布）。

  • 需要持久化时在每个节点追加 --appendonly yes（示例未开启）。

  • 使用固定子网（172.28.0.0/24）+ 静态 IP，避免容器重启后 IP 漂移导致集群配置失效。

网络创建失败并报 Pool overlaps，说明 yaml 中自定义子网（本文 172.28.0.0/24）与 Docker 主机上已有网络（其他 compose 网络、Docker 自动创建的网桥等）网段重叠：

✘ Network redis_redis-net Error 0.0s
failed to create network redis_redis-net: Error response from daemon: invalid pool request: Pool overlaps with other one on this address space

解决：先 docker network ls 与 docker network inspect <name> 排查已占用网段，把 yaml 中的子网换成未占用网段（如 172.29.0.0/24），并同步修改 6 个节点的静态 IP 末段。

若 --cluster create 一直卡在：

Sending CLUSTER MEET messages to join the cluster
Waiting for the cluster to join

说明节点间总线网络不通：gossip 走的是 1700x 总线端口，卡住的原因通常是——create 命令中的地址与节点 cluster-announce-* 公布值不一致、1700x 端口未映射、或宿主机防火墙拦截。

必读提醒：

  1. Windows Docker Desktop 不支持 --network host，不要用 host 网络方式执行 create；直接在任一节点容器内执行上文命令（容器间走 compose 网络天然互通）。
  2. 若节点曾加入过旧集群，其数据目录下会残留 nodes.conf，需清理后再建，否则报 “Node is not empty / already exists”。
  3. create 成功后用 redis-cli --cluster check 127.0.0.1:7000 验证槽位与主从关系（--cluster info 查看概要）。

OpenSearch

OpenSearch 是 Elasticsearch 7.10 之后由 AWS 主导分叉的开源检索分析引擎，API 与 ES 7.x 高度兼容（迁移索引与客户端几乎零改动），Dashboards 即对应 Kibana。编排要点与 ES 高度一致：OPENSEARCH_JAVA_OPTS 控制堆内存、memlock/nofile 资源限制、数据卷持久化，以及 2.12+ 新增的初始管理员密码机制——下面的单机与集群两个示例，正好演示“关闭安全插件”与“启用安全插件（.env 注入凭据）”两种形态。

单机 + Dashboard（关闭安全插件）

单机开发最省事的做法是整体禁用安全插件（plugins.security.disabled=true），免去证书、账号密码与 HTTPS 配置。有两个易踩的坑：

  1. 禁用安全后不能再设 OPENSEARCH_INITIAL_ADMIN_PASSWORD——2.12+ 镜像检测到“设了密码却禁用安全”会拒绝启动（该变量在下方已注释，仅供开启安全时参考）；

  2. Dashboards 必须同步禁用安全（DISABLE_SECURITY_DASHBOARDS_PLUGIN=true），否则它会继续以 HTTPS + 账号方式连接 ES，报连接被拒绝。

集群 + Dashboard（启用安全插件）

集群版保留安全插件（两个节点的 environment 中都没有 plugins.security.disabled=true），节点间走内部认证，Dashboards 凭账号登录。为避免把密钥硬编码进 yaml，密码统一放在与 yaml 同目录的 .env 文件中（compose 启动时自动加载）：

要点

  1. 主机名可达：节点间通过 discovery.seed_hosts 互指，compose 网络内解析服务名 opensearch-node1 / opensearch-node2 即可；Dashboards 的 OPENSEARCH_HOSTS 同样指向服务名，浏览器访问 http://localhost:5601 输入 .env 中的账号密码登录；
  2. 多节点密码必须一致：OPENSEARCH_INITIAL_ADMIN_PASSWORD 仅在集群首次初始化安全索引时生效，之后再改 .env 不会变更已存密码，反而会让新节点因凭据不一致而无法加入；
  3. 双节点集群无故障容错（任一节点宕机即失去多数派、集群不可写），仅适合联调演示，生产请扩展为 ≥3 节点（照抄 node1 段再增补一段即可）。

Neo4j

Neo4j 是业界应用最广的原生图数据库：数据以“节点 + 关系 + 属性”的形式落盘（而非在关系型数据库之上模拟图），关系与实体是同等的一等公民，存储与遍历都针对图结构做了专门优化——多跳关系查询（如“A 的朋友中谁认识 B 公司的员工”）比关系型的递归 JOIN 快若干个数量级，因此在社交网络、风控反欺诈、知识图谱等场景中被广泛采用。

容器化部署的关键在于理解 Neo4j 5.x 的配置注入语法：官方镜像把所有设置收敛为 NEO4J_ 前缀环境变量（. 转 _、: 转 __，如 server.memory.heap.max_size → NEO4J_server_memory_heap__max__size），并引入初始密码机制（NEO4J_AUTH 只在空数据卷首次启动时生效）。下文依次给出单机、运维命令、配置文件与 3 节点集群四组编排——集群示例专门演示 5.x 相对 4.x 的集群配置项迁移（causal_clustering_* → server.*），这是网上大量旧教程最容易照抄出错的地方。

访问：http://localhost:7474（HTTP，Neo4j Browser 界面）；7687 为 Bolt 协议端口（客户端驱动连接用）。

单机（Standalone）

单机形态使用 Community 社区版（镜像免费、无许可限制；Community 与 Enterprise 的差距仅在集群与热备能力，单机功能一致）。两个易错点：

  • NEO4J_AUTH 格式为 用户名/密码，且只在数据卷为空（首次启动）时生效，改密码请用下文“重置初始密码”命令；

  • 镜像对密码有强度校验（建议 ≥8 位并混合大小写字母与数字），不满足会启动失败并在日志中打印原因。

  • 登录账号即 yaml 中 NEO4J_AUTH 设定的组合：用户 neo4j / 密码 123@Admin；已通过环境变量设置初始密码，登录时不会再出现“首次登录强制改密”流程；

  • 若数据卷已存在旧数据，直接改 yaml 里的密码不生效（NEO4J_AUTH 只在空卷首启时生效），需用 neo4j-admin dbms set-initial-password 重置（见上文命令）；

  • 上文 yaml 使用 5.20-community：Community 与 Enterprise 在单机场景功能一致，仅集群与热备能力不同（集群必须 Enterprise）。

配置

Neo4j 5.x 的配置统一写在容器内 /conf/neo4j.conf；官方镜像还支持把它翻译成 NEO4J_ 前缀环境变量注入 compose：规则为 . → _、: → __，例如 server.memory.heap.max_size 对应 NEO4J_server_memory_heap__max__size。APOC 等插件的参数写在 /conf/apoc.conf（或用同规则环境变量）。注意 4.x 时代的 dbms.* 前缀在 5.x 大多已迁移为 server.*，照抄旧教程会静默失效：

集群版（3 Core 节点）

集群由 3 个 Core 节点组成：每台都保存完整数据副本，写请求经 Raft 共识被多数派（≥2）确认后才提交，因此节点数必须是奇数且最多容忍 1 台故障；还可按需追加 Read Replica（只读副本，不参与共识，专门扩展读能力）。

  • 集群必须使用 Enterprise Edition 并接受许可（-community 镜像不含集群模块，即便配置了成员名单也只会以单机模式启动）；

  • 节点间通信端口约定：5000 discovery / 6000 transaction / 7000 raft，仅经 compose 内部网络互访即可，无需映射到宿主机；

  • 以下示例全部为 5.x 语法：4.x 的 NEO4J_causal_clustering_*、NEO4J_initial_mode_constraint 在 5.20 镜像上不生效，照抄 4.x 教程最常见的现象是——三个容器各自以单机模式启动，show servers 里全是 UNKNOWN 或节点间互不可见。

部署自查与常见问题

无论单机还是集群形态，up -d 之前建议按下面顺序过一遍，可以规避本文 90% 的“起不来”问题：

  1. 端口冲突：报 port is already allocated 时，只改 yaml 左侧宿主机端口（右侧容器端口勿动）；

  2. 网段冲突：自定义 subnet（如 172.28.0.0/24）报 Pool overlaps 时，用 docker network ls / docker network inspect <name> 找出占用网段，换一个未占用的；

  3. 配置与安全开关自相矛盾：Kafka 的 KAFKA_（confluent 系）与 KAFKA_CFG_（bitnami 系）前缀不可混用；ES / OpenSearch 的安全开关、密码、Token 必须整体一致——关闭安全就不设密码/Token，开启安全则全部配齐，Redis 集群还要保证所有节点的 announce 地址一致；

  4. 数据卷与配置目录：相对路径卷以执行 compose 的目录为基准；Kafka 的 KAFKA_LOG_DIRS、ES 的 path.data 等必须指向已挂载的卷目录；不要整体挂载 ES/OpenSearch 的 config 目录（空目录会遮住镜像自带配置）；

  5. 镜像漂移：生产环境固定 tag（如 opensearch:3.3.2 而非 latest），多节点集群必须全节点同版本，部署前先 docker compose pull 验证仓库可达。

统一排障手段：docker compose logs -f <service> 看启动日志 → docker compose ps 看健康状态 → docker exec -it <容器名> <自检命令>（如 curl localhost:9200、redis-cli ping）逐层定位，最后再检查宿主机防火墙与端口占用。
