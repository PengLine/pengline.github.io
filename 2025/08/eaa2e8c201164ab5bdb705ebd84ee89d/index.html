负载均衡算法的多种实现方案

发表于2025-08-28|更新于2026-09-06

|浏览量:

常见的负载均衡算法列举与实现。

Server 对象定义

在分布式系统中，负载均衡器部署在客户端与服务器集群之间，作为请求流量的统一入口。其核心目标是最大化吞吐量、最小化响应时间、避免单点过载。

算法分类上，负载均衡策略有 静态 与 动态 之分。静态算法（随机、轮询、加权随机等）在决策时不参考后端实时状态，实现简单但无法感知负载波动；动态算法（最小连接数、加权响应时间等）则结合实时健康检测与负载指标做调度，效果更佳但复杂度更高。本文聚焦静态算法的几种经典实现及其原理。

随机

随机从集群中选择一个服务器

随机算法的数学期望

随机算法的核心在于各服务器被选中的概率相等。设有 (n) 台服务器，在 (k) 次独立请求中，每台服务器的期望被调用次数为 $ (E = k/n)$，方差为 $\text{Var} = k \cdot (1/n) \cdot (1 - 1/n)$。方差衡量了实际分布与均匀分布的偏离程度——当请求数 (k) 较小时，方差相对较大，可能出现倾斜；当 (k) 增大时，中央极限定理保证实际分布趋近均匀。

代码中使用 SecureRandom.getInstanceStrong() 而非 Math.random() 或 java.util.Random，原因在于 SecureRandom 基于操作系统熵池（如 /dev/random）生成不可预测的随机数，在安全敏感场景下可防止攻击者通过预测随机序列来操纵流量分配。但代价是性能较低，高并发场景可考虑使用 ThreadLocalRandom 提升吞吐，或退化为 Random 并配合定期重新种子。

TreeMap 在 Java 中基于红黑树实现，key 按自然顺序或 Comparator 排序。加权随机构造时，将累计权重作为 key、Server 作为 value 存入 TreeMap，形成形如 {1→A, 3→B, 6→C, 10→D} 的映射。随机数落在哪个区间就选择对应的服务器，整个区间划分和查找的过程如下：

flowchart TD
    A[服务器列表] --> B[计算累计权重<br>A:1 B:3 C:6 D:10]
    B --> C[存入 TreeMap<br>key=累计权重, value=Server]
    C --> D[生成随机数 r = 0,10]
    D --> E[weightMap.tailMap]
    E --> F[取 firstKey 对应的 Server]
    F --> G{验证权重匹配度}
    G --> H[(r 落在权重区间<br>即命中对应 Server)]
    style H fill:#9f9

TreeMap.tailMap(key, inclusive) 返回一个视图，包含所有 key 大于指定 key 的映射；firstKey() 取其中最小的 key。由于红黑树增删改查均为 O(log n)，加权随机构造完成后每次查找的时间复杂度为 O(log n)，远优于区间法每次遍历 O(n)——当服务器数量达到数百台时这一差异尤为显著。

轮询

把来自用户的请求轮流分配给集群中的服务器

轮询算法通过 currentServerIndex = (currentServerIndex + 1) % servers.size() 实现请求的均匀分配。取模运算确保索引在 [0, n-1] 范围内循环，其行为可以用一个有限状态机来描述：

flowchart TD
    S0[状态<br>currentServerIndex=0] -->|分配请求给 Server0| S1[(状态<br>currentServerIndex=1)]
    S1 -->|分配请求给 Server1| S2[(状态<br>currentServerIndex=2)]
    S2 -->|分配请求给 Server2| SN[... 依次类推]
    SN -->|到达 n-1 后<br>取模归零| S0
    style S0 fill:#6af,color:#fff
    style S1 fill:#6af,color:#fff
    style S2 fill:#6af,color:#fff

轮询算法的优点是实现简单、请求绝对均匀，但缺点是无法感知服务器负载差异——若某台服务器性能较弱，仍然会被分配相同数量的请求，可能导致该节点过载。为此业界提出了加权轮询（Weighted Round-Robin）和最少连接数（Least Connections）等改进方案。

当前实现中 currentServerIndex 使用 volatile 保证可见性，但 getNextServer() 方法中的 check-then-act 模式存在竞态条件：两个线程同时进入时可能读到相同的 index。生产环境建议加 synchronized 或使用 AtomicInteger 保证原子性。

算法选型对比

面对不同的业务场景，选择合适的负载均衡算法至关重要。下表总结了各算法的核心特征和适用场景：

算法 时间复杂度 空间复杂度 请求分布 适用场景
随机 O(1) O(n) 概率均匀 服务器性能均等、请求量大的场景
加权随机(TreeMap) O(log n) O(n) 按权重概率分布 服务器配置异构、需要权重控制
加权随机(区间法) O(n) O(n) 按权重概率分布 服务器数量较少时的简单实现
轮询 O(1) O(n) 严格均匀 无状态服务、连接时效短的场景

并发安全分析

静态负载均衡算法通常不持有服务端的状态信息，因此天然适合无状态架构。但多线程环境下仍需注意：

  • SecureRandom：线程安全，但 getInstanceStrong() 在 Linux 下会阻塞等待熵池，高并发时可能导致延迟尖刺。可考虑在初始化时预生成随机种子后改用 ThreadLocalRandom。

  • TreeMap：WeightRandom 类中的 weightMap 在构造后只读，因此线程安全。若需动态调整权重，需加锁或使用 ConcurrentSkipListMap。

  • volatile + mod：PollingSlb 中的 currentServerIndex 使用 volatile 保证可见性，但复合操作（读-改-写）仍非原子。推荐使用 AtomicInteger 的 getAndIncrement() % n 模式保证线程安全。
