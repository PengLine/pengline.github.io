Java 多线程之等待全部执行完成

发表于2025-08-28|更新于2026-09-08
|Java多线程
|浏览量:

需求：多线程任务（查询、文件、API）同时执行，等所有线程执行完成后才能继续向下，执行其他任务

核心思想：将“并发执行”与“同步等待”解耦。任务提交后由线程池并行处理，主线程通过某种同步原语阻塞，直到所有任务完成。Java 中常用的实现手段可分为三类：

  1. Future / CompletableTask：通过返回值对象阻塞等待每个任务结果；

  2. 计数器型：CountDownLatch 在任务完成时递减计数，主线程等待计数归零；

  3. 信号量型：Semaphore 初始计数为 0，任务完成后释放许可，主线程 acquire 全部许可。

无论哪种方式，底层都依赖 AQS（AbstractQueuedSynchronizer） 的共享模式：等待线程在 AQS 队列中阻塞，当条件满足时由最后一个完成任务唤醒。

submit() 多线程

底层通过实现 Future 接口实现返回值，获取 callable 接口。

只有等线程执行完成获取到结果后才能继续执行后面的流程，会阻塞直到结果返回。

FutureTask 状态流转

submit() 返回的 Future 实际为 FutureTask。它内部维护一个状态机，主线程调用 get() 时若任务未完成则进入 AQS 等待队列，任务执行完成后通过 LockSupport.unpark 唤醒等待线程。

stateDiagram-v2
    [*] --> NEW: submit()
    NEW --> COMPLETING: run() 正常返回
    NEW --> COMPLETING: run() 抛异常
    COMPLETING --> NORMAL: 结果赋值
    COMPLETING --> EXCEPTIONAL: 异常赋值
    NORMAL --> [*]: get() 返回结果
    EXCEPTIONAL --> [*]: get() 抛出 ExecutionException
    NEW --> CANCELLED: cancel()
    COMPLETING --> CANCELLED: cancel() (极少)

get(long timeout, TimeUnit) 会让当前线程在 AQS 队列中限时等待；超时后抛出 TimeoutException，但任务仍会继续执行。

使用

Semaphore（信号量）

计数信号量用来控制同时访问某个特定资源的操作数量，或者同时执行某个指定操作的数量。计数信号量还可以用来实现某种资源池，或者对容器施加边界。

Semaphore 中管理着一组虚拟的许可，通过 acquire 获取一个许可，如果没有许可则一直阻塞。其本质就是操作系统的P-V操作，当资源足够的时候线程获得资源并执行，资源不足时线程等待或者退出，当资源被释放时线程又可以获取竞争资源继续执行；

Semaphore 等待模型

本例中 Semaphore 初始许可数为 0，每个任务完成时调用 release() 增加一个许可，主线程调用 acquire(threadNum) 一次性获取全部许可。若许可不足，主线程在 AQS 共享队列中阻塞，直到最后一个任务释放。

sequenceDiagram
    participant Main as 主线程
    participant AQS as AQS 共享队列
    participant T1 as 任务1
    participant T2 as 任务2
    participant T3 as 任务3

    Main->>AQS: acquire(3) state=0
    AQS-->>Main: 阻塞

    T1->>AQS: release() state=1
    T2->>AQS: release() state=2
    T3->>AQS: release() state=3
    AQS-->>Main: 唤醒
    Main->>AQS: acquire(3) 成功

注意：若某个任务异常退出而未执行 release()，主线程将永远阻塞。因此 release() 应放在 finally 块中，或使用 Callable + Future 结合异常处理。

CountDownLatch（计数器）

一种同步工具类，可以延迟线程的进度直到其到达终止状态。可以用来确保某些活动直到其他活动都完成后才继续执行。

应用场景：

  • 确保某个计算在其需要的所有资源都被初始化之后才继续执行。

  • 确保某个服务在其依赖的所有其他服务都已经启动之后才启动。

  • 等待直到某个操作的所有参与者都就绪再继续执行。

实现原理：

闭锁状态包括一个计数器，该计数器被初始化为一个正数，表示需要等待的事件数量。 countDown 方法用来递减计数器，表示有一个事件已经发生了， await 方法用来等待计数器达到零。如果计数器的值非零，那么 await 方法会一直阻塞直到计数器为零，或者等待中的线程中断、等待超时。当某个线程调用await()方法时，由于tryAcquireShared会判断state是否等于0，如果不等于，就会进入等待队列，直到countDown调用sync.releaseShared(1)使得sync的状态到0，await的线程才会继续执行；

CountDownLatch 状态流转

CountDownLatch 内部同样基于 AQS 共享模式：构造时设置 state = count，每个 countDown() 通过 releaseShared(1) 将 state 减 1；当 state == 0 时，唤醒所有在 await() 上阻塞的线程。

sequenceDiagram
    participant Main as 主线程
    participant AQS as AQS(state=3)
    participant T1 as 任务1
    participant T2 as 任务2
    participant T3 as 任务3

    Main->>AQS: await() state≠0
    AQS-->>Main: 进入等待队列

    T1->>AQS: countDown() state=2
    T2->>AQS: countDown() state=1
    T3->>AQS: countDown() state=0
    AQS-->>Main: doReleaseShared 唤醒
    Main->>Main: 继续执行

不可复用：CountDownLatch 的计数归零后无法重置，若需循环使用请改用 CyclicBarrier。

实践中的问题与解决方案

问题 1：任务异常导致主线程永久阻塞

现象：使用 CountDownLatch 或 Semaphore 时，某个子任务抛异常，未执行 countDown() / release()，主线程 await() / acquire() 一直不返回。

根因：计数器/信号量的释放操作没有放在 finally 中，异常退出破坏了同步契约。

解决步骤：

  1. 将 countDown() / release() 放入 finally 块；

  2. 或者使用 Future.get()，异常会以 ExecutionException 形式抛出，不会丢失；

  3. 对批量任务，使用 ExecutorService.invokeAll()，框架会自动处理任务完成或异常。

问题 2：部分 Future 超时后结果不一致

现象：对多个 Future 逐个 get(timeout)，某次超时后抛 TimeoutException，但其他任务仍继续执行，最终汇总结果缺少该任务输出。

根因：Future.get(timeout) 超时仅表示等待线程放弃等待，任务本身仍在线程池中运行；若不取消，可能产生副作用。

解决步骤：

  1. 超时后调用 future.cancel(true) 中断任务线程；

  2. 使用 CompletableFuture.allOf(...).orTimeout(...) 统一控制超时；

  3. 记录任务状态，超时不成功的任务按失败重试或降级处理。

问题 3：CountDownLatch 计数设置错误

现象：CountDownLatch 初始计数与实际任务数不一致，导致主线程提前唤醒或永久阻塞。

根因：动态任务数量（如分页查询、条件过滤后任务数变化）与硬编码计数不匹配。

解决步骤：

  1. 使用任务集合的 size() 初始化 CountDownLatch；

  2. 任务提交后禁止再修改集合；

  3. 复杂场景改用 CompletableFuture.allOf(tasks.toArray(new CompletableFuture[0]))。

问题 4：Semaphore 的 release 次数大于 acquire 次数

现象：Semaphore 许可数被异常放大，导致后续同步语义失效。

根因：业务代码中 release() 调用次数多于任务完成次数，或在异常分支重复释放。

解决步骤：

  1. 每个任务只释放一次，且必须在 finally 中执行；

  2. 对“等待全部完成”场景，更推荐使用 CountDownLatch，语义更直观且不会引入额外许可。

方案选型速查

场景 推荐方案 理由
需要任务返回值 Future#get / CompletableFuture.allOf 可获取异常与结果
无需返回值，仅需等待 CountDownLatch 语义清晰、不可复用、计数直观
任务数动态变化 CompletableFuture.allOf 无需预设计数器
需限制并发 + 等待全部完成 Semaphore 既能限流也能作为完成信号
