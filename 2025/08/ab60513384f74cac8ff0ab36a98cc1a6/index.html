Java 多线程之等待至少一个执行完成

发表于2025-08-28|更新于2026-09-08
|Java多线程
|浏览量:

需求：多个线程同时执行一个任务，只要一个成功就退出，其他线程任务可以取消或无视。

核心思想：“多路竞速 + 首个完成即放行”。与“等待全部完成”不同，主线程只需等到第一个任务完成即可继续，其他任务要么被忽略，要么被显式取消。实现方式可分为三类：

  1. 单次信号型：CountDownLatch(1)，首个任务 countDown() 后主线程放行；

  2. 循环栅栏型：CyclicBarrier(2)，主线程与首个到达的任务互相等待后一起放行；

  3. 队列/信号量型：Semaphore(0).release() 或 BlockingQueue.take()，首个任务投递结果后主线程被唤醒。

无论哪种方式，都必须处理“剩余任务如何取消”的问题；否则它们会继续占用线程池资源，甚至可能产生副作用。

注意：如果要暂停线程池中其他未执行完成的线程，需要先记录下来，然后调用其打断方法。

CountDownLatch（计数器）

一种同步工具类，可以延迟线程的进度直到其到达终止状态。可以用来确保某些活动直到其他活动都完成后才继续执行。

应用场景：

  • 确保某个计算在其需要的所有资源都被初始化之后才继续执行。

  • 确保某个服务在其依赖的所有其他服务都已经启动之后才启动。

  • 等待直到某个操作的所有参与者都就绪再继续执行。

实现原理：

闭锁状态包括一个计数器，该计数器被初始化为一个正数，表示需要等待的事件数量。 countDown 方法用来递减计数器，表示有一个事件已经发生了， await 方法用来等待计数器达到零。如果计数器的值非零，那么 await 方法会一直阻塞直到计数器为零，或者等待中的线程中断、等待超时。当某个线程调用await()方法时，由于tryAcquireShared会判断state是否等于0，如果不等于，就会进入等待队列，直到countDown调用sync.releaseShared(1)使得sync的状态到0，await的线程才会继续执行；

CountDownLatch(1) 竞速模型

将计数器初始化为 1，任意一个任务率先调用 countDown() 即可把 state 从 1 减到 0，从而唤醒在 await() 上阻塞的主线程。该模型实现简单，但无法阻止其他任务继续执行。

sequenceDiagram
    participant Main as 主线程
    participant AQS as AQS(state=1)
    participant T1 as 任务1
    participant T2 as 任务2
    participant T3 as 任务3

    Main->>AQS: await()
    AQS-->>Main: 阻塞

    T2->>AQS: countDown() state=0
    AQS-->>Main: 唤醒
    T1->>T1: 继续执行（已无人等待）
    T3->>T3: 继续执行（已无人等待）

CAS 结果覆盖风险：示例中使用 AtomicInteger.compareAndSet(0, n) 保存首个结果。若多个任务几乎同时完成，只有一个能成功写入，其余被忽略，这通常符合“任一成功”语义。

CyclicBarrier（循环栅栏）

栅栏能阻塞一组线程直到某个事件发生，直到所有线程都到达栅栏点，栅栏才会打开。所以栅栏一般用于多个线程需要相互等待的情况

闭锁用于等待事件，而栅栏用于等待其他线程。

可以使一定数量的参与方（线程）反复地在栅栏位置汇集，await方法将阻塞直到所有线程都到达栅栏位置。

原理实现:

CyclicBarrier 维护了一个计数器，和一个 generation 每次调用await都会有将计数器减一，并且产生一个新的 generation ，只要计数器不为零，所有前置线程都会触发 await(); 内部会调用 LockSupport.park(this); 方法将线程加入等待队列， 所有线程就绪，会调用 trip.signalAll(); 唤醒所有线程，同时执行一个用户自定义的 Runnable 策略

CyclicBarrier 双 barrier 模型

本例创建两个 CyclicBarrier(2)：一个用于“任务线程与主线程”同步，另一个用于“任务线程之间”同步。首个到达的任务线程与主线程在第一个 barrier 相遇后共同放行。CyclicBarrier 可重置复用，但实现“任一成功”语义较为迂回，生产环境较少使用。

sequenceDiagram
    participant Main as 主线程
    participant T1 as 任务1
    participant T2 as 任务2
    participant T3 as 任务3
    participant B1 as CyclicBarrier(2)

    Main->>B1: await()
    T1->>B1: await()
    T2->>T2: 仍在执行
    T3->>T3: 仍在执行
    B1-->>Main: 屏障打开
    B1-->>T1: 屏障打开

注意：若任务线程未到达 barrier 就异常退出，会触发 BrokenBarrierException，需要额外处理屏障损坏后的恢复逻辑。

Semaphore（信号量）

计数信号量用来控制同时访问某个特定资源的操作数量，或者同时执行某个指定操作的数量。计数信号量还可以用来实现某种资源池，或者对容器施加边界。

Semaphore 中管理着一组虚拟的许可，通过 acquire 获取一个许可，如果没有许可则一直阻塞。其本质就是操作系统的P-V操作，当资源足够的时候线程获得资源并执行，资源不足时线程等待或者退出，当资源被释放时线程又可以获取竞争资源继续执行；

Semaphore 单许可放行模型

Semaphore(0) 表示初始无可用许可，主线程 acquire() 会阻塞；任一任务完成后 release() 释放一个许可，主线程随即被唤醒。与 CountDownLatch(1) 类似，但 Semaphore 的许可可以被多次释放/获取，若使用不当容易破坏同步语义。

sequenceDiagram
    participant Main as 主线程
    participant Sem as Semaphore(0)
    participant T1 as 任务1
    participant T2 as 任务2

    Main->>Sem: acquire()
    Sem-->>Main: 阻塞
    T2->>Sem: release()
    Sem-->>Main: 唤醒
    Main->>Main: 继续执行
    T1->>T1: 继续执行

Queue（阻塞队列）

通过队列的阻塞等待实现

阻塞队列投递模型

BlockingQueue.take() 在队列为空时阻塞；任一任务完成后 add() / put() 一个元素，主线程立即拿到结果。LinkedBlockingQueue 容量默认无界，建议使用有界队列防止任务过多导致内存问题。

sequenceDiagram
    participant Main as 主线程
    participant Q as BlockingQueue
    participant T1 as 任务1
    participant T2 as 任务2

    Main->>Q: take()
    Q-->>Main: 阻塞（队列空）
    T2->>Q: add(result)
    Q-->>Main: 返回 result
    Main->>Main: 继续执行

如何打断其他线程

取消剩余任务流程

“任一成功”模型中，首个任务完成后应尽快取消其他正在执行的任务，避免资源浪费。由于线程池中的线程由池管理，直接 interrupt() 只是发送中断信号，任务必须响应中断（如 Thread.sleep() 会抛 InterruptedException）才能真正退出。

flowchart TD
    A[启动所有任务并记录 Thread] --> B{任一任务完成?}
    B -->|是| C[从队列/结果获取首个结果]
    C --> D[遍历已记录线程]
    D --> E[调用 Thread.interrupt]
    E --> F{任务是否响应中断?}
    F -->|是| G[任务退出]
    F -->|否| H[继续执行直到自然结束或超时]
    B -->|否| I[继续等待]

更优雅的做法：提交 Callable 任务并保存 Future 列表，首个任务完成后调用其他 Future.cancel(true)；这样既不需要手动维护 Thread 集合，也能确保线程池接收到中断信号。

实践中的问题与解决方案

问题 1：结果覆盖与重复处理

现象：多个任务几乎同时完成，AtomicInteger.compareAndSet(0, n) 只有一个成功，但其他任务仍在执行并产生副作用（如扣款、写库）。

根因：“等待任一成功”只保证主线程被唤醒，不保证其他任务停止。

解决步骤：

  1. 在获取首个结果后，立即对其他 Future 调用 cancel(true)；

  2. 任务内部必须定期检查 Thread.currentThread().isInterrupted()；

  3. 对不能中断的阻塞操作（如 Socket IO），设置 socket 超时或使用 CompletableFuture.orTimeout。

问题 2：任务不响应中断导致取消失败

现象：调用了 Thread.interrupt() 或 Future.cancel(true)，但任务仍在运行。

根因：任务代码吞掉了 InterruptedException 或没有检查中断标志。

解决步骤：

  1. 在循环和阻塞调用处正确处理中断；

  2. 吞掉 InterruptedException 后应重新设置中断标志：Thread.currentThread().interrupt()；

  3. 对 CPU 密集型任务，在关键位置检查 isInterrupted() 并主动退出。

问题 3：CountDownLatch(1) 误用为全部完成

现象：业务需要等待所有任务完成，却错误使用 CountDownLatch(1)，导致只等一个任务完成就继续。

根因：对同步工具语义理解不清。

解决步骤：

  1. 明确需求是“任一完成”还是“全部完成”；

  2. “全部完成”使用 CountDownLatch(N) 或 CompletableFuture.allOf；

  3. “任一完成”使用 CountDownLatch(1)、CompletableFuture.anyOf 或 ExecutorCompletionService。

问题 4：线程池任务堆积

现象：大量“任一成功”任务被提交到线程池，但其他未成功任务未被取消，导致线程池长期满载。

根因：缺少取消机制，或取消信号未能传递到任务内部。

解决步骤：

  1. 使用 ExecutorCompletionService.take() 获取首个结果后，批量 cancel 剩余 Future；

  2. 为任务设置全局超时，超时后强制取消；

  3. 监控线程池活跃线程数与队列长度，及时发现堆积。

方案选型速查

场景 推荐方案 理由
仅需第一个结果 ExecutorCompletionService 自然返回最先完成的任务结果
需要取消其他任务 Future#cancel + CountDownLatch(1) 结构简单，取消语义清晰
任务数固定且可复用 CyclicBarrier 可重置，但实现竞速较迂回
需要结果顺序无关 CompletableFuture.anyOf 函数式组合，支持链式超时处理
