|浏览量:

SSH 公钥认证原理

SSH 免密登录基于非对称加密：本地持有私钥，远程服务器（GitHub/Gitee）保存公钥。认证时服务器用挑战-响应机制验证客户端是否拥有对应私钥，整个过程不会在网络上传输私钥。

sequenceDiagram
    autonumber
    participant Client as Git 客户端 (SSH)
    participant Agent as ssh-agent
    participant Server as Git 服务器 (sshd)

    Client->>+Server: 发起 SSH 连接 (携带用户名)
    Server->>Server: 查询 authorized_keys 匹配公钥
    Server->>Client: 发送 Challenge (包含 会话ID + 随机数)
    Client->>+Agent: 请求私钥签名 (传入 Challenge 数据)
    Agent-->>-Client: 返回签名结果 (Signature)
    Client->>Server: 提交签名数据
    Server->>Server: 使用公钥验证签名
    Server-->>-Client: 返回认证结果 (Success / Failed)

SSH Config Host 匹配流程

~/.ssh/config 中的 Host 支持通配符，SSH 会按从上到下的顺序匹配第一个符合的条目，并应用对应的 HostName、IdentityFile 等参数。

flowchart TD
    A[ssh git@github.com] --> B[读取 ~/.ssh/config]
    B --> C{逐行匹配 Host}
    C -->|匹配 github.com| D[使用对应 IdentityFile]
    C -->|未匹配| E[使用默认 ~/.ssh/id_rsa]
    D --> F{ssh-agent 是否已加载该密钥?}
    E --> F
    F -->|是| G[建立连接]
    F -->|否| H[自动加载 / 提示输入密码]
    H --> G

多账号场景决策树

flowchart TD
    A[需要在同一设备管理多个 Git 账号] --> B{是否同一平台?}
    B -->|是<br/>多个 GitHub 账号| C[使用不同 Host 别名<br/>如 github / github_blog]
    B -->|否<br/>GitHub + Gitee| D[按 Host 区分配置]
    D --> E{企业内网/防火墙?}
    E -->|是| F[配置 Port 443 + HostName ssh.github.com]
    E -->|否| G[默认 22 端口]
    C --> H[仓库 remote URL 使用对应 Host 别名]
    G --> H
    F --> H

Git 配置作用域

作用域 配置文件 优先级 适用场景
system /etc/gitconfig 最低 系统管理员统一配置
global ~/.gitconfig 中 用户级默认用户名/邮箱
local .git/config 最高 单仓库独立身份

多账号场景下，应避免使用 git config --global user.email，而是在每个仓库内使用 git config user.email 设置本地身份，防止提交作者信息混乱。

实践中的问题与解决方案

1. Permission denied (publickey)

  • 现象：git push 或 ssh -T git@github.com 返回 Permission denied。

  • 根因：私钥未加载、公钥未添加到平台、或 SSH Config 中的 IdentityFile 路径错误。

  • 解决步骤：

    1. 确认 ~/.ssh/id_rsa_xxx.pub 已完整复制到 GitHub/Gitee 的 SSH Keys；
    2. 执行 ssh-add ~/.ssh/id_rsa_xxx 将私钥加入 ssh-agent；
    3. 检查 ~/.ssh/config 中 IdentityFile 使用绝对路径且文件存在。

2. Host 别名不匹配导致使用错误密钥

  • 现象：配置了多个 GitHub 账号，但 push 时总提示另一个账号无权限。

  • 根因：仓库的 remote URL 未使用对应 Host 别名，例如仍用 git@github.com 而不是 git@github_blog。

  • 解决步骤：

    1. 用 git remote -v 查看仓库 remote URL；
    2. 根据账号修改为 git@github_blog:username/repo.git 这类别名地址；
    3. 用 ssh -T git@github_blog 验证对应身份。

3. ssh-agent 未持久化，重启后失效

  • 现象：每次开机后第一次 push 都需要重新 ssh-add。

  • 根因：ssh-agent 默认不会自动加载私钥，重启后环境变量丢失。

  • 解决步骤：

    1. Windows 可配置 OpenSSH Authentication Agent 服务为自动启动；
    2. macOS 在 ~/.ssh/config 中设置 AddKeysToAgent yes 并启用钥匙串；
    3. Linux 可在 ~/.bashrc 或 ~/.zshrc 中配置 ssh-add 自动加载常用密钥。

4. 多个 GitHub 账号冲突

  • 现象：同一仓库 push 时，平台显示的作者不是期望账号。

  • 根因：SSH 认证只解决“谁能推送”，而提交作者由 user.name / user.email 决定；全局配置被错误使用。

  • 解决步骤：

    1. 清除全局 user.name 与 user.email；
    2. 在每个仓库内设置本地配置：
    3. 使用 git config user.email 核对当前仓库身份。

5. 企业内网 22 端口被屏蔽

  • 现象：ssh -T git@github.com 超时，切换 443 端口后仍失败。

  • 根因：防火墙仅允许 HTTPS 出站，或 DNS 解析被污染；~/.ssh/config 中 HostName 未改为 ssh.github.com。

  • 解决步骤：

    1. 在 ~/.ssh/config 中设置：
    2. 验证连通性：ssh -p 443 -T git@ssh.github.com；
    3. 若仍失败，尝试通过 HTTPS 代理或企业跳板机访问。

6. Windows 下配置文件权限过宽

  • 现象：SSH 提示 Bad permissions 并忽略 config 文件。

  • 根因：Windows 对 ~/.ssh/config 及私钥文件权限要求严格，若 Everyone 用户拥有读写权限则拒绝使用。

  • 解决步骤：

    1. 右键文件 → 属性 → 安全 → 高级 → 禁用继承；
    2. 删除非当前用户和 SYSTEM 的条目；
    3. 确保私钥文件权限为当前用户只读（约 600）。

7. 提交作者信息显示错误

  • 现象：GitHub/Gitee 上提交记录显示的是另一个用户名或灰色头像。

  • 根因：本地 user.email 与平台账号邮箱不匹配，或未设置 Git 的 no-reply 邮箱。

  • 解决步骤：

    1. 使用平台注册的邮箱作为 user.email；
    2. 或启用平台隐私邮箱（如 GitHub 的 xxx@users.noreply.github.com）；
    3. 历史错误提交可用 git commit --amend --author 或 git filter-repo 修正。

SSH 连接异常（提交失败）

Git 提交时报错：

ssh: connect to host github.com port 22: Connection timed out
fatal: Could not read from remote repository.

用以下三个命令测试，均无法连接

解决方法：

修改~/.ssh/config 配置，Port 改为 443，HostName 改为 ssh.github.com
