JVM 为什么同时保留解释器与 JIT？分层编译如何兼顾启动速度和峰值性能

发表于2025-10-08|更新于2026-09-28
|JavaJVM
|浏览量:

同一段字节码，在同一个 JVM 进程里，刚启动的第一秒和运行十分钟之后，性能可能相差一个数量级以上（常见现象，具体倍数随负载而定）。代码没有变，变的是执行方式：前者大部分时间跑在解释器里，后者已经逐步切换到 JIT 编译出的本地机器码。理解"解释器 + JIT"这套双引擎机制，是看懂 Java 启动曲线、预热行为、甚至一批诡异性能故障的前提。

本文属于知识总结类文章，结构为：概述 → 关键机制拆解（热点探测、分层编译、去优化、核心优化手段）→ 验证手段 → 故障实战 → 权衡与建议。文中涉及 HotSpot 内部机制的描述基于 64 位 HotSpot 的默认分层编译模式（JDK 8 及之后的主流形态），代码示例均已标注是真实字节码、源码机制的简化描述，还是纯示例代码；涉及数值的地方都给出自验方法，不把估算当实测。

一、为什么不是"只用解释器"或"只用编译器"

Java 源文件要变成机器指令，要经过两段编译：

  • 第一段（前端编译）：javac 把 .java 编译成 .class 字节码。javac 基本不做依赖运行信息的优化，只做少量确定性处理（编译期常量折叠、常量字符串拼接、泛型擦除等语法糖展开）。

  • 第二段（后端执行）：字节码在运行期由 JVM 执行引擎处理——先解释执行，热了再被 JIT 编译成机器码。

为什么第二段不干脆一步到位？因为两条极端路线都有硬伤：

  • 纯解释器：实现最简单、启动最快、内存最省，但每条字节码都有"取指—分发—执行"的固定开销，且完全不做跨指令优化（例如两次相邻的内存读取不会被合并）。跑得越久越吃亏。

  • 纯 AOT / 全量预编译：启动后全程跑机器码，但没有运行时画像（profile）可用——不知道哪个分支更常走、哪个虚方法只有一种实现、哪个对象从不逃逸。而 JIT 最强的那批优化恰恰依赖运行时数据。此外 Java 的动态特性（运行期加载类、反射、invokedynamic、动态代理）让"执行前编译一切"在通用场景下难以成立。

混合方案的收益可以粗略量化（理论分析）：设编译成本为 $C_{\text{jit}}$，解释执行单次耗时为 $T_{\text{interp}}$，编译后单次耗时为 $T_{\text{jit}}$，某段代码预计执行 $N$ 次，则编译划算的条件是：

$$
C_{\text{jit}} + N \times T_{\text{jit}} ;<; N \times T_{\text{interp}}
\quad\Longleftrightarrow\quad
N ;>; \frac{C_{\text{jit}}}{T_{\text{interp}} - T_{\text{jit}}}
$$

执行次数 $N$ 低于临界值 $N^*$ 时，编译是赔本买卖；超过之后，执行得越多，编译投资回报越高。OpenJDK 团队在自己的博客里也用类似的思路解释分层编译的动机：为一个只执行一次的方法花大量编译周期，等于"编译时间比执行时间还贵"。

由此自然推出 HotSpot 的形态：冷代码解释执行，热代码编译执行，"冷热"由运行时热点探测动态判定。这也解释了为什么 JVM 默认以 mixed mode（混合模式）运行——用 java -version 可以看到 mixed mode, sharing 字样；另外两个手工模式是 -Xint（强制纯解释，用于对照实验）和 -Xcomp（优先编译，解释器只在编译无法进行时兜底，通常只用于压测 JVM 自身）。

二、JVM 解释器：模板解释器

2.1 职责与执行模型

解释器负责逐条读取字节码指令，将其翻译成对应平台的本地操作并执行，同时维护运行时状态：Java 栈帧、局部变量表、操作数栈、程序计数器（PC）等。它不做任何投机优化，语义上严格贴近字节码定义，可以理解为整个执行体系的语义基准线。

2.2 模板解释器：查表跳转，而不是 switch-case

HotSpot 的解释器由模板解释器（Template Interpreter）实现。其机制可概括为（对 HotSpot 源码机制的简化描述）：JVM 启动时，依据 TemplateTable 为每一条字节码指令预生成一段本地机器码"模板"，并把各模板入口地址填入一张分发表（dispatch table）。运行期解释循环只做一件事：取当前字节码 → 查表跳转到对应模板 → 模板执行完毕后自带"取下一条字节码并跳转"的尾部逻辑。

与传统"一个大 switch-case 的字节码循环"相比，模板解释器把逐条指令的分支判断换成了一次间接跳转，减少了每条指令上的分支预测压力，同时模板本身是针对平台手写优化的汇编，这就是 HotSpot 解释器在同侪中较快的原因。JVM 还提供 -XX:+PrintInterpreter（诊断类参数）查看解释器实际生成的模板，有兴趣可以一试。顺带一提，HotSpot 内部还保留了一套 C++ 实现的字节码解释器（以及不依赖汇编的 Zero 解释器），用于无模板生成能力的平台或调试场景，但产品形态默认运行的就是模板解释器——这也是"HotSpot 解释器为什么快"的第一句答案：模板是针对平台手写的汇编，不是通用 C++ 分支循环。

需要诚实指出：模板解释器只是把"逐条分发"做到较快，并没有消除逐条分发的本质开销，也不会做跨指令优化——性能天花板仍然在 JIT 一侧。

2.3 解释器的不可替代角色

除了"启动快"，解释器在现代 HotSpot 里至少还有三个不可替代的职责：

  • 逃生门：JIT 敢做大量激进优化（投机内联、类型收紧），前提是"假设被打破时能全身而退"。退到哪里？退回解释执行（见第 3.5 节的去优化）。

  • 画像采集器：分层编译中，第 0 层和第 3 层的执行会持续收集方法调用次数、分支走向、虚方法类型分布等画像数据，供更高层级编译使用。

  • 兜底执行：被标记为"不可编译"的方法、编译尚未完成的方法、编译器整体被禁用（见故障 6.3）时的所有方法，都靠解释器维持运行。

一句话：解释器不是"低配替代品"，而是 JIT 激进优化的安全网——没有解释器兜底，JIT 不敢激进。

三、JIT 即时编译器

3.1 热点探测：识别"值得编译"的代码

JVM 不会盲目编译所有代码。热点探测（Hot Spot Detection）负责回答"哪些代码值得优化"，业界主要有两条路线：

  1. 基于采样的探测：周期性检查各线程的栈顶，某方法频繁出现在栈顶即判定为热点。实现简单、零侵入，但无法精确度量一个方法的热度，且容易被线程阻塞、锁等待等"停在栈顶"的场景干扰。Oracle JRockit 走的是这条路线（JRockit 干脆没有解释器）。

  2. 基于计数的探测：为每个方法（及代码块）维护计数器，统计执行次数，超过阈值即判定为热点并触发编译。精确、可解释，代价是每次执行都要维护计数器。

HotSpot 采用基于计数器的探测，并且沿用了这个项目名的由来思路：程序 80% 的执行时间往往花在 20% 的代码上，只编译那部分"热点（hot spot）"，性价比最高。

3.2 双计数器：方法调用计数器与回边计数器

HotSpot 为每个方法维护两类计数器（以下为机制的简化描述，阈值数值均为 64 位 HotSpot 的常见默认值，随版本与架构会变，文末给出实测命令）：

  • 方法调用计数器（invocation counter）：记录方法被调用的次数。它以"一次调用"为粒度增长——一个执行很久才返回的方法，在一次调用内只能让它 +1。

  • 回边计数器（back-edge counter）：记录方法内循环跳回循环头（back-edge）的次数，用于识别循环密集型热点。循环体每迭代一轮，回边计数就增长一次。

两者的触发条件不同：

  • 非分层模式（关闭分层编译时）：经典阈值由 -XX:CompileThreshold 控制，服务端模式默认 10000 次、客户端模式默认 1500 次（常见默认值）；回边阈值则按 CompileThreshold × OnStackReplacePercentage / 100 折算（客户端模式该比例约为 933，服务端约为 1400），超过即触发 OSR 编译。

  • 分层模式（默认）：CompileThreshold 不再生效，取而代之的是一组分层阈值，如 Tier2InvocationThreshold、Tier3InvocationThreshold、Tier3MinInvocationThreshold、Tier3BackEdgeThreshold、Tier4InvocationThreshold、Tier4BackEdgeThreshold 等（均为真实参数名）。以 x86-64 上的常见默认为例：Tier3InvocationThreshold 约为 2000、Tier4InvocationThreshold 约为 15000，同时还有配套的最小调用次数要求（MinInvocationThreshold）与回边阈值，并会按调用速率折算——速率越高，等效阈值越低，越早触发编译。具体数值随 JDK 版本和 CPU 架构变化明显，不要背数字，用下面的命令实测你机器上的值：

细心的读者会注意到回边阈值比调用阈值大一个数量级，这不是笔误：一次方法调用往往包含成百上千次循环回跳，若两个阈值同量级，任何带循环的方法都会瞬间触发编译，热点判定就失真了。调用计数刻画"被多少次请求需要"，回边计数刻画"单次调用内部有多耗"，两个量纲必须分开标定。

关于"热度衰减"的考证：不少资料（包括早期经典书籍）会提到方法调用计数器带半衰期衰减机制——长期不被调用的方法，计数器会周期性衰减，避免"历史热点"长期占用编译资源，对应参数 -XX:-UseCounterDecay 与半衰期参数 CounterHalfLifeTime（后者是 develop 级参数，正式版 JVM 不可调，默认 30 秒，衰减动作在 GC 时顺带进行）。需要修正的是：这套机制是非分层时代的设计，且已在现代 HotSpot 中逐步退场——UseCounterDecay 在 JDK 22 被标记 obsolete（JDK-8318480），CounterHalfLifeTime 随后也被移除（JDK-8340273）。分层编译下，热度判定由各层阈值与速率折算主导，不要再把"半衰期"当成可依赖的调优点。

3.3 OSR：栈上替换

双计数器并存还有一个工程原因：长循环问题。方法调用计数器以"一次调用"为粒度，如果热点位于一个长时间不返回的循环体里（空转等待、计算密集型长循环），只靠调用次数可能迟迟凑不够阈值——这次调用还没结束呢。此时由回边计数器兜底：循环每跳回循环头一次就累加计数，超阈值即触发 OSR（On-Stack Replacement，栈上替换） 编译。

OSR 与标准编译的区别在于替换对象：标准编译产物替换的是"方法的入口"，作用于下一次调用；OSR 编译产物只服务于"当前还在解释执行的栈帧"，在下一次回边时把解释帧就地切换成编译帧，循环剩余部分直接跑机器码，不必等方法自然返回。在编译日志里，OSR 编译任务以 % 标记区分（见第 5.1 节）。

其完整时序如下（示意图）：

sequenceDiagram
    autonumber
    participant I as 解释器
    participant Q as 编译队列
    participant C as JIT编译线程
    participant F as 正在执行的栈帧
    Note over I: 循环每跳回循环头一次，回边计数加一
    I->>Q: 回边计数超阈值，提交 OSR 编译任务
    I->>I: 不阻塞，继续解释执行后续迭代
    Q->>C: 后台异步编译该循环所在片段
    C-->>F: 编译完成，OSR 版本挂到方法上
    Note over F: 下一次回边时检查到可用版本
    F->>F: 栈上替换：解释帧就地切换为编译帧

3.4 分层编译：0~4 层的升降级

计数器命中后，JIT 并非一步到位生成最高质量机器码，而是采用分层编译（Tiered Compilation），JDK 8 起默认开启。共 5 个层级：

层级 执行方式 画像采集 定位
0 解释执行 部分（计数） 起点、逃生门
1 C1 编译，无画像 无 极小方法的终点，去优化后的稳妥去处
2 C1 编译，少量计数 有限 过渡层
3 C1 编译，全量画像 完整（分支、类型、虚方法） 为主层 4 采集画像
4 C2 编译 无（吃现成画像） 峰值性能所在

  • C1（客户端编译器）：编译快、优化保守，快速生效止血。

  • C2（服务端编译器）：编译慢但优化激进，依赖第 3 层采到的画像做投机优化，是长期运行的峰值来源。

典型路径是 0 → 3 → 4：先解释，热度起来后用 C1 全量画像版执行（比解释快得多，同时收集画像），画像成熟后再上 C2。C2 编译队列繁忙时可能先落到 1/2 层过渡；极小方法（如 getter）可能直接 0 → 1 就到头了——不值得为它上 C2。

flowchart TB
    T0["第 0 层：解释执行"] -->|"计数达到 Tier3 阈值"| T3["第 3 层：C1 全量画像"]
    T0 -.->|"极小方法，如 getter"| T1["第 1 层：C1 无画像快速版"]
    T3 -->|"画像成熟且达到 Tier4 阈值"| T4["第 4 层：C2 深度优化"]
    T3 -.->|"C2 队列繁忙时先落 1/2 层过渡"| T1
    T4 -.->|"假设失效：去优化"| T0

原文的简化模型仍然成立，把它放在这里对照：

flowchart LR
    A[解释执行<br/>Interpreter] -->|调用计数超阈值| B[C1 编译<br/>快速生效]
    B -->|热度继续升高| C[C2 编译<br/>深度优化]
    C -.->|假设失效时回退| A

几个与之配套的工程事实：

  • 编译是异步的。计数达标只是"提交编译任务"，真正的切换发生在编译完成之后（下一次调用命中新版本，或 OSR 在下一个回边点切换）。编译线程数由 -XX:CICompilerCount 控制（分层下会自动在 C1/C2 间分配，默认随 CPU 核数伸缩，通常至少为 2）；-Xbatch 可强制前台同步编译，用于实验而非生产。

  • 层级可以手动封顶。-XX:TieredStopAtLevel=1 只用 C1，常见于快速启动的短命进程（如构建工具、单测 JVM），用峰值损失换预热时间。

  • 为什么第 2 层存在：它是 C1 的"半画像"档位，画像采集比第 3 层便宜得多。当 C2 队列拥堵、方法被迫在 C1 层面多停留时，先用它保持尚可的执行速度，避免在大方法上长期背着全量画像的采集开销。

  • 编译产物（nmethod）存放在代码缓存（Code Cache）。64 位 HotSpot 分层模式下默认保留约 240MB（常见默认值），JDK 9 起默认分段管理（非方法段、C1 段、C2 段）。这个缓存会被填满，是故障 6.3 的伏笔。

  • 层级切换、编译产物安装都依托安全点（safepoint）机制协调，这也是 JVM 能保证"换代码不破坏执行一致性"的基础。

3.5 去优化：激进优化的"后悔药"

C2 的很多优化是投机性的：假设某虚方法只有一种实现（单态），就按直接调用编译并内联；假设某分支从不走进去，就把它裁掉。假设不成立时，JVM 必须有办法撤销已经装车的编译代码——这就是去优化（Deoptimization）。

什么时候发生（常见触发原因）：

  • 运行中加载了新类，打破"该调用点只有一种实现"的类层次分析（CHA）假设——动态代理、热部署、反射生成类是高发区；

  • 第 3 层类型画像之外的新类型第一次走到该调用点（超多态）；

  • 依赖的类被卸载或重定义；

  • 投机假设的哨兵检查失败（如编译时假定不会为 null、不会越界，运行时却在哨兵分支真的发生了）。

发生了什么、系统如何处理：编译代码里的假设点预先埋有罕见陷阱（uncommon trap）。假设被打破时，执行流进入陷阱，JVM 把该编译方法标记为 made not entrant（新调用不再进入编译版）；正在该方法编译帧里的线程，会在安全点被引导返回去优化入口，由运行时重建等价的解释器栈帧，从触发的字节码位置继续解释执行；随后解释器重新计数、重新画像，满足条件后再次编译。旧编译产物在没有任何线程引用后由代码缓存清扫回收，标记为 made zombie。如果同一个方法反复去优化，JVM 会将其标记为不可编译（日志中出现 made non-compilable），此后永久停留在解释执行——这是性能长期回退的典型来源（见故障 6.2）。

优化类别 典型技术 目标
调用优化 方法内联、去虚拟化 消除调用开销
内存优化 逃逸分析、标量替换 减少 GC、提升缓存
同步优化 锁消除、锁粗化 提升并发性能
控制流优化 概率导向分支优化、死代码消除 精简执行路径

数据流优化 循环外提、寄存器分配 提升 CPU 利用率

4.1 方法内联：一切优化的基石

内联把被调用方法的指令直接"复制"到调用点，消除栈帧创建、参数传递、返回值处理的开销；更重要的是，它把两个独立的方法体合并成一个编译单元，让常量传播、逃逸分析、死代码消除得以跨方法施展。可以说没有内联，后面一多半优化都会失效。

内联决策的主要约束（参数为真实参数名，默认值以常见版本为准）：

  • 大小限制：-XX:MaxInlineSize（默认 35 字节码）控制"不热"方法的内联上限；-XX:FreqInlineSize（x86-64 常见默认 325 字节码）控制热方法的内联上限；递归内联深度另有 MaxInlineLevel（默认 9）约束。

  • 虚方法分派：运行时画像显示调用点是单态（monomorphic）——只有一种实现——就可以内联（配合类型检查哨兵）；**双态（bimorphic）**可对两种类型做分支预测内联；**超多态（megamorphic）**则退回虚分派表调用，无法内联。

  • final/static/private 不是内联保证。一个常见误解是"加上 final 就能内联"。事实是：这些修饰符只是从语义上消除了部分虚分派的可能，是否内联仍取决于热度、方法大小与内联预算；反过来，非 final 的单态调用点同样能投机内联。判定依据永远是编译日志，不是修饰符。

为什么不无限内联：内联会放大代码体积，过大的方法体会拖累指令缓存命中、挤占代码缓存、拉长编译时间，反而降速。JIT 的内联预算本质上是"调用开销节省 vs 代码膨胀代价"的折中。

4.2 逃逸分析与标量替换（含一处常见讹误的考证）

逃逸分析（Escape Analysis）判断对象的作用域是否"逃出"当前方法或线程，HotSpot 的实现将逃逸程度分为三级：

逃逸级别 含义 可行的优化
NoEscape 仅在方法内使用，未被外部引用 标量替换（消除分配）
ArgEscape 作为参数传给其他方法，但未被长期持有或返回 通常仍需分配；无线程逃逸时同步仍可能消除
GlobalEscape 被全局引用、返回或存入静态字段 无法消除分配

逃逸分析的基本行为是分析对象的动态作用域：定义后若仅在被调用方使用且不存入长生命周期结构，属于方法逃逸的边界情形；若被赋值给类变量、实例字段或可被其他线程访问，则是线程逃逸，优化全部失效。

一处需要修正的常见讹误：很多文章（包括本文旧版）说逃逸分析让对象"在栈上分配"。就 HotSpot 而言，目前并没有把整个对象整体分配到虚拟机栈上的"真·栈上分配"实现；“栈上分配"实际是靠**标量替换（Scalar Replacement）**落地的——对象不再作为整体创建，其字段被拆散为若干局部变量，自然地存在于栈帧或寄存器里。术语上区分这两者，有助于解释为什么某些场景"看起来该优化却没优化”（例如对象太大、字段太多、数组长度运行期才确定时，标量替换往往放弃）。

相关开关：-XX:+DoEscapeAnalysis（默认开启，JDK 6u23 起）、-XX:+EliminateAllocations、-XX:+EliminateLocks。注意逃逸分析本身不跨方法、不跨编译单元，它的分析范围完全依赖内联撑开——内联失败，逃逸分析大概率失效，这是该优化的结构性边界。验证是否生效推荐用 JMH 的 -prof gc 观测分配速率（见 5.5 节），比看单个开关可靠。另外，逃逸分析本身并不免费：连接图构建与指针分析消耗编译时间，这也是它只在高层级（第 4 层）启用、对超大方法可能直接放弃分析的原因——优化决策同样要算收益。

4.3 锁消除与锁粗化

动态编译同步块时，JIT 借助逃逸分析判断锁对象是否只被当前线程访问。若是（NoEscape/ArgEscape 且无线程逃逸），同步可安全移除：

对应地，若逃逸分析认定对象发生线程逃逸（如作为 this 返回、存入集合），锁消除不会发生——这也是"局部变量加锁却没快起来"的常见解释。另一个方向是锁粗化（Lock Coarsening）：连续对同一对象反复加锁解锁（如循环里反复调 StringBuffer.append），JIT 会把锁范围合并扩大到整个循环外，减少加锁次数——以放大临界区为代价换锁操作开销，两个方向各有适用面。

4.4 循环优化

  • 循环展开：将循环体复制多次，减少循环控制（如 i++、条件判断、回边）开销。例如 for (int i = 0; i < 4; i++) 可能展开为 4 条独立语句。

  • 循环不变量外提：把循环体内不随迭代变化的计算移到循环外。

注意外提的前提是"该计算在循环内无副作用且不被循环体改变"，这依赖内联与别名分析；一旦循环体内有未知调用，JIT 会保守放弃外提。它还有一个容易出事的反面：对"每次迭代读一次普通字段"的写法，JIT 会把这个读取当作不变量外提出循环——这正是故障 6.4 的根源。

  • 关于"死循环消除"的准确表述：某些资料声称 JIT 会删除"无副作用且结果未使用"的循环，这个说法要谨慎对待。更准确的是两点：其一，循环结构在 C2 中会被规范化为带守卫的主循环（guard）加异常退出的尾循环（post-loop）形式；其二，JMM 之下，对普通字段的空转等待循环，读取被外提后确实可能"永远退不出去"，这是数据竞争下被允许的优化，不是 JVM 的 bug——修复责任在代码，见 6.4。

4.5 死代码消除与常量折叠

移除结果未被使用或不可达的代码。需要区分两层：

  • javac 层：if (false) { ... } 这种编译期常量条件在 javac 阶段就不会生成对应字节码（JLS 明确允许这种"条件编译"写法）；static final 编译期常量与常量表达式的折叠也在 javac 完成。

  • JIT 层：更常见于内联与常量传播之后——内联后实参恒定，分支被裁剪，死代码随之消亡。

4.6 分支的概率导向优化

这里也修正一个常见说法：JIT 并不能直接"控制" CPU 的分支预测器——那属于硬件行为。C2 真正做的是基于运行时画像的概率导向优化：为每个分支维护跳转频率（如 99% 走 if 分支），据此重排代码块布局让热路径连续、对概率极端的分支做投机裁剪（配合去优化哨兵兜底）、把异常处理等冷路径放到代码末尾。CPU 分支预测与指令缓存命中率的改善，是这些布局变化的间接收益。

5.5 用 JMH 验证"看不见"的优化

标量替换、锁消除这类优化没有直接的打印开关覆盖所有路径，推荐用 JMH（Java Microbenchmark Harness）的 -prof gc 分析器验证：正常堆分配在 JMH 报告里体现为 gc.alloc.rate.norm（每次操作的分配字节数）。若"看起来不逃逸的对象分配"被标量替换掉，该指标会显著下降乃至归零——这是可复现的观测方法，本文不给出具体数值，请以你机器上的实测为准。反过来，压测吞吐类结论必须用 JMH 或全链路压测并充分预热，否则测到的多半是解释执行阶段的失真数据。

六、故障实战

下面五个场景均按"现象 → 发生了什么 → 系统如何处理 → 恢复与预防"展开。除 6.1 引用的公开复盘案例外，均为机制层面的分析，不含编造的实测数据。

6.1 压测初期 P99 虚高：预热不足

  • 现象：服务刚启动就压测，P99 比稳定期高出数倍；持续跑一段时间后自行回落。

  • 发生了什么：三层因素叠加。其一，大量代码还停在 0 层解释执行，天然慢一个数量级；其二，编译线程与业务线程抢 CPU，大任务编译被频繁上下文切换，机器码"交付"得更晚；其三，编译任务排队（C2 队列繁忙时方法先落 1/2 层过渡），加上 GC 尚未进入稳态。

  • 系统如何处理：JVM 自动逐层升级，最终到达第 4 层峰值态，但这个过程需要真实流量喂出来。

  • 恢复与预防：压测前用接近真实的流量预热（常见做法 5~10 分钟起步，具体以吞吐曲线走平为准，这是经验值不是定值）；自动化流量网关按权重渐进放量。这里有一个被 Red Hat 工程师公开复盘过的真实案例：他们对 PetClinic 做预热测试，发现打开一个"不应影响行为"的日志参数后，预热时间从约 14 分钟缩到约 4 分钟——根因正是该参数的 I/O 让应用线程频繁挂起，反而让编译线程拿到了 CPU；最终解法是在预热期压低请求速率、再逐步加压，避免业务线程饿死编译线程。这个案例说明：预热期的并发度本身就是预热速度的变量，而不是与预热无关的配置。验证预热是否完成，可在压测环境临时挂上 -XX:+PrintCompilation 观察：当第 4 层编译的增速明显放缓、不再有新的大方法进入编译时，基本可判定 JIT 进入稳态；生产环境则以 JFR 指标与吞吐曲线走平作为信号。

6.2 频繁去优化：性能偶发回退与 made non-compilable

  • 现象：长稳压测中吞吐周期性小幅下跌又恢复；打开编译日志后看到大量 uncommon trap、made not entrant；极端时某方法直接 made non-compilable，吞吐再也没回到过峰值。

  • 发生了什么：C2 编译时的投机假设被运行期打破——最常见的是单态调用点突然出现新类型（动态代理逐个生成新类、热部署替换类、反射创建子类），编译代码被撤销。

  • 系统如何处理：偶发去优化是分层编译的正常代价：编译版标记 not entrant，在执行的线程安全点回退到解释器重新画像，随后重编译，吞吐短暂回落后恢复。但若同一方法反复去优化，JVM 会将其标记为不可编译，永久停留解释执行——回退不再有恢复路径。

  • 恢复与预防：少量 uncommon trap 不必干预；频繁发生时排查运行期类生成行为（热部署、无界动态代理、脚本引擎反复定义类），从源头收敛；对已被标记 non-compilable 的方法，确认是否在热路径上，必要时调整代码结构（减少对该调用点的类型多态）再观察。

6.3 运行数小时后吞吐断崖：代码缓存耗尽

  • 现象：进程平稳运行一段时间后性能阶梯式下滑，GC 日志正常，堆内存无压力；日志出现 CodeCache is full. Compiler has been disabled.（JVM 真实告警文案）。

  • 发生了什么：编译产物全部存放在代码缓存（64 位分层模式常见默认约 240MB）。大量动态生成代码——脚本引擎、Groovy、字节码框架、无界动态代理——会让编译产物持续增长直至填满缓存。

  • 系统如何处理：默认开启的代码缓存清扫（-XX:+UseCodeCacheFlushing）会回收长时间不活跃的编译产物腾出空间；一旦生成速度超过清扫速度，缓存告满，JVM 直接停用全部 JIT 编译器，新方法只能解释执行——性能从此断崖。

  • 恢复与预防：短期调大 -XX:ReservedCodeCacheSize；用 -Xlog:codecache 观察水位趋势；根治手段是给动态代码生成设上限（缓存脚本编译结果、复用代理类）。这个故障的特征是"堆没问题但系统变慢"，很容易被误判为 GC 或业务问题，看到该告警文案基本可以一锤定音。

  • 恢复与预防：跨线程可见性必须显式声明——volatile 字段、AtomicBoolean、锁或阻塞原语（park、队列取任务）。另外，"忙等"本身就该用阻塞等待替代，既修正确性又省 CPU。

6.5 C2 编译崩溃：hs_err 与 exclude 兜底（罕见）

  • 现象：进程突然消失，工作目录出现 hs_err_pid<pid>.log，错误帧指向 C2 编译线程（CompilerThread）。

  • 发生了什么：JIT 编译器自身缺陷或特定字节码模式/内在函数触发的边界问题。与解释执行不同，编译线程崩溃时 JVM 选择 fail-fast 直接终止——编译期的一致性状态不值得冒险维持。

  • 系统如何处理：hs_err 文件会记录崩溃线程、正在编译的方法（Current CompileTask）、寄存器与栈帧。

  • 恢复与预防：绝大多数 JIT 缺陷随 JDK update 版本修复，优先升级补丁版本；临时缓解可用 -XX:CompileCommand=exclude,<类名>::<方法名> 把肇事方法排除出编译（退回解释执行，用性能换稳定），或极端情况下 -XX:TieredStopAtLevel=1 只用 C1。这两者都是止血手段，不是终点。

七、设计权衡与实现边界

  • 为什么 C1、C2 两级而不是单级：单级高质量编译器意味着长预热（C2 首次编译慢）；单级低质量编译器意味着低峰值。两级结构让"快速生效"与"深度优化"解耦，且第 3 层的 C1 顺便承担画像采集，一举两得。

  • 为什么不做全量 AOT：核心是画像缺失与动态特性。作为对照，GraalVM Native Image 是现实的 AOT 路线：启动快、内存占用低，但受封闭世界假设约束（构建期必须枚举反射/动态代理配置），且多数负载下不做画像引导优化（PGO）时峰值一般低于充分预热的 C2。两条路线是不同取舍，不是简单替代。

  • 为什么不无限内联：见 4.1，代码膨胀的负面效应（指令缓存、代码缓存、编译时间）会反噬收益。

  • HotSpot 实现本身的不足（宁指出不足，不粉饰）：

    1. 没有真·栈上分配，逃逸分析的分配消除完全依赖标量替换，大对象与运行期定长数组难以覆盖；
    2. 逃逸分析不跨编译单元，命脉被内联拿捏，内联失败则整条优化链失效；
    3. 画像驱动的投机优化让性能与运行历史耦合——同一方法在不同负载下的编译形态不同，测试环境难以精确复现生产行为；
    4. 早期宣传的计数器半衰期机制已随版本演进退场，老书籍的相应章节不宜直接套用。

  • 编译线程数与各层阈值不建议跟风调整：CICompilerCount 与 Tier 阈值系列的默认组合经过了大量场景打磨，多数业务服务的收益来自预热和代码结构，而不是这些旋钮；确要调整，必须在同一负载下 A/B 复测，并确认调整后去优化行为没有恶化。

  • 适用边界：本文机制描述以 64 位 HotSpot 默认分层编译为准（JDK 8~21 为主）。OpenJ9、GraalVM JIT、Android ART 的热点探测与编译层级设计各不相同，结论不可平移；文中所有默认值请用 PrintFlagsFinal 在目标 JDK 上实测。

八、总结与建议

  • JVM 执行引擎 = 解释器（启动快、内存省、语义基准、JIT 的安全网）+ JIT（热代码高性能），由双计数器热点探测驱动、按 0~4 层分级升降。

  • 三条主线贯穿全文：热点探测（方法调用 + 回边双计数器、OSR 兜底长循环）→ 分层编译（C1 快速生效与 C2 深度优化的分工、编译队列与代码缓存）→ 核心优化（内联是基石，逃逸分析与锁消除依附于它，投机优化必然伴随去优化）。

  • 性能层面没有"免费的优化"：每一项 JIT 优化都有失效条件（内联有大小与多态边界、逃逸分析怕逃逸、外提怕副作用、投机假设怕新类型），失效时系统能自愈（去优化回解释），但自愈不无限（non-compilable 不可逆、代码缓存满编译器停摆）。

  • 实践清单：

    1. 压测与容量评估必须预热，并控制预热期并发度，别让业务线程饿死编译线程；
    2. 调优先看证据：-XX:+PrintCompilation、-XX:+PrintInlining（或 -Xlog:jit+compilation / -Xlog:jit+inlining）与 JMH -prof gc；
    3. 跨线程正确性永远显式声明（volatile/原子类/锁），不要赌 JIT 的行为；
    4. 长期运行且含动态代码生成的服务，把代码缓存水位纳入监控；
    5. 默认参数通常已是最优组合，改阈值前先用 PrintFlagsFinal 确认真实默认值，并 A/B 实测，而不是照抄文章数字——包括本文。
