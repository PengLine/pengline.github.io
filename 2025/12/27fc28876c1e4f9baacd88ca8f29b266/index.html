Mysql 各种索引详解和使用指南

发表于2025-12-07|更新于2026-09-06
|DBMySQL
|浏览量:

索引是一种数据结构，用于帮助我们在海量数据中快速定位目标行——它的作用类似书籍目录：没有目录只能逐页翻阅（全表扫描），有了目录便能按页码直达（索引查找）。索引在数据库层面以 B+ 树等结构组织，查询时沿树路径以 O(log N) 次磁盘 IO 完成定位。

阅读导览：
① 索引的物理形态——存储引擎如何组织索引文件，MyISAM 与 InnoDB 的本质差异；
② 索引分类全景——按结构（B+ 树 / Hash / 全文 / 空间）与按组织方式（聚簇 / 二级）两大维度；
③ 原理深挖——最左前缀为什么成立、覆盖索引与索引下推如何省 IO；
④ 失效场景与选择规则——哪些写法会让优化器弃用索引，如何量化区分度；
⑤ EXPLAIN 实战——type 访问类型金字塔与 Extra 关键标记的判读；
⑥ 索引设计清单——建与不建的边界、常见误区。

以下以 MySQL 8 为例说明（存储引擎默认为 InnoDB）：

索引详解

索引是一种特殊的文件(InnoDB数据表上的索引是表空间的一个组成部分)，它们包含着对数据表里所有记录的引用指针。

不同的存储引擎索引的结构也有区别：

  • InnoDB：数据与索引共同存放在表空间（独立表空间模式下每表一个 .ibd）。表按主键组织为聚簇索引——索引即数据、数据即索引，这一形态天然支撑行级锁与 MVCC 需要的数据页结构。

  • MyISAM：索引保存在独立的 .MYI 文件中，与数据文件 .MYD 分离——B+ 树索引的叶子节点不存数据，而是存储行在 .MYD 中的物理地址。

flowchart LR
    subgraph MyISAM[MyISAM：索引与数据分离]
        M1[.MYI B+ 树索引<br/>叶子存行地址] --> M2[.MYD 数据文件<br/>按地址定位行]
    end
    subgraph InnoDB[InnoDB：数据即索引]
        I1[聚簇索引 B+ 树<br/>叶子节点 = 数据页 完整行]
        I2[二级索引 B+ 树<br/>叶子存 索引键 + 主键] -->|回表| I1
    end

    style InnoDB fill:#e8f5e9,stroke:#4caf50

添加索引后 .MYI 文件增大，可见索引是单独存储的

NULL 与索引：InnoDB 二级索引允许同一列存在多个 NULL（NULL 之间互不相等，唯一索引也不阻止多行 NULL）；NULL 与空字符串 '' 是两种不同的值——NULL 表示“未知/缺失”，不参与 = / > / < 等普通比较，只能用 IS NULL / IS NOT NULL 判断，并影响 COUNT(col) 与基数统计。

优点：极大提高查询速度——把全表扫描的 O(N) 行访问，降为沿索引树的 O(log N) 次磁盘 IO。

缺点：

  • 写放大：对表执行 INSERT / UPDATE / DELETE 时，不仅要维护数据页，还要同步维护每一棵索引树（插入/删除索引项、可能触发页分裂），写入性能随索引数量线性下降；

  • 空间占用：索引需要额外磁盘空间——每个索引都是一棵独立的 B+ 树副本。

以 1000 条数据为例，占用空间对比图：

添加一个组合索引后，磁盘占用多了约 160 KB

组合索引包含的字段越少、字段类型越小，磁盘占用相应越少——索引体积与字段个数、字段长度正相关。

提示：删除索引后，InnoDB 表空间内被释放的页不会立刻归还操作系统，而是标记为可复用；需要执行 OPTIMIZE TABLE 或重建表（ALTER TABLE ... ENGINE=InnoDB）后空间才会物理收缩。

索引类型

先建立一张分类地图——索引并非只有一种形态，可以从数据结构、列的数量、数据组织方式三个维度理解：

flowchart TD
    T[MySQL 索引] --> D1[按数据结构]
    T --> D2[按列数量]
    T --> D3[按数据组织]

    D1 --> B[B+ 树<br/>InnoDB 主选结构<br/>等值 范围 排序]
    D1 --> H[Hash<br/>InnoDB 自适应哈希<br/>仅等值匹配]
    D1 --> F[全文索引<br/>倒排索引<br/>大文本关键词检索]
    D1 --> S[空间索引<br/>R-Tree<br/>地理坐标检索]

    D2 --> C1[单列索引]
    D2 --> C2[组合索引<br/>最左前缀规则]

    D3 --> PC[聚簇索引<br/>叶子节点 等于 数据行<br/>每表仅一个]
    D3 --> SC[二级索引<br/>叶子节点存 键值加主键<br/>查找需回表]

  • B+ 树索引：是一种平衡多路查找树，所有数据记录都存储在叶子节点，非叶子节点只存索引键值和指向下一级节点的指针。

  • Hash 索引 ：基于哈希表实现，对索引列计算哈希值，直接定位到数据位置。

  • 单列索引：即一个索引只包含单个列，一个表可以有多个单列索引

  • 组合索引：即一个索引包含多个列

  • 聚簇索引（聚集索引、主键索引）：以 InnoDB 作为存储引擎的表，表中的数据都会有一个主键，即使你不创建主键，系统也会帮你创建一个隐式的主键。

  • 非聚簇索引（辅助索引或二级索引）：以主键以外的列值作为键值构建的 B+ 树索引

B+ 树索引

B+Tree 是一种平衡多路查找树，所有数据记录都存储在叶子节点，非叶子节点只保存索引键值和指向下一级节点的指针。

叶子节点之间通过指针连接，形成有序链表，支持高效的范围查询（如 BETWEEN、>、<）和排序（ORDER BY）。

  • 支持等值查询（=）、范围查询、排序。

  • 查询复杂度为 O(log n)。

  • InnoDB 的主键索引（聚簇索引）就是 B+Tree。

B 树特征

  • 每个节点都存储key和data。

  • 所有节点带有指向记录的指针，在内部节点出现的索引项不会再出现在叶子节点中。

  • 所有叶子节点指针为null，都是没有通过指针连接的。

  • 对于在内部节点的数据，可直接得到，不必根据叶子节点来定位。

B+ 树特征

1.单一节点存储更多的元素，使得查询的IO次数更少。（树的高度较低）

2.所有查询都要查找到叶子节点，查询性能稳定。(非叶子节点存储索引，叶子节点存储数据)

3.所有叶子节点形成有序链表，便于范围查询。（叶子节点是链表结构（顺序连接存储数据））

B+ 树优势

  • 非叶子节点只存索引键：每层能容纳的键数远多于“键+数据”混存的传统 B 树。InnoDB 页默认 16KB（SHOW VARIABLES LIKE 'innodb_page_size'），一次磁盘 IO 恰好加载一页，页内二分定位后继续 IO 下一层；

  • 叶子节点按序串成链表：范围查询定位到起始页后，沿叶子链表顺序读取即可，无需再沿树回溯。需要说明：MySQL 8.0 中叶子页间为单向 next 指针串联（“双向链表”多见于教材对 B+ 树的通称，InnoDB 的实现是页内记录有序 + 页间单向链）；

  • 三层能存多少数据（以 bigint 主键 8 字节 + 页内指针 6 字节估算）：

    • 每页索引键数 ≈ 16 × 1024 / (8 + 6) ≈ 1170 个；
    • 叶子数据页按行均 1KB 计，每页约容纳 16 行；
    • 三层 B+ 树可承载 ≈ 1170 × 1170 × 16 ≈ 2190 万行——这正是“千万级表索引树高度仅 3 层”的由来：无论定位哪一行，都只需 3~4 次磁盘 IO。

  • 千万量级（MyISAM / InnoDB）表的索引树高度通常为 3~5 层，具体取决于索引键大小与行宽。

Hash 索引

基于哈希表实现，对索引列计算哈希值，直接定位到数据位置。

⚠️ 先澄清一个常见误区：InnoDB 不允许用户直接创建 HASH 索引——CREATE INDEX ... USING HASH 会被忽略并退化为 B+ 树。InnoDB 中真正的哈希结构是引擎内部的自适应哈希索引（Adaptive Hash Index）：由引擎监控热点查询后自动为 B+ 树部分页面构建哈希索引，命中即 O(1) 定位，无需人工干预（由 innodb_adaptive_hash_index 控制开关）。

本节讨论的 Hash 索引，在“可创建索引”语境下更贴近 MEMORY / NDB 引擎的实现：散列函数负责把键均匀打散，冲突机制采用链接法（类似 Java HashMap 的数组+链表，只是没有红黑树），一旦碰撞仍需顺序比较同桶内的多个键。

Hash索引是将索引键通过Hash运算之后，将 Hash运算结果的Hash值和所对应的行指针信息存放于一个Hash表中，由于不同索引键存在相同Hash值，所以即使取满足某个Hash键值的数据的记录条数，也无法从Hash索引中直接完成查询，还是要通过访问表中的实际数据进行相应的比较，并得到相应的结果。

  • 只支持等值查询（=、IN）。

  • 不支持范围查询、排序、前缀匹配（如 LIKE 'abc%'）。

  • 优化器不能使用 HASH 索引来加速 ORDER BY 操作。

  • 查询速度极快（O(1)），但冲突处理和哈希函数可能带来开销，所以不适合高重复值的列（如性别、状态等）。

和 BTree 的区别

  • Hash索引结构的特殊性，其检索效率非常高，索引的检索可以一次定位，不像B-Tree索引需要从根节点到枝节点，最后才能访问到页节点这样多次的IO访问，所以Hash索引的查询效率要远高于B-Tree索引。

  • 哈希索引只支持等值比较查询（＝、 IN 、<=>），不支持任何范围查询（因为经过Hash算法处理之后的Hash值大小关系，并不能保证和Hash运算前完全一样）；

  • Hash索引无法避免数据排序操作；

  • Hash索引不能利用部分索引键查询（不支持多列联合索引的最左匹配规则）；

  • 发生碰撞时仍需访问数据行逐一比对：哈希值相同的多个键必须回到数据行逐行比较才能确认结果，且桶内数据无序，无法利用页内有序性做范围过滤；

  • 如果有大量重复键值的情况下，哈希索引的效率会很低，因为存在哈希碰撞问题

全文索引

全文索引（FULLTEXT），是基于倒排索引（Inverted Index），将文档中每个词映射到包含该词的文档列表。

用于对大文本字段（如 TEXT、VARCHAR） 进行关键词搜索。适用 InnoDB（MySQL 5.6+）、MyISAM 存储引擎

  • 支持自然语言搜索、布尔搜索。

  • 不支持普通 WHERE 条件（如 LIKE）。

MySQL 原生全文索引对中文支持极差，因为中文没有天然的空格分隔，且每个汉字都是“字母数字字符”。

MySQL 不会按语义分词，如果使用 utf8mb4 字符集，每个汉字被视为一个独立的“词”。但由于 最小词长限制（默认 ≥3），单个汉字长度为 1，会被直接丢弃。所以最终就根据符号分隔了，没有语义检索效果。

分词原理和规则：

在建立和查询时会进行分词，但其分词机制相对简单，不依赖外部分词器（如中文常用的 jieba、IK 等），而是基于预定义的分隔符和停用词规则进行处理。

MySQL 全文索引的分词主要依据以下规则：

  • 以“非字母数字字符”作为分隔符

    • 默认将字母、数字、下划线（_）和美元符号（$） 视为“词字符”

    • 其他字符（如空格、标点、中文标点、换行符等）被当作分隔符，用于切分词语

      Hello, world! How are you? 会被分为：['Hello', 'world', 'How', 'are', 'you']

  • 最小词长限制

    • MyISAM 引擎：由系统变量 ft_min_word_len 控制（默认为 4）。

    • InnoDB 引擎：由 innodb_ft_min_token_size 控制（默认为 3）。

      小于该长度的词会被直接忽略，不会被索引。如果 ft_min_word_len=4，则 “the”、“a”、“is” 等短词不会被索引。

      修改该参数后，必须重建全文索引才能生效。

  • 停用词过滤

    • MySQL 内置一个停用词列表（如 “the”, “and”, “or”, “is” 等常见无意义词），这些词即使长度达标，也不会被索引。
    • 默认停用词表包含约 36 个英文单词（InnoDB）或 700+ 个（MyISAM）。可通过自定义停用词表覆盖默认行为。

如何让 MySQL 全文索引支持中文？

  1. 预处理文本，人工插入分隔符：在应用层对中文进行分词（如用 jieba），然后用空格或特殊符号连接

  2. 降低最小词长 + 接受单字匹配：设置 innodb_ft_min_token_size = 1，这样就能搜单字，但无法理解词组语义

空间索引

空间索引（SPATIAL）基于 R-Tree（一种多维空间索引结构）。用于地理空间数据类型（如 POINT、GEOMETRY）。

适用 MyISAM、InnoDB（MySQL 5.7+）存储引擎。要求列必须为 NOT NULL，且使用空间数据类型。

聚簇/主键索引

每张表只能拥有一个聚簇索引（行数据只有一种物理排列顺序）；而二级索引列上可以存在多个 NULL（见上文 NULL 说明）。

聚簇索引就是按照每张表的主键构造一棵 B+ 树，叶子节点存放的是整张表的行记录数据（也称数据页）。这个特性决定了 InnoDB 是索引组织表：数据本身就是索引的一部分，主键的物理顺序即数据的存储顺序。

聚集规则：有主键则定义主键索引为聚集索引；没有主键则选第一个不允许为NULL的唯一索引；还没有就使用innodb的内置rowid为聚集索引。 主键如果更改代价较高，故建表时要考虑自增ID不能频繁update这点，且最好有顺序（数字）。

优点：

  • 数据访问更快，因为聚簇索引将索引和数据保存在同一个B+树中，从聚簇索引中获取数据更快
  • 对主键的排序查找和范围查找非常快
  • 叶子节点即数据页，存储行记录的全部字段

缺点：

  • 插入速度严重依赖于插入顺序，按照主键的顺序插入是最快的方式，否则将会出现页分裂，严重影响性能。因此，对于InnoDB表，我们一般都会定义一个自增的ID列为主键

  • 更新主键的代价很高，因为将会导致被更新的行移动。因此，对于InnoDB表，一般定义主键为不可更改

  • 二级索引访问需要两次索引查找，第一次找到主键值，第二次根据主键值找到行数据。

查找原理：

注：主键默认即为聚簇索引；树的根页通常在缓冲池（Buffer Pool）中常驻，即上图“页 1”一般不产生磁盘 IO，真正的 IO 计数从第二层开始。

  1. 首先 找到 id=18 的键值，对应指针为p2，定位到页3。

  2. 将页3数据读入内存，找到索引键值18，拿到对应的指针，定位到页8（第一次IO）。

  3. 将页8数据读入内存，找到索引键值18，拿到符合的数据。（第二次IO，叶子节点数据都是链表顺序连接的）

  4. 将页8中数据遍历查找符合条件的。

  5. 根据页8的指针，读取页9数据到内存，继续遍历符合的数据，以此类推（第三次IO）。

最终我们找到满足条件的所有数据，总共 12 条记录：

(18,kl), (19,kl), (22,hj), (24,io), (25,vg) , (29,jk), (31,jk) , (33,rt) , (34,ty) , (35,yu) , (37,rt) , (39,rt) 。

非聚簇/非主键索引

又称辅助索引、二级索引、非聚集，是除主键以外的其他索引。它与聚簇索引的组织关系及“回表”路径可概括为：

flowchart LR
    subgraph PK[聚簇索引树]
        P1[根页] --> P2[内节点]
        P2 --> P3[叶子等于数据页<br/>存放整行记录]
    end
    subgraph SK[二级索引树]
        S1[根页] --> S2[内节点]
        S2 --> S3[叶子存放<br/>索引键 加 主键值]
    end
    S3 -->|① 先拿到主键值| Q[回表]
    Q -->|② 按主键再查一次聚簇索引| P3

在聚簇索引之上创建的索引称之为辅助索引，辅助索引访问数据总是需要二次查找（回表）。辅助索引叶子节点存储的不再是行的物理位置，而是主键值。

Innodb辅助索引的叶子节点并不包含行记录的全部数据，叶子节点除了包含键值外，还包含了相应行数据的聚簇索引键。以便于拿到该键值二次查询聚簇索引。

查找原理

通过辅助索引首先找到的是主键值，再通过主键值找到数据行的数据页，再通过数据页中的Page Directory找到数据行。

在叶子节点中，不再存储所有的数据了，存储的是键值和主键，如，叶子节点中的 x-y（索引键值 - 主键值）。

查找的流程跟聚集索引一样，最终找到主键后，需要再到聚集索引中查找具体对应的数据信息，此时又回到了聚集索引的查找流程。

组合索引

使用组合索引，需要遵守最左前缀原则：查询条件必须从最左边的列开始，才能有效利用索引。

例如：索引 (a, b, c) 可用于 WHERE a=1 AND b=2，但不能用于 WHERE b=2 或 WHERE c=3。

为什么最左前缀成立？ 这与 B+ 树的键值组织方式直接相关：组合索引的键按字典序排列——先按 a 排序，a 相同再按 b 排，b 也相同才轮到 c。因此只给 b、c 条件时，树中任意一层都无法用二分确定搜索范围（键的有序前缀缺失），索引便无从定位；反过来，WHERE a=1 AND c=5 能用索引完成 a 的等值定位，却无法继续约束 c（中间隔着 b），只能把 c 降级为叶子上的过滤条件。

但是在 Mysql 8中，在优化器做了大量优化，在符合场景的数据也可能会用到索引，具体参考：MySQL 8.0 新增功能函数和使用案例

  • where子句中使用最频繁的一列放在最左边，因为MySQL索引查询会遵循最左前缀匹配的原则，即最左优先，在检索数据时从联合索引的最左边开始匹配。

  • 将离散度高的列放前面，可以过滤更多的数据，使得扫描行数更少，过滤掉的数据更多。

覆盖索引

如果查询的所有列都在索引中，无需回表查询数据行，性能极高（从索引中就能够取得所需数据，不必从数据表中读取）。

SELECT id from orders WHERE status = 'PAID' – id 在索引中，无需再到叶子结点查询数据节点，称之为实现了索引覆盖。

避免了回表操作，减少I/O提高效率。MySQL 只能使用B+Tree索引做覆盖索引，因为只有B+树能存储索引列值。

  • 辅助索引不包含行数据的所有信息，故其大小远小于聚簇索引，因此可以减少大量的IO操作。

  • 索引覆盖只需要扫描一次索引树，不需要回表扫描聚簇索引树，所以性能比回表查询要高。

  • 索引中列值是按顺序存储的，索引覆盖能避免范围查询回表带来的大量随机IO操作。

    判断一条语句是否用到索引覆盖： explain 命令中的 Extra列中包含 Using index 就表示使用到了索引覆盖

索引下推

处理包含过滤条件的查询语句。是MySQL5.6推出来的一个查询优化方案，主要是减少数据库中不必要的数据读取和计算。

作用：本该在 server 层进行筛选的条件，下推到存储引擎层进行筛选判断，能有效减少回表（下推的前提是查询条件都是索引列）。

原理：在使用索引进行查询时，将查询的过滤条件也应用到索引查找过程中，以减少需要读取和处理的数据量，从而提高查询性能。

所以，应该尽可能的建立联合索引，而不是独立的索引。既可以节省空间，又可以提高查询效率（索引覆盖、索引下推）。

示例： select * from t_user where name like 'L%' and age = 17; 其中name 和age为一个联合索引

不用索引下推的执行过程：

第一步：利用索引找出name带’L’的数据行：LiLei、Lili、Lisa、Lucy 这四条索引数据第二步：再根据这四条索引数据 id 值，逐一进行回表扫描，从聚簇索引中找到相应的行数据，将找到的行数据返回给 server 层。第三步：在server层判断age = 17,进行筛选，最终只留下 Lucy 用户的数据信息。第四步：将符合条件的索引对应的 id 进行回表扫描，最终将找到的行数据返回给 server 层。

用索引下推的执行过程：

第一步：利用索引找出name带’L’的数据行：LiLei、Lili、Lisa、Lucy 这四条索引数据第二步：根据 age = 17 这个条件，对四条索引数据进行判断筛选，最终只留下 Lucy 用户的数据信息。（注意：这一步不是直接进行回表操作，而是根据 age = 17 这个条件，对四条索引数据进行判断筛选）第三步：将符合条件的索引对应的 id 进行回表扫描，最终将找到的行数据返回给 server 层。

8.0 索引优化

MySQL 8 对索引做了大量优化，具体参考：MySQL 8.0 新增功能函数和使用案例

  • 索引跳跃扫描（Index Skip Scan）：针对最左匹配原则的“解药”。联合索引 (gender, age) 上执行 WHERE age = 20 时，8.0 优化器会对前导列 gender 的每一个 distinct 值“跳跃”式地各搜一段 age 索引，相当于自动补全了前导列。使用前提很苛刻：前导列 distinct 数量必须少（如性别仅 2~3 个值），否则跳跃次数过多，优化器仍会放弃；

  • 隐藏索引（INVISIBLE）：索引被标记为不可见后优化器不会使用，但 DDL 仍持续维护——用于上线前无损验证“删掉该索引到底影响哪些查询”，确认无影响再真正 DROP，避免大表删除后又要重建的风险；

  • 降序索引（DESC）：8.0 起才支持真正倒序存储的索引。ORDER BY a DESC, b ASC 可直接精确匹配 INDEX (a DESC, b ASC)，不再依赖对正序索引的反向扫描（反向扫描无法利用部分优化，且此前版本根本不存在降序索引概念）；

  • 函数索引（Functional Index）：WHERE YEAR(create_time) = 2024 走不了普通索引，是因为每行的函数结果无法与索引键直接比较；8.0 允许 INDEX ((YEAR(create_time))) 把函数计算结果本身建成索引列，从根源上解决“函数导致失效”的问题（也支持表达式前缀）。

规则与失效

失效场景

什么情况下索引不会被命中？先用一张决策树快速自查，再逐个展开：

flowchart TD
    Q[一条 WHERE 查询] --> C1{条件命中<br/>索引列?}
    C1 -->|否| X1[只能全表扫描]
    C1 -->|是| C2{索引列上套了函数运算<br/>或发生隐式类型转换?}
    C2 -->|是| X2[索引失效<br/>改函数索引或改写条件]
    C2 -->|否| C3{OR 连接的条件中<br/>存在非索引列?}
    C3 -->|是| X3[整体失效<br/>改用 UNION 或全列建索引]
    C3 -->|否| C4{LIKE 以 % 开头?}
    C4 -->|是| X4[无法前缀匹配<br/>考虑覆盖索引或全文检索]
    C4 -->|否| C5{联合索引<br/>不满足最左前缀?}
    C5 -->|是| X5[多数场景不可用<br/>8.0 视情况 Skip Scan]
    C5 -->|否| C6{区分度过低<br/>命中行占比过高?}
    C6 -->|是| X6[优化器弃用索引<br/>全表扫描反而更优]
    C6 -->|否| D[命中索引]

  • 条件没有使用索引列：WHERE 中全是无索引列，优化器无索引可用，只能全表扫描；

  • OR 连接了非索引列条件：即使其中一个条件命中了索引，只要 OR 另一侧没有索引，整体也无法走索引。想让索引生效，要么给 OR 涉及的每个列都建索引，要么改写为 UNION 拼接多个单索引查询；

  • LIKE 以 % 开头：LIKE '%name' 的匹配起点不确定，无法利用键有序性做前缀定位（除非查询列全在索引中，走覆盖扫描）；LIKE 'name%' 属于范围查询，前缀部分可正常用索引；

  • 范围条件右侧的列失效：联合索引 (age, name) 上执行 WHERE age > 20 AND name = 'test'，age > 20 完成定位后，name 的有序性已被打破，无法继续约束；

  • 不等于（!= / <>）：语义是“排除少量值”，B+ 树无法直接表达“跳过某值”，通常退化为扫描后过滤。若被排除值占绝大多数、命中值极少且覆盖在索引中，优化器也可能选择索引扫描（8.0 代价估算更精细，但不能依赖此行为）；

  • 隐式类型转换：列是字符串而条件传了数字（或反之），MySQL 会先对列做函数式转换再比较，等于在索引列上套了函数——WHERE phone = 13800000000（phone 为 varchar）将无法使用索引，务必用引号包住条件值；

  • 索引列上做函数/运算：WHERE YEAR(create_time) = 2024、WHERE price * 0.9 > 100——索引键存的是原始值，无法与运算结果比较；MySQL 8.0 的解法是建函数索引；

  • NOT IN / NOT EXISTS：优化器通常改写为反连接（anti-join）执行，能否用索引取决于改写后的形态与代价评估，不存在“版本一刀切不支持”的说法；

  • IS NOT NULL：NULL 在 InnoDB 索引中按最小值排序存放，IS NOT NULL 可转为范围扫描，但命中占比过高时优化器仍会选择全表扫描；

  • 区分度过低：索引列取值极少（如 bool、tinyint 状态列）时，一个等值条件就会命中大量行，回表随机 IO 超过顺序扫描，优化器评估后主动弃用索引——这不是“索引坏了”，而是“不该用”。

选择与规则

是否需要建立索引、值得建立索引？哪些字段适合建立索引？

先厘清两个常被混淆的量化概念：

  • 区分度（cardinality ratio）：COUNT(DISTINCT col) / COUNT(*)，越接近 1 表示列上重复值越少，等值定位后剩余候选行越少，越适合建索引；

  • 命中占比（值的选择性）：某个查询条件下预计命中的行数占总行数的比例。MySQL 优化器并不机械套用“选择性公式”，而是通过成本模型估算两种方案的总代价——全表扫描的顺序 IO + 过滤代价，对比索引访问的树路径 IO + 回表随机 IO——选择代价更低的一方执行。

经验法则：当等值条件的命中占比超过 20%（如 WHERE status='x' 将命中表中 1/4 的行）时，回表随机 IO 往往已超过全表顺序扫描，此时全表扫描比走索引更快——这也是区分度过低的列（性别、状态）不该建索引的根本原因。

索引并不免费：它消耗磁盘空间，每次 DML 都要同步维护（插入/删除索引项，可能触发页分裂与合并），表结构 DDL 同样牵动索引。因此建索引前务必权衡读写比，谨慎选择。

  • 选择高区分度的列建索引（如用户ID，而非性别）。

  • 避免在索引列上使用函数或表达式，如 WHERE YEAR(create_time) = 2024 会导致索引失效。

  • 合理使用组合索引，遵循最左前缀原则。

  • 监控索引使用情况：通过 EXPLAIN 分析执行计划。

  • 避免过度索引：索引会占用空间，并降低 INSERT/UPDATE/DELETE 性能。

不适合建立索引的列：

  • tinyint 或用作标志的 int 列（如性别、状态）：取值个数太少，任何等值条件都会命中大量行（区分度低、命中占比高），回表反而慢于顺序扫描；

  • 更新频繁的字段。

  • 不会出现在where子句中的字段。

  • 数据可能为null或空或0的字段

  • 存储占用过大的，如：text，json

适合建立索引的列：

  • 字段离散度越高，越适合选作索引的关键字。如主键和唯一字段（主键索引自动创建）。

  • 很少更新的字段（因为也会牵连更新索引）。

  • 占用存储空间少的字段。

  • 存储空间固定的字段。

  • Where子句中经常使用的字段，分组字段、排序字段和多表连接字段（外键索引自动创建）。

  • 尽量使用联合索引（前缀）

最左匹配规则（联合索引）

  • 最左优先：以最左边列为起点，任意连续的前缀组合都能匹配上——索引 (a,b,c) 等效于 (a)、(a,b)、(a,b,c) 三组索引；跳过前导列的条件无法使用索引；

  • 顺序存储的必然结果：索引键先按最左列排序，再依次按后续列排序，所以只有连续前缀能保持有序性供二分定位；

  • 遇到范围查询即停止匹配：>、<、BETWEEN、LIKE 'x%' 出现后，当前列仍可用索引，但从它之后的列起有序性被打破，停止匹配。

因此，应把范围、模糊这类“不确定性”条件涉及的列放到组合索引的靠后位置，前面放等值条件列。例如 WHERE a = 1 AND c > 4 AND b = 2 配合索引 (a, b, c)——等值列 a、b 完整命中，范围列 c 恰好收尾，索引利用率最大化。

EXPLAIN 详解

EXPLAIN 是分析和优化 SQL 查询性能最重要、最常用的工具——它不真正执行查询，而是输出执行计划：优化器基于成本模型选定访问路径后，把每一步的访问方式、所用索引、预估行数完整呈现。读 EXPLAIN 的核心是抓两条主线：访问类型（type）在金字塔上走多深、额外操作（Extra）是否需要回表/排序/建临时表。

标注约定：★★★ 为最重要，★★ 次之，★ 供参考。以下为 EXPLAIN 输出中各列的含义：

type（访问类型，★★★ 最重要）

访问类型描述 MySQL 如何读取数据，按性能从优到劣恰好构成一条“金字塔”，越往上越快、越往下越慢：

flowchart TD
    A[system 系统表<br/>仅一行] --> B[const 主键或唯一索引等值<br/>最多一行]
    B --> C[eq_ref 多表 JOIN<br/>按唯一索引逐行匹配]
    C --> D[ref 非唯一索引等值<br/>可能多行]
    D --> E[range 索引范围扫描<br/>BETWEEN IN 大于 小于]
    E --> F[index 全索引扫描<br/>遍历整棵索引树]
    F --> G[ALL 全表扫描<br/>性能最差 重点优化]

（图中自上而下逐级退化，以下逐个说明。）

  • 最优级别

    • system：表只有一行记录（系统表）

    • const：通过主键或唯一索引一次就找到

      SELECT * FROM users WHERE id = 1;

  • 优秀级别

    • eq_ref：唯一索引扫描，通常用于多表 JOIN 之间的外键索引

      SELECT * FROM users u JOIN orders o ON u.id = o.user_id;

  • 良好级别

    • ref：非唯一索引扫描，返回匹配某个值的所有行

      EXPLAIN SELECT * FROM users WHERE phone_number = '14524043463'

    • fulltext：全文索引扫描

    • ref_or_null：类似 ref，但包含 NULL 值搜索

  • 一般级别

    • range：索引范围扫描（BETWEEN、IN、>、< 等）

      EXPLAIN SELECT * FROM users WHERE id BETWEEN 1997867665955237888 AND 1997869822548984078;

  • 需要优化

    • index：全索引扫描（读取整个索引）

    • ALL：全表扫描（不使用索引，性能最差，需要优化）

Extra（额外信息，★★★ 最重要）

提供额外的执行信息：

  • Using index：覆盖索引直接返回结果id，无需回表其他非索引字段。

  • Using index condition：索引条件下推（ICP）, 将 WHERE 条件中索引列的过滤下推到存储引擎层执行。可以减少回表次数，提高查询性能

需要关注和优化的问题：

  • Using where：在存储引擎检索后再过滤相关数据

  • Using temporary：使用临时表（可能需要优化）

    优化排序后

  • Using filesort：使用文件排序（需要优化）

  • Using join buffer：使用连接缓冲区

    多表连接查询，如果type = ALL ，这是因为相关表缺少外键连接索引，则使用连接缓冲区。

    有外键索引的 type = ref，并显示具体的索引名信息。

ref（用到的索引列，★★）

显示与索引进行比较的列或常量，判断是否真正“用对”了索引：

  • const：与常量比较（如 WHERE id = 1 中的 1）；

  • 列名：与另一张表的列比较（常见于 join 条件）；

  • func：比较的是函数结果，常伴随隐式类型转换出现——此时要警惕索引失效。

select_type（查询类型，★★）

  • SIMPLE：简单 SELECT，不使用 UNION 或子查询

  • PRIMARY：查询中最外层的 SELECT

  • SUBQUERY：子查询中的第一个 SELECT

  • DERIVED：派生表（FROM 子句中的子查询）

  • UNION：UNION 中的第二个或后续 SELECT

  • UNION RESULT：UNION 的结果

  • DEPENDENT SUBQUERY：依赖外部查询的子查询

rows（预估扫描行数，★★）

MySQL 基于统计信息预估需要扫描的行数（值越小越好）。注意它是“预估值”，真实执行可能偏差较大——当 rows 与实际行数数量级明显不符时，通常是统计信息过期（执行 ANALYZE TABLE 刷新），或过滤条件集中在非索引列上。

filtered（过滤比例，★）

存储引擎层返回的数据经过服务层过滤后剩余的比例（百分比值，越大越好）

联合判读：rows × filtered% ≈ 最终处理的行数。若某一步 rows = 100 万而 filtered = 1%，说明大量行被取出后才被过滤，通常意味着缺少更精确的索引，需要在该过滤列（或联合索引列）上做文章。

id（查询标识符）

SELECT 查询的序列号

SELECT * FROM users WHERE id IN (SELECT user_id FROM orders); 子查询的 id 会不同

  • id 相同：按顺序执行

  • id 不同：id 值越大，优先级越高，越先执行

  • id 为 NULL：表示 UNION 结果或子查询

key（实际用的索引）

查询实际使用的索引。如果为 NULL，表示没有使用索引

key_len（索引长度）

使用的索引字节数。可判断是否使用了索引的全部部分

复合索引 (name, age)， 如果只用到 name，key_len 会较短

possible_keys（可能用的索引）

查询可能使用的索引列表，如果为 NULL，考虑添加合适的索引

table（访问的表）

显示查询涉及的表名。可能是实际表名、别名或 <derivedN>、<unionM,N> 等

索引设计清单与常见误区

设计清单（Checklist）

评审一条 SQL 或设计一张表时，按以下顺序自查：

  • 先看 EXPLAIN：type 是否达到 range 及以上？Extra 是否出现 Using filesort / Using temporary？

  • 单表等值查询：高频 WHERE 列组成联合索引，等值列在前、范围列在后；

  • 排序 / 分组：ORDER BY / GROUP BY 列尽量纳入索引（键顺序需与排序方向一致才能消除 filesort）；

  • 多表 JOIN：被驱动表的连接列必须有索引（目标是 type 达 ref 及以上），且两侧列的类型、字符集、排序规则完全一致；

  • 覆盖优先：高频查询的 SELECT 列尽量并入联合索引，争取 Extra = Using index，彻底消除回表；

  • 区分度把关：先用 COUNT(DISTINCT col) / COUNT(*) 验证，区分度过低的列不要单独建索引；

  • 控制数量：OLTP 表单表索引控制在 5 个以内，写多读少的表更要克制；

  • 统一类型：关联字段与条件值的类型必须一致，避免隐式类型转换悄悄杀死索引；

  • 定期体检：关注 Handler_read_rnd_next 突增与慢查询日志，借助 performance_schema 统计索引使用率，长期零使用的索引先置 INVISIBLE 验证再下线。

常见误区

  1. “索引越多越好”——每个索引都拖慢写入并占用磁盘，多列场景应优先合并为联合索引，而非各建单列索引；

  2. “字段套函数没事”——WHERE YEAR(create_time) = 2024 会隐式放弃索引，应改写为 create_time BETWEEN '2024-01-01' AND '2024-12-31' 或建函数索引；

  3. “低区分度列也能建索引”——性别、状态类列的等值条件命中行占比过高，走索引比全表扫描更慢；

  4. “OR 只要一边有索引就行”——另一边没有索引时整体仍会全表扫描，应改写为 UNION；

  5. “NULL 不能建索引”——InnoDB 二级索引完全支持 NULL（且允许多个），真正要担心的是 NULL 占比过高导致过滤效果差、统计失真；

  6. “删索引立刻释放空间”——InnoDB 表空间需执行 OPTIMIZE TABLE 或重建表才会物理收缩（见文首实测提示）。

一处经典实战复盘

某订单表执行 WHERE merchant_id = ? AND create_time BETWEEN ? AND ? ORDER BY create_time DESC LIMIT 20，起初只有主键索引，慢查询耗时 2s+。逐项诊断：

  1. EXPLAIN 显示 type = ALL、Extra = Using filesort——全表扫描 + 额外排序；
  2. 加联合索引 (merchant_id, create_time DESC)：等值 + 范围完整命中，ORDER BY 也由索引天然完成，filesort 消失；
  3. 再把高频统计语句的 SELECT 列并入索引，实现覆盖扫描；最终耗时降至毫秒级。

这则案例印证了本文的主线：结构决定访问方式，访问方式决定性能——SQL 调优从来不是“加个索引碰运气”，而是先读懂 EXPLAIN 揭示的访问路径，再反推缺失的索引结构。更多系统级调优手段（配置参数、刷盘策略、慢查询治理等）可继续阅读本站 DB 目录的姊妹篇《MySQL 数据库性能全面优化方案》。
