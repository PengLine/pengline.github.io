Elasticsearch 深度分页的陷阱与最优解

核心问题：在数据量达到千万甚至亿级时，Elasticsearch（以下简称 ES）往往是首选。但在分页场景下，ES 的 from/size 机制存在一个毁灭性的陷阱：它不是“跳过前 N 条”，而是“取出前 N+M 条再丢弃前 N 条”。

解决思路：从偏移量思维切换到游标思维（search_after），用排序值代替偏移量，配合 PIT 保证翻页一致性。

基础分页：from / size（新手陷阱）

这是 ES 最直观的分页方式，类似于 SQL 的 LIMIT offset, size。

from + size 分页方式的原理相对简单。当执行一个搜索查询并指定了 from 和 size 参数时，Elasticsearch 会进行以下步骤：

  1. 分发查询：Elasticsearch会将查询请求分发到所有相关的分片上。

  2. 查询分片：每个分片都会执行查询，并返回前 from + size 条符合条件的文档（但实际上只会用到最后的 size 条）。

  3. 合并和排序：协调节点（通常是执行搜索的Elasticsearch节点）会收集所有分片返回的结果，将它们合并成一个全局的结果集，并根据查询中指定的排序规则进行排序。

  4. 截断和返回：协调节点会从排序后的结果集中截取从 from 位置开始的 size 条记录，并将它们返回给客户端。

由于 from + size 需要合并和排序所有分片返回的结果，因此当 from 值很大时，这个过程可能变得非常慢，因为需要处理大量数据。

致命缺陷：深度分页下协调节点内存爆炸

指标 第 1 页（from=0） 第 100 页（from=990） 第 10000 页（from=99990）
每个分片取回 10 条 1000 条 100000 条
3个分片总计 30 条 3000 条 300000 条
协调节点内存 极低 几 MB 几百 MB ~ GB 级
网络开销 极小 中等 极大（频繁 GC 甚至 OOM）

根本原因：ES 无法在分片级别知道全局排序的第 990 条在哪，所以每个分片必须把所有可能的数据（前 990+10 条）全部送到协调节点，由协调节点做全局归并排序。

默认保护机制：max_result_window

ES 默认设置 index.max_result_window = 10000，意味着 from + size 不能超过 10000。

作用：防止无意识的深度分页打崩集群。

千万别轻易调大这个值！ 调大意味着允许更深的分页，会极大增加协调节点的内存压力。如果必须随机跳页，请结合业务限制最大可访问页数。

优化方案：search_after（游标分页）

search_after 是 ES 官方推荐的深度分页解决方案，其核心思想与 Redis 的 ZREVRANGEBYSCORE 完全一致：用排序值代替偏移量。

  1. 首次查询：正常的 from=0, size=10，并记录最后一条数据的排序字段值。

  2. 后续查询：使用 search_after 传入上一页最后的排序值，ES 直接定位到该值之后的数据。

游标持久化：Point In Time（PIT）

使用 search_after 时有一个隐藏问题：索引在查询过程中可能发生变化（新增/删除/更新），导致 search_after 的排序值指向的数据发生变化，进而出现数据重复或遗漏。

解决方案：在查询前创建一个 Point In Time（PIT），相当于给索引拍了一张“快照”，确保整个翻页过程中数据视图一致。

PIT 生命周期管理（生产必读）

PIT 并不是创建后就可以“放养”的资源，它有以下三个生产级注意事项：

注意点 说明 规避方式
keep_alive 需持续续期 PIT 有存活时间，超时后自动失效，已持有的游标将无法继续翻页 每次翻页请求都带上 keep_alive（如 5m）实现“滑动续期”；长任务则周期性地刷新 POST /_pit?keep_alive=5m
open PIT 数量有上限 每个节点默认最多同时打开 500 个 PIT（search.max_open_pit_contexts），超限后创建新 PIT 会报错 用完立即 DELETE /_pit；后端对“翻页会话”做超时回收
PIT 会固定 segment 不被回收 这是最隐蔽的磁盘陷阱：PIT 存在期间，其依赖的 Lucene segment 会被固定（pin）住，即使索引滚动删除旧数据，这些 segment 占用的磁盘空间也不会释放 翻页会话务必短平快（秒级到分钟级）；大批量导出时分段批量 DELETE，避免长时间持有一个 PIT

常见事故还原：业务方开启了一个 keep_alive=1h 的 PIT 后忘记释放，索引侧持续写入触发段合并与滚动，数小时后 Lucene 报告 磁盘空间不足——根因正是被 PIT 固定的 segment 无法回收。排查手段：GET /_nodes/stats 查看 search.open_contexts 字段，该值等于当前所有节点打开的 PIT 总数，若长期居高不下即可锁定泄漏点。

替代方案：scroll（滚动查询，已过时）

scroll 是 ES 早期提供的深度分页方案，适用于大量数据的批量导出（如 ETL），不适用于实时用户交互。

特性 scroll search_after
快照 创建时生成完整快照 依赖 PIT（可选）
内存占用 高（保留上下文快照） 低（无状态游标）
排序一致性 强一致 PIT 保证一致
适用场景 数据导出、全量遍历 实时滚动加载
ES 官方态度 推荐仅用于导出，不推荐用于分页 官方推荐首选

注意：ES 7.x+ 中，scroll 的 search_type=scan 已被弃用。新的导出场景请使用 search_after 配合 PIT。

最佳实践总结

核心原则：能用 search_after 就不用 from/size，能加 PIT 就加 PIT，永远不把 max_result_window 调大到 10000 以上。

业务场景选型矩阵

业务场景 推荐方案 理由
C 端 App 消息列表 search_after + PIT 无限下拉，性能恒定，体验最佳
后台管理列表（含跳页） from/size + 限制最大页数（前 100 页） 用户通常不看深页，限制保护集群
数据导出（全量同步） search_after + PIT + 循环 替代 scroll，无状态，易恢复
实时监控/日志查看 search_after + PIT 时间线滚动，天然适合

排序字段设计的黄金法则

使用 search_after 时，排序字段必须保证全局唯一，否则会出现数据跳跃。

  • 推荐方案：[时间戳, 文档ID] 组合排序。

  • 避免使用：只有 score 或只有 timestamp（当有大量相同时间戳时）。

MySQL vs Redis vs Elasticsearch

对比维度 MySQL Redis ZSET Elasticsearch
深度分页方案 WHERE id > last_id ZREVRANGEBYSCORE search_after
随机跳页支持 支持（但性能差） 不支持（需限制） 支持（但有限制）
数据量级 亿级（磁盘） 千万级（内存） 十亿级（分布式）
排序字段要求 最好为主键或唯一索引 Score 必须复合（处理同分） Sort 必须唯一（加 tiebreaker）
一致性保证 事务隔离级别 无（实时数据） PIT 快照
选型结论 事务性业务主库 热数据 TopN 缓存 全文搜索与分析

Elasticsearch 的深度分页是一个典型“分布式系统比单机更难”的问题。search_after 本质上是将“我只要第 N 条”的随机访问问题，转化为“我要排在 X 之后的数据”的顺序访问问题——这是所有数据库解决深度分页的终极哲学。
