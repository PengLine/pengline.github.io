Redis 常见数据结构和数据类型

发表于2025-12-07|更新于2026-09-06
|DBRedis
|浏览量:

Redis 的存储体系可以拆成三个层次来理解——类型（Type） 是用户看到的样子，数据结构 是内存里的真实形态，编码（Encoding） 是连接二者的适配器。理解这套“一变多态”的模型，是读懂全文的前提：

三个易混淆概念先厘清（面试高频）：

  • 数据类型（Type）：用户通过命令看到的逻辑类型——String / List / Hash / Set / ZSet / Stream 等，用 TYPE key 查看；
  • 数据结构：底层物理存储结构——SDS、ziplist、listpack、quicklist、dict、intset、skiplist 等，由 Redis 内部自动选择；
  • 编码（Encoding）：连接二者的“适配器”，同一类型在不同规模/内容下会切换不同编码——用 OBJECT ENCODING key 查看，是排查内存问题的第一把钥匙。

Redis 的对象模型：type / encoding / ptr

Redis 中每个键值对象都是一个 redisObject，它用“逻辑类型 + 编码 + 指针”三个字段解耦了用户视图与物理实现：

flowchart TD
    K[redisObject 对象] --> T[type 字段
String / Hash / List / Set / ZSet]
    K --> E[encoding 字段
int / embstr / raw / listpack / skiplist ...]
    K --> P[ptr 指针]
    E -->|决定创建/切换| D[底层数据结构
SDS / dict / quicklist / intset ...]
    T -.->|不直接绑定| D

    style D fill:#e8f5e9,stroke:#4caf50

图中隐含的设计思想是 “一变多态”：同一个 String 类型，可以是一个 8 字节整数（int 编码）、一段 ≤ 44 字节的短字符串（embstr），也可以是一个巨型字节数组（raw）；数据规模增长时编码自动升级、并只升不降（除非重建对象）。后文将逐一展开每种结构的原理与切换规则。

数据结构

底层结构 描述 对应上层类型
SDS (Simple Dynamic String) 动态字符串：记录长度与容量、空间预分配、二进制安全、长度 O(1)。 String
linkedlist 双向链表：节点分散、内存不连续，每个节点指针开销大。 List（历史版本，已弃用）
ziplist 压缩列表：内存连续、节省空间，但存在连锁更新的极端风险。 List / Hash / ZSet（7.0 前小数据）
quicklist 双向链表 + 紧凑段的结合体，节点内是 ziplist / listpack。 List（3.2+）
listpack 紧凑列表：ziplist 的继任者，无连锁更新、内存更省。 List / Hash / ZSet（7.0+ 小数据）
dict 哈希表：SipHash 散列 + 拉链法 + 渐进式 rehash。 Hash / Set / ZSet / 全局键空间
intset 整数集合：升序数组 + 二分查找，插入越界时整体升级。 Set（全整数且数量少）
skiplist 跳表：多层索引链表，查找 O(log N)，范围查询友好。 ZSet（数据多时，与 dict 配合）
rax（基数树） 压缩前缀树：对高重合前缀的顺序 ID 极为友好。 Stream

注：Redis 7.0 引入 listpack 逐渐替代 ziplist，以解决 ziplist 在极端情况下的连锁更新问题；3.2 之前 List 曾直接使用 ziplist 作为整表编码，3.2 起仅作为 quicklist 的节点内部结构。

动态字符串（SDS）

String 类型的主要底层实现：当值是不可解析为整数的字符串时，Redis 都以 SDS 承载字节内容。

  • 兼容 C 字符串，但更高效。

  • 记录长度（len）和可用空间（alloc），避免频繁重分配。

  • 二进制安全（可存储任意字节数据）。

  • 以 O(1) 时间复杂度获取字符串长度。

双向链表（linkedlist）

List 类型最早的底层实现之一（Redis 3.2 之前与 ziplist 按元素规模二选一），3.2 起被 quicklist 取代。

  • 每个节点包含前驱和后继指针。

  • 支持 O(1) 头尾插入/删除。

  • 内存开销较大（每个节点有额外指针）。

哈希表（dict）

当元素较多时，Hash 类型与 Set 类型都会采用哈希表编码（hashtable）。

  • 平均 O(1) 的查找、插入、删除（哈希冲突严重时退化 O(N)）；

  • 使用拉链法解决冲突：每个桶（bucket）挂一条链表，新节点头插；

  • 通过渐进式 rehash 完成扩容/缩容，全程不阻塞主线程。

渐进式 rehash 的底层机制：dict 内部同时维护两张哈希表 ht[0] 与 ht[1]。当负载因子触发阈值时，ht[1] 先申请新空间，随后把迁移动作打散到每一次增删改查中——rehashidx 游标每处理一个命令就向后推进一个桶，全部迁完后交换 ht[0]/ht[1] 指针并释放旧表。

flowchart LR
    A[ht0 负载因子超阈值] -->|申请 2 倍容量
rehashidx 置 0| B[ht1 新表就绪]
    B --> C[每次增删改查
顺带迁移一个桶]
    C --> D[新写入只进 ht1
ht0 只减不增]
    D --> E[迁移完成
交换指针 释放旧表]

触发条件与工程注意：

场景 条件 说明
扩容 负载因子（used/size）≥ 1 无 BGSAVE/BGREWRITEAOF 子进程时；有子进程时阈值放宽到 ≥ 5，避免 rehash 与 COW 叠加导致内存翻倍
缩容 负载因子 < 0.1 元素大量删除后自动收缩，释放内存

实践提示：查询键时会先查 ht[0]、未命中再查 ht[1]，所以 rehash 中途不会漏数据；但 rehash 期间内存峰值 = 新旧两表之和，超大 Hash 的扩容瞬间可能吃掉大量内存——这是“大 Hash 键”需要拆分（如按业务字段拆小 Hash）的底层原因之一。

压缩列表（ziplist）

曾用于小规模的 List / Hash / ZSet（Redis 7.0 之前），是 listpack 的前身。

  • 连续内存存储，节省内存。

  • 适合存储少量、小体积的元素。

  • 插入/删除可能需要内存重分配（O(N)）。

历史触发条件（Redis 7.0 之前各类型使用 ziplist 时的默认配置；现代版本由 listpack 及对应 *-max-listpack-* 参数接管）：

  • List 元素数量 ≤ 512 且每个元素大小 ≤ 64 字节（Redis 3.2 之前，受 list-max-ziplist-size 控制）；

  • Hash 字段数 ≤ 512 且所有 field/value 长度 ≤ 64 字节（受 hash-max-ziplist-entries / hash-max-ziplist-value 控制）；

  • ZSet 成员数 ≤ 128 且成员长度 ≤ 64 字节（受 zset-max-ziplist-entries / zset-max-ziplist-value 控制）。

ziplist 的致命缺陷——连锁更新（Cascade Update）：

ziplist 的每个条目都要用 prevlen 字段记录前一个条目占用的字节数（小于 254 字节用 1 字节记录，否则用 5 字节）。当某个条目被修改、长度膨胀到 254 字节以上时，它的 prevlen 从 1 字节变为 5 字节，会挤压后续条目；后续条目若也因此越过 254 字节阈值，又会继续挤压下下个条目……形成链式反应，最坏情况下单次插入的时间复杂度退化为 O(N²)，主线程可能被拖入秒级卡顿。

触发连锁更新的数据特征：大量长度恰好位于 253 ~ 254 字节临界附近的条目。这类数据平时极少见，但一旦出现（如批量导入长度雷同的日志片段），Redis 会出现难以解释的写延迟毛刺——这正是 Redis 7.0 引入 listpack 取代 ziplist 的直接原因。

快速列表（quicklist）

Redis 3.2+ 中 List 的底层实现。由 ziplist（或 Redis 7.0+ 的 listpack）组成的双向链表。

  • 结合了链表的灵活性和 ziplist 的内存效率。

  • 避免单个 ziplist 过大导致的内存重分配开销。

紧凑列表（listpack）

替代 ziplist，用于 List、Hash、ZSet 等的小数据编码。

  • 比 ziplist 更节省内存。

  • 解决 ziplist 的连锁更新问题（修改一个 entry 可能导致后续所有 entry 偏移变化）。

  • 设计更简单、安全。

跳跃表（skiplist）

Sorted Set（ZSet）的底层实现之一（与 dict 配合）。

  • 有序结构，支持范围查询（如 ZRANGE）。

  • 平均 O(log N) 的查找、插入、删除。

  • 比平衡树实现简单，且支持并发优化。

  • 配合 dict：ZSet 同时维护一个 dict 用于 O(1) 查找 score。

整数集合（intset）

当 Set 中所有成员都是整数且数量不超过 set-max-intset-entries（默认 512）时使用。

  • 连续内存存储，按升序排列。

  • 节省内存，支持二分查找（O(log N)）。

  • 升级机制：插入非整数时自动升级为 hashtable；插入超出当前位宽范围的整数时（如 int16 → int32 → int64），内部整体扩容重写，两种升级都不可逆。

数据类型

如果说“数据结构”一节回答的是内部长什么样，本节则回答每种类型对外提供什么语义、何时用哪种编码——同一类型在不同数据规模下自动切换编码（且只升不降），是理解 Redis 内存模型的关键。

五种常用基本数据类型（速览，底层机制见下方各小节）：

  • String：二进制安全的字节串，单 key 最大 512MB（可存图片、序列化对象等）

    • 编码：int（整数值）/ embstr（≤ 44 字节短串）/ raw（长串），三者只升不降
    • 典型：缓存、计数器（INCR）、分布式锁（SET NX EX）、限流

  • Hash：散列键值对，适合对象字段级存储与部分更新

    • 编码：listpack（字段少且短，Redis 7 起替代 ziplist）→ hashtable（dict，数据多时）
    • 典型：对象缓存、购物车、计数聚合（HINCRBY）

  • List：有序可重复列表，支持两端 push/pop（有序双向、增删快查询慢）

    • 编码：3.2 之前是 linkedlist / ziplist；3.2 之后统一为 quicklist（双向链表 + 节点内 listpack）

    • 典型：【排行榜、消息队列、栈】

    • lpush list:1 0 1 2 3 4 5 6 添加7个数到列表

    • rpop list:1 从右边弹出一个（队列）

    • lpop list:1 从左边弹出一个（栈）

  • Set：无序、不可重复集合，支持交集、并集、差集运算

    • 编码：intset（全整数且数量 ≤ 512）或 hashtable（dict）

    • 典型：【共同好友、点赞签到打卡、统计访问IP、好友推荐（交集）】

    • sadd sign:2020-01-16 1 2 3 4 5 6 7 8 添加某天签到用户的ID，8个

    • smembers sign:2020-01-16 列出某天所有签到用户的ID

    • spop sign:2020-01-16 随机弹出一个某天签到用户的ID（抽奖去重）

  • Sorted Set：有序集合，member 唯一、score 可重复，按 score 排序

    • 编码：listpack（成员少且短）→ skiplist + dict（数据多时）
    • 典型：【排行榜、延时队列、滑动窗口限流】

其他数据类型（多依附于上述基础类型或模块实现）

  • bitmap（位图）：本质是 String 之上的位数组视图（详见下文）

    • bitop and continue:site site:2020-01-18 site:2020-01-17 计算某段时间内，都签到的用户数量
    • bitcount site:2020-01-17 0 100 统计某一天网站的签到数量

  • hyperloglog（基数统计）：概率算法，约 12KB 固定内存即可统计亿级 UV（标准误差 0.81%），代价是不能反查具体元素

  • Stream（消息队列）：基于基数树（rax）的追加式日志，支持消费组与 ACK 确认，弥补 List 队列无确认机制的短板

  • bitfield（位域，批量的bit位操作）：本质是 String 位运算的批量原子接口

  • geo（地理空间）：底层为 ZSet + geohash 编码，附近的人、两点距离皆由其支撑

各种数据类型对应的数据结构：

Redis 数据类型与底层结构映射

Redis 类型 编码（encoding） 底层数据结构
String int / embstr / raw long / 紧凑 SDS（embstr）/ 标准 SDS
List quicklist quicklist（节点内为 listpack）
Hash listpack / hashtable listpack（小数据）或 dict
Set intset / hashtable intset（整数小集合）或 dict
Sorted Set listpack / skiplist+dict listpack（小数据）或 skiplist+dict

String（int / embstr / raw）

String 虽是最基础的类型，内部却远不止“一种字符串”——Redis 会根据值的内容与长度，把它归入 int / embstr / raw 三种编码之一，用 OBJECT ENCODING key 可以一眼看穿：

编码 适用条件 底层形态 内存行为
int 值能被解析为 long 整数（如 10086） long 整数 直接存放在 redisObject.ptr 中，零额外堆分配
embstr 字符串长度 ≤ 44 字节 紧凑型 SDS redisObject 与 SDS 头尾相连，一次 malloc 完成
raw 字符串长度 > 44 字节 标准 SDS redisObject 与 SDS 分两次分配

为什么阈值恰好是 44 字节：Redis 的内存由 jemalloc 管理，它对 64 字节以内的小块有专属内存桶。一个 embstr 对象由 redisObject（16 字节）+ sdshdr8 头部（len/alloc/flags 共 3 字节）+ 结尾 \0（1 字节）构成，固定开销合计 20 字节——64 减去 20，恰好剩下 44 字节给数据本身，使总占用始终不越出 64 字节桶，一字节都不浪费。

编码切换的“单向车道”规则：

  • 写入整数 → int；写入 ≤ 44 字节的短串 → embstr；写入长串 → raw；

  • 对 int 执行 APPEND 等字符串拼接、对 embstr 执行任何修改型命令（APPEND / SETRANGE / GETSET），都会直接落入 raw——因为 embstr 是只读优化，结构上根本没有预留修改接口；

  • 编码只升不降：一旦进入 raw 便不会退回 embstr / int，除非删除后重建 key。

int 编码的价值不止于省内存：INCR / DECR / INCRBY 在 int 编码上直接操作 long 整数，免去字符串解析即可完成原子自增——这是 Redis 做计数器、限流器高性能的底层原因之一。

SDS 的结构演进：早期 SDS 头部是固定 int free + int len + char buf[]（共 8 字节头），对短字符串浪费明显；Redis 3.2 起按字符串长度把头部细分为 sdshdr5 / 8 / 16 / 32 / 64 五档，长度字段从 1 字节到 8 字节自适应（后缀数字即 len/alloc 所占位宽），Redis 7 又移除了不再使用的 sdshdr5。由此，一个 10 字节的短串也只需 3 字节头部，再叠加上述 44 字节阈值，短 value 场景的内存效率被压榨到了极致。下文的 C 结构即早期版本的示意：

SDS 的二进制安全、空间预分配、惰性释放等设计细节已在上文“动态字符串（SDS）”一节展开，此处不再重复。

实践问题与解决方案：

  • 超大 Value：String 上限虽达 512MB，但超过 10KB 的 value 在网络序列化、AOF 持久化、主从全量同步时都会显著放大延迟——大文本 / 大 JSON 应拆块存入 List / Hash，或改用对象存储、Redis 只留引用；

  • 频繁 APPEND 大字符串：raw 编码每次 APPEND 都可能触发扩容 realloc 与整段 memcpy，写入吞吐会断崖式下跌；日志追加类场景优先使用 Stream（XADD）或按时间分 key；

  • 计数溢出：INCR 达到 long 上限（9223372036854775807）会报错——热点计数可预置分片计数器（key 后缀编号分片）再异步汇总；

  • SETNX 锁的原子性陷阱：SETNX 后再补 EXPIRE 是两步操作，中途宕机会造成死锁——务必用 SET key value EX seconds NX 一步完成；释放锁时用 Lua 脚本比对持有者标识，防止误删他人锁。

List（快速列表）

quicklist 实际上是 zipList 和 linkedList 的混合体：将 linkedList 按段切分，每一段使用 zipList 来紧凑存储，多个 zipList 之间使用双向指针串接起来。

相对于链表它压缩了内存

分段阈值与 LZF 压缩（两个高频面试点）：

  • list-max-listpack-size（默认 -2，即单节点约 8KB）：决定每个节点内 listpack 的容量上限——太大则单段插入的内存搬迁成本高，太小则节点指针开销占比回升；
  • list-compress-depth（默认 0）：配置为 1 表示首尾各 1 个节点保持不压缩、其余中间节点全部 LZF 压缩——消息队列类“两端写、中间读”的场景可显著节省内存，代价是访问中间节点需要先解压。

实践问题与解决方案：

  • LRANGE 全量拉取：对十万级 List 执行 LRANGE list 0 -1 会一次性返回全部元素、撑爆网络缓冲区，应分页拉取或配合 LLEN 控制规模；

  • 长列表的无界增长：持续 LPUSH 而不消费会让 List 无限膨胀，消费端读取后应及时 LTRIM 裁剪，或用 RPOPLPUSH 转入备份列表再删除；删除超大 List 同样使用 UNLINK 异步回收；

  • 中间插入成本：元素集中于中间频繁插入时，单个 listpack 段仍可能触发内存搬迁——可把列表按业务拆短（每个 key 限长），或用 ZSet 加 score 模拟更灵活的顺序结构；

  • 队列语义的边界：List 做消息队列没有 ACK 与消费组概念，消费中途崩溃消息即丢失——可靠性要求高的场景应升级为 Stream（见后文）。

Hash（哈希表 + 紧凑编码）

Hash 是“对象字段级存储”的主力类型，底层在 listpack（Redis 7 起，此前为 ziplist）与 hashtable（dict） 两种编码间自动切换：

编码 触发条件（默认配置） 底层结构
listpack 所有 field/value 长度均 ≤ 64 字节（hash-max-listpack-value）且字段数 ≤ 512（hash-max-listpack-entries） 连续内存紧凑排列，一次分配
hashtable 任一 field/value 超过 64 字节，或字段数超过 512 dict：字段哈希到桶，拉链解决冲突

即：当哈希对象同时满足“键值对的键与值长度都小于 64 字节”与“键值对数量小于 512 个”两个条件时使用紧凑编码。任意条件被打破即升级为 hashtable，且只升不降——这解释了为何“存到一半变大的 Hash”内存会突然上涨：listpack 的全部元素要整体搬迁进新分配的 dict，搬迁期间新旧结构并存。

hashtable 编码的底层形态：本质是前文详述的 dict——每个 field 经 SipHash 散列到桶，桶内用拉链法挂接冲突字段；元素规模增长后由渐进式 rehash 平滑扩容，全程不阻塞主线程（机制详见上文“哈希表（dict）”一节）。

上图为 dict 的拉链结构示意：下方数组即桶表，每个桶头挂一条单向链表，冲突字段沿链表向后查找。

实践问题与解决方案：

  • 大 Hash 的连锁风险：Hash 达到百万字段后，HGETALL 一次性返回全部字段（网络与序列化双重阻塞）、rehash 期间新旧两表并存（内存峰值翻倍）、DEL 释放内存同样耗时——应按业务维度拆分为多个小 Hash（如按用户 ID 或业务字段分片），这正是上文“大 Hash 键需要拆分”的落地姿势；

  • field 无法独立设置 TTL：Hash 的过期只能作用到整个 key；业务需要字段级过期时，可用“Hash 存值 + ZSet 存字段过期时间戳”的双写结构，由定时任务扫描 ZSet 删除过期字段；

  • 避免整体序列化进 String：若业务只改动对象的一个字段却用 String 全量读改写，会产生严重写放大与网络开销——Hash 的字段级命令（HSET / HINCRBY / HGET）正是为此设计；

  • HSCAN 替代 HGETALL：必须遍历大 Hash 时，务必使用 HSCAN 游标分批迭代，配合 COUNT 控制每批返回量。

Set（intset + 哈希表）

Set 的底层只有两种编码：intset（成员全为整数且数量不多）或 hashtable（成员含字符串 / 数量超限），自动选择逻辑如下：

条件 编码 底层结构
成员全部是整数，且数量 ≤ 512（set-max-intset-entries） intset 连续内存、升序排列的整数数组
出现非整数成员，或数量 > 512 hashtable dict：键为成员，value 统一为 NULL

intset 的底层机制：本质是一段连续内存上的升序整数数组，靠二分查找实现 O(log N) 的成员判定。intset 内部同时声明了 int16_t / int32_t / int64_t 三种视图，当插入的元素超出当前视图的表示范围时，触发整体升级——重新分配空间并把全部存量元素按新类型逐一重写（O(N)），升级后只升不降：即使把大整数全部删光，也不会退回小类型，除非重建该 key。

hashtable 编码的细节：Set 复用的就是前文 Hash 所用的 dict，只是 value 恒为 NULL；因此 Set 同样享有渐进式 rehash，不会因扩容出现长时间阻塞。

intset 升级的正确类比：它与 String 的 int→embstr→raw 一样遵循“只升不降”——这是 Redis 以空间换时间、拒绝过度设计的典型体现：升级场景极少触发，为其实现降级逻辑纯属浪费。

实践问题与解决方案：

  • SMEMBERS 拉全量：对十万级成员的 Set 执行 SMEMBERS 会把全量成员一次性序列化返回，主线程与网络双双承压——改用 SSCAN 游标分批迭代；

  • SINTER / SUNION 计算风暴：集合间运算复杂度与参与集合的规模乘积相关（O(N×M)），高频交集可用 SINTERSTORE 把结果物化为独立 key，避免每次请求都现场计算；

  • 大 Set 的删除阻塞：DEL 百万成员大集合时，主线程要逐个释放 dict 节点，可能卡顿数百毫秒——直接改用 UNLINK key 让后台线程异步回收；

  • 哈希碰撞攻击：若成员哈希高度集中，hashtable 拉链会退化为单链表。Redis 4.0 起使用对随机种子敏感的 SipHash 做哈希，攻击者无法预构造同桶数据，从源头化解该风险。

跳跃表是一种有序的数据结构，通过在每个节点中维持多个指向其他节点的指针，从而达到快速访问节点的目的。

Redis 使用跳跃表作为有序集合的底层实现之一：当有序集合包含的元素数量比较多，或成员的字符串比较长时，Redis 就会切换为“跳跃表 + 字典”的复合结构。

编码触发条件（默认 zset-max-listpack-entries 128、zset-max-listpack-value 64）：成员数 ≤ 128 且每个成员长度 ≤ 64 字节时用 listpack 紧凑编码；一旦超限立即升级为 skiplist + dict 复合结构，且只升不降。

为什么是“跳表 + 字典”的黄金组合：

单一方案 致命缺陷 结论
只用 dict 只能 O(1) 查分数，无法按分数排序、做范围查询 不够用
只用 skiplist 精确查 member 需 O(log N)，重复写入还要先查重 不够快
skiplist + dict 空间多一份指针开销，读写路径各取所长 Redis 最终方案

dict 负责 “member → score” 的 O(1) 映射（顺带完成成员唯一性校验），skiplist 负责按 score 排序的范围操作；二者共享同一份 member 数据，ZADD 时同步更新两处。

skiplist 的底层设计：每个节点除了持有 member 与 score，还维护多层前进指针（forward）与跨度（span）。层数由随机算法按 1/4 概率逐层向上生成（幂律分布），Redis 7 中最高 64 层——之所以把“平衡”交给概率而非强制旋转，是因为期望层数低（约 1.33 层），插入/删除只需局部修改指针，期望代价 O(log N)，实现复杂度却远低于红黑树。

上图为 Redis 中跳跃表的实际结构：score 升序排列，每层前进指针按层稀疏，span 字段标注每次跨越的节点数——定位“排第几”时沿路径累加 span 即可。

span 是排名的基石：每个前进指针都附带 span（跨越的节点个数）。执行 ZRANK / ZREVRANK 时，只需沿查找路径把各段 span 累加即可得到排名，无需遍历全表——复杂度同为 O(log N)。另外，当多个成员分数相同时，Redis 规定按 member 的字典序继续比较，保证任意时刻都存在确定的全序，范围查询结果稳定可预期。

为什么不用红黑树 / B+ 树：红黑树的范围查询需要中序遍历、实现与调平衡复杂；B+ 树面向磁盘页优化，在纯内存场景优势不明显。跳表实现简单、范围查询只需沿最底层指针线性推进，还天然适合无锁并发下的局部修改——这也是 RocksDB MemTable、LevelDB 等 LSM 引擎普遍选用跳表的原因。

实践问题与解决方案：

  • 大 ZSet 的高频 ZADD：榜单类 key 若每秒成千上万次 ZADD，skiplist 指针读写与 dict 双重更新会持续消耗 CPU，且单 key 过大时无法水平拆分——优先考虑分层聚合（分钟榜→小时榜→日榜）、ZREMRANGEBYRANK 裁剪只留 Top N，或降低刷分频率；

  • ZRANGEBYSCORE 深分页：skiplist 的排名天然“越深越贵”——LIMIT offset count 每页都要从头累加 span 跳过 offset 个节点，offset 很大时退化为 O(offset) 遍历；业界常用“记录上一页最后 score 作为游标”代替页码翻页（详见本站《Redis ZSET 的深度分页解决方案》一文）；

  • ZUNIONSTORE / ZINTERSTORE 聚合：对多个大 ZSet 做并/交运算属于 CPU 密集操作且结果需落盘，应安排到业务低峰或交给独立聚合任务，避免阻塞主线程；

  • 内存权衡：skiplist 每个节点平均 1.33 层、每层一个指针，内存开销明显高于 listpack。若业务分数集中在固定小集合（如枚举 0~100），可适当调大 zset-max-listpack-entries，让更多 key 停留在紧凑编码。

bitmap（sds）

即位图——本质是 String（SDS）之上的一层位视图：一串连续的二进制位（bit），通过偏移量（offset）读写单个位（0/1），时间复杂度 O(1)。它并不存在独立的数据结构，SETBIT / GETBIT 在底层就是按字节寻址 SDS 中的某个位。

  • 空间账：1 个 bit 表示一个用户的状态，10 亿用户也只需约 125MB（10 亿 ÷ 8 字节）；位偏移上限为 2^32-1，与 String 的 512MB 上限一致；

  • 适合场景：数据量大且只有二值状态的统计——签到（第 N 天是否签）、登录态、在线状态、留存分析、黑名单；

  • BITCOUNT 的底层：Redis 用“预计算查表 + 按字节分组计数”统计值为 1 的位数（每字节 256 种组合的计数表），整体耗时与字符串长度成正比；

  • BITOP 的底层：对参与 key 的字节数组逐字节执行 AND / OR / XOR 逻辑运算后写入目标 key，结果长度取参与者的最大值——本质是 CPU 密集的批量位运算，大位图上执行需谨慎。

核心命令一览：

命令 功能 说明
SETBIT key offset value 将第 offset 位设为 0/1 O(1)，返回旧值，自动按需扩展字符串
GETBIT key offset 读取第 offset 位 O(1)，越界按 0 处理
BITCOUNT key [start end [BYTE|BIT]] 统计区间内值为 1 的位数 O(N)，start/end 以字节为单位
BITPOS key bit [start [end]] 查找第一个 0/1 位的位置 O(N)，可用于“分配下一个空闲位”
BITOP op destkey key [key...] AND / OR / XOR / NOT 批量位运算 O(N)，结果写入 destkey；NOT 仅支持单 key
BITFIELD key [GET/SET/INCRBY type offset] 按位域读写与原子自增 每条子命令 O(1)，一次调用可组合多条

BITFIELD 值得一提：它能以“位域”为单位原子操作（如 BITFIELD key INCRBY u8 100 1 实现 8 位计数器的溢出保护），本质是把 String 变成一块可寻址的位寄存器堆——很多限流器、令牌桶的精简实现都基于它。

布隆过滤器（Bloom Filter）

⚠️ 先纠一个常见的张冠李戴：布隆过滤器不是 Redis 的原生数据类型，也与 RoaringBitmap（RBM） 无关——RBM 是确定性压缩位图（常用于大数据列存与索引加速），而布隆过滤器是概率型结构，两者唯一共同点只是“都借助了 bit 数组”。原生 Bitmap 的回答是确定的（不存在就是不存在），布隆给出的则是“一定不存在 / 可能存在”的概率性结论，通常需借助 Redis 4.0 的 RedisBloom 模块或自行用 String 位运算模拟。

布隆过滤器是一种精巧的概率型数据结构（probabilistic data structure），用极小的内存回答“元素是否在集合中”，代价是以少量误判换取空间：

  • 绝不漏报：一旦某位为 0，元素必然不在——判断“不存在”是确定的；

  • 可能误报：判断“存在”只是“很可能存在”——所有位都为 1，也可能是其他元素恰好把它们填满（false positive）。

原理：布隆过滤器本质是一个 bit 向量。插入元素时用 k 个相互独立的哈希函数算出 k 个位置并全部置 1；查询时同样计算 k 个位置，只要有 1 个位置为 0 即可断定元素不存在，全部为 1 则只能回答“可能存在”。例如下图中 “baidu” 的三个哈希位为 1、4、7，“tencent” 为 3、4、8，位 4 被两次置位发生覆盖：

查询 “dianping” 时哈希到 1、5、8，位 5 为 0 → 确定不存在；查询 “baidu” 时 1、4、7 均为 1 → 只能说可能存在，因为 1、4、7 可能被其他元素（如 tencent 覆盖的位 4）碰巧全部置位。

误判率的数学控制：误判率由位数组长度 $m$、哈希函数个数 $k$、已插入元素数 $n$ 共同决定，近似关系为误判率 $\approx (1 - e^{-kn/m})^k$。给定容量比 $m/n$ 时，最优哈希个数 $k = (m/n)\ln 2$——工程上通常让位数组长度为预估元素数的 8~10 倍、$k$ 取 5~7，即可把误判率压在 1% 上下。由此也引出三个实践铁律：

  • 按峰值容量预分配：位数组过短会迅速饱和、误判率飙升，且扩容需要重建——RedisBloom 用 BF.RESERVE key error_rate capacity 显式指定容量与误差率；

  • 不能删除元素：置位是“叠加”的，直接清位会误删其他元素——需要删除语义时改用计数布隆过滤器（每位置扩展为计数器）或 Cuckoo Filter；

  • 多哈希的 CPU 成本：$k$ 越大误判率越低但插入/查询都退化为 O(k)，需要与吞吐要求做权衡。

经典使用场景：缓存穿透防护（拦截不存在 key 的查询，避免打穿到数据库）、爬虫 URL 去重、黑名单预筛、推荐系统的已读过滤——落库前先过布隆，“一定不存在”的结论可以省掉一次昂贵的磁盘或网络 IO。

Redis 中的实践问题与解决方案：

  • 实现方式选型：生产推荐 RedisBloom 模块（BF.ADD / BF.EXISTS / BF.RESERVE，天然支持分布式多 key 扩展）；轻量场景也可用 Lua 脚本 + String 位运算模拟，但需注意单条 Lua 的执行时长上限；

  • 大 Value 阻塞风险：布隆体积随容量线性增长，百万级容量即达 MB 级，不当使用极易产生大 Value，增加阻塞与网络传输风险——生产环境应对体积庞大的过滤器分片拆分（如按业务 ID 模数散列到多个 key，每个 key 维护独立哈希位数组），将单 key 控制在百 KB 量级；

  • 误判的业务兜底：凡使用布隆的业务必须设计“误判兜底”策略（如穿透拦截后允许少量回源查询），不能把概率性结论当作绝对事实。

HyperLogLog（基数统计）

HyperLogLog 不是一个独立的数据结构，而是概率型基数估计算法在 Redis 中的实现，用于回答“这个集合有多少个不重复元素”，却几乎不占用内存。

底层原理（伯努利过程）：对每个元素做哈希后观察其二进制串——末尾连续 0 的个数为 k，说明这串哈希值来自一个大约 $2^k$ 规模的随机试验集合。单次观测方差极大，于是 HLL 把哈希值前若干位当作“桶号”拆进 $m = 16384$ 个寄存器（每个 6 bit，合计固定约 12KB），对桶内各自的最大 k 做调和平均修正，最终估计误差约 $1.04/\sqrt{m} \approx 0.81%$：

  • PFADD key element...：元素只参与“最长零串”的竞争，本身不存储——这就是它能容纳亿级基数却只用 12KB 的原因；

  • PFCOUNT key：给出带误差的基数估计；多个 key 的估计可先 PFMERGE 再计数（合并也是 O(寄存器数)）；

  • 同一元素无论 PFADD 多少次都只算一次——天然去重。

实践问题与解决方案：

  • 只能算基数、不能查成员：HLL 不存元素，需要“查某个用户是否访问过”请用 Bitmap 或 Set；

  • 小基数时误差相对放大：Redis 对极小基数场景做了 LinearCounting 精修，但精确计数的强一致场景仍应使用 Set；

  • 跨天/跨周 UV 合并：每日各存一个 key，周 UV 直接 PFMERGE 汇总，比把全量 Set 再并集省几个数量级的内存；

  • 与去重业务的区别：如果后续还要“取出这批用户”，HLL 无能为力，选型时先确认是否只需“计数”。

Stream（消息队列）

Stream 是 Redis 5.0 引入的原生消息队列，弥补了 List 队列“无确认、无消费组、消息易丢”的结构性短板。

底层结构：消息按单调递增 ID（毫秒时间戳-序号）组织在 基数树（rax） 上——rax 是压缩前缀树，对“前缀高度重合”的顺序 ID 极为友好，相邻 ID 共享前缀、只存差异部分；每个树的叶节点用 listpack 紧凑存放一批连续消息。追加消息 O(1)，按 ID 范围读取同样高效。

消费模型：XREADGROUP GROUP g c 建立消费组，组内消费者各自维护游标；消息被读取后进入该消费者的 PEL（待确认列表），只有 XACK 之后才会移除——消费者崩溃后可用 XAUTOCLAIM 把超时未 ACK 的消息转移给其他消费者，实现至少一次投递。

实践问题与解决方案：

  • 内存无界增长：持续 XADD 不消费会让 rax 无限膨胀——用 XADD ... MAXLEN ~ 100000 做近似裁剪（~ 允许牺牲少量精度换取 O(1) 裁剪），或定期 XTRIM；

  • 消费积压：消费慢于生产时积压消息占满内存，需监控 XLEN 与流长度，配合背压（暂停生产）或扩容消费者；

  • 持久性语义：Stream 的可靠性依赖 AOF 配置——appendfsync always 才接近“不丢”，everysec 仍可能丢失秒级窗口；

  • 版本要求：XAUTOCLAIM、XGROUP CREATE ... MKSTREAM 等命令需 Redis 6.2+，旧版本只能用 XCLAIM 手动转移。

Geo（地理位置）

Geo 是“附近的人”“两点距离”等功能的基础，而它的底层只有两个老朋友：ZSet + geohash 编码。

底层原理：GEOADD 时把经纬度按 geohash 算法编码——将纬度区间 [-90, 90] 与经度区间 [-180, 180] 反复二分，每轮产出 1 bit，经纬度 bits 交叉拼接成 52 位整数，作为 ZSet 的 score（52 位恰好落入 double 的 52 位显式尾数位，可无损表示，二维精度约 0.6 米）；member 即地点名。于是：

  • 按 score 排序 = 按地理位置排序，ZRANGEBYSCORE 天然支持“矩形框选”；

  • GEORADIUS 的执行路径：按半径换算经纬度边界 → 用 ZRANGEBYSCORE 粗筛候选 → 逐点计算球面距离精确过滤并排序。

geohash 的边界陷阱：两个实际很近的点若恰好分处某条二分边界两侧，它们的 geohash 前缀会差异巨大、score 相距遥远——直接按 score 范围搜索会漏人。Redis 的做法是搜索时把目标格子及其 8 个邻域格子一并纳入候选（geohash neighbor 扩展）再做距离过滤，这也是“附近的人”结果不残缺的底层保证。

实践问题与解决方案：

  • 热 key 问题：“附近的人”往往集中在核心城区，单个 Geo key 承受全网流量——可按城市/区域分 key，再对跨界查询合并结果；

  • 过期与清理：位置信息天然有时效，Geo 却没有字段级过期——可像 Hash 一样配套 ZSet 记录上报时间，由任务清理陈旧坐标；

  • 超大 key 风险：用户量百万级后单 key 的 ZSet 体量巨大，GEORADIUS 的粗筛+精排在该 key 上串行执行，响应会劣化——需配合分片与本地缓存降级。

使用指南

选型指南：

需求场景 推荐类型 理由
普通缓存、计数器、锁 String 最简单，性能最高
对象存储、部分更新 Hash 结构化，支持字段级操作
消息队列、最新列表 List 支持 Push/Pop，有序
去重、交集并集运算 Set 自动去重，集合运算丰富
排行榜、排序、延时队列 ZSet 自带分数排序
海量 UV 统计 HyperLogLog 空间换精度，极省内存
签到、状态位 Bitmap 位操作，空间利用率极致
附近的人、距离计算 Geo 封装了经纬度计算
可靠消息队列 Stream 支持消费组确认机制

注意事项：

  1. 内存优化：尽量用 Hash 代替多个 String 存储对象（每个 key 自身还有对象头与字典项开销）；小数据量时 Redis 会自动使用紧凑编码（listpack / intset / embstr）。

  2. 大 Key 问题：Value 过大（如 String > 10KB，Hash/List/Set/ZSet 元素过多）会导致网络传输、持久化与删除时主线程卡顿——用 MEMORY USAGE key 体检、redis-cli --bigkeys 扫描定位，删除一律改用 UNLINK 异步回收。

  3. 热 Key 问题：某个 Key 被极高频率访问会使单分片负载失衡——redis-cli --hotkeys（需开启 LFU 策略）辅助定位，本地缓存 + 随机后缀多副本分摊读流量是常用解法。

  4. 过期策略：Redis 采用惰性删除 + 定期删除，过期 key 未必立即消失，且超大 key 到期瞬间的删除动作会阻塞主线程——不要完全依赖过期时间处理强一致业务。

  5. 编码体检：怀疑内存异常先执行 OBJECT ENCODING key——若本应紧凑的小数据 key 呈现 raw / hashtable，说明经历了“写入超大值后回删”的只升不降过程，重建 key 才能恢复紧凑态。

  6. 慢命令排查：SLOWLOG GET 查看主线程慢命令，重点排查随规模增长的 O(N) 命令（KEYS / HGETALL / SMEMBERS / LRANGE 全量）；生产禁止 KEYS *，遍历一律 SCAN 游标分批。

  7. 避免大 Value 往返：单次命令返回几十 MB 数据会拖垮网络与序列化，读取集合类数据应分页/分批（HSCAN / SSCAN / ZSCAN / LIMIT）。
