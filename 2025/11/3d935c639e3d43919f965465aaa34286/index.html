MySQL 8.0 新增功能函数和使用案例

发表于2025-11-15|更新于2026-09-07
|DBMySQL
|浏览量:

MySQL 8.0 引入了众多新特性和功能，显著提升了性能、安全性和易用性。本文按“分析能力（窗口函数 / CTE）→ 索引能力（Skip Scan / 隐藏索引 / 降序索引 / 函数索引）→ 文档能力（JSON）→ 引擎与安全能力”四条主线展开，每个主题都配有可直接运行的 SQL 示例、实现原理与使用边界。

阅读导览：
① 窗口函数——排名三兄弟的差异、LAG / LEAD 的前后行访问、聚合窗口与滑动窗口；
② 通用表表达式（CTE）——递归 CTE 的“锚点 + 递归成员”执行模型，与派生表的本质区别；
③ 索引优化——Skip Scan 何时才能用、隐藏索引的软删除玩法、降序索引的存储原理、函数索引的实现机制；
④ JSON 能力——JSON_TABLE 行转列、JSON Schema 服务端校验、In-Place 部分更新；
⑤ 其他优化——原子 DDL、数据字典、默认字符集、Hash Join、不可见列等一批关键变化与升级注意点。

窗口函数

允许在结果集的分区上执行计算，而无需将行分组为单个输出行，这使得复杂的分析查询（如排名、移动平均值等）更容易实现。

排名函数

根据窗口内行序与并列情况生成序号的函数，三者对“并列名次”的处理策略不同（是否占位、是否跳号），是报表与面试中的高频对比点：

  • ROW_NUMBER()：为每一行分配一个唯一的连续序号（如果有相同值，排名也会不同）。

  • RANK()：与 ROW_NUMBER() 类似（如果有相同值，排名也相同，下一个排名值会跳过）。

  • DENSE_RANK()：与 RANK() 类似（如果有相同值，排名也相同，下一个排名值不会跳过）。

场景：查询每个班按分数排序的名次

窗口函数的执行原理与实践注意

窗口函数与普通聚合的本质区别：

对比维度 普通聚合（GROUP BY） 窗口函数（OVER）
输出行数 每组一行，行被压缩 每行保留，结果追加为新列
计算范围 全表按组独立汇总 基于当前行可见的“窗口帧（frame）”
计算顺序 先过滤，后分组聚合 WHERE 之后、外层 ORDER BY 之前
典型用途 汇总报表 排名、同环比、移动平均、占比

执行阶段：优化器把窗口函数拆成独立算子，位置在 WHERE / GROUP BY 之后、外层 ORDER BY / LIMIT 之前——先按 PARTITION BY + ORDER BY 对结果集分区排序（无索引支撑时需要排序 + 临时表），再逐分区计算每行的窗口帧，最后才投影与输出：

flowchart LR
    A[基础行集<br/>WHERE 过滤后] --> B[分区排序<br/>PARTITION BY + ORDER BY]
    B --> C[窗口帧计算<br/>每行确定可见帧范围]
    C --> D[追加结果列<br/>ROW_NUMBER / SUM 等]
    D --> E[外层 ORDER BY / LIMIT]

实践中的三个注意点：

  • WHERE 中不能直接引用窗口函数：窗口函数在 WHERE 过滤之后才计算，若要按排名过滤（如 WHERE rn = 1），必须把窗口函数放进子查询 / CTE，再在外层过滤（本文多处示例即此写法）；

  • 大分区排序可能落临时表：PARTITION BY / ORDER BY 无法命中索引时结果集需整体排序，先走内存临时表，超过 tmp_table_size（默认 16MB）后溢出到磁盘临时表，性能骤降——大表上的窗口查询要留意执行计划中的 Using temporary / Using filesort；

  • LAST_VALUE 的默认帧陷阱：默认帧是“从分区起点到当前行”，因此 LAST_VALUE() 不显式声明 ROWS ... UNBOUNDED FOLLOWING 时只会返回当前行自身的值（看起来“没生效”）——本文示例特意显式声明了帧范围，这是窗口函数最经典的坑之一。

通用表表达式（CTE）

CTE 可以“给一段查询起名字”，让复杂 SQL 分层、可复用、可递归。按是否引用自身分为非递归 CTE（命名子查询，可被多次引用）与递归 CTE（锚点 + 递归成员，擅长查询树形结构），相比层层嵌套的子查询大幅提升可读性与可维护性。

递归 CTE 的执行模型与使用边界

执行模型：锚点成员先产出第一批行，随后递归成员以“上一批产出的行”为输入反复迭代，直到某次迭代不再产生新行才停止——每层结果通过 UNION ALL 累积（若用 UNION 去重，会额外引入去重开销与语义风险）：

flowchart TD
    S[锚点成员<br/>先产出起始行集] --> R[递归成员<br/>JOIN 上一层结果找出下一层]
    R --> C{本次迭代产出新行?}
    C -->|是| R
    C -->|否| D[输出各层累积结果<br/>如含 level 层级列]

实践中的四个边界：

  • 递归深度上限：默认 cte_max_recursion_depth = 1000，超限报 ERROR 3636: Recursive query aborted——业务上先想清楚“树最深多少层”，必要时显式调大该参数，但更应先排查数据中是否存在环；

  • 无环检测，小心死循环：若组织架构出现循环上级（A 的上级是 B，B 的上级又是 A），递归 CTE 会无限迭代直到撞深度上限——建模时应保证上级链无环，或在递归成员中附加终止条件（如 level 上限）；

  • 每层迭代都是自连接：递归成员的关联列（如 manager_id）必须有索引，否则每层全表扫描，层数一多性能骤降；

  • CTE 不一定物化：优化器对非递归 CTE 可能直接合并（Merge）展开进主查询，也可能物化（Materialization）成中间表——同一 CTE 被多处引用时物化可避免重复计算，但也可能丢失条件下推的机会，具体行为以 EXPLAIN 中的 Materialized / Merged 标识为准。

CTE 与派生表（嵌套子查询）怎么选：CTE 可被多次引用、可递归、语义自上而下更清晰；派生表只能用一次且不能递归。两者性能没有绝对优劣（取决于优化器的合并 / 物化决策），优先按可读性与复用性选择即可。

索引优化

联合索引

索引跳跃扫描（ index skip scan） 是 MySQL 8.0 的重要优化特性。它允许在跳过复合索引最左列的情况下仍能使用索引，前提是前导列取值少（低基数），能显著提升特定查询的性能，避免不必要的全表扫描。

核心思想：当查询条件跳过了复合索引的前导列（第一列），但该前导列的**取值数量较少（低基数）**时，优化器会：

  1. 枚举前导列的每一个可能值；
  2. 对每个值，执行一次“常规的最左前缀扫描”；
  3. 合并所有结果。

本质上是“用多个小范围扫描，代替一次全表扫描”。

在不符合组合索引最左前缀的原则的情况，优化器依然能使用组合索引。以 idx_u1(rank1, rank2) 为例，WHERE rank2 = 30 的 Skip Scan 决策过程如下：

flowchart TD
    Q[WHERE rank2 = 30<br/>idx_u1（rank1, rank2）] --> D{前导列 rank1 取值少?}
    D -->|是| E[枚举 rank1 的 DISTINCT 值<br/>rank1=1 / rank1=5 / ...]
    D -->|否| N[放弃 Skip Scan<br/>全索引扫描 / 全表扫描]
    E --> G1[段内扫描 rank1=1 AND rank2=30]
    E --> G2[段内扫描 rank1=5 AND rank2=30]
    G1 --> M[合并各段结果返回]
    G2 --> M

限制条件（官方文档限定，全部满足才可能走 Skip Scan）

  • 前缀的值数据量少，过大不会使用ISS

  • select 选择的字段不能包含非该联合索引的字段，在其他联合索引的也无效如c1 字段在组合索引里面可以 ，并且这个组合索引的前缀值较少，会使用到该联合索引
    select * 的sql 就走不了skip scan

  • sql 中不能带 group by或者distinct 语法

  • Skip scan仅支持单表查询，多表关联是无法使用该特性。

  • 对于组合索引 ([A_1, …, A_k,] B_1, …, B_m, C [, D_1, …, D_n])，A,D 可以为空，但是B ,C 字段不能为空。

示例：

phone 表中建有两个联合索引：一个以高基数（近乎唯一）的 name 开头，另一个以低基数的 gender 开头（gender、phone）。当查询跳过前导列、直接按 phone 过滤时，只有前导列取值少的那份索引（gender、phone）才值得被 Skip Scan 使用；name 开头的索引前导列值几乎不重复，枚举它的代价接近全量扫描，优化器会直接放弃。

隐藏索引

  • 软删除：当索引不需要时，只需要将这个索引先设置为隐藏索引，使查询优化器不再使用这个索引，但是，此时这个索引还是需要MySQL后台进行维护，当确认将这个索引设置为隐藏索引系统不会受到影响时，再将索引彻底删除。

  • 灰度发布：创建索引时，首先将索引设置为隐藏索引，通过修改查询优化器的开关，使隐藏索引对查询优化器可见，通过explain对索引进行测试，确认这个索引有效，某些查询可以使用到这个索引，就可以将其设置为可见索引，完成灰度发布的效果。

降序索引

  • 只有InnoDB存储引擎支持降序索引，只支持BTREE降序索引。

为什么要“物理降序”：索引页内的记录本身按序排列。8.0 之前索引只能按升序构建，执行 ORDER BY c2 DESC 时 InnoDB 只能从叶子节点反向遍历（或交给 filesort）；8.0 起叶子节点真正按声明方向存储，c2 DESC 可以正向顺序扫描，(c1 ASC, c2 DESC) 这类混合方向排序也因此第一次能完整命中索引。

而“GROUP BY 不再隐式排序”是 8.0 对旧行为的明确废弃：此前 GROUP BY c2 的结果会默默附带按 c2 升序排序，升级后该保证消失——依赖“分组结果自动有序”的老 SQL 必须显式补 ORDER BY，否则输出顺序不受保证（这是升级到 8.0 时常见的行为差异）。

函数索引

函数索引允许你基于表达式创建索引，例如 INDEX(UPPER(name)) 或 INDEX(DATE(created_at))。

实现机制：函数索引在底层由**隐藏的虚拟列（Generated Column）**承载——创建索引时 MySQL 自动生成不可见的虚拟列保存表达式求值结果并为其建索引，因此索引键本质上是“表达式的值”。

  • 支持 JSON 数据的索引：对 JSON 字段的提取路径表达式（如 JSON_EXTRACT(details, '$.category')）建函数索引后，按路径过滤也能走索引（见下方示例）。

  • 命中条件：查询中的表达式必须与索引表达式一致（如 WHERE UPPER(name) = 'ZHANG'）；写成 WHERE name = 'zhang' 无法命中 UPPER 索引，这也是函数索引要解决的历史痛点——早期版本只能手动维护冗余列；

  • 维护成本：每次 DML 都要额外计算表达式并更新索引（写放大），高频写入的表需先评估收益；

  • 验证方法：EXPLAIN 中 key 列出现该函数索引名即命中，也可用 SHOW INDEX 查看其隐蔽的虚拟列。

JSON 相关

对 JSON 字段的操作函数

JSON_TABLE

将 JSON 字段转成关系表输出，同时可以实现统计等聚合查询。它是 8.0 的核心 JSON 增强之一（5.7 只能把数据取到应用层自行解析）——上面 FROM users, JSON_TABLE(...) 的逗号连接即**隐式 LATERAL（横向派生表）**语义，让“把每行 JSON 中的数组展开成多行、再与主表行关联”成为可能。

JSON 部分更新

只修改 JSON 文档中发生变化的部分，而不是重写整个文档！使用了一种称为 “In-Place JSON Patching” 的机制：

  • InnoDB 将 JSON 文档存储为一种内部二进制格式（基于 BSON 类似结构）；

  • 当执行 JSON_SET，JSON_REPLACE，JSON_REMOVE 等操作时，引擎会：

    • 定位到需要修改的具体节点；
    • 只更新该节点及其父路径上的元数据；
    • 避免重写未变化的部分；

  • 如果修改导致文档大小显著增加，仍可能触发完整重写，但大多数小修改是原地完成的。

版本与前提：JSON 部分更新是 8.0 引入的能力（5.7 每次 JSON_SET 都会整文档重写）；且真正的“日志级收益”需要 binlog 使用 ROW 格式——此时 Binlog 记录的是 JSON 的二进制 diff（Binlog 日志量也大幅下降），STATEMENT 格式下从库仍需重放完整 SQL，无法享受此优化。

其他优化（引擎、安全与兼容性）

8.0 除上述能力外，还在引擎底座与安全体系上做了大量“看不见”的改造，按主题分组如下：

数据字典与 DDL

  • 原子 DDL：与 DDL 相关的数据字典更新、存储引擎操作、Binlog 写入被纳入同一原子操作——要么全部成功，要么整体回滚，不会残留“半成品表”。注意它保证的是元数据一致性，大表 rebuild 的耗时与中断恢复仍依赖 InnoDB 自身的 redo 机制；

  • 事务性数据字典：元数据从 .frm 散文件迁入 InnoDB 数据字典表（8.0 彻底告别 .frm），SHOW / INFORMATION_SCHEMA 读取更快，字典与文件不一致的隐患消失——原子 DDL 正建立在这一底座之上；

  • INSTANT 加列：ALTER TABLE t ADD COLUMN ..., ALGORITHM=INSTANT（8.0.12+）只改元数据、秒级完成，解决“大表加列长时间锁读写”的痛点（前两代算法 COPY / INPLACE 都需重建表）。

安全与账号

  • 角色（Role）：CREATE ROLE 定义权限集合后统一授予账号，回收权限只需从角色剥离，适合“一组开发 / 一组只读”的批量管理；

  • caching_sha2_password 默认认证：替代易受嗅探的 mysql_native_password，全程加密且带服务端缓存，安全性显著提升；

  • 默认字符集 utf8mb4：库表默认 utf8mb4 / utf8mb4_0900_ai_ci，从源头消除 emoji、生僻字乱码（5.7 默认 latin1）。

查询与优化能力

  • Hash Join（8.0.18+）：无索引等值 JOIN 不再退化为逐行嵌套循环，先对小表建哈希表再探测大表，EXPLAIN 中可见 Using join buffer (hash join)；

  • CHECK 约束强制执行（8.0.16+）：5.7 的 CHECK 只解析不生效，8.0 起在服务端真正校验（上文 JSON Schema 校验即基于 CHECK 落地）；

  • 直方图（Histogram）：ANALYZE TABLE ... UPDATE HISTOGRAM ON col 记录列值分布，优化器对倾斜数据（如 90% 集中在少数取值）的估算不再被“均匀假设”误导；

  • 正则函数：REGEXP_SUBSTR / REGEXP_INSTR / REGEXP_REPLACE / REGEXP_LIKE 把正则处理内建进 SQL，替代“取出后在应用层处理”的写法。

InnoDB 与存储

  • 自增计数器持久化：自增值随 redo 持久化，重启不再回退（5.7 曾出现重启后自增复用、覆盖已有行的高危问题）；

  • 不可见列（Invisible Columns，8.0.23+）：列声明 INVISIBLE 后不参与 SELECT *，适合为历史表追加“不想被通配查询暴露”的辅助列——注意它与隐藏索引是两个不同概念（一个藏列、一个藏索引）；

  • 资源组（Resource Group）：把不同来源的查询划分到不同资源组并分配 CPU 优先级，适合 OLTP / 分析混合负载隔离；

  • Clone 插件：CLONE INSTANCE 在线克隆实例，搭建新从库的速度远超逻辑备份恢复。

升级到 8.0 的兼容性注意：

  • 认证插件：mysql_native_password 默认禁用，5.x 时代的老客户端 / 驱动会认证失败——优先升级驱动，应急可显式开启旧插件；

  • 默认 sql_mode 更严格：包含 ONLY_FULL_GROUP_BY 等规则，GROUP BY 漏列、隐式类型转换等“能跑但危险”的老 SQL 会直接报错；

  • 行为差异：查询缓存被移除；GROUP BY 不再隐式排序；FROM a, b 这类无 JOIN 条件的隐式连接写法被禁止（需显式 JOIN）；

  • 授权语法拆分：GRANT ... IDENTIFIED BY 'pwd' 一条龙“建号 + 授权”的方式废弃，需先 CREATE USER 再 GRANT。

总结

MySQL 8.0 不是“多几个函数”的小版本，而是把分析能力（窗口函数 / CTE）、索引体系（降序 / 函数 / Skip Scan）、查询引擎（Hash Join）、元数据底座（原子 DDL + 数据字典）、安全基线（新认证 + utf8mb4）整体重做了一遍。对工程团队最有价值的迁移策略是分三步走：先做功能验证——用窗口函数替换用户变量模拟、用 CTE 重构深嵌套子查询、用 INSTANT 加列解掉大表 DDL 痛点；再做行为适配——梳理隐式排序依赖、处理严格 sql_mode 带来的报错、升级客户端认证；最后完成基线与监控——核对字符集、binlog 格式（ROW）与关键参数差异，并把 8.0 新能力纳入日常 SQL Review 的检查清单。
