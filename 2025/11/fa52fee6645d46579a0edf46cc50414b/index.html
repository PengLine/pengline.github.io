Java 线程的休眠、等待、加入、让步有何区别？锁释放与状态迁移深度辨析

发表于2025-11-23|更新于2026-09-23
|Java多线程
|浏览量:

在 Java 中，线程的 休眠（sleep）、等待（wait）、加入（join） 和 让步（yield） 是四种不同的线程协作与控制方式。它们名字相近、表面都涉及"线程暂停"，但底层机制完全不同：有的依赖对象监视器，有的只依赖操作系统的定时器；有的会释放锁，有的死抱锁不放；有的改变线程状态，有的连状态都不变。

混淆这四个方法的代价很高：轻则写出"靠运气运行"的时序代码，重则在线上出现偶发超时、线程永久挂起、服务假死这类难以复现的故障。本文的目标是把它们的机制讲透：从 JDK 源码与 HotSpot 实现层面逐条考证结论，绘制状态迁移图与时序图，并用真实工程中的故障场景沉淀定位与修复经验。

为避免歧义，先约定本文的资料分级：

  • 【真实源码】：直接来自 JDK 或 Javadoc 的代码与原文表述，未做逻辑改动。

  • 【源码简化】：保留核心逻辑、省略非主干分支的代码。

  • 【实现层面】：HotSpot 虚拟机内部实现，属于实现细节而非语言规范，版本间可能重构，不能当作规范依赖。

  • 【理论分析】：基于模型推导的结论，无实测数据支撑。

  • 【示例数据】：演示用的输出或数值，不具复现性，不代表真实环境。

先给出四者的核心对比（后文逐个展开论证）：

方法 是否释放锁 是否阻塞 是否需要同步上下文 是否可中断 用法 典型用途
wait() 是 是 是 是 Object.wait 线程间协作（生产者-消费者）
sleep() 否 是 否 是 Thread.sleep 定时暂停
join() 否 是 否 是 Thread.join 等待线程结束。
yield() 否 否 否 否 Thread.yield 礼让 CPU（提示）

这张表里"是否释放锁"一列最容易背错也最关键。注意其中有两处需要修正直觉的地方：join() 标注"否"指的是不释放调用者自己持有的业务锁，但 join() 内部基于 wait() 实现，在等待期间它会释放目标 Thread 对象的监视器锁——这一点第四节会结合源码展开。wait() 标注"是"也只针对调用 wait 的那个对象的监视器，若线程还持有其他对象锁，那些锁并不释放。

一、先建立坐标系：线程状态与监视器模型

四个方法的一切行为差异，最终都体现在线程状态和锁的持有关系上，所以先把这两套坐标系建立起来。

1.1 官方六状态模型

java.lang.Thread.State 枚举（Javadoc 定义）共六个状态：

  • NEW：线程对象已创建但尚未调用 start()。

  • RUNNABLE：包括"可被调度"与"正在运行"两种情形，Java 官方模型把传统教科书里的就绪与运行合并为一个状态。

  • BLOCKED：正在竞争某个对象的监视器锁、尚未获得。

  • WAITING：无限期等待，需要被显式唤醒（wait()、join()、LockSupport.park()）。

  • TIMED_WAITING：限时等待（sleep(ms)、wait(ms)、join(ms)、parkNanos）。

  • TERMINATED：run() 执行完毕或异常退出，线程终止。

用状态机完整表达（包括很多资料画漏的一条边：WAITING/TIMED_WAITING 被唤醒后，如果锁还没抢回来，会先回到 BLOCKED）：

stateDiagram-v2
    [*] --> NEW: new Thread()
    NEW --> RUNNABLE: start()
    RUNNABLE --> BLOCKED: 竞争监视器锁失败
    BLOCKED --> RUNNABLE: 竞争成功获得锁
    RUNNABLE --> WAITING: wait() / join() / LockSupport.park()
    RUNNABLE --> TIMED_WAITING: sleep(ms) / wait(ms) / join(ms) / parkNanos
    WAITING --> BLOCKED: 被唤醒后重新竞争锁失败
    TIMED_WAITING --> BLOCKED: 被唤醒后重新竞争锁失败
    WAITING --> RUNNABLE: 唤醒且重新获得锁 / 目标线程终止 / unpark
    TIMED_WAITING --> RUNNABLE: 超时或唤醒且重新获得锁
    RUNNABLE --> TERMINATED: run() 执行结束
    TERMINATED --> [*]

这张图里"唤醒 ≠ RUNNABLE"是理解 wait() 行为的钥匙：被 notify() 的线程只是离开了等待集，它还必须重新抢到监视器锁才能从 wait() 返回；抢锁失败期间，线程处于 BLOCKED 状态。这一点与 sleep() 形成鲜明对比——sleep() 到点唤醒后不需要抢任何锁，直接回 RUNNABLE。

1.2 传统"五态/三种阻塞"模型的由来与辨析

上面这张"5 种状态"图来自传统操作系统教科书的划分，很多老资料用它解释 Java 线程。它把阻塞细分为三类，这个视角本身有价值，但必须与官方模型对应清楚，否则看线程栈时会误判：

  • 新建状态(New) : 线程对象被创建后，就进入了新建状态。例如，Thread thread = new Thread()，且threadStatus = 0。

  • 就绪状态(Runnable): 也被称为"可执行状态"。线程对象被创建后，其它线程调用了该对象的start()方法，从而来启动该线程。例如，thread.start()，就绪状态的线程，随时可能被CPU调度执行。

  • 运行状态(Running) : 线程获取CPU权限进行执行。需要注意的是，线程只能从就绪状态进入到运行状态。

  • 阻塞状态(Blocked) : 线程因为某种原因放弃CPU使用权，暂时停止运行。直到线程进入就绪状态，才有机会转到运行状态。在等待进入一个临界区，阻塞的情况分三种：

    • 等待阻塞（等待唤醒）（in Object.wait()） – 通过调用线程的**wait()**方法，让线程等待某工作的完成。位于对象等待池中的阻塞状态（Blocked in object’s wait pool），涉及线程通信。如果大量线程在该状态，获得了监视器之后，又调用了wait() 方法
    • 同步阻塞（等待获取监视器）（waiting for monitor entry） – 线程获取同步锁失败 (因为锁被其它线程所占用)，它会进入同步阻塞状态。位于对象锁池中的阻塞状态（Blocked in object’s lock pool），涉及线程同步。如果大量线程在该状态，可能是争夺一个全局锁而被阻塞（某线程在临界区时间太长，以至于新线程迟迟无法进入临界区）
    • 其他阻塞（等待资源）（waiting on condition） – 通过调用线程的**sleep()或join()**或发出了I/O请求时，线程会进入到阻塞状态。当sleep()状态超时、join()等待线程终止或者超时、或者I/O处理完毕时，线程重新转入就绪状态。如果大量线程在该状态，可能获取第三方资源网络阻塞，迟迟得不到响应，导致大量线程进入等待状态。或者IO读写较慢。

  • 消亡状态(Dead) : 线程执行完了或者因异常退出了run()方法，该线程结束生命周期。

对照官方模型做三点修正：

  1. "等待阻塞"对应 WAITING/TIMED_WAITING（wait 家族），"同步阻塞"对应 BLOCKED，这两个映射是干净的。

  2. "其他阻塞"是混合体：sleep()/join() 在官方模型里分别是 TIMED_WAITING 与 WAITING/TIMED_WAITING，并不是 BLOCKED；而网络 IO 阻塞在 Java 视角下根本不是任何等待状态——一个卡在 socketRead0() 上的线程，Thread.getState() 返回的是 RUNNABLE。这是线程栈分析中最经典的误判点：看到 RUNNABLE 以为线程在跑，实际它在内核里等网络。BIO 场景下大量线程"RUNNABLE 但卡在 IO"，对应上文"获取第三方资源网络阻塞"的诊断提示。

  3. 传统模型里"Running 与 Runnable 分离"在 Java 中被合并，Thread 层面无法区分"正在 CPU 上运行"与"就绪等待 CPU"，这也是 Java 线程状态模型有意做的简化。

1.3 监视器模型：一个对象的"两个队列"

理解 wait() 与 join() 必须先认识 JVM 的监视器结构。【实现层面】在 HotSpot 中，每个被 synchronized 保护的对象在 JVM 内部关联一个 ObjectMonitor（对象监视器），其中至少有两类"排队区"：

  • 竞争队列（EntryList/cxq）：已经执行到 synchronized 入口、正在抢锁的线程排在里头，对应线程状态 BLOCKED。

  • 等待集（WaitSet）：曾经持有锁、但主动调用 wait() 放弃锁进入等待的线程排在里头，对应线程状态 WAITING。等待集中的线程不参与锁竞争，直到被 notify()/notifyAll()、超时或中断移出等待集，重新进入竞争队列。

synchronized 抢锁失败与 wait() 等待，表面都是"线程停下来了"，实际分属两个不同的队列、两种不同的状态、两套不同的唤醒路径。后文所有对 wait() 行为的解释，都可以落回这个模型。

二、休眠（sleep）：线程级的定时暂停

作用：让当前线程暂停执行指定的时间，但不会释放锁（不释放已持有的对象锁）。

Thread.sleep 的语义在 Javadoc 中写得很清楚（翻译）："使当前正在执行的线程休眠（暂时停止执行）指定毫秒数……该线程不会失去任何监视器的所有权。"这句 “does not lose ownership of any monitors” 就是"sleep 不释放锁"的官方出处。

2.2 为什么 sleep 不释放锁：设计取舍

不是 HotSpot"做不到"，而是不该做。sleep 的设计定位是"线程级的定时暂停"，它与任何对象、任何临界区无关——它甚至定义在 Thread 而不是 Object 上，就是为了表明它不依附于监视器模型。

反证一下"如果 sleep 释放锁"会发生什么：线程 A 在 synchronized(lock) 临界区里调用 sleep(200) 想模拟一次慢处理，若锁被释放，另一个线程 B 会趁 A 睡觉时进入同一临界区，A 醒来后继续执行——同一临界区出现了两个线程交错操作，synchronized 保护的原子性被自己临时放开的锁击穿。临界区内的中间态（比如"扣了 A 账户、还没加到 B 账户"）会被其他线程看到。所以"sleep 不释放锁"是保证临界区原子性语义自洽的必然选择，而它的代价就是下一节的故障场景：临界区里睡觉 = 持锁占坑。

对比 wait() 为什么就必须释放锁：wait 的定位是"等待某个条件成立"。如果等待者不放锁，条件永远无法被别的线程制造出来（别人进不了临界区改状态），逻辑上就是死锁。释放锁是"等待条件"语义的必然要求，不释放锁是"定时暂停"语义的必然要求——两个设计各自自洽，差异来自语义而非实现水平。

2.4 故障场景一：用 sleep 轮询做同步，偶发超时

发生什么：某系统用"下游异步生成报告 + 轮询查询"的方式实现导出功能。调用线程发起任务后循环 Thread.sleep(100) 再查一次状态，约定"轮询 30 次（3 秒）还没完成就报超时"。压测时一切正常，上线后偶发报"导出超时失败"，且集中在业务高峰。

为什么：sleep 轮询的延迟由轮询周期决定。【理论分析】设轮询周期为 $T$，任务完成时刻在某个周期内近似均匀分布，则发现完成的平均延迟为：

$$\bar{d}=\int_0^T (T-t),\frac{1}{T},dt=\frac{T}{2}$$

即平均要白等 $T/2$，最坏白等 $T$。但这只是"慢"，不是"偶发失败"。真正的杀手是：sleep 的恢复时间在负载高峰时被拉长。睡眠结束后线程还要参与调度，高峰期 CPU 就绪队列很长，"睡 100ms"实际可能 150ms 后才轮到执行；再加上下游任务本身在高峰期完成变慢，“3 秒 30 次"的实际覆盖能力大幅缩水。更隐蔽的是，轮询代码若还夹带了 synchronized 读取共享状态，多个轮询线程会互相挤占，进一步恶化时序。本质问题是：用时间猜结果，把"任务大概 3 秒内能完成"这个统计假设当成了同步协议——负载一变，假设失效，故障就按概率出现，所以"偶发、难复现”。

系统如何处理：业务侧报导出失败，用户重试，高峰期重试流量进一步加剧负载，形成正反馈劣化；同时每个卡在轮询里的请求占着一个容器线程，大量导出请求会耗尽 Web 线程池，把"偶发超时"放大成"整站变慢"。

如何恢复与根治：恢复上，先扩容或调大轮询预算止血。根治必须把"轮询猜"换成"完成即知"：

  • 有条件谓词的，用 wait/notifyAll（或 ReentrantLock + Condition）实现"完成信号"；

  • 任务分发的，直接用 BlockingQueue，消费者 take() 阻塞等待，天然零轮询；

  • 带返回值异步任务的，用 CompletableFuture.supplyAsync(...)，调用方 thenApply/get(timeout) 感知完成，超时由框架保证。

2.5 故障场景二：在临界区里"持锁睡觉"

发生什么：线程栈显示几十个业务线程 BLOCKED (waiting for monitor entry)，全部堵在同一个全局锁（比如包了一层 synchronized 的缓存查询方法）上，RT 抖动从毫秒级飙到秒级。

为什么：持锁线程在临界区里调用了 sleep（常见于"慢一点怕打爆下游"的节流代码）。sleep 不释放锁，于是"睡 500ms"变成了"独占全局锁 500ms"——其他线程全部堆积在 BLOCKED。这也解释了 1.2 节引用的诊断口诀：“大量线程在同步阻塞状态，可能是争夺一个全局锁而被阻塞（某线程在临界区时间太长，以至于新线程迟迟无法进入临界区）”。

系统如何处理与恢复：BLOCKED 堆积本身不会自动解除，只有持锁线程醒来并退出临界区才能逐个放行；若持锁线程在睡眠期间还嵌套等别的锁，就直接升级成死锁。恢复手段：把 sleep 移出临界区（节流应在锁外做）；缩小临界区（锁内只做内存操作，慢调用放锁外）；全局锁降级为分段锁或改用 ReentrantLock 的 tryLock(timeout) 避免无限堆积。预防规则很简单：synchronized 块内禁止出现 sleep、RPC、磁盘 IO 等一切不可预估耗时的调用。

三、等待（wait）：监视器上的条件等待

作用：让当前线程在某个对象上等待，会释放该对象的锁，直到被其他线程唤醒（notify/notifyAll）。

wait() 是 Object 的本地方法，调用它会让持有对象锁的线程释放锁并进入等待集（wait set），同时释放 CPU；线程在等待集中不参与锁竞争，直到被 notify()/notifyAll() 唤醒，或因超时、中断而返回，才会回到同步块重新竞争锁。

展开成监视器视角的三步：【实现层面】

  1. 入等待集：当前线程进入 obj 对应 ObjectMonitor 的 WaitSet，状态转为 WAITING；

  2. 释放锁并挂起：释放 obj 的监视器，唤醒竞争队列中的等待者，自己挂起；

  3. 被唤醒后重新竞争锁：从等待集移回竞争队列，抢到锁后才能从 wait() 返回、继续执行后续代码。

第 3 步常被忽略：wait() 返回时线程必然重新持有该对象的锁（这也是 Javadoc 明确的语义），所以 wait() 之后的代码仍然处于受保护的临界区内，可以安全地继续读取共享状态。

为什么 wait 必须在 synchronized 中调用？因为"检查条件 → 进入等待"必须是原子的。如果允许无锁 wait，会出现这样的交错：消费者判断"队列空了"→（此刻生产者放入数据并 notify，但没人在等，通知消失）→ 消费者才执行 wait → 永久等待。持锁调用把"看条件"和"睡下去"绑成原子操作，通知才不会插在中间丢失。这是 wait 必须持锁的第一性原因，而不只是"API 硬性规定"。

3.3 notify 的唤醒顺序：规范不保证，实现近似 FIFO

  • notify 的唤醒顺序取决于JVM的实现，可能是随机，可能是顺序唤醒

  • 在hotspot 虚拟机中，是顺序唤醒，每次取出第一个等待的元素

这段话大方向正确，但要分"规范"与"实现"两层说清，工程上才敢放心依赖（或明确不依赖）：

  • 规范层面：JVM 规范与 Javadoc 都不保证任何唤醒顺序，notify() 只承诺"唤醒等待在该监视器上的某一个线程，选择是任意的（arbitrary）"。任何依赖唤醒顺序的程序都是错的。

  • 实现层面（HotSpot）：等待集内部是一条双向链表，线程调用 wait 时按先后顺序追加（近似 FIFO）；notify() 默认取出等待集头节点（最早开始等待的线程）移回竞争队列。但注意**“先被唤醒"不等于"先拿到锁”**：被移出的线程进入竞争队列后，要与正在 synchronized 入口排队的线程一起重新竞争，最终谁先拿到锁由锁的出队策略决定。所以即使在 HotSpot 上，也只是"唤醒顺序近似公平"，"锁的获得顺序"仍无保证。

另外 notify 与 notifyAll 的取舍：notifyAll 会把等待集整体唤醒，全员重新抢锁，抢不到的继续回等待集——正确但开销 $O(n)$（惊群）；notify 只唤醒一个，开销小，但若不同线程等待的条件谓词不同（比如生产者、消费者共用了同一个对象 wait），被唤醒的可能恰好是不满足条件的那类，通知被"无效消耗"，极端时造成部分线程永远等不到通知。安全准则：条件谓词存在多类等待者、或无法证明只有一类时，一律 notifyAll；能证明单类等待者时才用 notify 省开销。

3.4 虚假唤醒与标准模板

Javadoc 对 Object.wait 有一段必须重视的原文（翻译）：“线程也可能在没有被通知、中断或超时的情况下醒来，即虚假唤醒（spurious wakeup）。虽然实践中很少发生，但应用程序必须通过测试本应导致线程被唤醒的条件来防范它，条件不满足就继续等待。”

【实现层面】虚假唤醒的源头在操作系统层：POSIX 条件变量规范显式允许 pthread_cond_wait 无故返回（某些多核平台为性能放宽了"必须先发生 signal"的要求），JVM 落到 pthread 实现上，便把这个口子如实透传给了 Java 层，并以 Javadoc 条款要求调用方防御。

3.5 超时变体与中断语义

  • wait(long timeout)：超时后自动从等待集移出、重新竞争锁并返回。wait(0) 表示无限等待。注意超时返回与被 notify 返回在返回值上无法区分（返回类型是 void），"等到条件成立"还是"只是超时"必须靠重新检查条件谓词判断——这也是 while 模板的另一个必要性。

  • wait(long timeout, int nanos)：【真实源码】JDK 8 中只是把纳秒向上取整进位到毫秒后调用 wait(timeout)，无真实纳秒精度，工程上应视为与毫秒版等价。

  • 中断语义有个精细点：Javadoc 明确，wait 期间被中断时，InterruptedException 不会在锁被恢复之前抛出——即线程先重新拿到锁，再以持有锁的状态抛异常，保证异常抛出点仍在合法的临界区语境里。中断标志在异常抛出时被清除。

3.6 故障场景三：wait 未持锁抛 IllegalMonitorStateException

发生什么：新同事给老代码加"等待初始化完成"逻辑，把 obj.wait() 写在了没有 synchronized 包裹的方法里，联调时稳定抛 java.lang.IllegalMonitorStateException，HotSpot 下的异常消息是 “current thread not owner”。

为什么：wait/notify/notifyAll 的前置条件是当前线程必须是该对象监视器的持有者，JVM 在方法入口做所有权校验，不满足立即抛异常。典型触发方式有三种：其一，压根没在 synchronized 块里调用（本例）；其二，wait 与 notify 用的不是同一个对象（例如代码锁的是 lock 对象、却调用了 queue.wait()）；其三，嵌套锁下在最外层对象上 wait——wait 只释放并要求持有"被调用的那个对象"的锁，在内层对象上 wait 同样不满足所有权。

系统如何处理与恢复：这是显式异常，不会静默，通常在开发期就暴露，属良性故障。修复方法：让 wait/notify 与 synchronized 使用同一个对象并保证成对出现。预防上，可以把"锁对象"与"条件对象"封装在一起（或直接用 Condition，其 await/signal 前置条件是持有对应的 Lock，语义更显式），并统一团队模板：synchronized (lock) { while (!cond) lock.wait(); }。

3.7 故障场景四：丢失唤醒导致线程永久 WAITING

发生什么：线上一个消费线程突然"消失"，不再处理任何消息，线程栈显示它停在 WAITING (on object monitor)，栈顶是 Object.wait，且永远没有恢复的迹象。

为什么：这是丢失唤醒（lost wakeup）。wait/notify 的通知是无记忆的——如果 notify() 发生时等待集里没有线程，通知直接蒸发，不会记下来补偿后来的等待者。典型时序：消费者检查完条件（队列空）之后、还没执行到 wait() 之前的间隙，生产者完成了"放入数据 + notify"，此时通知发给了一个"还没开始等"的消费者；随后消费者进入 wait()，而生产者认为自己已经通知过了不再发——信号被永久错过。此外还有两类同源故障：用 notify 却存在多类等待者（3.3 节），以及被 notify 唤醒的线程因条件不满足回等待集时恰好没有其他线程再触发通知。

系统如何处理：没有系统兜底——WAITING 状态的线程不参与调度也不会超时，任务永久堆积，消费线程等价于泄漏。这类故障不会抛任何异常，只能靠线程栈发现。

如何恢复与根治：恢复上用 jstack 抓栈，定位"永久 WAITING 且无人 notify"的线程，评估后重启实例恢复消费。根治分三档：短期，在业务条件上加"哨兵唤醒"（写入方在状态可能变化时总是 notifyAll，配合 while 模板自愈）；中期，给无限等待加超时——wait(millis) 循环重查条件，即使信号丢失也能靠超时自愈；长期，直接放弃裸 wait/notify，改用 BlockingQueue（take/put 天然处理好条件与唤醒）或 ReentrantLock + 多个 Condition（每个条件独立等待集，signal 精确唤醒，无记忆问题则由"持锁检查条件"的约定覆盖）。裸 wait/notify 在新业务代码里几乎没有不可替代的场景。

3.8 故障场景五：嵌套锁下 wait 只释放一把锁

发生什么：线程 A 持有 lockA 后进入 synchronized(lockB)，在 lockB 上 wait()；线程 B 需要 lockA 才能制造条件唤醒 A。结果：A 在 lockB 的等待集里沉睡，但它仍持有 lockA；B 拿不到 lockA，永远造不成条件——形成"自己锁死自己"的变体死锁。

为什么：obj.wait() 只释放 obj 这一把监视器，对线程持有的其他锁不产生任何影响。很多资料说"wait 会释放锁"，省略了"仅限被调用的那个对象"这个定语，就是这类故障的认知根源。

如何恢复与预防：恢复同死锁处理（jstack 检测 Found one Java-level deadlock 或人工分析锁持有链，重启）。预防原则：等待条件的临界区要"最小持锁"——进入 wait 前确保只持有与条件相关的这一把锁；两把锁的协作场景，重构为单一锁对象，或改用 JUC 的显式锁结构。

3.9 wait/notify 与 Condition 的选型

ReentrantLock 配套的 Condition 是 wait/notify 的 JUC 对应物，差异决定了选型：

维度 synchronized + wait/notify ReentrantLock + Condition
等待集数量 每对象仅一个等待集 一个锁可派生多个 Condition，按条件分队列
唤醒精度 notifyAll 惊群 / notify 易错 signal 精确唤醒指定条件的等待者

选型建议：单条件、简单互斥的场景用 synchronized + while + notifyAll 模板即可；多条件协作（如有界缓冲区的"非满""非空"两个条件）、需要公平性或精确唤醒的，用 Condition；纯数据交接用 BlockingQueue，连锁都不必手写。

四、加入（join）：等待另一个线程终止

作用：让当前线程等待另一个线程执行完毕后再继续执行。

原文有一个流传很广的说法需要修正：“调用 join() 的线程拥有优先使用 CPU 时间片的权利，其他线程需要等待 join() 调用线程执行结束后才能继续执行”——这是误传。join 与 CPU 时间片、优先级毫无关系：调用 t.join() 只是让当前线程阻塞等待目标线程 t 终止，其他线程照常调度，t 该抢时间片照样抢。

【真实源码】以上是 java.lang.Thread 的 join(long)，JDK 8 至 JDK 21 基本未变（仅变量修饰等微调）。Javadoc 对此也有官方注解（翻译）："该实现基于 this.isAlive 条件对 this.wait 的循环调用。线程终止时会调用 this.notifyAll。"三处源码细节值得逐条读透：

  1. synchronized 修饰：join 锁的是目标线程对象自身（synchronized(t)）。这解释了 join 的"不释放锁"到底指什么——它等待期间释放的是 t 的监视器（内部 wait 释放），对调用者自己的业务锁不碰。副作用是：若你的业务代码也 synchronized(t) 并长期持有，t.join() 会先卡在锁竞争上（BLOCKED 而非 WAITING），这也正是 Javadoc 建议不要在 Thread 实例上自行使用 wait/notify 的原因——避免与 join 的内部用法互相干扰。

  2. while (isAlive()) 而不是 if：与 3.4 节的 while 模板同源。理由有三：虚假唤醒要重新检查；其他线程可能对 t 调用 notify()/notifyAll()（Javadoc 建议别这么做，但拦不住），误唤醒后必须回查 isAlive；带超时版本每次醒来要重算剩余等待时间（delay = millis - now），时间没等够就继续 wait(delay)。

  3. isAlive() 是唯一条件谓词：join 等的不是"任务执行成功"，只是"线程死了"。run() 抛出未捕获异常同样算终止，join() 照样正常返回——异常被吞进线程的死亡过程。需要感知执行结果或异常时，join 不是合适的工具（见 4.6）。

4.2 为什么 join 能"等到线程死"：终止通知机制

join 内部 wait(0) 无限等待，那谁来唤醒它？【实现层面】HotSpot 在线程退出路径（JavaThread::exit 过程中）会以该线程的 Thread 对象为目标执行一次 notifyAll，即源码层面的 ensure_join 逻辑：线程终止时对 threadObj 加监视器锁、清除引用、设置死亡标记，然后通知所有在该对象上等待的线程。Javadoc 里 “As a thread terminates the this.notifyAll method is called” 说的就是这件事。

所以 join 的完整闭环是：主线程 t.join() → 对 t 加锁 → while(isAlive()) wait(0) 进入 t 的等待集 → t 的 run() 结束 → JVM 在 t 终止时 t.notifyAll() → 主线程被唤醒重新抢 t 的锁 → isAlive() 为 false，循环退出，join 返回。join 不是一个独立机制，只是"以 Thread 对象为条件对象的 wait/notify"——理解这一点后，join 的一切行为（可中断、超时变体、状态迁移）都能从 wait 推导出来。

4.5 故障场景六：无超时 join 挂死，服务假死

发生什么：主线程（或调度线程、发布脚本触发的预热逻辑）调用 t.join() 等一个数据加载线程，某天该线程内部因为下游配置错误进入死循环/网络调用无超时地挂住。结果主流程永久停在 WAITING，服务"进程在、但不干活"，探针超时告警，发布流程卡死。

为什么：join() 等价于 wait(0) 无限等待，唯一解除条件是目标线程终止。目标线程的任何非终止型故障（死循环、无超时的阻塞 IO、内部又 join 了别人形成 join 链）都会让等待方永久挂起。这类故障的共同根因是：把"子线程必然会结束"当成了无需验证的假设，而这个假设在分布式环境里几乎必然在某天被打破（网络无超时、依赖死锁、逻辑 bug）。

系统如何处理：无任何自动恢复——WAITING 不超时、无告警钩子，只能靠外部探针或人工发现。恢复手段：jstack 确认主线程停在 join、目标线程栈停在何处（死循环栈顶在业务方法、IO 挂死栈顶在 socketRead0），修复后重启。

如何恢复与根治：根治三件套——其一，永远用带超时的 join(millis) 并 isAlive() 复查，超时分支明确降级（默认值、告警、重试）；其二，更推荐用 CountDownLatch：latch.await(timeout, TimeUnit.SECONDS) 返回布尔值，语义上"等到没等到"一目了然，且不受"在 Thread 对象上做锁操作"的副作用影响；其三，异步任务一律 CompletableFuture.get(timeout)，还能拿到异常。编排"主线程等一批任务"的场景，CountDownLatch/CompletableFuture.allOf 全面优于逐个 join。

4.6 join 的适用边界：拿不到结果，也感知不到异常

join 的返回值是 void、目标线程的异常随线程死亡被吞掉（除非注册 UncaughtExceptionHandler），所以它只适合纯时序编排——“必须先做完 A 再做 B”，不关心 A 的产出与成败。需要结果或异常传播时，Future.get()（抛 ExecutionException 携带子任务异常）、CompletableFuture.thenApply 是正确工具。还有一个边界坑：Thread.currentThread().join()（自己 join 自己）会导致永久自锁——当前线程永远等不到自己终止，这类代码通常来自把线程引用传错位置的 bug，代码评审时值得专设一条检查。

五、让步（yield）：对调度器的一次提示

作用：提示调度器 Thread.yield() 让当前线程主动让出 CPU 资源，给其他线程运行的机会。Javadoc 原文（翻译）：“向调度器提示当前线程愿意让出对处理器的当前使用。调度器可以随意忽略这个提示。”

【真实源码】JDK 各版本的声明：

提出申请释放 CPU 资源，至于能否成功释放由 JVM 与操作系统决定。

5.1 操作系统层与优先级的真相

【实现层面】HotSpot 上，Linux 将 yield 落到 sched_yield()，Windows 落到 SwitchToThread() 一类原语：让出后当前线程回到就绪队列参与下一轮竞争，若没有其他可运行线程，它可能立刻再次被调度——这就是"yield 后输出顺序几乎不变"的底层原因。注意 yield 与 sleep 有个关键差异：yield 后线程仍是 RUNNABLE，它只是没被选中执行的那一刻，而不是"等待状态"；sleep 则实实在在进入 TIMED_WAITING。

老资料常说 yield “给相同优先级或更高优先级的线程机会”，这是早期文档的历史说法，现行 Javadoc 已无此表述，规范层面没有任何优先级相关承诺。

那线程优先级本身靠不靠谱？【实现层面】一个少有人知的事实：HotSpot 默认把 JavaPriority1_To_OSPriority 到 JavaPriority10_To_OSPriority 这组参数设为 -1，含义是不把 Java 优先级映射到操作系统线程优先级。也就是说默认配置下，setPriority 基本不影响 CPU 调度，Java 优先级更多是 JVM 内部记录与个别内部机制的参考值。即便映射生效，调度器给的也只是概率倾斜而非承诺。【理论分析】假如某调度器按权重 $w_i = p_i$ 线性分配时间片，优先级 10 与 5 的两个线程时间占比为：

$$R=\frac{p_{high}}{p_{high}+p_{low}}=\frac{10}{10+5}\approx 66.7%$$

【示例数据】这个 66.7% 只用于说明"概率倾斜、统计上才可观察"的含义，并非任何真实 JVM 的行为。结论：优先级与 yield 一样，只能影响"可能性"，永远不能作为正确性依赖。

Yield 是一种启发式尝试，旨在改善线程之间的相对进展，否则会过度使用 CPU。 它的使用应与详细的分析和基准测试相结合，以确保它确实具有预期的效果。很少适合使用这种方法。 它对于调试或测试目的可能很有用，它可能有助于重现由于竞争条件引起的错误。 在设计并发控制结构（例如java.util.concurrent.locks包中的结构）时，它也可能很有用。

（以上为 Javadoc 对 yield 的官方评价，要点翻译如下。）

  1. 不确定性

    • yield方法只是一个提示性的方法，它不能保证当前线程往往会让出 CPU 资源，也不能保证其他线程往往会被选中执行。因此，在使用yield方法时，不能依赖它来实现特定的线程执行顺序。

  2. 性能影响

    • 频繁地调用yield方法可能会对性能产生一定的影响。因为每次调用yield方法都会导致当前线程进入就绪状态，然后由调度器重新选择下一个要执行的线程，这个过程可能会消耗一定的时间和系统资源。

  3. 优先级问题

    • yield方法并不能改变线程的优先级。如果一个线程的优先级较高，即使其他线程调用了yield方法，调度器仍然可能会优先选择高优先级的线程执行。

那 yield 什么时候才真的有用？官方给的定位很克制：调试/测试中放大竞争窗口、复现竞态问题；以及自研并发结构里做自旋退避。JDK 9+ 的自旋场景有了更好的选择：Thread.onSpinWait()，它编译为 x86 的 PAUSE 指令（ARM 上是 YIELD 提示），明确告诉 CPU"这是自旋等待"，能降低流水线功耗与对同核超兄弟线程的干扰——自旋微调用它，别用 yield。

5.3 故障场景七：yield 忙等烧 CPU

发生什么：一个"等配置刷新"的线程写成 while (!refreshed) { Thread.yield(); }，上线后该核 CPU 长期 100%，同宿主其他服务延迟上升。

为什么：多核机器上 yield 后几乎总有核可用，调度器转一圈又把它挑起来，循环退化成全速自旋——yield 既没让线程进入任何等待状态，也没降低它的调度优先级，只是"绕了一圈回来接着烧"。这与 2.4 节 sleep 轮询是同源问题的两个极端：sleep 版本浪费时延、yield 版本浪费 CPU。

系统如何处理与恢复：操作系统无感知、不会限流，靠 CPU 监控告警发现；重启即恢复，但代码不修必然复发。根治按等待时长选型：微秒级等待用 LockSupport.parkNanos(n) 或 Thread.onSpinWait()；毫秒级及以上用条件等待或 CompletableFuture；配置刷新这类场景用监听回调/CountDownLatch，等待成本为零。原则一句话：任何等待都应该"睡着等"，而不是"醒着转"。

三个方法都有"带时间参数"的变体，但超时那一刻发生的事完全不同，这是选型时最常被忽略的细节：

6.5 总结与建议

  • 四者的本质区别在是否释放锁与是否阻塞：wait() 释放该对象锁并进入等待集；sleep()/join() 不释放调用者的业务锁但阻塞当前线程（join 内部对目标 Thread 对象做的是 wait 语义）；yield() 既不阻塞也不释放锁，只是让出一次调度机会。

  • 状态对照：sleep(millis)、wait(timeout)、join(millis) 进入 TIMED_WAITING；无参 wait()/join() 进入 WAITING；yield() 始终处于 RUNNABLE。

  • 选型建议：定时节奏用 sleep()；生产者-消费者等线程间协作用 wait()/notifyAll()（while 守卫）或更安全的 Condition/BlockingQueue；等待子任务完成用带超时的 join() 或 CountDownLatch/CompletableFuture；不要指望 yield() 控制执行顺序，需要确定性先后时用 join() 或 CountDownLatch 更可靠。

  • 四条高频事故守则，评审时可当检查清单：临界区内不 sleep；wait/notify 必须同锁且 while 守卫；join 必须带超时或先验证子线程必然终止；任何等待都要有"睡着等"的形态，禁止裸轮询与 yield 忙等。

  • 中断是一条贯穿四者的协作通道：sleep/wait/join 都通过 InterruptedException 响应取消，捕获时要么上抛要么 Thread.currentThread().interrupt() 恢复标志，唯独不要静默吞掉。
