LangChain 框架功能详解和使用案例

发表于2025-11-06|更新于2026-09-02
|AIAgent
|浏览量:

概述与核心价值

LangChain 是当前主流的开源大语言模型应用开发框架，核心思路是"模块化抽象 + 流水线编排"：它把模型接入、提示词管理、文档检索、状态记忆、工具调用与逻辑控制流拆成标准组件，开发者通过简单组合，就能把一个"只会聊天的大模型"变成可查库、可检索、记得住上下文、能自主决策的业务应用，例如智能客服、知识库问答、文档摘要器和自动化代理（Agents）。

与直接裸调模型 API 相比，LangChain 的价值体现在三点：

  • 统一接口：OpenAI、千问、Ollama、Hugging Face、Google 等模型提供商的接入方式一致，切换模型只改一行代码，方便做成本控制与降级方案；

  • 标准抽象：Prompt、Chain、Agent、Memory、Tool 等概念具备统一的组合方式和生命周期，工程结构清晰、易测试易维护；

  • 生态丰富：官方与社区提供了向量库、关系数据库、消息历史存储、各类工具的海量现成集成，避免重复造轮子。

典型应用场景与组件对应关系如下：

应用场景 使用组件
智能客服 Memory + Chain + LLM
知识库问答 Retrieval + RAG + Vector DB
自动化办公助理 Agents + Tools（Gmail、Excel、API）
代码生成助手 LLM + Prompt + OutputParser
多轮推理任务 Agents + Plan-and-execute

下文围绕模型管理、提示工程、链式编排、智能决策、工具调用、状态记忆、上下文理解、状态图（LangGraph） 八个核心维度逐一拆解，最后给出单/多智能体实战案例与选型建议。

1. 模型管理（LLM）：统一接口，屏蔽厂商差异

LangChain 的 Model 层把各家模型包装为两类统一接口：

  • 文本生成（LLM/ChatModel）：ChatOpenAI、ChatTongyi（Qwen）、ChatOllama、ChatAnthropic；

  • 向量化（Embedding）：OpenAIEmbeddings、DashScopeEmbeddings（Qwen）、OllamaEmbeddings；

  • 多模态：ChatGoogleVertexAI（支持图像 + 文本）。

其中 Ollama 用于本地部署，数据不出内网、零 API 费用，是开发验证阶段的常用选择。以下示例在同一链条上使用对话模型 qwen3:4b 与 embedding 模型 nomic-embed-text（默认服务地址 http://localhost:11434），完成"文档切分 → 向量化入库 → 检索 → 问答"的完整 RAG 流程：

这段代码体现了两个常用技巧：一是 RecursiveCharacterTextSplitter(chunk_size=300, chunk_overlap=50)，按 300 字符切块、保留 50 字符重叠，防止语义在切点处被截断；二是用 search_kwargs={"k": 3} 控制召回条数——k 越大上下文越全但耗时越长，还容易引入噪声，3 是性价比常见的取值。

2. 提示工程（Prompt）：从字符串模板到多轮消息

提示层解决"如何把需求稳定地表达给模型"，LangChain 提供四类模板：

模板 作用
PromptTemplate 传统字符串模板，适合单轮问答
ChatPromptTemplate 多轮消息模板（System / Human / AI），贴近 Chat 模型
FewShotPromptTemplate 内置少量示例的提示，引导输出格式
MessagesPlaceholder 动态消息插槽，用于注入历史对话、Agent 中间推理过程

实际项目中用得最多的是 ChatPromptTemplate。以 SQL 查询 Agent 为例：业务规则（先查 users 表拿 id、再关联 orders 表、不要输出 SQL）全部写进 system 消息，MessagesPlaceholder("agent_scratchpad") 则是给 Agent 预留的"思考草稿区"——它会被自动填充为工具调用与观察结果的交替消息，让模型知道"目前已经查到了什么"：

提示模板同样可以定制"记忆摘要"的生成方式。ConversationSummaryMemory 默认用自己的摘要 prompt，也可传入自定义模板，把"需要保留的关键信息类型"写清楚（如用户姓名、订单、问题类型），摘要质量会明显提升：

排坑提示：system 消息中约束的越具体，模型行为越稳定。例如"不要输出 SQL 信息""只用中文返回"这类指令，能显著减少 Agent 把内部推理步骤暴露给用户的情况。

3. 链式编排（Chain）：把组件串成流水线

Chain 是 LangChain 最核心的抽象——把"取模版 → 填变量 → 调模型 → 解析输出"等步骤串联为可复用流水线。常用链包括：

  • LLMChain：Prompt + LLM 的最简组合；

  • SequentialChain：多步骤按顺序执行，前一步输出作为后一步输入；

  • RetrievalQA：RAG 问答链，自动完成"检索 → 拼接上下文 → 问答"；

  • ConversationalRetrievalChain：带记忆的 RAG，支持多轮追问；

  • 自定义 Chain：新版推荐直接用 | 管道符组合 Runnable。

知识库问答最简单的方式是直接使用 RetrievalQA：

chain_type="stuff" 表示把检索到的文档"一股脑塞进"提示词，适合文档量小的场景；文档量大时可换 map_reduce 或 refine 策略分块处理。

新版 LangChain 更推荐用 | 管道符（LCEL 语法） 手动构建链。下面的"路由链"先让 LLM 输出三类标签之一，再接 StrOutputParser() 把输出转成纯字符串，供后续分支判断使用——这就是"Chain 风格路由"的基石：

排坑提示：路由 prompt 必须强调"严格输出三者之一"，否则模型偶尔输出解释性文字，导致下游分支判断失败；取结果后 strip() 去除首尾空白也是必要防御。

4. 智能决策（Agent）：让 LLM 自主决定调用谁

Chain 的执行路径是开发者写死的；而 Agent 把"下一步做什么"交给模型判断——模型根据用户意图在工具列表中做选择，AgentExecutor 驱动 “Thought → Action → Observation” 循环，直到得到最终答案。常用 Agent 类型：

类型 机制 适用
openai-tools OpenAI Function Calling 风格（推荐） 工具较多、需结构化传参
react ReAct 思维链推理 通用场景
self-ask-with-search 自问自答 + 搜索 复杂事实查询

排坑提示：handle_parsing_errors=True 建议常开——本地小模型输出格式不稳定，开启后解析失败不会直接抛异常，而是把错误回传模型让它重试；verbose=True 便于观察 Thought/Action 过程，排查"为什么没走预期工具"非常有效。

5. 工具调用（Tool）：函数即工具

工具是 Agent 的"手"。@tool 装饰器能把任意 Python 函数变成工具，函数的 docstring 会被当作工具描述提供给 LLM 做选择判断，因此描述要写清楚"这个工具能干什么、适合什么问题"：

两个实用细节：一是工具内部要自行捕获异常并返回兜底数据（如 detect_scenes 出错时返回模拟片段），因为 Agent 依赖工具返回值继续推理，抛异常会中断整个循环；二是复杂业务函数用 @tool 声明式包装，简单场景也可以用 Tool(name=..., func=..., description=...) 直接实例化，两种写法等价。

6. 状态记忆（Memory）：让 LLM 记住上下文

大模型本身无状态，多轮对话"失忆"是刚需痛点。Memory 层负责三件事：保存对话历史（让 LLM 知道上下文）、维护状态（跟踪用户偏好、任务进度）、支持多轮交互（如填表、分步任务）。不同记忆类型的取舍：

类型 适用场景 特点
ConversationBufferMemory 简单对话 保存全部历史（可能超 token）
ConversationBufferWindowMemory 长对话 仅保存最近 N 轮
ConversationSummaryMemory 超长对话 用 LLM 生成摘要
EntityMemory 实体跟踪 记住人物/物品属性
VectorStoreRetrieverMemory 知识库问答 从向量库检索相关记忆

按对话长度与用途进一步给出推荐对照：

场景 推荐 Memory 类型
简单聊天机器人 ConversationBufferMemory
长对话（>10轮） ConversationBufferWindowMemory(k=5)
超长对话（>50轮） ConversationSummaryMemory
角色扮演/实体跟踪 ConversationEntityMemory
知识库问答 VectorStoreRetrieverMemory
生产环境持久化 RedisChatMessageHistory

窗口记忆：ConversationBufferWindowMemory(k=3) 只保留最近 3 轮，防止 token 超限，代价是最早的内容被丢弃：

摘要记忆：对话超过 50 轮时，即使窗口记忆也不够用——ConversationSummaryMemory 让 LLM 边聊边把历史压缩成摘要，几乎不占 token：

排坑提示（摘要记忆最常见）：return_messages=True 时记忆以 List[BaseMessage] 消息对象返回，必须配合 MessagesPlaceholder("chat_history") 注入才能被 Chat 模型接受；如果传入 summary_prompt 自定义摘要模板，它只对"独立存储"生效，需要自行获取最近几轮切片时按消息对象遍历（如 history = "\n".join(...) 转文本）。而 return_messages=False 时返回纯文本摘要，不需要注入 Placeholder。

Agent 中的记忆：让 Agent 记住工具调用历史同样简单——memory_key="chat_history" + return_messages=True，再在 prompt 中预留 MessagesPlaceholder("chat_history")：

排坑提示（多轮 Agent 最常见的隐性 Bug）：memory_key、MessagesPlaceholder("chat_history")、以及 prompt 模板中的变量名三者必须完全一致，否则历史注入不进去，模型"失忆"且不报错。

7. 上下文理解：查询重写消除指代

多轮对话中用户常说"它质量怎么样"“那个商品退了没”，直接拿原句去检索知识库或查库几乎必然失败。通用的解法是先把问题改写为无指代的独立问题，再执行检索。原笔记提供了三种上下文来源：

方式一：结合摘要 + 最近消息，由 LLM 重写查询（最通用，处理"这个""那个"等模糊指代）：

方式二：规则解析用户身份后拼进查询（零成本，适合提取姓名等固定模式信息）。从历史消息中扫描"我是/我叫/我的名字是"关键词提取用户名，再拼成 （当前用户姓名：xxx）原问题，让下游 SQL 查询能直接命中用户维度；规则匹配不上的场景可升级为 NER（命名实体识别）：

方式三：从摘要记忆中提取。把最近 N 轮对话交给 LLM 做信息抽取（chain = prompt | llm | StrOutputParser()），返回结构化结果。与方式一的差别在于：方式一改写问题本身，方式三抽取的是"用户档案"类事实（如姓名、订单号），抽取结果可复用、可入库。

排坑提示：查询重写前后各打印一行调试日志（[RAG 调试] / [DB 调试]）非常有用——检索效果差时，能立刻定位是"重写坏了"还是"向量库没召回"。

8. 状态图（LangGraph）：可控、循环、分支、多智能体

当流程需要循环、条件分支、并行执行、多智能体协作时，线性 Chain 与自由行动的 Agent 都难以表达——前者写不出循环，后者不可控。LangGraph 以"状态机"方式建模：每个节点读写共享 State，边决定流转方向，天然支持条件分支、循环与多智能体路由，且可中断、可恢复、可调试。最小可用图只有三步：

关键点：Annotated[list, add_messages] 声明了消息的"累积式"更新策略——每个节点返回的新消息自动追加到历史，而不是覆盖；START / END 是内置的入口与出口哨兵。复杂场景在此基础上增加节点与条件边即可（见下文多智能体案例）。

实战案例：单/多智能体智能客服

综合案例（完整工程见 GitHub: agent-flow-demo）的业务规则：订单/用户/状态 → 查 SQLite；退换货政策/产品说明/FAQ → 查 RAG 知识库（knowledge_base 下的 return_policy.txt、product_guide.txt）；其余 → 直接 LLM 闲聊。三种实现共用此规则，但架构不同：

① 单智能体（LangChain Agent）：逻辑收敛于一个 Agent，靠工具 description 自主路由，支持多轮记忆。优点是实现最快、代码最少；缺点是推理路径不可控——复杂问题可能来回试错多个工具，且所有逻辑耦合在一个 Agent 的上下文里。

② 多智能体（LangGraph）：把系统拆成 Router、DB、RAG、General 四个专业节点，由路由智能体先分类，再沿条件边分发到对应节点执行，路由结果写入 State 驱动流转：

相比单 Agent 的优势：路由用 with_structured_output 强约束输出格式（不会返回非法分类）；每个专业智能体只负责一类任务，上下文更短、提示更聚焦，推理质量与可维护性都更好；路由节点显式化后，问题出在哪一步一目了然。含自动摘要记忆、支持多轮上下文理解的升级版见 hybrid_langgraph_summarized_multi_agent.py。

③ 多智能体（Chain 风格）：不使用 Agent 框架，router_prompt | llm | StrOutputParser() 完成分类后，直接 if/elif 调用各子系统——DB 与 RAG 分支用 RunnableLambda 包装成 Runnable，与其他 Chain 统一 invoke 风格：

该方案最轻量、路径完全可控、无 Agent 框架开销，适合流程固定、无需模型临场发挥的内部系统；代价是每加一个分支都要手写路由判断，扩展性弱于 LangGraph。

此外仓库还提供 base_demo.py：加载 PDF（PyPDFLoader）→ RecursiveCharacterTextSplitter 切块 → Chroma 入库 → create_stuff_documents_chain + create_retrieval_chain 组装标准 RAG 问答链，是上手 RAG 的最小完整范例，建议先跑通它再进入多智能体改造。

总结与建议

  • 选型：线性固定流程用 Chain（| 管道最简洁）；需要 LLM 临场决策、调多个工具用 Agent + AgentExecutor；含分支、循环、多智能体协作或需中断恢复的场景，直接上 LangGraph。

  • 模型与向量库解耦：Chat/Embedding 接口在多厂商间一致，本地用 Ollama 验证、生产平滑切云厂商；embedding 模型决定 RAG 召回上限，分块大小与 k 值值得单独调优。

  • 记忆与提示词三处一致：memory_key、MessagesPlaceholder("chat_history")、prompt 变量名必须对齐，这是多轮 Agent 最常见的隐性 Bug；解析异常记得开 handle_parsing_errors=True。

  • 查询重写是 RAG 的隐形瓶颈：多轮对话先做指代消解再检索，配合调试日志，能显著提升知识库问答命中率。

  • 注意版本拆分：新版本组件拆分到 langchain_community、langchain_ollama、langchain_chroma 等子包，旧教程中的统一导入写法已过时，报 ModuleNotFoundError 时优先检查导入路径。
