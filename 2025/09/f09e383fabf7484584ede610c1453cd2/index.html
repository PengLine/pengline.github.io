Java 多线程之有序执行的实现方案

发表于2025-09-28|更新于2026-09-08
|Java多线程
|浏览量:

线程在启动以后，并不是第一时间就会立马执行。而是要等待CPU的一个资源调度，而CPU调度的顺序是通过复杂算法计算得到的。

等启动的线程得到CPU指令后，才和主线程做一个切换，执行run方法。这就造成了每次我们执行的结果都是随机的。

可以通过一些方式控制线程执行的顺序：

核心思想：“线程有序执行”本质上是将并行的线程流转换为串行依赖图。每条线程作为图中的一个节点，边表示“前置任务完成后才能启动/继续”。实现方式可分为三类：

  1. 线程级串行：join() 让调用线程等待目标线程结束后再继续；

  2. 同步原语链：Object.wait/notify、Condition、CountDownLatch、CyclicBarrier、Semaphore 通过状态传递实现顺序控制；

  3. 队列调度：ExecutorService.newSingleThreadExecutor() 利用 FIFO 任务队列天然保证提交顺序。

选择方案时应区分“线程启动顺序”与“线程执行完成顺序”。join() 控制的是完成顺序，而 ExecutorService 控制的是启动顺序。

join()（优先执行）

调用线程需等待该join()线程执行完成后，才能继续用下其他线程。

底层通过wait和notify实现，保证线程执行顺序

join() 串行模型

Thread.join() 内部调用 wait() 阻塞当前线程，目标线程终止时由 JVM 自动调用 notifyAll() 唤醒所有等待线程。它强制线程按“完成顺序”串行化，但代价是线程必须依次创建/启动，无法真正并行。

sequenceDiagram
    participant Main as 主线程
    participant T1 as 线程1
    participant T2 as 线程2
    participant T3 as 线程3

    Main->>T1: start()
    Main->>T1: join()
    Main-->>Main: 阻塞
    T1->>T1: 执行任务1
    T1-->>Main: 终止，notifyAll
    Main->>T2: start()
    Main->>T2: join()
    T2->>T2: 执行任务2
    T2-->>Main: 终止
    Main->>T3: start()
    T3->>T3: 执行任务3

注意：join() 不会释放已持有的锁。如果在同步块内调用 join()，可能导致死锁。

Object（等待+唤醒）

Object的方法，是让当前线程进入等待状态，释放它所持有的锁。“直到其他线程调用此对象的 notify() 方法或 notifyAll() 方法”，当前线程被唤醒(进入“就绪状态”)。

所有的实例都有一个等待队列，它在实例的wait方法执行后停止操作的线程的队列。

执行wait方法后，线程便会暂停操作，进入等待队列

Object.wait/notify 链式时序

该示例通过两把“对象锁”demo1、demo2 构建了一条依赖链：线程 3 等待线程 2 通知，线程 2 等待线程 1 通知。由于 wait() 会释放锁，后续线程获取锁后即可发出下一条唤醒信号。

sequenceDiagram
    participant T1 as 线程1
    participant T2 as 线程2
    participant T3 as 线程3

    T3->>T3: synchronized(demo2) wait()
    T3-->>T3: 释放 demo2 锁并等待
    T2->>T2: synchronized(demo1) wait()
    T2-->>T2: 释放 demo1 锁并等待
    T1->>T1: 获取 demo1 锁，执行任务1
    T1->>T2: notify() demo1
    T2->>T2: 被唤醒，获取 demo1 锁，执行任务2
    T2->>T3: notify() demo2
    T3->>T3: 被唤醒，获取 demo2 锁，执行任务3

关键细节：

  • 必须先启动最后等待的线程，确保 wait() 在对应 notify() 之前执行；
  • wait() 必须在循环或确定的状态下使用，以防御虚假唤醒；
  • notify() 只唤醒一个等待线程，若存在多个消费者应使用 notifyAll()。

ExecutorService（单线程池）

利用并发包里newSingleThreadExecutor产生一个单线程的线程池，而这个线程池的底层原理就是一个先进先出（FIFO）的队列。

代码中executor.submit依次添加了123线程，按照FIFO的特性，执行顺序也就是123的执行结果，从而保证了执行顺序。

ExecutorService FIFO 调度模型

newSingleThreadExecutor() 内部使用 ThreadPoolExecutor + 无界 LinkedBlockingQueue（FIFO）。当核心线程数为 1 且未关闭时，所有 submit() 任务按提交顺序进入队列，由唯一的 Worker 线程依次消费。因此它天然保证的是任务启动顺序，而不是多个 CPU 核上的并行执行。

sequenceDiagram
    participant Main as 主线程
    participant Q as 任务队列
    participant W as 唯一 Worker 线程

    Main->>Q: offer(任务2)
    Main->>Q: offer(任务1)
    Main->>Q: offer(任务3)
    W->>Q: take()
    Q-->>W: 任务2
    W->>W: 执行任务2
    W->>Q: take()
    Q-->>W: 任务1
    W->>W: 执行任务1
    W->>Q: take()
    Q-->>W: 任务3
    W->>W: 执行任务3

注意：单线程池保证顺序的前提是任务之间没有依赖阻塞。若某个任务死循环或阻塞，后续任务将全部被拖慢。

Condition（条件变量）

通常与锁关联。需要在多个 Condition 中共享一个 Lock 实例时，可将其传递给构造方法；否则 Condition 会自己生成一个 ReentrantLock 实例。

  • **await()**方法类似于Object类中的wait()方法。

  • **await(long time,TimeUnit unit)**方法类似于Object类中的wait(long time)方法。

  • **signal()**方法类似于Object类中的notify()方法。

  • **signalAll()**方法类似于Object类中的notifyAll()方法。

Condition 条件变量时序

Condition 与 ReentrantLock 配合使用，将“锁”与“等待/通知”解耦。示例中通过 threadFlag 记录当前应执行的线程编号，每个线程先判断状态，不符合则进入对应条件队列等待，被唤醒后继续执行并发出下一条信号。

sequenceDiagram
    participant L as ReentrantLock
    participant C1 as Condition1
    participant C2 as Condition2
    participant T1 as 线程1
    participant T2 as 线程2
    participant T3 as 线程3

    T1->>L: lock()
    T1->>T1: 执行任务1
    T1->>C1: signal()
    T1->>L: unlock()
    T2->>L: lock()
    T2->>T2: threadFlag == 1，继续执行
    T2->>T2: 执行任务2
    T2->>T2: threadFlag = 2
    T2->>C2: signal()
    T2->>L: unlock()
    T3->>L: lock()
    T3->>C2: await()（若 threadFlag != 2）
    C2-->>T3: signal() 唤醒
    T3->>T3: 执行任务3
    T3->>L: unlock()

最佳实践：使用 Condition.await() 时应配合 while 循环判断条件，以应对虚假唤醒；状态变量建议用 volatile 或原子类型保证可见性。

CountDownLatch（计数）

位于java.util.concurrent包下，利用它可以实现类似计数器的功能。

CountDownLatch 计数传递链

CountDownLatch 基于 AQS 的共享模式实现：计数器为 0 时，所有调用 await() 的线程被同时放行；否则线程进入等待队列。该示例用两个 CountDownLatch 把三线程串成“前驱完成 → 后继放行”的链。

sequenceDiagram
    participant C1 as CountDownLatch c1
    participant C2 as CountDownLatch c2
    participant T1 as 线程1
    participant T2 as 线程2
    participant T3 as 线程3

    T2->>C1: await()
    T3->>C2: await()
    T1->>T1: 执行任务1
    T1->>C1: countDown()
    C1-->>T2: 计数归零，放行
    T2->>T2: 执行任务2
    T2->>C2: countDown()
    C2-->>T3: 计数归零，放行
    T3->>T3: 执行任务3

注意：CountDownLatch 的计数器一次性，减到 0 后无法重置。若需要重复使用，应使用 CyclicBarrier 或 Phaser。

CyclicBarrier（回环栅栏）

通过它可以实现让一组线程等待至某个状态之后再全部同时执行。

当所有等待线程都被释放以后，CyclicBarrier可以被重用。当调用await()方法之后，线程就处于barrier了。

CyclicBarrier 回环栅栏模型

CyclicBarrier 通过“等待集满 N 个线程后统一放行”实现同步。示例中 barrier1 的参与数为 2，因此线程 1 打印后需等待线程 2 也到达；二者同时越过后，线程 2 继续执行并在 barrier2 处等待线程 3，形成“阶段性会合并继续”的有序控制。

sequenceDiagram
    participant B1 as CyclicBarrier barrier1(2)
    participant B2 as CyclicBarrier barrier2(2)
    participant T1 as 线程1
    participant T2 as 线程2
    participant T3 as 线程3

    T1->>T1: 执行任务1
    T1->>B1: await()
    T2->>B1: await()
    B1-->>T1: 集满 2 个线程，放行
    B1-->>T2: 集满 2 个线程，放行
    T2->>T2: 执行任务2
    T2->>B2: await()
    T3->>B2: await()
    B2-->>T2: 集满 2 个线程，放行
    B2-->>T3: 集满 2 个线程，放行
    T3->>T3: 执行任务3

关键细节：

  • CyclicBarrier 支持重置和复用（调用 reset()），但重置会触发 BrokenBarrierException；
  • 任一等待线程被中断或超时，栅栏会被“破坏”，其他线程也会收到 BrokenBarrierException。

Semaphore（信号量）

是一个计数信号量，包含一组许可证。每个acquire()都会阻塞，直到获取一个可用的许可证，每个release()都会释放持有许可证的线程，并且归还一个可用的许可证。

acquire()：当前线程尝试阻塞地获取 1 个许可证，若获取到可用许可证则停止等待并继续执行。

release()：当前线程释放 1 个可用的许可证。

Semaphore 许可证传递链

Semaphore 维护一组许可证。示例中将两个信号量初始化为 0，线程 1 先 release() 发放一个许可证，线程 2 acquire() 拿到后才继续执行，并向下一个信号量发放许可证，以此类推。它本质上是把“前驱完成”这一事件抽象为许可证的释放。

sequenceDiagram
    participant S1 as Semaphore semaphore1(0)
    participant S2 as Semaphore semaphore2(0)
    participant T1 as 线程1
    participant T2 as 线程2
    participant T3 as 线程3

    T2->>S1: acquire()
    T3->>S2: acquire()
    T1->>T1: 执行任务1
    T1->>S1: release()
    S1-->>T2: 许可证可用，放行
    T2->>T2: 执行任务2
    T2->>S2: release()
    S2-->>T3: 许可证可用，放行
    T3->>T3: 执行任务3

注意：release() 不强制要求调用线程必须先 acquire()，因此使用时要避免误释放导致顺序错乱。

方案选型对比

方案 控制粒度 是否可复用 适用场景 注意点
join() 线程完成顺序 不可复用 简单串行、父子线程依赖 持有锁时调用易死锁
Object.wait/notify 对象监视器 不可复用 两个线程交替、简单条件等待 必须处理虚假唤醒，注意 notify 顺序
ExecutorService.newSingleThreadExecutor() 任务提交顺序 线程池可复用 任务天然可串行、无强依赖 单点阻塞会拖慢整个队列
Condition 锁 + 多个条件队列 不可复用 需要精确控制多个条件的复杂同步 建议使用 while 判断条件
CountDownLatch 计数器 一次性 一个线程等待多个前置任务完成 计数到 0 后不能重置
CyclicBarrier 栅栏回合点 可复用 多阶段流水线、分批集结 注意 BrokenBarrierException
Semaphore 许可证数量 可复用 资源限流、顺序令牌传递 防止误 release() 导致计数异常

实践中的问题与解决方案

1. 把“启动顺序”当成了“完成顺序”

  • 现象：使用 ExecutorService 提交任务后，发现结果输出顺序与预期不一致。

  • 根因：单线程池只保证任务被调度的顺序，若任务内部还有 sleep、I/O 或异步回调，实际完成顺序仍可能乱序。

  • 解决步骤：

    1. 需要“完成顺序”时，改用 Future.get()、CompletableFuture.thenCompose() 或 CountDownLatch 做显式依赖；
    2. 在任务内部按阶段拆分，提交到池前用 CompletableFuture 链式编排。

2. 虚假唤醒导致执行乱序

  • 现象：使用 Object.wait() 或 Condition.await() 时，线程偶尔会在未收到通知的情况下继续执行。

  • 根因：JVM 规范允许虚假唤醒（spurious wakeup），使用 if 单次判断会跳过条件检查。

  • 解决步骤：

    1. 永远将 wait()/await() 放在 while (条件不满足) 循环中；
    2. 用明确的状态变量或计数器作为继续执行的判断依据。

3. 持有锁时调用 join() 造成死锁

  • 现象：在 synchronized 块内调用 t.join()，程序卡死。

  • 根因：join() 不释放已持有的锁，目标线程若需要同一把锁则无法继续，形成循环等待。

  • 解决步骤：

    1. 将 join() 移到同步块外部；
    2. 或用 CountDownLatch/Condition 等不依赖对象锁的同步工具。

4. 线程中断后状态未清理

  • 现象：调用 shutdownNow() 或中断线程后，后续 await()、acquire() 抛出异常，但程序未正确收尾。

  • 根因：InterruptedException 会清除线程中断标志，若只打印栈 trace 不恢复或退出，可能遗留半完成状态。

  • 解决步骤：

    1. 捕获 InterruptedException 后，根据业务决定是否 Thread.currentThread().interrupt()；
    2. 在 finally 中释放已获取的锁、信号量或许可证，避免资源泄漏。
