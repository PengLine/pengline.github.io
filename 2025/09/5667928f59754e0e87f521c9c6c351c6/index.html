Java 多线程之交替执行的实现方案

发表于2025-09-30|更新于2026-09-08
|Java多线程
|浏览量:

两个线程交替打印1-100，列举以下几种方法：

  1. synchronized+object：wait()等待，notify() 唤醒
  2. Lock-condition（条件变量）：c1.signalAll() 唤醒，c2.await() 等待
  3. volatile 修饰的变量，通过值控制（可以是 boolean，或者是数字类型）
  4. Semaphore（信号量），acquire()获取许可，release()释放许可
  5. CyclicBarrier（循环栅栏），await() 使等待
  6. AtomicBoolean，基于 CAS 机制实现线程交替打印
  7. LockSupport：park() 阻塞当前线程、unpark(Thread t) 释放目标线程

核心思想：线程交替执行的本质是“条件轮转”——每次只有一个线程满足执行条件，执行完毕后修改条件并唤醒下一个线程，自己则进入等待。实现条件轮转的手段可分为两大类：

  • 阻塞协作型：wait/notify、Condition、LockSupport、Semaphore、CyclicBarrier，依赖线程阻塞/唤醒；

  • 自旋检查型：volatile 标志、AtomicBoolean，依赖 CPU 自旋读取共享变量。

阻塞协作型适合通用场景，CPU 占用低；自旋检查型代码简单，但空转会浪费 CPU，仅适合极低竞争或教学演示。

Object（等待+唤醒）

Object.wait/notify 交替模型

线程 A、B 共享同一把对象锁和同一个 num。每个线程进入同步块后先 notify() 唤醒对方，再打印并 wait() 释放锁。由于 wait() 会释放对象锁，对方线程能够进入同步块继续执行，从而形成交替。

sequenceDiagram
    participant A as 线程A
    participant Monitor as 对象 Monitor
    participant B as 线程B

    A->>Monitor: synchronized 进入
    A->>Monitor: notify
    A->>A: print num=1
    A->>Monitor: wait 释放锁
    B->>Monitor: synchronized 进入
    B->>Monitor: notify 唤醒A
    B->>B: print num=2
    B->>Monitor: wait 释放锁
    A->>Monitor: 被唤醒，继续

虚假唤醒风险：wait() 可能在没有 notify() 的情况下被唤醒（spurious wakeup）。生产环境应把 wait() 放在 while 条件判断中，或在循环内检查执行权限。

Condition（条件变量）

Semaphore（信号量）

Semaphore 双信号交替模型

两个信号量 semaphore1(1) 和 semaphore2(0) 形成互斥令牌。线程 A 先 acquire(semaphore1) 拿到令牌并打印，然后 release(semaphore2) 把令牌交给线程 B；线程 B 拿到令牌后同理交回。任意时刻只有一个线程持有有效信号量。

sequenceDiagram
    participant A as 线程A
    participant S1 as Semaphore1
    participant S2 as Semaphore2
    participant B as 线程B

    A->>S1: acquire
    S1-->>A: 许可
    A->>A: print
    A->>S2: release
    B->>S2: acquire
    S2-->>B: 许可
    B->>B: print
    B->>S1: release
    A->>S1: acquire

扩展性：该模型可自然扩展到 N 个线程，形成信号量环：每个线程持有当前信号量，完成后释放下一个线程的信号量。

CyclicBarrier（循环栅栏）

主要用于让一组线程互相等待，直到所有线程都达到了一个公共屏障点（Barrier Point），然后这些线程才继续执行。

LockSupport（阻塞/释放）

LockSupport 许可证模型

LockSupport.park() 会让当前线程阻塞，直到获得一个“许可证”；unpark(thread) 会给目标线程发放一个许可证（最多保存一个）。本例中主线程先 unpark(t1)，之后 t1 打印并 unpark(t2)，t2 打印并 unpark(t1)，形成交替。相比 wait/notify，LockSupport 不需要获取对象锁，也不会抛出 InterruptedException。

sequenceDiagram
    participant Main as 主线程
    participant A as 线程A
    participant B as 线程B

    Main->>A: unpark(A)
    A->>A: park() 立即返回
    A->>A: print
    A->>B: unpark(B)
    B->>B: park() 立即返回
    B->>B: print
    B->>A: unpark(A)
    A->>A: park() 立即返回

许可证累积特性：同一个线程多次 unpark 不会累积多个许可证，最多保留一个。因此交替场景必须成对使用 park/unpark，否则可能丢失同步节拍。

方案选型对比

方案 是否需要锁 CPU 占用 扩展性 适用场景
Object.wait/notify 需要对象锁 低 中 传统同步，2~N 线程交替
Condition 需要 ReentrantLock 低 高 多条件变量、需要精确唤醒
Semaphore 不需要 低 高 明确的令牌传递场景
CyclicBarrier 不需要 低 中 需要线程互相等待后再继续
BlockingQueue 不需要 低 高 生产者-消费者式交替
volatile 不需要 高（自旋） 中 简单双线程、非生产环境
AtomicBoolean 不需要 高（自旋） 中 简单双线程、演示 CAS
LockSupport 不需要 低 中 不需要锁的精确阻塞唤醒

实践中的问题与解决方案

问题 1：死锁——两个线程同时 wait/park

现象：两个线程都进入等待状态，没有任何线程被唤醒，程序卡住。

根因：

  • wait/notify 中未保证至少有一个线程先执行 notify；

  • LockSupport 中初始 unpark 丢失或两个线程都先 park。

解决步骤：

  1. 确保程序启动时有明确的“先手”线程；

  2. 使用带超时的 wait(timeout) 或 parkNanos(timeout)，超时后主动检查状态；

  3. 多线程场景使用 Semaphore 或 Condition，避免手动维护唤醒顺序。

问题 2：竞态导致重复打印或跳号

现象：两个线程打印了同一个数字，或跳过了某个数字。

根因：num++ 不是原子操作，或自旋方案中线程切换时机导致条件判断与打印不是原子的。

解决步骤：

  1. 将 num++ 和条件修改放在同步块内；

  2. 自旋方案使用 AtomicInteger 的 incrementAndGet；

  3. 打印前再次确认当前线程拥有执行权。

问题 3：自旋方案 CPU 飙高

现象：使用 volatile 或 AtomicBoolean 的方案 CPU 占用接近 100%。

根因：线程在等待条件时持续循环检查 flag，没有释放 CPU。

解决步骤：

  1. 生产环境避免使用自旋实现交替；

  2. 改用 LockSupport、Condition 或 Semaphore 等阻塞方案；

  3. 若必须使用自旋，加入 Thread.yield() 或短暂 sleep 降低 CPU 占用。

问题 4：虚假唤醒导致乱序

现象：wait() 在没有 notify() 时被唤醒，导致两个线程同时进入临界区。

根因：JVM 规范允许 wait() 虚假唤醒，必须把等待放在循环中检查条件。

解决步骤：

  1. 使用 while (!canRun()) { obj.wait(); } 而不是 if；

  2. 每次被唤醒后重新判断当前线程是否应该执行；

  3. Condition.await() 同样需要放在循环中。
