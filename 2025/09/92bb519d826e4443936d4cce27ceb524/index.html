LangChain + RAG 构建医疗问答Agent

发表于2025-09-04|更新于2026-09-03
|AIAgent
|浏览量:

背景问题与方案概述

大模型虽能回答医学问题，但直接开放问答存在两点不足：一是缺乏可靠的医学知识来源——模型凭训练记忆作答，容易产生幻觉；二是调用云端 API 成本高、医疗数据存在隐私顾虑。

本文 Demo 的思路是构建一个完全本地化的医疗问答智能体（Agent）：以预设医疗知识库做 RAG 检索增强，配合网络搜索、症状提取、严重程度评估等多类工具，让 LLM 自主决策调用路径，为用户提供专业、准确的医疗健康咨询服务。

整个方案基于三个核心开源组件：

  • LangChain：构建 LLM 应用的开源框架，核心价值是模块化设计、标准化接口与丰富工具链，让开发者聚焦业务逻辑而非底层细节。它提供七大组件（Agent、Models、Chains、Tools、Memory、Callbacks、RAG），以统一接口对接 OpenAI、Hugging Face 等主流 LLM（本文使用 Ollama 本地模型）。

    LangChain 主要解决五类问题：LLM 集成（多模型统一调用）、上下文管理（长文本/多轮对话的分块、摘要与记忆）、数据增强（结合文档、数据库做 RAG）、工作流编排（Chain 组合多步骤）、代理能力（让 LLM 动态调用工具完成复杂任务）。

    其上层 LangGraph 用于编排复杂流程，专门解决两类问题：① 线性链的局限——基础 Chain 难以处理循环/分支；② Agent 的扩展——增强鲁棒性（自动重试、状态回溯）。

  • Ollama：本地 LLM 运行框架，简化模型下载、运行与管理。

    其 API 特点包括：流式输出（实时 token 生成，兼容 OpenAI API 风格）；多模型管理（可同时运行不同模型，但 VRAM 有限时会停一个跑另一个，需规划资源）；参数控制（通过 API 高度可定制）；CPU 兼容（VRAM 不足时自动把模型卸载到 CPU，低显存机器也能跑大模型）；语言无关（Python、JavaScript、Go 等任何支持 HTTP 的语言均可调用）。

  • Chroma：开源向量数据库，专为存储与检索高维向量设计。核心基于 HNSW 算法实现近似最近邻搜索，主要特点：多存储后端（支持 DuckDB、ClickHouse 等）、多语言 SDK（Python/JavaScript）、API 简洁（collection 的 add/query/update/delete 即可完成全生命周期管理）、检索性能高。

三者分工明确：Chroma 存"医疗知识"，Ollama 跑"推理大脑"，LangChain 负责把检索结果、工具调用与对话组织成一条可控的推理链路。

整体架构可进一步抽象为四层：

  • 知识层（data/ 医疗文档 + Chroma 向量库）负责沉淀权威内容；

  • 检索层（Retriever + RetrievalQA）负责把问题向量化并召回相关片段；

  • 决策层（Agent + 四类工具）负责判断"该用哪个工具、要不要多步推理"；

  • 安全层（入口合法性校验 + 来源追溯 + 异常兜底）负责守住边界。

四层各自独立、可整体替换——把医疗文档换成产品手册，稍作调整就是一个售后客服 Agent，这正是模块化框架带来的直接红利。

快速上手：三大组件的典型用法

在进入医疗 Demo 之前，先分别看三个组件的典型用法，建立直观印象。

代码与实现

完整工程（含 data/ 医疗知识库与 tools/medical_tools.py）参考 GitHub 源码。核心类 MedicalAgent 的工作链路：将 data/ 目录下的 txt 医疗文档切分后写入 Chroma 向量库 → 用 RetrievalQA 构建知识库检索链 → 向 Agent 注册"知识库检索 / 网络搜索 / 症状提取 / 严重程度评估"四类工具 → 由 LLM 依据问题意图自主路由调用。

工程结构与运行流程

工程目录按职责分为三部分：

  • data/：医疗知识库目录，放置若干 txt 文档（高血压、糖尿病、脑血栓等慢病主题）；

  • tools/medical_tools.py：MedicalTools 医疗专项工具实现（症状提取、严重程度评估、查询合法性校验）；

  • 入口脚本：MedicalAgent 核心类（即上文完整代码），启动时加载知识库并初始化 Agent。

运行流程共三步：

① 安装模型并启动 Ollama（前置准备中的命令）；

② 把医疗文档放入 data/ 目录（代码用 glob 扫描目录下全部 *.txt，缺失时打印警告并用占位文档建空库，保证流程不中断）；

③ 执行入口脚本。启动过程中会打印 使用FakeEmbeddings创建向量存储...，随后依次抛出示例问题并打印回答。

入口处的示例问题覆盖了典型慢病咨询场景（高血压是什么/如何预防、老年高血压注意事项、糖尿病预防、三病关联），预期行为：医学知识类问题由 LLM 自主路由到 “Medical Knowledge Base” 工具，回答末尾附 来源: 文件名 供追溯；若知识库未命中，则会尝试 Web Search 兜底。

核心逻辑解释

  1. 工具路由机制：Agent 采用 zero-shot-react-description 模式，即"零样本 + ReAct 思维链"，由 LLM 观察问题后自行选择工具。四类工具通过 description 字段声明能力边界，路由依赖它——医学知识类问题命中知识库检索；需要时效性的信息（最新研究、新闻）命中 Web Search；症状类文本交给提取与评估工具。description 写得越准确，路由准确率越高。该模式的名字也点出了它的软肋：工具选择完全依赖 description 与模型理解力，工具数量越多、描述越模糊，路由越容易出错——实践中应精简工具清单、写清每个工具的能力边界，必要时在描述中附带示例问题帮助模型对齐。

  2. RAG 检索链路：load_medical_knowledge() 用 CharacterTextSplitter（chunk_size=1000、chunk_overlap=200，重叠区保证跨块语义不丢失）切分文档后写入 Chroma；问答时以 stuff 模式将召回的相关片段与问题一并塞给 LLM 生成答案。retrieval_chain 开启 return_source_documents=True，query_medical_knowledge() 会把命中文档的 source 元数据（文件名）去重后拼接到答案尾部——让回答可追溯，是医疗场景的必备设计。

  3. 医疗专项工具：tools/medical_tools.py 中的 MedicalTools 承担三类医疗逻辑——extract_symptoms 从自由文本中抽取症状词（疾病问诊第一步）、assess_severity 依据提取到的症状列表给出严重程度分级、validate_medical_query 在问答入口校验问题合法性（拦截与医疗无关或不宜回答的问题）。

  4. 安全兜底设计：run() 在交给 Agent 之前先做合法性校验，非法问题直接返回提示而不消耗模型调用；handle_parsing_errors=True 让 Agent 输出格式异常时可自愈重试；知识库查询工具内部 try/except 兜底，任一环节报错都不会让整体流程崩溃，而是返回可读的错误信息。

  5. 面向医疗场景的设计取舍：医疗问答对准确性的容忍度远低于普通闲聊，代码中的多处设计都为此服务——用 RAG 强制答案"有据可依"，而不是让模型凭记忆自由发挥；回答强制附带 来源 文件名，用户可自行核对；入口处 validate_medical_query 拦截"帮我开药"等不适合模型直接回答的问题。这些机制共同构成一条防御链：宁可不答，不可乱答。

四类工具的典型路由路径可以预期为：

用户问题类型 期望命中的工具 回答形态
疾病定义/预防/慢病注意事项 Medical Knowledge Base 知识库片段作答 + 来源文件名
最新研究进展、医疗新闻 Web Search 互联网检索结果摘要
一段症状自述文本 Symptom Extractor → Severity Assessment 症状清单 + 严重程度分级
与医疗无关的闲聊 validate 入口拦截 直接返回提示，不消耗模型调用

说明：本文 Demo 仅用于技术演示，回答不能替代专业医生诊断；真实医疗场景还需叠加权威数据源与人工审核。

注意事项与排坑提示

  • Ollama 连接与超时：base_url 必须指向 http://localhost:11434（Ollama 默认 API 地址），否则请求直接失败；首次加载模型或机器性能不足时推理很慢，务必调大 timeout（示例设 300s）。此外并非所有模型都支持 format="json" 强制结构化输出，不支持的模型开启后请求会异常——代码中已注释掉该参数，这是实测踩过的坑。

  • 模型名与 ollama pull 保持一致：代码中 model 填的是 Ollama 中的模型名（如 gemma3:4b），必须先 ollama pull 下载对应模型，名称不一致会报模型不存在。Demo 入口示例用的是 qwen2，可根据实际拉取的模型调整。

  • 响应速度与召回量的权衡：本地小模型推理慢，Demo 做了多处取舍——检索文档数 k 从 3 降到 2、verbose=False 关闭过程输出、max_iterations=3 配合 early_stopping_method="force" 限制 Agent 推理步数。若回答质量下降，优先恢复 k 与迭代次数，而不是盲目追求速度。

  • Embedding 的选用（重要）：代码用 FakeEmbeddings 是为了避免下载外部模型、让 Demo 开箱即跑，但它只产生随机向量、不具备真实语义检索能力，跑通流程可以、正式使用不可。替换方案：ollama pull nomic-embed-text 后用 langchain_ollama 的 OllamaEmbeddings 接入真实 embedding，否则知识库召回形同虚设。

  • 依赖与导入规范：新版 LangChain 把模型、向量库、工具拆分到 langchain_ollama、langchain_chroma、langchain_community 等子包，老教程中统一从 langchain 导入的写法已过时并会触发弃用警告（Demo 开头已显式过滤 LangChainDeprecationWarning）；调用链统一用 invoke() 替代已过时的 run() 方法。

  • 网络与数据依赖：Web Search 工具（DuckDuckGo）需要外网访问，离线环境会超时失败，此时应让 Agent 只保留知识库工具；医疗文档建议使用 UTF-8 编码（TextLoader 中显式指定 encoding="utf-8"），避免中文乱码导致检索质量下降。

  • 从 Demo 到可用产品：本文工程定位是技术演示，正式落地还需三步——把 FakeEmbeddings 换成真实的本地 embedding 模型（如 OllamaEmbeddings(nomic-embed-text)）恢复语义检索；扩充权威知识源并建立更新机制（陈旧文档会直接拉低回答质量）；叠加人工审核与责任边界（如高危症状提示就医、敏感问题转人工），这些也是医疗 AI 合规落地的必经之路。
