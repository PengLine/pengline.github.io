Ubuntu 系统如何搭建 Kubernetes 集群

发表于2025-09-09|更新于2026-09-07
|DevOpsK8S
|浏览量:

Kubernetes 集群的搭建看似命令繁多，实则是一条高度套路化的流水线：选好容器运行时 → 装齐 kubeadm/kubelet/kubectl 三件套 → 主节点 init → 工作节点 join → 补上 CNI 网络插件 → 验证 Dashboard。任何一个环节的版本错位、内核参数缺失或镜像仓库不可达，都会让集群卡在 Node NotReady 或 Pod Pending 上，而这类问题的排查手段又是高度同构的。

本教程以 Ubuntu 24.04 + containerd + kubeadm 为例，完整记录一个 1 主 2 从（master200 / slave201 / slave202，均为 192.168.159.0/24 网段）的 Kubernetes v1.28 集群从零到可用的全过程，包含：系统环境与内核参数调优、容器运行时配置（SystemdCgroup、pause 镜像替换）、kubeadm 初始化与 join、CNI 网络插件选型（CoreDNS/Flannel/Calico/Cilium）、Dashboard 部署与 Token 获取，以及一套可直接照抄的故障排查手册。

集群整体拓扑如下：

阅读导览

  1. 基础安装：时间同步、关闭 Swap、内核模块与 sysctl 参数（iptables 桥接转发）
  2. 容器运行时：containerd 安装、SystemdCgroup 开启、pause 镜像替换为国内源
  3. 集群安装：kubeadm init 初始化主节点、工作节点 join、常见初始化故障排查
  4. 网络插件：CNI 原理与 Flannel / Calico / Cilium 三选一，CoreDNS 修复
  5. Dashboard：安装、NodePort 暴露、两种 Token 获取方式
  6. 业务验证：Deployment + NodePort Service 部署 nginx，端到端访问

版本说明：本教程以 v1.28.15 为例展开（2025 年的稳定版本线），截至 2026 年 v1.28 已停止维护。生产环境请前往 pkgs.k8s.io 版本列表 选择当前仍受支持的版本，下文命令中的版本号、镜像仓库地址同步替换即可，流程完全一致。

相关参数解释：

  • apiserver-advertise-address：集群广播地址，用 master 节点的内网 IP。

  • image-repository：由于默认拉取镜像地址 k8s.gcr.io 国内无法访问，这里指定阿里云镜像仓库地址。

  • kubernetes-version： K8s 版本，与上面安装的软件版本一致。

  • service-cidr：集群 Service 网段。

  • pod-network-cidr：集群 Pod 网段。

  • cri-socket：指定 kubelet 使用的 CRI 运行时 socket 路径。本文使用 containerd，对应 unix:///run/containerd/containerd.sock（cri-dockerd.sock 是 Docker 作为运行时时的路径，二者不可混用）。

网络插件（CNI）

官方插件索引：Cluster add-ons

先说结论：CoreDNS 是 kubeadm 自带的集群内 DNS 服务（不属于 CNI，必须保留）；需要真正三选一的是容器网络插件——Flannel（最简）、Calico（功能最全，生产首选）、Cilium（eBPF 数据面）。同一集群只能安装一个 CNI，混装会导致网络规则互相覆盖、Pod 间通信错乱。

插件 数据面 NetworkPolicy 加密 适用场景
Flannel VXLAN overlay 不支持 无 快速验证、测试环境
Calico BGP / VXLAN 支持 WireGuard 可选 生产环境主流选择
Cilium eBPF 支持 原生支持 高性能与大集群

重要：CNI 的 Pod 网段必须与 kubeadm init 的 --pod-network-cidr 一致（本文为 10.244.0.0/16）。Calico 默认配置是 192.168.0.0/16，下文安装时需要修改，否则节点网络永远不会 Ready。

CoreDNS（集群内 DNS，必装）

DNS 由集群插件管理器自动启动，是集群的内置 DNS 服务——Service 之间的域名解析（如 kubernetes.default）都由它承担。

从 Kubernetes v1.12 开始，CoreDNS 是官方推荐的 DNS 服务器，取代了 kube-dns；若集群由旧版本升级而来，可能仍是 kube-dns 在工作。

重建 CoreDNS（仅当 DNS 解析异常时执行）

风险提示：下面的删除操作会让集群 DNS 中断数十秒到数分钟，期间所有 Service 域名解析失败。请先确认问题是“CoreDNS 配置/镜像损坏”，而不是“节点 NotReady 或镜像拉取失败”——后者应先修节点，重装 CoreDNS 无济于事。

将以下内容粘贴进去（YAML 缩进敏感，可在 vim 中先 :set paste 再粘贴，避免自动缩进破坏格式）：

flannel

项目地址：flannel-io/flannel

由 CoreOS 开发、CNCF 维护的 Flannel 是最直接、最流行的 overlay 网络方案，数据面基于 VXLAN（早期版本还支持 UDP），是容器编排网络最早的成熟实现之一，安装与排障成本最低。

安装前先从 Flannel releases 确认最新稳定版（示例中的 v0.13.1-rc2 已非常陈旧），并确保镜像可拉取（国内环境把 quay.io 镜像替换为可用代理源）：

calico

项目地址：Calico 官方快速开始

Calico 是生产环境最主流的网络方案：基于 BGP 三层路由（可选 VXLAN 封装），不依赖 overlay 隧道，网络路径短、性能好，且原生支持 NetworkPolicy 与 WireGuard 加密，还提供 eBPF 数据面选项。

安装要点：先装 Tigera Operator，再下发 custom-resources.yaml（必须把默认的 Pod 网段 192.168.0.0/16 改成与 kubeadm init 一致的 10.244.0.0/16，代码块内已用 sed 处理）：

cilium

基于 eBPF 的下一代网络方案：数据包在内核态直接转发，路径最短、吞吐最高，且自带强大的可观测性与 L7 网络策略能力；代价是要求内核较新（建议 ≥ 5.8）且组件更多。

常见问题及解答

问题 答案
1. 创建Service Account时提示权限不足 确保你有足够的权限在集群中创建Service Account。如果你是集群管理员，可以尝试使用cluster-admin权限。
2. 获取Token信息时提示找不到Secret 确认Service Account名称是否正确，且是否已经成功创建。可以通过kubectl get sa命令查看Service Account列表。
3. 登录时提示Token无效 确认 Token 复制是否完整；方式二签发的短期 Token 默认 1 小时过期，过期后重新 kubectl create token 即可；方式一的长期 Token 无过期问题。
4. 无法打开Kubernetes Dashboard 确认Kubernetes Dashboard是否已经正确安装并启动。可以通过kubectl get pods -n kubernetes-dashboard命令查看Dashboard的运行状态。
5. 登录后无法看到集群资源 确认Service Account是否已经绑定到正确的ClusterRole，且ClusterRole是否拥有足够的权限。

生产环境建议

  1. 版本锁定：安装时已通过 apt-mark hold 锁定 kubelet/kubeadm/kubectl，后续升级须走官方版本线（先升 kubeadm、再升 kubelet），避免组件版本失配。
  2. etcd 备份：kubeadm 将 etcd 以静态 Pod 方式托管，生产环境应定期用 etcdctl snapshot save 备份，并演练恢复。
  3. 证书续期：kubeadm 签发的控制面证书默认一年到期，用 kubeadm certs check-expiration 监控、kubeadm certs renew all 续期后重启相关组件。
  4. 控制面隔离：生产建议给控制面节点打污点 kubectl taint nodes master200 node-role.kubernetes.io/control-plane:NoSchedule，让业务 Pod 全部调度到工作节点。
  5. 高可用规划：单控制面节点只是“可用”而非“高可用”，生产集群至少需要 3 个控制面节点 + 负载均衡（kube-vip / 云 LB）暴露 apiserver。
  6. 镜像离线化：内网或弱网环境可在构建机 ctr image pull 后导出、导入（见上文 ctr 命令），提前备好 pause、coredns、calico 等基础镜像。
