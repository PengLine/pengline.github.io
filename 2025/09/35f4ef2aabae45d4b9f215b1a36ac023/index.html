VMware 如何扩展 Centos7 的磁盘容量

发表于2025-09-15|更新于2026-09-07
|DevOpsCentos
|浏览量:

在实际生产与开发环境中，使用 VMware 搭建的 Centos 7.6 虚拟机常常会遇到“磁盘容量不够用”的问题：在 VMware 图形界面中给虚拟磁盘扩容后，进入系统执行 df -h，却发现容量并没有变化。这不是扩容失败，而是扩容只发生在虚拟磁盘（vmdk）这一物理层，Linux 系统内部的存储链路——分区表、LVM 卷组、逻辑卷、文件系统——尚未感知到新增空间，需要逐层打通才能真正“吃到”容量。

本文以 Centos 7.6 + LVM（卷组名 centos_master）为例，梳理一条完整的扩容路径：VMware 侧扩容 → fdisk 新增分区 → 修改分区类型为 LVM（8e）→ pvcreate 创建物理卷 → vgextend 扩展卷组 → lvextend 扩展逻辑卷 → xfs_growfs 刷新文件系统，并补充扩容过程中的常见坑（重复 pvcreate 产生 unknown PV、PE 粒度取整、xfs 与 ext4 的 grow 差异等）。

本文场景：当前磁盘组为 centos_master，需要为系统盘新增一个分区 sda3，将 VMware 扩展出的空间并入根文件系统。

前置：VMware 侧扩展虚拟磁盘

进入 VMware 图形界面前，先确认以下两点，否则扩容按钮可能不可用或导致数据风险：

  1. 关闭虚拟机（或在客户机内确认分区未被占用时操作）。若虚拟机存在快照，磁盘扩展按钮通常置灰，需先删除快照（快照会锁定 vmdk 的几何信息）或在无快照的克隆上操作。

  2. 右键虚拟机 → 设置 → 硬盘 → 磁盘实用工具 → 扩展，输入扩展后的总容量（例如从 50G 扩到 100G）。扩展的是整个虚拟磁盘的容量上限，后续还需在系统内完成分区与 LVM 扩展。

扩展完成后启动系统，先确认系统是否识别到新的磁盘容量：

为什么 df -h 看不到新容量

Linux 的根文件系统并不是直接躺在物理磁盘上，中间隔着 LVM 这层“池化”抽象，扩容的信息需要沿存储链路逐层传递：

graph TD
    A[VMware 扩展 vmdk 容量] --> B[sda 物理磁盘容量变大]
    B --> C[sda3 新分区<br/>fdisk 划分并改类型 8e]
    C --> D[PV 物理卷<br/>pvcreate 初始化]
    D --> E[VG 卷组 centos_master<br/>vgextend 并入新 PV]
    E --> F[LV 逻辑卷 root<br/>lvextend 扩大容量]
    F --> G[XFS 文件系统<br/>xfs_growfs 在线刷新]
    G --> H[df -h 最终感知新容量]

  • df -h 统计的是已挂载文件系统的容量，它只认逻辑卷这一层；

  • VMware 扩容只改变了虚拟磁盘的“物理上限”，分区表里还没有 sda3，卷组不知道有新空间，逻辑卷自然也没变大；

  • 所以必须依次完成“分区 → PV → VG → LV → 文件系统”五步，任何一步缺失，df -h 都不会变化——这也是大多数“扩容没生效”案例的根因。

扩容步骤方法

扩容总览

flowchart LR
    A[VMware 扩展磁盘] --> B[fdisk 新增分区 sda3]
    B --> C[分区类型 83 改 8e]
    C --> D[重启系统]
    D --> E[pvcreate 建物理卷]
    E --> F[vgextend 扩展卷组]
    F --> G[lvextend 扩展逻辑卷]
    G --> H[xfs_growfs 刷新文件系统]
    H --> I[df -h 验证]

第一步：新增分区

进入系统后，新容量需要通过新增的分区“注册”到系统中（将扩展出的空闲扇区划成一个新分区，而不是修改已有分区——已有分区在磁盘中段，无法就地扩展）：

分区保存后，若 lsblk 看不到新分区，说明内核分区表未刷新，可执行 partprobe /dev/sda 通知内核重读分区表；若提示设备忙，则按下一节重启系统后再继续。

新分区创建后默认的类型 Id 是 83（Linux native），而 LVM 物理卷要求分区 Id 为 8e（Linux LVM），需要手动修改，否则 pvcreate 可能因分区类型不匹配而无法使用该分区：

第三步：初始化物理卷

关键认知：LVM 直接管理块设备，新分区并不需要预先格式化——文件系统是在逻辑卷（LV）创建/扩展时由你选择的（本文根文件系统为 xfs）。这里真正要做的是 pvcreate，把 sda3 初始化为物理卷（PV），写入 LVM 元数据标签：

常见误区：若此前按“老教程”先执行过 mkfs.ext3 /dev/sda3（对新分区建立文件系统），再执行 pvcreate 时 LVM 会检测到文件系统签名并提示是否清除，输入 y 即可——这一步本质上会擦掉刚建的文件系统，属于多余操作。若想彻底清理，可执行 wipefs -a /dev/sda3 后重新 pvcreate。正确顺序永远是：分区 → pvcreate → vgextend → lvextend，中间不需要任何 mkfs。

第四步：扩展卷组与逻辑卷

物理卷就绪后，先将其并入卷组 centos_master，再从卷组中切出空间给根逻辑卷：

提示：若希望把卷组中所有剩余空间全部给某个 LV，也可直接用 lvextend -l +100%FREE /dev/mapper/centos_master-root，由 LVM 自动按 PE 对齐，避免手算容量。

第五步：刷新文件系统

lvextend 只扩大了逻辑卷的块设备尺寸，文件系统元数据仍然认为容量未变，必须执行对应的 grow 命令让文件系统“在线长大”。Centos 7 默认根文件系统是 xfs，xfs 只支持扩大不支持缩小，扩容命令为 xfs_growfs（后接挂载点或设备路径）：

xfs 与 ext4 的分水岭：若文件系统是 ext4，使用 resize2fs /dev/mapper/centos_master-root（也可直接用 xfs_growfs 的镜像命令无法互用）。误用会在 xfs 上报 “not a valid XFS filesystem”，在 ext4 上会提示命令不存在。判断依据就是上一步的 df -T。

第六步：修复 unknown 物理卷

如果同一个分区被重复执行了 pvcreate（例如 fdisk 后没有重启/partprobe，旧的分区设备节点仍被内核占用，重复创建导致 LVM 元数据出现两份记录），pvdisplay 中会出现一个名称为 unknown device 的 PV，卷组会认为有一块盘处于“丢失”状态。此时需要把卷组中所有未知/已丢失的设备剔除：

使用 pvs 查看时会看到名称为 unknown 的 PV，这正是卷组内 LVM 元数据与实际设备对不上的表现：

预防：pvcreate 前先 lsblk 确认新分区已被内核识别（必要时 partprobe 或重启），避免对“同一设备”执行两次初始化；本文第二步已安排重启，正是为了规避这类元数据错乱。

整个扩容链路可概括为一张表：

层次 对象 命令 作用
虚拟化层 vmdk 虚拟磁盘 VMware 图形界面 提升磁盘容量上限
分区层 /dev/sda3 fdisk + partprobe 把新增空间划成可用分区（Id=8e）
物理卷层 PV pvcreate 写入 LVM 标签，纳入 LVM 管理
卷组层 centos_master vgextend 让卷组感知到新空间
逻辑卷层 root LV lvextend 扩大逻辑卷块设备
文件系统层 xfs xfs_growfs 在线扩展文件系统，df 最终可见

常见问题速查

现象 根因 解决
扩容后 df -h 无变化 中间某一层未打通（最常见：忘了 xfs_growfs） 按上文链路逐层 lsblk、pvs、lvs 定位断点
pvcreate 报“找不到设备” 分区表未刷新，内核仍用旧几何信息 partprobe /dev/sda 或重启后重试
出现 unknown device PV 对同一分区重复 pvcreate vgreduce --removemissing /dev/centos_master
lvextend 提示空间不足 请求容量超过卷组 Free 空间或未按 PE 对齐 用 -l +100%FREE 或按 PE 粒度手工计算
xfs_growfs 报 “not a valid XFS filesystem” 文件系统其实是 ext4 df -T 确认后用 resize2fs
VMware 扩展按钮置灰 存在快照或虚拟机正在运行 删除快照、关机后再扩展
