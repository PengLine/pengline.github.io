Redis ZSET 的深度分页解决方案

在 Redis 中，ZSET（有序集合） 的分页实现与 MySQL 完全不同，因为它是一个内存数据结构，不存在“回表”和“磁盘 I/O”问题。然而，这并不意味着 ZSET 可以无限制地进行深度分页。

当偏移量（Offset）极大时，Redis 需要遍历跳表中的大量节点才能定位到目标位置，这会导致服务端 CPU 开销激增和响应延迟显著上升。本文将深入剖析其底层原理，并给出工业级的解决方案。

ZSET 的核心分页命令

Redis 提供了两个原生命令用于正序和倒序的分页查询：

命令 作用 时间复杂度
ZRANGE key start stop 按 Score 升序 返回指定索引范围内的元素 O(log(N) + M)
ZREVRANGE key start stop 按 Score 降序 返回指定索引范围内的元素（排行榜常用） O(log(N) + M)

关键点：start 和 stop 是基于 0 的索引，且是闭区间。

  • 分页公式（假设每页 10 条，查第 3 页）：
    • start = (page - 1) * 10 = 20
    • stop = page * 10 - 1 = 29
  • 执行命令：ZREVRANGE my_rank 20 29 WITHSCORES

优点：极快，百万级数据返回 10 条仅需几十微秒。
缺点：和 MySQL 的 OFFSET 一样，越往后翻越慢，因为 Redis 需要内部跳过前 N 个元素（跳表遍历）。

时间复杂度全景：

场景 命令 复杂度 100 万元素中取第 10 页 100 万元素中取第 5 万页
前几页（浅分页） ZREVRANGE key 90 99 O(N + M) 微秒级 不可用（偏移量 50 万）
深分页 ZREVRANGE key 500000 500009 O(N + M) - 数十毫秒级，且随深度线性恶化
按分数范围 ZREVRANGEBYSCORE key (last -inf O(log N + M) 恒定微秒级 恒定微秒级

M 为返回条数（10 条），是可控的；真正失控的是 N —— 偏移量本身。只要偏移量不超过 1 万，ZRANGE 家族性能都很好；超过 1 万后应立刻切换游标方案。

为什么 ZRANGE 深度分页会变慢？

跳表（Skip List）的结构特性

Redis ZSET 底层使用跳表 + 哈希表的组合。哈希表负责 O(1) 的 single 查询，而跳表负责范围查询和排序。

跳表是一种多层级的链表结构。在查找某个元素时，可以通过层级索引跳跃实现 O(log N) 的查找。但是，ZRANGE 命令需要返回按排名（Rank）排序的元素。

核心瓶颈：跳表虽然查找元素快，但按排名（下标）访问需要从最顶层的头节点开始，逐级向下遍历并累加节点数量，直到到达目标 Rank。这个过程的平均复杂度为 O(N)，其中 N 是偏移量的大小。

原理示意图

下图展示了 Redis 跳表的结构以及深度分页的遍历路径：

        Head --> L1_1[节点A L1] --> L1_2[节点B L1] --> L1_3[节点C L1] --> L1_4[节点D L1] --> L1_5[节点E L1] --> L1_6[节点F L1] --> Null
    end

当执行 ZRANGE key 10000 10010 时，Redis 无法直接“跳”到第 10000 个节点。

它必须从跳表的底层链表（L1）的头节点开始，沿着 后退指针 或 前进指针，逐个节点地数过去，直到数到第 10000 个节点。

这意味着： 偏移量越大，Redis 需要遍历的节点就越多，CPU 消耗呈线性增长，这是深度分页变慢的根本原因。

为什么跳表定位元素是 O(log N)，定位排名却是 O(N)？

这是理解 ZSET 分页瓶颈的关键，两种操作面对的“索引”完全不同：

  • 按 Score 定位元素：跳表从顶层开始，通过各层“跨度（span）”指针快速跳过区间——每层能越过成百上千个节点，复杂度 O(log N)，这也是 ZSCORE、ZRANGEBYSCORE 快的原因；

  • 按 Rank（排名）定位元素：ZRANGE key start stop 的 start 是第几个，而不是“哪个分数”。跳表的跨层级指针只记录“跳过的节点数量”，因此 Redis 必须从 Header 出发，沿着底层（L1）前进指针逐节点累加计数，直到累计数等于 start——复杂度退化为 O(start)。

graph LR
    subgraph 按Score查找 OlogN
        A1[zrangebyscore key 900 +inf<br/>从顶层索引直接跳跃] --> A2[毫秒级定位到分数边界]
    end
    subgraph 按Rank查找 ON
        B1[zrange key 1000000 -1<br/>从底层链表头开始] --> B2[逐个节点计数 100 万次] --> B3[CPU 消耗随偏移量线性增长]
    end

同理，ZREVRANGE 的倒序深翻需要从尾部（Tail）沿后退指针逐个计数，代价完全相同。因此排行榜第 1000 名之后的翻页在数据量百万级时已经能感知到延迟，千万级时不可接受。

基于 Score 的游标分页（Cursor-based）

要彻底解决深度分页问题，必须放弃 OFFSET 思维，利用 ZSET 天生的范围查询能力，将“按偏移量查”转变为“按分数范围查”。

核心命令：ZREVRANGEBYSCORE (降序) 或 ZRANGEBYSCORE (升序)。

标准实现流程（无限滚动加载）

假设我们有一个游戏排行榜，需要按分数从高到低拉取数据，且支持“加载更多”。

  • 第一页请求：获取分数最高的前 10 名。

    ZREVRANGEBYSCORE rank +inf -inf LIMIT 0 10 WITHSCORES

    返回结果：

    1. “player_A” -> “1000”

    2. “player_B” -> “995”

    3. …

    4. “player_J” -> “980”

    记录游标：记录下当前页最后一名的 Score 值，即 980。

  • 第二页请求（查询分数小于 980 的数据）：

    ZREVRANGEBYSCORE rank 979 -inf LIMIT 0 10 WITHSCORES

    注意：这里使用 979 而不是 980，是为了排除边界值，防止上一页最后一个玩家在下一页重复出现（即开区间 (980）。

遭遇“同分”问题（Score 重复）

如果上例中，player_J 的 Score 是 980，但还有 player_K 也是 980 分。如果直接用 979 作为游标，player_K 会被漏掉，因为它排在 player_J 之后，但分数相同。

sequenceDiagram
    participant C as 客户端
    participant R as Redis

    Note over C,R: 第一页：ZREVRANGEBYSCORE rank +inf -inf LIMIT 0 2 WITHSCORES
    R-->>C: 返回 [A:980, J:980]，游标记录为 979
    Note over C,R: 第二页：ZREVRANGEBYSCORE rank 979 -inf LIMIT 0 2
    R-->>C: 返回 [K:970, L:960]<br/>K 的分数是 970 被返回<br/>而实际上 K 在 J 之后应为第二页第一名（漏数据）
    Note over C,R: 根源：游标只带了 Score，丢失了同分时的相对次序

解决方案：组合排序（Score + 唯一二级排序）

我们需要确保 ZSET 的排序是全局唯一且确定的。常用的技巧是将 Score 设计为复合数值。

设计公式：$Final_Score = (原分数 * 10^N) + (最大唯一ID - 当前唯一ID)$

N 必须足够大，足以容纳 ID 的最大值（例如 ID 最大为 1 亿，则 $10^8$）。这样，Score 的整数部分代表实际分数，小数部分代表 ID 的降序。

示例：

  • 玩家 A：Score = 1000，ID = 100 → 存储值 = $1000 * 10^6 + (10^6 - 100) = 1000999900$

  • 玩家 B：Score = 1000，ID = 200 → 存储值 = $1000 * 10^6 + (10^6 - 200) = 1000999800$

  • 由于 ID 越大，减去的值越小，因此最终 Score 越大，实现了“同分按 ID 降序”的效果。

此时的游标传递：上一页最后一条数据不仅需要传回 Score，还需要传回 Member（或唯一 ID）。下一页查询时，使用 ZREVRANGEBYSCORE 的 (score 开区间条件，或者加上 BYLEX 辅助，但最简单的方式是继续使用 (score 开区间，因为 Score 已经是全局唯一的。

支持“随机跳页”（局限性讨论）

在后台管理系统中，用户可能希望直接点击“第 100 页”。这种场景下，游标分页（仅支持上一页/下一页）无法满足需求。

应对策略：

策略 实现方式 适用场景
限制最大偏移量 前端只允许查询前 5000 条（即前 500 页），超出时提示“数据过多，请精确搜索”。 绝大多数 C 端排行榜场景，用户只关心 Top 100。
分段分页（分桶） 将 ZSET 按分数区间拆分成多个小 ZSET（例如每 100 分一段），先定位段，再在段内做 ZRANGE 小范围查询。 分数分布均匀且已知的场景（如 0-1000 分）。
替换数据结构 如果排序不依赖 Score，只按插入时间排序，考虑使用 Redis List (LRANGE 分页，O(1) 定位)。 消息队列、通知列表。

最佳实践总结

原则：能用范围查询（BYSCORE）绝不用索引偏移（RANGE），能限制页数就限制页数，绝不依赖 Redis 进行超过 10000 偏移量的随机跳页。

  1. C 端（用户端）场景：必须使用 ZREVRANGEBYSCORE + 游标，配合复合 Score 处理同分问题，性能恒定 O(log N)。

  2. B 端（管理后台）场景：允许使用 ZREVRANGE，但必须在代码层面硬限制 start + stop <= 5000，防止恶意请求拖垮 Redis。

  3. 内存优化：如果只展示排行榜昵称，可以 ZRANGE 只返回 Member，再通过 Pipeline 批量查 Hash 获取用户详情，避免一次性返回过大 Payload。

  4. 监控告警：对 Redis 的 slowlog 进行监控，任何超过 10ms 的 ZRANGE 或 ZREVRANGEBYSCORE 都需要人工 Review。

Redis 与 MySQL 的深度分页对比

对比维度 MySQL 深度分页 Redis ZSET 深度分页
存储介质 磁盘（HDD/SSD） 内存
性能瓶颈 磁盘随机 I/O 与回表（随机读） CPU 计算（跳表遍历）与网络传输
索引结构 B+ 树（叶子节点双向链表） 跳表（多层级链表）
按 Rank 定位 需扫描叶子节点并回表，成本极高 需遍历底层链表节点，成本线性增长
游标优化 WHERE id > last_id 利用聚簇索引直接定位 ZREVRANGEBYSCORE (last_score 直接定位跳表节点
最终选型 适合复杂条件筛选与随机跳页 适合高性能 TopN 与时间线滚动流

Redis ZSET 的深度分页并不是一个无法解决的难题，关键在于转变思维方式。从“我要第 N 条数据”转变为“我要 Score 小于 X 的数据”，利用 B+ 树/跳表的天然范围查找能力，让性能不受数据总量增长的影响。

在业务层做合理的分页限制和降级策略，往往比单纯的技术优化更加重要。
