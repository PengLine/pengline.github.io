Redis ZSET 深度分页真的越翻越慢吗？跳表 span 定位与 Score 游标的工程取舍

Redis ZSET 的深度分页解决方案

本文定位：这不是参数清单，而是围绕一个工程问题解释"为什么这样设计、什么时候会失效、应该如何验证"。文中引用的 Redis 源码均为源码简化版（用于说明机制，以你实际版本的 src/t_zset.c 为准）；示例代码用于说明流程；所有性能论述均区分官方复杂度声明 / 源码理论分析 / 经验量级判断，不提供虚构的实测数字，文末给出在你自己环境里复测的命令配方。

一、先给结论：三个反直觉的事实

ZSET 很适合做排行榜，但围绕它流传着一个错误很广的结论：“ZSET 按排名定位是 O(N)，深分页越翻越慢”。把源码和官方文档对照之后，真实的结论是三个反直觉的事实：

  1. ZREVRANGE key 500000 500009 这种"跳到第 5 万页"的操作，在百万级元素的 ZSET 上并不慢。官方文档对 ZRANGE/ZREVRANGE 声明的复杂度是 $O(\log N + M)$（N 为集合元素总数，M 为返回条数）。Redis 的跳表在每一层前进指针上维护了 span（跨度） 字段，使得"按排名定位"与"按分数定位"一样都是 $O(\log N)$，而不是朴素跳表的逐节点计数 $O(N)$。

  2. ZSET 深分页真正的代价不在单次查询的 CPU，而在语义：rank 是"位置"而不是"身份"，两次翻页之间只要有人加分、删号，排名整体平移，按 rank 翻页就会重复/漏读；而 MySQL 那套"深分页必须游标化"的性能直觉，直接搬到 Redis 上会得出错误的优化理由。

  3. 真正会线性恶化的隐藏路径确实存在，但不在你以为的地方：ZRANGEBYSCORE/ZREVRANGEBYSCORE 的 LIMIT offset count 中，大 offset 在 Redis ≤7.2 上是逐节点跳过（官方文档明说 “up to O(N)”，7.4 起才引入 span 跳跃优化）；此外还有全量拉取、超大 payload 等真正危险的模式。

所以正确的方案仍然是 Score 游标分页 + 复合分数化解同分——但理由与很多文章写的不一样：不是为了省那点定位 CPU，而是为了翻页语义的稳定性、接口的一致性，以及避开 LIMIT offset 这类版本相关的线性陷阱。

二、问题定义

2.1 ZSET 的底层结构：字典 + 跳表

Redis ZSET（有序集合）同时维护两个结构（t_zset.c 文件头注释的意译）：

  • 字典（dict）：member → score 的映射，支撑 $O(1)$ 的 ZSCORE 单点查询；

  • 跳表（skiplist）：按 (score, member) 有序组织，支撑范围查询与排名操作。

两者共享同一份 member 字符串。当元素较少时（Redis 7.0 起 zset-max-listpack-entries 默认 128 个、单元素 64 字节以内，旧版本对应 zset-max-ziplist-* 配置），ZSET 会使用 listpack 紧凑编码——此时的范围操作是线性扫描，但 N ≤ 128，不构成深分页问题；深分页的讨论都针对 skiplist 编码。

与 MySQL 不同，ZSET 是纯内存结构，不存在"回表"和磁盘随机 I/O，代价模型完全不同。这也意味着：把 MySQL 深分页的性能结论直接套到 Redis 上，会得出似是而非的优化方案——这正是本文要纠正的核心。

2.2 两种完全不同的分页需求

排行榜/时间线场景里，"分页"其实是两种需求，接口设计与优化手段完全不同：

  • 随机跳页：“帮我取第 300 页”——后台管理、审核列表。本质是"按 rank 定位"。

  • 连续下滑：“加载更多”——C 端无限滚动流。本质是"按 Score 范围续读"，上一页的末尾是下一页的起点。

需求不同，方案不同。先看最常用的按 rank 分页命令。

2.3 核心 rank 分页命令

命令 作用 官方复杂度
ZRANGE key start stop 按 Score 升序 返回指定索引范围内的元素 O(log(N) + M)
ZREVRANGE key start stop 按 Score 降序 返回（排行榜常用；6.2 起可由 ZRANGE ... REV 替代） O(log(N) + M)

关键点：start 和 stop 是基于 0 的索引，且是闭区间。

  • 分页公式（每页 10 条，查第 3 页）：
    • start = (page - 1) * 10 = 20
    • stop = page * 10 - 1 = 29
  • 执行命令：ZREVRANGE my_rank 20 29 WITHSCORES

优点：实现最简单，单次查询快——百万级数据返回 10 条的耗时是微秒量级（这是官方复杂度模型下的数量级判断，不是实测结论，请按 3.4 节自测）。

缺点：rank 是位置而不是身份，翻页间隔内的写入会造成重复与漏读（第 4 节展开）；且页码语义要求调用方用 ZCARD 计算总页数，而这个"总数"在并发写入下是漂移的。

三、原理考证：按排名定位到底是 O(N) 还是 O(log N)？

这是全文最重要的一节，也是网上大量文章（包括本文旧版）出错的地方。

3.1 跳表为什么快：不只靠"多层索引"，还靠 span

朴素的跳表只有"多层前进指针"，查找元素时自顶向下逐层扫描，期望 $O(\log N)$。但朴素的跳表没有"这条指针跳过了多少个节点"的记忆——如果 ZSET 用的是这种结构，ZREVRANGE key 500000 500009 就真的只能从尾部沿链表逐个数 50 万个节点，复杂度 $O(\text{offset})$。

Redis 的跳表在 Pugh 论文的基础上做了关键增强：每条前进指针都带一个 span 字段，记录"沿着这条指针走到下一个节点，一共跨过了多少个节点"。插入与删除时（zslInsert/zslDeleteNode）同步维护 span。来看源码简化版：

ZRANK/ZREVRANK（官方复杂度 $O(\log N)$）与 ZRANGE 家族按排名的定位走的就是这条路径：实现里只要 start > 0（正向用 start+1、反向用 llen-start 换算成 1-based rank），就用 zslGetElementByRank 直接跳到目标节点，再沿第 1 层顺序取 M 个。定位的成本与偏移量深浅基本无关。

3.2 一次 rank 定位的完整走位

下图是一个 6 元素、两层的跳表（L2 只含 A、E），演示"取第 5 名"如何只走 2 步：

  • 取 rank=5：Head→A（累计 1）→ A 沿 L2 的 span=4 直达 E（1+4=5，命中），2 步。

  • 取 rank=6（F）：Head→A→E（L2 到头）→ 降至 L1 → E→F，3 步。

  • 一般地，期望跳转次数约为 $\log_{1/p} N = \log_4 N$（p=0.25）：百万级元素约 10 次，千万级约 12 次（理论期望值）——与起点深浅基本无关。

这就是"为什么取第 5 万页不会比取第 1 页慢多少"的机制解释：按 Score 定位与按 Rank 定位走的是同一套 span 累计路径，都是 $O(\log N)$：

3.3 复杂度全景（修正版）

场景 命令写法 服务端复杂度 深度敏感？
浅分页 ZREVRANGE key 90 99 $O(\log N + M)$ 否
深分页（第 5 万页） ZREVRANGE key 500000 500009 $O(\log N + M)$ 否（span 定位）
Score 游标 ZREVRANGEBYSCORE key (980 -inf LIMIT 0 10 $O(\log N + M)$ 否
Score 游标写错（带 offset） ZREVRANGEBYSCORE key +inf -inf LIMIT 500000 10 $O(\text{offset} + M)$（≤7.2 逐节点跳；≥7.4 大 offset 走 span 跳跃） 是，随 offset 线性恶化
全量拉取 ZRANGE key 0 -1 WITHSCORES $O(N)$ + 巨大回包 是
listpack 编码 任意范围命令 $O(N)$，但 N ≤ 128 集合小，无影响

上表复杂度均来自官方文档声明与源码结构分析，属于理论分析；"在你的版本上是否可感知"请按 3.4 节实测。
M（返回条数）是业务可控的；真正需要警惕的是后三行的 N 项。M 为 10 时（如每页 10 条），ZRANGE 家族在深浅偏移下的耗时差异可以忽略——"偏移量超过 1 万就性能崩坏"的说法没有源码依据。

四、深分页真正的三条代价路径

4.1 排名不稳定：并发写入下的重复与漏页（最主要的正确性问题）

rank 是"位置"，不是"身份"。两次翻页请求之间，只要有任何一个 member 的 score 发生变化（ZINCRBY、ZADD），位于变更点之后的所有排名都会整体平移：

  • 有人加分挤进前面 → 后面所有元素排名 +1 → 下一页会把上一页末尾的元素再给你一次（重复），同时把本应出现在下一页末尾的元素挤出去（漏读）；

  • 有元素被删除 → 后面排名 -1 → 下一页跳过一个元素。

时序图演示"重复"是怎么发生的：

sequenceDiagram
    participant U as 用户
    participant S as 服务端
    participant R as Redis

    Note over U,R: t0：第 11 名是甲（score=88）
    U->>S: 第 1 页：ZREVRANGE rank 0 9
    S->>R: ZREVRANGE rank 0 9
    R-->>S: 返回第 1~10 名
    Note over R: t1：乙加分挤进第 5 名，甲滑到第 12 名
    U->>S: 第 2 页：ZREVRANGE rank 10 19
    S->>R: ZREVRANGE rank 10 19
    R-->>S: 返回此刻的第 11~20 名
    Note over S: 甲再次出现在第 2 页（重复）；<br/>原第 20 名被挤到第 21 名（漏读）

注意：这不是 ZSET 的缺陷，而是"位置分页"这类接口的固有语义。MySQL 的 LIMIT/OFFSET、Elasticsearch 的 from/size 有完全相同的问题（站内另一篇《海量数据为何越翻越慢？MySQL 深分页的三层代价与游标方案》对此有展开）。区别只在于：Redis 的 rank 翻页单次查询并不慢，所以这个问题更容易被忽略——它不报错、不超时，只是数据悄悄错位，等产品与用户发现时往往已经积累了一段时间。

游标方案把"锚点"从位置换成数据本身：下一页的起点是"上一页最后一个 member 的 score"。只要锚点不变，翻页期间插入多少高分新数据都不影响后续翻页的相对顺序——已见过的高分新数据，本来也不该再出现在下滑流里。

4.2 隐藏的线性路径：BYSCORE 命令的 LIMIT offset

游标分页的标准写法是 LIMIT 0 count，但很多实现会把 offset 语义带进 BYSCORE 命令，比如想跳过前 50 万条直接取后面的数据：

官方文档对这条路径有明确警告：“if offset is large, the sorted set needs to be traversed for offset elements before getting to the elements to return, which can add up to O(N) time complexity.” 源码层面，Redis ≤7.2 的实现就是在找到分数边界后沿第 1 层逐节点跳过 offset 次（源码简化版）：

Redis 7.4 起引入 zslNthInRange：offset 小于源码常量 ZSKIPLIST_MAX_SEARCH（值为 10）时仍逐节点跳；超过则利用 span 做排名换算，从顶层节点直达目标，恢复为 $O(\log N)$。也就是说：

  • ≤7.2：LIMIT 大 offset 是货真价实的 O(N) 陷阱，一条命令能把单线程的 Redis 拖出长尾；

  • ≥7.4：这个陷阱在源码层面被修复，但官方文档至今仍保留 O(N) 警告（保守表述，兼顾旧版本）；

  • 无论什么版本，LIMIT 0 count + 游标续读都是跨版本安全、语义最清晰的写法。

这也是游标方案"性能上不吃亏"的另一半理由：它天然不踩这条路径。

4.3 其他真实代价：大 M、全量拉取与 payload

  • 返回条数 M 才是单次命令的线性项：ZRANGE key 0 -1 WITHSCORES 在百万元素的 key 上会构造上百 MB 的回包——这是真正会拖垮 Redis 主线程（输出缓冲区暴涨、网络打满）的操作，属于典型大 Key 反模式，详见站内《Redis 大 Key 为什么危险？》。

  • payload 放大：member 里塞长 JSON（昵称、头像、简介全放进去）会让同样的 M 放大几倍到几十倍。正确做法是 ZSET 里只放 ID，详情用 Pipeline 批量查 Hash。

  • "总数 + 页码"接口的隐性语义成本：ZCARD 本身 $O(1)$ 不贵，但它返回的是"此刻"的总数；每次翻页都重算总数并配合 rank 定位，页码对应的内容会在并发写入下漂移（第 6 节展开）。

五、方案：基于 Score 的游标分页

5.1 标准实现（无限滚动加载）

以游戏排行榜为例，按分数从高到低、"加载更多"式翻页。游标就是上一页最后一个 member 的 score：

5.2 同分问题：游标只带 Score 会漏数据

如果 player_J 是 980 分，而 player_K 也是 980 分且按次序排在 J 之后。用 (980 开区间翻下一页时，K 会被整段跳过——开区间把"所有 980 分"都排除了，包括还没展示过的：

sequenceDiagram
    participant C as 客户端
    participant R as Redis
    Note over C,R: 集合中有 A:980, J:980, K:980, L:970<br/>（同分按 member 字典序排列：A → J → K）
    Note over C,R: 第一页：ZREVRANGEBYSCORE rank +inf -inf LIMIT 0 2 WITHSCORES
    R-->>C: 返回 [A:980, J:980]，游标 = 980
    Note over C,R: 第二页：ZREVRANGEBYSCORE rank (980 -inf LIMIT 0 2
    R-->>C: 返回 [L:970]——K:980 被开区间整段跳过（漏数据）
    Note over C,R: 根源：游标只携带 Score，同分内部还有一层"次序"，<br/>而 Score 无法表达这层次序

先明确一个事实：ZSET 对同分 member 并非乱序。官方文档明确：分数相同时按 member 的字典序（二进制字节序比较）排列。所以同分顺序是确定、可复现的，只是这个顺序是 member 字符串序，往往不是业务想要的（比如纯数字 ID 不补零时，“9999” 会排在 “10000” 前面）。

问题的本质是：Redis 没有提供按 (score, member) 二元组定位的命令——你无法用一条命令表达"取 score < 980 的，或 score = 980 且 member 次序在 J 之后的"。所以要么两步查询，要么让 Score 本身承载次序。三种做法对比：

方案 A：复合 Score（推荐，一条命令搞定）

把 tie-breaker 编进分数，让合成后的 Score 全局唯一：

$$S_{final} = S \times 10^{N} + (10^{N} - ID)$$

$10^N$ 必须大于 ID 的最大取值（ID 上限 1 亿，则取 $N = 8$）。这样整数部分是业务分数，低位是 ID 的反序。

示例（$N=6$，ID 上限 $10^6$）：

  • 玩家 A：S=1000，ID=100 → $1000 \times 10^6 + (10^6 - 100) = 1000999900$

  • 玩家 B：S=1000，ID=200 → $1000 \times 10^6 + (10^6 - 200) = 1000999800$

方向性注意：公式 $(10^N - ID)$ 的实际效果是 ID 越大、减去越多、合成分数越小、排名越靠后，即"同分按 ID 升序"（先到先得）——上面 A（ID=100）排在 B（ID=200）前面。本文旧版把这句写成了"ID 越大减去的值越小"，方向说反了。如果业务要"新用户靠前"，把低位改成 $(ID - ID_{min})$ 即可。方向是工程决策，不是定式，但必须写进文档。

由于合成 Score 全局唯一，同分漏数据问题随之消失，游标退化为普通的开区间续读：

方案 B：两段查询（不改存量数据，但复杂）

游标携带 (score, member) 二元组，每页发两条命令：score < s 的一段 + score = s 的一段（后者取回后客户端按 member 字典序过滤出排在 last_member 之后的、拼进本页）。省去了数据迁移，但多一次 RTT，且"同分块"可能很大，边界拼接逻辑容易写错。除非存量数据不可动，否则不推荐。

方案 C：接受 member 字典序（零成本，顺序不可控）

业务对同分顺序无要求时，直接用 (score 开区间，并在接口文档写明"同分按 member 字典序展示"。但要意识到：漏读问题在"同分块超过页大小"时依然存在——上一页同分块没展示完就翻页，剩余同分 member 会被跳过。所以方案 C 只适用于"同分概率极低"或"同分整块一起展示"的场景，不能当作同分问题的通用解。

5.3 复合分数的精度红线：$2^{53}$

复合分数方案最大的坑不在设计而在数值表示：ZSET 的 score 是 IEEE-754 双精度浮点数（double），有效精度只有 53 位尾数。所有绝对值不超过 $2^{53}$ 的整数才能被 double 精确表示：

$$2^{53} = 9{,}007{,}199{,}254{,}740{,}992 \approx 9.007 \times 10^{15}$$

因此合成分数必须满足预算约束（理论推导）：

$$\underbrace{(S_{max} + 1) \times 10^{N}}{\text{合成值上界}} \le 2^{53} \quad\Longrightarrow\quad N \le 15.95 - \log{10}(S_{max}+1)$$

  • 原文示例（S 上限千级、N=6）：合成值上界约 $10^9$，安全余量极大 ✓；

  • 反例：分数上限 $10^9$（积分、金额分很常见）却取 $N=7$（想要 $10^7$ 的 ID 空间）：合成值上界 $10^{16} > 2^{53}$，低三位被舍入——同分玩家的 tie-break 被整块抹平，多人共享同一个 double 值，排序退化回 member 字典序且行为随数值漂移，属于"上线数周后才发现、极难排查"的错误。

三条工程纪律：

  1. 上线前算预算：把 $(S_{max}+1) \times 10^N \le 2^{53}$ 写成单测断言；任何"调大分数上限"的需求单必须触发重新评估；

  2. 小数分数先整数化：分数保留 2 位小数时先乘 $10^2$，确保缩放后的业务分数是整数，且相邻两档分数的间距（换算到合成刻度后）≥ tie-break 空间，否则同分处理会跨档串味；

  3. 客户端全程当字符串处理：ZSCORE 返回的是字符串；JS 前端的 Number 同样只有 53 位精度，JSON.parse 大整数会静默丢精度；Java 侧不要把 score 塞进 double 参与运算，统一用字符串或 BigDecimal 透传。

（负分数场景下公式依然保序：相邻档位间距仍是 $10^N$，tie-break 落在 $[0, 10^N)$ 内不会跨档。）

5.4 游标失效与数据变更的边界

游标方案并非对写入完全免疫，它只是把"全局漂移"缩小成"锚点附近"的局部效应。与 rank 分页逐项对比：

并发变更 rank 分页 Score 游标分页
锚点之后插入新数据 全部错位（重复+漏读） 无影响（新数据分数高于游标，本就不该再出现）
锚点 member 被删除 错位 无影响（该 member 本就不该再出现）
已读 member 被降分（降到游标以下） 错位 会在后续页重复出现一次
已读 member 被加分（升到游标以上） 错位 从后续页"消失"（刷新后回到前面的页）
key 被淘汰/过期 整体失效 整体失效，返回空页

后两行是游标方案的理论极限——任何不复制快照的分页都无法同时做到"实时"与"不变"。工程上通常靠产品策略消化：对"已读内容重复"容忍（信息流常态），对"降分重复"敏感的场景在客户端按 member 去重；需要严格一致视图的场合（B 端对账、导出、发奖），用快照 key（见第六节）。

六、支持"随机跳页"的取舍

后台管理系统里用户就是要点"第 100 页"，纯游标（只有上一页/下一页）无法满足。基于本文前面的考证，各策略的真实代价与适用边界如下：

策略 实现方式 真实代价与适用场景
限制最大偏移 前端/服务端硬限制可翻范围（如只允许前 5000 条），超出提示"请精确搜索" 要限制的不是定位 CPU（span 定位不贵），而是语义：深处的页码在并发写入下没有意义，且超大 M 的恶意请求需要兜底。绝大多数 C 端排行榜用户只关心 Top 100
rank 随机跳页（接受漂移） 直接 ZREVRANGE key off off+9 单次 $O(\log N + M)$，服务端开销可接受；代价是页内容在写入下漂移。适合"看个大概"的 B 端报表
快照 key 需要严格一致时用 COPY rank rank:snapshot:20260923（Redis 6.2+）或 ZUNIONSTORE 生成周期快照，翻页全部走快照 一致性最强，支持随机跳页；代价是额外内存（按快照周期 × 集合大小估算）与生成开销。适合对账、导出、发奖
分桶（按分数段拆 ZSET） 每 100 分一个子 ZSET，先定位段再段内翻页 旧经验。现在看多数场景不再必要（深翻本身不贵），还引入"分数跨段迁移"的一致性维护成本。仅当单 key 大到需要拆分内存/热点时才考虑
换 List LRANGE 分页 本文旧版此处有误：LRANGE 的复杂度是 $O(S+N)$（S 为 start 偏移量），List 并没有"O(1) 按下标定位"能力，深翻一样劣化，还失去了按 Score 排序能力。仅当数据天然按插入序、只需线性回放时才选 List

结论：随机跳页真正的成本不在"定位第 N 个元素"，而在"第 N 个"这个概念在动态数据上是否还有意义。先和产品确认要不要精确页码，再谈实现。

七、方案对比：Redis / MySQL / Elasticsearch

把三种存储的深分页放在一起看，会发现"offset 贵不贵"的答案完全相反：

维度 MySQL LIMIT/OFFSET MySQL 游标 WHERE id > ? ES from/size ES search_after + PIT Redis ZRANGE offset Redis Score 游标
定位成本 $O(\text{offset}+M)$ 扫描行（二级索引还有回表放大） $O(\log N + M)$ B+树定位 协调节点归并 from+size × 分片数，max_result_window 默认 1 万 $O(M)$ $O(\log N + M)$（span 定位） $O(\log N + M)$
并发写入语义 重复/漏读 锚点附近重复/漏读 重复/漏读 快照一致性（PIT） 重复/漏读 锚点附近重复/漏读
随机跳页 支持 不支持 支持 不支持 支持 不支持
典型风险 深翻拖垮 I/O 与 CPU 需要有序唯一游标 深翻被 window 上限拒绝 快照生命周期管理 误用 LIMIT offset 线性路径 同分漏读、$2^{53}$

两个关键洞察：

  1. Redis 是其中唯一"offset 定位本身就不贵"的存储（感谢 span）。所以"Redis 深分页必须游标化"的性能论证是错的；游标在 Redis 上的价值是语义稳定 + 接口统一 + 规避版本相关的 LIMIT offset 陷阱。

  2. MySQL/ES 的深分页优化经验不能横移：在 MySQL 上"必须游标化"是性能救命（站内《海量数据为何越翻越慢？MySQL 深分页的三层代价与游标方案》与《Elasticsearch 深度分页为何越来越慢？从 from/size 到 search_after + PIT》分别展开）；在 Redis 上同样的写法动机不成立，反而要警惕把 SQL 的 LIMIT offset,count 习惯带进 ZREVRANGEBYSCORE——那才是 Redis 上的真陷阱。

八、故障实战复盘

以下三个场景是"典型故障模式"的复盘式分析（场景组合自社区高频问题与源码可证行为，非特定公司事故记录），按"发生什么 → 为什么 → 系统如何表现 → 如何定位与恢复"展开。

场景一：同分玩家"集体消失"

  • 发生什么：运营反馈某个分数段的玩家在排行榜第二页之后看不到了，但 ZCARD 显示人数正常；没有报错、没有慢查询。

  • 为什么：游标实现用了"整数步进"写法（last_score - 1 或 -0.0001），而该分数段恰逢活动结算、出现大量同分。开区间把整个同分块跳过——5.2 节里被漏掉的 K 不是一个人，是一批人。

  • 系统如何表现：数据缺失但不报错，监控全绿；只有玩家投诉或运营抽查才能发现，属于"沉默型"数据缺陷。

  • 如何定位：抽一个"消失"的 member，ZSCORE 查分数；用 ZREVRANGEBYSCORE key (该分数 -inf LIMIT 0 10 复现翻页路径，确认该分数整块被跳过；再用 ZRANGEBYSCORE key 分数 分数 量一下同分块的大小。

  • 如何恢复：短期用 ZRANGEBYSCORE key s s 把同分块补齐展示；根治是上复合 Score——但需要全量迁移（读全量 member → 计算合成分 → ZADD 原子覆盖），迁移期间旧接口读旧分数、新接口读新分数，用双 key 或灰度切换过渡；完成后下线"整数步进游标"代码路径。

场景二：一条"跳到最后一页"的请求拖出 Redis 长尾

  • 发生什么：管理后台上线"跳转最后一页"功能后，Redis 的 P99 从亚毫秒飙到几十毫秒，slowlog 里堆满 zrevrangebyscore，其他业务请求一起变慢。

  • 为什么：实现用了 ZREVRANGEBYSCORE key +inf -inf LIMIT 999990 10——BYSCORE 命令的大 offset 在 ≤7.2 上是逐节点跳过（4.2 节），一条命令扫描近百万个节点；又因为 Redis 单线程执行命令，长命令会把队列里所有请求一起拖慢。讽刺的是，同样的数据用 ZREVRANGE key 990 999（先 ZCARD 算出末页 offset，再按 rank 定位）是 $O(\log N + M)$，毫秒以内。

  • 系统如何表现：slowlog 告警、INFO commandstats 中 cmdstat_zrevrangebyscore 的 usec_per_call 随业务增长抬升；其他无关业务的 P99 同步恶化——单线程排队效应会让故障"看起来像全站问题"。

  • 如何定位：SLOWLOG GET 看慢命令形态；INFO commandstats 对比该命令平均耗时的历史曲线；确认 Redis 版本是否 ≥7.4。

  • 如何恢复：代码层禁止 BYSCORE 命令携带非零 offset（封装层硬编码 LIMIT 0）；"跳最后一页"改用 rank 定位或提供"查看尾部 Top N"的独立入口；有条件时升级到 ≥7.4 获得 zslNthInRange 修复——但不要把升级当治愈，旧版本兼容性仍是硬约束。

场景三：复合分数超 $2^{53}$，同分名次"随机跳变"

  • 发生什么：排行榜改版后分数上限从十万级提到十亿级（积分加倍活动），随后用户投诉"同分玩家的先后名次每隔几分钟变一次"，不同页面读到的同一人名次还不一致。

  • 为什么：复合分数公式没随分数上限重新评估——$10^9 \times 10^7$ 量级的合成值超过 $2^{53} \approx 9.007 \times 10^{15}$，double 舍入把低位 tie-break 整段抹掉，同分玩家的合成分数坍缩成同一个值，展示顺序退化回 member 字典序；再叠加客户端浮点解析误差（JS Number 同样只有 53 位精度），对外表现为"名次随机跳变"。

  • 系统如何表现：Redis 本身没有任何异常——它只是忠实地存了两个物理上相同的 double；错误发生在"业务语义 → 数值表示"的映射层，所以监控、慢查、错误日志全都安静。

  • 如何定位：取两个"业务同分、ID 不同"的 member，ZSCORE 对比——合成值完全相同即坐实；检查合成值的十进制位数是否逼近 16 位。若 5.3 节的单测断言存在，这类问题在 CI 阶段就会被拦住。

  • 如何恢复：重算全量合成分数（缩紧 N，或改用 5.2 节方案 B 的 member tie-break），ZADD 原子覆盖迁移；迁移期间写入走"新分数 + 旧分数"双 key 过渡；对外先冻结名次展示。恢复的难点不在技术而在信任：名次类数据出错后需要运营公告与补偿预案，这是选型时就该写进评审文档的回滚成本。

九、注意事项与排坑清单

  1. BYSCORE 命令永远 LIMIT 0 count：offset 的成本跨版本不一致（≤7.2 为 O(N)，≥7.4 才修复），这是线上最常见的"Redis 深翻变慢"真凶。在封装层禁止 offset 参数透传。

  2. 游标边界用 ( 开区间，不要手工 ±1：浮点分数没有"最小步长"，-0.0001 这类手工步进在分数刻度变化后必然出错；同分问题必须用复合 Score 或两段查询显式解决，纯开区间会整块跳过同分 member。

  3. 复合分数先算 $2^{53}$ 预算再上线：$(S_{max}+1) \times 10^N \le 2^{53}$ 写成单测断言；分数上限变更必须重新评估；客户端全链路字符串透传，禁止过 JS Number。

  4. 限制单页 M 与总 payload：单页建议 ≤100 条；member 只存 ID，详情用 Pipeline 批量查 Hash；封禁 ZRANGE key 0 -1 式全量拉取，把大 Key 巡检纳入日常。

  5. 监控对准"单命令耗时"而非"接口耗时"：slowlog-log-slower-than 建议收紧到毫秒级观察 ZSET 命令；INFO commandstats 的 usec_per_call 按 cmd 维度跟踪趋势——rank 定位本身不该成为慢源，谁慢谁可疑。

  6. "共 X 页"的展示要么放弃，要么接受漂移：ZCARD 是 $O(1)$，但它返回的是"此刻"的总数，与用户当前页码没有一致性保证；展示"已超过 99% 的玩家"这类模糊口径通常更稳妥。

十、最佳实践总结

原则：能按数据续读（BYSCORE 游标）就不按位置翻页（rank offset）；必须按位置翻页时，清楚自己在用"会漂移的排名"；永远不要把 offset 塞进 BYSCORE 命令的 LIMIT。

  1. C 端（无限滚动）：ZRANGE ... BYSCORE REV LIMIT 0 10（或 ZREVRANGEBYSCORE ... LIMIT 0 10）+ 复合 Score 处理同分，性能恒定 $O(\log N + M)$，并发写入下语义最稳。

  2. B 端（随机跳页）：ZREVRANGE 按 rank 翻页是可接受的（span 定位 $O(\log N)$），但必须硬限制单页大小与可翻范围——防的是 payload 与滥用，不是定位成本；需要严格一致视图时用快照 key。

  3. 接口设计：游标做成不透明字符串；响应必带 score；空页即终止；不要把 Redis 内部的 rank 直接暴露给前端当业务概念。

  4. 数据设计：复合 Score 的精度预算进单测；小数分数先整数化；member 不放大 payload。

  5. 可观测性：slowlog 与 commandstats 双看板；ZSET 命令单次耗时异常即告警，优先排查 LIMIT offset 与全量拉取两种模式。

十一、回到最初的问题

"Redis ZSET 深度分页为什么慢"这个问题本身就问错了一半：rank 定位不慢（$O(\log N)$），慢的是把"位置"当成"身份"的翻页语义，以及藏在 LIMIT offset 里的线性路径。把 MySQL 深分页的教训平移到 Redis，会得到正确的方案（游标化）和错误的理由（定位成本）——而理由错了，方案迟早会在某次"简化重构"中被改回去。理解 span 这个细节不是为了炫技，而是为了知道哪些优化是必要的，哪些只是仪式。
