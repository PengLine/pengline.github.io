PenShot 安全加固：环境变量信任边界、回调 SSRF 与配置脱敏

版本基线：本文基于 PenShot v0.4.5 之上的安全加固分支（PR #88，当前 review 分支 review/pr-89）复核，2026-11-17。该批次截至写作时尚未进入正式发布版本，接口与默认行为可能随合并调整；正式发布后请以 Release 与 CHANGELOG 为准。

相关链接：GitHub | 安全加固 PR #88

分镜 Agent 的安全讨论很容易停在“模型会不会生成不当内容”。但 PenShot 是一个带 REST 接口、任务队列和 Webhook 回调的服务：它接收外部传入的剧本与配置，也会主动向外部地址发请求。真正的攻击面在这一进一出之间。

这次安全加固批次处理了四类问题，彼此独立但指向同一条原则——信任边界要显式：

问题 攻击方式 加固手段
请求配置里的 api_key: "$SECRET" 让服务端展开宿主机环境变量，探测或盗用密钥 只在受信本地配置加载上下文允许展开
任意 callback_url SSRF：访问回环、内网、云元数据地址，或用 DNS Rebinding 绕过校验 静态校验 + DNS 全量验证 + 目标 IP 固定
GET /config 返回完整配置 泄露宿主机路径、数据库连接串与密钥对象 改为白名单脱敏响应
请求传入 checkpoint_dir / postgres_uri 指定任意落盘路径、连接攻击者数据库 请求反序列化时强制重置

下面按源码逐项拆开。

一、环境变量展开：从“哪里都能展开”到“只在受信上下文”

1.1 原来的问题

配置模型允许 api_key 写 ${OPENAI_API_KEY} 这类引用，加载时通过 os.getenv() 展开。这对本地 settings.yaml / .env 是合理需求——密钥不该明文进仓库。

问题在于，LLMBaseConfig、EmbeddingBaseConfig、ImageBaseConfig 同时也会被请求体实例化。于是外部请求只要传：

服务端就会在宿主环境里查找这个变量，把值填进配置。攻击者未必能直接读回密钥，但可以借此改变服务端行为；如果某个接口随后把配置回显或写进任务记录，泄露就发生了。

1.2 加固后的模型

核心是一个默认关闭的 ContextVar（src/penshot/config/security/env_resolver.py:20）：

只有 Settings.__init__ 会用这个上下文包住配置加载（src/penshot/config/config.py:51-56）：

也就是说：

  • 本地配置加载（settings.yaml、.env、环境变量覆盖）→ 允许 $VAR，保持原有部署方式；

  • 请求体反序列化（同步、异步、批量接口）→ 默认不在受信上下文，$VAR 直接抛 ValueError；

  • 字面量密钥 → 照常接受，不受影响。

resolve_api_key_value() 是统一入口（env_resolver.py:88），LLM / Embedding / Image 三套配置的 api_key 校验器都改为调用它。展开前还会校验引用语法：

  • 支持 ${VAR}、${VAR:default}、$VAR；

  • 变量名必须是标准 POSIX 标识符 ^[A-Za-z_][A-Za-z0-9_]*$，拒绝 BAD-NAME、空白、空引用、未闭合的 ${；

  • SecretStr 会先取出原始值再判断，避免因为类型包装绕过校验。

批量接口是容易漏的入口，因为它既能平铺传 llm.api_key，也能传 llm.default.api_key / llm.fallback.api_key。_validate_batch_provider_section()（src/penshot/api/rest_api.py:51）把两种结构都实例化成对应配置模型，从而统一触发同一套环境变量策略；测试覆盖了 llm、embed、image 三组、平铺与嵌套共十余种写法。

边界说明：这不是“禁止环境变量”，而是把展开能力限制在“能改本地配置文件的人”手里。能改 .env 的人本来就能读到宿主环境，信任边界没有扩大；外部请求则不再具备这个能力。

二、回调 SSRF：校验 URL 不够，还要固定 IP

Webhook 回调是典型的出站请求：任务完成后，服务端向用户提供的 callback_url POST 结果。如果不校验，它天然是一个 SSRF 原语——攻击者可以让服务器访问 127.0.0.1 的管理端口、10.0.0.0/8 的内网服务，或者云环境的 169.254.169.254 元数据接口。

2.1 静态校验：先把明显不该发的挡掉

validate_callback_url() 与 _parse_and_validate_callback_parts()（src/penshot/neopen/task/task_lifecycle_service.py:265、:118）先做不依赖 DNS 的检查：

检查项 拒绝的输入
协议 ftp://、file:// 等非 http/https
用户信息 https://user:pass@example.com、https://@example.com
端口 非法端口、超出 1–65535
主机名 localhost、*.localhost、*.local、*.internal
字面量 IP 回环、私网、链路本地、多播、保留、未指定、非全局地址
特殊 IP IPv6 zone id；IPv4-mapped、6to4、Teredo、NAT64 中内嵌的私网 IPv4；RFC 8215 本地 NAT64 前缀

最后两条值得单独说。只判断“这个 IPv6 地址是不是公网”并不够：::ffff:127.0.0.1 在字符串层面是 IPv6，实际指向回环；64:ff9b::7f00:1 通过 NAT64 也能落到 127.0.0.1。代码会把这类过渡机制里内嵌的 IPv4 抽出来再校验一次（_extract_embedded_ipv4()），这也是 SSRF 防护里最常见的漏点之一。

2.2 DNS 校验：任何一条私网记录都整体拒绝

域名不能只看字面量，必须解析。请求入口（ProcessRequest.validate_callback 与 set_callback）先做静态校验；DNS 全量验证与实际发送前的 IP 固定发生在 _trigger_callback_async 调用 resolve_and_pin_callback_target() 时。加固后的逻辑是：

  1. 在 5 秒超时、最多 8 个并发查询的限制下解析全部 A/AAAA 记录；

  2. 每一条记录都必须是公网地址；

  3. 只要出现一条私网、回环或 IPv4-mapped 内网记录，整个 URL 拒绝——不能因为“第一条是公网”就放行，否则攻击者可以用混合记录绕过；

  4. 并发信号量要等底层 getaddrinfo 真正结束才释放，避免慢查询超时后提前归还配额、导致在途查询突破上限。

这部分对应 _assert_public_ip()、_resolve_public_ips_with_guard()（task_lifecycle_service.py:89、:168）。

2.3 DNS Rebinding：校验完再解析一次就前功尽弃

即使 DNS 校验通过，还有一个经典的时间差攻击：校验时域名解析到公网 IP，真正发请求时 TTL 已过、域名改解析到 127.0.0.1。只“校验 URL”不解决这个问题。

PenShot 的做法是解析一次，然后把 TCP 连接目标固定为已验证的 IP（resolve_and_pin_callback_target()，task_lifecycle_service.py:213）：

  • pinned_url 只替换了主机部分，路径与查询串保持不变；

  • 原域名放进 Host 请求头，服务端虚拟主机路由不受影响；

  • HTTPS 场景通过 extensions["sni_hostname"] 保留 SNI，证书仍按原域名校验；

  • 实际发送时 follow_redirects=False、trust_env=False（task_lifecycle_service.py:665），避免 30x 跳转把请求带到未校验地址，也避免读取环境里的代理配置。

flowchart TD
    U[callback_url] --> P[解析与静态校验]
    P -->|协议/凭据/端口/主机名| L{字面量 IP?}
    L -->|是| IP[公网 IP 校验]
    L -->|否| D[DNS 解析全部记录]
    D --> A{每条记录都是公网?}
    A -->|否| X[拒绝]
    A -->|是| PIN[固定已验证 IP<br/>保留 Host 与 SNI]
    IP --> PIN
    PIN --> S[发送回调<br/>禁止重定向]

这套组合解决的是“校验目标”和“连接目标”不一致的问题。校验与连接之间不再有第二次 DNS 解析，Rebinding 就失去了作用点。

三、配置暴露与请求净化：白名单比黑名单可靠

3.1 GET /config 不再返回完整配置

原来的接口直接返回 ShotConfig，其中包含：

  • checkpoint_dir：宿主机落盘路径；

  • postgres_uri：数据库连接串；

  • llm / embed / image：各供应商配置对象，含 API Key（虽然用了 SecretStr，但完整对象本身不应出现在公开接口）。

加固后改为 PublicConfigResponse（src/penshot/api/rest_api.py:886），只列出可以公开的标量开关与阈值：enable_llm、时长范围、分割阈值、循环上限、检查点数量、缓存开关等。from_shot_config() 按 model_fields 白名单取值，checkpoint_dir、postgres_uri、llm、embed、image、api_key 都不在响应里。

白名单的代价是：将来新增公开字段需要手动加进模型。但对配置接口来说，这比黑名单安全——新字段默认不暴露，不会因为开发者忘了加过滤而泄露。

3.2 请求里的宿主机配置必须重置

外部请求可以带 config，但其中有两类字段不该由调用方决定：

字段 风险 处理
checkpoint_dir 写入任意路径 强制重置为服务端 data_checkpoint 目录
postgres_uri 连接攻击者控制的数据库，或读取内网数据库 强制置为 None

_sanitize_request_shot_config()（rest_api.py:43）同时挂在 ProcessRequest 与 SyncProcessRequest 的 config 校验器上；批量接口则在字典层面 pop 掉这两个键，再校验 llm / embed / image 子配置。这样无论走哪个入口，宿主机基础设施参数都不会被请求覆盖。

四、这套防护没有解决什么

安全加固最容易写成“已经安全了”。按当前分支的实现，至少还有这些边界：

  1. 内网 Webhook 会被一并拒绝。这是有意为之，但如果你的部署确实需要回调到内网服务（例如企业内网的通知网关），当前没有 allowlist 机制，需要在前置网关做转发，或自行扩展白名单。上线前要确认回调目标不是被误伤的私网地址。

  2. IP 固定不等于全链路加密。HTTPS 的 SNI 与证书校验保留，但如果调用方显式关闭 ssl_verify，中间人风险仍然存在。生产环境不要关。

  3. 回调失败只记录日志，没有重试。安全校验失败意味着这次回调不会发出；依赖回调的下游需要保留轮询兜底。

  4. 认证、限流、多租户不在这一批次内。这些接口仍然是“谁都能调”的形态，安全加固只处理了四条具体路径，不能替代整体的访问控制方案。

  5. 该批次尚未正式发布。分支上的接口与默认值可能调整，生产接入前请以正式 Release 为准。

五、验证清单：怎么确认加固真的生效

代码库为这批改动补了两组单测：tests/unit/test_env_resolver.py 与 tests/unit/test_security_hardening_88.py。常用的验证点可以直接对照：

  • test_untrusted_api_key_rejects_env_expansion：请求上下文里 $VAR 必须报错；

  • test_trusted_env_expansion_resolves_env_var_and_default：本地配置上下文里 ${VAR} 与 ${VAR:default} 正常展开；

  • test_validate_callback_url_rejects_unsafe_targets：覆盖回环、私网、IPv4-mapped IPv6、NAT64、云元数据地址、内网域名、非法协议等；

  • test_validate_callback_url_dns_resolution_blocks_private_and_mixed_records：DNS 返回公私混合记录时整体拒绝；

  • test_resolve_and_pin_callback_target_ipv4_and_ipv6_formatting：IPv4/IPv6 的固定 URL、Host 头与 SNI 格式；

  • test_dns_resolution_timeout_and_concurrency_limit：慢 DNS 的超时与并发配额；

  • test_trigger_callback_async_disables_redirects_and_pins_resolved_ip：发送时固定 IP、关闭重定向；

  • test_get_default_config_redacts_internal_paths_and_credentials：/config 不出现路径、连接串与密钥；

  • test_request_config_sanitizes_checkpoint_dir_and_postgres_uri：同步、异步、批量三个入口的路径净化；

  • test_batch_process_request_blocks_env_expansion_across_llm_embed_and_image：批量配置的平铺与 default/fallback 结构全部拦截。

六、结论

这次加固没有引入新的“安全框架”，做的是把四个隐含假设改成显式规则：

  1. 配置的信任边界要分层：本地文件可展开环境变量，外部请求不行；

  2. 出站 URL 是安全边界：静态校验、DNS 全量校验、IP 固定，三步缺一不可；

  3. 公开接口用白名单：默认不暴露，新增字段再显式放行；

  4. 请求只能改业务参数：路径、数据库连接这类基础设施配置由服务端决定。

对使用者的直接影响是：请求体里不能再写 $ENV_VAR 形式的 API Key，回调地址必须是公网可达的 http/https URL。对二次开发者的启示是：凡是“用户传 URL、服务端去访问”的地方，都值得按同一套方法审一遍。
