断点续跑、业务失败与成本核算实测

版本基线：NeoTask 1.1.1（PyPI，2026-11-15）；1.1.0（2026-11-13）引入本文涉及的 API。
测试环境：Windows 10 / Python 3.13 / Memory 与 SQLite 后端，探针使用 1.1.1 wheel。
口径说明：本文数字来自本机探针，只用于确认行为，不构成性能承诺。

先说结论：1.1 新增的不是三个“更好用的回调”，而是三件以前必须由业务自己兜底的事。 断点续跑把“失败后从头再来”改成“从最近一步继续”；业务失败把“重试没有意义的失败”从自动重试链路里摘出来；成本核算把散落在业务日志里的 token 与费用变成可按任务聚合的字段。

这三件事在 1.0.x 里都只能靠业务代码打补丁：自己存进度、自己判断异常类型、自己写用量表。1.1 把它们收进任务模型后，代价是多出几条必须弄清楚的边界——本文用探针逐条确认。

一、三个原语各自解决什么

原语 入口 1.0.x 的做法 1.1 的变化
断点续跑 save_checkpoint / load_checkpoint 业务自己写进度表，再按业务主键查回 状态存进 checkpoint 仓储，重试时自动注入 task.data["__checkpoint__"]
业务失败 report_failure(reason, detail) 抛异常，和系统故障一起走自动重试 标记 failure_reason，直接 FAILED，不消耗重试预算
成本核算 report_cost(...) / get_cost_summary() 另建用量表或在日志里打点 累加到 estimated_cost / cost_tracking，可按任务或批次汇总

判断标准很简单：如果失败重试一次结果还是一样，用业务失败；如果重试有意义但代价高，用断点续跑；如果一次执行消耗了外部资源，用成本核算。

2.1 自动重试与手动 retry 都会注入

Worker 处理失败时，如果还有重试预算，会先把最近 checkpoint 注入 task.data 并落库，再重新入队（🔧 worker/pool.py:677）。手动 pool.retry(task_id) 走另一条路径：终态任务先由 reset_for_retry 重置为 PENDING，同样在重置时注入 checkpoint（🔧 core/lifecycle.py:997，注入在 :1020）。

2.3 版本号是单调递增的，不是只保留 5 个就停在 5

默认 checkpoint_keep_versions=5（🔧 models/config.py:293），但它是“保留最近 5 个版本记录”，不是“版本号最大到 5”。探针连续保存 7 次：

读到的始终是最新状态，checkpoint_version 一路涨到 7，历史记录按保留策略清理。排查问题时不要用“版本号 ≤ 5”判断有没有 checkpoint。

2.4 四条边界

  1. 进程执行器拿不到上下文。 save_checkpoint() / load_checkpoint() 依赖 Worker 绑定的 contextvar，ProcessExecutor 在独立进程里运行，需改用 pool.save_checkpoint(task_id, state) / pool.load_checkpoint(task_id)（🔧 api/task_pool.py:1181）。

  2. 状态必须可 JSON 序列化。 不要把连接、文件句柄、ORM 对象塞进去。

  3. Memory 后端退出即丢。 checkpoint 和任务一起在内存里，进程重启后没有可恢复的状态。

  4. 终态清理会删 checkpoint。 默认 enable_terminal_cleanup=True、terminal_retention_seconds=0，即按任务自身 ttl 清理（默认 ttl 3600 秒）。如果人工介入的重试窗口比这更长，任务和 checkpoint 会一起消失，retry 自然失败。

第 4 条尤其要注意：它把“失败后随时可以 retry”变成了“失败后要在保留期内 retry”。需要长期保留失败现场时，把 terminal_retention_seconds 调大，或在业务侧先归档 checkpoint。

三、业务失败：让“重试没意义”的失败直接定稿

系统异常和业务判定失败是两类事。数据库超时值得重试；内容审核不通过，重试一百次还是同样的输入。1.1 用 failure_reason 把后者单独标出来：

report_failure 是同步函数（🔧 core/failure.py:84），登记后任务函数继续执行到自然返回，Worker 收尾时按登记原因把任务判为 FAILED（🔧 worker/pool.py:543）。探针在 max_retries=3 下验证：

retry_count 保持 0，说明没有消耗重试预算；error 保留了原因和明细，failure_reason 则是可查询的稳定标识。业务失败也不投递死信——它已经能按 failure_reason 筛出来，和“系统异常重试耗尽”区分开。

从任务外部（编排层、进程执行器的父进程）也可以用 pool.report_failure(task_id, reason, detail)，但它只对 RUNNING 状态生效（🔧 api/task_pool.py:1055）。还在排队的任务应先 cancel()，否则调用返回 False。

四、成本核算：按任务聚合，而不是只写日志

执行体里上报用量：

report_cost（🔧 core/cost.py:92）会把同一任务内的多次上报累加。探针结果：

两点设计值得注意：

  • 金额与用量分列存储。 estimated_cost 是独立列，cost_tracking 存 token、调用次数、币种等明细；聚合时用 pool.get_cost_summary(task_ids)（🔧 api/task_pool.py:1155），不传 task_ids 就汇总全部任务。

  • 终态任务仍可追加成本。 apply_cost 不限制 RUNNING（🔧 core/lifecycle.py:709-730），因为进程执行器的父进程往往在子进程结束后才拿到用量。币种不一致时汇总结果的 currency 会变成 MIXED，不要把它当真实币种展示。

进程执行器同样拿不到 report_cost() 的 contextvar，需在父进程调用 pool.report_cost(task_id, ...)。

五、父子关联与外部队列 ID

submit(parent_task_id="...") 只建立关联，不做自动汇总（🔧 api/task_pool.py:703）。子任务列表用 pool.get_children(task_id) 查，按创建时间升序，同样不递归（🔧 api/task_pool.py:979）。如果要把子任务的成本汇总到父任务，需要自己取 get_children() 再调 get_cost_summary(children)。

外部生成的 task_id 也可以直接传。它适合把业务主键当幂等键：重复提交会明确抛 TaskAlreadyExistsError，不会静默产生第二条任务。这个“明确失败”比“假装成功”更好排查，但调用方要接住这个异常。

六、1.1.1 的升级点：老库自动补列

1.1 新增了 failure_reason、checkpoint_version、parent_task_id、estimated_cost、cost_tracking、queue_wait_ms、duration_ms 七个任务列。1.1.1 在启动期检查老库并逐条 ALTER TABLE ADD COLUMN（🔧 storage/sqlite.py:201-216）。

探针用一个只含 1.0.x 列的 SQLite 文件验证：启动后七列补齐，旧任务仍可读取，新任务可以写入 parent_task_id。

这条升级路径只做“新增列 + 默认值”，不搬运数据，也不做跨后端迁移；老库里的历史任务不会凭空获得 checkpoint 或成本信息。

顺带一提，SQLite 的并发边界在 1.0.8 已经改过：默认启用 WAL、busy_timeout=30000，并在进程内串行化写连接（🔧 utils/sqlite_compat.py:33-40）。1.0.5 时代“多 Worker 很快报 database is locked”的结论，不应再直接套到当前版本上。

七、Blackboard 只在内存后端

pool.context_set/get/delete 提供进程内共享上下文，带可选 TTL，采用惰性过期（🔧 storage/memory.py:484）。它的定位是“同进程内多个任务共享一点状态”，不是分布式共享内存：

  • 只有 Memory 后端有；SQLite 后端调用会抛 UnsupportedFeatureError: blackboard is not supported by the 'sqlite' backend。

  • 值在写入和读取时深拷贝，不会因为共享引用被就地修改。

  • 进程退出即丢，不能当持久化存储或跨进程通信。

如果状态需要跨 Worker、跨重启，仍应回到任务数据或 checkpoint。

九、复现与边界

  • 源码与行为以 NeoTask 1.1.1 为准；官网文档目前仍以 1.0.8 为基线，1.1 的接口建议直接对照源码。

  • 本文只验证了 Memory 与 SQLite 后端、单进程探针；Redis 后端、多进程并发和进程执行器下的恢复链路没有覆盖，上线前应在预发环境按同样步骤复测。

  • “自动注入 checkpoint”依赖任务记录仍存在。终态清理、手动删除都会连带删除 checkpoint，长保留期的失败现场要提前配置 terminal_retention_seconds。
