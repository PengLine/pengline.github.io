PenShot 资产交接：asset_plan 是合同，不是图片

PenShot 相关链接：GitHub

文档定位：这是一篇机制文档，只描述 v0.4.5 主线代码里真实存在的字段、分支和落盘行为。文中不会把"计划里写了"当成"已经生成了"。
事实边界：asset_plan、asset_manifest、asset_ref 三段语义在 0.4.2 到 0.4.5 之间有过收紧，旧文章里"三视图会作为首帧"的说法已经失效。
代码标记：出现"源码/实现"字样时，对应逻辑可在 origin/main 核对；示例 JSON 用于说明结构，不是某次真实任务的完整产物。

读完本文后，你应该知道什么

  • asset_plan 和 asset_manifest 各自解决什么问题，为什么不能混用；

  • asset_ref 在 0.4.4 之后只承载什么，角色三视图与道具静帧分别怎么被引用；

  • 下游回填清单时，哪些引用错误会阻断、哪些只是提示；

  • 场景锚定不一致时，PenShot 会替换、阻断还是放行；

  • 为什么"跑完 PenShot 就有一堆图片"这个预期，在默认配置下并不成立。

一、先把预期降下来：PenShot 默认不生成图片

GENERATE_ASSETS 节点的文档写得很直白：默认不调用任何生图接口，只输出 asset_plan 供下游按需生成；只有显式启用生成执行器时，才会在本地生成并落盘。

这带来一个容易被忽略的结论：资产计划里的资产，默认状态是 pending，不是 generated。AssetStatus 只有四个值：

状态 含义 谁来写
pending 待生成，等待下游执行 PenShot 产出计划时的默认值
generated 已生成并拿到可用引用 下游回填清单，或本地执行器
failed 生成失败，带失败原因 回填清单里 error 非空的绑定
skipped 契约中已有可用资产，跳过重复生成 PenShot 复用旧契约时标记

所以"资产生成报告"里的 generated 数量，默认是 0；pending 才是常态。报告同时带 mode 字段，明确本轮处于哪种模式：

  • plan：只产出声明式计划；

  • manifest：消费下游回填清单，不重复调用生成；

  • generated：注入执行器后在本地产出。

这三个模式不是三种部署形态，而是同一条链路上的三个入口。下游可以先只拿计划，也可以带着上次的清单回来复用。

二、asset_plan：一份可执行的生图指令

AssetPlanDocument 是 PenShot 交给下游的"合同"，核心字段不多。注意 schema_version 取的是契约版本 CONTRACT_SCHEMA_VERSION，在 v0.4.5 里仍然是 0.4.4，不要把它当成产品版本号：

三个资产类型各有分工：

类型 典型对象 关键附加字段 在片段里的引用角色
character_sheet 角色三视图 views、consistency.identity_lock identity_reference，不作首帧
prop 关键道具静帧 state_variants（如 crumpled → balled） prop，可带 state
scene 场景锚点静帧 usage.scenes first_frame，唯一可作首帧的资产

usage 不是装饰字段。下游可以据此按片段、按场景懒生成，而不是把整份计划一次性全量出图。路由完成后，PenShot 会用 backfill_usage 把片段显式引用的资产并回使用范围，保证"声明引用了谁"和"谁该在哪个片段可用"是同一份口径。

道具的 state_variants 也不是自由文本：它由 advance_prop_state 按片段顺序单向推进。第 7 个片段把纸条揉成团之后，后面片段即使原文还写"皱巴巴"，状态也保持 balled，不会倒回去。

三、asset_manifest：把"规范 ID"接到"真实引用"

下游生成完图片，需要把结果回填成 AssetManifest：

这里最容易出错的是 ID。下游很可能用自己的命名（ds_char_001），所以清单提供了 asset_id_map。get_binding 的解析顺序是：先按映射查下游实际 ID，再回退规范 ID；两种都查不到才返回空。这样未改名和已改名的回填都能兼容。

AssetManifest 在 0.4.5 还接受下游直接写 assets 数组的旧格式，模型校验时会把它转成 bindings。这只是兼容入口，不改变内部口径。

回填发生在下一次任务提交时：把清单作为 asset_manifest 传入，GENERATE_ASSETS 会逐条应用绑定。绑定有 asset_ref 且引用校验通过，资产标 generated；引用校验失败（file:// 文件缺失、sha256 不匹配）时保持 pending，不会把坏引用挂进契约；binding.error 非空则标 failed；没覆盖到的仍是 pending。契约中已经标 generated、且本地引用文件确实存在的资产会被标成 skipped，避免重复出图。清单本身解析失败时只记告警并忽略，不会阻断整条流水线。

如果人工通过 AssetPromptEdit 改了某个资产的提示词，PenShot 会把这个资产重置为 pending，并把它从旧清单里摘掉。旧图对应的是旧提示词，继续复用才是真正的不一致。

四、asset_ref 只代表首帧：0.4.4 之后最重要的语义收紧

0.3.x 时代，很多人把 asset_ref 理解成"这个片段引用的角色图"。0.4.4 起这个理解不成立。

apply_image_to_video_routing 的注释写得很清楚：asset_ref 只承载下游回填清单中的场景首帧绑定，角色三视图的真实引用不会写进 asset_ref。片段内的资产引用统一放在 references 里，每条带 role：

  • 角色三视图：role="identity_reference"，as_first_frame=False；

  • 场景锚点：role="first_frame"，as_first_frame=True；

  • 道具静帧：role="prop"，as_first_frame=False，可带状态。

于是下游判断"要不要走图生视频"时，不能看 asset_ref 是否为空，而要看 references 里有没有 as_first_frame=true 的条目。示例代码也是这么写的：先找首帧引用，解析不到真实引用时才回退文生视频。

首帧指令有两种形态，取决于场景资产是否已经回填：

第二种形态很关键：它说明 asset_ref 为空不代表链路坏了，只代表首帧还没被下游生成。PenShot 保留了可执行的声明式提示词，而不是伪造一个引用。

五、引用校验：什么会阻断，什么只是提示

validate_asset_ref 的判定比直觉宽松，这是为了兼容历史产物：

引用形态 判定
http:// / https:// 直接通过，不下载
file:// 且文件不存在 阻断
裸路径且文件存在 通过，可校验 sha256
裸路径但文件不存在 默认通过，视为下游自定义标识
裸路径 + require_local_file=True 文件不存在即阻断
checksum 不匹配 阻断

也就是说，工作流默认不会因为一个 /cdn/xxx.png 式的标识去报错；离线校验工具则会打开 require_local_file，把"看起来像路径但其实没有文件"的情况拦下来。远程引用即使带了 checksum，也只记录不验证，并生成一条提示。

配套的 scripts/asset_manifest_tool.py 提供 template、validate、apply 三个子命令：生成空绑定骨架、校验清单、离线把绑定写回计划副本。它不实例化文生图客户端、不发网络请求，也不允许输出路径覆盖输入文件。适合在没有生成环境的地方先把清单结构对齐。

六、场景锚定：宁可阻断，也不让首帧写错地点

0.4.5 新增的场景锚定检查，是资产交接里最值得单独说的一段。它解决的问题很具体：片段描述写的是"教室"，首帧却挂了"走廊"的场景资产。

resolve_scene_anchor 只在一种前提下启动：片段文本明确提到其他场景，且没有提到当前首帧场景。然后分三种结果：

  • auto_replace：唯一命中另一个场景资产，直接把首帧引用换成它，并用新场景重建首帧提示词；

  • ambiguous：同时命中多个场景资产，无法唯一判断，片段标 needs_manual_fix；

  • no_asset：文本出现了其他场景词，但契约里没有对应资产，同样阻断。

阻断的片段会汇总到 RoutePlan.blocked_fragments。下游渲染队列应当跳过这些片段，而不是"先渲了再说"。这一点比自动替换更重要：自动替换解决的是明确错误，阻断解决的是不确定。

检查还会剔除引号内台词。角色在台词里说"回走廊"，不代表画面就在走廊；如果把这句算作场景证据，首帧会被错误地替换。

七、降级资产：服装信息不足时，不允许生成正脸

apply_asset_attention_constraints 处理的是另一类风险：角色资产被标记为 requires_special_attention，且服装关键字段（类型、颜色、材质）缺失。

这时引用该角色的片段不会拿到"按完整正脸生成"的许可，而是追加一条可执行约束：本片段须降级为剪影/背影（silhouette / back view），不得生成正脸与服装细节。同时 RouteDecision.degraded_assets 里会带结构化条目：

这不是审美偏好，而是悬疑类剧本的硬约束：服装信息不足还硬给正脸，观众会立刻发现角色前后不是同一个人。把它写成可消费的字段，下游才能在执行层真正落实，而不是停留在一条自然语言告警里。

八、一个最小可用的下游回路

如果只想跑通链路，最小步骤只有三步：

  1. 从任务结果里取 asset_plan，只为 usage.fragments 命中的资产出图；

  2. 把结果写成 asset_manifest，用 asset_id_map 记录改名；

  3. 把清单作为 asset_manifest 重新提交，或在同一进程里传给 generate_assets。

仓库里的 examples/sdk/08_asset_handoff.py 演示了完整回路：构造契约与指令、产出计划、按 references 调视频服务、再把清单回填。它的价值不在代码长度，而在把"计划 → 生成 → 回填 → 复用"四个动作串成了一次可重复执行的流程。

九、边界与常见误读

  • asset_plan 不是资产包：它只有提示词与约束，没有像素。默认配置下跑完 PenShot，不会凭空多出一目录图片。

  • generated 不代表 PenShot 生成：它只表示"这个资产已经有可用引用了"，来源可能是下游回填，也可能是本地执行器。

  • asset_ref 不是角色引用：0.4.4 起它只代表场景首帧绑定。角色身份走 references 里的 identity_reference。

  • 执行器不是默认开启：ImageClientExecutionAdapter 只在显式注入或配置开启文生图时实例化；它的 generate_videos 明确返回 supported: false，不会假装能生成视频。

  • 引用校验宽松是有意的：裸路径不存在默认放行，是为了不让历史产物整批失效；需要严格校验时用离线工具。

  • 阻断片段必须被下游尊重：blocked_fragments 不是提示信息，是"不要进入渲染队列"的清单。

十、结论

PenShot 在 0.4.x 做的最重要的一件事，是把"资产"从一句提示词，变成一份有版本、有状态、有引用语义的交接契约。

  • 计划层负责"该有什么、长什么样、在哪些片段用"；

  • 回填层负责"真实资产在哪里、叫什么、校验过没有"；

  • 路由层负责"哪个片段拿哪个资产当首帧，哪些片段必须阻断或降级"。

这三层分开之后，PenShot 不需要假装自己是一个生图平台，下游也不需要猜 PenShot 的隐含约定。判断一份资产链路是否真的可用，不要看计划里写了多少资产，要看 status、references 与 blocked_fragments 有没有被下游真正消费。
