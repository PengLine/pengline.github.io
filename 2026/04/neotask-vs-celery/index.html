Celery 三件套为何偏重？NeoTask 1.0.5 进程模型与选型边界

Celery 三件套为何偏重？NeoTask 1.0.5 进程模型与选型边界

Celery 是 Python 生态最成熟的任务队列，成熟到很多人把它当成"任务队列"的同义词。但成熟有成熟的代价：broker、worker 进程、result backend 三件套，外加一套不算短的配置。对一个只想把"发邮件、转码、爬数据"挪到后台的中小项目来说，这套架构经常比业务本身还重。

NeoTask 的定位恰好相反：任务池是一个嵌入应用进程的 Python 对象。TaskPool(executor=...) 构造即装配，start() 起一条后台事件循环线程，SQLite 形态下不需要任何外部服务。

这篇文章以 NeoTask 1.0.5（2026-10-29 发布）为基线，从依赖、进程模型、源码接线三个角度对比两者的真实差异，并明确哪些场景仍应选 Celery。文中 🔧 表示仓库原样源码，📝 表示示例代码；所有性能数字仅来自 NeoTask 自己的基准脚本，不做跨框架臆测。

一、选型分水岭不是"快"，是进程模型

先给结论：Celery 是独立部署单元，NeoTask 是库。

这个差别决定了一切后续差异：

维度 Celery NeoTask 1.0.5
运行位置 独立 worker 进程 应用进程内的后台事件循环线程
外部依赖 broker（Redis/RabbitMQ）+ result backend 无（memory/SQLite 形态）；Redis 形态 1 个
故障域 worker 与业务进程隔离 与业务进程同生共死
扩展方式 增加 worker 进程/机器 增加应用实例（Redis 形态）
调试 起 worker 或用 apply() 绕过 断点直接命中任务函数

如果你的任务系统要服务多个团队、多种语言、多个队列，Celery 的独立部署是优势；如果任务只是这个 Python 服务的一部分，独立部署就是额外的运维负担。先选进程模型，再谈功能清单，这是选型里最不容易后悔的顺序。

二、Celery 的负担具体在哪

2.1 配置不是能力，是前置成本

让 Celery 真正可用，至少要配齐 broker、result backend、序列化、时区、并发模型与任务时限：

这些配置大多不是业务需要，而是架构需要：因为 worker 是独立进程，所以要序列化；因为要跨进程传结果，所以要有 backend；因为 prefork 会泄漏内存，所以要有子进程回收策略。

2.2 依赖与部署链：1.0.5 是 3 个基础依赖

Celery 的依赖树包含 kombu、billiard、vine 等，加上 broker 与 result backend，一套部署至少涉及 2 个外部服务。

NeoTask 的硬依赖在 1.0.5 中收敛为 3 个（🔧 实证来自 wheel 的 METADATA）：

版本 无条件安装的依赖 说明
0.1.1 / 0.4.1 无 早期"零依赖核心"形态
1.0.1 aiosqlite、redis、psutil、croniter 一度四个全部转正
1.0.2 aiosqlite、croniter 收敛回 2 个，redis/psutil 移回 extra
1.0.5 aiosqlite、croniter、colorama 新增 colorama 用于 CLI 彩色输出

要说清楚的是：“3 个 pip 包"不等于"3 个外部服务”。aiosqlite 是 Python 内置 sqlite3 的异步封装，croniter 是纯 Python 的 Cron 解析器，colorama 只影响终端颜色；三者都不需要额外进程。按"外部服务数"衡量，NeoTask 在 memory/SQLite 形态下仍是 0，Celery 至少是 2。这是两者部署成本的真实差距。

2.3 调试与资源占用

Celery 任务失败时，堆栈常裹着 kombu/worker 的多层包装；本地调试要么起 worker，要么 task.apply() 绕过分发层，而后者测不到真实链路。

NeoTask 的任务函数就是普通 async 函数，运行在应用进程的后台事件循环线程里（🔧 api/task_pool.py:332 的 start()），IDE 断点直接命中：

调试差异要提前知道：任务跑在后台守护线程的循环里，不是主线程；asyncio 的上下文与主线程不同。同步函数会被自动包装（🔧 api/task_pool.py:225-245），默认的 ASYNC 执行器下，同步阻塞代码会卡住整个循环——这类坑官方最佳实践里有专门提醒。

资源方面，Celery 默认 prefork，每个 worker fork 多个子进程，内存随任务量台阶式上涨；NeoTask 是单进程（事件循环线程 + 可选线程/进程执行器），内存增量以 MB 计，可与 FastAPI 共存：

代价也明确：业务进程 OOM，任务池一起停。Celery 的 worker 隔离在这一点上不可替代。

优先级是内置的：TaskPriority 四级（CRITICAL/HIGH/NORMAL/LOW），入队按优先级排序；Cron 由 croniter 解析，1.0.5 还修复了 Cron 别名。状态机是 PENDING/RUNNING/SUCCESS/FAILED/CANCELLED/SCHEDULED 六态，任务结果与状态存在同一套存储抽象里——没有独立的 result backend。

3.2 周期任务：1.0.5 默认持久化

早期版本最容易被吐槽的一点是周期任务只存内存，重启即丢。1.0.5 的 SchedulerConfig 把 enable_persistence 默认设为 True（🔧 models/config.py:267）：

  • SQLite 形态：周期注册写进 SQLite，重启后恢复；

  • Redis 形态：写进 Redis，适合多节点调度；

  • memory 形态：无法持久化，注册时输出一次明确的降级警告（🔧 api/task_scheduler.py:342-370），不会静默丢失。

这仍然要求使用者确认存储形态：用 memory 跑周期任务，等于接受重启后重新注册。生产环境要么用 SQLite/Redis，要么把注册逻辑放进应用启动流程。

3.3 进度上报：1.0.5 已接通

1.0.2 时代 task.progress 字段和 on_progress 订阅器都在，却没有发布方。1.0.5 补上了这条链路：

实现上，Worker 在执行前把 ProgressReporter 绑定到 ContextVar（🔧 worker/pool.py:404-432），业务代码调用 report_progress()；同步任务用 report_progress_sync()。上报是尽力而为的：任务已结束、存储不可写时只记 debug，不会让业务任务失败。

它的边界也要说清：进度只覆盖"Worker 执行上下文"内的代码。业务里另起线程池、另起 event loop 跑的子任务拿不到 reporter，需要自己把回调传下去。这不是缺陷，而是 ContextVar 方案的固有边界。

3.4 存储即结果，少一个 backend

Celery 需要单独选型、部署、维护 result backend。NeoTask 的任务数据（data/status/result/error/progress）与队列在同一存储抽象内：memory 是 dict，SQLite 是单文件表，Redis 是 JSON + 状态索引（🔧 storage/sqlite.py、storage/redis.py）。查询任务与查询结果用的是同一套 API（get_task/wait_for_result），少一套存储就少一份运维和一致性风险。

四、迁移实践里最容易踩的语义差异

4.1 重试：Celery 在任务内决定，NeoTask 在框架层决定

NeoTask 在 max_retries 内按线性退避重试（🔧 worker/pool.py:455-474，delay = retry_delay × 新重试次数），任务代码无法决定"这次不重试"。需要业务判定时，只能抛异常或返回错误码由外层决策。1.0.5 新增的 retry() 是人工重试入口，不是任务内的自动重试控制。

4.2 周期任务：Celery Beat 是独立进程，NeoTask 是调度线程

差异有三点：Celery Beat 要单独起进程；NeoTask 的周期任务跑在调度器线程里；NeoTask 的持久化依赖 enable_persistence 与存储形态，memory 形态仍会丢。把注册放进启动流程，是两种方案都安全的做法。

五、能力边界：1.0.5 仍然没有的东西

5.1 没有 DAG / WorkflowEngine

WorkflowEngine 仍是 v1.5 路线图，1.0.5 源码里没有对应模块，from neotask import WorkflowEngine 会失败。当前的多任务串联只能在业务层做：

  • 任务 A 的 executor 内 pool.submit() 任务 B，用 wait_for_result 或事件回调做门控；

  • 把流程状态放进业务表，任务执行时检查前置状态；

  • 编排复杂时选 Prefect/Temporal，别让任务队列硬扛 DAG。

5.2 没有队列级路由与多租户

NeoTask 只有一个优先级队列 + 一个延时队列，没有按任务类型路由到不同 worker 集群的能力，也没有多租户与配额。需要"高优任务单独一组 worker""按租户限流"时，Celery 的多队列路由或专门的多租户方案更合适。

5.3 故障域与语言边界

  • 故障隔离：Celery worker 与业务进程隔离，业务 OOM 不影响消费；NeoTask 与业务同进程，进程挂了任务池一起挂（Redis 形态下任务还在，等进程恢复后重连消费）。

  • 跨语言：Celery 有跨语言 worker/消息协议；NeoTask 是纯 Python，worker 只能是 Python 进程。

  • Web 控制台：1.0.5 包含 web/、cli/ 与 Prometheus 导出（contrib/prometheus.py），但 TaskPool 不自动挂载 Web 服务，需要自行装配；Celery 侧 Flower 是成熟独立服务。

5.4 跨框架性能数字不可信

“Celery 1-2ms vs NeoTask 0.3-0.5ms 提交延迟”"5000/s vs 10000/s 吞吐"这类数字，双方都没有可复现的公开对照基准。NeoTask 官方基准脚本测的是自身端到端链路，1.0.5 在 memory 存储、10 Worker 下的量级是：只提交 14,657 tasks/s，提交并等待完成 2,433 tasks/s，串行往返 P50 15.50 ms。这些数字不能直接与 Celery 的吞吐对比，因为任务粒度、存储、是否等待完成都不同。选型时请自建同口径压测。

六、什么时候仍应选 Celery

  • 大规模生产与生态：Celery 有十年打磨与大量千万级/天部署案例；NeoTask 1.x 发布仅数月，核心业务建议先验证再上。

  • 多队列路由与优先级隔离：按任务类型/参数路由到不同队列与 worker 集群。

  • 语言异构 worker：需要非 Python 消费者。

  • 独立进程的故障隔离：业务进程崩溃不能影响任务消费。

  • 成熟监控生态：Flower、Prometheus 集成、社区插件。

反过来，NeoTask 更适合：中小项目的异步化改造、FastAPI/Flask 同进程后台任务、单机零外部服务的定时任务、桌面工具与原型验证。这些场景里，Celery 的三件套确实过剩。

七、为什么 NeoTask 这么设计

  1. 把"部署单元"降级为"对象"：TaskPool 构造即装配、start() 即运行、shutdown() 即回收（含上下文管理器），复杂度从运维层挪回代码层。代价是伸缩上限与进程绑定。

  2. 用存储抽象吸收部署差异：memory/SQLite/Redis 共享同一套 TaskRepository/QueueRepository 接口，开发到生产的切换是一行配置。代价是三种形态的故障模型不同，必须按场景选。

  3. 诚实的边界比功能表更有价值：1.0.5 已接通进度上报、周期持久化、手动重试与优雅停机，但 DAG、路由、多租户仍不在范围内。评估任何框架时，把"文档功能清单"与"源码接线清单"分开核对，比看对比表可靠得多。

总结

Celery 的复杂度来自它要解决的问题：独立部署、跨语言、大规模、多队列。NeoTask 的简单来自它主动放弃了这些：嵌入进程、纯 Python、单队列、单机优先。

选型时先问三个问题：任务需不需要跨语言消费？需不需要独立进程隔离故障？需不需要队列路由与成熟生态？三个都是"是"，Celery 依然是对的答案；三个都是"否"，嵌入式任务池省下的两个外部服务和一层运维，才是真实收益。

NeoTask 1.0.5 实测：3,000 个 noop 任务、10 个 Worker，关闭预取完成吞吐 2,382 tasks/s，默认 prefetch_size=20 只有 181 tasks/s，相差 13 倍。预取器是全局单例、按 0.1 秒节奏补货，任务太快时瓶颈从队列争用变成补货节奏。
