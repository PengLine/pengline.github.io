嵌入式任务池凭啥省掉 Broker？NeoTask 调度链路与边界

很多 Python 项目第一次遇到"接口不能等十分钟"的需求时，会本能地去找 Celery：装 Redis、起 worker、配 result backend，一套流程走完，任务队列反而成了系统里最重的基础设施。

NeoTask 走的是另一条路：把任务池做成一个 Python 对象。TaskPool(executor=...) 构造即装配，start() 在应用进程里拉起一条后台事件循环线程，任务函数就是普通的 async def。SQLite 形态下不需要任何外部服务，Redis 形态下才引入分布式能力。

这条路省掉了 Broker、worker 进程和 result backend 三件套，但也换来了新的问题：没有独立进程，故障域怎么隔离？没有 Broker，任务怎么保证不丢？没有 Celery 的生态，哪些能力必须自己补？

这篇文章沿 NeoTask 1.0.5 的真实源码走一遍调度链路，再回答这些取舍问题。文中 🔧 表示仓库原样源码（附路径），📝 表示示例代码；所有性能数字来自 1.0.5 基准脚本，环境与口径会一并说明。

一、一条 submit 到底走了哪些环节

先看门面。TaskPool.submit() 的签名在 1.0.5 里是：

四个参数分别对应任务数据、可选的业务主键、优先级、延时和任务级 TTL。它本身不做业务，只把活交给 TaskDispatcher：

这条链路值得注意的地方有三个：

  1. 先落任务记录，再入队。create_task 先把 PENDING 状态写进存储，队列里放的是 task_id 而不是任务体。这是"存储即队列"的前提：节点崩溃后，任务状态还在，回收器才有东西可扫。

  2. 入队失败不是静默丢弃。队满时任务被标记 FAILED 并抛 QueueFullError，调用方明确知道这次提交没成功。很多自研队列在这里只返回 False，任务从此消失。

  3. 分发器与生命周期管理器分离。TaskDispatcher 只负责"把任务送进队列"，状态流转归 TaskLifecycleManager。两者拆开之后，手动重试（1.0.5 的 retry()）可以复用同一套状态机，而不必绕过分发器直接改存储。

任务出队后进入 WorkerPool。Worker 不是拿到任务就执行，而是先做状态校验、再抢执行锁、再置 RUNNING：

注意这里的 ttl=30 是硬编码的：Worker 执行锁固定 30 秒，看门狗按 ttl × 0.3 即每 9 秒续期一次。TaskPoolConfig.lock_timeout 在这条路径上并不生效，手动 acquire_lock() 的 ttl 也是独立参数（默认 30 秒）——把配置调大不会延长执行锁，这是 1.0.5 里很容易被误读的一处，锁的排障细节在分布式锁与看门狗实战里展开。

整条链路可以压缩成一张图：

flowchart LR
    A["submit()"] --> B["TaskDispatcher<br/>create_task → PENDING"]
    B --> C{"delay > 0 ?"}
    C -- 否 --> D["PriorityQueue.push"]
    C -- 是 --> E["DelayedQueue.schedule"]
    D & E --> F["WorkerPool 出队"]
    F --> G["状态校验 PENDING"]
    G --> H["acquire 锁 30s + WatchDog"]
    H --> I["置 RUNNING → executor"]
    I --> J["SUCCESS / FAILED"]
    J --> K["事件总线 + Future 唤醒"]

这张图解释了 NeoTask 的基本性格：所有关键动作都落存储，队列只是索引入口。因此 memory 存储快但重启即丢，SQLite 单文件可恢复但并发写入受限，Redis 可多节点共享但引入网络依赖——三种形态的差异全部来自这一条设计。

二、三种存储，三种故障模型

TaskPoolConfig 在 1.0.5 里提供三个工厂方法：

SQLite 的默认路径是 /data/neotask.db（🔧 models/config.py:167），不是当前目录的 neotask.db。容器里没有 /data 目录时会直接报错，这是部署时的第一个坑。选择显式路径，比记住默认值可靠。

三种形态的边界需要用"故障模型"而不是"性能排序"来理解：

形态 任务记录在哪 重启后 多进程/多节点 主要代价
memory 进程内 dict 全部丢失 不支持 零依赖，零持久化
SQLite 单个 .db 文件 可恢复 单机多 worker 写入易锁冲突 写放大、database is locked
Redis Redis 键与状态索引 可恢复 支持，对等消费 多一个外部服务与网络故障面

具体到 SQLite，1.0.5 基准里有个很扎眼的边界：100 条任务突发提交，1 个 Worker 能全过（25.5 tasks/s），2 个 Worker 从第 37 次提交开始报 database is locked，4 个 Worker 从第 36 次开始报。这不是 bug，而是 SQLite 单写者模型与"每个状态变更都要落库"叠加的必然结果。SQLite 适合单进程、低并发的持久化，不适合多 Worker 抢写；要并发，就换 Redis，或者把 Worker 并发压到 1。完整复现见 SQLite 多 Worker 为什么会 database is locked。

Redis 形态则把"任务记录 + 队列 + 锁 + 心跳 + 死信"全部外置，节点之间对等消费。它换来的不是更快的单机性能，而是故障域的分离：一个节点挂掉，任务还在 Redis 里，其他节点能接手。代价也很直白——Redis 不可用时，整个任务池不可用；网络抖动会同时影响出队、续锁和心跳。

三、定时任务：周期注册为什么会"重启即丢"

TaskScheduler 是另一个门面，负责延时、指定时间点、固定间隔和 Cron。它的一个历史坑是周期任务只存在内存里，进程重启后注册全部消失。1.0.5 的 SchedulerConfig 把这件事改成了显式配置：

默认 enable_persistence=True，SQLite/Redis 形态下周期任务会写进专属存储，重启后恢复；memory 形态无法持久化，注册时会输出一次明确的降级警告（🔧 api/task_scheduler.py:342-370）。这比"静默丢失"好得多，但仍然要求使用者做一件事：生产环境不要用 memory 形态注册周期任务，或者在应用启动流程里重新注册。

延时任务还有一条可选路径：enable_time_wheel=True 时走时间轮，适合大量秒级延时；默认关闭，用每 0.1 秒检查堆顶的内存延时队列（🔧 queue/delayed_queue.py:34）。两者不是性能玄学，而是精度与开销的取舍——时间轮减少扫描开销，但槽位与 tick 配错会放大误差。另外要记住：TaskPool 的延时任务只存在这个内存堆里，不跟存储后端走，进程重启即丢；周期任务是另一套带持久化注册表的链路，别把两者混为一谈。

四、1.0.5 补上的进度上报

早期版本的 task.progress 字段有存储、有订阅器，却没有发布方，on_progress 永远收不到事件。1.0.5 补上了这条链路：Worker 在执行任务前把 ProgressReporter 绑定到 ContextVar，业务代码直接调用导出的函数即可。

同步任务用 report_progress_sync()；它内部区分"已在 Worker 事件循环线程"和"在线程池线程"两种情况，前者用 create_task 调度，后者用 run_coroutine_threadsafe 提交并等待（🔧 core/progress.py）。进度上报是尽力而为的：任务被删除、事件循环关闭或存储不可写时，上报失败不会让业务任务失败。

这个设计值得借鉴的地方在于 ContextVar：进度回调跟着任务上下文走，不需要把 reporter 作为参数塞进每一个业务函数，也不会因为并发任务而串号。代价是它只对"在 Worker 执行上下文里"的代码有效，自己另起线程池跑的子任务拿不到 reporter，需要显式传递。

五、分布式能力：心跳、回收、锁、预取各管一段

Redis 形态下，NeoTask 的高可用不是靠一个"主节点"兜底，而是四个组件各管一段：

  • 心跳（HeartbeatManager）：节点定期写心跳键，默认 5 秒一次、20 秒超时（🔧 TaskPoolConfig）。

  • 回收器（TaskReclaimer）：每 30 秒扫 RUNNING 索引。超时回收看任务自身的 ttl（默认 3600 秒），孤儿回收看执行节点是否还在活跃集合里。没有装配节点管理器时，孤儿回收整轮跳过——宁可晚回收，不可错回收。

  • 执行锁 + 看门狗：防止同一任务被两个节点同时执行；锁续期失败时停止续期，而不是疯狂重试。

  • 预取器（TaskPrefetcher）：批量把任务拉到节点本地队列，减少 Redis 往返；默认 prefetch_size=20，本地队列容量是其 5 倍。

预取是 1.0.5 里最需要按场景开关的组件。基准显示：微任务场景下，默认预取完成吞吐约 181 tasks/s，关闭预取反而达到 2,382 tasks/s，相差 13.1 倍。原因是预取器为每个任务做了额外的批量搬运与本地队列调度，任务本身只有微秒级时，这些开销占了主导；而 20ms 的 IO 型任务，预取又能显著提升吞吐。预取不是"默认开启就一定更好"的优化，而是一个按任务粒度选择的开关，细节见默认预取让短任务慢 13 倍。

1.0.5 的基准数字可以给一个量级参考（Windows 10、i7-1165G7、Python 3.13、memory 存储、10 Worker）：

场景 结果 口径
只提交 2,000 个 noop 14,657 tasks/s 不含执行
提交并等待 3,000 个任务 完成 2,433 tasks/s，P50 790 ms 含状态落库与事件
单任务串行往返 P50 15.50 ms 200 次串行
20 ms IO 任务，1→8 Worker 32.1 → 249.3 tasks/s（7.76×） 400 个任务
SQLite 串行 100 条 30.1 tasks/s 单 Worker

这些数字共同说明一件事：提交端很快，完成端受执行模型与存储约束。拿 14,657 的提交吞吐去和 Celery 的端到端吞吐比较，是口径错误；1697 ops/s 与 2,433 tasks/s 为什么不能直接比，那篇专门拆过。

六、能力边界：省掉的东西，迟早要还

嵌入式任务池不是"更轻的 Celery"，它有自己的边界，且边界大多来自"没有独立进程"这一根因：

  • 没有 DAG 编排。WorkflowEngine 仍是 v1.5 路线图，1.0.5 源码里没有对应模块。多任务串联要在业务层做：任务 A 的 executor 内提交任务 B，用 wait_for_result 或事件回调做门控。

  • 没有队列级路由。只有一个优先级队列和一个延时队列，无法像 Celery 那样按任务类型路由到不同 worker 集群。

  • 故障域与应用进程绑定。应用 OOM 或进程被杀，任务池一起停；Redis 形态下任务还在，但要等进程恢复后重连消费。

  • 多租户、配额、跨语言 worker 都不在范围内。这些是 v2.0 的规划，不是现成能力。

  • Web 控制台需要自行装配。1.0.5 包含 web/、cli/ 与 contrib/prometheus.py，但 TaskPool 不会自动挂载 Web 服务；要监控就接事件、指标或 Prometheus 导出。

反过来，它的优势也很具体：单进程内少一次序列化与网络往返，任务函数可以直接断点调试；SQLite 形态零外部服务，适合桌面工具、单机服务和原型；Redis 形态与业务共享一套 Redis，不必再养一个 Broker。

选型时先问三个问题：任务需不需要跨语言消费？需不需要独立进程隔离故障？需不需要队列路由与成熟生态？三个都是"是"，选 Celery；三个都是"否"，嵌入式任务池的运维收益才真正兑现。

七、最小可用示例

三个容易踩的点：TaskPool 支持上下文管理器，退出时会优雅停机；wait_for_result 默认超时 300 秒，长任务要显式放大；SQLite 路径要显式给，别依赖 /data/neotask.db 的默认值。定时任务则换 TaskScheduler，API 与 TaskPool 基本对称，周期注册记得确认 enable_persistence 与存储类型匹配。

八、工程结论

  1. NeoTask 的核心不是"功能少"，而是"把队列做成存储索引"。任务记录先落库、队列只放 ID、Worker 出队后二次校验状态——这条主线决定了它的恢复能力，也决定了三种存储的故障模型。

  2. 省掉 Broker 的代价是故障域与运维责任内移。单进程部署更简单，但进程挂了任务池一起挂；SQLite 零依赖，但多 Worker 抢写会锁；Redis 能分布式，但多了一个必须高可用的外部服务。选型不是选功能表，是选你愿意承担的故障模型。

  3. 1.0.5 把几个历史缺口补上了，但边界仍要自己守。进度上报已接通，周期任务在 SQLite/Redis 下可持久化，手动重试与优雅停机在 1.0.5 修复；但 DAG、路由、多租户仍不在范围内，预取要按任务粒度开关，SQLite 并发要克制。把这些边界写进架构决策记录，比事后从脏数据里反推便宜得多。

源码与行为以 NeoTask v1.0.5 为准；调度、存储、分布式各环节的源码级说明见官方文档。
