NeoTask 配置说明

📚 返回首页 | 📖 快速上手 | 📘 API 参考 | ⚙️ 配置说明 | 🐙 GitHub | 🐱 NeoTask 官网

版本基线：本文对照 NeoTask v1.0.2（PyPI 发布版），所有字段默认值出自 neotask/models/config.py（全文 372 行，本文配置类地图即该文件目录）。
代码标注约定：🔧 表示真实源码（仓库原样摘录，附文件路径，可自行对照）；📝 表示示例代码（用法演示、改进建议或教学代码，不代表仓库实现）。

概述：三个必须先知道的要点

  1. 配置来源只有两层：代码传入的 config 对象 > dataclass 默认值。没有环境变量层——源码中不存在任何 os.environ/NEOTASK_* 读取逻辑。

  2. WorkflowConfig 不存在：编排类能力在 1.0.2 无配置落点；TaskConfig 是旧版兼容配置（见第六节）。

  3. 绝大多数参数"写了就生效"，但仍有一批参数从未被读取（死参数，见第二节清单）。调参前先核对该清单，否则会得到"配置了却没反应"的困惑。

配置类全景（🔧 models/config.py）：

配置类 服务对象 关键备注
TaskPoolConfig TaskPool（即时任务） 主配置，见第二节
SchedulerConfig TaskScheduler（定时任务） 与 TaskPoolConfig 字段同构但独立，见第五节
StorageConfig / LockConfig 存储/锁工厂内部契约 由 TaskPoolConfig 翻译而来，一般不需直用
ExecutorConfig 执行器（async/thread/process） type 是 str（与 TaskPoolConfig 的枚举字段不同）
HeartbeatConfig / QueueConfig / WorkerConfig 分布式心跳 / 队列 / Worker 子模块 TaskPool 装配时多采用硬编码值（见 3.2）
WebUIConfig Web UI（需自行启动 WebUIServer） 默认 disable；enable(port, auto_open)
TaskConfig 旧版统一配置（兼容） 七件套组合 + with_webui
DistributedConfig 分布式（备用） TaskPool 装配不消费
常量 DEFAULT_TASK_POOL_CONFIG 等 全局默认实例 模块加载时生成

一、TaskPoolConfig：真实字段总表

🔧 models/config.py:161。所有默认值与源码逐字段一致：

存储域

参数 类型 默认 生效情况 说明
storage_type str "memory" ✅ memory/sqlite/redis，三档
sqlite_path str "neotask.db" ✅ sqlite 档数据库路径
redis_url str? None ✅ redis 档必填（redis 模式校验）

执行器域（任务的"执行载体"）

参数 类型 默认 生效情况 说明
executor_type ExecutorType 枚举 ExecutorType.ASYNC ✅ 见下方枚举说明
max_workers int 10 ✅ thread/process 执行器的池大小

🔧 executor/factory.py:19 的枚举共 5 值：ASYNC("async") / THREAD("thread") / PROCESS("process") / CLASS("class") / AUTO("auto")。传参建议用 ExecutorType.ASYNC 枚举；若传裸字符串 "async"，dataclass 不校验类型会照单全收，但工厂侧比较逻辑以枚举为主，跨版本有兼容风险。

为什么有两套"并发数"（新手最常混淆）：executor 是任务函数怎么跑（async=事件循环里直接 await / thread=线程池 / process=进程池），worker_concurrency 是多少个队列消费协程在拉任务。AsyncExecutor 模式下 worker 数与"同时执行的任务数"强相关（每个 worker 同一时刻执行一个任务）；thread/process 模式下实际并行度由 max_workers 决定，worker 只是投递者。

Worker 域

参数 类型 默认 生效情况 说明
worker_concurrency int 10 ✅ 队列消费协程数
prefetch_size int 20 ✅ 预取批量（内部放大为 ×5 本地队列等，见 预取机制）
task_timeout float? None ✅ 单任务执行超时（asyncio.wait_for），None=不限
enable_prefetch bool True ✅ 预取器总开关
prefetch_min_threshold int 5 ❌ 死参数 预取低水位由 prefetch_size÷4 计算，此字段全库零读取

队列与锁域

参数 类型 默认 生效情况 说明
queue_max_size int 10000 ✅ 队列容量上限；满时 TaskDispatcher.dispatch 抛 QueueFullError（见 优先级任务）
priority_levels int 4 ⚠️ 仅 QueueConfig 子层使用；TaskPool 装配不消费
lock_type str "memory" ✅ memory/redis；与存储档位独立，分布式必须 redis
lock_timeout int 30 ✅ redis 锁 TTL（经 LockConfig.redis 传入）

重试域

参数 类型 默认 生效情况 说明
max_retries int 3 ✅ 执行异常/超时的最大重试次数
retry_delay float 1.0 ✅ 重试延迟基数（实际延迟 = retry_delay × 新重试次数，递增退避）

监控域

参数 类型 默认 生效情况 说明
enable_metrics bool True ✅ MetricsCollector 创建并在池启动时 start、关闭时 stop；全局订阅 created/started/completed/failed/cancelled/retry 六类事件，系统采样循环自启，见 节点监控
enable_health_check bool True ✅ SystemHealthChecker 创建；get_health_status() 按 5s TTL 惰性执行检查（单项超时 5s），未装 psutil 时 system 项记 healthy/available=False；关闭后不再输出 checks
enable_reporter bool False ✅ True 时启动 60s 周期 ConsoleReporter（挂 get_stats）

回收 / 心跳 / 死信域（仅 Redis 模式有对象）

参数 类型 默认 生效情况 说明
enable_reclaimer bool True ❌ 死参数 reclaimer 在 Redis 模式无条件装配，此开关不被读取
reclaimer_interval float 30.0 ❌ 死参数 装配硬编码 interval=30
enable_heartbeat bool True ❌ 死参数 心跳随 NodeManager/HeartbeatManager 无条件启动
heartbeat_interval int 5 ❌ 死参数 装配硬编码 HeartbeatConfig(interval=5)
heartbeat_timeout int 20 ❌ 死参数 装配硬编码 timeout=20
enable_dead_letter bool True ✅ Redis 模式下创建 DeadLetterQueue 并注入 WorkerPool；重试耗尽与回收器的最终失败任务都会写入死信
dead_letter_max_size int 10000 ✅ 死信队列容量，创建 DeadLetterQueue 时传入
dead_letter_ttl int 604800 ✅ 死信保留 7 天（与任务清理无关）

节点标识

参数 类型 默认 生效情况 说明
node_id str socket.gethostname() ✅ __post_init__ 自动填充；多节点部署务必显式指定

二、死参数：为什么"写了没反应"

上一节清单暴露了一个反直觉事实：配置类里躺着一批字段，装配代码从不读取（🔧 config.enable_reclaimer / config.heartbeat_interval / config.prefetch_min_threshold 等）。它们不是 bug——dataclass 字段当然"存在"，只是没有被消费：

与这些零消费字段不同，监控与死信类开关都已接线：enable_metrics / enable_health_check / enable_dead_letter 均被读取并装配出真实组件，其中 DeadLetterQueue 由 WorkerPool（重试耗尽）与回收器共同写入（🔧 task_pool.py:182、worker/pool.py:192）。

为什么这么设计（探讨）

  • 配置类由各模块的 dataclass 汇总而来，字段是"设计意图的存档"；装配层图省事直接写默认值，导致意图与实现分叉——声明式参数被命令式硬编码架空。

  • 好处：装配代码自包含、可读；坏处：使用者按文档调 heartbeat_interval=2 期望更快心跳时，行为零变化（还会觉得是自己没调对）。

  • 实操建议：调任何参数前先确认"消费点"——本文档已标注 ✅/⚠️/❌，生产上以 2 分钟看一次实际日志（心跳 5s 一条、回收 30s 一次）验证参数是否生效。

三、类方法档位：官方推荐的创建姿势

🔧 TaskPoolConfig 提供三个语义化工厂（config.py:217），等价于手写字段但更省心：

⚠️ 记住：storage_type 与 lock_type 是两套独立开关。TaskPoolConfig.redis(...) 只切存储，锁默认仍是 memory——分布式场景要显式 lock_type="redis"，否则节点间执行锁互不可见（详见 分布式锁 与 持久化 的组合表）。

四、SchedulerConfig：定时调度器配置

🔧 models/config.py:248，TaskScheduler 专用。字段与 TaskPoolConfig 的存储/Worker/重试域同构（TaskScheduler 初始化时把 6 个字段翻译给底层 TaskPool，🔧 task_scheduler.py:68），差异在调度专属域：

参数 默认 生效情况 说明
enable_persistence False ❌ 不生效 周期任务持久化开关；底层 _load_tasks/_save_task 全是 TODO 空实现（🔧 scheduler/periodic.py:709）——周期定义任何时候都只活在内存，重启即失
scan_interval 1.0 ✅ 调度循环扫描间隔（秒）；注意不是 0.05
enable_periodic_manager True ✅ 周期任务管理器（interval/cron 的调度者）
enable_time_wheel False ✅ 时间轮开关。开启后 submit_delayed 走时间轮：任务先以 PENDING 落库，再 TimeWheel.add_task；超出量程自动退回延时队列（详见 延时任务）
time_wheel_slots 60 ✅ 时间轮槽位数，与 tick、max_rounds(100) 共同决定量程
time_wheel_tick 1.0 ✅ 滴答间隔；TaskScheduler 用本值，量程 = 60 × 100 × 1.0 = 6000s（注意 TimeWheel 类默认 0.1 → 600s）
default_max_runs None ✅ 周期任务默认最大执行次数
default_missed_policy "skip" ✅ 错过执行策略：skip 与 ignore 等价（丢弃错过的槽位，只推进 next_run）、run_once 只补跑一次、catch_up 补跑且单轮上限 5 次

另有语义化类方法：memory() / sqlite(path) / redis(url) / high_performance()（启用时间轮 360 槽 + 0.5s 扫描）/ lightweight()（关周期管理器与时间轮 + 2s 扫描）。

五、配套配置类速览（大多不用直碰）

类 真实字段与默认 说明
StorageConfig type="memory"、redis_url、sqlite_path（类方法 sqlite 默认 “tasks.db”，注意与 TaskPoolConfig 的 “neotask.db” 不同） 存储工厂的内部契约，由 TaskPool._init_storage 从 TaskPoolConfig 翻译（🔧 task_pool.py:234）
LockConfig type="memory"、redis_url、lock_timeout=30、heartbeat_interval=10、watch_dog_enabled=True 锁工厂契约；watchdog 自动续期由 lock 层自行消费
ExecutorConfig type="async"（str！注释含 async/thread/process/class/auto）、max_workers=None ExecutorFactory 直接用；类方法 async_executor/thread_executor(max_workers=10)/process_executor
HeartbeatConfig interval=5.0、timeout=20.0、cleanup_interval=30.0、max_reclaim_per_cycle=100 分布式心跳参数（TaskPool 装配硬编码 interval=5/timeout=20，见第二节）
QueueConfig max_size=1000、priority_levels=4、delayed_queue_check_interval=0.1 子模块级队列配置
WebUIConfig enabled=False、host=“127.0.0.1”、port=8080、auto_open=False、enable_websocket=True Web UI 配置；TaskPool 不会自动启动它，需自行实例化 WebUIServer
TaskConfig node_id + storage/lock/worker/queue/executor/webui 七件套（“兼容旧版 API”），类方法 memory/redis(url)/sqlite(path)/with_webui(port) 旧版聚合配置；DEFAULT_TASK_CONFIG 常量模块级预置

六、部署档位配置示例

调优参考（📝 经验值，非源码承诺）：

维度 建议 备注
worker_concurrency IO 密集 = CPU 核 ×2~4；CPU 密集 = 核数 async 执行器下为协程并发
max_workers thread/process 执行器专用 async 执行器忽略
prefetch_size 低延迟 1~5；高吞吐 20~50 内部还有 ×5/÷4/×3 的水位换算
task_timeout 平均耗时 ×3，别卡太死 超时走"重试→失败"，见快速上手 FAQ
lock_timeout 单任务最长耗时 ×2 以上 依赖 watchdog 续期时给足余量
queue_max_size 内存档注意 1KB/任务量级 满队列 submit 抛 QueueFullError，务必留余量
max_retries / retry_delay 3~5 次 / 1~5 秒 递增延迟 retry_delay×N

七、故障排查：配置相关的真实坑

现象 真实原因 处置
改了 heartbeat_interval/enable_reclaimer 等毫无反应 死参数（见第二节清单），装配硬编码 接受默认或改源码/等官方参数化
开了 enable_persistence，重启后周期任务没了 periodic 持久化族是 TODO 空实现 周期定义只能自己持久化重建（脚本启动时重新 submit）
测试环境 sqlite_path=":memory:" 任务不执行 实体与队列各持一条连接，各自独立内存库——出队后按 task_id 查实体查不到 测试改用临时文件路径或 memory 存储
队列满时 submit 直接抛 QueueFullError TaskDispatcher.dispatch 校验队列容量并抛出（queue_max_size 上限） 捕获该异常或给队列留余量
调了 task_timeout 没生效 可能是给 TaskPool 传了默认 config？task_timeout 默认 None 需显式传 TaskPoolConfig(task_timeout=...) 或类方法后赋值
executor_type 传字符串后行为怪异 该字段类型是 ExecutorType 枚举 统一用 ExecutorType.ASYNC 等枚举
SQLite 多进程各自消费同一 db 出队非原子 + 进程内锁互不可见 回到单进程，或升 Redis 档（详见持久化一文）
健康检查结果 5 秒内不刷新 get_health_status 有 HEALTH_CHECK_TTL=5.0 缓存，连续调用复用上次结果 属预期；需即时结果可看 last_check 时间戳
print(pool._config) 调试 可用（私有属性，版本间可能变动） 生产建议包一层 get_config()

总结

NeoTask 的配置体系用一句话概括：dataclass 字段齐全得像完整产品，装配代码却只消费了其中一部分。要点回顾：

  • 主配置 TaskPoolConfig 31 个字段中仍有 6 个死参数（全库零读取），其余参数（含监控 / 死信 / 时间轮开关）均真实生效——调参前对照第一节的 ✅/❌ 标注；

  • 配置来源只有"代码 config > 默认值"两层，环境变量与 WorkflowConfig 不存在，别按旧资料配置；

  • 存储三档 + 锁两档是独立开关，分布式 = storage redis + lock redis 双开；

  • SchedulerConfig 的 enable_persistence 尚未实现（周期定义只活在内存），周期任务可靠重建才是正解。
