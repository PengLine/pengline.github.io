PenShot 分块策略源码考证：双阈值切分、重叠真相与接线现状

PenShot 的核心目标之一是把任意剧本（包括小说、电影级超长剧本）自动拆分为 AI 视频模型可处理的片段序列。而超长剧本（场景动辄上百个、文本远超模型上下文窗口）无法一次性喂给 LLM，因此分块（Chunking）是这类型剧本落地的前置工程问题。但本文要回答的不止"怎么拆"——还有一个更基础的问题：分块能力在 PenShot 里到底上线了没有？

源码给出的答案很明确：LongScriptChunker（110 行）实现了 30 场景与 180 秒双阈值切分、3 场景重叠两块真实机制，但全仓库没有任何生产调用方；README 的开发路线图至今仍把"超长剧本分块处理 + 向量数据库上下文记忆"列在中期规划。本文以源码为准绳，逐行还原分块器的真实逻辑，撤回系列早期版本中"四种分块策略、并行处理、增量检查"等误传，并厘清"未接线原型"与"已接线连续性防线"两套体系的真实边界——以及想把分块器接入生产前，必须先补上的设计缺口。

相关链接：GitHub | 官网 | 文档 （架构设计 · 召回策略 · MCP Server · 一致性策略 · RAG 增强）

一、概述：分块在 PenShot 中的真实位置

1. 版本与路线图：两个反证

系列早期文章曾把"超长剧本处理"描述为 PenShot v0.7 的能力阶段。核对源码会发现两个反证：

  • pyproject.toml 中项目版本号是 0.3.8，全仓库不存在 v0.7 这一版本标识；

  • README.md 的"开发路线图 → 中期规划"一节里，至今仍写着"超长剧本分块处理 + 向量数据库上下文记忆"——在项目自己的官方口径里，分块处理仍属于规划中能力。

源码里的 LongScriptChunker 从哪来？git log 显示它出自提交 6494cd1（2026-04-28），提交说明为"新增 剧本分块处理和检查，提示词风格守护"——恰好是本文原版的创建日期。这是一次"先行写出原型"的提交：分块器、跨块验证器、提示词风格守卫三个组件同日落库，但此后再未接入工作流，至今全仓库零调用方。

2. README 里更诚实的表述

README"系统说明与注意事项"表格中还有一句直白的说明：

长文本处理 | 超长剧本建议分段输入，系统已内置上下文记忆与 RAG 机制

注意措辞——建议分段输入：当前产品形态是让用户手动切分超长剧本，系统为每个输入片段提供记忆与检索支持；自动分块属于尚未兑现的路线图承诺。这也解释了为什么分块器原型存在却不接线：它是一次对"中期规划"的提前探索，只是还没到收口的阶段。

3. 分块要解决的三个核心矛盾

把视野拉回工程本身。无论哪个系统处理超长剧本，分块都要回答三个问题：

  • 上下文窗口限制：LLM 输入长度有限，超长剧本无法一次性解析，必然要拆。

  • Token 峰值控制：整本送入会造成极高的单次 Token 峰值与成本，拆小后单次请求的规模更可控。

  • 语义与连续性：分块不能把叙事切碎——若在关键语义节点处硬切，角色状态、场景连续、动作递进都会被破坏，因此理想的分块应当是语义感知的。当然，"理想"与"已实现"之间的距离，正是本文后文要逐段丈量的对象。

补充原理：分块的本质是在"块内语义自洽"与"块间可衔接"之间找平衡。块太小会频繁要求 LLM 重新理解上下文（产生补全描述成本），块太大又逼近甚至超出窗口限制。引入重叠（overlap）正是为了在块边界附近保留上下文冗余，确保前后块的连续信息不断裂——这一点在 PenShot 的真实实现里同样成立，只是参数与宣传不同（见第二章）。

4. 本文的考证口径

延续本系列的"三口径"方法，全文对每个组件都会标注它的真实状态：

口径 含义 本文涉及
已接线 被生产代码真实调用 连续性检查器、修复生成器、重试机制
已实现未接线 代码完整但全仓库无调用方 分块器、跨块验证器、提示词风格守卫
规划中 仅存在于路线图或设计文档 自动分块处理、向量数据库跨块上下文记忆

二、LongScriptChunker 源码解构：30 场景、180 秒与 3 场景重叠

1. 组件全貌：110 行的真实代码

分块器的全部实现集中在 continuity_guardian/long_script_chunker.py 一个文件里，共 110 行，只有两个构件：ScriptChunk 数据类与 LongScriptChunker 分块器本体。

先记住三个真实参数：每块上限 30 个场景、预估时长上限 180 秒、块间重叠 3 个场景。其中"重叠 3 个"与系列早期文章宣传的"重叠 5 个"不一致，后文用同一套代码逐一核对。分块主流程如下：

2. 双阈值切分：场景数与时长的或逻辑

chunk_script 是分块器唯一的主方法，核心是一个"或"条件：

机制拆解：

  1. 两个独立触发条件：当前块场景数达到 30，或者"再放入一个新场景后预估总时长会超过 180 秒"，任一满足即封块；

  2. 封块先于入块：判断发生在 chunk_scenes.append(scene) 之前——触发时先结算旧块，再把当前场景放入新块。因此场景永远不会被切开，这正是方法注释中"保持场景边界（不断开场景内部）"的落地方式。它也意味着单个超长场景会成为新块的起点，即便其预估时长超过 180 秒；

  3. 新块从重叠场景起跑：封块后执行 chunk_scenes = overlap（上一块末尾 3 个场景），并重算 current_duration。

为什么是双阈值？ 两个参数各自对应一类约束：

  • 场景数（30）是复杂度约束：块内场景越多，需要维护与校验的角色/场景/道具状态越多，下游检查的开销随块内元素规模上升；

  • 时长（180 秒）是成本约束：源码注释写明 180.0 秒即"3分钟"——这是对 AI 视频生成环节的考量，单块对应成片越短，生成失败后重做的代价越小。

只保留单一阈值都不可靠：只看场景数，30 个对白密集的场景预估时长可能突破 600 秒；只看时长，一个不足 10 秒却包含几十个微动作的块同样难处理。双阈值"先到先封"是两条线同时设限的保守选择。

3. 时长估算：max(10.0, 元素数 × 4.0) 的近似

_estimate_scene_duration 是分块器里唯一的"业务算法"：

对每个场景取"元素个数 × 4 秒"，并设 10 秒下限。这是一个粗粒度估算，精度有限，但设计意图清晰：

  • 不依赖模型调用：若为了算准时长而调 LLM 逐场景预估，分块本身就成了新的成本大头——分块只是前置工程，不该引入昂贵的附加调用；

  • 下限保护：空白或极简场景至少按 10 秒计，避免 0 秒场景让块无限膨胀；

  • 已知失真点：4 秒/元素的系数不区分元素类型——一句动作描述与一段 5 轮对白的镜头在这里等价。这是原型阶段的合理妥协；如果接入生产，最直接的改进是按元素类型（对白/动作/场景描述）分档加权重。

所有块的唯一构造入口是 _create_chunk：

注意：entry_character_states、exit_character_states、continuity_anchors 三个字段只在数据类里声明了默认空字典，构建块时从未被赋值。也就是说，"块间状态传递"目前只是一组占位字段——分块器切出了块，但没有填充任何块的入口/出口角色状态，也没有连续性锚点。

它说明"跨块状态传递"在分块层尚未实现，而不是像早期文章示例那样"块1结束状态自动变成块2开始状态"。该能力若要落地，最自然的接入点正是这三个字段（第四章再展开接线缺口）。

5. 重叠真相：3 个场景，不是 5 个

早期文章演示过"100 场景剧本、每 30 场景一块、重叠 5 个场景"。用真实源码重算同一剧本，重叠参数应为 overlap_scenes=3：

上例按"场景数阈值先触发"推演。真实轮次中两种阈值哪个先到哪个封块，块边界可能比纯计数更碎一些。

为什么重叠 3 个？ 从代码看，重叠的作用是让新块的起点带上上一块的"尾部状态"，用 3 个场景做状态过渡：

  • 重叠过少（如 1 个）：新块只能看到上一块的最后一个场景，角色在更早场景里的服装、道具状态无从继承；

  • 重叠过多（如 10 个）：Token 浪费明显，且重叠场景可能在下游产出中重复生成；

  • 3 个场景大致覆盖"过渡-变化-稳定"的最小叙事单元，是原型阶段的经验值，不是经过评测调优的结论参数。

还有一个容易忽略的细节：封块那一轮 current_duration 会按重叠场景重算，即重叠场景的预估时长会占用新块的时长预算。这是正确的会计处理——新块确实要重新处理这 3 个场景，预算不能白送。

三、被撤回的宣传：四种策略、并行处理与增量检查

1. 四种分块策略：源码里只有一种

早期文章列出过四种分块策略——按场景、按角色弧、按情绪波、平衡分块。对照 110 行源码就会发现，实际实现的只有一种：按场景数分块（外加时长阈值兜底）。“角色弧”“情绪波”"平衡分块"三种说法在全仓库没有任何对应实现——没有弧线检测、没有情绪曲线分析、也没有多维度混合评分。

宣传的策略 源码对应 真实状态
按场景分块 LongScriptChunker.chunk_script（场景数 + 时长双阈值） 已实现，未接线
按角色弧分块 无 不存在，无对应代码
按情绪波分块 无 不存在，无对应代码
平衡分块 无 不存在，无对应代码

为什么只实现"按场景"？这是工程上最保守的选择，而不是偷懒：场景是剧本里唯一自带结构化边界的单元。LongScriptChunker 的入参是上游剧本解析阶段产出的 parsed_script，其 scenes 列表编号连续、边界明确，按场景切分天然满足"不断开场景内部"的硬约束。而"角色弧""情绪波"要求先对全剧本做叙事结构分析（谁在哪个区间成长、情绪曲线如何起伏），这类分析本身就要把完整剧本送进 LLM——为了分块而先做一次全量理解，在成本上与"不分块"的初衷相矛盾。先切后验、把语义一致性问题交给下游检查兜底，是多数长文本系统更现实的路径。

2. 并行处理：并不存在

早期文章的"并行处理"流程图描述过多 Worker 架构：块1-块4 分别交给 Worker 1-4 并发处理，再做状态传递与结果融合。这个架构在源码中不存在：

  • LongScriptChunker 只做切分，输出 List[ScriptChunk]，没有任何并发调度代码；

  • 全仓库的 ThreadPoolExecutor 只出现在 llama_index_router.py 的 KnowledgeRouter 里，且 KnowledgeRouter 本身也是未接线组件；

  • 工作流本体基于 LangGraph 节点串行推进（workflow_nodes.py），不存在"分块后并发处理再合并"的模块。

需要区分的是：并行是"分块后的自然诉求"，不是"已实现的机制"。一旦分块器接线，如何处理各块确实要面对这个选择——串行逐块处理实现最简单且天然保持顺序；并行处理省时，但引入状态融合与顺序保证的复杂度。当前代码还处在"连串行路径都没有"的阶段，谈并行属于超前。

3. 增量检查：不存在

早期文章还描述过"增量一致性检查"的四项优化：只检查变化部分、受影响场景扩散、增量修复建议、检查缓存。这些同样没有实现——全仓库检索不到任何增量检查、影响范围计算或检查缓存的代码。已接线的 ContinuityGuardianChecker 每次检查都是全量的：check_all_continuity 收到剧本、镜头序列、片段序列等完整上下文，六类检查逐项跑满。

把三组"撤回"放在一起，规律很清楚：越靠近分块器周边的能力，越容易被想象出来——因为它们在逻辑上"应该有"。源码考证的价值恰恰是把"逻辑上应该有"和"代码里真的有"分开：分块器本体的双阈值与重叠是真的；围绕它的策略体系、并行架构、增量优化则没有对应实现。

四、跨块一致性校验：未接线原型与已接线防线

分块器不接线，是否意味着 PenShot 完全没有连续性保障？并非如此。源码里存在两套与"连续性"相关的体系，命运截然不同：一套是围绕跨块检查设计的原型组件（未接线），另一套是真正在生产链路里运行的检查-修复闭环（已接线）。本章逐一对照。

1. CrossChunkValidator：未接线的跨块检查原型

与分块器同批落库的 cross_chunk_validator.py（102 行）定义了 CrossChunkValidator，负责"跨块过渡检查"。它的核心方法 validate_chunk_transition(prev_result, curr_result) 只做两件事：

对照早期文章宣传的"四维校验"（角色/场景/道具/风格），真实实现只有两维：

宣传的校验项 真实实现 说明
角色跨块一致 有 角色消失（high）+ 主角突现（medium）
场景跨块一致 有 场景切换跟随检查（low）
道具跨块一致 无 无对应检查代码
风格跨块一致 无 无对应检查代码

另外两个细节值得注意：

  • 输入契约没有生产者：validate_chunk_transition 期望的 prev_result / curr_result 字典需要携带 characters_in_chunk、main_characters、last_location、first_location 等字段。这类字典没有任何生产代码构造——既没有调用方，也没有将 ScriptChunk 转成该字典的转换函数。整个方法像是一份"接口草稿"；

  • merge_chunk_contracts 有一个隐蔽的副作用：它取 merged = chunks_contracts[0] 后直接原地修改（merged.characters[name] = char、appearance_scenes.extend(...)），属于对调用方传入对象的就地变更而非拷贝合并。如果接入生产并多次调用（例如重试场景），第一个契约对象的 appearance_scenes 会被重复追加。这类缺陷在原型阶段无伤大雅，接线时却必须处理——也侧面印证了"未经过生产调用"的事实。

2. "跨块状态传递"示例的真相

早期文章里有一段"块1结束状态（张三在医院，穿病号服）→ 块2开始状态（继承医院，切到病房）"的示例。回到第二章已考证的事实：ScriptChunk.entry_character_states / exit_character_states / continuity_anchors 三个字段从未被填充，校验器也没有消费它们的代码。所以这段演示描述的是设计意图，不是系统行为——在当前代码里，“块1的结束态"不会自动变成"块2的起始态”，这个继承链条整条都缺失。

它对应的正是接线分块器时最关键的待补工作：谁来填充每个块的入口/出口角色状态（服装、位置、情绪）？以什么粒度（角色全集还是主要角色）？填充数据从哪来（分块器自己解析场景，还是复用剧本解析阶段已产出的角色信息）？这些问题在现有原型里都没有答案。

3. 已接线的防线：六类检查 + 修复重试闭环

与未接线的跨块原型相对，真正在生产链路里运行的是另一套组件——ContinuityGuardianChecker（557 行）与 ContinuityRepairGenerator。它们不做"跨块"检查，而是做**跨阶段（段落/镜头/片段级）**检查，接线点在工作流的连续性守护节点：

check_all_continuity 依次执行六类检查：

检查发现问题后的处理链路（continuity_check_node，workflow_nodes.py）：

flowchart TB
    A["continuity_check_node<br/>构建 continuity_context"] --> B["_check_continuity<br/>checker.check_all_continuity（六类检查）"]
    B --> C{"有连续性问题？"}
    C -->|无问题| D["continuity_passed = True<br/>进入下一阶段"]
    C -->|有问题| E["知识库检索历史解决方案<br/>search_similar_scene（top_k=2）"]
    E --> F["_analyze_continuity_issues<br/>定位问题来源阶段"]
    F --> G{"重试次数 < 3？"}
    G -->|是| H["生成修复参数<br/>_route_to_fix_stage 回退源头阶段重试"]
    G -->|否| I["needs_human_review = True<br/>转人工审核"]

这条链路的关键设计点：

  1. 问题溯源到阶段：_analyze_continuity_issues 不是笼统报错，而是把每个问题归因到产出它的工作流阶段，_route_to_fix_stage 直接把流程回退到对应源头重试——修复发生在问题产生的地方，而不是在检查节点打补丁；

  2. 历史方案注入：检索历史相似问题的修复方案（search_similar_scene，top_k=2）挂到问题上供修复参考——这就是《召回评测》一文中考证过的"连续性检查的历史方案检索"接线点；

  3. 重试有硬上限：max_continuity_retries=3（state.domain 上的默认值），超限不再自动修复而是 needs_human_review=True 转人工——避免无限重试烧 Token，也把"自动修复不了"的场景显式暴露给人；

  4. 去重缓存：checker 内部维护 _seen_issues / _processed_shots / _processed_fragments 三个集合，每次 check_all_continuity 开始先清空——同一批输出里重复的问题不会反复上报。

修复参数的生成本身也是一层转发：continuity_check_node 调用 _create_continuity_repair_params（L1617），后者再委托 self.generator.generate_repair_params（L1629）——ContinuityRepairGenerator 才是实际的修复参数生成器。

所以，PenShot 的连续性保障现状可以概括为：块级（跨块）防线是未接线原型，阶段级（跨段落/镜头/片段）防线是已接线的生产机制。早期文章把两者混为一谈，用后者的存在感给前者的"完备性"背书，这是需要纠正的叙述。本章涉及的连续性组件接线状态汇总如下：

组件 文件 状态
LongScriptChunker long_script_chunker.py（110 行） 已实现未接线
CrossChunkValidator cross_chunk_validator.py（102 行） 已实现未接线
PromptStyleGuardian prompt_style_guardian.py 已实现未接线
ContinuityGuardianChecker continuity_guardian_checker.py（557 行） 已接线（六类检查）
ContinuityRepairGenerator continuity_repair_generator.py 已接线（修复参数生成）

五、向量上下文记忆的真实映射

早期文章宣称向量上下文记忆提供四类能力：跨块状态传递、语义记忆检索、上下文压缩、记忆衰减。把这张表放到真实源码里逐项映射，结论是"两个不存在、两个换了形态"：

宣称的能力 系统里的真实形态 对分块场景的可用性
跨块状态传递 ScriptChunk 入口/出口状态字段占位，无实现 不可用
语义记忆检索 长期记忆（Chroma 成功案例库）+ 连续性修复的历史方案检索（search_similar_scene） 目标不同，需改造
上下文压缩 中期记忆摘要链（LangChain 摘要），已接线 机制类似，可借鉴
记忆衰减 无任何实现 不存在

三处关键落差值得说清楚：

  1. 三层记忆服务的是"跨任务经验复用"，不是"块间状态传递"。短期、中期、长期记忆（详见《召回评测》一文）都以会话/剧本为粒度：短期记忆的键是 penshot:memory:{session_id}，长期记忆按 script_id 过滤相似成功案例。而跨块状态传递要求的是"块 A 的出口状态原样注入块 B 的入口"——这是一条确定性的数据流，不是相似性检索能替代的；

  2. 语义记忆检索对分块的价值有限：长期记忆入库门槛是 completeness >= 0.8 的成功案例，当前真机三剧本实为 0 文档；历史方案检索（top_k=2）只服务连续性修复场景。两者都不是"按块召回远端上下文"的通道；

  3. 记忆衰减没有实现，也不建议照搬："远距离记忆权重自动衰减"在分块场景里甚至是危险设计——块间状态传递要求确定性继承（服装、道具必须以字面值传递），任何"权重衰减"都会引入状态漂移。

README 路线图里"超长剧本分块处理 + 向量数据库上下文记忆"的表述，指向的正是这个缺口：用向量库做跨块上下文记忆是规划中的方向，而不是已交付的能力。若要落地，现有长期记忆（Chroma + script_id 过滤）是最接近的基座，但它的入库门槛与查询语义都要重新设计——这也是"接线分块器"课题的一部分。

总结与建议

按"三口径"盘点分块相关的全部能力：

口径 能力 说明
已接线 六类连续性检查 + 修复重试闭环 continuity_check_node 内运行，重试上限 3 次后转人工
已接线 历史方案检索 search_similar_scene（top_k=2）为修复注入历史经验
已实现未接线 双阈值分块 + 3 场景重叠 LongScriptChunker（110 行）完整实现，零调用方
已实现未接线 跨块过渡检查 CrossChunkValidator 角色/场景两维检查，输入契约无生产者
已实现未接线 提示词风格守护 PromptStyleGuardian，零调用方
规划中 自动分块处理 + 向量数据库跨块上下文记忆 README 开发路线图·中期规划

想接线分块器的话，按什么顺序做什么：

  1. 先补状态字段：让 _create_chunk 真正填充 entry_character_states / exit_character_states——这是跨块一致性的数据前提，没有它，校验器再完备也无米下锅；

  2. 再设计块级执行的串行路径：分块→逐块处理→合并，先把串行走通，再评估并行是否值得（并行会引入顺序保证与状态融合成本）；

  3. 最后才谈策略升级：在双阈值+重叠的机械切分上线验证之前，"角色弧/情绪波分块"没有落地必要——它们解决的是"边界更优美"的问题，而当前系统连边界处的状态传递都没打通；

  4. 保留人工兜底：连续性修复重试 3 次即转人工的设计已被生产验证——分块接入后，"块级问题无法自动修复"的场景同样应转人工而不是无限重试。

实践建议：对正在使用 PenShot 的用户，超长剧本当前的正解仍是 README 给出的方案——分段输入。把剧本按叙事段落手动切分，逐段调用工作流，利用系统已接线的记忆与连续性机制保证段内质量；自动分块是路线图上的事情，不是今天的按钮。对二次开发者，LongScriptChunker 的 110 行代码是一份清晰的接线起点：数据结构已备好、参数有据可依、缺口被本文逐一定位——差的只是把它接进工作流的那几根线。

收个尾：本文从"分块能力在 PenShot 里上线了没有"这个朴素问题出发，逐行读了 110 行的分块器、102 行的跨块验证器，又对照了真正在生产里运行、557 行的连续性检查器。结论并不复杂：真实的代码比宣传的小，但也比宣传的更诚实——双阈值、重叠 3 场景、10 秒下限这些不起眼的常数背后，是"先切后验、状态优先"的工程判断。把这些常数的来龙去脉讲清楚，比罗列四种不存在的分块策略更有价值。
