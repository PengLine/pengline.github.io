NeoTask API 参考：公开方法签名总表 + TaskScheduler 委托链与周期分支

📚 返回首页 | 📖 快速上手 | 📘 API 参考 | ⚙️ 配置说明 | 🐙 GitHub | 🐱 NeoTask 官网

版本基线：本文对照 NeoTask v1.0.2（PyPI 发布版），全部方法签名与行为出自 neotask/api/task_pool.py（839 行）、neotask/api/task_scheduler.py（923 行）逐行核实。
代码标注约定：🔧 表示真实源码（仓库原样摘录，附文件路径，可自行对照）；📝 表示示例代码（用法演示、改进建议或教学代码，不代表仓库实现）。

概述：三个必须先知道的要点

  1. API 门面只有两个类：TaskPool（即时任务）与 TaskScheduler（定时任务），另有一个未导出的异步门面 TaskEngine（见第八节）。工作流编排 API 不存在——没有 WorkflowEngine / WorkflowDefinition / TaskNode / WorkflowConfig。

  2. 同步方法 ≠ 同步实现：所有"同步版"方法都通过 asyncio.run_coroutine_threadsafe 把协程投递到后台事件循环线程执行并阻塞等待结果（🔧 task_pool.py:300 _run_coroutine）。因此绝大多数公开方法内部先调用 _ensure_running()——不先 start() 直接调 submit() 也会自动启动；但 wait_for_result 等不触发自动启动，需保证池已运行。

  3. TaskScheduler 是一个"组装器 + 委托器"：它内部持有一个 TaskPool，39 个公开方法中 24 个是原样委托（🔧 task_scheduler.py:699 起"委托给 TaskPool 的方法"注释段），真正自研的只有：延时/定点提交（委托时附加 delay）、周期任务管理族、get_stats 附加段、cancel 双查逻辑。

下面按九组逐一给出签名（其中锁管理、节点与事件、on_progress / on_reclaimed 常被遗漏）。

1.1 生命周期：start 一次，自动启动的池

🔧 task_pool.py:310。start() 会创建一个 daemon 线程，在该线程内 new_event_loop 并依次启动：事件总线 → 队列调度器 → Worker 池 → 监督器，然后按存储类型附加节点管理/心跳/回收器/上报器等分布式组件（详见《节点监控》），最后 loop.run_forever()。

shutdown()（🔧 369）的关闭顺序与启动相反：停收新任务 →（graceful 时）等队列清空 → 停分布式组件 → 停核心组件 → 关存储连接。两个细节值得注意：

  • graceful 语义是"等队列清空"，不是等 Worker 优雅退出后再停——随后 worker_pool.stop(graceful, timeout) 才处理执行中任务，两段分别受 timeout 约束。

  • 关闭仓库时捕获 "different loop" 异常并忽略（🔧 411-414）：SQLite/Redis 连接若在别的线程创建，跨循环关闭会炸，源码选择吞掉。

为什么这么设计：把整个 async 世界隔离在一个专属后台线程里，业务线程就能以"同步 API 调协程"的方式使用——代价是 _run_coroutine 是阻塞桥，在事件循环线程内调用任意同步方法会死锁（这是常见事故，见第十节故障 1）。异步版本 API（submit_async 等）就是为此提供的逃生门。

📝 生命周期标准姿势：

1.2 任务提交：submit 的 delay 就是"延时任务"

🔧 task_pool.py:473。submit 把任务交给 TaskDispatcher.dispatch（入队 + 持久化 + 发 task.created 事件），返回任务 ID。参数语义：

参数 默认 说明
data 必填 任意可 JSON 序列化对象，原样传给执行函数
task_id None 自定义 ID；重复提交统一抛 TaskAlreadyExistsError——入队前 create_task 先做存在性检查（🔧 lifecycle.py:64-66），与存储后端无关
priority NORMAL(2) 接受 TaskPriority 枚举或整数，0=CRITICAL 1=HIGH 2=NORMAL 3=LOW，小者先出队
delay 0 延迟秒数，>0 时进延时队列（ZSET 方案见《延时任务》），这不是 TaskScheduler 的专利
ttl 3600 任务生命周期秒数，写入 Task.ttl；目前仅作元数据，没有内置 reaper 依据它删除任务

submit_batch 不是批量原语：源码是 for 循环逐个调 submit（🔧 501-512），无事务、无原子性，中途失败前面已提交的任务不回滚。

📝 四种提交形态等价关系：scheduler.submit_delayed(d, s) ≈ pool.submit(d, delay=s)；scheduler.submit_at(d, t) ≈ pool.submit(d, delay=max(0, (t - now).total_seconds()))——TaskScheduler 的实现正是这样逐字委托（见第二节）。

1.3 任务等待：最容易被低估语义的一组

🔧 task_pool.py:529。底层是 TaskLifecycleManager.wait_for_task（🔧 core/lifecycle.py:265），完整语义链：

  1. 任务不存在 → 抛 TaskNotFoundError(task_id)；

  2. 已终态：SUCCESS → 直接返回 task.result；FAILED → raise Exception(task.error)；CANCELLED → raise Exception("Task was cancelled")（注意都是裸 Exception，不是 TaskError）；

  3. 未终态：取 Future 等待，future.wait(timeout) 超时抛 neotask.common.exceptions.TimeoutError（自定义类，见第七节）；等待异常后再查一次任务状态兜底（🔧 lifecycle.py:291-306 的防漏通知逻辑）。

为什么这么设计：失败/取消的任务以"抛异常"而非"返回错误字典"呈现，是为了让调用方无法忽略失败——代价是与 wait_all 的行为不对称（见下）。

wait_all（🔧 537）是串行循环：逐个 wait_for_result(task_id, timeout)，任何异常（含超时）都被捕获并塞成 {"task_id": {"error": "..."}} 返回，永不向上抛。两个推论：

  • 总耗时最坏 = N × timeout（不是共享一个超时预算）；

  • 单任务失败被静默吞进结果字典，{"error": ...} 与正常任务返回的真字典混在一起难以区分。

📝 严谨的等待姿势（区分三类失败）：

1.4 任务查询：get_task 与 get_result 的序列化差异

🔧 task_pool.py:569-623。三个方法都调 lifecycle.get_task，差异在返回形态：

  • get_task → Task.to_dict()（🔧 models/task.py:64）：14 个字段，但 data 与 result 是 JSON 字符串（存储格式），时间字段是 ISO 字符串，空值被归一化为 ""；

  • get_result → 手工拆包的小字典：result 字段已被 json.loads 还原为对象（来自 from_dict），并附 status/error/created_at/completed_at；

  • get_status → 只取 task.status.value。

最容易踩的坑：pool.get_task(id)["result"] 与 pool.get_result(id)["result"] 类型不同（前者字符串、后者对象），下游代码混用会拿到 '{"data": 1}' 而不是 {"data": 1}。Task.to_dict 的序列化行为在 Memory/SQLite/Redis 三存储间是同一个函数，无后端差异。

1.5 任务管理：cancel 只管状态机，retry 走重派发

🔧 task_pool.py:627-653。cancel 先 queue_scheduler.remove(task_id) 尝试从队列移除，再调 TaskLifecycleManager.cancel_task（🔧 core/lifecycle.py:227）：

  • 任务不存在或状态不在 PENDING/RUNNING → 返回 False；

  • 成功 → 状态置 CANCELLED、存库、通知 Future（等待方会收到裸 Exception("Task was cancelled")）、发 task.cancelled 事件。

一个真实的语义盲区：Worker 执行前校验任务必须是 PENDING（🔧 worker/pool.py:255），但执行成功后无二次状态检查就直接 complete_task 落库。因此对 RUNNING 任务 cancel：只把状态标记成 CANCELLED，不中断执行中的函数；函数若随后正常返回，状态会被覆写回 SUCCESS 并照常发 task.completed。生产上把 cancel 当作"只对排队中（PENDING）任务可靠"更稳妥。

retry = TaskDispatcher.redispatch(task_id, delay)（🔧 dispatcher.py:99）：只做存在性检查（查无此任务返回 False），然后按任务原优先级重新入队——不校验状态是否 FAILED、不递增 retry_count、不发事件。所以它是"把任意任务硬塞回队列"的手动重试；retry_count < 3 的阈值只在 Worker 自动失败链路里生效（模型侧 is_retriable()，🔧 models/task.py:151），手动 retry 不受次数约束。

delete 直接走 lifecycle.delete_task（🔧 core/lifecycle.py:251）：存储删除 + 清缓存 + 移除 Future + 发 task.deleted，不区分状态，且恒返回 True（存储层删除失败的返回值被忽略）。运行中的任务被删后，Worker 完成时 complete_task 会再次 repo.save——三后端 save 均为覆盖/upsert 写（SQLite INSERT OR REPLACE），记录会以执行前的旧快照重建，等于"删了还会回来"。

1.6 队列控制：pause 的是"调度器取任务"这个动作

🔧 task_pool.py:736-766。四者全部委托给 QueueScheduler：pause 停的是调度器从队列取任务交给 Worker 的循环，已入队任务保留、执行中任务不打断；clear_queue 清空的是待处理队列（各后端实现不同，Redis 是删除 ZSET 键）。pause 期间 submit 仍可入队，队列长度会涨。

1.7 统计监控：get_stats 真实结构

🔧 task_pool.py:736-800。get_stats() 的返回结构：

success_rate 初始为 1.0 而非 0.0（stats.total > 0 else 1.0，🔧 670）——新池"零失败率"，语义是"没有失败过"而非"全成功"。

get_health_status()（🔧 800）返回 {"status", "node_id", "last_check", "checks", ...}。启用 enable_health_check（默认 True）时，同步/异步版本都会先经 _refresh_health_if_stale() 惰性执行检查：仅当上次结果超过 HEALTH_CHECK_TTL = 5.0 秒才重新探测，否则复用缓存。检查项为 storage / queue / system，逐项串行执行，单项超时 DEFAULT_CHECK_TIMEOUT = 5.0 秒并记为 UNHEALTHY（message 为 timed out after Xs）；未安装 psutil 时 system 项记 healthy 且 details = {"available": False}（psutil 属可选 [monitor] extra）。enable_health_check=False 时不带 checks 键，只返回 {status, node_id} 与分布式字段。get_worker_stats() 直通 WorkerPool 的统计（每 Worker 一个条目）。

1.8 锁管理

🔧 task_pool.py:770-788。锁键固定为 task:{task_id}，走 _lock_manager（memory 模式是进程内锁，redis 模式是带看门狗的 Redis 锁，机制见《分布式锁》）。为什么这么设计：把"任务级互斥"做成池的固有能力，让同一任务在多个节点/多次执行间互斥；但它与任务生命周期无耦合——忘记 release_lock 的锁只能等 ttl 过期（或依赖 Redis 锁的看门狗续期配置）。

1.9 节点与事件回调

🔧 task_pool.py:792-839。get_active_nodes 只在 redis 模式有数据（节点注册表，机制见《节点监控》）；is_leader 的实现就是 return False，源码注释写着"去中心化架构中始终返回 False"（🔧 806）——它不是占位符，是设计声明：NeoTask 无主节点，任何"我是不是 Leader"的判断都该写死否。

回调注册走事件总线订阅（event_bus.subscribe("task.xxx", handler)），handler 收到的是 TaskEvent 对象（event_type/task_id/data）。v1.0.2 中池内建的事件订阅见第六节事件表；on_* 只是把总线订阅封装成命名方法。

注意 on_progress：它订阅 task.progress 事件，但该事件的发布函数 _update_task_progress（🔧 worker/pool.py:348）全库无任何调用方——进度事件不会触发，注册了 on_progress 也收不到回调。

二、TaskScheduler：四族 39 个公开方法

🔧 api/task_scheduler.py。构造函数只收两个参数：executor（可选，传给内部 TaskPool）与 config（SchedulerConfig，默认 SchedulerConfig()）。初始化时把 config 的 6 个字段翻译成 TaskPoolConfig 并创建内部 TaskPool（🔧 68-77，翻译规则见《配置说明》第五节）。

2.1 族一：生命周期（4 个）

🔧 task_scheduler.py:92。start() 顺序：① 先启动内部 TaskPool（独立线程事件循环）；② 等其 _loop 就绪（轮询 5s，超时抛 RuntimeError）；③ enable_periodic_manager=True 时创建 PeriodicTaskManager(pool, storage=None) 并在池的事件循环里 start()；④ enable_time_wheel=True 时创建 TimeWheel 并 start(callback)；⑤ 启动调度线程跑 _scheduler_loop（🔧 225）：每 scan_interval（SchedulerConfig 默认 1.0 秒）扫描一次到期任务——启用 PeriodicTaskManager 时扫管理器任务列表，否则扫内存周期任务表，到点以 EXEC_ 前缀 ID 提交执行。

submit_interval / submit_cron 有两条实现路（🔧 479-614）——

  • enable_periodic_manager=True（SchedulerConfig 默认）：委托给 PeriodicTaskManager.create_interval/create_cron（该管理器的持久化族仍是 TODO，见《配置说明》）；

  • enable_periodic_manager=False 时：走调度器自己的内存字典 _periodic_tasks（PeriodicTask 对象），由后台调度线程按 scan_interval 驱动。

两条路的返回 ID、get_periodic_tasks() 输出一致，但周期定义都只活在内存：内存路重启即失，PeriodicTaskManager 路的持久化仍是 TODO（🔧 scheduler/periodic.py），同样不落盘。

2.2 族二：延时 / 定点提交（4 个）

🔧 task_scheduler.py:331-424。submit_delayed 有两条路径，由 SchedulerConfig.enable_time_wheel 决定：

  • enable_time_wheel=False（默认）：原样调 pool.submit(data, task_id, priority, delay_seconds, ttl)（🔧 358），走 TaskPool 的延时队列（ZSET）；

  • enable_time_wheel=True：走 _submit_delayed_via_time_wheel——先用 create_pending_task_async 把任务以 PENDING 落库（不入队），再 TimeWheel.add_task；若延迟超出量程（add_task 返回 -1），自动 retry_async 退回延时队列。到期由 _on_delayed_task_ready → enqueue_task_async 入队，且仅当任务仍为 PENDING 才入队，等待期间取消是安全的；shutdown() 会 TimeWheel.drain() 并把剩余任务按重算延迟重新入队。

submit_at 先把 execute_at 换算成 max(0, (execute_at - now).total_seconds()) 再走 submit_delayed（Adapter 模式，🔧 409-412）。两者签名都带 ttl: int = 3600。

2.3 族三：周期任务管理（7 个）

🔧 task_scheduler.py:479-614。要点：

  • run_immediately=True（默认）决定第一次执行的时机：内存路把 next_run 置为 now 并立刻以 EXEC_{task_id}_0_{uuid4hex4} 内部 ID 提交一次（🔧 528-544）；PeriodicTaskManager 路把该值转发给管理器控制首跑（next_run = now，start_at 在未来时以 start_at 为准）。后续每次到期触发用 EXEC_{task_id}_{run_count}_{uuid4hex4}（🔧 277，run_count 从 1 递增）——查询"某次执行"要用 EXEC_ ID，查"周期定义"用原 ID；

  • submit_cron 先 CronParser.is_valid 校验，非法表达式抛 ValueError（🔧 578）；cron 支持 5 段 分 时 日 月 周；

  • max_runs 限制总执行次数，name 仅作展示/标识（PeriodicTaskManager 路会用作任务 name）；missed_policy 覆盖 SchedulerConfig.default_missed_policy——skip 与 ignore 等价（丢弃错过的槽位、只推进 next_run），run_once 只补跑一次，catch_up 补跑且单轮上限 5 次；

  • get_periodic_tasks 返回的字典含 task_id/name/interval_seconds/cron_expr/priority/next_run/last_run/run_count/is_paused/max_runs/created_at（🔧 674-700）；

  • 两条实现路（PeriodicTaskManager vs 内存字典）的 cancel/pause/resume 都返回 bool；内存路 cancel_periodic 对不存在的 ID 返回 False。

2.4 族四：委托族（24 个）

🔧 task_scheduler.py:699-923，源码注释原话就是"委托给 TaskPool 的方法"。逐字委托：submit submit_async wait_for_result wait_for_result_async get_status get_status_async get_result get_result_async get_task task_exists cancel delete retry get_stats get_queue_size get_health_status pause resume clear_queue on_created on_started on_completed on_failed on_cancelled。

三个非纯委托的特例：

  1. cancel(task_id)（🔧 809）：先查"是不是周期任务"（PeriodicTaskManager 或内存表），是则走 cancel_periodic，否则才委托 pool.cancel——同一个方法名承担两层语义；

  2. get_stats()（🔧 853）：取 pool.get_stats() 后附加 periodic（管理器路）/ periodic_tasks_count（内存路）与 time_wheel（启用时）三段；

  3. submit 的 docstring 注明 Delegation，行为与 pool 完全相同。

委托矩阵（Scheduler 没有的方法）：submit_batch / submit_batch_async、wait_all / wait_all_async、get_task_async、task_exists_async、delete_async、retry_async、cancel_async、get_stats_async、get_queue_size_async、pause_async、resume_async、clear_queue_async、get_worker_stats、锁族 4 个、节点族 3 个、on_progress、on_reclaimed —— 共 25 个只在 TaskPool 上有。业务上想用批量等待或进度回调，请直接持有一个 TaskPool（或 scheduler._pool，但不建议）。

三、Task / TaskStatus / TaskPriority 类型

3.1 TaskStatus：六态，终态只有三个

🔧 models/task.py:15。枚举值全部是小写字符串：

枚举 value 说明
PENDING "pending" 已入队待执行
RUNNING "running" Worker 执行中
SUCCESS "success" 成功（终态）
FAILED "failed" 失败（终态）
CANCELLED "cancelled" 取消（终态）
SCHEDULED "scheduled" 枚举中存在；v1.0.2 队列流转主要在其余五态

TaskStatus.is_terminal()（🔧 24）只认 SUCCESS/FAILED/CANCELLED——状态机的"终态判定"统一走这一个方法（清理、统计、等待逻辑都依赖它）。Task.is_retriable() = FAILED 且 retry_count < 3（硬编码 3，不读任何配置）。

3.2 TaskPriority：四档整数，越小越先

🔧 models/task.py:29：CRITICAL=0、HIGH=1、NORMAL=2、LOW=3。提供 TaskPriority.from_value(int)（未知值回退 NORMAL）。API 参数标 Union[int, TaskPriority]，两态都收，入库统一转 int。

3.3 Task：14 字段实体

🔧 models/task.py:45。@dataclass 字段：

字段 默认 说明
task_id / data 必填 data 任意 JSON 对象
status PENDING 见 3.1
priority NORMAL 见 3.2
progress / progress_message 0.0 / "" 进度（0-1），update_progress() 会 clamp 到 [0,1]
node_id "" 执行节点，start() 时写入
retry_count / ttl 0 / 3600 重试计数 / 生命周期秒数
created_at / started_at / completed_at 时间戳 UTC
result / error None 执行结果 / 错误信息

状态迁移方法 start(node_id) / complete(result) / fail(error) / cancel() 都同时写时间戳。序列化契约（写进任何存储后端都走它）：to_dict() 把 data、result 压成 JSON 字符串、时间转 ISO、None 归一化空串；from_dict() 反向解析（🔧 64-122）。TaskStats（🔧 156）是统计容器，success_rate = completed / (completed + failed)。

四、事件对象与事件类型全集

发布点全部来自真实代码（下表按触发时机排序）：

event_type 发布位置 data 内容
task.created lifecycle 入队后 任务 to_dict()
task.status_changed update_status()（🔧 lifecycle.py:128） {"old_status", "new_status"}
task.started Worker 取到任务 {"node_id": ...}
task.completed 执行成功 result（直接是结果对象）
task.failed 执行失败 {"error": ...}
task.cancelled cancel_task()（🔧 lifecycle.py:247） 无（None）
task.deleted delete_task() 无
task.progress 发布函数 _update_task_progress（🔧 worker/pool.py:348） {"progress", "message", "timestamp"}（该函数无调用方，事件实际不会触发）
task.retry Worker 重试分支 {"retry_count": ...}
task.reclaimed 回收器（🔧 worker/reclaimer.py:348/378） 回收原因

为什么这么设计：事件总线（EventBus）是池内部组件间的"松耦合胶水"——Future 完成通知、指标记录、重试计数全部靠它，on_* 回调只是把总线订阅开放给用户。TaskPool 的指标订阅器 _setup_event_handlers（🔧 task_pool.py:271）全局订阅 created/started/completed/failed/cancelled/retry 六类事件：task.created 的 payload 是 Task.to_dict()、带 priority，task.retry 携带 retry_count。用户若自订 on_* 之外的裸事件名（如 task.status_changed、task.deleted）也能收到这些内部事件。

五、事件回调与内部订阅关系

注册 on_created 等回调只是向总线 subscribe，总线本身是异步队列 + 独立 worker 派发（🔧 event/bus.py）。源码把"指标记录"也实现为总线订阅（_setup_event_handlers，🔧 task_pool.py:271）：

  • 指标订阅（subscribe_global）覆盖 created/started/completed/failed/cancelled/retry 六类事件；

  • task.created 的 payload 是 Task.to_dict()、带 priority，因此 priority_counts 记录真实优先级分布；task.retry 带 retry_count，记入 total_retried。

对用户而言：事件回调是"尽力而为"的通知，不是任务结果的一致来源——结果一致性请用 wait_for_result / get_result，回调只适合日志、旁路统计等可丢场景。

六、异常体系：6 个类，其中一个名字有坑

🔧 common/exceptions.py（46 行全文），全部在 neotask/__init__.py 顶层导出：

异常 基类 构造参数 抛出场景
TaskSchedulerError Exception - 全局基类
TaskNotFoundError TaskSchedulerError task_id wait_for_task 等查无此任务
TaskError TaskSchedulerError task_id 通用任务错误
TaskAlreadyExistsError TaskSchedulerError task_id 重复任务 ID（存储层）
QueueFullError TaskSchedulerError queue_size 队列满
TimeoutError TaskSchedulerError task_id, timeout wait_for_task 超时

最大的坑在 TimeoutError：它继承 TaskSchedulerError，不是内置 TimeoutError。若你 from concurrent.futures import TimeoutError 或依赖 Python 内建的 asyncio.TimeoutError，except 永远接不住 NeoTask 的超时；反过来，顶层 from neotask import TimeoutError 会在模块作用域遮蔽内建名。判别式写法：except Exception as e: if isinstance(e, TaskSchedulerError) and type(e).__name__ == "TimeoutError"，或直接 from neotask.common.exceptions import TimeoutError as NeoTimeoutError。

另外注意 wait_for_result 对 FAILED/CANCELLED 抛的是裸 Exception（带 task.error 字符串），不是上述任何子类——catch 链里 except TaskNotFoundError 之后必须留一个兜底 except Exception，否则 asyncio/线程桥会把未捕获异常打进日志（见第十节故障 2）。

八、补充：core/engine.py 的 TaskEngine —— 第二条 API 面，但不可见

🔧 core/engine.py（380 行）定义了 EngineConfig（27 行）与 TaskEngine（55 行）——一个纯异步门面：configure()/initialize()/start()/stop()、submit(data, task_id=None, priority=5, delay=0, ttl=3600)、submit_batch/wait/wait_all/get_task/get_status/get_result/cancel/get_stats/pause/resume/is_running。

三个与主门面显著不同的点：

  1. 未导出：__init__.py 的 __all__ 没有它，neotask.core.engine 也不在文档目录内——from neotask import TaskEngine 直接 ImportError；

  2. priority 语义冲突：TaskEngine 的 submit 注释写着"优先级 1-10，数字越小优先级越高"，默认 5（🔧 engine.py:268）——与 Task/TaskPriority 模型（0-3 四档）不在同一坐标系，若混用会得到一堆"5 号优先级"任务在 0-3 队列里按 NORMAL 处理；

  3. 它内部同样组装 dispatcher/lifecycle/queue/worker/metrics（initialize() 里逐件拉起），与 TaskPool 是平行实现而非被 TaskPool 复用（TaskPool 未 import engine.py）。

结论：这是早期纯异步设计的遗留门面。写新代码请用顶层导出的 TaskPool/TaskScheduler；看到网上示例 from neotask.core.engine import TaskEngine 时要知道它是内部类，字段/行为不保证与公开门面一致。

九、为什么这么设计：门面与桥的取舍

  1. 同步门面 + 异步内核：任务调度器的用户大多是同步业务代码（Web 请求线程、脚本），强制 async 会劝退大部分使用者。NeoTask 选择"专属事件循环线程 + run_coroutine_threadsafe 阻塞桥"，让 pool.submit() 像普通库一样调用——代价是同步方法与事件循环线程有死锁红线（见故障 1），于是又补了全套 *_async 逃生门。

  2. _ensure_running() 隐式启动：submit 系列都带自动启动（🔧 295-298），wait/cancel 不带——设计意图是"提交是主路径，不能让用户忘了 start"，但副作用是"忘 start 直接 wait"会抛 RuntimeError("TaskPool not started. Call start() first.")。两者行为不对称是刻意的：等待一个没启动的池是程序错误，应尽快暴露。

  3. 委托而不是继承：TaskScheduler 组合 TaskPool 而非继承它，因此能对 cancel、get_stats 做差异化覆盖（周期任务优先），又不必背上锁/节点那组与定时调度无关的方法。代价就是上面那张"25 个方法不存在"的委托矩阵——查文档前先想清楚你手里的是哪个门面。

  4. 异常即状态：等待 API 用"抛异常"表达失败/取消（而不是返回 error 结构），保证 result = await wait() 成功路径拿到的必是可用结果。

十、故障场景实战

故障 1：在事件循环线程里调同步 API → 死锁

症状：自定义 executor 是异步函数，内部调用了 pool.wait_for_result(...) 或 pool.submit(...) 等同步方法，程序卡死无日志。

根因：executor 跑在池的专属事件循环线程里；同步方法走 _run_coroutine 向同一个循环投递协程并 future.result() 阻塞等待——循环正忙于执行你的 executor，永远没机会跑新投递的协程，经典"自己等自己"死锁（🔧 task_pool.py:300-306）。

修复：执行器内部一律用 await pool.submit_async(...) / await pool.wait_for_result_async(...)；拿不准时统一 *_async 族。

故障 2：except 接不住超时，异常被桥吞掉

症状：wait_for_result 超时后 try/except 没打印任何东西，进程却挂着卡死；或 except TimeoutError 从未命中。

根因：两层叠加——① 自定义 TimeoutError 遮蔽内建名（见第六节）；② _run_coroutine 对协程异常是 future.result() 直接上抛，若外层只 except (TaskNotFoundError, TimeoutError) 而任务实际 FAILED（裸 Exception），异常一路逃逸。

故障 3：wait_all 一批 50 个任务，偶发"整个调用耗时几分钟"

症状：单任务平均 1s，wait_all(ids, timeout=60) 本应 ~60s 封顶，实测偶发跑到几分钟。

根因：wait_all 是串行 for 循环，每个任务独立计时 60s（🔧 537-550）。若最后一个任务恰好失败且靠后，前面 49 个各等满 60s 累计 ≈ 50 × 60s。timeout 是"每任务"预算，不是整批预算。

故障 4：get_task 里"读不到结果"

症状：任务显示 success，但 pool.get_task(tid)["result"] 拿到的值 json.dumps 后是字符串、if not result 判断还经常误判。

根因：to_dict() 把 result 序列化成 JSON 字符串（🔧 models/task.py:79），空结果存成 ""；而 get_result(tid)["result"] 才是解析后的对象（None 保持 None）。两个 API 的 result 通道类型不同且"空"的表现不同（"" vs None）。

修复：读结果一律用 get_result()；确实要完整任务字典时，对 data/result 字段自行 json.loads 并兼容空串。
