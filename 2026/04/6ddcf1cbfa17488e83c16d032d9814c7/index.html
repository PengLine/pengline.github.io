PenShot 开发指南源码考证：双启动链、双层状态机与二次开发扩展点

相关链接：GitHub | 官网 | 文档 （架构设计 · 集成指南 · MCP Server · 一致性策略 · RAG 增强）

情景预览：本文给你什么

本文以源码考证的视角重写开发指南：从 main.py、http_server.py、rest_api.py 与 function_calls.py 出发，逐项核验安装、配置、启动与调用的真实行为，再对照 WorkflowOrchestrator、PromptManager 与 BaseAgent 给出二次开发的真实扩展点。全文按项目概览 → 系统架构 → 快速开始 → 五种集成方式 → 开发环境搭建 → 二次开发 → 性能优化 → 常见问题排查的顺序展开，并纠正三处流传较广的误读：任务终态是 success 而非 COMPLETED、任务队列默认在进程内而非 Redis、penshot.logger 并没有 set_level 函数。如果是初次接触，建议先通读项目概览与系统架构，再按快速开始实操。

一、项目概览

1.1 什么是 PenShot？

PenShot（Pen & Shot）是一个基于大语言模型的多智能体协作系统，专门用于将自然语言剧本自动转换为适合AI视频生成的提示词序列。它通过多个专业化智能体的协同工作，完成剧本解析、镜头分割、视频分割、提示词转换和质量审查等全流程任务。

1.2 核心能力

  • 剧本智能解析：支持自然语言剧本、标准格式剧本、AI分镜脚本、纯对话等多种输入格式

  • 智能镜头拆分：基于剧本语义自动生成镜头序列，保持道具和角色一致性

  • 长镜头智能分割：对超过时长阈值的镜头进行智能分割，确保视觉连贯性

  • 双语提示词生成：同时生成英文和原始语言的高质量提示词

  • 音频提示词生成：基于剧本内容生成配套的音频提示词（台词、环境音、旁白）

  • 质量审查：自动审查提示词质量，检测截断、道具不一致等问题

价值定位：面向短剧/短视频/AI 影视创作者与自动化流水线，解决从写完剧本到手工拆镜、再到逐段写提示词这一串高重复度劳动，让创作者把精力放在内容本身。

1.3 技术栈

组件 技术选型 用途
LLM OpenAI 兼容多厂商（openai / qwen / deepseek / ollama） 剧本解析、镜头分割、提示词转换
Embedding text-embedding-v4（模板默认，可换 3-small 等） 语义检索与 RAG 知识库
工作流框架 LangGraph ≥ 1.1.4 多智能体流程编排
API 框架 FastAPI + uvicorn RESTful 服务
协议支持 MCP / A2A 接入 IDE 与跨 Agent 协作
任务与状态 进程内队列 + SQLite 检查点（Redis 可选） 任务调度、断点续传与跨进程共享

说明：.env.example 模板默认使用 OpenAI gpt-4o 与 text-embedding-v4，注释明确系统支持 openai、qwen、deepseek、ollama 四类厂商；LLM__FALLBACK__* 备用段可在主模型不可用时自动回退（模板里是 deepseek-chat）。模型切换方式详见常见问题 Q4。

2.3 任务状态机：任务级生死线与阶段级进度

任务的生命周期由两层状态体系共同刻画：任务级 TaskStatus 管生死，共 8 个值；阶段级 TaskStage 管进度，共 24 个带权重的中文阶段。先看任务级状态机——任一环节失败都会落入 FAILED 终止，杜绝半成品被当作成功结果返回：

    FAILED --> [*]

常见误读：终态 COMPLETED 在这套代码里并不存在。你在 REST 注释与部分示例里看到的 completed 有两个完全不同的来源：一是 list_tasks 接口 status_filter 里的枚举值（源码瑕疵，传它永远筛不到任务，见 4.4）；二是阶段明细 progress_details 中单个阶段的完成标记（complete_stage 写入 status: "completed"）。判断任务成功一律认 TaskStatus.SUCCESS。

阶段语义：细粒度进度由 TaskStage 提供——从 init、parsing_start、parsing_script 一路到 continuity_complete、output_generating、complete，每个阶段带 code、中文名与权重（0-100，用于加权估算总进度）。/api/v1/status/{task_id} 返回的 current_stage、stage_name 与 stages_progress 就来自这套体系。

三、核心模块详解

3.1 多智能体协作模型

五个智能体按流水线串联，每个智能体都配有 LLM 与规则/模板两套实现，由工厂（Factory）或配置开关在构造期选择，运行时再按需回退：

        B[镜头分割智能体<br/>ShotSegmenterAgent]
        C[视频分割智能体<br/>VideoSplitterAgent]
        D[提示词转换智能体<br/>PromptConverterAgent]
        E[质量审查智能体<br/>QualityAuditorAgent]
        
        A -->|结构化数据| B
        B -->|镜头序列| C
        C -->|片段序列| D
        D -->|提示词数据| E
        
        A -.->|降级| A1[规则解析器]
        B -.->|降级| B1[规则镜头分割器]

降级接线现状（三口径考证）：运行期降级真实接线了两条——提示词转换在单片段粒度 try/except，LLM 转换失败即回退模板转换器（llm_prompt_converter.py）；视频分割的 LLM 实现内部持有 rule_splitter 实例，异常时整镜头回退规则分割（llm_video_splitter.py）。剧本解析的规则校验路径已实现但调用被注释（script_parser_agent.py），属于预留开关，二次开发时不要把 use_local_rules 当作现成功能。

3.2 智能体职责说明

智能体 输入 输出 核心功能
ScriptParserAgent 自然语言剧本 ParsedScript 解析剧本结构，提取角色、场景、对话、动作
ShotSegmenterAgent ParsedScript ShotSequence 将剧本元素拆分为镜头，估算时长，分配镜头类型
VideoSplitterAgent ShotSequence FragmentSequence 智能分割长镜头，生成片段序列
PromptConverterAgent FragmentSequence AIVideoInstructions 生成双语视频和音频提示词，保持道具一致性
QualityAuditorAgent AIVideoInstructions QualityAuditReport 审查提示词质量，检测截断、不一致问题

代码布局：每个智能体是一个子包，如 neopen/agent/script_parser/ 内含 base_script_parser.py、llm_script_parser.py、rule_script_parser.py 与 script_parser_models.py；对外暴露的 ScriptParserAgent 包装类位于 neopen/agent/script_parser_agent.py，负责注册两套实现、编排解析流程与质量评估。其余四个智能体同构。

四、快速开始（准备工作 → 步骤）

4.1 环境准备

前置环境要求：需要 Python 3.10+（pyproject 中 requires-python >= 3.10）与有效的 LLM API 密钥；Redis 7.0+ 可选，用于多进程部署时的任务记录共享。克隆后用 pip install -e . 以可编辑模式安装，便于修改源码即时生效；开发场景可装 pip install -e ".[dev]" 一次带上 pytest、black、flake8、mypy 等工具。安装后会注册 story-shot-agent、vs-agent 与 story-shot-agent-serve 三个命令入口。

4.2 环境配置

编辑 .env 文件，配置必要的 LLM 与 Embedding 参数：

配置命名规则：配置项采用 PENSHOT_LLM__DEFAULT__* 双下划线分层命名，DEFAULT 是默认 profile，FALLBACK 是备用厂商；API_KEY 务必替换为自己的密钥（也支持 ${ENV_VAR} 间接引用环境变量）。若使用本地 Ollama，把 BASE_URL 指向 http://localhost:11434/v1 即可。Redis 段同时接受完整的 PENSHOT_REDIS_URL=redis://:password@localhost:6379/0 写法（.env.example 注释里有说明）。

4.3 启动服务

服务监听地址由配置决定：默认从 PENSHOT_API__HOST（模板 localhost）与 PENSHOT_API__PORT（8000）读取，命令行参数可覆盖；启动后提供完整 REST API 与 /docs 交互式文档。

多入口差异（源码考证）：main.py 与 http_server.py 最终都启动 penshot.app:app，但启动器各有侧重——main.py 支持 --reload 热重载与 workers 多进程（reload 与多进程互斥，reload=True 时强制 workers=1）；http_server.py 额外提供 --max-concurrent/--queue-size 参数（经环境变量传给应用）；CLI 的 serve-rest 是 cli.py 里 cmd_serve_rest 的封装。还需注意：多进程模式下任务队列与回调是进程内状态，任务记录需经 Redis 跨进程共享，未配置 Redis 时启动会打印警告且在进程间分裂（提交到进程 A 的任务在进程 B 查询为 not_found）。

调用流程：典型的三步——提交、轮询状态、取结果。提交后拿到 task_id，循环查询 GET /status/{task_id}，直到 status 变为 success（不是 COMPLETED），再调 GET /result/{task_id} 取提示词数据。请求量不大、想要低延迟的场景可以直接走同步接口 POST /storyboard/sync，一次请求阻塞到出结果；它的错误语义要注意——任务业务失败时抛 HTTP 400，错误文本在 FastAPI 标准的 detail 字段里（取自 result.error，兜底文案为 任务处理失败），成功时才返回完整的 ProcessResult 结构，两条路径的响应体不同，客户端要分开处理。

常用端点速览（rest_api.py 共 17 个路由，以下是集成时最常用的 9 个）：

方法 路径 说明
POST /api/v1/storyboard 异步提交，立即返回 task_id
POST /api/v1/storyboard/sync 同步提交，阻塞到出结果，业务失败返回 400
POST /api/v1/storyboard/batch 批量异步提交，单批上限 50 条
POST /api/v1/storyboard/batch/sync 批量同步提交，单批上限 20 条、超时 600 秒
GET /api/v1/status/{task_id} 查询状态，含 current_stage 与 stages_progress 阶段进度
GET /api/v1/result/{task_id} 获取结果，未完成时返回带 message 的任务结构
DELETE /api/v1/task/{task_id} 取消任务，对已结束的任务返回 400
GET /api/v1/queue/status 队列负载状态
GET /api/v1/health 健康检查

三处接口细节提醒（源码考证）：其一，取消任务的真实路由是 DELETE /api/v1/task/{task_id}，但 http_server.py 启动横幅里印的是 POST /api/v1/cancel/{id}，照横幅调用只会 404，以 rest_api.py 的路由表为准；其二，GET /tasks 的 docstring 声明了 status_filter 参数（枚举值里还出现了 completed），但函数签名里根本没有这个参数——传了会被静默忽略，且返回的 tasks 恒为空列表，它更像一个尚未接线的占位实现；其三，GET /result/{task_id} 在任务未完成时不返回 HTTP 202，而是正常 200 加上 message 字段提示处理中，客户端要靠 body 里的 status 判断进度，不要依赖 HTTP 状态码。

字段说明（全部取自该真实样例，无构造数据）：外层 task_id/status/success/processing_time_ms/created_at/completed_at 是任务封套，业务数据全在 data.instructions 内——metadata 记录生成时间、模型选择与后处理修复史，project_info 汇总片段数与总时长（2.77 + 4.5 = 7.27 秒），fragments 是逐片段的视频与音频提示词，global_settings 与 execution_suggestions 是给下游视频生成环节的衔接建议。注意 processing_time_ms 为 3221383（约 53.7 分钟），这是含 LLM 多次请求与重试的单次真实耗时，不是性能基准，别拿它做容量规划。

两个对照代码时要注意的细节：其一，fragments[].audio 是配套的声音设计（环境底噪、音效与负面提示词），当前源码 AIVideoPrompt 模型的字段名就是 audio，而仓库这份样例 JSON 是旧版落盘的、用的旧键名 audio_prompt，写解析代码时以模型字段为准，别硬编码键名；其二，repair_history 里这条 989 -> 200 是一次真实触发的超长截断，当前源码中相关实现的计数口径值得留意——llm_prompt_converter.py 与 prompt_converter_agent.py 都用 only_count_en（按英文单词计数）判断超长，但执行截断用的却是字符切片 prompt[:阈值 - 20] + "..."，修复统计里的长度又是 len() 字符口径，一次修复里三种计数口径并存；这也是为什么 new_stats.avg_prompt_length 是 183（180 字符 + 3 个省略号），与触发时的数字不在同一量纲，后文常见问题会展开这套口径问题的排查思路。

六、开发环境搭建（准备 → 步骤）

6.1 环境要求

  • Python 3.10+（pyproject.toml 的 requires-python 下限）

  • 有效的 LLM API 密钥（OpenAI 兼容接口；默认模型 gpt-4o，可切其他厂商）

  • Redis 7.0+（可选：默认部署不需要；仅多进程部署时用于跨进程共享任务记录，任务队列本身在进程内）

6.2 安装步骤

几点说明（源码考证）：项目用 pyproject.toml 管理依赖，没有 requirements.txt，别照老习惯去找它；[dev] 附加组包含 pytest 等测试依赖，只跑服务的话 pip install -e . 也够；Redis 不是启动前置，只有多进程部署才需要（docker run -d -p 6379:6379 redis:7-alpine）；Windows 下激活虚拟环境用 venv\Scripts\activate。

6.3 项目结构

二次开发入口：新增功能通常改 src/penshot/neopen/agent/（智能体与编排）、src/penshot/neopen/prompts/v1.x/（提示词模板）、src/penshot/api/（对外接口）。main.py 是服务入口（uvicorn 加载 penshot.app:app），mcp_server.py 是 MCP 入口；日志级别不在代码里改，编辑 src/penshot/config/logging.yaml 即可。

八、性能优化建议

  1. LLM 缓存（默认关闭，属预留能力）：BaseLLMAgent 提供了 _call_llm_with_cache（md5 缓存键含 prompt、system_prompt、temperature 与 task_id，带 TTL 与容量控制），但 AIConfig.enable_llm_cache 默认是 False，源码注释直言原因是 LLM 输出不稳定；而且缓存键包含 task_id，跨任务即使描述相同也不会命中——它的定位是任务内去重，不是跨任务复用。独立类 LLMCache（cache/llm_cache.py）的实例化在代码里被注释，属未接线状态；启用前建议先实测命中率与质量收益。

  2. 并发处理：max_concurrent 控制同时执行的任务数、queue_size 控制排队上限，两者在 PenshotFunction / create_penshot_agent 构造时确定；取值建议对齐 LLM 服务的速率限制，而不是越大越好。

  3. 多进程部署才需要 Redis：默认的进程内队列没有网络往返开销；只有横向扩展 worker 进程时，Redis 才作为跨进程的任务记录共享层登场（见 4.3 的多入口差异）。

  4. 降级策略分两层看：运行内已接线的有两条——提示词转换失败时按片段回退模板转换、视频拆分规则兜底（见 3.1）；script_parser_agent 里规则校验的接线目前处于注释状态，评估时不要把它算作已生效能力。

  5. 提示词长度控制：注意 max_prompt_length 的计数口径问题（触发按英文单词数、截断按字符数，见 Q2），过长提示词除了 token 成本，更直接的伤害是真实触发的截断会丢掉大量细节。

九、常见问题

Q1: 任务状态一直是 PENDING？

排坑（源码考证）：PENDING 说明任务已创建但还没被取走执行。先分清部署形态——默认是进程内队列，跟 Redis 无关，所以先查两件事：active_tasks 是否已达 max_concurrent 上限（并发打满时新任务排队等）；任务提交与查询是否落在同一进程（多 worker 且未配 Redis 时，提交到进程 A 的任务在进程 B 查询是 not_found）。确实启用了多进程 + Redis 的部署，再核对 .env 中 PENSHOT_REDIS_* 键与连接信息是否一致。

Q2: 提示词被截断？

排坑（源码考证 + 真实案例）：仓库自带的运行样例 examples/data/results/function_calls_data.json 里就留下了真实截断记录，repair_history 显示两条提示词从 989、881 被截到 200。对照源码注意三点：触发判断用 only_count_en 计英文单词数，截断动作却是字符切片 prompt[:阈值 - 20] + "..."，修复统计再用 len() 字符数，三种口径混用；所以看到 989 -> 200 别按单一单位去换算。调参入口是 ShotConfig.max_prompt_length（它的注释写"单词数"，与实现并不完全一致，建议自己实测确认）；不想被截的话，除了调大阈值，更稳的是在提示词模板里约束 LLM 的输出长度。

Q3: 道具信息丢失？

确保 GlobalMetadata 中正确配置了 key_props，并在解析、拆分、转换各阶段的传递链路中保持一致。

Q4: 如何自定义 LLM 模型？

修改 .env 中的 PENSHOT_LLM__DEFAULT__MODEL_NAME 配置。

排坑：改模型时需同时核对 BASE_URL 与 API_KEY 是否匹配目标厂商；若为本地 Ollama，BASE_URL 通常指向 http://localhost:11434/v1。gpt-4o 只是模板里的默认值，切换厂商属于配置行为，不涉及代码改动。

Q5: 生产环境要不要 Redis？

排坑（源码考证）：先纠正一个过度概括——Redis 在这套代码里并不是"任务队列 + 状态管理 + 结果缓存"的通吃角色。任务队列与并发控制在进程内（TaskManager），Redis 的定位只有一个：多进程/多实例部署时的任务记录共享层。判断标准很简单：单实例部署不必上 Redis；要跑 uvicorn 多 worker 或横向扩容多副本时才需要，并接受"未配 Redis 时任务在进程间分裂为 not_found"的约束（见 4.3）。
