PenShot 快速开始

本文是一份可以跟着做的实操：从安装 PenShot、配置 .env，到用异步 API 跑通《雨中的约定》剧本，拿到一份可直接投喂给 Runway / Pika / Sora 等模型的提示词列表。文中所有运行数据都取自仓库自带的真实样例文件（examples/data/results/ 下的六个 JSON），并标注生成时间与口径来源——包括一次质量审计 6 项检查通过 5 项、失败 1 项的真实结果。遇到与直觉不符的地方，本文会指出项目当前的实现行为，而不是理想化的描述。

相关链接：GitHub | 官网 | 文档 （架构设计 · 召回策略 · MCP Server · 一致性策略 · RAG 增强）

一、整体流程概览

在动手之前，先建立整体认知。PenShot 将原始剧本转换为结构化的视频提示词，核心处理链路如下：

flowchart LR
    subgraph Input["输入层"]
        A[原始剧本<br/>自然语言 / 标准剧本]
    end
    
    subgraph Core["核心处理链（六个节点）"]
        B[剧本解析<br/>parse_script]
        C[分镜拆分<br/>segment_shot]
        D[片段分割<br/>split_video]
        E[提示词转换<br/>convert_prompt]
    end
    
    subgraph Control["质量与控制层"]
        F[质量审查<br/>audit_quality]
        G[连续性检查<br/>continuity_check]
    end
    
    subgraph Output["输出层"]
        H[分镜序列 + 双语提示词<br/>+ 音频提示词]
    end
    
    A --> B --> C --> D --> E --> F --> G --> H
    F -->|发现问题| I[生成修复参数<br/>打回上游重跑]
    F -->|严重问题| J[人工干预 / 错误处理]

整体思路：这条链路由 6 个核心节点组成（对应 PipelineNode 枚举的六个值，另有输出/修复/人工干预等辅助节点），对使用者来说是一条自动流水线——放入结构化的剧本，拿回分镜序列、视觉提示词与音频提示词。质量审查发现问题会生成修复参数并打回上游重跑；严重问题转入人工干预或错误处理。

真实运行示例：输入《雨中的约定》（12 个剧本元素），得到 12 个镜头、13 个片段、总时长 48.0 秒，每个片段都带双语视觉提示词与音频提示词；最终质量审查 6 项检查通过 5 项，LLM 连贯性检查发现 5 个问题。

数据口径说明：同一剧本在不同时间运行，LLM 的输出会波动——仓库 docs/testing 下的 v0.3 评测报告（2026-05-05 的另一次运行）给出的是 11 个元素、10 个镜头、平均 3.38 秒、6 个问题。本文选用 examples/data/results 下的样例链，因为它有六个环节的完整落盘文件可以逐项对照；引用评测报告的地方会单独标注。

二、准备工作

在安装与配置前，先确认运行环境满足要求。

系统要求

组件 版本要求
Python 3.10 及以上
Redis 可选（6.0+，多进程部署与记忆持久化时建议）
内存 建议 8GB 以上
存储 建议 2GB 以上

说明：Python 要求 3.10+，与仓库 pyproject.toml 中的 requires-python = ">=3.10" 以及 PyPI 包声明保持一致。Redis 是可选组件，承担两个角色：短期记忆的会话存储（不可用时自动降级为文件持久化，不会因此启动失败）与多进程模式下的任务记录共享（多 worker 部署时若不配置会看到启动警告，提交与查询可能落在不同进程）。单进程 SDK 场景完全可以不装 Redis。

安装步骤

  1. 安装主包

penshot 已发布到 PyPI（截至写作时从 0.2.1 迭代到 0.3.7），并提供官方 Docker 镜像 neotems/penshot，不是只存在于 GitHub 的源码包。

关于 LLM 依赖（对照 pyproject.toml）：核心依赖里自带 langchain-ollama，不额外安装即可连接本地 Ollama；使用 OpenAI/DeepSeek 需要 langchain-openai/langchain-deepseek，使用通义千问需要 dashscope——这三项都在 llm-providers 可选组里，一条命令装齐：pip install "penshot[llm-providers]"。缺失厂商 SDK 时请求会直接失败并报错，而不是静默切换模型。

下面按工作流的六个核心节点逐个拆解本次运行，所有数据与 4.1 节同源，便于你在排查问题、调参时定位到正确的环节。

阶段二：镜头分割（segment_shot）

LLM 分镜器（LLMShotSegmenter）把剧本元素转换为视觉镜头，每个镜头带景别、时长、主角色与置信度（本次 12 个镜头的置信度在 0.97-1.0 之间）。

shot_002 medium 3.0 秒 林小雨擦拭《飞鸟集》
shot_003 medium 5.2 秒 自语：明明说好今天还书的……
shot_004 wide 3.5 秒 陈阳骑车入画，书落水洼

阶段三：视频分割（split_video）

把镜头切分为适合 AI 视频生成的片段。这里存在两套分割器：规则分割器 RuleVideoSplitter 与 LLM 分割器 LLMVideoSplitter，规则侧的核心逻辑（节选自 rule_video_splitter.py）是：

实际走哪条路径由 _should_use_llm_split() 判定：时长超过阈值的镜头会被交给 LLM 分割器。本次运行的 video_splitter_result.json 给出了路径分布——cutter_type 为 LLMVideoSplitter、ai_split_count 为 2、rule_split_count 为 11：

  • 11 个时长 2.8-5.2 秒的镜头走规则路径，1:1 映射为片段；

  • 唯一超过 5.5 秒的 shot_009（6.0 秒）触发 LLM 智能分割，被切成 2 段：frag_009（3.2 秒）+ frag_010（2.8 秒）。

注意 LLM 切出的段数不是公式算出来的：按规则公式这类 6.0 秒镜头会等分 3 段，而 LLM 结合镜头内容判断切 2 段更合理。它的决策过程完整落盘在 ai_decision 字段，节选如下：

镜头时长为6.0秒，超过分割阈值5.5秒，且包含多层动态信息：1）陈阳身体动作（直起身）；2）道具状态变化（拎空袋→托书）；3）视线与情感递进……台词为完整单句但语义有明显节奏停顿点……适合在省略号处自然分割以匹配呼吸与情绪节奏。

拆分出的两个片段还各带 key_frames（关键帧描述）与 continuity_plan（角色一致性/场景一致性/转场建议），frag_010 额外标记 requires_special_attention: true——分割不只是在时间轴上切开，还要把连续性约束下传给后续环节。

本次映射结果：12 个镜头 → 13 个片段，13 个片段中 12 个小于 5 秒（唯一例外是 frag_003 的 5.2 秒）。

阶段四：提示词转换（convert_prompt）

这一步由 LLM 驱动的 LLMPromptConverter 完成：把 13 个片段的描述逐个转换为视频提示词、负向提示词与音频提示词三件套。它不是字符串模板拼接——每个片段都单独调用 LLM，由模型根据内容自由组织措辞。以 frag_001 的真实提示词开头为例：

提示词的组成结构（以 frag_001/frag_002 为例）：

组成部分 真实示例 说明
景别前缀 Cinematic wide shot / medium shot, cinematic lighting LLM 自行组织，形式不固定
场景环境 overcast sky / wet pavement / coffee shop sign 环境锚点，跨片段重复
角色服装 Lin Xiaoyu … cream-colored long dress 同一实体的措辞刻意复用
关键道具 cobalt-blue hardcover ‘Gitanjali’ … water stain 道具连续性描述
摄影风格 Fujifilm Superia film grain, 35mm … 统一调色方向
中文回译 全景镜头：灰蒙蒙低云压境…… 与英文一一对应，便于核对
负向提示词 cartoon, anime, 3D render, … 抑制常见瑕疵

为什么不用固定模板？固定模板会把素材差异抹平，也无法按片段内容做取舍。但 LLM 自由生成也有代价——本次审计发现的 米white（英文描述里混入中文汉字米）、陈阳未罗马化、frag_009 中 matte 与 reflective 的措辞矛盾，都是措辞漂移的实例。这说明一致性主要靠提示词约束加审计兜底，而不是靠模板保证。

音频提示词：每个片段同时生成 audio_prompt——环境音与人声的混合描述，model_type 在 AudioLDM_3（纯环境音）与 XTTSv2（人声台词）之间按内容选择；previous_audio_id 逐段串联（frag_002 指向上一条 audio_001），为下游音频生成保留上下文链。

阶段五：质量审计（audit_quality）

审计节点做 6 项检查：5 项基础检查（片段时长限制、提示词内容、提示词长度、片段数量、模型支持）加 1 项 LLM 连贯性检查。本次运行的 quality_auditor_result.json 显示：5 项通过、LLM 连贯性检查未通过，共落盘 5 条 violations：

严重程度 数量 涉及片段 内容摘要
critical 1 条 frag_013 非英文色名 米white 混入、陈阳未罗马化、提示词被截断（省略号残留）
major 2 条 frag_013 / frag_009 气象逻辑矛盾（golden-hour sunlight 与连绵阴雨矛盾）；服装与动作不连续（雨衣 matte 与 reflective 矛盾、图书交接缺镜）
moderate 2 条 frag_011 / frag_003 场景锚点漂移（招牌文案在 frag_011 才首次出现）；frag_003 时长 5.2 秒超出建议上限

两个分数要区分：这份 JSON 的 stats.quality_score 是 0.0，顶层 score 却是 100.0。两者口径不同——stats.quality_score 按权重逐条扣分（critical 40、major 25、moderate 10、warning 5、info 0，从 100 分基分扣除），本次 5 条违规合计扣 110 分、被收敛到 0；顶层 score 是历史版本未同步的默认字段。判断运行是否通过应看 status（本次 critical_issues）、needs_human_review（true）与 stats 明细，而不是顶层 score。

本次结论：conclusion 字段为发现 1 个严重问题、需要人工干预；timeline_impact 评估修复需 1-2 小时、不建议直接进入生产（can_proceed: false）。13 个片段中 4 个片段涉及问题，高风险片段是 frag_013 与 frag_009。

阶段六：连续性检查（continuity_check）

工作流的六个核心节点里，最后一个不是输出而是守护——continuity_check_node（workflow_nodes.py）。它汇总各阶段产物做视觉、角色、场景、动作四类连续性校验，识别问题来自哪个上游阶段，并生成针对性修复参数路由回去重跑（_route_to_fix_stage），同时受节点循环上限约束（CONTINUITY_CHECK 最多 5 次循环、2 次重试，来自 workflow_state_types.py）。

本次落盘结果里能看到这一机制的两类痕迹：每个片段字段 continuity_notes.continuity_check 均为 passed（分割器侧写入的逐片段校验结论）；被 LLM 拆分出的 frag_010 带 requires_special_attention: true，提示下游重点检查它与 frag_009 的衔接（台词在省略号处被切开）。

设计意图：质量审计关注单个片段是否达标，连续性检查关注片段之间是否连贯。两者都可能把问题打回上游，但修复路径不同——审计侧重重新生成或修复提示词，连续性检查则按问题来源阶段路由，避免整条链路重跑。

代码方式配置

绝大多数场景不需要写代码：.env 中的 PENSHOT_LLM__DEFAULT__TEMPERATURE 等键会在导入时自动加载（见第二章）。代码方式适合在调用时做单次覆盖。

阈值调整建议（依据内容节奏因地制宜）：

场景 推荐阈值 说明
快节奏动作片 3.0-4.0秒 更多短片段，节奏更快
文艺剧情片 4.0-5.5秒 保留长镜头，氛围感
对话密集场景 5.0-6.0秒 保持对话完整
风景/环境 5.0-8.0秒 保留画面美感

调参的核心矛盾是叙事完整性 vs 模型输入限制：阈值越小片段越碎、节奏越快但易切割台词；阈值越大越能保持镜头完整但可能超过模型时长上限。参考 v0.3 评测报告的另一次运行：那次没有镜头越过 5.5 秒阈值，AI 分割器整场未触发——阈值是否生效高度依赖输入内容的节奏，调参前建议先看一遍分镜结果的时长分布。

七、数据口径与复现方法

这批样例数据的性质：examples/data/results/ 下的六个 JSON 是一次历史真实运行的阶段产物，仓库里的演示脚本 examples/workflow/02_pipeline_stages_demo.py 会读取它们讲解流程阶段；脚本注释明确说明这批文件不承诺与最新 schema 逐字段一致。因此它们适合用来理解数据链路与字段结构，但不适合当作实时结果或性能基准：

  • 字段名可能滞后（如 audio_prompt 与当前模型字段 audio 的差异）；

  • 数值只代表当时那次运行（输入、模型、温度都会影响结果）。

第二次运行的对照数据：docs/testing/v0.3 功能完成度评测报告.md 记录了 2026-05-05 的另一次评测运行，给出完全不同的数值——11 个元素 → 10 个镜头（平均 3.38 秒）→ 10 个片段，审计发现 6 个问题（Major 1、Moderate 2、Warning 2、Info 1），工作流六阶段完整执行。两次数据说明：流程结构稳定，但具体数值会随输入与模型显著波动。

复现方法：在自己的环境里跑一遍，最快的方式是第二章的示例代码（或 examples/sdk/01_sync_breakdown.py）——前提是 .env 中的 LLM Key 已配置；跑完后把各阶段结果落盘，就能用与本文相同的视角对照自己的数据。注意：没有 LLM 配置时流程不会长时间空转，01_sync_breakdown.py 会直接提示配置缺失并退出。

八、质量保障机制

两层审计

层 内容 特点
规则检查 5 项基础检查（片段时长限制/提示词内容/提示词长度/片段数量/模型支持） 纯代码逻辑，瞬时完成
LLM 连贯性 把全部片段的正反向提示词整体交给 LLM 审阅 耗时数十秒，能发现语义矛盾

LLM 连贯性检查的问题按维度分类，从 violations 的 description 前缀可以直观看到：[气象]、[角色]、[场景]、[提示词]、[时长]——分别对应环境连续性、角色一致性、场景锚点、提示词质量与节奏问题。

修复闭环的真实状态

flowchart TB
    A[各阶段产物] --> B[5 项规则检查]
    B --> C[LLM 连贯性检查]
    C --> D{存在 critical 问题?}
    D -->|是| E[needs_human_review<br/>需人工审核]
    D -->|否| F[recommended_actions<br/>修复建议落盘]
    E --> F
    F --> G[连续性检查节点<br/>可路由回上游重试]

需要如实说明当前实现的边界：审计报告会给出 recommended_actions（本次 5 条，逐条对应 violations 的修复建议）并置位 needs_human_review，但 docs/testing/ 的 v0.3 评测报告记录 repair_applied: false——修复参数虽已生成，并未触发自动重跑，该缺口被列为 P0 问题。相比之下，连续性检查节点内置了按阶段路由与最多 2 次重试的闭环，两者能力并不对等。审计报告的 timeline_impact 把修复估算为 1-2 小时，正是因为当前修复主要靠人工。

判定规则（quality_auditor_models.py）：

  • 加权扣分：critical 40 分、major 25 分、moderate 10 分、warning 5 分、info 0 分，从 100 分基分逐条扣除并收敛到 0-100 区间；

  • 状态分档：90 分以上 PASSED、75 分以上 MINOR、60 分以上 MODERATE、40 分以上 MAJOR、20 分以上 CRITICAL，更低为 FAILED；

  • needs_human_review：存在 critical，或 major 超过 2 条时置位。

九、记忆系统

PenShot 的记忆模块（knowledge/memory/）把记忆分为四级枚举（MemoryLevel：EPHEMERAL、SHORT_TERM、MEDIUM_TERM、LONG_TERM），组织上归为三层：

flowchart TB
    subgraph Short["短期记忆（会话窗口）"]
        S1[消息缓冲 deque<br/>maxlen=short_term_size]
        S2[RedisChatMessageHistory<br/>可选持久化]
    end
    subgraph Medium["中期记忆（阶段摘要）"]
        M1[阶段产出摘要<br/>受 max_tokens 约束]
    end
    subgraph Long["长期记忆（向量检索）"]
        L1[VectorStoreRetrieverMemory]
        L2[top_k=3<br/>score_threshold=0.7]
    end
    Input[各阶段写入] --> Short
    Short --> Medium
    Medium --> Long
    Long -.->|语义检索| Output[后续阶段读取]
    Medium -.->|阶段摘要| Output
    Short -.->|即时上下文| Output

三层各自是什么（memory_models.MemoryConfig 默认值）：

层 载体 关键参数
短期 消息缓冲 + Redis 会话（RedisChatMessageHistory） short_term_size=20、short_term_ttl=3600
中期 阶段摘要（受 token 上限约束） medium_term_max_tokens=500
长期 向量库检索（LangChain 记忆工具） long_term_k=3、long_term_score_threshold=0.7

Redis 是可选依赖：短期记忆初始化时先探活 Redis，可用时把会话写入 Redis（key 形如 penshot:memory:{script_id}:{session_type}），不可用时降级为本地文件（data/memory/{script_id}/short_term.json）——所以本地跑没有 Redis 也能完成全流程，不会阻塞任务。

一点纠偏：角色服装、道具状态能跨片段衔接，主要靠各阶段携带的连续性信息——分镜产出带 element_ids 与时间轴的镜头序列、LLM 分割写入 continuity_plan、提示词刻意复用措辞——记忆系统提供的是增强。v0.3 评测报告显示：记忆系统当时处于部分实现状态（短期会话为空、长期向量库 78 条文档），任务依然走完六阶段。把长剧本一致性的根本原因全归于记忆系统，并不符合当前实现。

十、常见问题与检验方法

Q1：处理一个剧本需要多长时间？

没有固定答案。以 4.1 节样例为例：从解析产物落盘（17:22:48）到审计报告落盘（17:29:44）就用了约 7 分钟，其中提示词转换环节占了 4 分半（13 个片段各自生成视频与音频提示词）。耗时的决定性因素是 LLM 调用次数与模型响应速度，而不是剧本字数本身，不同服务商之间的差异可能达到数倍。建议先用短剧本估时，再评估长剧本。

Q2：支持哪些 LLM？

官方支持四类厂商：OpenAI、通义千问（DashScope）、DeepSeek、Ollama（见 .env.example 注释）。默认配置在 PENSHOT_LLM__DEFAULT__*，默认模型不可用时可配置 PENSHOT_LLM__FALLBACK__* 备用（示例值指向 deepseek-chat）。依赖侧对应可选安装组 llm-providers（含 langchain-openai / langchain-deepseek / dashscope）。

Q3：如何提高生成质量？

  • 剧本描述尽量具体（服装颜色、道具特征、天气），含糊描述在提示词生成时会被放大为不一致；

  • 保持低 temperature（默认 0.1），减少措辞漂移；

  • 拿到审计报告后按 recommended_actions 逐条修正——当前版本自动修复尚未闭环，人工介入是主要手段；

  • 长剧本拆段处理，降低单次调用的上下文压力。

Q4：生成的提示词支持哪些视频生成模型？

VideoModelType 枚举定义了 8 种：RUNWAY_GEN2、RUNWAY、SORA、VEO、Pika、MIDJOURNEY、STABLE、DALLE；音频侧 AudioModelType 定义了 6 种：XTTSv2、AUDIOLDM_3、BARK、ELEVENLABS、AZURE_TTS、OPENAI_TTS。样例运行使用 runway_gen2 + XTTSv2。注意枚举中并没有 Kling（尽管项目描述里提到过它），需要用的话要自行扩展。

Q5：质量报告的分数为 0 怎么办？

先确认看到的是哪个字段（第五章解释过双口径）：stats.quality_score 归零意味着加权扣分已把 100 分扣满。处理路径是逐条核对 violations：

问题类型 解决方案
提示词截断 检查提示词长度约束（max_prompt_length）与输出 token 上限
角色描述不一致 在剧本中统一角色外貌和服装描述，减少自由发挥空间
动作逻辑缺失 补充动作过渡描述（如道具交接的动作镜头）
风格/锚点漂移 在剧本或全局配置中固定场景锚点措辞

几项快速自检：① 结果为空 → 检查剧本格式是否为推荐结构，并确认 .env 的 LLM Key 已配置；② 长时间停留在同一阶段 → 多为 LLM 调用超时或网络问题，查看终端日志中的重试信息（Redis 不可用时记忆会降级为文件，不会阻塞任务）；③ 片段时长超限 → 核对 max_fragment_duration 与 duration_split_threshold。
