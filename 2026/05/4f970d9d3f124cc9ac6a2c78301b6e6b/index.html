一、故障恢复的第一性原理

节点会崩，网络会断，进程会被 kill -9。故障恢复要回答的唯一问题是：“正在执行、但执行者已经消失的任务，如何被再次执行，且不重复、不丢失？”

主流的答案有两个流派：

流派 思路 代表系统
主动检测派 心跳监控发现节点死亡 → 立刻接管其任务 多数分布式调度器
被动租约派 执行者持有租约（锁 + TTL），租约过期即视为可接管，不关心执行者死活 NeoTask（v1.0.2）

NeoTask 以被动租约为主、心跳判死为辅。超时回收完全不需要判断"谁死了"——只需要两样东西：

  1. 每项执行都有租约（分布式锁 TTL 30s + 看门狗续期）；

  2. 有个回收器定期检查"看起来没人管的执行"，把它们重新入队。

为什么以租约为主：判活是概率性的，租约是确定性的。 心跳可能误报（网络抖动）、判死可能误杀（GC 停顿）；但锁的 TTL 是 Redis 上的硬事实——过期就是过期，与"节点是否真的死了"无关。把恢复建立在"租约过期"而不是"节点判死"上，系统就摆脱了对故障检测精度的依赖：检测可以慢、可以错，恢复依然正确（详见 去中心化 一文的"两态哲学"）。

在此之上，孤儿回收补上了"节点级"的快速通道：它借助 NodeManager 的活跃节点集合，判定"任务的执行节点是否已失联"，从而比 ttl 超时更早地接管崩溃节点的任务。它的判定有两条硬约束——没有节点管理器就不动作（返回 None 跳过）、绝不回收本节点自己正在执行的任务——这正是"判活不可靠"哲学在节点级回收上的落地方式（详见第五节）。

于是故障恢复的主角仍是回收器（TaskReclaimer）：超时/僵尸锁回收只依赖锁与 ttl，孤儿回收才需要知道节点集合在哪。

三个扫描的判定对象各不相同：

扫描 周期 判定对象 判定条件
僵尸锁扫描（LockScanner） 60s 锁本身 锁存在时间 > 300s 阈值 或 owner 无主
超时回收 30s RUNNING 任务 now - started_at > task.ttl（默认 3600s）
孤儿回收 30s RUNNING 任务（跳过本节点） node_id 非空 且 不在活跃节点集合；无节点管理器时整段跳过

三者都只读不杀——真正"处置"动作统一收敛在 _reclaim_single_task（见下节）。这让回收逻辑只有一处需要严格正确，其余全是扫描。

3.3 处置动作：重新入队 or 标记失败

🔧 _reclaim_single_task 是唯一处置入口（节选）：

为什么这么设计：处置动作统一收敛 + 递增延迟重试。

  • 所有回收原因（超时/孤儿/僵尸锁）走同一个处置函数，行为一致、可审计（ReclaimResult 记录 reason）；

  • 重试延迟 1s、2s、3s 递增——线性退避。为什么不是指数退避？回收是低频事件（30s 周期），重试对象彼此独立，冲突概率低；线性退避让"节点刚恢复就绪"时任务尽快回流，同时给下游短暂喘息；

  • 超过 max_retries（默认 3）的任务被标记 FAILED 而不是无限重试——防止"永远在回收-失败-回收"的震荡，把选择权交还给观测端；

  • 重新入队被拒时不会留下卡死的 PENDING：队列满/禁用导致 push 返回 False 时，任务直接标记 FAILED 并投递死信；超限失败同样投递死信（详见第九节）。

3.4 回收动作里的锁语义：为什么可能"删不掉"

回收器对锁执行 release(lock_key)——但 分布式锁 一文讲过，RedisLock 的释放是 Lua GET + owner 比对 + DEL。回收器并不知道执行者的 owner 值，因此：

  • 若原执行者还活着（锁在续期）→ release 失败，锁安然无恙——正在执行的任务不会被打断；

  • 若原执行者已死（锁已过期/无人续期）→ 锁本身已消失，release 幂等无害。

这是整个回收体系最重要的安全属性：回收者无权删除活锁。 它的"回收"只改状态与队列，真正决定"任务是否继续被执行"的，永远是锁。

四、超时回收：判定口径是任务 TTL

4.1 超时口径：以任务自身的 ttl 为准

"卡死 5 分钟（300s）自动回收"是一个常见误解。对照 v1.0.2 源码，默认判定值不是 300s，而是任务对象自身的 ttl。真实判定逻辑：

🔧 worker/reclaimer.py 的 _reclaim_timeout_tasks：

任务对象的 ttl 字段默认是 3600（1 小时）（🔧 models/task.py：ttl: int = 3600），提交 API 的默认值同样是 3600（🔧 core/dispatcher.py 的 ttl: int = 3600）。所以：

场景 实际超时判定值 回收时间
未显式指定 ttl 的任务（默认） task.ttl = 3600 启动后 1 小时 才回收
提交时指定 ttl=300 task.ttl = 300 5 分钟回收
任务对象没有 ttl 属性（理论兜底） ReclaimerConfig.task_timeout = 300 5 分钟回收

也就是说："5 分钟内恢复"对应的不是默认行为，而是显式设置了任务 TTL 或依赖兜底分支的行为。 默认配置下，"卡死任务"的兜底回收是 1 小时量级。设计者有意为之：任务的 TTL 应该由提交方按业务预期显式声明（“我这个任务最多跑多久”），系统尊重这个声明；只有连声明都没有的旧数据才落到 300s 兜底。

实践建议：所有可能长时间运行或可能卡死的任务，提交时显式传 ttl（如视频转码任务 ttl=600），不要依赖默认值——否则"看起来卡死"的任务会白白占着 RUNNING 状态索引一小时。

五、孤儿回收：节点跳过与失效节点判定

5.1 判定前提：必须有节点管理器

孤儿回收的设计意图是"回收那些执行节点已死亡的任务"。判定条件是：任务带 node_id，且该节点不在活跃节点集合中。活跃节点从哪来？来自节点管理器。

🔧 worker/reclaimer.py 的 _get_active_nodes：

这里的关键语义是**"无法判定"用 None 表示，而不是空集合**：

  • 未配置节点管理器（内存/SQLite 形态，或人为不注入 NodeManager）→ 返回 None，_reclaim_orphan_tasks 直接跳过整轮孤儿回收，并只在首次打印一条警告：Orphan reclaim skipped: no node manager configured, cannot determine active nodes。空集合会被误读为"所有节点都死了"，所以绝不返回空集；

  • 查询活跃节点抛异常 → 同样返回 None 并打印警告，本轮跳过（宁可晚回收，不可错回收）；

  • 配置了节点管理器 → 返回当前仍存活（status=active 且心跳未超时）的节点 id 集合（NodeManager.get_active_nodes 按心跳与状态过滤）。

5.2 本节点跳过：一个节点绝不回收自己正在跑的任务

即便拿到了活跃节点集合，_reclaim_orphan_tasks 还有一道本节点跳过：

_get_local_node_id() 取自节点管理器的 node_id。于是孤儿回收的真实语义是：

只有"本节点之外、且其执行节点已不在活跃节点集合中"的 RUNNING 任务，才会被判为孤儿。

正在本节点正常执行的任务，无论跑多久，都不会被自己回收；存活节点上执行的任务，也不会被其他节点回收——只有"执行节点已经失联/退出"的任务才进入回收。

5.3 一套 node_id，四处同源

一个容易产生误解的点是"任务上的 node_id 与节点注册的 node_id 是否同一套体系"。当前实现中它们是同一套：

写入点 来源 值
TaskDispatcher 创建任务 TaskPoolConfig.node_id 配置值（默认 socket.gethostname()）
WorkerPool.start_task 标记 RUNNING WorkerPool._node_id（同 TaskPoolConfig.node_id） 同上
NodeManager 注册节点 TaskPool 显式传入 node_id 同上
TaskReclaimer 本节点跳过 node_manager.node_id 同上

也就是说，任务打标、执行者标记、节点注册、回收跳过共用同一个 TaskPoolConfig.node_id（未显式配置时默认主机名）。只要同一个 TaskPool 实例装配的组件共享配置，四者必然一致，不会出现"任务写 A、节点集合存 B"的错位。

只有绕过 TaskPool、单独构造 NodeManager 且不传 node_id 时，才会走 {hostname}_{pid}_{uuid8} 的自动生成路径——这属于自定义装配场景，需要自行保证与任务侧的 node_id 一致。

5.4 这对使用者意味着什么

  1. 孤儿回收是节点崩溃后的快速恢复通道：Redis 形态默认装配节点管理器；只要目标任务不属于本节点、且其执行节点已失联，回收会在 30s 扫描周期内触发，恢复时间约 30~90s，远快于 TTL 超时回收的 1 小时；

  2. 长任务不再被误回收：本节点执行的长任务被显式跳过；存活节点上的任务因其 node_id 仍在活跃集合中而不会被回收——判定基于真实的节点存活状态，而不是"node_id 非空"；

  3. 没有节点管理器时该功能自动静默退化：不会误回收，只会等待超时回收（task.ttl，默认 3600s）兜底；日志里能看到那条一次性警告。

六、僵尸锁回收：LockScanner 与阈值设计

6.1 为什么要单独扫锁

有些锁从诞生起就没有对应任务（任务已被删除/已完成但锁未释放、手动操作残留），或锁的 owner 已消失但 TTL 被反复续期到异常。任务状态扫描看不到这些"无主之锁"，需要直接对锁本身体检。

6.2 阈值 300s 的含义与"为什么这么设计"

僵尸锁阈值 300s 比锁 TTL（30s）大一个数量级。为什么不是"锁存在超过 30s 就清理"？

  • 锁 TTL 30s 是"单次最长持有"，但有看门狗的任务锁会无限续期（只要任务在跑）。正常长任务的锁完全可以合法存活几十分钟；

  • 真正"僵尸"的锁是没有看门狗、owner 已死的锁——它最多 30s 就会自然过期，根本轮不到扫描器；

  • 那 300s 阈值抓的是什么？异常场景下的残留：看门狗协程泄漏（stop 失败）导致锁被空续期、代码路径绕过正常释放（如进程被 SIGKILL 前最后一刻续期成功）、Redis 主从切换后 TTL 丢失又重建的锁。

所以 300s 阈值 = “给一切合法持有留足余量（10 倍 TTL），只清理明显异常的顽固锁”。扫描器也会结合 get_lock_info（owner/expire 时间）二次确认，避免误删活跃任务锁——与回收器的"无权删活锁"原则一致。

6.3 与任务关联的僵尸锁还有一路

🔧 _reclaim_stale_locks（Reclaimer 内，任务视角）：按 lock:task:* 模式扫锁，对任务已不存在或任务状态非 RUNNING 的锁执行释放。典型场景：任务被取消/失败后，异常路径没走到 finally 释放锁，任务状态已经不是 RUNNING，锁却还在——这路扫描负责收尾。

七、时间线推演：一个节点崩溃后究竟发生什么

设：节点 B 正在执行任务 T（已 acquire 锁、看门狗续期中），进程突然被 kill -9。默认配置下的真实时间线：

gantt

    dateFormat HH:mm:ss
    axisFormat %M:%S

    section 执行阶段
    B 执行任务 T :done, exec, 00:00:00, 10s
    B 崩溃（kill -9） :milestone, crash, 00:00:10, 0s

    section 检测阶段

    锁已过期，release 幂等 :done, rel, 00:00:31, 0s
    任务置 PENDING 重新入队（延迟 1s） :active, requeue, 00:00:31, 1s

    section 接管阶段
    其他节点出队 :done, pop, 00:00:32, 0s
    acquire 锁成功，重新执行 :milestone, redo, 00:00:32, 0s

真实恢复时间 ≈ 30~60s（等一个扫描周期 + 重试延迟），关键前提是任务处于 RUNNING、带 node_id，且执行节点确实已从活跃节点集合中消失（由其他存活节点触发回收；本节点永远不会回收自己的任务）。若孤儿回收被关闭、未装配节点管理器或判定不命中，恢复时间退化为 TTL 超时回收（默认 1 小时）。

为什么这么设计：宁可晚恢复，不可错恢复。 30s 的扫描周期意味着崩溃恢复最坏要等约 60s——对大部分任务调度场景完全可接受（任务本身没有"必须秒级恢复"的 SLA 承诺），却换来了扫描开销可忽略（每 30s 一次，每次最多 100 个任务）。要更快恢复？调小 interval 与锁 TTL，代价是误回收窗口变小但扫描频率上升，量力而行。

任务状态机是故障恢复的核心模型。每个任务在其生命周期中经历多个状态，状态转换由节点操作和故障检测共同驱动。

任务创建后进入创建状态。如果任务有延迟要求，进入调度状态等待执行时间到达。执行时间到达后进入排队状态，等待被节点抢占。节点抢占成功后进入已分配状态，此时任务已被锁定但尚未开始执行。任务开始执行后进入运行中状态。

正常完成的任务进入成功状态，执行失败的任务进入失败状态。成功和失败都是终态，但失败状态可能触发重试。重试时任务重新进入排队状态。

当节点在任务执行过程中崩溃时，其 RUNNING 任务会被其他节点判为孤儿。恢复机制把孤儿任务改回 PENDING（排队）重新入队，或在重试超限时改判 FAILED（同时投递死信队列）。

说明："孤儿"与"死信"是恢复过程中的判定/归宿，不是持久化的任务状态。真实的 TaskStatus 只有 6 个值：pending / running / success / failed / cancelled / scheduled。下面的状态图用于说明流转关系，其中"孤儿/死信"应理解为恢复动作的分支，最终落到的是 PENDING 或 FAILED。

八、为什么这么设计：四个哲学问题

问题一：为什么不主动"杀掉"故障节点的任务？

"检测到节点死了 → 立即 kill 它的任务 → 重新调度"是直觉方案。NeoTask 不这么做的原因在 去中心化 已述：判活不可靠。杀掉一个"假死"节点（GC 停顿、网络抖动）正在执行的任务，等于亲手制造重复副作用（任务可能已写到一半）。被动等锁过期 = 把"任务是否该被接管"的裁决权交给 Redis 的硬时钟，不信任任何节点的软状态。

问题二：回收器自己崩溃了怎么办？

回收器是无状态、可重入的：它不持有跨周期业务状态（只有一个 _orphan_reclaim_warned 标记，用于避免"无节点管理器"的警告刷屏），崩溃后重启，下一轮 30s 照扫不误。任务恢复不依赖"回收器恰好活着"——这与任务执行不依赖"提交节点活着"是同一哲学：所有关键路径都不依赖单点进程。

问题三：为什么回收重试要"先改状态再入队"？

顺序是：置 PENDING → 清 node_id → save → push(延时)。若反着来（先入队后改状态），入队到改状态之间，其他节点可能出队并读到旧状态（RUNNING）而放弃执行。先改状态再入队，保证任务一旦出现在队列里，就处于可被领取的 PENDING 态。同理，start_task（置 RUNNING）发生在锁获取成功之后（见 分布式锁）——锁在前、状态在后，避免出现"状态 RUNNING 但无锁保护"的裸奔窗口。

问题四：为什么"超过重试次数"的归宿是 FAILED + 死信队列？

直觉上失败 3 次应该进死信——现在确实是：重试超限（Worker 失败处理与回收器超限两条路径）都会先 fail_task 把状态置为 FAILED，再投递死信队列（下节）。为什么保留 FAILED 状态：FAILED 是任务状态机的一等公民（可查询 status:failed 索引、可手动重发），对"只需要知道失败了"的场景已经足够；死信队列则额外保留完整上下文与原因分类，供人工工作流消费。两者并存：状态回答"它失败了吗"，死信回答"失败细节是什么、要不要人工介入"。

十、幂等性：恢复动作的安全带

恢复机制天然引入重复：同一任务可能被原执行者执行、又被接管者执行（若原执行者其实是假死）。NeoTask 的多层防护：

层 机制 保护什么
状态闸门 执行前检查 PENDING 已被接管的任务不再被第二人执行
分布式锁 acquire（NX EX 30s）失败即放弃 同一时刻只有一个执行者
看门狗 锁在任务存续期持续有效 长任务不被误接管
回收器的锁语义 无权删活锁（owner 校验） 回收动作不打断活任务
状态机终态 SUCCESS/FAILED 后不再入队 已终态任务不被回收

框架只能保证"调度层面的幂等"（任务不双跑），保证不了"业务层面的幂等"（任务跑两次副作用相同）。 例如"发短信"任务被回收重跑一次 = 两条短信。业务侧需要自备幂等键（订单号、request_id），把"调度至多一次"升级为"业务恰好一次"。这一条在任何任务系统里都是铁律——框架文档会反复强调，因为它不在框架能力边界内。

十二、故障场景实战

场景一：节点崩溃后任务 1 小时没恢复

现象：节点宕机，其他节点正常，但某任务迟迟不恢复（远超 30~60s 预期）；查 status:running 索引发现任务一直在 RUNNING。

根因排查路径：

  1. 查任务 node_id 是否为空——孤儿回收只认"带 node_id 的 RUNNING 任务"；若任务 node_id 为空（创建后清过字段等），孤儿判定不命中；

  2. 查是否装配了节点管理器——内存/SQLite 形态没有 NodeManager，回收器会打印 Orphan reclaim skipped: no node manager configured... 并整轮跳过；此时只能靠 ttl 超时回收；

  3. 查节点是否"真的被判死"——任务所属节点的 node_id 必须不在活跃节点集合里才会被回收。若崩溃节点的心跳键未过期（timeout×2），它会短暂仍算活跃，回收要等它过期；另外本节点永远不会回收自己的任务，所以"回收器所在节点 = 任务执行节点"时不会触发；

  4. 查 enable_orphan_reclaim 是否被关；

  5. 若都正常，任务应在一两个扫描周期内被捞回——还不恢复则检查回收器是否存活（pool.get_stats()["reclaimer"]["is_running"]）、Redis 连接是否健康。

处置：手动干预最快——通过 API 取消任务重新提交，或调用 reclaimer.reclaim_now() 手动触发一轮回收。

场景二：任务反复被回收，最终进入死信

现象：一个执行节点不稳定（反复重启/被回收）的长任务，error 字段不断出现 Reclaimed due to ...、retry_count 逐次累加，达到 max_retries 后被标记 FAILED，并出现在死信队列里。

根因：回收路径每次命中都会 retry_count + 1 并以 retry_delay × 次数 线性延迟重新入队；这是设计行为——回收本质是"重试"。当执行节点持续不可用（任务反复落到不稳定节点、或每次都在完成前失联），重试次数会被耗尽。耗尽后回收器直接置 FAILED 并投递死信（原因映射为 TIMEOUT/ORPHANED/MAX_RETRIES 等）。

处置：

  1. 确认业务执行器幂等（最优先）；

  2. 排查执行节点为何反复失联（内存/CPU/网络/Redis 抖动），这通常才是根因；

  3. 视业务容忍度调大 max_retries；对"必须完成"的任务，消费死信队列并在节点恢复后 dlq.replay(task_id) 重放。

场景三：回收器与执行者竞态——任务在跑却被置回 PENDING

现象：A 节点正在执行任务 T（已 acquire 锁）；回收器判定孤儿，把 T 置 PENDING 重新入队；B 节点出队后 acquire 失败放弃；A 节点继续执行完成 → 状态 SUCCESS。看起来一切正常，但若 A 恰好在"回收器 save(PENDING) 之后、完成之前"崩溃——任务已出队两次且副本都 acquire 失败，任务从队列消失、状态停在 PENDING/RUNNING 之间，无人再执行。

根因：回收的"改状态"与"锁"之间没有原子校验——真实代码先改状态后尝试 release 锁；如果先做"acquire 锁成功才允许回收"，就能杜绝这个窗口。

处置与改进建议（📝 供上游参考/自补丁）：

启示：任何"接管"动作都应该先证明原执行者已放弃（锁已过期/owner 失效），再动状态——"无权删活锁"不仅要体现在 release 语义上，还应体现在回收判定上。

场景四：Redis 主从切换导致锁大面积"丢失"后任务双执行

现象：Redis failover 后，一批 RUNNING 任务对应的锁消失（主库未同步的锁数据丢失），恢复后多节点同时 acquire 成功，同一任务双执行；业务侧出现重复扣款/重复通知。

根因：锁存在 Redis 主节点内存中，异步复制下 failover 丢失锁 = 租约失效但执行者还活着。这是分布式锁在 Redis 架构下的经典缺陷（详见 分布式锁 故障场景四）。

处置：

  1. 业务侧幂等（唯一解法，再次强调）；

  2. 关键任务用 wait_for_result 感知双执行（第二个执行者会因状态闸门失败而快速返回）；

  3. 对 Redis 复制延迟做监控（INFO replication 的 lag），failover 演练要常态化——恢复机制本身也要故障演练。

十三、总结

主题 结论
第一性原理 被动租约派：恢复基于"锁过期"而非"节点判死"，容忍检测误差
真实主角 TaskReclaimer：超时回收 + 孤儿回收（30s 周期）+ 组合 LockScanner（60s 周期）
超时语义 以任务 ttl 为准（默认 3600s），task_timeout=300 只是兜底——"5 分钟回收"是误解
孤儿回收判定 活跃节点来自 NodeManager；无节点管理器→跳过整轮（None，非空集）；本节点任务被显式跳过——不再误回收正常任务
node_id 体系 任务打标 / Worker 标记 / NodeManager 注册 / 回收跳过共用 TaskPoolConfig.node_id，四处同源
安全底线 回收器无权删活锁（owner 校验）；处置统一收敛在 _reclaim_single_task
死信队列 DeadLetterQueue 已接线：Worker 重试超限与回收失败/超限自动投递；replay() 支持人工重放
幂等边界 框架保证"不双跑"，业务保证"双跑无副作用"
时间线 崩溃恢复 ≈ 30~60s（孤儿通道）；未装配节点管理器或关闭孤儿回收后退化 ≈ ttl 超时（默认 1h）

一句结语：故障恢复的优雅不在"方案多高级"，而在边界是否诚实——锁是硬租约、扫描是软检测、回收是补偿动作，三者各守边界，系统就能在"检测不可靠"的前提下依然可靠。孤儿回收必须"无法判定就不动作"（无节点管理器则跳过、本节点任务不回收），宁可能力静默退化，也不误伤正在执行的任务；失败任务的最终归宿是 FAILED 状态 + 死信队列，二者共同承担"可查询"与"可人工介入"。
