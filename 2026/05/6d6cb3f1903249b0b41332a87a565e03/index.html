概述

在分布式任务调度系统中，"同一任务被多个节点重复执行"是所有一致性问题里最隐蔽、也最昂贵的一种：它不像宕机那样立即报警，而是在数据层悄悄留下脏数据。

为什么任务调度如此依赖分布式锁？先看三个朴素方案各自的破绽：

方案 思路 破绽
进程内 asyncio.Lock 同一进程内互斥 多节点部署时完全失效，节点间仍会重复执行
数据库 SELECT ... FOR UPDATE 行锁互斥 每个任务都要开启事务，调度吞吐被锁等待和连接池拖垮
单纯 SET NX 不加过期 键存在即互斥 持锁节点崩溃后锁永不释放，系统整体死锁

破绽的共性在于：任务调度的锁不仅要"互斥"，还要能"自愈"。节点会崩、网络会抖、进程会被 kill -9，锁必须接受"持有者可能永远不再回来"这一事实，并给出超时兜底。

NeoTask 的答案是把 Redis 的 SET NX EX、Lua 原子脚本、看门狗自动续期三件套组合起来，再叠加任务状态机与回收器，形成"锁防重、状态机挡重、回收器兜底"的三层防线。本文按真实源码逐层拆解这三层防线，并回答一个实操中一定会被问到的问题：锁续期失败以后，任务怎么办？

为什么任务调度系统需要一把"会过期"的锁

不加锁会发生什么

一个去中心化调度系统里，任务从提交到执行要经过：入队（ZADD）→ 抢占（Lua ZRANGE+ZREM）→ 执行 → 上报状态。如果不加锁，任何一个环节的重入都会造成重复执行：

flowchart TB
    subgraph NoLock["无锁下的重复执行路径"]
        A[任务重复提交] -->|同一条业务数据提交两次| Q[两个 task_id]
        B[抢占重试] -->|网络超时但服务端已出队| Q2[同一 task_id 被两个节点取出]
        C[故障恢复] -->|孤儿任务重新入队但原节点仍在执行| Q3[同一 task_id 并发执行]

        Q --> R1[重复扣款 / 重复发券]
        Q2 --> R2[幂等冲突 / 数据覆盖]
        Q3 --> R3[脏写 / 幽灵结果]
    end

重复执行在"执行方"眼里往往无害——每次执行都是完整的、自洽的；伤害全部发生在业务侧：重复扣款、重复推送、库存超卖。所以锁的价值不是保护 NeoTask 自身，而是替业务把"最多执行一次"的承诺变现。

为什么是"锁 + TTL"，而不是纯互斥

SET lock:task:xxx owner NX EX 30 这一条命令同时完成三件事：

  1. NX：键不存在才写入，保证互斥（同一时刻只有一个节点写成功）；

  2. owner（锁值）：写入随机持有者标识，后续释放/续期时校验身份，防止"释放别人的锁"；

  3. EX 30：过期自动删除，持有者崩溃后锁也能自愈。

flowchart LR
    subgraph Atomic["SET NX EX 一条命令的三种语义"]
        NX1[NX<br/>键不存在才成功<br/>→ 互斥] 
        VAL[VALUE<br/>随机 owner<br/>→ 身份可校验]
        EX1[EX 30s<br/>到期自动删除<br/>→ 崩溃自愈]
    end

Redis 的单线程事件循环保证这条命令本身原子，不存在"先检查后设置"的竞态窗口——这正是它取代"GET 判断 + SET"两步写法的原因。

为什么用 Redis，而不是 ZooKeeper / etcd

维度 Redis（NeoTask 选型） ZooKeeper / etcd
部署成本 与任务队列共用，零额外组件 需要独立集群，运维成本高
延迟 亚毫秒级，适合高频抢占 毫秒~十毫秒级，且写盘
复杂度 SET NX EX 原生支持 需要临时节点 + Watch 机制
一致模型 主从可能短暂丢失（可容忍窗口） 线性一致，更严格

NeoTask 的锁不是要保护"金钱转账"这类强一致场景，而是要防止"同一任务被执行两次"。后者的诉求是：正常时绝对互斥，异常时尽快收敛。Redis 的主从切换丢失几毫秒的 SET 结果，最多造成短暂的双执行窗口，随后由状态机与回收器收敛——这个取舍是 NeoTask 定位为"轻量嵌入式调度库"的必然选择。若业务对一致性有极端要求，仍应在业务侧做幂等校验（见后文故障实战）。

一个常见的误解是"内存锁没有用"——实际上在 SQLite/内存存储模式下，NeoTask 退化为单机任务池，此时 asyncio.Lock 级别的互斥已经足够，且省去了 Redis 依赖。锁的强弱永远要匹配部署形态，这正是抽象接口存在的意义。

这里有一个值得品的设计细节：Redis 的 SET key value NX EX 本身已经是一条原子命令，不需要 Lua 包装。团队在 RedisLock 类里虽然定义了 LUA_ACQUIRE 脚本，但 acquire() 实际走的是 redis-py 原生的 client.set(nx=True, ex=ttl)——效果相同、代码更少。这说明Lua 不是装饰品，只在"需要多条命令组合成事务"时才必要（比如下面的安全释放）。

owner 为什么用 uuid4() 而不是"节点 ID + 时间戳"？三个原因：

  1. 不可伪造的随机性：UUID 由本地生成、全局唯一，任何其他节点都无法猜测或构造出同样的值；

  2. 无需协调：节点 ID 方案需要先注册再取 ID，引入额外依赖，而 UUID 零协调；

  3. 释放校验的基础：锁值是释放时的"身份证"，随机化杜绝了"恰好撞值误删他人锁"的极端可能。

两个关键点：

  1. owner 按 key 取：RedisLock 用实例内的 self._owners 字典保存「key → owner token」映射，extend() 取的是这一把锁自己的 owner。因此同一个 RedisLock 实例并发持有多个锁时，各锁续期互不影响——不会出现"后 acquire 的锁覆盖前一把锁的 owner、导致先持有的锁续期失败"。

看门狗据此判断锁是否还在自己名下；"锁续期失败以后任务怎么办"后文专门推演。

为什么"先校验状态 PENDING，再加锁"？

WorkerPool 在加锁之前先检查任务状态，加锁成功后才把状态置为 RUNNING。这个顺序的妙处在于：

  • 状态机是第一道防线：任务一旦进入 RUNNING，其他节点即使抢到锁也会因"状态不是 PENDING"而跳过执行（pool.py 中 if task.status != TaskStatus.PENDING: return）；

  • 锁是第二道防线：防止两个节点几乎同时读到 PENDING 并同时开始执行——状态检查是"读后判断"，天然有竞态，锁把整个"检查-置位-执行"变成临界区。

锁与状态机是互补而非重复的关系：锁保证互斥，状态机保证"即使锁因异常丢失，错误的执行路径也会被状态挡住大半"。这也是任务调度锁与普通业务锁最大的不同——调度系统永远不信任单一机制。

看门狗机制：为长任务续命的守护协程

为什么需要看门狗：TTL 的两难

锁的 TTL 是一个经典的"电车难题"：

  • TTL 太短：任务稍微跑久一点锁就过期，另一个节点可能重新抢占同一任务 → 重复执行；

  • TTL 太长：持锁节点崩溃后，锁要等很久才释放 → 故障恢复慢、任务长时间无人接管。

看门狗（WatchDog）的思路是把 TTL 设短（30s），然后由守护协程在任务执行期间持续续期——既保证崩溃后快速自愈（最多等 30s），又保证正常长任务不会因 TTL 到期而中断。

为什么续期间隔是 TTL 的三分之一

interval = max(0.5, ttl * interval_ratio)，默认 interval_ratio = 0.3，即 TTL 30s 时每 10s 续期一次。为什么是 1/3 而不是 1/2 或 1/10？

  • 为什么不能太晚（> TTL/2）：如果续期间隔接近 TTL，一次网络抖动或 GC 停顿就可能让锁在两次续期之间过期——看门狗形同虚设；

  • 为什么不能太频繁（< TTL/10）：每次续期都是一次 Redis 往返，任务量大时是纯开销；

  • TTL/3 的经验依据：留出 2/3 的 TTL 作为"安全余量"，允许大约两次续期失败而不丢锁——30s 的锁允许约 20s 的连续故障窗口，对网络抖动足够宽容。

为什么看门狗"续期失败就停止"，而不是"疯狂重试"？

注意 _watchdog_loop 中：续期失败（extend 返回 False）→ 打 warning → self._running[key] = False → 退出循环。而普通异常（如 Redis 连接抖动抛异常）→ continue 继续尝试。

这个设计的意图是区分"锁丢了"与"网络抖了"：

  • extend 返回 False 意味着 Redis 明确告知"owner 不匹配或键不存在"——锁已经易主或消失，继续续期只会给别人的锁续命，必须立即停手；

  • 抛异常说明是瞬时网络问题，锁大概率还在，值得重试。

深入探讨：锁续期失败以后，任务怎么办？

这是本文最值得展开的问题，也是生产环境里真正会咬人的场景。分三个层次回答：

第一层：看门狗停了，任务本身会怎样？

看门狗停掉 ≠ 任务被中断。 在 v1.0.2 的 pool.py 中，看门狗与业务执行是两个独立的协程，看门狗退出循环只是不再续期，业务协程对锁丢失一无所知，会继续执行直到完成，然后在 finally 里照常调用 watchdog.stop() 与 release()。

这里暴露出一个设计取舍：锁丢失后，正在执行的任务是"立即中断"还是"跑完再说"？NeoTask 选择后者。原因是任务调度场景里，强制中断执行中的业务逻辑几乎总是更危险——协程可能正写一半数据库、正在调用第三方 API，贸然取消会造成半截状态。宁可让它跑完，把一致性交给状态机与业务幂等兜底。

第二层：什么情况下会真的出问题？

续期失败要真正造成"重复执行"，需要同时满足：

  1. 看门狗续期失败且锁过期；

  2. 任务被重新入队（如回收器判定孤儿、或人工重试）；

  3. 新节点抢占并执行时，任务状态尚未更新为终态（RUNNING/PENDING 都拦不住新执行——实际上 pool 只放行 PENDING，若任务仍 RUNNING，新节点会跳过；真正危险的是任务已 PENDING 且被重新入队，原节点还在跑）。

因此最危险的组合是：超时/孤儿回收把任务重新入队（状态重置为 PENDING）后，原节点还没跑完——此时新老两个节点都在执行同一任务，且状态机完全失效。这正是 reclaimer（worker/reclaimer.py）把任务重新入队时必须同时释放旧锁的原因，也是任务处理器必须幂等的根本理由。

第三层：多锁并发时续期的正确行为

如前面 RedisLock.extend 所述，extend 用 self._owners.get(key) 取该锁自己的 owner token，并以 LUA_EXTEND 脚本原子比对 + 续期——因此同一个 RedisLock 实例同时持有多个锁时，各锁续期互不干扰。默认 worker_concurrency > 1、多个长任务并发运行时，这个性质正是看门狗不被误停的前提。

时序上可以这样理解：

sequenceDiagram
    participant W1 as Worker-1
    participant W2 as Worker-2
    participant L as RedisLock(共享实例)
    participant R as Redis

    W1->>L: acquire(task:A) → owner=uuidA
    L->>R: SET lock:task:A uuidA NX EX 30
    W2->>L: acquire(task:B) → owner=uuidB
    L->>R: SET lock:task:B uuidB NX EX 30

    Note over L: self._owners = {A: uuidA, B: uuidB}

    W1->>L: WatchDog 续期 task:A
    L->>R: Lua: GET lock:task:A == uuidA → EXPIRE 30
    Note over L: 按 key 命中 uuidA → 续期成功

    W2->>L: WatchDog 续期 task:B
    L->>R: Lua: GET lock:task:B == uuidB → EXPIRE 30
    Note over L: 按 key 命中 uuidB → 续期成功

实操建议：extend 返回 False 只发生在"本实例已不是该 key 的持有者"——键被删除、TTL 过期后已被他人接管，或本实例从未 acquire 过该 key。若确实看到长任务的看门狗停止续期，排查方向是 owner 是否被外部清理（如 cleanup_by_owner）或锁 TTL 是否短于任务执行节奏：

  1. 调大 TTL（如 60s/120s），为长任务留出更宽的续期窗口；

  2. 确认没有运维脚本误删活锁（见后文"误删活锁"场景）；

  3. 业务侧保持幂等，作为最终防线（永远需要的习惯）。

僵尸锁扫描器：为什么"扫描清理"是必要的

即使有 TTL 兜底，真实世界仍会出现残留锁：时钟漂移、Redis 主从切换丢命令、release 因网络异常未送达而任务已结束……这些锁虽然最终会过期，但在过期前会阻塞同名任务的重新调度。LockScanner 就是为此存在的后台协程。

清理的判定策略是多信号交叉验证：TTL 已耗尽（ttl <= 0）、锁键不存在、或空闲时间超过阈值——避免误删"正在被看门狗正常续期"的活锁。这也是为什么扫描器与看门狗必须协同：扫描器只清理"持有者失联"的锁，活跃任务由看门狗持续续期，天然不会被扫到。

为什么 TTL 阈值默认 300s 而不是更激进

stale_ttl_threshold = 300 意味着"剩余 TTL 小于 300s 且空闲很久"才判僵尸。阈值太小的代价是误杀：网络分区时，活跃节点的看门狗可能暂时续期失败，若扫描器此时激进清理，会造成"锁被清 → 其他节点抢占 → 原节点还在执行"的重复执行事故。清理僵尸锁宁可慢，不可错——反正 TTL 兜底会释放，扫描器只是加速收敛，激进换不来正确性。

任务抢占与锁：为什么"出队"和"加锁"是分开的

这是最容易产生技术误解的地方：NeoTask 的批量抢占（Lua 出队）并不加锁。

抢占的真实原子操作

🔧 真实源码（v1.0.2，src/neotask/storage/redis.py，RedisQueueRepository 批量弹出脚本）：

ZRANGE + ZREM 在 Lua 中原子执行，保证同一任务只被一个节点取出——这是"抢占"层面的互斥。而分布式锁（SET NX EX lock:task:{id}）发生在 Worker 真正执行任务之前（见前文生命周期时序图）。

为什么不做成"出队即加锁"？

把"出队 + 加锁"合成一个 Lua 脚本在技术上完全可行（ZRANGE → SET NX → ZREM），但 NeoTask 刻意拆成两步，原因有三：

  1. 出队与执行的节奏不同：出队是批量动作（一次 pop N 个），执行是逐个动作。若出队即加锁，预取的 20 个任务就要同时持有 20 把锁——一旦节点在处理本地队列时崩溃，20 把锁同时残留，恢复时还要批量清理，放大了故障面；

  2. 本地队列缓冲层：预取机制先把任务放进节点本地队列，任务尚未开始执行。此时加锁毫无意义，只会提前占用 TTL；真正需要锁保护的是"开始执行"这个时刻；

  3. 锁的语义是"执行互斥"而非"分配互斥"：分配（出队）的互斥由 ZREM 原子性保证；执行的互斥由锁保证；两者边界清晰，各自的故障模型也简单。

flowchart LR
    subgraph Preempt["抢占阶段（分配互斥）"]
        A[Lua: ZRANGE + ZREM<br/>原子取出任务] --> B[任务进入节点本地队列]
    end

    subgraph Execute["执行阶段（执行互斥）"]
        C[Worker 取出任务] --> D[SET NX EX lock:task:{id}<br/>获取执行锁] --> E[RUNNING 执行]
    end

    B --> C

既然出队已经互斥，为什么执行前还要锁？

因为出队互斥只防"同时取出"，防不了"再次取出"：任务失败重试会重新入队、故障恢复会把孤儿任务重新入队、人工补偿可能重复提交。任务在队列里进出多次后，同一 task_id 完全可能在两个节点上"各自执行一轮"。执行锁 + PENDING 状态检查，就是为了挡住这些跨轮次的重复。

一句话总结设计哲学：队列负责"任务不重"，锁负责"执行不重"，状态机负责"结果不乱"。

Redis 集群（Cluster）注意事项

锁键 lock:task:{id}、任务键 task:{id}、队列键 queue:priority 属于不同业务键。在 Redis Cluster 下，Lua 脚本只能操作同一 slot 的键——NeoTask 的锁脚本与批量弹出脚本都只操作单键，天然兼容集群；但如果业务需要多键原子操作，应使用 hash tag（如 {task:123}:...）把相关键钉在同一 slot。请勿在集群模式下自行编写跨键 Lua 脚本。

故障场景实战

场景一：看门狗续期失败，任务还在跑

现象：长任务（>30s）执行期间，日志出现大量 Watchdog failed to renew lock for key: task:xxx, stopping；任务最终完成，但业务侧偶发重复处理。

定位步骤：

  1. 查日志确认续期失败是"返回 False"还是"抛异常"（前者=锁易主/owner 不匹配，后者=网络抖动）；

  2. 若任务并发高且共用一个 RedisLock 实例，确认锁实现按 key 校验 owner（见上文"第三层"），避免共享实例导致续期互相干扰；

  3. 用 redis-cli GET lock:task:xxx 对比 owner 与任务实际执行节点日志中的 acquire owner。

处理方案：

  • 临时：调大 lock_timeout（如 60s），为长任务留出更宽的续期窗口；

  • 排查：确认锁没有被外部脚本误删（cleanup_by_owner 等），锁 TTL 是否短于任务执行节奏；

  • 兜底：任务处理器实现幂等（以业务唯一键去重），这是任何调度框架都替代不了的最后防线。

场景二：节点宕机，锁与任务双双残留

现象：某节点被 kill -9，其上 RUNNING 任务在锁过期后未被及时接管，任务积压。

推演时间线：

sequenceDiagram
    participant N as 宕机节点
    participant R as Redis
    participant RC as Reclaimer(其他节点)

    N->>R: 持有 lock:task:A（TTL 30s） 任务 RUNNING
    Note over N: 节点进程被杀

    R-->>R: 看门狗消失，无续期
    Note over R: 30s 后锁自动过期
    RC->>R: 周期性扫描 RUNNING 任务
    RC->>RC: 判断执行节点失联 → 回收
    RC->>R: 状态重置 PENDING + 重新入队（带延迟）
    RC->>R: 释放旧锁（防新老并发）

处理方案：

  1. 确认 reclaimer 已启用（enable_orphan_reclaim=True、enable_auto_requeue=True）；

  2. 调低扫描间隔可加快接管，但注意回收与扫描都需要分布式锁保护，避免多个回收器同时处理同一任务；

  3. 恢复后核对死信/失败队列，确认无任务因超过最大重试次数被放弃。

场景三：误删活锁导致的重复执行

现象：运维手动执行 cleanup_by_owner 清理"故障节点"锁后，某任务被两个节点同时执行，产生脏数据。

根因：误判了节点状态——目标节点只是网络分区（心跳中断），并未真正宕机，它手里的锁还在被看门狗续期；运维强制删锁后，任务被其他节点抢占，而原节点"复活"后继续执行。

预防原则：

  • 删除前必须三重确认：心跳超时 + 锁空闲超时 + 任务无进度更新；

  • 优先用 cleanup_stale_locks(ttl_threshold)（自动判断空闲）而不是 cleanup_by_owner（人工指定）；

  • 处理流程遵守"先标记节点死亡 → 等宽限期 → 再清锁"的顺序，与故障恢复篇的节点状态机保持一致。

场景四：Redis 故障转移期间锁的短暂双主

现象：Redis 主从切换瞬间，两个节点几乎同时 SET NX 成功（旧主上的写入未同步到新主），锁互斥失效。

根因：Redis 主从复制是异步的，锁写入可能在新主上丢失。这是 Redis 分布式锁的固有边界（Redlock 也只是降低概率而非消除）。

处理方案：

  • 接受窗口：调度场景下双执行窗口通常为毫秒级，配合状态机（PENDING 检查）与业务幂等可完全消化；

  • 追求极致：为 Redis 开启 min-replicas-to-write 等强一致选项，或接受 Redlock 方案的额外复杂度；

  • 明确边界：NeoTask 的锁定位是"低成本防重"，不承诺线性一致；需要严格互斥的业务（如资金操作）应在业务事务内二次校验。

总结

NeoTask 的分布式锁是"轻量但分层"的设计范本，把分布式锁这一经典命题拆成了四个可独立演进的部件：

部件 职责 一句话设计理由
SET NX EX 原子获取 + 崩溃自愈 单条原子命令同时解决互斥与 TTL
Lua 释放/续期脚本 身份校验的原子化 杜绝"误删他人锁"这一分布式锁头号事故
WatchDog 长任务续期 把"短 TTL 快速自愈"与"长任务不断锁"这对矛盾解耦
LockScanner / 状态机 残留兜底 锁不是银弹，异常要靠周期扫描与状态机收敛

贯穿始终的设计哲学是**“分层防御、各司其职”**：出队互斥防止任务被重复取出，执行锁防止任务被并发执行，PENDING/RUNNING 状态机挡住异常路径的重入，回收器处理节点故障的遗留，看门狗在正常路径上为长任务续命。没有任何一层假设其他层一定可靠——这也是分布式系统设计的通用答案。

RedisLock.extend 采用按 key 的 owner 校验 + LUA_EXTEND 原子脚本：同一个锁实例并发持有多个锁时，各锁续期互不干扰，长任务 + 高并发这一最需要看门狗的场景反而是它最稳的场景。理解这一点，是正确使用 NeoTask 分布式锁的基础。

锁能保证的是"不重不漏尽量少靠运气"，而真正让业务高枕无忧的，永远是幂等的任务处理器 + 可观测的锁状态 + 清晰的故障恢复流程。
