PenShot 实战复盘：《深夜来电》七元素剧本的六阶段链路与质量分对照

系列前文《快速开始》介绍了安装与最小可运行示例。本文换一个角度：把一个短剧本交给 PenShot，然后把每一次运行的落盘产物拆开，逐阶段对照，看每个环节到底做了什么、留下什么、哪里出了问题，以及一份只有 19 秒的剧本如何走出一条 5.0 分到 90.0 分的质量曲线。

数据口径说明：本文所有数字来自本地数据目录 data/output/SN1780745829485283341820/ 下两次真实任务的落盘文件：TSK17807426061109503223（2026-06-11 运行，简称运行 1）与 TSK17807426072316085190（2026-07-23 运行，简称运行 2）。该目录不随源码发布，但产物字段可对照源码核验；涉及机制解释的部分单独标注源码位置。

相关链接：GitHub | 官网 | 文档 （架构设计 · 召回策略 · MCP Server · 一致性策略 · RAG 增强）

一、案例剧本与两次运行

1.1 《深夜来电》：七个元素的极简短剧

《深夜来电》是一个约 19 秒的独幕短剧：深夜 11 点，城市公寓客厅窗外大雨滂沱，林然裹着旧羊毛毯蜷在沙发里，一通显示未知号码的电话打来，电话那头是多年未见的旧识陈默。全剧只有三句台词与一次情绪转折，属于典型的情绪驱动型短剧。

解析器把它拆成 7 个元素（1 个场景 + 3 个动作 + 3 段对话），两个角色：林然（主角，视觉出场）与陈默（配角，只以电话声音出场——记住这个设定，后文质量审查的主要违规就来自它）：

元素 类型 时长 情绪 内容摘要
elem_001 scene 5s calm 深夜 11 点客厅，大雨、黑白老电影、半杯凉茶、旧相册，林然蜷在沙发
elem_002 action 3s anxious 手机震动显示未知号码，指尖悬停后按下接听
elem_003 dialogue 2s tense 电话那头：是我。
elem_004 action 2s shock 林然手指收紧、指节泛白、呼吸停滞
elem_005 dialogue 2s hesitant ……陈默？你还好吗？
elem_006 dialogue 2s resigned 我回来了。
elem_007 action 3s emotional 猛然坐直、瞳孔收缩、毛毯从肩头滑落

7 个元素时长合计 19.0 秒，与解析产物 stats.total_duration = 19 一致。

1.2 两次运行的信息与端到端耗时

同一个 script_id（SN1780745829485283341820）在 6 周内跑了两次，恰好构成一组对照：

项 运行 1（06-11） 运行 2（07-23）
task_id TSK17807426061109503223 TSK17807426072316085190
产物时间窗 09:51:19 → 09:53:05 16:09:00 → 16:10:42
端到端耗时 约 106 秒 约 102 秒
终审判定 major_issues / 5.0 分 minor_issues / 90.0 分

18 倍的终审分数差，来自同一份剧本、同一套六阶段链路。这是本文后半段要拆开的核心问题。

二、六阶段链路实录

产物目录下每个阶段都有独立的落盘文件，逐份对照如下。六个阶段的保存时间戳也记录在文件 metadata 中，可以还原出阶段级耗时结构。

2.1 阶段一：剧本解析

script_parser_result.json 输出的 stats 在两次运行中完全一致：

指标 运行 1 运行 2
元素总数 7 7
总时长 19.0s 19.0s
对话 / 动作数 3 / 3 3 / 3
完整度评分 0.87 0.87
解析置信度（综合） 0.76 0.76
场景 / 角色 / 对话 / 动作 0.6 / 0.75 / 0.67 / 1.0 0.6 / 0.75 / 0.67 / 1.0
解析尝试次数 1 1

两次运行的统计口径完全一致，但细节文案仍有可观测的波动：陈默的角色描述，运行 1 是 声音沙哑，低沉，身份为林然的旧识（3 个 key_traits），运行 2 是 沙哑男声，身份为林然的旧识（2 个 key_traits）；场景 weather 字段一次是 大雨、一次是 雨天。LLM 解析在结构层稳定、在措辞层波动的特性，在这两份产物里体现得很清楚。

另一个值得注意的分布：动作维度置信度 1.0、对话 0.67、场景仅 0.6。结构化程度越高的信息（谁做了什么）提取越稳，而场景包含时间、光线、氛围等需要推断的隐式信息，最容易出现偏差——这也意味着人工复核的优先级应该放在场景标注上。

2.2 阶段二：镜头拆分

shot_segmenter_result.json 的两次结果都是 7 个镜头，但景别与时长分配并不相同：

镜头 运行 1 景别 / 时长 运行 2 景别 / 时长
shot_001 wide_shot / 4.63s wide_shot / 4.21s
shot_002 medium_shot / 2.0s medium_shot / 2.0s
shot_003 close_up / 3.0s close_up / 3.0s
shot_004 extreme_close_up / 2.36s close_up / 4.5s
shot_005 close_up / 4.5s close_up / 4.8s
shot_006 close_up / 3.0s close_up / 3.0s
shot_007 medium_shot / 2.4s medium_shot / 2.4s
合计 21.89s（均值 3.13s） 23.91s（均值 3.42s）

分布上两次都是 1 全景 + 2 中景 + 若干特写 的框架：开场用全景建立空间，情绪推进段全部使用特写。差异出现在中段——运行 1 用了 extreme_close_up（极特写）加一个 2.36 秒的短镜头刻画手指收紧的动作，运行 2 则是 4.5 秒的 close_up。这段是林然接听电话后的情绪爆发点，两次运行给出了不同强度的视觉方案：一次用更近的景别与更短的时长制造压迫感，一次用更长的凝视给情绪留白。两种都说得通，属于 LLM 时长估算与景别选择的正常波动区间。

2.3 阶段三：视频分段

video_splitter_result.json 的 metadata 显示，两次运行的分段方式完全一致：

这里有一个容易误读的组合：cutter_type 是 LLMVideoSplitter、split_method 是 llm，但 ai_split_count = 0、rule_split_count = 7。原因是分割器的分流阈值——只有时长超过 5.5 秒的镜头才会交给 LLM 做语义分割，其余镜头按规则直通（源码 rule_video_splitter.py 中的 duration_split_threshold，默认 5.5）。本剧最长的镜头是 4.8 秒，7 个镜头全部落在直通区间，所以 7 个镜头与 7 个片段一一对应，两次运行都没有触发 AI 分割。

这解释了为什么小剧本的耗时结构里，分段阶段几乎不花时间（两次运行该阶段都在 5 秒上下）：没有 LLM 调用，纯规则计算。

分段产物里每个片段还携带了溯源信息与连续性备注，以运行 2 的 frag_001 为例：

element_ids 把片段与解析元素挂上了钩，start_time 从 0 开始严格递推——这两项保证了哪怕后续手工微调片段，也能追溯到原始剧本位置。

2.4 阶段四：指令转换

prompt_converter_result.json 记录了每个片段的视觉提示词、负面提示词与音频包。这是成本最高、也是两次运行差异最大的阶段。以 frag_001 为例：

运行 1 的提示词为纯英文：

运行 2 改为 英文 + 中文回译 的双语结构：

每个片段同时携带音频包 audio，字段结构与视觉提示词同构：

字段 运行 2 的 frag_001 取值
audio_id audio_001
prompt 双语的雨声 / 雷声 / 电视静电 / 沙发吱嘎 / 呼吸声描述
model_type AudioLDM_3（对话片段自动切换 XTTSv2）
voice_type narration
voice_character 对话片段会填具体角色名（如 frag_002 对应 Lin Ran）
negative_prompt noisy, low quality, distorted, robotic, bad audio

转换阶段两次运行分别耗时约 39 秒与 36 秒（同为 7 个片段），单片段约 5 秒——与《快速开始》中 13 片段示例的结论一致：该阶段耗时接近 片段数 × 单次 LLM 调用延迟。

2.5 阶段五：质量审查

quality_auditor_result.json 是两次运行分歧最大的产物。先看两边相同的部分——5 项规则检查全部通过：

再看两边不同的部分——违规清单：

# 运行 1：8 条违规 运行 2：4 条违规
1 major · frag_006：出现 Chen Mo 的声音，但该角色从未在视觉上出现 warning · frag_005：Chen Mo? Are you okay? 缺少对方回应
2 major · frag_007：突然切换黑白模式，与此前 ETERNA 彩色风格不一致 info · frag_001：半杯茶道具后续未再提及
3 moderate · frag_006：台词出现在极端特写中，未明确说话人 info · frag_002：打开的相册后续未保持连续性
4 moderate · frag_007：坐直动作在 frag_006 中无铺垫，动作跳跃 warning ·（阶段级，无片段归属）
5 moderate · frag_004：与其前一片段的特写景别和动作顺序矛盾
6 warning · frag_004：提示词以省略号开头，疑似截断
7 warning · frag_005：情感描述被省略号截断
8 warning ·（阶段级，无片段归属）

运行 1 的结论是 发现 2 个主要问题、3 个中度问题、3 个警告，运行 2 是 发现 2 个警告。结合权重表：critical 扣 40 分、major 扣 25 分、moderate 扣 10 分、warning 扣 5 分、info 不扣分（从 100 分起扣，下限 0）——两边的最终分数可以直接核算出来：

  • 运行 1：100 − (2×25 + 3×10 + 3×5) = 100 − 95 = 5.0 分

  • 运行 2：100 − (2×5 + 2×0) = 100 − 10 = 90.0 分

两边产物里的 score 字段与按权重表手算的结果完全一致。质量分不是黑盒玄学，而是一张可复盘的扣分账单。

2.6 阶段六：连续性检查

continuity_report.json 的两次结果：

项 运行 1 运行 2
连续性问题数 1（moderate） 0
continuity_retry_count 1 1
continuity_passed false false

运行 1 报告了 1 个 moderate 级问题并触发了 1 次重试；运行 2 报告 0 个问题——但 continuity_passed 依然是 false。与此同时，片段级产物里的 continuity_notes.continuity_check 在运行 2 中却是 passed。也就是说：片段级标记与报告级布尔值在语义上没有打通，0 问题的情况下报告级字段仍固定为 false。这是一个产物级的真实边界，排查连续性状态时不要只看 continuity_passed，要结合问题数一起判断。

三、5.0 分与 90.0 分的差异从哪里来

3.1 提示词产出质量的代际差异

把两次运行的违规清单对齐看，运行 1 的问题集中在三类，且都在运行 2 中消失或降级：

  • 截断类（3 条 warning→ 0 条）：运行 1 的提示词出现以省略号开头、情感描述被截断的情况，运行 2 未复现；

  • 风格类（1 条 major → 0 条）：运行 1 的 frag_007 意外混入黑白模式描述，与其自身 style 字段声明的 ETERNA 彩色风格冲突；运行 2 的 7 个片段风格字段统一；

  • 动作跳跃类（1 条 moderate → 0 条）：运行 1 的 frag_007 坐直动作缺少铺垫；运行 2 通过更长的前置镜头（shot_004 由 2.36 秒加长到 4.5 秒）缓解了节奏跳跃。

3.2 提示词双语化带来的可审查性

运行 2 的提示词开始输出中文回译（见 2.4 节），这不是显示层的装饰——质量审查器与人工复核都需要读懂英文提示词里到底写了什么。运行 1 的英文提示词在审查日志里被指出以省略号开头时，人很难第一眼判断截断处的语义，中文回译让这类结构性问题变得直观。审查质量与产出可读性互相促进，这是运行 2 违规数量大幅下降的重要原因之一。

3.3 两次运行没有变的东西

对照两组产物也要说清楚哪些环节不是分数差异的来源：

  • 解析统计完全一致（7 元素 / 19 秒 / 相同置信度分布）；

  • 分段策略完全一致（规则直通 7 个片段，未触发 LLM 分割）；

  • 角色设定未变（陈默始终只以声音出场）——运行 1 的视觉未出场 major 违规在运行 2 依然存在，只是降级为 warning 级的对话不完整提示。

换句话说，分数提升主要来自提示词生成质量的提升，而不是链路机制的变化。

四、从产物里挖出来的五个坑

以下每一条都能在产物文件里找到对应证据，属于跑通链路之后才会遇到的坑。

坑 1：5 项检查全过，不代表没有质量问题

两次运行的 stats.pass_rate 都是 1.0（5/5 通过），但违规清单分别是 8 条和 4 条。规则层检查的是时长越界、提示词为空、模型名不受支持这类硬性条件；语义层问题（角色未出场、风格漂移、动作跳跃）只能由 LLM 审查发现。看到检查全绿就放行，会把语义问题带到生成环节。

坑 2：质量分低不等于整条链路失败

运行 1 只有 5.0 分，但它的解析、分段、提示词结构、音频包全部产出正常，连续性也只报告了 1 个 moderate 问题。低分来自提示词文本层的瑕疵，而不是流程断裂。处理姿势应该是定向修复违规项，而不是推翻重跑——重跑后新的 LLM 采样可能引入新的问题。

坑 3：连续性状态要同时看两级字段

continuity_passed = false 在两次运行中都出现，但运行 2 的问题数是 0、片段级标记是 passed。单看报告级布尔值会误判为连续性故障。判断顺序建议：先看问题清单与严重度，再看片段级备注，最后才参考报告级布尔值。

坑 4：道具与角色的跨片段追踪是违规高发区

运行 1 的 8 条违规里，5 条与跨片段一致性有关（声音角色未视觉出场、风格切换、动作顺序矛盾、景别跳跃）；运行 2 残留的 4 条里有 2 条是道具追踪（半杯茶、相册）。景别、风格、道具这三类信息在片段间传递时最容易丢失，人工复核时值得优先扫一遍。

坑 5：阶段统计文本可能被摘要污染

打开运行 1 的 stage_statistics.json 会看到一件怪事：四个阶段的统计文本完全相同，都是 解析脚本阶段共尝试 1 次……总耗时 19.0 秒——这是解析阶段的摘要被 LLM 复用覆盖到了所有阶段字段。同样的现象也出现在 repair_history.json 与 quality_report.json 的 audit_history 里。这是产物生成链路的真实缺陷：阶段级文本可能互相污染。需要精确的阶段数据时，以各阶段独立产物文件（如 shot_segmenter_result.json、video_splitter_result.json）为准，不要依赖汇总报告里的文本字段。

五、总结

把两次运行放在一起看，《深夜来电》的复盘给出三条可复用的结论：

  1. 链路是稳的：解析统计、分段策略、角色设定在两次运行间保持一致，LLM 波动主要发生在措辞与时长估算这类自由度较高的环节；

  2. 质量分是可核算的：100 分起步、按 critical 40 / major 25 / moderate 10 / warning 5 逐项扣减，产物里的分数与手算完全一致，可以用它定位问题而不是只看数字高低；

  3. 产物要分两级读：规则检查与语义审查、片段级备注与报告级状态、独立产物与汇总报告，这三组概念各自有独立的可信度层级，混读会把正常输出误判成故障。

如果你正在把 PenShot 接入自己的生产链路，建议先拿一个小剧本跑两次，对照本文的产物结构把每个文件读一遍——读懂产物，比读懂文档更能预判它上线后的行为。
