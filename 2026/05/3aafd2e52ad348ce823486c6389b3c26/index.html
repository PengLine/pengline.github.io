一、为什么任务调度要选无主架构

1.1 主从架构的隐性成本

分布式系统控制平面常见的方案是主从（leader-follower）：一个主节点负责任务分配与调度决策，从节点执行。这套模型的概念足够直观，但随之而来一长串经典难题：

问题 说明
领导者选举 谁来当主？需要共识算法（Raft/Paxos 或依赖 etcd/ZooKeeper）
脑裂（Split-brain） 网络分区导致两个"主"同时决策，任务被双发
心跳调优 超时太短误杀主节点触发频繁选举，太长则故障转移慢
故障转移期间降级 换主窗口内新任务可能无人受理

主从不是不能用，而是它把"正确性"绑定在一个动态选出的单点上——为了实现高可用，先要解决一个比业务更难的分布式一致性问题。任务调度场景的值（吞吐、任务完成率）与这套复杂度并不相称。

1.2 无主架构：让存储层当"主"

flowchart TB
    subgraph Decentralized["去中心化（NeoTask 选择）"]
        direction TB
        N1[节点 A] --> R[(Redis<br/>共享存储)]
        N2[节点 B] --> R
        N3[节点 C] --> R
        N1 -.->|零节点间通信| N2
        N2 -.->|零节点间通信| N3
    end

    subgraph Centralized["主从（放弃的方案）"]
        direction TB
        M[主节点<br/>选举产生] --> S1[从节点 1]
        M --> S2[从节点 2]
        M --> S3[从节点 3]
        E[选举/脑裂/故障转移] -.->|复杂度| M
    end

为什么这么设计：把"谁是主"的问题外包给 Redis，而不是自己实现共识。 Redis 本身就是单线程执行命令的强一致存储——多个节点对同一个 key 的原子操作天然串行。节点间不需要互相通信、不需要选举，因为所有节点在与同一个"存储主"对话。代价是 Redis 成为事实上的单点（可用性靠 Redis 自身的 Sentinel/Cluster 保障，见第十一节）。

这套取舍的本质是用基础设施换架构：

维度 主从 NeoTask 无主
正确性保障 选举 + 租约 + 脑裂防护 Redis 原子原语（ZSET/Lua/SET NX）
新增节点 发现 + 数据迁移 注册 + 抢占（零迁移）
节点故障 选举新主（秒级~分钟级） 锁/任务 TTL 自然过期（回收器接管）
运维心智 高 低（但依赖 Redis 高可用）

二、整体架构：存储层是唯一的事实中心

NeoTask 的去中心化架构在逻辑上分为三层，但必须强调：节点层之间不存在任何直接通信通道，所有协调都发生在存储层。

graph TB
    subgraph NodeLayer["节点层（对等，无主）"]
        N1[节点 A<br/>完整处理单元]
        N2[节点 B]
        N3[节点 C]
    end

    subgraph RedisLayer["存储层 - Redis（唯一事实中心）"]
        T[(task:{id}<br/>String JSON 任务详情)]
        Q[(queue:priority<br/>ZSET 优先级队列)]
        DQ[(queue:delayed<br/>ZSET 延时队列)]
        L[(lock:task:{id}<br/>String 执行锁)]
        S[(status:{值}<br/>SET 状态索引)]
        R[(neotask:node:{id}<br/>Hash 节点注册)]
        NS[(neotask:nodes<br/>SET 节点集合)]
    end

    subgraph ObserverLayer["观测/恢复层"]
        REC[TaskReclaimer 回收器]
        WDT[WatchDog 锁续期]
        HC[健康检查]
    end

    N1 -->|ZRANGE+ZREM 抢占| Q
    N2 -->|ZRANGE+ZREM 抢占| Q
    N3 -->|ZRANGE+ZREM 抢占| Q
    N1 -->|SET NX EX 加锁| L
    N2 -->|SET NX EX 加锁| L
    N1 -->|HSET 心跳| R
    N2 -->|HSET 心跳| R

    Q -->|扫描超时/孤儿| REC
    L -->|续期| WDT
    S -->|扫描| REC

注意图中的 Redis key 都是 v1.0.2 的真实命名：任务详情是 String + JSON（RedisTaskRepository.save），锁是 lock:task:{task_id}，节点注册是 neotask:node:{node_id} + 集合 neotask:nodes。更多细节见 分布式锁 一文。

为什么这么设计：任务调度的"状态"必须能被任何节点在任何时刻读取。 若节点各自维护任务归属，宕机即丢状态；全部放 Redis，任何节点崩溃都只损失"正在跑的协程"，不损失任务的真实状态。观测层（回收器、看门狗）因此得以独立于节点运行——这正是故障恢复的基础。

三、对等节点：每个节点都是完整的处理单元

所有节点进程内跑着同一套组件（v1.0.2 的 TaskPool 即节点的完整化身）。从源码看，一个节点的内部结构如下（组件名为真实类名）：

graph TB
    subgraph NodeInternal["节点（TaskPool 进程）内部"]
        subgraph API["提交面"]
            DISP[TaskDispatcher<br/>提交分发]
            LCM[TaskLifecycleManager<br/>状态机]
        end

        subgraph Exec["执行面"]
            WPOOL[WorkerPool<br/>worker 协程池]
            PSCH[QueueScheduler<br/>队列调度]
            PREF[TaskPrefetcher<br/>预取器]
            WDT[WatchDog<br/>锁续期]
        end

        subgraph Infra["分布式基础设施"]
            NM[NodeManager<br/>注册/心跳]
            HB[HeartbeatManager<br/>心跳/死节点回收]
            REC[TaskReclaimer<br/>超时/孤儿回收]
            COORD[Coordinator<br/>预留]
        end

        DISP --> LCM --> PSCH
        PSCH --> PREF --> WPOOL
        WPOOL --> WDT
        NM --> R[(Redis)]
        HB --> R
        REC --> R
        PSCH --> R
    end

为什么这么设计：节点对等 + 组件齐备 = 任意节点可随时接管任意任务。

关键洞察：节点之间不是"分工"关系而是"冗余"关系——每个节点都能处理每个任务，重复的危险交给锁与状态机消除，而不是靠"任务只发给特定节点"来回避。这样扩容只是增加冗余度，缩容只是减少冗余度，不需要数据迁移。

四、抢占式消费的真实链路

4.1 三个阶段的真实代码路径

网上的去中心化教程常画一条"提交→原子抢占（出队+加锁）→执行"的顺滑流水线。v1.0.2 的真实链路要微妙得多：

sequenceDiagram
    participant Client as 客户端
    participant NodeX as 任意节点
    participant Redis as Redis
    participant Worker as 另一个节点的 Worker

    Note over Client,Redis: 阶段一：提交（任意节点）
    Client->>NodeX: submit(data)
    NodeX->>Redis: SET task:{id} JSON  ← String 类型，非 Hash
    NodeX->>Redis: ZADD queue:priority {id} 分数
    NodeX-->>Client: task_id

    Note over Redis,Worker: 阶段二：出队（所有节点都在做）
    Worker->>Redis: EVAL pop Lua
    Redis->>Redis: ZRANGE queue 0 count-1 + ZREM（原子，但只动队列）
    Redis-->>Worker: [task_ids]（此刻任务无主！）

    Note over Worker,Redis: 阶段三：执行前加锁（拿到任务之后）
    Worker->>Redis: SET lock:task:{id} uuid NX EX 30
    alt 加锁成功
        Worker->>Redis: HSET task:{id} status RUNNING（经状态机）
        Worker->>Worker: 启动 WatchDog 续期
        Worker->>Worker: 执行业务
    else 加锁失败（被抢/锁残留）
        Worker->>Redis: ZADD queue:priority 重新入队（仅当仍 PENDING）
        Worker->>Worker: 放弃，取下一个
    end

五、出队原子 ≠ 执行原子：核心设计

5.1 为什么不在 Lua 里顺便加锁？

有一种常见误解是把抢占描述为"Lua 原子完成出队 + SET NX 加锁"。v1.0.2 的真实设计不是这样，而且这是有意为之的取舍，理由有三：

1. 出队与执行的语义目标不同。 出队要保证的是"任务只被取出一次"（队列完整性）；加锁要保证的是"任务只被执行一次"（执行互斥）。把两者焊进一个 Lua 脚本，意味着"取出来"与"锁上"必须同时成功——如果锁 SET NX 失败（锁残留），脚本要么把任务放回队列（多一次往返）、要么返回空（白白出队）。在 Redis 脚本里处理这种分支，脚本会越来越像业务代码，失去"最小原子操作"的可维护性。

2. 锁可能失败，队列操作不能回滚。 出队一旦发生就必须有去处。若脚本"出队+加锁"中加锁因 TTL 过期残留失败，脚本已 ZREM 的任务还得 ZADD 回去——出现锁过期抖动时，任务会在两个节点之间来回踢皮球（乒乓效应）。

3. 职责分离让锁的机制可以独立演进。 看门狗续期、锁扫描清理、锁 TTL 调整，这些只跟"锁"有关；批量出队、延时到期迁移，这些只跟"队列"有关。两者解耦后，分布式锁 的看门狗与 预取机制 的批量拉取才能各自独立优化。

5.2 那"无主窗口"的重复执行怎么防？

靠三道防线而不是一次原子操作：

防线 机制 源码位置 防什么
① 状态闸门 执行前检查任务仍是 PENDING，否则放弃 _execute_task 已被别的节点置 RUNNING 的任务
② 分布式锁 SET lock:task:{id} NX EX 30 + 看门狗续期 _execute_task + WatchDog 同一任务被两个节点同时执行
③ 幂等重入 加锁失败的节点把任务放回队列（仅 PENDING 时） _execute_task 任务因锁竞争被"丢弃"

为什么这么设计（三防线）：分布式系统里"检查-执行"之间永远存在竞态窗口，与其追求一个覆盖全链路的超级原子操作（复杂、脆弱、难调试），不如接受窗口存在，用状态机 + 锁 + 幂等分别堵住窗口的每个出口。代价是极端情况下（进程在置 RUNNING 后、释放锁前崩溃）任务会短暂地"既不在队列也不可执行"——这正是回收器扫描锁 TTL 的用武之地，详见 故障恢复。

6.2 心跳与锁的 TTL 参数互相咬合

参数 值 含义
心跳间隔 5s 活跃节点每 5 秒刷一次
判死阈值 20s 4 个心跳周期没刷 = 判死
节点键 TTL 40s 2×阈值，防 Redis 键堆积
任务锁 TTL 30s（默认） 看门狗每 9s 续期（max(0.5, TTL × 0.3)）
回收间隔 30s（默认） 回收器扫描周期

参数关系：判死阈值 20s > 锁续期间隔 9s，且任务锁 TTL 30s > 心跳阈值 20s。这不是巧合——它保证"节点心跳还在"时锁一定不会过期（还能续期），而"节点真死了"之后最多 30s 锁就过期、任务可被回收。

七、为什么两态就够了：TTL 判活的哲学

7.1 三态模型：ACTIVE / STOPPED / FAILED

v1.0.2 的 NodeStatus 只有 ACTIVE / STOPPED / FAILED 三态，没有 SUSPECT（可疑）态；_health_check_loop 里还留着 # TODO: 处理故障节点。判活只有一个动作：读 last_heartbeat 与 now 比大小。也就是说，运行期虽然区分"优雅停（STOPPED）“与"判死（FAILED）”，但对消费者而言节点只有"活着、能被抢占同一队列"和"死了、任务需回收"两种有效语义——这正是标题所说"两态就够了"的含义。

为什么可以这么"糙"？因为节点故障检测在这里不是正确性依赖：

  • 任务不会丢：节点死后，它持有的锁最多 30s 过期，任务被回收器重新入队；

  • 任务不会重：节点活着但网络抖动，锁还在续期，其他人抢不到；

  • 即使误判一个活节点为死，代价也只是"提前回收"，而回收动作本身有锁保护，不会真把活任务抢走（回收前要 acquire 同一把锁）。

也就是说：判活只是优化信号（早点知道谁死了可以早点回收），不是正确性闸门。真正兜底正确性的是锁与任务状态机。既然如此，一个 20s 阈值就够——把 gossip 级别的怀疑-确认机制（φ 探测器、宽限期）留给需要"强一致视图"的系统（如分布式数据库选主），调度器不需要。

为什么这么设计：系统能容忍"慢回收"，但不能容忍"错回收"。 慢回收只是延迟几十秒，错回收（把活节点的任务重新入队）会导致双执行。所以判死逻辑宁可保守地靠 TTL，也不引入任何"推定死亡"的激进路径。

7.2 优雅退出与崩溃退出的区别

退出方式 表现 Redis 侧 任务影响
优雅退出 shutdown() → 等队列排空 → unregister() status=stopped，键 60s 过期，移出节点集合 无丢失，锁全部正常释放
崩溃/断电 无任何动作 status 仍是 active，心跳停更，20s 后判死、40s 键过期 锁 30s 内过期，任务被回收

优雅退出的关键在 stop() 中 wait_until_empty——先停止接收新任务并等本地队列清空，再注销。先断供给、再断身份，避免"我明明还在收尾，别人却以为我死了"。

八、两套节点管理实现：NodeManager 与 HeartbeatManager

v1.0.2 源码里存在两套节点管理实现，这是阅读源码时必须知道的现实。二者的关键差别不在"格式之争"，而在职责侧重：

维度 NodeManager（distributed/node.py） HeartbeatManager（core/heartbeat.py）
节点键 neotask:node:{id} neotask:node:{id}（共用）
节点集合 neotask:nodes neotask:nodes（共用）
心跳配置 5s / 超时 20s 由 HeartbeatConfig 配置（interval/timeout）
任务状态读写 经 TaskRepository 经 TaskRepository（不直接操作 Redis 任务键）
死节点任务回收 无（回收交给 TaskReclaimer） 自带 _check_and_reclaim_dead_nodes

两套实现不是"各写各的"。 HeartbeatManager 刻意采用与 NodeManager 一致的键布局（NODE_KEY_PREFIX = "neotask:node:" / NODES_SET_KEY = "neotask:nodes"），因此二者读写同一批注册键、互相可见，不会各自维护一套节点视图。回收任务时 HeartbeatManager 也从 TaskRepository.list_by_status(RUNNING) 读任务，再按 task.node_id == 死亡节点 过滤——这条路径对 memory / sqlite / redis 三种后端都成立，不会出现"以不兼容格式读写同一批 key"的问题。

实践启示：

  1. 两套实现同时在跑，回收能力有重叠：TaskReclaimer 负责超时/孤儿回收，HeartbeatManager 负责"归属已死节点"的任务回收。排障时要两份日志都看；

  2. HeartbeatManager 通过 TaskRepository 访问任务状态，而非直接操作 Redis 键——这保证它不会与存储后端的任务格式脱节；

  3. 生产排障时若发现"死节点任务迟迟不回收"，除回收器外，还要确认 HeartbeatManager 的监控循环是否有正常上报 get_stats()。

9.2 设计取舍：为什么预留而不接入

flowchart LR
    subgraph Today["v1.0.2 现状（shared）"]
        A[submit] --> B[TaskDispatcher] --> C[(queue:priority)] --> D[各节点自由抢占]
    end
    subgraph Reserved["为分区/亲和预留的接口"]
        E[Coordinator.distribute_task_to_node] --> F[记录 neotask:node_task:{id}]
        E --> G[仍入共享队列]
        H[affinity 记录] --> I[neotask:affinity:{id}]
    end
    subgraph Future["将来（partitioned）"]
        J[按 node_id/affinity 定向分发] --> K[节点专属队列]
    end

为什么这么设计：把"路由能力"与"默认无路由"做成同一个类的两面。 无主架构的价值主张是"消费者自取，无需路由"——一旦引入定向分发（分区模式、节点亲和），就重新引入了"谁来路由"的问题。NeoTask 的策略是：

  1. 默认路径不经过协调器——让最简架构保持最简（零路由代码进入主链路）；

  2. 协调器作为可插拔门面预留在侧——将来要分区模式时，把 dispatcher.push 换成 coordinator.distribute_task_to_node 即可，节点专属队列 + 定向分发的原语（neotask:node_task:{id}）已经备好；

  3. 需要定向分发/亲和性的用户可以手动调用 Coordinator API（distribute_task_to_node 等原语已实现），但它默认不参与主链路，rebalance() 与 handle_node_failure() 目前仍是 pass 占位（源码中标注 # TODO）。

对读者的提示：看到架构图里有、而代码主链路没有的组件，先确认它的"接入点"，再看它的"实现"。 Coordinator 属于"已预留、未接入"这一类；任务编排 一文中的 DAG 引擎则更进一步——它目前仍是路线图规划，源码中尚无对应模块。

十、水平扩展：负载如何自然分配

10.1 为什么"谁快谁多干"能自动成立

无主系统的负载均衡不靠调度器分配，而靠队列水位差自然形成：

flowchart TB
    subgraph NodeA["节点 A（处理快）"]
        A1[本地队列空得快] --> A2[频繁触发批量抢占] --> A3[拿到更多任务]
    end
    subgraph NodeB["节点 B（处理慢）"]
        B1[本地队列积压] --> B2[达到高水位暂停抢占] --> B3[拿不到新任务]
    end
    subgraph Queue["共享队列"]
        Q[queue:priority]
    end
    A2 --> Q
    B2 -.->|暂停| Q

每个节点的预取循环以本地队列水位为准（低于低水位拉一批、高于高水位暂停）——于是处理快的节点队列总是先空、总是先抢，处理慢的节点自然少抢。系统吞吐量由所有节点的消费速率之和决定，任何单节点都不是瓶颈；新节点注册后立刻加入抢占，无需重新分片、无需迁移存量任务（存量任务在共享队列里，谁抢到算谁的）。

10.2 线性扩展的边界条件

"吞吐随节点线性增长"有两个隐含前提，缺一不可：

  1. Redis 不是瓶颈——出队/加锁/心跳都集中在 Redis，节点多了 Redis 命令量线性上涨（单实例 Redis 约 10 万级命令/秒，抢占频率要按 节点数 × 每节点 QPS 估算）；

  2. 任务可并行——同一任务无写冲突（否则要靠锁串行化，扩展收益被锁竞争吃掉）。

实践上，达到这两个边界前更早出现的通常是：锁竞争（热点任务）、心跳风暴（数百节点同时 5s 一次 HSET 尚可，但回收器扫描是全量 smembers + 逐节点 hgetall，节点数上千时单次扫描变慢）。

十一、分区容错：什么能扛，什么不能扛

graph TB
    subgraph Case1["情况一：节点 ↔ Redis 断连"]
        N[节点] -.-x|断连| R[(Redis)]
        N -->|本地队列还能执行已取任务| LOCAL[已取任务继续跑]
        N -->|新任务/心跳/续期全部失败| LOST[锁 30s 后过期<br/>看门狗停摆]
        LOST --> REC[其他节点回收重跑]
    end

    subgraph Case2["情况二：Redis 自身不可用"]
        R2[(Redis)] -.-x|宕机/分区| ALL[所有节点失去队列与状态]
        ALL --> DOWN[全系统停摆<br/>无任务可抢、无状态可写]
    end

结论一：单节点失联 = 局部自愈。 节点与 Redis 断连时：已取出（出队成功）的任务仍能在本地执行完成（任务数据在出队后由 task:{id} 读取，若断连发生在读任务之后）；但锁续期会失败，30s 后锁过期，若任务还没执行完，其他节点可能重新抢占——这时看门狗续期失败的处理策略就至关重要（详见 分布式锁 的"锁续期失败后任务怎么办"）。

结论二：Redis 不可用 = 全系统停摆（这是无主架构的固有代价）。 去中心化把一致性负担外包给了 Redis，也把可用性押在了 Redis 上。节点层的无主不改变存储层是事实单点的事实。因此生产建议不是"Redis 单机 + 自求多福"，而是：

部署形态 适用规模 说明
Redis 单机 + AOF 开发/试验 数据不丢但可用性无保障
Redis Sentinel 生产单集群 主从切换秒级，客户端透明
Redis Cluster 多分片大规模 注意锁键需在同一 slot（{task} hash tag）

Redis 发生 failover 时锁的丢失语义（双主窗口）与对策，见 分布式锁 故障场景四。

十二、故障场景实战

场景一：节点"假死"——GC 长停顿导致心跳中断

现象：某节点执行大任务时 JVM/Python 进程 GC 或 CPU 打满，心跳 20s 没刷。其他节点判定其死亡，任务锁 30s 过期，正在跑的任务被重新入队并被别的节点抢走执行——原节点 GC 结束后继续跑旧任务，同一任务双执行。

根因：心跳中断 ≠ 任务停止。锁 TTL 一到，保护就没了。

处置：

  1. 大任务必须用子任务进度上报 + 长 TTL 或切分小任务，避免单任务执行超过锁 TTL（30s）；

  2. 关键业务任务实现幂等键（业务侧去重），把"双执行"从事故降级为"重复调用"；

  3. 监控节点 GC 停顿与心跳延迟，把"心跳 20s 阈值"与"业务任务最长执行时间"对齐设计。

启示：这是无主架构"自动恢复"的阴暗面——恢复动作本身可能制造双执行。自动化的回收必须配合幂等消费，否则"高可用"变成"高重复"。

场景二：回收器扫到"还活着的节点"的任务

现象：网络抖动 25s（>20s 阈值但 <30s 锁 TTL？或节点只是到 Redis 的链路抖动而本地任务在跑），节点被判死，回收器尝试回收它的 RUNNING 任务——但任务锁还没过期，acquire 失败，任务安全。

根因：判活（20s）比锁 TTL（30s）更激进，制造了"判定死亡但任务仍在保护中"的窗口。

处置：这个场景的正确结局是回收失败即安全——回收必须走"先加锁、后改状态、再入队"的顺序，加锁失败就跳过。不要为回收写绕过锁的强制路径（如直接 HSET 改状态），那会把最后的保护也拆掉。

启示：多组件协作的分布式系统，每个"善后"动作都必须重新走一遍主人物的授权检查（锁），否则善后者就是新的破坏者。

场景三：扩容高峰期的"抢占风暴"

现象：业务高峰紧急扩容 10 个节点，所有新节点本地队列为空，同时触发批量抢占 + 大量 task 读取，Redis 命令量瞬时 ×10，出现超时与连接池占满，老节点续期延迟，部分锁提前过期。

根因：冷启动节点没有预取退避（队列空 = 立即抢），同步放大 Redis 压力形成正反馈。

处置：

  1. 节点启动后先做预热等待（等待心跳注册 + 首轮延迟抢占据），参考框架中 start() 后 await asyncio.sleep 的现有节奏；

  2. 分批扩容（每批 2~3 个），观察 Redis 延迟稳定后再加；

  3. 连接池 max_connections 按峰值节点数规划（RedisTaskRepository(max_connections=10) 默认偏小，多节点时需调大）。

启示：去中心化的扩展是"自组织"的，但自组织只在稳态成立；瞬态（冷启动、风暴）需要外部节流，框架提供原语，容量规划还是人的事。

场景四：误删 Redis 中的节点键或任务键

现象：运维误执行 DEL neotask:node:* 或清库脚本误伤 task:*，节点注册信息全部消失。节点本身还活着，心跳每 5s 会把 neotask:node:{id} 重新 HSET 吗？——注意：心跳只更新已有键的字段，不重建被删的键（heartbeat() 里只有 HSET + EXPIRE，没有重建字段），且节点集合 neotask:nodes 若也被删，新节点的注册集就丢了。

根因：注册信息是"软状态"，依赖键存在；删除键后节点不会自愈重建（除非重启）。

处置：

  1. 对 Redis 高危命令（FLUSHDB/DEL/KEYS）做审计与权限收敛；

  2. 节点监控加"注册键存在性"自检，发现缺失自动 register()（源码未内置，需业务侧兜底或二次开发）；

  3. 误删后的恢复路径：重启节点（最可靠）或手动重放 register。

启示：以 Redis 为事实中心的系统，Redis 中的数据要当"数据库"对待：有备份、有审计、有重建路径。把状态全放 Redis 的便利，代价是 Redis 的每一个误操作都是全局事故。

十三、总结

主题 结论
为什么无主 把"谁是主"外包给 Redis 原子性，省掉选举/脑裂/故障转移整套复杂度
事实中心 Redis 是唯一共享状态源；节点间零通信
提交链路 create_task（SET String JSON）+ ZADD，落库与入队不原子，孤儿靠回收兜底
出队与加锁 pop Lua 只 ZRANGE+ZREM，不含加锁；锁在 worker 执行前独立 acquire
防重三防线 状态闸门（PENDING 检查）+ 分布式锁（NX EX 30s）+ 幂等重入
节点管理 NodeManager：neotask:node:{id} HSET + 5s 心跳 + 20s 判死 + 40s TTL，三态模型
两态哲学 判活只是优化信号；正确性由锁与状态机兜底，容忍慢回收、严防错回收
节点管理实现 NodeManager 与 HeartbeatManager 两套实现共用同一注册表（neotask:node:{id} / neotask:nodes），任务状态经 TaskRepository 读写；Coordinator 已预留但未接入主链路
扩展边界 自然负载分配靠队列水位差；瓶颈通常在 Redis 与锁竞争而非节点数
容错边界 单节点失联局部自愈；Redis 不可用 = 全局停摆，必须上 Sentinel/Cluster

一句结语：去中心化不是"没有中心"，而是把中心从"会选主的节点"换成"不会犯错的存储"。NeoTask 的架构之美在于承认了这一点——所有节点的行为都退化到最简单：抢队列、拿锁、执行、刷心跳。系统级复杂度没有消失，它被转移到了 Redis 的原子原语与回收器的补偿逻辑里——那才是真正的"分布式系统代码"所在之处。
