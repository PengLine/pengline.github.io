NeoTask 节点监控详解：事件驱动指标与滑动窗口 + 健康检查 + Prometheus 集成

NeoTask 节点监控详解

📚 返回首页 | 📖 快速上手 | 📘 API 参考 | ⚙️ 配置说明 | 🐙 GitHub | 🐱 NeoTask 官网

版本基线：本文对照 NeoTask v1.0.2（PyPI 发布版）。
代码标注约定：🔧 表示真实源码（仓库原样摘录，附文件路径，可自行对照）；📝 表示示例代码（用法演示、改进建议或教学代码，不代表仓库实现）。

概述

可观测性文章最容易写成"理想架构图"，所以先明确 NeoTask 的监控资产实际是哪几件：

  1. MetricsCollector（🔧 monitor/metrics.py）：进程内指标收集器，靠事件总线驱动记录任务生命周期指标，带滑动窗口分布统计与 Prometheus 文本导出方法。

  2. SystemHealthChecker（🔧 monitor/health.py）：注册制健康检查器，内置 storage/queue/system 三项检查，逐项串行执行并按三态聚合出结论。

  3. ReporterManager 族（🔧 monitor/reporter.py）：周期性把指标推到控制台/文件/Prometheus Pushgateway（推模式，不是拉模式）。

  4. 节点状态记录（🔧 distributed/node.py）：Redis Hash 上的节点注册与心跳时间戳，仅 Redis 模式存在。

指标与健康检查都已接入运行链路：TaskPool 初始化时装配全局事件订阅器（重试、优先级都在内），启动时拉起 MetricsCollector.start() 采样循环；健康检查则在每次读取 get_health_status() 时按 TTL 决定是否重新执行。

能力边界同样需要说清——以下三处在 1.0.x 中确实不存在，属于"基础设施只建了一半"的形态：

# 缺口 表现 详见
1 NodeManager._health_check_loop 只留 TODO 心跳过期只让节点从"活跃列表"消失，无标记、无告警 第六节
2 contrib/prometheus.py 是空壳 + 无 HTTP 端点 "标准 /metrics 拉取"不存在，只有推模式与手工导出 第七节
3 WebUIServer 无实例化调用方 只有 / 与 /api/stats 两个端点，且要自己启动 第七节

真正掌握 NeoTask 的可观测性边界，靠的是分清"已接线"与"需自建"这条线。

一、架构概览：事件驱动 + 进程内统计，没有聚合层

数据流只有两跳：

flowchart LR
    subgraph Producer["事件产生方"]
        A[dispatcher/worker/lifecycle<br/>emit TaskEvent]
    end
    subgraph Bus["事件总线"]
        B[subscribe_global<br/>全局订阅]
    end
    subgraph Local["进程内（无跨节点聚合）"]
        C[MetricsCollector<br/>计数器+滑动窗口]
        D[SystemHealthChecker<br/>三态健康检查]
    end
    subgraph Export["导出（按需/周期）"]
        E[get_stats API<br/>同步阻塞拉取]
        F[ReporterManager 60s<br/>Console/File/Pushgateway]
    end
    A --> B
    B --> C
    C --> E
    C --> F
    D --> E

事件挂钩装配在 TaskPool 初始化时（🔧 api/task_pool.py 的 _setup_event_handlers）：一个 subscribe_global 的处理器监听 6 种事件，翻译成指标记录调用：

事件 指标调用 效果
task.created record_task_submit total_submitted+1、pending+1、priority_counts+1（优先取自 payload）
task.started record_task_start 记排队时间、pending-1、running+1
task.completed record_task_complete 记执行时间/重试次数、total_completed+1、running-1
task.failed record_task_failed 记执行时间/重试次数、total_failed+1、running-1
task.cancelled record_task_cancelled total_cancelled+1、running-1
task.retry record_task_retry total_retried+1、累计该任务重试次数
task.reclaimed 仅 debug 日志 无指标

要点：

  • 指标是事件推导值，不是存储扫描值。事件丢（总线异常、处理器抛错被吞）则计数漂移。

  • 无跨节点聚合：每个进程的 MetricsCollector 只统计本进程执行的事件，集群总览需要外部系统自己做（比如 Pushgateway 按 job 聚合，见第七节）。

  • 事件处理器是异步协程，挂在事件总线上串行执行：高吞吐下指标记录本身参与任务关键路径的调度（每次记录还带 asyncio.Lock），这是使用指标时需要权衡的开销。

二、任务指标：真实的字段族与两个口径注意点

2.1 TaskMetrics 字段全景

指标容器 TaskMetrics（🔧 metrics.py:24）分三族，get_summary()/to_dict() 输出 21 个键：

累计计数器：total_submitted / total_completed / total_failed / total_cancelled / total_retried

瞬时量：pending（事件推导的排队中）/ running / scheduled（保留字段，恒 0，见 2.3）

滑动窗口分布（deque maxlen=1000，窗口内样本自动淘汰）：

属性 含义 输出键
avg_execution_time 执行时间均值 avg_execution_time
p50/p90/p95/p99_execution_time 执行时间分位数（线性插值法） 同名
avg_queue_time / p95_queue_time 排队时间（提交→开始） 同名
avg_retry_count 重试次数均值 avg_retry_count
throughput 1/平均执行时间（见 2.2） throughput
success_rate / failure_rate 完成/（完成+失败），未完成任务不参与分母 同名
priority_counts 按优先级分布（取自 task.created 的 payload） 同名

执行时间的均值与中位/90/95/99 分位都在，实现是标准线性插值（🔧 metrics.py）；"排队时间"的定义是 record_task_start 时用提交时间戳作差，窗口上限 1000 条。

2.2 吞吐量的定义

throughput = 1.0 / avg_execution_time（🔧 metrics.py）。它不是"每秒实际完成任务数"（这里没有时间窗计数），而是**“若每个任务都耗时等于均值、且单 worker 无并发损耗时的理论单流速率”**——假设 avg 100ms 得 10 任务/秒。真实吞吐 = 完成数 ÷ 观察时长，需要外部系统用 total_completed 增量自己算：该公式与节点数、并发度、观察窗口无关，只随执行时间均值变化。

用于横向对比"哪个版本更快"尚可；用于容量规划（“集群每秒能吞多少”）会系统性偏离——多 worker 并发时实际吞吐高于 1/均值，瓶颈通常不在单任务耗时。

2.3 两个口径注意点：两套 pending 与恒 0 的 scheduled

注意点一：两个 pending 并存且口径不同。

来源 定义 特征
get_stats()["pending"] 生命周期管理器全库扫描 PENDING 状态任务（每状态 limit 10000，🔧 lifecycle.py:340） 反映存储真实状态，成本高（全表/全键扫描）
get_stats()["metrics"]["pending"] 事件推导：submit+1 / start-1 反映本进程事件流，漂移可能（进程重启清零、事件丢失）

SQLite/Redis 模式下两者数值可能不一致（例如节点 A 提交、节点 B 执行时，B 的 metrics.pending 会是负数——因为 B 没收到 submit 事件就收到了 start！record_task_start 里 pending = max(0, pending-1) 的防御只保证不为负，不保证准确）。集群模式下metrics.pending 天然不可信，应以 stats.pending 为准。

注意点二：scheduled 恒为 0。 TaskMetrics.scheduled 只在 record_task_scheduled() 时递增，但这个记录方法在全库检索中没有任何调用方（延迟任务走的是队列重投，不经这条指标），字段因此长期停在 0。它目前是个保留字段，不要当"待执行的延时任务数"使用——那个数字在 DelayedQueue 与时间轮各自的 size() 里。

2.4 系统指标：60 秒一次的 psutil 采样

MetricsCollector 顺带收集系统指标（SystemMetrics：cpu_percent / memory_percent / memory_used_mb / thread_count / task_count / uptime_seconds）。采样循环 _collect_system_metrics_loop 由 MetricsCollector.start() 拉起，TaskPool 的 start_components() 会调用它，shutdown_components() 对称调用 stop()——所以启用指标后系统指标是自动采集的，无需手动启动。三点使用须知：

  1. 默认间隔 60 秒（system_metrics_interval=60.0），不是"每五秒采集一次"。

  2. 系统指标只在 get_full_summary() 出现，get_summary() 不含 system 键。TaskPool 的 get_stats() 走的是前者（🔧 api/task_pool.py），因此 stats["metrics"]["system"] 可直接取到。

  3. 依赖 psutil：缺失时 import psutil 失败 → 返回空 SystemMetrics() 且无日志告警，system 字段会是 None。它属于 [monitor] 可选依赖，需要该指标时记得安装。另外 cpu_percent(interval=0.1) 是同步阻塞调用，每次采样会卡事件循环约 0.1 秒——60 秒一次，可忽略。

task_count 字段实为 len(self._task_start_times)——“正在本进程执行的并发任务数”，命名与直觉不符，别当任务总量用。

三、健康检查：注册制三态模型

健康检查的设计是一个注册表 + 三态聚合（🔧 monitor/health.py）。

HealthChecker 提供注册/注销/执行/聚合：

  • register(name, check_func) 注册任意异步检查函数；check_all() 串行执行所有检查（逐项、无并发），每项用 asyncio.wait_for 包了单项超时（check_timeout，默认 DEFAULT_CHECK_TIMEOUT = 5.0 秒），超时或异常 → 该项记 UNHEALTHY；

  • 聚合规则（🔧 health.py）：任一 UNHEALTHY → UNHEALTHY；否则任一 DEGRADED → DEGRADED；全 HEALTHY → HEALTHY；从未执行过 → UNHEALTHY。

SystemHealthChecker 内置三项（🔧 health.py）：

检查 实现 判定
storage task_repo.exists("health_check") ping 一次真实查询 异常 → UNHEALTHY
queue queue.size() >10000 → DEGRADED；异常 → UNHEALTHY
system psutil：CPU / 内存 / 磁盘使用率 任一 >90% → DEGRADED

超时段与阈值是硬编码的"一刀切"（5 秒 / 90% / 10000），阈值无参数化配置，check_timeout 只能经 SystemHealthChecker(check_timeout=...) 调整。检查项通过 register 开放扩展——业务可以追加"Redis 延迟 > 阈值 → DEGRADED"之类的自定义项。

psutil 缺失时 system 记 HEALTHY 而非 DEGRADED（message 里带 available: false）：psutil 现在是 [monitor] 可选依赖，若缺它就把整体拉成 degraded，默认安装在没装 extra 时会永远上报 degraded，这个信号也就没用了。

为什么这么设计：注册制而非硬编码分层

liveness/readiness/deep 分层隐含"部署平台按层消费"的假设（K8s 探针语义），而 NeoTask 的健康检查消费方只有一个——get_health_status() 调用者。注册制让检查项按需堆叠、聚合规则统一，比预定义分层更省事；代价是"分层消费"能力不存在：没有独立暴露 liveness 与 readiness 的入口，想接 K8s 探针只能自己包装。

四、健康检查的触发：按需执行 + TTL 复用

健康检查不是后台周期任务，而是**“读时检查、窗口内复用”**：TaskPool 读取健康状态时先判断上次结果是否过期，过期（或从未执行）才真正跑一遍检查。

装配与触发链路：

  1. SystemHealthChecker 在 TaskPool 装配（enable_health_check=True 默认，🔧 task_pool.py）；

  2. get_health_status() / get_health_status_async() 先调用 _refresh_health_if_stale()：若 last_check 距今小于 HEALTH_CHECK_TTL（5 秒）直接返回，否则 await check() 执行全部内置检查；

  3. 随后 _collect_health() 汇总结果，并拼上分布式组件的字段（active_nodes / heartbeat / reclaimer），这些字段来源独立、与检查无关。

设计动机：健康接口通常被探针高频轮询，每次调用都跑 storage ping + psutil 采样（后者还会同步阻塞事件循环约 0.1s）代价过高；用一个 TTL 窗口把"探针频率"与"检查频率"解耦，5 秒内的连续轮询只打一次真实检查。

因此默认配置下 get_health_status() 会返回真实结论：

enable_health_check=False 时 _health_checker 为 None，_collect_health() 只返回 {status, node_id} 加分布式字段，不会出现 checks。

两个已知成本：_check_system 里 psutil.cpu_percent(interval=0.1) 的同步阻塞会在每次真实检查时卡事件循环约 0.1s；storage 检查在 Redis 故障时可能挂到 TCP 超时。后者已由单项超时兜住（默认 5 秒 → 该检查记 UNHEALTHY），前者是 5 秒最多一次、每次 0.1s 的抖动，可接受。

五、Reporter：60 秒批量的推式上报

enable_reporter=False（默认关）。开启后 TaskPool 启动流程会装配（🔧 task_pool.py）：

真实的上报链路（🔧 monitor/reporter.py）：

  • ReporterManager._report_loop：每 1 秒 tick，指标攒批（满 10 条或距上次 flush 超 60 秒）后整体推送——批量上报设计，非每秒一条；

  • ConsoleReporter：print(json.dumps(metrics, indent=2))，默认唯一挂载；

  • 另有现成上报器可自行 add_reporter：FileReporter（JSON Lines 追加写文件）、PrometheusReporter（推 Pushgateway：POST {url}/metrics/job/{job}，🔧 reporter.py:73）。

注意三点：回调是同步方法 get_stats（内部 run_coroutine 跨线程阻塞等待），上报循环每 tick 都会完整执行一次全库状态扫描 + 指标快照——开启 reporter 后每 60 秒至少一次 O(状态数) 的存储扫描，大库时上报本身成为间歇性负载源；Reporter 的批量语义对 Pushgateway 不友好（Gateway 只保留最后一次推送，batch 中间态无意义，但代码对每个 reporter 逐个 report，行为等价于最后一条覆盖）。

六、节点状态监控：三态、心跳时间戳、无故障发现

节点状态记录存在于 Redis 模式（🔧 distributed/node.py）：

状态只有三态：ACTIVE / STOPPED / FAILED（🔧 node.py）。没有"可疑（SUSPECT）“过渡态，没有"恢复中”，也没有分级超时策略——心跳过期只是让节点从活跃视图里消失。

节点记录是 Hash：neotask:node:{node_id} 存 7 个字段（node_id/hostname/pid/status/started_at/last_heartbeat/metadata），节点 ID 生成式 {hostname}_{pid}_{uuid4前8位}。register 写入后立即 expire(40s)（心跳超时 20s × 2），加入 neotask:nodes SET；心跳每 5 秒 hset last_heartbeat + 续期；unregister 只置 stopped + 60s 过期，不删除 SET 成员。

"活跃节点"是过滤出来的，不是标记出来的：get_active_nodes() 对 SET 全量成员逐个 HGETALL，过滤条件 status == ACTIVE 且 now - last_heartbeat < 20s（🔧 node.py）。心跳过期只意味着"该节点从活跃列表消失"，没有任何代码把它标记为 FAILED 或触发告警——_health_check_loop 每 20 秒醒来一次，调用 get_active_nodes() 后只留下一行 # TODO: 处理故障节点：循环存在，逻辑缺席。真正"发现故障并善后"的职责在 HeartbeatManager 与 TaskReclaimer（互链 故障恢复），但那是任务回收语义，不是监控告警语义：节点死亡不会产生任何事件或告警输出。

另外 NodeInfo 只有身份与心跳字段，没有"当前负载、活跃任务数"之类的落点；get_active_nodes() 对外只暴露 node_id/hostname/pid（🔧 api/task_pool.py）。节点维度的负载视图需要指标层自己拼。

七、Prometheus 集成：推模式已就绪，拉模式需自建

NeoTask 不内置 HTTP 拉取端点（"HTTP 端点 /metrics 供 Prometheus 抓取"需要自己搭）。现成素材是三条：

素材 位置 形态 打通方式
to_prometheus_format() 🔧 monitor/metrics.py 输出完整文本（HELP/TYPE/字段齐全，含 counter/gauge 分类、毫秒换算、priority label） 手工暴露：自建 HTTP 端点返回该文本，或配合 exporter
PrometheusReporter 🔧 monitor/reporter.py 推 Pushgateway：POST {url}/metrics/job/{job}（aiohttp） reporter_manager.add_reporter(PrometheusReporter("http://pushgateway:9091"))
contrib/prometheus.py 🔧 文件只有 docstring 空壳占位，无实现 自行填充或忽略

集成判断（📝）：单机/少节点用 Pushgateway 推模式最省事（ReporterManager 已内置批量循环）；多节点集群且已有 Prometheus 拉取基建时，自起一个极薄 HTTP 端点包 to_prometheus_format() 即可（📝）：

WebUIServer（🔧 web/server.py，FastAPI + uvicorn 后台线程，提供 / 与 /api/stats 两个端点，默认 127.0.0.1:8080）同样未接入：SchedulerConfig.webui 默认 disable，没有任何组件实例化它。若要一个现成的 REST 入口，目前只有手动启动它拿到的 /api/stats，没有 /health、没有 /metrics。

八、公开监控 API 速查

TaskPool 暴露的监控查询入口（全部同步阻塞跨线程调用，见 API 参考）：

API 返回要点 口径注意
get_stats() queue_size、total/pending/running/completed/failed/cancelled（存储扫描）、success_rate、node_id、metrics 子对象（事件推导，含 system）、prefetcher（启用预取时）、reclaimer 两套 pending 并存（见 2.3）
get_worker_stats() 每个 worker 的 WorkerStats（worker_id/active_tasks/completed_tasks/failed_tasks/is_busy）；预取统计走 get_stats()["prefetcher"]，见 预取机制 —
get_health_status() status/last_check/checks + active_nodes/heartbeat/reclaimer 读取时按 5 秒 TTL 决定是否重跑检查（见第四节）
get_active_nodes() [{node_id, hostname, pid}]（仅 Redis 模式，其余返回 []） 心跳过滤视图，非全量注册

九、实战：取数、探针与集成

场景一：正确取重试率与优先级分布

目标：在监控面板展示"重试总量"与"各优先级提交占比"。

取数：这两个指标已由 TaskPool 的内联事件处理器写入，直接读即可：

口径提醒：avg_retry_count 的样本同时来自成功与最终失败的任务——只统计成功侧会让这个值系统性偏低（重试最多的恰恰是失败任务）。

场景二：把健康接口接到探针

目标：用 get_health_status()["status"] 做存活/就绪判定，且不让探针变成负载源。

正确接法：直接把 get_health_status() 暴露给探针即可，它自带 5 秒 TTL：

探针频率高于 5 秒时，只有窗口外的第一次会真正执行检查，其余直接复用——所以可以放心用 1 秒级的探针间隔。不要改成每次调用都 await check()：那会让 storage ping + psutil 采样跟着探针频率跑，cpu_percent(interval=0.1) 的同步阻塞还会按次累积。

排查：若 checks 为空对象，说明 enable_health_check=False（此时 _collect_health 不会附加检查摘要）；若某项为 unhealthy 且 message 含 timed out，说明该依赖在 check_timeout（默认 5 秒）内没返回。

场景三：集成 Prometheus 时发现没有 /metrics 可抓

现象：找 “prometheus_enabled / prometheus_port / /metrics” 配置项，四处没有；给容器加 Prometheus 注解抓 9090 端口，连接被拒。

根因：NeoTask 不内置拉取端点；真实只有 (1) MetricsCollector.to_prometheus_format() 文本方法（无 HTTP 载体）、(2) PrometheusReporter 推 Pushgateway（需自己 add_reporter 且依赖 aiohttp）、(3) contrib/prometheus.py 空壳。enable_reporter=True 默认也只挂 ConsoleReporter，不会产生任何网络流量。

排查：grep 源码确认无 http server 启动代码；确认 aiohttp / psutil 等可选依赖是否安装。

解决：按第七节选路——临时验证用 Pushgateway 推模式（最贴合内置代码）；生产拉模式自建 /metrics 薄端点包 to_prometheus_format()。

本质教训：选推还是拉，先确认框架里有没有现成的 HTTP 端点。NeoTask 没有，所以推模式（PrometheusReporter）最省事，拉模式必须自建薄端点。

总结

NeoTask 的可观测性是采集与调度已通、导出按需焊接：

  • 事件驱动的指标模型：生命周期事件 → 计数器/瞬时量/滑动窗口分位，重试与优先级都取自真实 payload，字段全、口径清楚（两个使用注意点见 2.3）；

  • 健康检查：注册制三态 + 逐项超时，读取时按 5 秒 TTL 触发执行，默认配置下返回真实结论；

  • 导出链路：内置推模式（Pushgateway）与 Prometheus 文本导出，拉取端点需自建薄壳；

  • 节点状态：三态 + 心跳时间戳，无状态机、无故障发现——死亡判定交给回收链路，监控语义的告警需要自建。

一句话收束：采集（真实）与调度（执行）都已接线，导出（打通）按你的监控栈选一条路。具体接法见第九节，配合 配置说明 与 最佳实践 食用更佳。
