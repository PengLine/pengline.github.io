从 Prompt 压缩到 Agent 成本控制

阅读提示：本文围绕「AI 应用 Token 优化：从 Prompt 压缩到 Agent 成本控制」展开，重点区分模型/框架能力、工程实现和实际运行边界。示例配置用于说明思路，生产环境请结合目标版本与真实负载复测。

大模型应用上线以后，Token 往往不是一个单纯的计费指标。

它同时影响请求成本、上下文长度、接口延迟、模型吞吐量，以及 Agent 能够持续运行多少轮。

尤其是 AI Agent、RAG、代码生成这类应用，一次请求真正发送给模型的内容通常远比用户输入本身复杂：

flowchart TD
    A[System Prompt] --> C[Context 上下文组装]
    B[历史对话] --> C
    D[当前任务] --> C
    E[用户上下文] --> C
    F[RAG 检索结果] --> C
    G[Tool 定义] --> C
    H[Tool 执行结果] --> C
    I[Agent 状态] --> C

    C --> J[LLM 模型推理]
    J --> K{是否需要调用 Tool}

    K -- 否 --> L[模型输出]
    K -- 是 --> M[Tool 执行]
    M --> N[Tool 执行结果]
    N --> C

因此，Token 优化真正需要解决的问题并不是：如何让模型少输出几个字？而是：如何让模型只接收完成当前任务真正需要的信息。

Token 优化的排查顺序

线上出现 Token 成本异常时，可以按照这个顺序排查：

flowchart TD
    A[Token 成本异常] --> B[统计请求组成]

    B --> C[History]
    C --> D[System Prompt]
    D --> E[RAG]
    E --> F[Tool Schema]
    F --> G[Tool Result]
    G --> H[Agent Loop]

    H --> I[重复请求]
    I --> J[Cache]
    J --> K[Model Routing]
    K --> L[高级压缩]

推荐优先检查：

优先级 检查项 常见问题
1 History 无限增长
2 System Prompt 重复规则
3 RAG Top-K 过大
4 Tool Schema Tool 数量过多
5 Tool Result 返回完整对象
6 Agent Loop 重复调用
7 Cache 重复请求
8 Model Routing 小任务使用大模型
9 Output 输出过度冗长
10 高级压缩 在前面都解决后再考虑
