耗时任务排队不想引 Celery？用 NeoTask 嵌入式任务池四步跑通

|浏览量:

耗时任务排队不想引 Celery？用 NeoTask 嵌入式任务池四步跑通

版本基线：NeoTask v1.0.5（2026-10-29 发布）。文中代码均为用法示例（📝），不是仓库源码摘录；涉及实现细节处会给出源码路径（🔧），可自行对照。

AI 生图、视频转码、批量抓取、报表生成……凡是耗时超过一个请求周期的活儿，都需要"排队"。传统答案几乎只有一个：Celery + Redis/RabbitMQ，外加一套 worker 部署与监控。但对很多中小项目来说，任务量还没到那个量级，运维复杂度却先拉满了。

NeoTask 的思路不同：把任务池内嵌进应用进程，纯 Python asyncio 实现，不依赖外部中间件就能跑；等真上量了，再切换 Redis 模式横向扩展。本文带你跑通最小链路，把四种任务类型和背压语义一次讲透，最后给出"什么时候该升级"的判断依据。

一、安装：按需选 extra，不绑架依赖

NeoTask 支持 Python ≥ 3.8。1.0.5 的基础包带三个依赖：aiosqlite（SQLite 存储）、croniter（Cron 解析）、colorama（Windows 控制台彩色日志）。其余能力全部做成可选 extra，按需加装：

安装命令 解锁能力
pip install neotask 内存 + SQLite 存储、定时调度、事件总线、彩色日志
pip install neotask[redis] Redis 存储 / 分布式锁 / 去中心化
pip install neotask[monitor] 系统指标采集（psutil，健康检查用）
pip install neotask[ui] Web UI 监控面板（fastapi + uvicorn）
pip install neotask[full] 上述全部

三、四种任务类型：一套 API 全覆盖

即时、优先级、延时三种任务共用 TaskPool.submit，靠参数区分；Cron 周期任务走 TaskScheduler 门面（内部同样持有一个 TaskPool）：

任务类型 写法 典型场景
即时任务 pool.submit(data) 生图、转码、通知推送
优先级任务 pool.submit(data, priority=1) 付费用户请求插队（数字越小越先执行）
延时任务 pool.submit(data, delay=1800) 订单 30 分钟未支付自动关单
Cron 定时 scheduler.submit_cron(data, "0 2 * * *") 每日凌晨报表、周期性巡检

延时任务的实现机制值得说一句，也有一个必须知道的边界：它不是"提交时挂起一个 sleep"，而是进入独立的延时队列（内存最小堆，元素是 (到期时间, 优先级, task_id)，🔧 queue/delayed_queue.py:94-97），到期后由调度循环取出，再按原优先级推回优先队列（🔧 queue/queue_scheduler.py:64-70）。即时任务与延时任务的执行路径因此完全一致。

但 1.0.5 的延时队列没有接存储后端：QueueScheduler 里的 DelayedQueue() 是纯内存实现，进程重启后堆里的到期信息就没了，任务会在存储里停在 PENDING 且没有任何组件把它重新入队（实测：SQLite 模式下提交 delay=2 后立即重启，5 秒后状态仍是 pending）。Redis 存储里虽然有 queue:delayed ZSET 的实现，但 TaskPool.submit(delay=...) 走的不是那条路径。需要跨重启的延时任务，请把"何时该投递"记在业务表里，启动时扫描补投；周期任务则是另一套链路——SchedulerConfig.enable_persistence 默认 True，在 SQLite/Redis 存储下会持久化注册信息（memory 形态仍会丢）。

flowchart LR
    A[submit 提交任务] --> B{带 delay?}
    B -- 否 --> D[优先队列]
    B -- 是 --> C[延时队列<br/>按到期时间排序]
    C -->|到期转正| D
    C -.->|进程重启后丢失| X[任务停在 PENDING<br/>需业务补投]
    D --> E[Worker 池<br/>并发闸门控制]
    E --> F{执行结果}
    F -->|成功| G[状态 SUCCESS]
    F -->|失败| H[按策略自动重试]
    H -->|超限| I[状态 FAILED<br/>可订阅事件告警]

四、背压与重试：队列满时会发生什么

单机任务池最容易埋雷的地方是"只管进、不管满"。NeoTask 的语义很明确：队列容量默认 10000（queue_max_size），队列满或调度器已停服时，submit 会抛 QueueFullError，任务被标记为 FAILED——不存在"记录为 PENDING 但永远无人消费"的幽灵任务。

这个设计把背压问题显式化到了提交方：

配合 pool.get_queue_size() 提前感知水位，高峰期的处理策略就从"任务莫名消失"变成"显式决策"。失败重试同理：执行器抛异常后，任务在 max_retries（默认 3）内按 retry_delay × 新重试次数 线性退避重排（🔧 worker/pool.py:474），超限转 FAILED，全程可通过事件总线订阅状态变化；Web 面板需要自己装配（见第七节）。

如果重试本身也把队列塞满了，任务会被直接标记 FAILED 并投递死信（Redis 模式下默认启用），不会无限循环。这也是"重试"与"背压"必须一起考虑的原因：下游故障时，自动重试会放大流量，队列容量与重试上限要按下游承载能力配。

五、持久化怎么选：一张决策图

三种存储后端对应三个成熟度阶段，切换只需改配置，执行器代码不动：

flowchart TD
    Q{任务丢得起吗?} -->|丢了无所谓<br/>纯加速| M[内存模式<br/>最快，重启即清]
    Q -->|不能丢<br/>单机部署| S[SQLite 模式<br/>默认推荐 落盘恢复]
    Q -->|不能丢<br/>多机/多进程| R[Redis 模式<br/>分布式抢占与故障恢复]

    S -.->|量涨了 加机器| R
    R -.->|需要锁续期/孤儿回收| R2["分布式锁 + 看门狗<br/>+ 回收器"]

    style M fill:#f1f8e9
    style S fill:#e3f2fd
    style R fill:#fff3e0

内存模式适合"丢了也能重跑"的场景（如缓存预热）；SQLite 是单机默认推荐——任务行与优先队列都落盘（queue 表），进程重启后排队中的即时任务能继续被消费，且零额外服务；Redis 模式面向多机部署，优先队列是共享 ZSET，任务被多个消费者抢占，执行前还有分布式锁兜底，正常情况下不会重复执行（故障切换窗口的边界见分布式锁一篇）。

三种模式共享同一套"落盘但不等于全落盘"的边界：延时队列始终是内存结构（见第三节），进程重启后延时中的任务不会自动恢复；执行中的任务在 memory/SQLite 形态下没有回收器，崩溃或重启后没有任何组件自动接管 RUNNING 记录，只能人工重提——只有 Redis 形态才有回收器做超时与孤儿回收。选存储时把这两类任务单独算进去，别把"任务表落盘"理解成"所有状态都能续上"。

事件回调直接注册在任务池上（on_completed / on_failed / on_progress 等一族，handler 是收 TaskEvent 的 async 函数），任务状态从 RUNNING 转 FAILED 的瞬间推送告警，比用户来问"我的图怎么还没好"体面得多。

回调在事件总线上异步分发，回调里抛异常不会影响任务主流程——告警逻辑写得再糟也拖不垮执行链路。

1.0.5 起进度链路也接通了：执行器内调用 report_progress(0.0~1.0, message)，任务池侧用 on_progress 订阅 task.progress 事件。注意它只在该任务被 Worker 执行的上下文里生效（靠 ContextVar 绑定），任务池外调用会返回 False；进程执行器不共享上下文，也不支持进度上报。

七、可观测性：任务池不是黑盒

内嵌任务池最容易被质疑的是"出了问题我怎么知道"。NeoTask 的观测手段分三层，按排障深度递进：

层级 手段 用途
程序内 事件总线（created/started/completed/failed/cancelled/progress/reclaimed 七类公开订阅） 业务侧实时感知，触发回调或告警
程序内 pool.get_queue_size()、get_stats() 等查询接口 提交前水位检查，背压决策
独立面板 pip install neotask[ui] 的 Web UI 组件 看队列深度、任务历史、失败分布，排障用

需要说明的是，Web UI 是独立装配的组件，TaskPool 不会自动挂载它；要面板就自己实例化 WebUIServer 并启动（🔧 webui/）。另外 task.retry 事件内部有发布、指标采集会消费它，但 1.0.5 没有对应的 on_retry 公开注册方法——要观察重试次数，从 get_stats() 或指标侧取。

运维视角的两个健康信号值得盯：队列深度的斜率（持续爬升说明消费能力不足，先看执行器是不是在外部 I/O 上空等，再考虑加并发或扩容）；失败率的突变（下游服务抖动会第一时间体现在这里，重试次数曲线是前置信号）。加装 [monitor] extra 后还有基于 psutil 的系统指标采集，可以接进现有的告警体系。

八、什么时候该切换 Redis 分布式模式？

单进程写法出现以下任一信号时，就该升级了：

  1. 多进程 / 多机部署：任务需要被多个消费者抢占，且同一任务不能被重复执行

  2. 节点会挂：worker 宕机后，它领走的任务需要被自动回收重派

  3. 需要防重入：关键任务要靠分布式锁兜底

pip install neotask[redis] 后，NeoTask 基于 Redis 心跳 + 回收器实现节点故障恢复，死信队列接住重试超限或无法重排的任务，消费端去中心化，不依赖中心调度器。生产语义（锁续期、孤儿任务、预取水位）在文档系列里有源码级展开：

  • 架构设计：三种部署形态与两阶段生命周期

  • 分布式锁：Redis 看门狗 + 任务抢占与故障恢复

  • 预取机制：批量拉取 + 高低水位 + 自适应策略

  • 故障恢复：回收器 + 孤儿任务 + 死信队列

  • 性能基准：实测数据解读与调优

九、Celery 还是 NeoTask？一句话选型

两者并不互斥：成熟度与生态优先选 Celery；单体内嵌、低运维、纯 asyncio 技术栈选 NeoTask。典型路径是原型期用 NeoTask 内嵌跑，任务量上来后再评估是否需要迁移——而如果你需要 Redis 分布式能力，NeoTask 本身也能撑住相当规模。

最后给三条工程结论：

  1. 先想清楚任务的丢失容忍度，再选存储后端——这比任何性能参数都优先；

  2. 背压策略在写代码时就定好（捕获 QueueFullError 的三选一），不要等队列真满了再补；

  3. 延时任务不要自己拿 dict + 定时器裸模拟——到期转正、优先级一致性与并发下的取消语义，自研很容易漏；但也要知道 1.0.5 的延时队列不跨重启，持久化需求得在业务层补上。
