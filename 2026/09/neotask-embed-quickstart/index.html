耗时任务排队不想引 Celery？用 NeoTask 嵌入式任务池四步跑通

AI 生图、视频转码、批量抓取、报表生成……凡是耗时超过一个请求周期的活儿，都需要"排队"。传统答案几乎只有一个：Celery + Redis/RabbitMQ，外加一套 worker 部署与监控。但对很多中小项目来说，任务量还没到那个量级，运维复杂度却先拉满了。

NeoTask 的思路不同：把任务池内嵌进应用进程，纯 Python asyncio 实现，不依赖外部中间件就能跑；等真上量了，再切换 Redis 模式横向扩展。本文带你跑通最小链路，把四种任务类型和背压语义一次讲透，最后给出"什么时候该升级"的判断依据。

一、安装：按需选 extra，不绑架依赖

NeoTask 支持 Python ≥ 3.8。基础包只带两个依赖（aiosqlite 用于 SQLite 存储、croniter 用于 Cron 解析），其余能力全部做成可选 extra，按需加装：

安装命令 解锁能力
pip install neotask 内存 + SQLite 存储、定时调度、事件总线（官方主推）
pip install neotask[redis] Redis 存储 / 分布式锁 / 去中心化
pip install neotask[monitor] 系统指标采集（psutil，健康检查用）
pip install neotask[ui] Web UI 监控面板（fastapi + uvicorn）
pip install neotask[full] 上述全部

三、四种任务类型：一套 API 全覆盖

任务池的核心提交接口只有一条，四种任务类型靠参数区分：

任务类型 写法 典型场景
即时任务 pool.submit(data) 生图、转码、通知推送
优先级任务 pool.submit(data, priority=1) 付费用户请求插队（数字越小越先执行）
延时任务 pool.submit(data, delay=1800) 订单 30 分钟未支付自动关单
Cron 定时 注册标准 cron 表达式 每日凌晨报表、周期性巡检

延时任务的实现机制值得说一句：它不是"提交时挂起一个 sleep"，而是进入独立的延时队列，到期后由调度循环唤醒、转正推入优先队列等待执行——Redis 模式下用两个 ZSET（queue:priority 按 score 出队、queue:delayed 按到期时间戳）加 Lua 原子弹出实现，转正路径与即时任务完全一致。你不需要关心这些细节，但它们保证了延时任务在重启后依然能按到期时间恢复，而不是随进程消失。

flowchart LR
    A[submit 提交任务] --> B{带 delay?}
    B -- 否 --> D[优先队列]
    B -- 是 --> C[延时队列<br/>按到期时间排序]
    C -->|到期转正| D
    D --> E[Worker 池<br/>并发闸门控制]
    E --> F{执行结果}
    F -->|成功| G[状态 COMPLETED]
    F -->|失败| H[按策略自动重试]
    H -->|超限| I[状态 FAILED<br/>可订阅事件告警]

四、背压与重试：队列满时会发生什么

单机任务池最容易埋雷的地方是"只管进、不管满"。NeoTask 的语义很明确：队列容量默认 10000（queue_max_size），队列满或调度器已停服时，submit 会抛 QueueFullError，任务被标记为 FAILED——不存在"记录为 PENDING 但永远无人消费"的幽灵任务。

这个设计把背压问题显式化到了提交方：

配合 pool.get_queue_size() 提前感知水位，高峰期的处理策略就从"任务莫名消失"变成"显式决策"。失败重试同理：失败任务按策略自动重试，超限转 FAILED，全程可通过事件总线订阅状态变化，或加装 [ui] extra 用 Web 面板直接观察。

五、持久化怎么选：一张决策图

三种存储后端对应三个成熟度阶段，切换只需改配置，执行器代码不动：

flowchart TD
    Q{任务丢得起吗?} -->|丢了无所谓<br/>纯加速| M[内存模式<br/>最快，重启即清]
    Q -->|不能丢<br/>单机部署| S[SQLite 模式<br/>默认推荐 落盘恢复]
    Q -->|不能丢<br/>多机/多进程| R[Redis 模式<br/>分布式抢占与故障恢复]

    S -.->|量涨了 加机器| R
    R -.->|需要锁续期/孤儿回收| R2["分布式锁 + 看门狗<br/>+ 僵尸锁扫描"]

内存模式适合"丢了也能重跑"的场景（如缓存预热）；SQLite 是默认推荐——任务落盘，进程崩溃后重启恢复，单机内嵌场景零额外依赖；Redis 模式面向多机部署，任务被多个消费者抢占，同一任务不会重复执行。

回调在事件总线上异步分发，回调里抛异常不会影响任务主流程——告警逻辑写得再糟也拖不垮执行链路。

七、可观测性：任务池不是黑盒

内嵌任务池最容易被质疑的是"出了问题我怎么知道"。NeoTask 的观测手段分三层，按排障深度递进：

层级 手段 用途
程序内 事件总线（task.created/started/completed/failed） 业务侧实时感知，触发回调或告警
程序内 pool.get_queue_size() 等查询接口 提交前水位检查，背压决策
独立面板 pip install neotask[ui] 的 Web UI 看队列深度、任务历史、失败分布，排障用

运维视角的两个健康信号值得盯：队列深度的斜率（持续爬升说明消费能力不足，先看执行器是不是在外部 I/O 上空等，再考虑加并发或扩容）；失败率的突变（下游服务抖动会第一时间体现在这里，重试次数曲线是前置信号）。加装 [monitor] extra 后还有基于 psutil 的系统指标采集，可以接进现有的告警体系。

八、什么时候该切换 Redis 分布式模式？

单进程写法出现以下任一信号时，就该升级了：

  1. 多进程 / 多机部署：任务需要被多个消费者抢占，且同一任务不能被重复执行

  2. 节点会挂：worker 宕机后，它领走的任务需要被自动回收重派

  3. 需要防重入：关键任务要靠分布式锁兜底

pip install neotask[redis] 后，NeoTask 基于 Redis 心跳 + 回收器 + 僵尸锁扫描实现节点故障恢复，消费端去中心化，不依赖中心调度器。生产语义（锁续期、孤儿任务、预取水位）在文档系列里有源码级展开：

  • 架构设计：三种部署形态与两阶段生命周期

  • 分布式锁：Redis 看门狗 + 任务抢占与故障恢复

  • 预取机制：批量拉取 + 高低水位 + 自适应策略

  • 故障恢复：回收器 + 僵尸锁扫描 + 孤儿任务

  • 性能基准：实测数据解读与调优

七、Celery 还是 NeoTask？一句话选型

两者并不互斥：成熟度与生态优先选 Celery；单体内嵌、低运维、纯 asyncio 技术栈选 NeoTask。典型路径是原型期用 NeoTask 内嵌跑，任务量上来后再评估是否需要迁移——而如果你需要 Redis 分布式能力，NeoTask 本身也能撑住相当规模。

最后给三条工程结论：

  1. 先想清楚任务的丢失容忍度，再选存储后端——这比任何性能参数都优先；

  2. 背压策略在写代码时就定好（捕获 QueueFullError 的三选一），不要等队列真满了再补；

  3. 延时任务不要自己拿 dict + 定时器模拟——到期转正、重启恢复、优先级一致性，这些细节自研很容易漏。
