NeoTask 最佳实践：调优入口只有一个配置类 + 预取/执行器/重试三大要点

📚 返回首页 | 📖 快速上手 | 📘 API 参考 | ⚙️ 配置说明 | 🐙 GitHub | 🐱 NeoTask 官网

版本基线：本文对照 neotask 1.0.2（PyPI 发布版）。所有"建议配什么参数"都经过生效链核实——先确认该参数真的被消费，再谈怎么调。🔧 = 真实源码，📝 = 示例代码。

概述：三个先决认知

  1. 调优入口只有一个：TaskPoolConfig。v1.0.2 里性能/可靠性相关的生效参数（并发、预取、超时、重试、存储、锁）全部由 TaskPoolConfig 一个类消费（🔧 api/task_pool.py:100-112 装配链逐一取值）。注意：WorkerConfig 在源码中无实例化；PrefetchConfig 只由 WorkerPool 内部从 prefetch_size 派生，TaskPool 路径不读取手工构造的实例——调优请直接改 TaskPoolConfig。

  2. 三个关键事实：批量提交 ≠ 更高性能（是 for 循环语法糖）；重试延迟是线性递增不是指数退避；不存在"低优先级任务自动提升"机制。三者都影响方案设计，见第二、三节。

  3. 通用工程建议与框架能力要对齐：NeoTask 1.0.2 没有内置 HTTP API 服务、没有任务级个性化重试配置、没有优先级老化——凡是需要这些能力的设计，要么绕道实现，要么换方案，别在配置里找开关。

一、架构选型实践

1.1 存储后端：先问"几个进程在跑"

场景 推荐 理由（源码级）
开发 / 单元测试 memory 无外部服务、零文件；进程内最快；重启即失
单进程生产（脚本/常驻单节点） sqlite 落盘可恢复；无需额外服务
多进程 / 多节点生产 redis 唯一能跨节点共享队列与状态的模式

三个必须知道的存储要点（细节见《任务持久化》）：

  • SQLite 的"单进程"是硬约束：出队是"SELECT 后 DELETE"的非原子两步（🔧 storage/sqlite.py 的 pop），两个进程抢同一队列会重复取到同一任务。同进程内多 Worker 没问题（共享队列对象），但别用多进程/多副本压同一个 SQLite 文件；

  • SQLite 默认路径有分叉坑：任务仓库默认 data/tasks.db、队列仓库默认 tasks.db（不同类、不同默认路径）。生产代码请用 TaskPoolConfig.sqlite(path="同一绝对路径") 显式统一，别依赖默认值；

  • Redis 模式才具备锁与节点心跳：内存/SQLite 模式下 get_active_nodes() 恒为 []、无分布式锁看门狗——"故障转移"能力只在 redis 档成立。

📝 生产常用构造（类方法带真实默认）：

Redis 部署本身建议走 Sentinel/Cluster 并开启密码——这是存储层可用性的兜底，与 NeoTask 无关但缺了它"分布式"无从谈起。

1.2 执行器：ExecutorType 是枚举，同步函数进 ASYNC 会卡死全场

真实执行器类型（🔧 executor/factory.py:19）：ExecutorType.ASYNC / THREAD / PROCESS / CLASS / AUTO，对应字符串值为 "async"/"thread"/"process"/"class"/"auto"。

三个源码级事实，直接影响选型：

  1. ExecutorFactory.create 只认枚举：传字符串 executor_type="async" 会一路比对失败，走到 raise ValueError(f"Unknown executor type: ...")（🔧 factory.py:71-72）——网上大量示例是错的；

  2. 同步函数会被"静默包装"：不管选哪种执行器，ExecutorFactory 都会把同步函数包成 async def wrapper（🔧 factory.py:77-82）。若你保持默认 ExecutorType.ASYNC，同步函数实际是在事件循环线程里同步执行——一个 CPU/阻塞型同步任务会卡住整个池的所有 Worker（所有 Worker 协程共用一个事件循环）。选型结论：

    • 异步函数 + I/O 密集 → ASYNC（默认，最优）；
    • 同步函数（含调用同步 SDK/requests/本地 CPU 计算）→ 必须显式 THREAD（轻）或 PROCESS（重 CPU）；

  3. AUTO 的自动选择只看函数形态：协程函数 → ASYNC；有 execute 方法的对象 → CLASS；其余同步函数 → THREAD（🔧 factory.py:54-62），AUTO 是比默认更安全的懒人选项。

二、配置调优：唯一生效入口 TaskPoolConfig

先看装配关系（🔧 api/task_pool.py:100-112）：TaskPool 把 config 中的 worker_concurrency / prefetch_size / task_timeout / enable_prefetch / max_retries / retry_delay 逐一喂给 WorkerPool，其余监控、锁、分布式组件分别读各自的 config 字段。凡是下表没列的参数（如 prefetch_min_threshold、reclaimer_interval），调了也没有反应（死参数全清单见《配置说明》）。

2.1 Worker 并发：worker_concurrency（默认 10）

worker_concurrency 是池内同时执行的任务数上限（内部 asyncio.Semaphore，🔧 worker/pool.py:72），与执行器类型协同生效：

  • 执行器为 ASYNC（任务真异步）：并发可以大，I/O 型任务建议 30-100，吃的是协程开销；

  • 执行器为 THREAD：受线程池 max_workers 上限约束，再高也只是排队，建议两者同量级；

  • 执行器为 PROCESS：max_workers 即进程数，别超过 CPU 核数。

从默认 10 起步，用压测数据调，而不是拍脑袋定"核数×N"——真实瓶颈通常在下游（DB/API），先看队列积压与任务耗时（见第六节排障）。

2.2 预取机制：调 prefetch_size，内部参数自动派生

预取只在 enable_prefetch=True（默认）时创建预取器，且配置是自动派生的（🔧 worker/pool.py:82-90）：

你调的 内部实际值
prefetch_size（默认 20） 每次预取数量 = 你给的值
—（自动） local_queue_size = prefetch_size × 5
—（自动） min_threshold = max(1, prefetch_size // 4)（低于它触发预取）
—（自动） max_threshold = prefetch_size × 3（高于它停预取）
—（自动） 策略固定 HYBRID

调优结论：

  • 高吞吐流水线：prefetch_size 调大（如 50-100）→ 本地队列与阈值自动放大，减少取任务次数；

  • 低延迟在线服务（要高优任务尽快插队）：prefetch_size 调小（如 5）→ 本地缓冲小，新提交的高优任务更快被取到；

  • TaskPoolConfig.prefetch_min_threshold 是死参数（TaskPool 装配不读它，🔧 task_pool.py:103 只传了 prefetch_size），别浪费时间调；

  • 手工构造 PrefetchConfig 只对"脱离 TaskPool 自己组装 WorkerPool + TaskPrefetcher"的定制场景有效——日常调优请直接改 prefetch_size；

  • 关停安全：WorkerPool.stop() 会把预取器中未消费的任务 drain_back 回队列（按真实优先级重新入队），不会因关停丢任务；空队列时预取循环带 0.1~0.5s 指数退避，避免空转打 Redis。

2.3 重试策略：线性退避，且只有全局两参数

真实机制（🔧 worker/pool.py:372-401）：任务失败后若 retry_count < max_retries，框架把状态重置 PENDING、retry_count + 1、按 delay = retry_delay × 新的重试次数 重新入队（🔧 pool.py:400）。

三个推导结论：

  1. 不是指数退避：retry_delay=1.0 时第 1/2/3 次重试延迟是 1s / 2s / 3s（线性）。真正的指数退避需要自建（见下）；

  2. 参数是池级全局的：max_retries=3、retry_delay=1.0 属于 TaskPoolConfig，没有任务级个性化重试配置。想"关键任务 5 次、普通任务 3 次"只有两条路：建两个不同配置的 TaskPool，或在 executor 内做业务级重试（捕获可重试异常自行重试后在池层表现为一次成功）；

  3. 手动 pool.retry(task_id) 绕过次数上限：它只是重新入队（dispatcher.redispatch 不校验次数、不递增计数，见《API 参考》1.5），适合做"人工干预重试"。

📝 需要指数退避时的自建方案（业务内退避 + 池层一次性成功）：

为什么这么设计（源码注释之外的事实）：池层重试是"断线续传"式保底（进程崩溃后任务按快照重跑），不是业务重试器；把业务重试放池层会导致业务错误与瞬时错误无差别重试，浪费 Worker。

2.4 任务超时：task_timeout 与 ttl 是两个东西

  • TaskPoolConfig.task_timeout（默认 None = 不超时）：有值时 Worker 用 asyncio.wait_for 包裹执行（🔧 worker/pool.py:302-306），超时按失败进入重试链路。防悬挂任务用这个；

  • submit(..., ttl=3600)：任务"生命周期"元数据，供清理与回收判据参考（详见《任务持久化》），不能当执行超时用。

生产建议：所有线上池至少给一个 task_timeout（如 300s），否则一个 while True 的任务会永久占用并发额度；长任务单独设池放宽超时。

三、提交与等待模式实践

3.1 批量提交没有性能增益

submit_batch 的实现是 for 循环逐个 submit（🔧 task_pool.py:501-512），无批量原语、无事务：耗时 ≈ 逐个提交之和，且中途失败前面已提交的不回滚。适用场景只有"少写几行代码"；要提升提交吞吐，正确的杠杆是预取/存储端（Redis pipeline 不在 v1.0.2 内，需自行扩展）。批量消费同理——Worker 侧一次 pop 一批靠的是预取器，不是 submit_batch 的镜像。

需要"全部提交成功才算成功"时自行校验：

3.2 wait_all 的时间预算与失败可见性

wait_all(task_ids, timeout) 是串行等待：每个任务独立计时 timeout（🔧 task_pool.py:537-550），最坏总耗时 N×timeout；任何失败/超时被吞成 {"task_id": {"error": "..."}} 字典。生产代码要么分批等，要么自己并发等待（示例见《API 参考》故障 3）。判失败的标准是结果字典里出现 "error" 键，别用 try/except 判断——wait_all 永不抛。

3.3 任务合并与分片（框架无关但真实受益）

每条任务 = 一次存储写 + 一次事件 + 一次队列操作。把 10000 条 1ms 的零碎任务合并成 100 条 100ms 的批次任务，调度开销可降两个数量级（配合 3.1 的分批提交）。前提是执行函数支持批处理且幂等。

3.4 避免饥饿：没有"优先级提升"，只有入场控制

NeoTask 的优先级队列是纯静态优先级序（内存 heapq / Redis ZSET 均按 priority 排序），不存在"长时间等待的低优先级任务自动提升"机制，也没有老化策略。防止低优任务饿死只能靠入场控制：

  • 限制高优任务的提交占比与总量（高优刷屏 = 低优饿死）；

  • 把低优任务拆小 + 用 submit(delay=...) 错峰，避免与高优洪峰同场；

  • 队列有上限 queue_max_size（默认 10000，🔧 config.py:179）；满了时 TaskDispatcher.dispatch 会抛 QueueFullError（neotask.common.exceptions.QueueFullError，底层 push 返回 False，🔧 dispatcher.py:78-93）——提交端捕获它做背压/重试即可，任务不会滞留在 PENDING。若 submit 后迟迟不 running 且 queue_size 贴着上限，先查是不是队列满被拒了。

3.5 cancel / delete / retry 的边界（三个真实语义）

  • cancel：只对排队中（PENDING）任务可靠。取消 RUNNING 任务只是改状态——不中断执行中的函数，函数成功返回后状态会被覆写回 SUCCESS（Worker 成功路径无二次状态检查，🔧 worker/pool.py:311）；

  • delete：不区分状态、恒返回 True；删运行中任务，Worker 完成后会以旧快照重建记录；

  • retry：不校验失败状态，可对任意任务"硬重试"。

所以生产代码的"取消 + 补偿"要自己闭环：先 cancel，再用 wait_for_result_async 短超时确认终态，必要时由业务侧幂等兜底。

四、部署与运维实践

4.1 优雅关闭：真实 shutdown 语义与信号集成

真实关闭顺序（🔧 task_pool.py:369-443）：停收新任务 →（graceful=True）等队列清空（受 timeout 约束）→ 停分布式组件 → Worker 停（graceful, timeout）→ 事件总线停 → 关存储连接。两个边界要知道：

  1. shutdown 是阻塞同步方法，内部向事件循环线程投递关闭协程并 future.result(timeout+5) 等待；必须从非事件循环线程调用（在事件循环线程内调用会死锁，见《API 参考》故障 1）；

  2. 等待队列清空 + Worker 收尾的总时长可能超过 timeout 一点（shutdown 内部等待是 timeout+5），容器探针给的宽限期要比 timeout 大。

📝 信号集成（SIGTERM 由主线程处理，安全）：

K8s Deployment 侧要点：terminationGracePeriodSeconds 应 ≥ shutdown timeout + 10s；preStop 钩子可省——SIGTERM 已足够，关键是容器内进程收到信号后别被立即 kill。

4.2 日志：框架自带一套体系，basicConfig 管不到它

v1.0.2 内部日志走自有体系（🔧 common/logger.py）：模块级函数 debug/info/warning/error/critical（🔧 logger.py:509-525）绑定全局 Logger(name="NeoTask")，文件侧是按天轮转的 DailyRotatingFileHandler（10MB/份、保留 30 份、最多 15 天，🔧 logger.py:28-40），控制台带彩色输出，配置由 LoggingConfigManager 管理（🔧 logger.py:261）。三个运维要点：

  1. logging.basicConfig(...) 只配置标准库 root logger，影响不到 neotask 内部日志（它自带 handler 且初始化时清空再装自己的）；

  2. 生产统一收集：neotask 日志默认写到其日志目录（按天命名文件，路径解析见 utils/path_utils.py），把该目录挂到 stdout 重定向或 sidecar 采集即可；不放心就盯着 logs/ 下的 neotask-YYYY-MM-DD.log 之类的轮转文件（见 logger.py 的 _generate_dated_filename）；

  3. 想调级别/输出，走 get_logging_manager() 提供的配置能力，不要试图给 logging.getLogger("NeoTask") 加 handler——模块初始化时会清理 handlers。

4.3 监控：没有现成 HTTP 端点，自己轮询

v1.0.2 不提供现成的 HTTP 端点：WebUIServer 无自动实例化方，contrib/prometheus.py 是仅含文档字符串的占位（见《节点监控》）。可落地的监控组合：

  • 存活探针：定时调 pool.get_stats()，若调用卡死/抛异常 → 事件循环可能已挂，重启进程；get_health_status() 也可直接作健康视图；

  • 积压告警：queue_size 持续增长或超过阈值（默认 queue_max_size=10000）；

  • 消费健康：pool.get_worker_stats() 观察各 Worker active_tasks/is_busy；get_stats()["metrics"]["avg_execution_time"]（启用 metrics 时）判断任务是否变慢，avg_retry_count 判断重试是否异常升高；

  • Prometheus：用 ReporterManager + PrometheusReporter 推 Pushgateway（上报器路径），或自己定时抓 get_stats() 转文本暴露——v1.0.2 无内置 /metrics 拉取端点，两条路都可行。

注意：get_health_status() 为读时刷新——结果在 HEALTH_CHECK_TTL=5.0 秒内复用缓存，超时重新执行检查；单项检查超时（DEFAULT_CHECK_TIMEOUT=5.0）判该检查 UNHEALTHY 并标注"timed out after Xs"；无 psutil 时 system 检查为 HEALTHY 并附 {"available": False}。可直接用于存活/健康探针。

4.4 网络面与安全

1.0.2 没有对外 HTTP API 服务，唯一网络面是 Redis 连接。加固清单：Redis 开密码（redis://:pass@host 已支持）、限制来源 IP、不暴露公网；任务数据敏感时提交前加密（见第五节）；容器以非 root 运行并限制日志目录写权限。

五、任务数据与安全实践

5.1 data/result 必须 JSON 可序列化（存储时的硬约束）

任务实体转存储格式的 to_dict() 会对 data 与 result 执行 json.dumps（🔧 models/task.py:68/79），而每次提交都会调用它来构造 task.created 事件载荷（🔧 core/lifecycle.py:82）——所以提交不可序列化对象（bytes、set、自定义类）时，无论哪种存储模式都会在入队前直接抛异常（memory 模式 save 只是 deepcopy、不序列化，但根本到不了那一步）。规则：

  • data 只放 dict/list/str/int/float/bool/None 的嵌套组合；

  • 二进制内容先 base64 编码成 str；

  • datetime 先转 ISO 字符串（框架时间字段自己做转换，但你 data 里的 datetime 不会）。

5.2 加密示例的字节坑

Fernet 加密示例有一个必现的字节坑：cipher.encrypt() 返回 bytes，直接放进 data 后 json.dumps 必然失败。正确姿势是加密后转文本：

解密密钥放环境变量/Secret 管理，别进代码库；加密只保护存储层，进程内存中的明文无法避免。

六、常见问题排查速查

6.1 任务积压：先看 stats，别猜

注意：TaskPool.get_stats() 没有 active_workers 键（那是 TaskEngine.get_stats() 的键），读了会直接 KeyError。排查路径：

  1. queue_size 持续 > 0 且 running 很小 → Worker 没在干活：查执行器类型（同步函数误配 ASYNC？）、pause 是否被误调；

  2. queue_size 大且 running 接近并发上限 → 任务变慢：查 metrics.avg_execution_time 走势、下游依赖；

  3. 一切正常但积压 → 提交速率超过处理速率：加节点（redis 模式）或调大并发。

6.2 任务重复执行/丢执行

  • Redis 模式：Worker 执行前拿 task:{id} 分布式锁（ttl=30s + 看门狗按 0.3× 间隔续期，🔧 worker/pool.py:260-281）。任务执行超 30s 且看门狗失效（如事件循环卡顿）时锁会过期，另一个节点可能重复取走同一任务 → 业务幂等是最终防线；

  • 内存模式没有锁：同进程内靠"状态机 + PENDING 检查"防重（🔧 pool.py:255-258），进程重启即丢内存队列；

  • SQLite 多进程：非原子 pop 会重复取任务（见 1.1），禁止多进程共写同一文件；

  • 调参方向：长任务把 lock_timeout 调大（默认 30），别只调任务超时。

6.3 进程"卡死"无日志

优先怀疑两类死锁（都可复现，见《API 参考》故障 1/2）：

  1. executor 内调用 pool.wait_for_result()/pool.shutdown() 等同步方法——事件循环线程里自己等自己；

  2. 同步阻塞函数（requests、while True 轮询）配了默认 ASYNC 执行器——单个任务卡住整个循环，其他任务全部假死。

自查：pool.get_stats() 是否也卡住？是 → 事件循环被占，重启进程并改执行器配置。

6.4 状态"倒退"：SUCCESS 变回 / 删了又出现

都是语义边界踩坑（第三节 3.5）：cancel RUNNING 任务后函数成功返回 → 状态被覆写 SUCCESS；delete 运行中任务 → Worker 完成时 repo.save 重建记录（SQLite INSERT OR REPLACE 等 upsert 语义）。处理：管理操作只对 PENDING 任务执行；运行中任务要"终止"请从业务侧打断（如检查取消标记）。
