|AIAgent
|浏览量:

指标是编的还是测的？从 PenShot、NeoTask、PenClip 看评测驱动开发

传统软件的"能用"有客观标准：接口返回 200、断言通过、负载压得住。AI 应用麻烦在"能用"是概率性的：分镜拆得连贯不连贯、提示词生成得好不好、检索召回准不准——每一次都有结果，但每次结果都不完全一样。这种概率性带来一种特有的事故形态：功能"感觉有效"，团队基于感觉迭代，直到某天用户告诉他们真相。

解药只有一个词：评测。但"做了评测"和"评测驱动"是两回事——前者是把跑分当装饰，后者是让每一个能力声明都有出处。我们在做 PenShot（剧本分镜智能体）、NeoTask（分布式任务池）、PenClip（视频混剪智能体）的过程中，踩过编不出指标的坑，也修过评测脚本自己的 bug，逐渐沉淀出三个产品的共性做法。本文把这三块基石拆开讲：口径决定怎么测，诚实决定敢报什么，前置决定何时测。每个产品的机制细节在官方文档有专门展开（召回评测、性能基准），本文聚焦方法论。

一、基石一：口径——NeoTask 用四个数字教会的事

NeoTask 的官方基准报告里有一组看起来"自相矛盾"的数字：优先级队列 31 万 ops/s，TaskPool 端到端 1697 ops/s，IO 任务 4671 ops/s，持续负载 64.6 ops/s。同一个框架，最慢和最快差了四个数量级——不是框架不稳定，而是这四个数字测的根本不是同一段东西：

数字 测的链路 负载 回答的问题
312,443 ops/s 纯内存堆操作（push/pop） 无 队列数据结构多快
1697 ops/s 提交→存储→调度→执行→回写全链路 noop 框架整体多快
4671 ops/s 全链路 + 20 worker 并发 5ms 睡眠 IO 型负载能并发多高
64.6 ops/s 5 秒持续提交 light 稳态低频提交的体感

差距为什么这么大？端到端测试里每个任务要经历完整生命周期——提交入队、存储写、worker 取任务、状态置 RUNNING、执行、状态回写、事件发布——每一步都有协程切换与状态操作，即使任务本身是 noop，事件循环的调度开销也被逐段放大。单任务全链路约 0.59ms，其中执行只占几十微秒，其余全是框架开销。队列组件的 31 万与整个框架的 1697，都是真的，但混用口径的对比是假的——做架构选型（NeoTask vs Celery vs 自研）必须用端到端口径，看队列数字选框架等于看轮胎直径买车。

光有口径还不够，数字必须与环境绑定出现。NeoTask 的基准报告原文里附了一张环境表，这是数字具备可比性的前提：

项目 说明
操作系统 Windows 10
Python 3.10.11
CPU Intel i7-10750H（6 核 12 线程，移动平台）
存储后端 内存存储（Memory）
版本 v0.3.0 时期测得（2026 年 4 月）

读这张表要带着三个提醒：内存存储意味着最乐观口径——不含持久化 IO 与网络往返；Windows + 笔记本 CPU 的绝对数值普遍低于同代 Linux 台式机；v0.3.0 不代表 v1.0.2 的水平——预取优化、看门狗、回收机制都是之后的版本才加的，更不代表接了 Redis 之后的分布式部署水平。一张没有环境戳的基准表，本质上是一张无法验证的声明。

这份报告最重要的启示不是任何一个数字，而是口径纪律。拿到任何一行吞吐数字，先问五个问题：测的是哪段链路？什么负载？什么环境（OS/Python/CPU/存储后端）？什么统计口径（吞吐还是 P95/P99，含不含排队）？什么测试意图（压极限还是模拟稳态）？五个问题没答清之前，数字不能用。

支撑这套口径的是基准脚本的一个设计决定：noop / light / cpu / io 四层执行器，把"框架开销"与"业务开销"解耦：

noop 任务体约等于零，测的是纯调度链路上限；light 模拟微任务（最接近大量小任务的生产画像）；cpu 给可控计算量（测 worker 并行收益）；io 任务睡眠（测并发度）。用"可控负载"而不是真实业务代码做基准，结果才能跨机器复现、跨版本对比——拿真实业务测，测出来的其实是下游 API 的延迟分布，框架优劣被噪声淹没。这四个执行器还有一层工具价值：它们本身就是负载画像的构造模板——评测自己的系统时，照着这四类把业务负载对号入座，比凭感觉写压测脚本靠谱得多。

统计口径上还有一条容易被忽略的细节：基准结果同时报告 avg / p50 / p95 / p99 四档延迟，而不是只给平均值——平均延迟对长尾无感，P99 才是线上体感的代理指标。一个均值漂亮、P99 爆炸的系统，用户体验是"偶尔卡死"而不是"挺快的"。实现这个统计骨架的代码朴素得出乎意料：

排序取位而已，没有任何统计库依赖。这里想说的是：报分位数的门槛其实低到不值得找借口——难的不是实现，是记得在报告里放这一栏。

这套基准里还有两个反直觉的细节，比数字本身更有教育意义：

其一，Worker 扩展性 1.00x 是个诚实的好结果。 官方实测数据摆出来是这样一个形状：

Worker 数量 吞吐量
1 801.58 ops/s
2 853.25 ops/s
4 805.08 ops/s
8 858.27 ops/s

从 1 加到 8，吞吐纹丝不动——因为测试用的微任务瓶颈在提交端（事件循环串行 submit），不在执行端，队列里始终没有积压。报告如实记录这个"不好看"的结果，而不是挑一个漂亮的任务类型掩盖它。正确读法是：微任务加 worker 无效；想让并发有意义，执行时间必须显著大于调度开销（IO 任务就是 4671 ops/s 的样子）。一个从不暴露负面结果的基准，测什么都好看，也就什么都说明不了。

其二，断言阈值故意定得极低。 基准脚本里的回归断言是"吞吐下限 1000 ops/s"，而实测 30 万+——差三百倍。这不是宽松，是设计：CI 机器上性能波动两个数量级都正常，阈值设在"掉到不足千分之一才算失败"的位置，只拦截结构性破坏（死循环、锁死、O(N²) 引入），不误伤环境抖动。把阈值贴到实测值，基准测试会变成天天误报的"狼来了"，最后被开发者跳过——那才是真正的回归失守。回归守护的价值在于长期有人听它报警，不在于报警多敏感。

顺带一提，持续负载那个 64.6 ops/s 是报告里最"难看"也最有信息量的数字——它比端到端吞吐还低 26 倍，看起来像框架有严重问题。但对照脚本读法就明白：它模拟的是"5 秒内低频持续提交"的稳态场景，而脚本的核心循环是每提交一个任务就 await asyncio.sleep(0.001)——意图是模拟每 1ms 来一个任务的稳态流。

数学验算一下：5 秒提交了 323 个任务，平均每轮循环 5000ms / 323 ≈ 15.5ms——脚本明明只让协程睡 1ms，多出来的 14.5ms 哪来的？根因在操作系统：Windows 默认定时器分辨率约 15.6ms（除非进程主动调用 timeBeginPeriod 提频），asyncio.sleep(0.001) 在 Windows 上的实际唤醒周期被放大到 ~15.6ms。于是这个数字的提交速率不是被框架限制的，而是被操作系统定时器限制的——在 Linux 上跑同一段脚本，结果会完全不同。

读基准报告的乐趣正在于此：难看的数字往往藏着口径的秘密，漂亮的数字往往藏着选择偏差。而两个方向的破译都依赖同一件事——读脚本，不只是读结果。

把口径纪律落到对外表达上，可以收敛成三条军规：分口径引用——引用任何数字都带上"端到端/队列/IO/稳态"的口径限定；带环境戳——数字与"什么机器、什么版本、什么存储"绑定出现；给复现命令——报告附上基准脚本的运行方式，读者能自己验。三条都做到，数字才有资格被别人引用。

二、基石二：诚实——PenShot 召回评测的撤回文化

如果说口径解决"怎么测"，PenShot 的召回评测实践解决的是更难的问题：测出来的东西敢不敢如实报。

PenShot 的三层记忆（短期 Redis 滑动窗口、中期 LLM 摘要、长期 Chroma 向量库）是分镜一致性的地基，角色卡检索不准，"第 30 场还有第 3 场的那张脸"就保不住。给这套系统做评测时，我们定过三条纪律：所有代码结论以源码为准、可回查；所有数据要么可复现、要么明确标注属性（真机证据与理论分析分开陈述）；宁可指出项目当前实现的不足，也不为了"显得高级"而堆砌概念。

第一条纪律落地后，评测报告的开篇不是结论而是一张"真机环境表"——所有配置都注明证据来源，读者可以逐行复核：

组件 真实配置 证据来源
LLM DeepSeek deepseek-chat（备用 Ollama qwen3:4b） .env + 运行日志
嵌入模型 DashScope text-embedding-v4（配置 1536 维，实测落盘 1024 维） .env + 日志
重排序模型 BAAI/bge-reranker-large（约 2.1GB，未接线） .env + 模型目录
短期记忆 Redis db1，20 条滑动窗口 日志 + 源码
长期记忆 Chroma（SQLite + HNSW） 数据目录快照
脚本知识库 LlamaIndex SimpleVectorStore（JSON 全量加载） 数据目录快照

这张表的价值不在罗列配置，而在让"证据会过期"成为可管理的状态：版本升级后逐行重测替换，而不是让一份两年前的配置表冒充现状。给证据标来源，本质上是给评测报告本身做版本管理。

第三条纪律尤其重要，它要求对每个能力都标注真实口径——“已接线（被生产代码调用）”“已实现未接线（代码完整但零调用方）”“规划中（只存在于路线图）”。PenShot 的检索链路里，生产路径只有提示词模板检索（余弦相似度 + 0.7 分数及格线）和场景相似检索；混合检索、MMR 多样性检索、BGE 重排序的装配代码都在，但全仓库没有任何生产调用方——它们是"已实现未接线"。把未接线的能力当已接线来宣传，是 AI 产品文档最常见的失真，而三口径标注法是这种失真的解药。

这三条纪律立刻招来了三个"不好看"的发现——恰恰是最有价值的部分：

发现一：配置与事实脱节，且不报错。 配置里嵌入维度写的是 1536，真机向量库里实测落盘是 1024——text-embedding-v4 支持多档维度，dimensions 参数没有生效，模型按自己的默认值输出了。这个偏差不会抛任何异常，但任何按"1536 维"假设处理数据的代码都会错位，未来按配置重建索引时新旧向量无法混用。类似的还有：重排序模型的路径解析带降级链，路径不存在时静默回退为模型名、可能触发约 2.1GB 权重的联网下载，日志里只有一行 warning。静默失效是评测的第一号敌人：它不 crash、不告警，只在结果里悄悄变质。

发现二：评测脚本自己有 bug。 项目里唯一的"重排序对照测试"，传入的 use_rerank 参数从未被实现读取——无论怎么调，脚本都会输出"重排序无效"。直接照搬这个脚本做决策，会得出完全相反的结论。教训很直接：评测工具本身也是代码，也要 review、也要验证它的有效性——用哑参数脚本跑出来的"对照实验"，比不做实验更危险。

发现三：样本量让指标失去意义。 真机脚本知识库只有 12 条记录（4 场景 + 8 角色），长期记忆 Chroma 集合在三个真实剧本下文档数全部为 0（写入要过"成功案例"门槛，数据还没积累起来）。在这种规模下谈"召回率 95%"是自欺——任何查询的返回都会被样本量淹没。同样，早期文章里"重排序把 top-1 准确率从 68% 提升到 86%"的说法没有任何测量依据（模型甚至没接线），被正式撤回；"绝大多数查询 100 毫秒内完成"之类的延迟数字同样撤回——代码里没有延迟埋点，索引里只有 12 条文档。

这就是"撤回文化"：没有出处的数字，撤回；只有理论依据的结论，标注"理论分析，非实测"；测不了的场景，明说测不了。PenShot 检查点机制至今没有公开性能基准，文档里写的是"在没有可复现基准的情况下，任何具体数字都不应被当作结论"——这句话看起来是减分项，实际上是整个评测体系可信度的来源。读者一旦发现你编过一次数字，你所有真实的数字都会被连坐。

三条纪律要可执行才有意义，对应的操作动作分别是：源码为准——报告里每个代码结论都标注文件路径与行号，让"可回查"不是态度而是动作；可复现——每个数据点配运行命令与环境说明，别人照着敲能得到同量级结果；宁可揭短——报告固定设置"局限与不足"一节，把没做到的事写在最显眼的位置。纪律落到动作，新加入的成员才不需要"领会精神"。

    Q -->|"真机可复现数据"| K["保留，标注环境与口径"]
    Q -->|"理论推演"| T["标注：理论分析，非实测"]

真机核对还有一层常被忽略的价值：定位真正的性能大头。以代码结构做理论拆解（明确标注"理论分析"），向量比对本身是纯本地 numpy 运算，即便上万条文档的线性扫描也在十毫秒量级；而查询文本的嵌入编码走云端 API，包含网络往返——当前链路的延迟大头大概率是嵌入 API 而非向量计算，这与"向量检索慢在计算"的直觉恰好相反，也直接决定了优化方向（本地嵌入缓存、批量嵌入）而不是盲目换向量库。

最后澄清一个实操问题：撤回不是简单删稿。实践里有三种形态，各有用途。数字撤回——在原文标注撤回原因与日期，让引用过的人能追踪到修正，而不是让旧数字在别人的文章里继续流传；结论降级——尚无实测但逻辑成立的判断，明确标注"理论分析，非实测"，保留参考价值也保留边界；引用链修正——错误结论若已被下游文档引用，沿引用链逐级修正，不能只改源头。撤回的目的不是装作没说过，而是校准信任：读者看到你撤回过错的数字，才知道留下来的数字是筛过的。

三、基石三：前置——PenClip 把验收写进版本规划

前两块基石都发生在"功能做完之后"。评测驱动的第三块基石是把它挪到前面：在写第一行实现代码之前，先定义什么叫做"做完了"。

PenClip 的版本演进文档里，每个版本的挑战清单都长成一张三列表：挑战、应对策略、验证方式。V0.1 MVP 阶段列了四个核心挑战，每个都带着量化验收线：

挑战 应对策略 验证方式
CLIP 标注不准（测试视频不在预定义标签内） 标签集合宽泛覆盖 + 匹配阈值降低 30% 标注召回率 > 70%
场景分割过碎 相邻同类标签合并 + 最小片段 2 秒 有效片段占比 > 80%
FFmpeg 转场调试困难 先 concat 拼接，稳定后叠加 xfade 无明显黑场或闪烁
架构认知偏差 文档明确 + 代码结构体现星型骨架 代码评审通过

V0.2 引入 LLM 指令解析时同样如此：“LLM 输出不可控"的应对是 JSON Schema 强校验 + 自动重试（最多 3 次），验证方式是结构合法率 > 98%。交付标准也量化到具体动作：3 个测试视频、一句话指令、5 分钟内出片、无明显黑场。V0.1 的交付标准写得同样具体：上传 3 个测试视频，输入"自我介绍放开头，活动放中间，风景放结尾”，5 分钟内生成完整视频、无明显黑场或音画不同步，且能力注册表可查询已注册的工作流、结构化日志完整记录执行链路。验收动作精确到"谁上传什么、输入什么、几分钟能看见什么"——这个粒度才叫验收，"体验良好"不叫。

这套做法的精髓在于验证方式先于应对策略被确定。传统流程是"写功能 → 测一下 → 看看多少分"，分数天然往后看齐——功能已经写完了，验收线怎么定都说得过去。PenClip 的顺序是反的：先定"标注召回率必须过 70%"，应对策略（宽泛标签 + 降阈值）和实现代码都为这个数字服务，没达标就是没做完，没有解释空间。验收线是需求的一部分，不是报告的一部分——这是"评测驱动"三个字里"驱动"的真正含义。

对 AI 应用来说前置定义验收还有一层特殊价值：LLM 行为不可控，"先把功能写出来看看效果"的迭代方式会让人在模糊地带反复摇摆（这版比上版好一点？还是差不多？）。有了量化验收线，摇摆被数字截断：结构合法率 98% 就是 98%，连续三个版本不达标就该换方案而不是继续调提示词。

验收线本身的制定也有三条经验。先跑首轮基线再定阈值——没有基线的阈值是愿望不是验收，"召回率 > 70%"这类数字应当来自首轮实测的分布，而不是拍脑袋；区分灾难线与目标线——灾难线（低于即失败，拦截回归）与目标线（本版本冲刺值，牵引优化）是两种阈值，混用的结果是团队对"失败"脱敏；验收必须可自动检测——依赖人工观感的验收线撑不过三个版本，"无明显黑场"这类描述要落到可脚本化的检查（帧亮度采样、音画偏移测量）才能长期执行。

还有一条配套的架构纪律让验收可持续：PenClip 从 V0.1 起所有能力都通过注册机制接入星型中枢，新增能力不修改中枢代码。这让每个版本的验收对象是增量能力本身，而不是"新代码有没有碰坏旧链路"——架构的稳定性把评测范围从全量回归缩小到增量验证，评测成本随版本数线性而不是平方增长。

这套注册机制还有一个容易被忽略的评测价值：能力注册表本身就是评测接口。V0.1 的注册协议要求每个能力自带完整的自描述信息：

注册字段 V0.1 示例
能力名称 linear_clip_workflow
支持的意图类型 ["PLAN_CREATE", "EXECUTE"]
所需参数 Schema {videos: list, slots: list}
输出格式 {timeline, output_path}
风险等级 medium

意图可枚举，意味着测试用例可以按意图穷举构造；参数有 Schema，意味着输入可以程序化生成；输出有格式声明，意味着结果可以自动断言；风险有分级，意味着评测深度可以按级分配——low 级冒烟验证、medium 级全量验收、high 级加对抗用例。评测对象从"整个系统"细化到"一次注册"，验收前置才不只是一句口号，而是有协议支撑的工程实践。

三者缺一都会退化成熟悉的形态：

退化形态 缺了什么 症状
选优型评测 诚实 只报好看的段落：31 万 ops/s 挂首页，1697 埋附录；"提升 18 个百分点"查无实验

三个产品各守住一角不是巧合：NeoTask 是基础设施，性能声明直接决定选型，所以口径纪律最重；PenShot 的核心资产是检索与记忆这类"效果型"能力，静默失效的代价最高，所以诚实性最重；PenClip 处在快速 MVP 演进期，版本节奏快，验收前置的收益最大。你的产品处在什么阶段、核心资产是什么，决定三块基石的优先级——但最好一块都别缺。

用一个虚构但典型的场景把三块基石串一遍。假设你在给客服系统加一个"AI 质检"能力，评测驱动的工作流是：前置——动工前先定验收线（误判率不高于人工抽检基线、结构合法率 98% 以上），写进需求文档；口径——拆开测，ASR 转写段、LLM 判断段、规则引擎段分别建基准，别用一个端到端准确率掩盖三段各自的退化；诚实——上线后只引用真机数据，代理指标与人工抽检的差距如实标注，没测过的场景写"暂无数据"。三步做完，这个功能的每个声明都有出处——评测驱动不是额外多做的事，而是把"出事再查"的精力前置成"声明先验"。

拿三问问自己的项目，就知道缺哪块基石：数字答不上口径五问，缺"口径"；文档里有"已实现未接线"却按已接线宣传，缺"诚实"；版本规划里没有验证方式列，缺"前置"。三个问题各花十分钟就能自测完，比任何评测框架的选型调研都该先做。

五、评测的边界：什么测不了也要说清楚

诚实性的最后一关，是承认评测本身有边界。三个实践里沉淀下来的"测不了"清单：

  1. 生成质量的主观维度：分镜的"导演感"、混剪成片的"节奏感"，目前没有客观指标。能测的是代理指标（结构合法率、时长合规、一致性检查通过率），代理指标与主观质量的差距要明说；

  2. 小样本场景的一切百分比：索引只有十几条文档时，任何准确率/召回率都被样本量淹没。诚实答案是"样本不足，暂无可信指标"；

  3. 没有基线就没有对比：所有"提升了 X%"的声明都隐含一个基线——基线是什么环境、什么版本、什么口径测的，必须一并交代，否则提升无意义；

  4. 跨环境外推：Windows 笔记本 + 内存存储 + 特定版本测出的数字，不代表 Linux 服务器 + Redis 集群 + 新版本的水平。评测文档必须写死"数据仅适用于文中记录的环境、版本与测试脚本"。

处理这四条边界的统一方法就是第二节的三口径标注法：真机证据、理论分析、规划中，三类结论分开陈述，绝不混装。读者看到一句没有属性标注的断言时，应当默认它是不可信的——写文档的人有责任让每个断言自带属性。

这四条边界还有一个共同根源：评测结论的可信半径由证据的覆盖范围决定。样本、环境、基线、主观维度——每一条都是在划定"这个数字在哪儿有效"。划定边界不是削弱结论，恰恰是把结论放进它能被信赖的位置。

六、把评测做成最小基础设施

三个产品还有一层不太显眼的共性：评测能力都以"随仓库交付的脚本"形态存在，而不是一份只存在于文档里的报告。NeoTask 的 tests/benchmark/ 目录放着四个基准脚本，PenShot 的召回评测脚本、PenClip 的交付验证动作都跟着代码走。这件事值得单独一节，因为它决定了评测是可持续的工程实践，还是一次性活动。

把评测做成基础设施，最小集是四件套：

  1. 脚本入仓：基准与评测脚本放进仓库的固定目录（tests/benchmark/、evals/），与代码同版本演进。评测可复现的第一前提是"测的东西"本身被版本化——脚本散落在个人电脑里，评测的可信度就依附于那个人；

  2. 结果带环境戳：每次运行的结果记录环境表（OS/Python/CPU/存储后端/版本/日期），没有环境戳的结果不能进报告、不能被引用——NeoTask 环境表的做法，抄就完了；

  3. 断言进 CI：给基准加"灾难线"断言（成功率下限、吞吐下限），让基准从一次性活动变成回归守护。阈值刻意定低，只拦结构性破坏，报警的公信力比灵敏度值钱；

  4. 报告四段式：环境 → 口径 → 结果 → 边界。前三段回答"数字从哪来"，最后一段回答"数字管不到哪"——缺了边界段的报告，等于宣布自己的数字适用于一切场景，恰恰是最快的失信方式。

基础设施化的本质是把可信度从个人转移到仓库：脚本可复现、结果可追溯、断言长期值守、报告自带边界。做到这一步，评测才配得上"驱动"两个字——不是某人心情好时的装饰品，而是每次能力声明都要过的一道闸。

四件套的共同点是便宜：没有一件需要专职平台团队——脚本入仓是复制粘贴，环境戳是打印几行变量，CI 断言是十几行代码，报告四段式是模板问题。评测基础设施的门槛从来不在技术，在于把"数字要有出处"当成发布的硬条件。最简的起步方式是先做到一件事：下一个能力声明写进文档之前，先跑一遍能产出它的脚本——习惯从这一步开始滚动。

七、落地清单：给你自己的 AI 项目

从三个产品的实践里抽出可以直接搬走的动作：

  1. 每个能力声明配一个出处：写进 README、官网、汇报材料的每个数字，必须能回答"谁测的、什么环境、哪段口径"，答不上来的删掉；

  2. 给能力标注三口径：已接线/已实现未接线/规划中（效果类能力），真机证据/理论分析/规划中（结论类声明）——未接线的能力不当已接线宣传；

  3. 基准先分离负载再谈数字：学 NeoTask 的 noop/light/cpu/io，把框架开销和业务开销拆开测，否则你测的是下游的延迟分布；

  4. 延迟报分位数不报平均：avg/p50/p95/p99 四档一起出，平均延迟对长尾无感，而用户的体感由长尾决定；

  5. 回归阈值定在"灾难线"而不是"实测线"：只拦结构性破坏，容忍环境抖动，守护报警的长期公信力；

  6. 真机核对一遍配置与落盘：维度、模型名、开关状态，配置写的不等于实际生效的——静默失效不会自己暴露；

  7. 评测脚本过 review：对照实验的开关参数被实现真正读取了吗？哑参数脚本会产出相反结论；

  8. 版本规划里先写验证方式：挑战、应对、验证三列齐全再动工，验收线是需求不是报告；

  9. 为小样本诚实：索引只有几十条文档时，别产出百分比指标——说"样本不足，暂无可信指标"比编一个数体面得多，也可信得多；

  10. 给评测结果配复现命令：报告里没有运行方式的结果等于占位符——把"谁测的"变成"你怎么验"，引用才有生命力。

八、工程结论

  1. AI 应用的"感觉有效"是一种债务——每次凭感觉的迭代都在积累不可证伪的声明，评测是唯一能把债务变成资产的手段：口径让数字可比较，诚实让数字可信任，前置让数字可执行；

  2. 评测体系自身的质量决定一切数字的质量：哑参数的对照脚本、不生效的配置、没有埋点的延迟声明——评测工具链自己先要被评测；

  3. 敢报难看的数字，是评测体系获得公信力的唯一路径：Worker 扩展性 1.00x、稳态负载 64.6 ops/s、检查点暂无基准、小样本无可信指标——这些"减分项"恰恰是让加分项被相信的原因。

回头看这三个产品的评测实践，最意外的收获是它们反过来改善了产品设计：为可测而定义的注册协议让能力边界更清晰，为诚实而梳理的调用链暴露了真正的接线缺口，为口径而拆分的执行器成了构造负载画像的模板。评测驱动的终点不是"数字好看"，而是系统本身变得可解释。

评测不是功能的对立面，而是功能的一部分：没有评测能力声明的 AI 产品，和没有质量保障的工厂一样，出厂的每一件都是样品。如果这篇文章只让你记住一件事，那就记住这个动作——下次写下"效果显著"四个字之前，先问自己一句：这个结论，我拿什么测的？
