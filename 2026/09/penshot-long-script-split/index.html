剧本变分镜还要人肉拆？用 PenShot 智能体把长剧本拆成 5 秒级视频片段

现在的 AI 视频模型（可灵、即梦、Veo 这一类）基本只吃 5 秒级短片段，而一部短剧的剧本动辄几十场戏。把剧本拆成"每个镜头 5 秒、角色形象前后一致、场景衔接连贯"的分镜脚本，是标准的导演级手工活——也是 PenShot 要自动化的那一环。

PenShot 是一个基于 LangGraph 的剧本分镜智能体：输入任意长度的剧本，输出可直接投喂给 AI 视频模型的分镜片段。内部由六个顺序执行的智能体节点组成流水线，每个节点"接收输入 → 调用 LLM 或规则 → 结果判定 → 进入下一节点或触发修复"。本文讲清楚三件事：怎么跑起来、流水线内部发生了什么、它擅长什么不擅长什么。

一、两条部署路径

路径 A：pip 安装

路径 B：Docker（推荐，环境隔离）

两类密钥通过环境变量注入（也可用 .env 文件，不要写进配置文件提交到仓库）：PENSHOT_LLM__DEFAULT__* 负责生成，PENSHOT_EMBED__DEFAULT__* 负责向量化。服务起在 8000 端口，提供 REST 接口；SDK 与 MCP 协议三条接入链路的差异在文档中心有专门对比。

二、六个智能体节点：流水线内部发生了什么

PenShot 把"剧本 → 分镜"拆成六个职责单一的节点，由 LangGraph 负责端到端协调：

节点 输入 → 输出 关键处理
剧本解析 原始文本 → 结构化剧本 格式自动识别 + LLM 提取场景/角色/元素 + 完整性评分
镜头拆分 结构化剧本 → 镜头序列 元素分组（对话合并规则）+ 三类时长估算器
视频分段 镜头序列 → 视频片段 超阈值镜头 LLM 语义切分 / 规则均分，保持连续性
提示词转换 视频片段 → 生成指令 产出可直接投喂视频模型的提示词
质量审计 生成指令 → 审计报告 规则校验，问题项回流修正
连贯性守护 全局视角审查 跨片段的角色/场景一致性检查

各节点的输入输出模型（ParsedScript、ShotSequence、FragmentSequence、AIVideoInstructions、QualityAuditReport）都是强类型的 Pydantic 模型——节点之间传的不是松散字符串，而是可校验的数据结构，这是流水线能稳定修复回流的基础。

flowchart TD
    A[剧本输入] --> B[剧本解析<br/>格式识别+语义提取]
    B --> C{完整性评分达标?}
    C -- 否 --> B
    C -- 是 --> D[镜头拆分<br/>元素分组+时长估算]
    D --> E[视频分段<br/>超长镜头语义切分]
    E --> F[提示词转换<br/>生成视频模型指令]
    F --> G[质量审计<br/>规则校验]
    G -->|问题项| F
    G -->|通过| H[连贯性守护<br/>跨片段一致性检查]
    H -->|漂移风险| F
    H -->|通过| I[分镜片段输出<br/>5 秒级 可直接生成]

值得注意的设计是两个回流环：质量审计发现问题退回提示词转换，连贯性守护发现漂移风险同样退回提示词重生成——生成质量不是靠一次调用赌出来的，而是靠校验层兜出来的。

三、三层记忆：为什么第 30 场还有第 3 场的那张脸

短剧最怕的是"角色漂移"：同一个角色在第 3 场和第 30 场长了两张脸。PenShot 的解法不是在提示词里反复堆描写，而是把约束结构化存取：

  1. 角色卡：解析阶段为每个角色建立结构化档案（外貌特征、服装、性格标签），镜头涉及该角色时按需注入提示词；

  2. 场景卡：场景的环境要素（时间、地点、光线、陈设）同样结构化，同一场景的多个镜头共享同一张卡；

  3. 风格卡：整部剧的视觉风格约束全局生效。

三层记忆配合向量化检索（这就是部署时要配 Embedding 模型的原因）：拆到第 30 场时，流水线按角色/场景名检索到对应的卡，把一致性约束写进当帧提示词。漂移的压制从"祈祷 LLM 记性好"变成了"检索必然命中"。

四、走读一遍：30 场戏短剧的拆解过程

用一个具体例子串起整条流水线。输入：一部 30 场戏、3 个主要角色的都市短剧剧本，约 2 万字。

第一站·剧本解析。格式识别判断出这是标准剧本格式，LLM 提取出场次结构、3 个角色的档案、关键道具，并对解析结果做完整性评分——角色是否有外貌描述、场景是否有环境要素。假设评分发现"反派角色的外貌描述缺失"，回流让 LLM 从对白与动作描写里补全，评分达标后输出结构化剧本。这一步决定了后面所有环节的质量上限。

第二站·镜头拆分。按叙事节奏与对话合并规则把 30 场戏拆成镜头序列，三类时长估算器给每个镜头估时长——对话多的场面按台词密度估，动作场面按节奏估，过渡镜头按经验值估。

第三站·视频分段。超过 5 秒级阈值的镜头进入二次处理：语义完整的走 LLM 切分（保持动作连续性），适合机械切分的走规则均分。输出是一串 5 秒级的视频片段序列。

第四站·提示词转换。每个片段结合角色卡/场景卡生成视频模型指令——"第 14 镜，女主在雨夜便利店门口，暖光，近景 5 秒"这样的结构化描述被转成可灵/即梦们真正吃的提示词格式。

第五站·质量审计 + 连贯性守护。审计器做规则校验（字段完整、时长合规、提示词自洽），守护器做跨片段检查（女主在第 3 镜和第 27 镜的服装是否一致）。任一环节出问题，退回提示词转换重生成。

全程对 LLM 的调用次数与剧本规模成正比——30 场戏意味着流水线要走几百次模型调用，这就是为什么检查点与断点续传对长剧本不是优化项而是必需品。

五、排障清单：三个最常见的卡点

按真实使用中出现的频率排序：

现象 根因 处理
解析评分反复不达标 剧本本身信息缺失（角色无外貌、场景无描述） 先人工补全剧本骨架再跑，或换更强的 LLM
中途 LLM 超时/限流 长剧本的调用密度高，撞上供应商限流 检查点续传接管，无需从头重跑；调整并发配置
记忆检索不准 Embedding 质量差或维度不匹配 核对 PENSHOT_EMBED__DEFAULT__* 配置与模型文档

第三条值得展开：角色卡检索靠向量化，如果 Embedding 模型配置错了（维度不匹配或用了低质量模型），"第 30 场拿第 3 场的角色卡"这个一致性保障就会静默失效——不报错，但生成结果里角色换脸。这类问题的排查入口是召回评测文档里的方法论。

六、工程边界：它擅长什么、不擅长什么

基于 v0.3.x 源码实测的结论，说清楚边界比吹能力更有用：

  • 擅长：叙事连贯的长剧本拆解、角色一致性要求高的连续剧、需要批量产出提示词的流水线场景

  • 不擅长：需要精确到帧的动作编排（这仍是导演的活）、对单镜头画面质量有极致要求的场景（取决于底层视频模型）

  • 依赖现实：生成质量与所配 LLM 强相关——解析、拆分、转换每一步都在调 LLM，模型能力直接决定下限；Embedding 质量影响记忆检索精度，角色卡检索不准，一致性约束就注入不到该注入的镜头

另一个值得预期的能力：工作流检查点。六段流水线跑几十场戏的剧本不是秒级的事，中途断掉不该从头再来——检查点机制把状态落盘支持断点续传，相关机制在文档里有专门展开（包括它当前版本的边界）。

文档中心对每一环都有源码级展开，重点推荐这几篇：

  • 节点详解：六大智能体的源码实现与规则逻辑

  • 一致性策略：多片段生成如何压制角色与场景漂移

  • 检查点：工作流状态落盘与断点续传

  • 召回评测：三层记忆真机实测与评测方法论

七、三条工程结论

  1. 一致性靠结构不靠祈祷：让"角色长一张脸"成为检索必中事件，而不是提示词工程的手气问题——这个思路在任何多片段生成场景（漫画、绘本、广告片）都可复用；

  2. 强类型数据契约是智能体流水线的地基：节点间传 Pydantic 模型而不是自由文本，校验和修复才有抓手；

  3. 先跑通边界内的场景：长剧本、强一致性、批量产出是它的主场；单镜头极致画质请直接把预算花在视频模型上。
