MySQL 为什么敢把数据先放内存？Buffer Pool 缓存与刷盘策略全景

发表于2026-09-28|更新于2026-09-28
|DB
|浏览量:

凌晨两点，一个跑批把主库的写入 RT 从 2ms 顶到了 800ms，告警群里炸开了锅。DBA 接手看了一圈：CPU 不高，磁盘不忙，唯一异常的是监控里脏页比例像坐了过山车——从 30% 一口气刷到 5%，然后又慢慢爬回来。这类"参数没动、就是周期性抖"的问题，十有八九和 InnoDB 的内存缓存与刷盘机制有关。

很多工程师对 MySQL 的印象停留在"有缓存所以快"，但一旦出毛刺就抓瞎：脏页是什么、什么时候刷、为什么 redo log 的大小能决定一台库的脾气？这篇文章把 Buffer Pool 的页管理、change buffer、redo log、checkpoint、doublewrite 和被移除的 Query Cache 串成一条完整的线，讲清楚 MySQL 为什么敢把数据先放内存，以及这套设计的代价。

阅读导览：
① 总览——InnoDB 在内存与磁盘之间到底放了几层东西；
② 一条 UPDATE 的流转——后文所有机制都挂在这条链路上；
③ Buffer Pool——按页缓存、三条链表、young/old 防污染 LRU 与预读；
④ change buffer——二级索引写入为什么能省一次随机读；
⑤ redo log 与三档刷盘——WAL 的交易、组提交与容量规划；
⑥ 脏页刷新与 checkpoint——系统稳定性的节拍器与刷脏抖动的来源；
⑦ binlog 与双 1——两阶段提交的顺序为什么不能反；
⑧ doublewrite 与 Query Cache——一个防止撕裂页，一个被 8.0 移除；
⑨ 三个故障场景复盘——毛刺、缓存污染、断电丢数据。

总览：内存与磁盘之间的五层设计

先建立一张总图。InnoDB 在内存与磁盘之间放了几层结构，各自解决不同的问题：

  • Buffer Pool：以页为单位缓存数据页和索引页，解决"读"的性能问题，是整个体系的中心；

  • change buffer：缓存对非唯一二级索引页的修改，解决"写二级索引必须先读页"的随机 IO 问题；

  • Log Buffer + redo log：把"数据页必须及时落盘"转换成"日志先落盘"，用顺序写换随机写，解决持久化与性能的矛盾；

  • 脏页刷新 + checkpoint：控制脏页以什么节奏回到表空间文件，是系统稳定性的节拍器；

  • doublewrite：解决部分写失效（torn page），保证断电后页是完整的；

  • binlog：Server 层的归档日志与复制基石，它的刷盘策略和 redo 组成著名的"双 1"配置。

这些组件服务的是同一个权衡：磁盘随机写慢、内存快但掉电即失。InnoDB 的答案可以浓缩成一句话：数据修改先在内存完成（快），用顺序写日志保证持久性（可靠），脏页由后台择机批量刷回（平滑）。理解了这一句，后面所有参数都有了存在的理由。

（下文以 MySQL 8.0 为主基准，涉及 5.7 与 8.4 差异处单独标注；除特别说明外，性能数字均为理论推演或标注了"示例"，不是实测数据。）

一、一条 UPDATE 的完整流转

先看一条最普通的更新语句，后文所有机制都挂在这条链路上：

sequenceDiagram
    participant S as SQL 层
    participant BP as Buffer Pool
    participant TS as 表空间文件（磁盘）
    participant LB as Log Buffer
    participant RL as redo log 文件
    S->>BP: 1 按 id=1001 定位数据页
    BP->>TS: 2 页不在内存，读入 16KB（随机读）
    TS-->>BP: 3 页载入，挂到 LRU old 区头部
    S->>BP: 4 在内存页中改行，页变为脏页
    S->>LB: 5 写 redo，记录物理修改
    S->>RL: 6 事务提交，按策略 write + fsync
    Note over BP,TS: 此时脏页尚未落盘
    BP->>TS: 7 后台 page cleaner 择机刷脏（先过 doublewrite）

六个步骤里有三个值得停下来想的问题。

第一，为什么第 4 步敢直接改内存里的页？ 因为第 5、6 步的 redo log 已经把"如何重做这个修改"记下来了。只要日志先持久化，数据页晚点落盘就不怕断电——这就是 WAL（Write-Ahead Logging，预写日志），InnoDB 一切设计的基石。

第二，为什么不干脆在提交时把数据页写回磁盘？ 一个 16KB 的页可能被改了 100 次，每次提交都写回就是 100 次随机 IO；只写 redo，是 100 次修改追加成几段顺序小写入。更关键的是 redo 是追加写的，两个事务改同一页互不影响磁盘位置，而随机写在并发下会互相拖慢。把"持久化的及时性"和"刷盘的高效性"解耦，是 WAL 最大的价值。

第三，脏页什么时候落盘？ 答案是"看情况"——由第五节的 checkpoint 机制决定，这正是本文的主角之一。

（简化说明：真实链路还包含 undo log 的写入、锁与 MVCC 可见性判断、change buffer 的可能介入、binlog 两阶段提交等，图中省略，后文逐一展开。）

二、Buffer Pool：以页为单位的缓存体系

2.1 为什么按页缓存，而不是按行

InnoDB 与磁盘交换数据的最小单位是页，默认 16KB（innodb_page_size=16384）。为什么不按"行"缓存？三个原因：

  1. IO 的物理特性：无论 HDD 还是 SSD，一次读取的成本大头在寻址与传输启动，读 1KB 和读 16KB 的耗时差别很小。按页缓存等于把一次昂贵 IO 摊给页内的几十行共用；

  2. 局部性原理：聚簇索引里主键相邻的行物理上挤在同一页，二级索引里键值相邻的项也在同一页，按页缓存天然利用了访问局部性；

  3. 实现复杂度：行级缓存意味着一致性、并发控制都要在行粒度上做，收益配不上复杂度。

Buffer Pool 的物理形态是一大片内存切成一页一页，每页配一个控制块（记录页号、链表指针、锁信息、LSN 等）。管理这些页靠三条链表，这是理解后面所有行为的地基：

  • free list：还没装内容的空闲页；

  • LRU list：所有"有内容"的页，按冷热排序；

  • flush list：所有脏页，按第一次被修改的时间（oldest_modification）从老到新排序——这保证了刷脏顺序与崩溃恢复的重放顺序一致。

读一个页的流程：先查页哈希表（页号到内存地址的映射），命中直接返回；未命中就从 free list 拿一个空页（free list 空了就从 LRU 尾部淘汰一个），读盘装入，挂到 LRU 的特定位置。这个"特定位置"就是下面要说的大门道。

2.2 改良版 LRU：young/old 双区与防污染设计

教科书式 LRU 在生产环境有两个致命弱点：

  • 预读失效：InnoDB 有预读机制（见 2.4），一次把相邻的几十页读进来，其中很多页可能根本不会被访问。它们挤在 LRU 头部，把真正的热页往后推；

  • 全表扫描污染：一次大扫描把所有页"摸"一遍，每页只访问一次。教科书 LRU 会把整张冷表塞进缓存，把原本的热页全部挤出，扫描一结束，命中率断崖下跌。

InnoDB 的解法是把 LRU 链表从中间分成两段：young 区（热数据，默认约占 5/8）和 old 区（默认约占 3/8），交界处叫 midpoint。新读入的页一律先放进 old 区头部，而不是 LRU 头部。

graph LR
    subgraph L1["改良版 LRU 链表"]
        direction LR
        YH["young 区头部（最热）"] --> Y["young 区（默认约 5/8）"] --> M["midpoint（新页入口）"] --> O["old 区（默认约 3/8）"] --> OT["old 区尾部（淘汰出口）"]
    end
    N["磁盘新读入的页"] -->|"midpoint 插入"| M
    M -->|"停留满 innodb_old_blocks_time 后再次被访问"| YH
    OT --> W["淘汰：脏页则刷盘，干净页直接释放"]

配套参数只有两个，默认值就很好：

  • innodb_old_blocks_pct = 37：old 区占比约 3/8；

  • innodb_old_blocks_time = 1000：页在 old 区至少停留 1000 毫秒，且期间被再次访问，才晋升 young 区。

这两个参数共同构成一道"访问模式过滤器"：

  • 对全表扫描：扫描的页进入 old 区后，扫描器很快流向后面的页，同一页不会被二次访问，它们在 old 区排队等淘汰，碰不到 young 区——扫描再大，污染也被限制在 3/8 的 old 区里；

  • 对预读：预读进来的页若真被业务访问，通常发生在第一次访问后的几毫秒内，间隔小于 1 秒阈值，不会晋升——只有"第一次访问 1 秒后又被访问"的页才配进 young 区，这恰好过滤掉一次性访问。

（真实机制的细节：晋升判断比较的是"第一次访问时间"与"后续访问时间"的间隔，间隔大于等于 innodb_old_blocks_time 才晋升；来得太快的二次访问反而被判定为一次性访问而不晋升。另外 young 区内部也有老化机制，长期不被访问的热页会逐渐降级回 old 区、最终被淘汰，所以缓存内容始终跟随真实访问模式漂移。）

这里有一个值得记住的边界情况：二级索引全表扫描 + 回表的场景。扫描先走二级索引页，再按主键回表读聚簇索引页——同一个聚簇索引页可能在一次慢扫描中被反复摸到。如果扫描足够慢，两次回表的间隔超过 1 秒，这些聚簇索引页就会被判定为热点、晋升进 young 区。这是 1 秒阈值防不住的污染路径，也是很多"跑了一次大报表之后缓存命中率崩了"事故的真实成因之一。InnoDB 无法区分"业务热点"与"重复扫描"，它选择相信"1 秒后还在被访问"这个信号，属于设计上的取舍。

顺带回应一个常见提问：为什么不用 LFU 或时钟（Clock）这类淘汰算法？LFU 用访问频次代替新鲜度，抗污染更强，但对"突发热点"反应迟钝——昨天热、今天冷的数据会赖在缓存里不走；Clock 是 LRU 的低成本近似，省的是链表维护开销，防污染能力并不比 LRU 更强。InnoDB 选择"LRU 分区"这个折中：保留 LRU 对突发热点的敏感性，用 old 区隔离一次性访问，实现代价和实际效果平衡得最好。这个思路对自研缓存同样有参考价值：淘汰算法的选择不在于谁更"先进"，而在于匹配真实访问模式。

2.3 预读：把随机 IO 顺序化

InnoDB 支持两种预读：

  • 线性预读：innodb_read_ahead_threshold 默认 56——一个 extent（64 个连续页）中如果顺序访问了超过 56 页，异步把下一个 extent 整体读入 Buffer Pool。对"范围扫描"是纯收益，相当于把未来的随机读合并成一次大顺序读；

  • 随机预读：innodb_random_read_ahead 默认 OFF。当某个 extent 里大部分页都被以随机方式访问过，就把整个 extent 读进来。收益不稳定，8.0 中默认关闭，一般不建议打开。

预读的代价是多占内存、多耗带宽，收益取决于访问模式是否真的"顺序"。这也是为什么 InnoDB 需要 old 区兜底：预读错了，错的页也只会在 old 区里安静地被淘汰。

2.4 监控与参数配置

缓存命中率的经典口径：

$$hit = \left(1 - \frac{diskReads}{totalReads}\right) \times 100%$$

适用边界也要说清楚：Buffer Pool 缓存的是"页"，不能缓存跨页的结果集；OLAP 型的大范围扫描命中率天然低，指望靠调参数让分析型负载跑出高命中是不现实的，这类负载应该隔离到从库或数仓。

三、change buffer：把二级索引的随机读攒起来

考虑一个高频写场景：订单表 5000 万行（示例设定），上面有个二级索引 idx_user_id。每次 INSERT 新订单，都要把索引项写进 idx_user_id 的某个索引页。user_id 基本随机，落点页分散在整个键空间，而这个量级的二级索引可能有几十万个页，Buffer Pool 装不下——于是每次插入都可能触发一次 16KB 的随机读，只为写几十个字节的索引项。

InnoDB 的解法：既然这次随机读只是为了"把修改落到那页"，那就先把修改记账——写到 change buffer，同时写 redo 保证可恢复。等这个索引页将来因为别的原因被读入 Buffer Pool 时（比如有查询命中它），再把积攒的修改**合并（merge）**进去；后台线程也会择机主动 merge。merge 的触发时机具体包括：目标索引页因查询被读入 Buffer Pool 时、后台线程定期执行时、崩溃恢复完成后、系统接近空闲时，以及正常停机前——所以 change buffer 的收益本质是"延迟合并"，欠下的 IO 迟早要还，只是换成了更便宜的时机和批量方式。

$$\text{期望节省 IO} = N \times p \times c$$

N 为二级索引写入次数，p 为目标页不在内存的概率，c 为单次页读取成本。对 HDD（c 约 10ms 量级）而 p 又高的库，去掉大部分随机读意味着写入吞吐成倍提升；对 NVMe（c 小一个数量级以上）绝对收益变小，但高并发下每秒数十万次微小的随机读仍是实打实的带宽与缓存污染开销。

为什么只对非唯一索引有效？ 唯一索引在写入前必须判断"这个键是否已存在"，判断的唯一办法是把那页读进来——随机读省不掉，change buffer 就失去了存在的前提。这也是"唯一索引 vs 普通索引"选型争论的核心论据之一：写入密集且能从业务上保证唯一性的场景，普通索引配合 change buffer 更快；需要数据库兜底唯一性时，老老实实用唯一索引，性能让位于正确性。

什么场景反而变差？

  • 写后立即读：插入后马上按该索引列查询，页被读入触发 merge，等于"先缓存再立刻合并"，多了一道手续；

  • 读多写少的表：merge 的收益覆盖不了缓存管理的开销；

  • change buffer 挤占 Buffer Pool：innodb_change_buffer_max_size 默认 25，即最多可占缓冲池的 1/4。它物理上位于系统表空间（8.0 仍是），其修改同样受 redo 保护，崩溃后可恢复。

值得注意的趋势是：MySQL 8.4 把默认值从 all 改成了 none。背景是现代 NVMe 的随机读性能大幅提升，change buffer 的收益被削弱，而 merge 延迟与崩溃恢复复杂度是实打实的成本。跑在 NVMe 上且写后读比例不低的库，关闭它是合理选择；HDD 或缓存命中率低的写入型库，保留 all 仍有价值。选型依据不是版本默认值，而是你自己的 p（页不在内存概率）和 c（单次读成本）。

四、redo log：用顺序写买持久化

4.1 WAL 为什么是基石

redo log 解决的问题是：事务提交了，但数据页还在内存里，此时断电怎么办？

答案是只保证"日志"先落盘。redo 记录的是物理层面的修改（某页某位置改成了什么，以 mini-transaction 为单位组织），数据页虽然还没落盘，但断电重启后可以按日志把修改重放一遍——这就是前滚。于是"持久性"不再依赖数据页的及时落盘，随机写被转换成了日志的顺序追加写。顺序写在磁盘上的吞吐比随机写高一到两个数量级，这笔交易非常划算。

文件形态上有两个时代：

  • 8.0.30 之前：ib_logfile0、ib_logfile1 两个文件循环写，每个文件大小由 innodb_log_file_size 控制（默认 48M），总容量默认约 96M；

  • 8.0.30 起：由 innodb_redo_log_capacity（默认 100M）统一管理，redo 文件放在数据目录的 #innodb_redo 下（默认 32 个文件轮转），且支持在线动态调整容量——这对后面的容量规划是重大利好。

innodb_log_buffer_size（8.0 默认 16M，8.4 起默认 64M）是 redo 的内存缓冲，Log Buffer 满了或者事务提交时会写到 redo 文件的 OS cache，再按策略 fsync。

4.2 innodb_flush_log_at_trx_commit：三档语义与丢失窗口

这是全文最重要的一个参数，三个取值的真实语义：

取值 提交时的动作 mysqld 进程崩溃最多丢 主机断电最多丢
0 不主动刷，后台约每秒刷一次 约 1 秒 约 1 秒
1 write 到 OS cache + fsync 0 0
2 只 write 到 OS cache，后台约每秒 fsync 0（数据在 OS cache） 约 1 秒

关键区别在"数据此刻在哪里"：

  • 0 档：提交后日志还在 Log Buffer（mysqld 自己的内存里），进程一崩就没了，所以两列都约丢 1 秒；

  • 2 档：提交后日志到了 OS page cache，mysqld 崩溃不影响它（内核还拿着），但断电时 OS cache 丢失；

  • 1 档：提交动作里包含 fsync，日志真正落到磁盘，理论上不丢。

三个档位的"约每秒一次"由 innodb_flush_log_at_timeout（默认 1 秒）控制，一般不改。注意"约 1 秒"是上限估计，实际丢失取决于最后一次成功刷盘的时间点，可能不到 1 秒，也可能因为刷盘线程阻塞而略多——所以 0/2 档的真实语义是"丢失窗口以秒计"，不是"精确丢一秒"。

4.3 组提交：把 fsync 摊薄

双 1 听起来每事务要做两次 fsync（redo 一次、binlog 一次），高并发下扛得住吗？答案是组提交（group commit）：多个并发事务的提交在同一瞬间排队，leader 带着整队人马合并成一次 fsync，把"每事务 1 次"摊薄成"每组 1 次"。

组提交的效果与并发度强相关：100 个事务同时提交，一次 fsync 摊给 100 个人，均摊成本极低；低并发（比如只有两三个连接的批处理）时组形不成，fsync 次数回不去，双 1 的代价才真正显形。这就是"OLTP 高并发下双 1 其实没那么慢，低并发批量导入才痛"的原因。binlog 侧还有 binlog_group_commit_sync_delay（默认 0，单位微秒）可以人为等一等、攒大组，用延迟换吞吐，属于特殊场景的微调手段。

4.4 redo 容量怎么定

redo 是循环写的，写满一头就得覆盖最老的日志，而覆盖的前提是"日志对应的脏页已经刷回磁盘"——checkpoint 就是这个"已经安全"的标记位。定义：

$$\text{checkpoint age} = \text{当前 LSN} - \text{最近检查点 LSN}$$

age 表示"最老的那批还没落盘的数据，对应的日志占了多少空间"，它必须始终小于 redo 总容量，否则新写入只能等待（细节见第五节）。由此得到容量规划的基线：

$$C \ge r \times T$$

C 为 redo 容量，r 为高峰期每秒生成的 redo 字节数，T 为目标容忍时长——age 从 0 涨到满所需要的时间，它同时近似等于崩溃恢复需要重放日志量的上界。观测 r 的办法很简单，每分钟采样一次：

两次采样差值除以间隔秒数即高峰速率。示例推演：高峰每秒 2MB redo，取 T 为 30 分钟，则 C 至少约 3.6GB，取整 4GB；若每秒 10MB，同样 30 分钟就要 18GB——所以"redo 给多少"没有通用答案，重度写入系统给到 GB 级很正常，默认 100M 只够玩具负载。

容量是一个双向 trade-off：容量越大，刷脏越平滑、checkpoint 越少，但崩溃恢复要重放的日志可能越多。恢复时间上限大约等于把 C 大小的日志重放完的时间，金融场景定容时要把恢复 SLA 一起算进去，而不是一味求大。

五、脏页刷新与 checkpoint：系统的节拍器

5.1 脏页从哪来、往哪去

Buffer Pool 中被修改过、还没写回磁盘的页就是脏页，它们挂在 flush list 上按修改时间排队。脏页回到磁盘有两条路径：

  • flush list 路径（主路径）：page cleaner 线程从 flush list 头部（最老的脏页）批量刷，相邻页合并成连续写，对磁盘友好；

  • LRU 淘汰路径（被迫路径）：需要新页而 free list 空了，从 LRU 尾部淘汰时发现页是脏的，只能现刷现释放。这是单页随机写，效率低。innodb_lru_scan_depth（默认 1024）控制每个 instance 每次扫描 LRU 尾部找可用页的深度，脏页多时这条路径的占比会上升，是 IO 混乱的信号之一。

page cleaner 的数量由 innodb_page_cleaners（默认 4）控制，通常建议设成与 innodb_buffer_pool_instances 一致。

5.2 checkpoint：给 redo 划"保质期"

数据页可以慢慢刷，redo 不能等——它是循环复用的，最老日志被覆盖前，对应脏页必须先落盘。checkpoint 就是推进"可以覆盖的位置"。InnoDB 用的是模糊检查点（fuzzy checkpoint）：不停止写入、不做全量快照，而是后台持续地把最老脏页刷出去、小步推进 checkpoint。只有正常停机（shutdown）时才做一次 sharp checkpoint，把所有脏页刷干净。

触发后台刷新的条件主要有四类：

  1. checkpoint 压力：checkpoint age 占 redo 容量的比例超过低水位（innodb_adaptive_flushing_lwm，默认 10，即容量的 10%）时启动自适应刷新，比例越高刷得越猛；

  2. 脏页比例：innodb_max_dirty_pages_pct（默认 90，即 90%）是硬性上限，innodb_max_dirty_pages_pct_lwm（8.0 默认 10）是低水位，低于上限就开始温和地刷；

  3. free 页不足：LRU 淘汰路径，见上；

  4. 系统空闲：没什么负载时顺手把脏页刷掉，为下一个高峰腾地方。

5.3 自适应刷新与 IO 预算

自适应刷新的思路是"算账"：根据 redo 的生成速率和脏页的老化速度，估算每秒需要刷多少页才能让 checkpoint 追得上写入，然后给 page cleaner 下指标。这个指标受 IO 预算约束：

  • innodb_io_capacity（默认 200）：page cleaner 每秒可以刷的页数预算。注意它是"页数"不是"磁盘 IOPS"，但应参照磁盘真实能力设置——机械盘 200~400，SATA SSD 数千，NVMe 可以更高。设低了后台刷新追不上写入，age 一路逼近上限；设高了后台刷脏抢前台带宽；

  • innodb_io_capacity_max（默认 2000）：压力模式下的上限，预算被允许超到这个程度；

  • innodb_flush_neighbors（8.0 默认 0，5.7 默认 1）：刷脏时顺手把同 extent 的脏页一起刷。机械盘上能减少寻道，是正收益；SSD 上没有寻道惩罚，多刷只是浪费写带宽，所以 8.0 起默认 0，SSD 用户保持默认即可。

5.4 刷脏抖动的五个来源

线上"周期性 RT 毛刺"的根源，绝大多数能归到以下几条：

  1. redo 容量太小：age 高频逼近上限，自适应刷新反复进入猛刷模式，IO 在"平静"与"全速"之间振荡；

  2. 用户线程被"围栏"（fencing）：每个 DML 进入 InnoDB 前都会做 log free check，发现 age 超过安全线时，用户线程会被挡在入口，先等 checkpoint 推进再放行。极端情况下大量会话堆积在写入口，表现为写入 RT 集体飙升——这是 InnoDB 给写入流量加的一道保险，也是抖动最刺眼的形态；

  3. io_capacity 低估：后台刷新预算跟不上脏页生成速度，被迫频繁动用上限预算甚至用户线程路径；

  4. LRU 单页刷混入：free list 紧张导致淘汰路径占比升高，随机单页写打散了后台的顺序批量写；

  5. 脏页比例冲顶：逼近 innodb_max_dirty_pages_pct 后强制刷新，与 checkpoint 压力叠加形成刷新风暴。

对应的治理手段在第九节的场景里展开。监控入手点：SHOW ENGINE INNODB STATUS 的 LOG 段（Log sequence number 减去 Last checkpoint at 即当前 age）、状态变量 Innodb_buffer_pool_pages_dirty 除以 Innodb_buffer_pool_pages_total 得脏页比例、以及 8.0 的 information_schema.INNODB_BUFFER_POOL_STATS。

六、binlog 刷盘与"双 1"取舍

6.1 内部两阶段提交：顺序为什么不能反

redo 在 InnoDB 层，binlog 在 Server 层，两者必须一致，否则崩溃恢复后主库与从库对不上账。InnoDB 用内部两阶段提交（2PC）把两者绑定：

sequenceDiagram
    participant S as Server 层
    participant I as InnoDB
    participant R as redo log
    participant B as binlog 文件
    S->>I: 提交事务
    I->>R: 1 写 redo，状态置为 prepare（组提交 fsync）
    I-->>S: prepare 完成
    S->>B: 2 写 binlog 并 fsync（sync_binlog=1）
    S->>I: 3 通知 InnoDB 提交
    I->>R: 4 写 commit 标记
    Note over S,B: 崩溃恢复：binlog 完整的事务放行，否则回滚

崩溃恢复的裁决规则是：binlog 完整的事务放行（补写 commit 标记），只有 prepare 没有 binlog 的事务回滚。逐个崩溃点验证顺序的必然性：

  • 若在 redo prepare 之后、binlog 写之前崩溃：恢复时找不到 binlog，事务回滚——两边都当它没发生过，一致；

  • 若 binlog 已 fsync、commit 标记没来得及写：恢复时 binlog 完整，事务被放行——主库不丢，从库也有这条 binlog，一致；

  • 反过来，如果先写 binlog 再写 redo：binlog 落盘后崩溃、redo 还是 prepare 之前的状态，从库会重放这条 binlog 而主库没有这笔修改——主从直接分叉。

所以"先 prepare、再 binlog、后 commit"的顺序不能动。

顺带厘清 redo 与 binlog 最容易混淆的三点：层次上，redo 属于 InnoDB 引擎层，binlog 属于 Server 层——任何存储引擎都会产生 binlog，redo 只有 InnoDB 才有；内容上，redo 是物理日志，记录"哪一页的哪个位置改成了什么"，binlog 是逻辑日志，8.0 默认的 ROW 格式记录"哪一行变成了什么"；形态上，redo 容量固定、循环复用，写满必须先推进 checkpoint，binlog 则是追加写，写满一个文件换下一个、靠过期清理释放空间。正因为这些差异，两者的刷盘策略只能分别配置、共同生效，这才有了下一节的双 1 组合。至于 STATEMENT/MIXED 格式与复制相关的细节不在本文展开，只提一句边界：搭配半同步复制（AFTER_SYNC）可以把"从库收到 binlog"也纳入提交条件，进一步收窄主从不一致的窗口，代价是提交延迟上升。

6.2 sync_binlog 三档与组合矩阵

sync_binlog 与 redo 侧参数同构：

  • 1：每次组提交都 fsync，最安全，默认值；

  • 0：binlog 写到 OS cache，由操作系统决定何时落盘；

  • N：攒 N 个事务组 fsync 一次，崩溃最多丢 N 个事务的 binlog。

两个参数组合起来才是完整的持久化等级：

innodb_flush_log_at_trx_commit sync_binlog 主机断电的丢失窗口 适用场景
1 1 无（已提交事务不丢） 交易、支付、账务，OLTP 默认起点
1 N redo 不丢，但 binlog 可能缺，主从不一致 中间态，谨慎使用
2 1 约 1 秒（redo 丢） 可容忍秒级丢失的日志、报表类库
0 0 1 秒以上，mysqld 崩溃也丢 批量导入等可重放负载临时切换

双 1 是 OLTP 的默认起点，而且在高并发组提交下代价远比直觉小。降低持久化等级省下的 fsync，本质是把风险从"小概率事件"变成"确定的丢失窗口"，这个决策应该由业务方签字，而不是 DBA 拍脑袋。另一个常见误区是只关一边：trx_commit=1 + sync_binlog=0 的组合，主库数据安全了，主从复制却可能丢事务，比两边都松更危险。

七、doublewrite buffer：防"撕裂页"的保险

InnoDB 的页是 16KB，而文件系统块通常是 4KB，磁盘扇区更小。写一个数据页到表空间文件时如果断电，可能只写进去一半——这就是部分写失效（torn page / 撕裂页）。

撕裂页的麻烦在于 redo 救不了它：redo 记录的是"在某页的某位置做某修改"，重放的前提是那一页本身处于完整、可解析的状态。半截页连页头校验（checksum）都过不了，InnoDB 不知道该从哪里重放，盲放只会得到更乱的数据。WAL 解决"改没改"，doublewrite 解决"页碎没碎"，两者缺一不可。

机制并不复杂，本质是先顺序写一份完整副本，再随机写正式位置：

  1. 脏页先拷贝到内存中的 doublewrite buffer；

  2. 整批页顺序写到磁盘上的 doublewrite 区域并 fsync（经典实现为两个 1MB 的块；8.0.20 起从系统表空间移出，成为数据目录下独立的 dblwr 文件）；

  3. 再把各页写到表空间文件的正式位置。

崩溃恢复时，若发现某个表空间页损坏（校验失败），就从 doublewrite 区域把完整副本拷回去，然后 redo 照常前滚。doublewrite 区域是顺序追加写的批量 IO，成本远低于"每页两次随机写"的直觉；真实代价是写带宽放大，脏页比例越高放大越明显：

$$W \approx 1 + d$$

d 为脏页占比——极端简化下的写放大系数，用于定性理解而非精确计算。

innodb_doublewrite 默认 ON，没有充分理由不要关。唯一值得评估关闭的场景是底层存储能书面保证 16KB 页的原子写（部分分布式块存储、支持原子写的文件系统或硬件），此时关掉可以省一份写放大；新版本还提供 DETECT_AND_RECOVER、DETECT_ONLY 等变体模式做折中。判断依据是存储层的原子写承诺，而不是"听说关了更快"。

八、Query Cache 为什么被 8.0 移除

在 Buffer Pool 之外，MySQL 曾经还有一层缓存：Query Cache，直接缓存 SELECT 语句的结果集，key 是 SQL 文本的哈希。它从 5.7.20 起被官方标记为废弃，8.0 彻底移除。理解它为什么死，恰好能反衬 Buffer Pool 为什么活。

Query Cache 有三宗罪：

  1. 失效粒度是表级：对某张表的任何一行修改（INSERT/UPDATE/DELETE），都会让这张表的所有缓存条目失效。写稍微多一点的表，命中率趋近于零，缓存的维护成本却是纯支出；

  2. 全局互斥锁：查缓存、写缓存、失效清理都要抢同一把锁，高并发下所有 SELECT 先排队抢锁，锁竞争的耗时比省下的解析执行时间还多。缓存层本身成了串行化点；

  3. 命中条件苛刻：SQL 文本必须字节级一致（空格、大小写、注释、字符集都算），同一语义的两种写法视为两条，命中率进一步打折。

它与 Buffer Pool 的本质区别在于缓存的对象不同：

维度 Query Cache Buffer Pool
缓存对象 查询的结果集 数据页/索引页本身
一致性来源 表级失效（写多即失效风暴） WAL + checkpoint，页永远是最新的，无需"失效"
并发模型 全局锁互斥 页级锁、多 instance 分片
失效行为 一行修改，整表缓存作废 修改直接作用在缓存页上，不存在失效

关键洞察是：Buffer Pool 里缓存的就是最新数据本身，写操作直接在缓存页上进行（配合 redo 保证持久），读操作通过 MVCC 构建需要的旧版本——所以根本不存在"数据变了，缓存怎么办"的问题，也就不需要失效机制。缓存"数据的载体"永远比缓存"数据的快照"健壮。

移除之后的替代方案：应用层缓存（Redis 等，需要自己处理一致性边界，可参考站内 Redis 持久化与淘汰策略两篇）、代理层缓存（如 ProxySQL 的 query cache），或者干脆依赖 Buffer Pool 与合理的索引——对绝大多数 OLTP 系统，第三条才是正路。

九、三个故障场景复盘

场景一：redo 太小引发的周期性写入卡顿

发生什么：每晚批处理窗口后，白天高峰期写入 RT 周期性飙升到几百毫秒。监控显示脏页比例从 20% 骤降到 5%（刚被猛刷过）再慢慢爬回来，周期十几分钟一轮；SHOW ENGINE INNODB STATUS 里 checkpoint age 频繁逼近 redo 容量。

为什么：实例还跑着默认 redo 容量（8.0.30 前是 2×48M=96M，之后默认也只有 100M），高峰每秒几 MB 的 redo 几分钟就把 age 顶到安全线。自适应刷新转入全速刷脏抢走 IO 带宽，更糟的是用户线程在 log free check 处被围栏挡住——写入被 InnoDB 亲手暂停，等待 checkpoint 推进。刷脏一结束负载回落，脏页比例又开始爬升，进入下一轮循环。

如何处理：把 redo 容量按 4.4 节的方法定容（采样 redo 速率 × 目标容忍时长），8.0.30+ 用 innodb_redo_log_capacity 在线调整，老版本改 innodb_log_file_size 需重启；同时核对 innodb_io_capacity 是否匹配磁盘真实能力，SSD 上确认 innodb_flush_neighbors=0。

如何恢复：参数调整后观察三个曲线——checkpoint age 的"锯齿"幅度收敛、脏页比例平稳在低水位区间、写入 RT 毛刺消失。恢复期不需要业务操作，但建议在低峰执行老版本的变更。

场景二：一次"无害"的全表扫描拖垮全站缓存

发生什么：运营在主库跑了一个 5 分钟的全表扫描报表，结束后常规查询 RT 上升 3~5 倍，持续约半小时才慢慢恢复。缓存命中率从 99% 跌到 90% 以下，磁盘读请求数出现一个陡峰。

为什么：扫表把 old 区刷了一遍是设计预期，污染本应被限制在 old 区。但事故型扫描通常叠加两个放大器：其一，如果是二级索引扫描 + 回表（见 2.2 节），慢扫描会让同一批聚簇索引页被反复访问，间隔超过 1 秒即被晋升 young 区，污染直接进入热区；其二，扫表读入海量新页时 free list 长期紧张，LRU 淘汰路径的脏页单页刷大量出现，随机 IO 又拖慢了前台查询。

如何处理：治理入口比调参数有效——大查询走从库或数仓，应用侧给查询加 max_execution_time 上限，报表账号与 OLTP 账号权限分离；参数侧可适度调大 innodb_old_blocks_time（比如 2000ms）收紧晋升门槛，代价是真正的热点回热也变慢，属于两害相权。

如何恢复：命中率随年轻区的自然老化回升，通常几十分钟量级；急迫场景可以对确认的热点表做定向预热（用覆盖全表主键范围的轻量 SELECT 让热页重新进入缓存），并配合 innodb_buffer_pool_dump_at_shutdown/load_at_startup 保证重启后的缓存恢复。

场景三：断电后"已提交"的订单不见了

发生什么：机房断电，恢复后业务反馈两笔"已提交"的订单消失；对账发现主库和从库缺同一批数据。实例本身正常拉起，页数据没有损坏迹象。

为什么：这台库为了压测吞吐把 innodb_flush_log_at_trx_commit 设成了 2、sync_binlog 设成了 100。断电时 OS page cache 里的 redo 整体丢失（约 1 秒窗口），恰好覆盖这两笔订单；sync_binlog=100 又让 binlog 侧也缺了货——两边"一致地丢"，反而没有主从分叉，但业务数据确实没了。这就是 4.2 与 6.2 两节丢失窗口的实物演示：持久化等级降级时，丢失不是"可能"，而是"断电必然发生在窗口内"。

如何处理：事后要做的第一件事是把丢失范围圈出来——用业务流水号与库内数据对比、核对上游消息队列与 binlog 的位点；然后按第九节开头的方式把持久化等级改回双 1（本例业务的定位是交易，本就该双 1）。真正的恢复要靠上游补偿：从业务日志或消息队列重放这两笔订单。

如何恢复（实例层面）：这次没受损纯属侥幸。若页损坏，恢复链路是：doublewrite 区域用完整副本替换撕裂页 → redo 前滚到崩溃点 → undo 回滚未提交事务。理解这条链路有助于评估一件事：恢复时间与 checkpoint age 高度相关，age 越大要重放的日志越多——又一个"redo 容量不是越大越好"的注脚。

十、总结与建议

把全文的机制收敛回一句话：InnoDB 用"内存改页 + 顺序写日志"把随机写变成顺序写，用 young/old 链表和 change buffer 把缓存命中率与写 IO 做到极致，再用 checkpoint、doublewrite 和两阶段提交把这一切在崩溃时收敛到一致。 每个参数都是这条权衡链上的一个旋钮。

graph TD
    A["写请求 UPDATE / INSERT / DELETE"] --> B["Log Buffer 记录 redo"]
    A --> C["Buffer Pool 页内修改，页变脏"]
    B -->|"trx_commit=1：提交即 write+fsync"| D["redo log 文件（顺序追加）"]
    B -->|"trx_commit=0 / 2：约每秒批量刷"| D
    D -->|"checkpoint age 逼近容量"| E["推进 checkpoint，催促刷脏"]
    C -->|"比例阈值 / checkpoint 压力 / LRU 淘汰"| F["Page Cleaner 后台刷脏"]
    F --> G["doublewrite：顺序写页副本并 fsync"]
    G --> H["表空间文件 .ibd（随机写）"]
    D --> I["崩溃恢复：重放 redo 前滚 + undo 回滚未提交"]

参数速查表（按治理优先级排序）：

参数 默认值 建议与说明
innodb_buffer_pool_size 128M 生产必改，专用实例给物理内存 50%~70%；5.7 起可在线调整
innodb_redo_log_capacity 100M 按高峰 redo 速率定容（C ≥ r×T），重度写入给 GB 级；8.0.30 起可在线调
innodb_flush_log_at_trx_commit 1 OLTP 保持 1，降级等于接受秒级丢失，需业务确认
sync_binlog 1 与上一项组成双 1；只降一边比两边都松更危险
innodb_io_capacity / _max 200 / 2000 对齐磁盘真实能力，NVMe 给数千；设低导致刷脏追不上
innodb_flush_neighbors 0（8.0） SSD 保持 0；机械盘可回 1
innodb_buffer_pool_instances ≥1G 时为 8 与 CPU 核数对齐
innodb_old_blocks_pct / _time 37 / 1000 一般不动；频繁扫表的库可适度调大 time
innodb_change_buffering 8.0 为 all，8.4 起 none NVMe 且写后读多可关；HDD 保留
innodb_max_dirty_pages_pct / _lwm 90 / 10 一般不动，纳入监控告警
innodb_log_buffer_size 16M（8.4 起 64M） 有大事务或批量导入时调大
innodb_doublewrite ON 除非存储层保证页原子写，否则不关

按负载类型给三条决策路线：

  • 交易型（金融、订单）：双 1 + 足量 redo + doublewrite 开启，用组提交扛并发，用监控扛抖动；

  • 日志/报表型（可重放、可容忍秒级丢失）：trx_commit=2 + sync_binlog=1 或更低组合，换取更稳的写入延迟；

  • 分析型（大扫描为主）：命中率的战场不在 Buffer Pool 参数，在隔离——从库、数仓、入口限流，把 OLTP 的缓存留给 OLTP。

最后说明本文的边界：文中机制以 8.0 主线为准，8.0.30 前后 redo 文件形态差异较大，引用参数前先确认版本；所有"约 1 秒""几十分钟"均依赖负载与硬件，是量级判断而非承诺；未展开的话题包括 undo 表空间管理、原子写硬件、binlog 复制细节与半同步的完整语义，建议配合站内 MySQL 执行链路与性能排查两篇阅读。

工程结论

  • 双 1 是 OLTP 的默认起点，任何"为性能关掉双 1"的决定都必须先回答一个问题：断电时这秒级窗口里的数据，业务能不能靠上游补偿找回来。

  • redo 容量要用高峰速率实测定容（Innodb_os_log_written 采样），不要沿用默认 100M 跑重度写入；容量同时决定恢复时间上限，不是越大越好。

  • 刷脏抖动治理三板斧：innodb_io_capacity 对齐磁盘、SSD 上 innodb_flush_neighbors=0、把 checkpoint age 与脏页比例纳入告警——毛刺出现前这些曲线早有征兆。

  • 大扫描是缓存毒药：入口限流与 max_execution_time 比事后调 LRU 参数有效得多；二级索引扫描回表的晋升路径（old 区 1 秒阈值防不住）要单独警惕。

  • doublewrite 保持开启，除非存储层能书面保证 16KB 页原子写；崩溃恢复链路（doublewrite 修页 → redo 前滚 → undo 回滚）值得每个 DBA 演练一次。
