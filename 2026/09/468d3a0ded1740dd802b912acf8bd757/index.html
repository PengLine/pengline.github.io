NeoTask 核心功能详解：组件树与两阶段装配 + 链路全解

📚 返回首页 | 📖 快速上手 | 📘 API 参考 | ⚙️ 配置说明 | 🐙 GitHub | 🐱 NeoTask 官网

本文是 NeoTask 系列"核心实现"篇，按源码实际结构讲述 TaskPool 两阶段装配 → 提交 → 队列 → 执行 → 回收 五条链路。源码中不存在 WorkflowEngine / DAG 编排层 / DistributedLock 类；Redis 任务存储是 SET task:{id} 的 JSON 字符串而非 HSET。文中凡涉及"未接线"的能力（如 task.progress 事件）都会直接标注。

概述

NeoTask 是一个纯 Python 实现的轻量级异步任务调度系统，专为耗时任务（AI 生成、视频处理、数据爬取等）设计。无需部署 Redis、PostgreSQL 等外部服务，安装后即可在任意 Python 项目中直接使用。

  1. 没有编排层，也没有 WorkflowEngine。v1.0.2 全部代码位于 neotask/ 包下 16 个子包、约 60 个模块，顶层 API 只有 TaskPool（即时任务）与 TaskScheduler（定时任务）两个门面，外加一个未导出的 TaskEngine。工作流/DAG 尚在规划阶段。

  2. TaskPool 是"构造期全量装配 + 启动期分批拉起"的两阶段门面。构造时在调用方进程完成 10 类组件初始化（不建事件循环）；start() 才创建后台守护线程 + 独立事件循环，按 事件总线 → 队列 → Worker → 监督者 → 心跳 → 回收器 的顺序启动组件。同步 API 与异步内核之间靠 run_coroutine_threadsafe 桥接。

  3. Redis 模式下的"故障回收"链路已闭环，且以 TaskRepository 为唯一任务读写通道：HeartbeatManager 与 NodeManager 共用同一份节点注册表（neotask:node:* / neotask:nodes），并经由 TaskRepository 读取 RUNNING 任务、按 node_id 只回收死亡节点自己的任务；TaskReclaimer 的活跃节点来自 NodeManager.get_active_nodes()，未配置节点管理器时返回 None 并跳过孤儿回收（而不是把全部任务误判为孤儿），且本节点任务被显式跳过。两条路径的失败任务都会投递死信队列。

装配形态说明

真实结构不是线性分层，而是 TaskPool 门面 + 星型组合：TaskPool 在构造期装配 10 类组件（生命周期、分发器、队列、Worker 池、监督者、事件总线、锁、以及 Redis 形态下的节点管理/心跳/回收器/死信），启动期在后台线程的事件循环里按依赖序拉起 8 个异步部件。TaskScheduler 内部持有一个 TaskPool 并全量委托，是它的客户而非兄弟节点。组件间不做互相查找，全部通过构造函数注入共享实例。详细拓扑见 1.2 节与架构设计篇。

二、TaskPool 装配解剖：构造十步 + 启动八步

TaskPool 的设计是典型的 Facade + 两阶段生命周期：构造阶段只组装对象图（纯内存操作，不碰事件循环）；启动阶段才在专用线程里创建事件循环并拉起全部异步组件。

2.2 线程模型：同步 API 背后有一个独立事件循环 🔧

这是理解 NeoTask 一切行为的关键。start()（task_pool.py:310-367）不在调用方线程跑 asyncio，而是：

由此产生三个推论（后文故障实战会用到）：

  1. 提交方线程 ≠ 执行方线程。任何线程调用 pool.submit() 都会走 run_coroutine_threadsafe(coro, self._loop) 把协程投递到后台循环执行（task_pool.py:300-306）。

  2. 主线程可以安全阻塞等待，同步 wait_for_result 不会卡死执行循环。

  3. asyncio.run() 包不住的坑：如果用户代码运行在某个事件循环内（如 FastAPI），TaskPool 的"线程+自带循环"模型依然独立工作——但若在未 start() 时调用任何 API，会得到 RuntimeError: TaskPool not started. Call start() first.（task_pool.py:303）。部分 API 内部有 _ensure_running() 兜底自动 start（task_pool.py:295-298），这也是"任务偶尔自启动"的源码级原因。

2.3 启动顺序：组件的严格依赖序 🔧

后台线程的 start_components()（task_pool.py:343-374）按依赖序拉起：

顺序 组件 说明
1 event_bus.start() 总线先行，后续组件的事件才有接收方
2 queue_scheduler.start() 内存模式下启动 DelayedQueue 的内部调度循环
3 worker_pool.start() 启动预取器 + 全部 worker 协程
4 supervisor.start() 监督者开始周期健康检查
5 node_manager.start() 仅 Redis 模式，注册节点
6 heartbeat_manager.start() 仅 Redis 模式，上报心跳 + 监控死节点
7 reclaimer.start() 仅 Redis 模式，启动回收循环与锁扫描器
8 metrics.start() 仅 enable_metrics=True（默认），启动系统指标采样循环
9 reporter_manager.start() 仅 enable_reporter=True，默认关闭

对应地，shutdown()（task_pool.py:395-471）是逆向优雅关闭：先 queue_scheduler.disable() 停止接收新任务，graceful=True 时 wait_until_empty(timeout) 等队列清空，然后依次停 回收器 → 心跳 → 节点管理 → 关闭死信队列 → 监督者 → Worker（带超时强杀）→ 队列 → 上报器 → 指标收集 → 事件总线，最后关闭存储连接并捕获 “different loop” 异常（存储对象可能与调用方共用循环导致关闭冲突）。

2.4 为什么这么设计

问题 答案
为什么不直接在 __init__ 启动组件？ 门面 API 需要支持"先建对象、后决定何时跑"，也避免 import 即产生线程；同时让 submit() 自动 _ensure_running() 成为可能
为什么要独立线程 + 独立事件循环？ 要让 submit() / wait_for_result() 是线程安全同步方法——这是"嵌入式调度器"的核心卖点：任意线程池代码可直接调用，无需手动管理 loop
为什么事件总线最先启动？ task.created 等事件在 submit 时即发出，若总线未启动，早期事件会丢失；总线先行的代价是 start() 之前提交的任务事件全部不可达
为什么 Worker 启动在队列之后？ Worker 一启动就进入取任务循环，队列必须已可服务；预取器在 Worker 之前启动，避免首批空转

三、提交链路：提交 → 调度→ 任务 → 入队

3.1 一次提交的完整旅程 🔧

真实提交路径（同步方法 submit → run_coroutine_threadsafe(submit_async) → TaskDispatcher.dispatch → TaskLifecycleManager.create_task → QueueScheduler.push）：

3.2 dispatch()：提交的真正入口 🔧

TaskDispatcher.dispatch（core/dispatcher.py:37-85）做三件事：归一化优先级、创建任务记录、按 delay 选择入队路径。

关键语义：create_task 是入队前的硬前置——它做存在性检查（重复 task_id 抛 TaskAlreadyExistsError，与存储后端无关）、先落库再发事件；入队失败时任务记录不删除，而是被标记 FAILED 并抛 QueueFullError（详见 3.4）。

3.3 create_task 与生命周期管理器的缓存层 🔧

TaskLifecycleManager（core/lifecycle.py）是全部状态变更的唯一入口，内部结构是存储接口 + 事件总线 + 二级缓存字典三件套。

  • get_task()（86-101 行）：先查缓存，未命中读存储并回填缓存；所有状态方法基于 get_task 拿到最新对象后再改字段、save、更新缓存、发事件。

  • create_task()（46-84 行）：查重 → 构造 Task → repo.save → 缓存 → 发 task.created，载荷为 task.to_dict()（82 行）。注意：to_dict() 会把 data/result 序列化成 JSON 字符串——即使 data 是纯 Python 对象、即使存储是内存后端，只要对象不可 JSON 序列化，这一行就会抛异常（内存模式的序列化坑不在存储层，而在这里）。

  • update_status()（103-134 行）：通用改状态 + 发 task.status_changed（含 old/new），但它不做状态机校验——任何状态到任何状态都允许，真正的状态守门在 start_task/complete_task/fail_task 内部。

3.4 队列满：入队失败即抛 QueueFullError 🔧

QueueScheduler.push（queue/queue_scheduler.py:77-99）的真实行为：

TaskDispatcher.dispatch 会检查返回值：push 返回 False（队列满或调度器已 disabled）时，先把已落库的 PENDING 任务 fail_task 置为 FAILED，再抛 QueueFullError（core/dispatcher.py:86-93）：

QueueFullError 从 neotask 顶层导出（neotask.common.exceptions.QueueFullError），携带队列容量。于是：

队列满（默认 queue_max_size=10000）或调度器已 disabled 时，提交方会收到 QueueFullError，任务被标记 FAILED——不再出现"记录为 PENDING 但永远无人消费"的幽灵任务。

生产对策：捕获 QueueFullError 做退避重试或上游限流；也可以用 pool.get_queue_size() 提前感知水位。延迟到期转正时若优先队列已满，_on_delayed_task_ready 会记录一条 error 日志（Delayed task {id} could not be promoted: priority queue is full）。

四、队列系统：内存 heapq 与 Redis ZSET 的两套实现

QueueScheduler 是 PriorityQueue + DelayedQueue 的门面，但结构细节容易记错——DelayedQueue 是独立的内存堆 + 自循环（不是 Redis 结构），满队列由上层抛 QueueFullError。真实实现如下。

4.1 内存模式：两个 heapq 堆 🔧

内存模式下 QueueRepository 不用（storage 的 memory 模块只负责 TaskRepository），PriorityQueue 与 DelayedQueue 各自持有堆，它们都被包在 queue_scheduler.py 的 QueueScheduler 门面后面：

  • PriorityQueue（queue/priority_queue.py:34-52）：堆元素是 (priority, sequence, task_id) 三元组，sequence 自增保证同优先级 FIFO；push 时 delay > 0 直接返回 False（延迟任务禁止直入优先队列）；满队列同样返回 False。

  • DelayedQueue（queue/delayed_queue.py）：堆元素是 (execute_time, priority, task_id)，另存 task_id -> DelayedTask 字典；自带调度循环，每 check_interval=0.1s 醒来一次，把 heap[0][0] <= now 的到期任务全部弹出并回调；cancel 采用"重建堆"的延迟删除策略；回调兼容两种签名，回调异常会被记录为 error 日志（Delayed task {id} callback failed: {e}），不再静默吞掉。

即：延迟任务到期后由 DelayedQueue 的循环唤醒，再推入 PriorityQueue 等待 Worker——不存在"延迟队列直接派发给 Worker"的路径。

4.2 Redis 模式：两个 ZSET + 原子弹出脚本 🔧

Redis 模式的队列实现在 storage/redis.py 的 RedisQueueRepository（215-378 行）：

  • queue:priority：member=task_id，score=priority（score 越小越先出队）；

  • queue:delayed：member=task_id，score=execute_at 时间戳；

  • pop()（265-286 行）：先 ZRANGEBYSCORE(queue:delayed, 0, now) 取到期任务 → ZREM → 以 score=5 写入 queue:priority（280 行），再用 Lua 脚本原子执行 ZRANGE + ZREM 弹出队首。

⚠️ 两个值得注意的实现细节：

  1. 到期转正的 score 是写死的 5，而 TaskPriority 的四档取值是 0-3——延迟任务转正后排在所有四档即时任务之后（score 越大越靠后），即**“延时到期任务优先级恒低于任意新提交的即时任务”**。这是源码行为，设计意图疑似为"延迟任务不该插队"；注意它与内存模式 DelayedQueue 的到期回调（按原 priority 推入优先队列）行为不同。

  2. pop 用 ZRANGE ... 0 count-1 + ZREM，两个命令包在 Lua 脚本里原子执行（238-252 行），避免多节点同时取到同一任务——这是去中心化消费的正确性基础，也解释了为什么直接调 QueueRepository.pop 是安全的。

4.3 QueueScheduler 门面的完整职责 🔧

QueueScheduler（queue/queue_scheduler.py）对外提供约 20 个方法，除 push/pop 外还包括：

  • pause/resume、disable/enable：队列级开关。disable 后 push 一律返回 False（shutdown 第一步就是 disable，见 2.3 节）；pause 由底层队列实现决定是否生效。

  • wait_until_empty(timeout)：优雅关闭时轮询等待队列清空。

  • pop(count) / pop_with_priority(count)：前者只返回 task_id 列表，后者连优先级一起返回（Worker 直连模式用前者，预取器用后者）。

  • get_stats() / get_detailed_stats()：上报给监控组件的水位数据。

4.4 为什么这么设计

问题 答案
为什么内存和 Redis 都选堆/ZSET 而不是 List？ 优先级队列需要"按分数取最小"的有序语义，List 只能 FIFO；ZSET 天然支持 score 排序 + 原子范围删除，内存 heapq 是同构实现，切换后端不必改上层
为什么延迟队列单独一个堆 + 独立循环，而不是塞进时间轮？ scheduler/time_wheel.py 的 TimeWheel 由 TaskScheduler 装配，enable_time_wheel=True 时才承接 submit_delayed/submit_at；默认（未启用时间轮）下延时任务直接进 TaskPool 的 DelayedQueue——它服务于一次性延时任务，100ms 粒度的最小堆足够且实现最简
为什么到期转正写死 score=5？ 源码注释未给出理由。可观察到的效果：延迟到期任务不会挤压即时任务——但这与"延迟任务原本的优先级"语义冲突，属 v1.0.2 的隐蔽行为，多延迟场景需实测排队顺序

五、执行链路：Worker 循环的八个阶段

Worker 是纯 asyncio 协程，没有线程池——并发上限由 asyncio.Semaphore(worker_concurrency) 控制（worker/pool.py:72），预取器负责把"共享队列竞争"变成"本地缓冲消费"。

5.1 worker_loop：两种取任务模式 🔧

_worker_loop（worker/pool.py:178-236）根据是否启用预取器走两条分支：

  • 预取模式（默认）：task_id = await self._prefetcher.get(timeout=0.1)，从本地缓冲取一个；取到则 create_task(_execute_task) 并登记到 _running_tasks。

  • 直接模式：task_ids = await self._queue.pop(self._prefetch_size)，一批取出再逐个创建执行协程。

两种模式的空转退避都是 sleep_time = min(0.01 * (1 << min(consecutive_empty, 6)), 0.5)（203、223 行）——空转等待指数增长但封顶 0.5 秒，避免空队列时 CPU 空转。

5.3 锁与看门狗的真实参数 🔧

  • 锁 TTL 硬编码 30 秒（pool.py:268），来自 acquire(lock_key, ttl=30)——不是配置项，lock_timeout 配置只影响 LockFactory 构造的锁实例默认 TTL，执行路径写死 30。

  • 看门狗（lock/watchdog.py）续期间隔为 interval = max(0.5, ttl * interval_ratio)，interval_ratio=0.3 → 每 9 秒 extend(key, ttl) 一次；续期失败立即停止（117-119 行），但不会中断任务——任务继续跑，锁到期后被别人抢走，出现双重执行窗口（这正是分布式锁篇排障场景一的根源）。

  • 内存模式 lock_manager 为 MemoryLock（无锁语义直通），因此单机重复执行防护实际由状态守门完成，分布式锁只在 Redis 锁后端下生效。

5.4 失败与重试：线性退避，不是指数退避 🔧

_handle_task_failure（worker/pool.py:372-413）：

要点：重试延迟 = retry_delay × 重试次数（第 1 次重试 1×、第 2 次 2×……），线性递增而非指数退避；每次重试都会复位 PENDING 再重新入队（走 DelayedQueue），所以重试任务不会饿死即时任务……不会——它到期后转正 score=5，反而排在所有即时任务之后（见 4.2）。

执行超时（asyncio.TimeoutError）与业务异常（Exception）走同一条失败路径，但任务级取消（CancelledError）例外：直接 cancel_task 落库为 CANCELLED 后返回（317-320 行）——不消耗重试次数。

5.5 状态守门的两个漏洞（v1.0.2 事实） 🔧

  1. RUNNING 任务的 cancel 会被覆盖：cancel 语义只对 PENDING 可靠。Worker 在 ③ 处检查 PENDING 后即不再看状态；若任务在 RUNNING 期间被外部 cancel()（lifecycle 允许取消 PENDING/RUNNING），执行成功后 complete_task 依然把状态写成 SUCCESS（⑤→⑦ 无二次检查）。cancel() 的"成功"只是把 Future 置为 error 通知等待方，落库状态随后被执行结果覆盖。

  2. complete_task/fail_task 只认 RUNNING：complete_task 要求当前状态恰为 RUNNING（lifecycle.py:169-171），否则返回 False 并告警——这意味着重试链路中若任务仍处于 PENDING（如被回收器抢先复位），旧 Worker 的成功回调会静默失效，而任务会再被消费一次（配合回收器缺陷，见 6.2 节）。

5.6 Supervisor：整池重启的"监督者" 🔧

WorkerSupervisor（worker/supervisor.py）默认配置：健康检查间隔 30s、Worker 挂起判定 300s、自动重启开启、最多 5 次、重启间隔 5s。_health_check（74-90 行）只做两件事：

  • 挂起检查：某 Worker is_busy 且超过 worker_timeout=300s 无 last_active 更新 → 判为 timeout；

  • 失败率检查：完成数+失败数 > 10 且失败率 > 50% → 判为 high_failure_rate。

而 _restart_worker（92-115 行）的"重启"是停掉整个 WorkerPool 再启动（await self._worker_pool.stop(graceful=False) + start()）——不是重启单个 Worker！多 Worker 场景下，一个坏 Worker 会拖垮全池并中断所有在途任务。配合"任务执行期间重启 = 在途任务变成孤儿"的连锁反应，这是 Redis 多节点部署时必须知晓的行为。

六、调度与回收链路：Redis 模式

6.1 TaskScheduler：默认走 PeriodicTaskManager 的扫描式调度 🔧

TaskScheduler（api/task_scheduler.py）与 TaskPool 同线程模型（自带守护线程 + 事件循环）。关键事实：默认配置（enable_periodic_manager=True）下，submit_interval / submit_cron / cancel_periodic 等全部委托给 PeriodicTaskManager（task_scheduler.py:476-485、540-549），它是 TaskScheduler.start 时以 storage=None（纯内存）创建的实例；仅当该管理器未启用时，才回落本地 _periodic_tasks 字典分支。调度线程的 _scheduler_loop（225 行起）每隔 scan_interval=1.0s 扫描，从 periodic_manager.list_tasks() 取任务，到期则执行（含 missed 补偿计算），每次执行都是独立 task_id。

要点：

  • 延时单次任务（submit_delayed 等）：未启用时间轮时直接调 pool.submit(delay=...)，进 DelayedQueue 后由 4.1 节的 0.1s 循环驱动，与扫描循环无关。

  • 时间轮已接线（enable_time_wheel 默认 False）：启用后，submit_delayed / submit_at 会走 _submit_delayed_via_time_wheel——先 create_pending_task_async 落库为 PENDING，再 time_wheel.add_task；到期回调只对仍为 PENDING 的任务 enqueue_task_async（等待期间被取消/删除的任务不会补跑）。延迟超出量程（槽位数 × max_rounds × tick，默认 tick=1.0 → 约 6000s）时 add_task 返回 -1，自动退回延时队列（retry_async）。shutdown() 会把未到期任务 drain() 出来、按重算后的剩余延迟交还延时队列，避免内存轮里的任务被静默丢弃。

  • 周期任务实例由 PeriodicTaskManager 保存在进程内存（storage=None）——进程重启后周期任务全部丢失（尚未做周期任务持久化，periodic.py 的 _load_tasks/_save_task 仍是 TODO）。

  • 扫描循环的粒度是 1 秒（非事件驱动），含 missed 补偿逻辑，周期实例与单次任务完全解耦。

6.2 回收链路：HeartbeatManager 与 TaskReclaimer 🔧

Redis 模式下存在两条已闭环的回收路径，都被装配进 TaskPool（task_pool.py:157-218）：

路径 A：HeartbeatManager 死节点回收（core/heartbeat.py）

  • 节点注册：与 NodeManager 共用同一份注册表——HSET neotask:node:{node_id}（node_id/status/last_heartbeat）+ SADD neotask:nodes，键 TTL 为 timeout × 2（默认 40s）。两个组件互相可见，不会各维护一套节点视图；

  • 心跳上报：每 interval=5s 更新 last_heartbeat（并续期 TTL）；

  • 死节点检测：_monitor_loop 每 cleanup_interval=30s 扫描 neotask:nodes，status != stopped 且 now - last_heartbeat > timeout(20s) 判死；

  • 任务回收：_reclaim_node_tasks 经 TaskRepository.list_by_status(RUNNING) 取任务（不直接操作任务键），只回收 task.node_id == 死亡节点 id 的任务；对每个命中任务：置 PENDING、清 node_id、清 started_at、写 error = "Reclaimed from dead node {id}"、repo.save，然后 queue_scheduler.push 重新入队；若 push 失败（队列满/禁用），警告并改判 FAILED。最后把死亡节点状态标为 reclaimed。任务状态全程走 TaskRepository，对 memory/sqlite/redis 三种后端都成立。

路径 B：TaskReclaimer 周期回收（worker/reclaimer.py）

  • 每 interval=30s 执行一次 _execute_reclaim：先回收超时任务，再回收孤儿任务（僵尸锁由内部 LockScanner 的独立 60s 循环处理）；

  • 超时回收：取全部 RUNNING 任务，elapsed > task.ttl（注意是任务自己的 ttl，默认 3600s，不是执行超时 task_timeout）→ 走 _reclaim_single_task：未超最大重试则复位 PENDING + retry_count+1 + delay=retry_delay × 新次数 重新入队 + 释放锁 + 发 task.reclaimed 事件；入队被拒则置 FAILED + 投递死信；超限则置 FAILED + 投递死信；

  • 孤儿回收：活跃节点来自 NodeManager.get_active_nodes()；_get_active_nodes 在未配置节点管理器时返回 None（不是空集合），此时整轮孤儿回收被跳过并打印一次性警告 Orphan reclaim skipped: no node manager configured, cannot determine active nodes。配置了节点管理器时，_reclaim_orphan_tasks 会跳过 node_id == 本节点 的任务，只回收 node_id 非空且不在活跃集合中的 RUNNING 任务。

  • node_id 口径统一：任务打标（Dispatcher）、Worker 标记（start_task(task_id, self._node_id)）、NodeManager 注册、回收跳过共用同一个 TaskPoolConfig.node_id（默认主机名），不存在两套命名错位。

✅ 结论：判死 → 回收 → 重入队 → 重执行 的链条已闭环，且不会误伤正常执行的任务（本节点跳过 + 存活节点跳过）。唯一仍需注意的既有事实：NodeManager._health_check_loop 内的 # TODO: 处理故障节点 尚未实现——那是节点管理器自身的健康巡检，与上面两条回收路径无关。

6.3 DeadLetterQueue：已接线的死信 🔧

queue/dead_letter.py 提供完整的死信能力（DeadLetterReason 枚举、send/get/list/replay/remove/count/clear、set_alert_callback），且已接入主链路。Redis + enable_dead_letter=True（默认）时，TaskPool 创建实例并注入 WorkerPool（set_dead_letter_queue）与 Reclaimer（构造参数 dead_letter）；默认 max_size=10000、ttl=604800（7 天）：

  • Worker 侧：_handle_task_failure 在"重试次数耗尽"或"重试重新入队被拒"时调用 _send_to_dead_letter（原因 MAX_RETRIES）；

  • 回收器侧：_reclaim_single_task 在"回收重试超限"或"重试入队被拒"时调用 _send_to_dead_letter，原因按回收原因映射（TIMEOUT→TIMEOUT、ORPHAN→ORPHANED、CANCELLED→CANCELLED，未知→BUSINESS_ERROR）；

  • 未注入死信实例（内存/SQLite 形态或关闭开关）时，投递方法静默跳过，不报错。

七、事件总线与订阅关系

7.1 EventBus 的两种订阅 🔧

event/bus.py 提供 subscribe(event_type, handler)（按类型订阅）与 subscribe_global(handler)（全量订阅）两种方式。TaskPool 内部的订阅关系（task_pool.py:258-293）：

事件 订阅方 动作
task.completed FutureManager complete(task_id, result) 唤醒等待方
task.failed FutureManager complete(task_id, error=...) 让等待方抛异常
task.cancelled FutureManager complete(task_id, error="Task cancelled")
task.created/started/completed/failed/cancelled/retry MetricsCollector 指标计数（enable_metrics=True 时）；task.created 载荷带 priority，task.retry 载荷带 retry_count
task.reclaimed 内置 handler 仅 debug 日志（监控用途）
task.progress 无发布方 _update_task_progress（pool.py:381）全库无调用点（断链）

注意事件流与生命周期是两条独立的通知通道：状态落库走 lifecycle → repository，通知走 lifecycle → future_manager（complete 是直接方法调用，181、220、245 行）+ event_bus（事件）。wait_for_result 依赖的是 FutureManager 通道而非事件通道，因此事件断链不影响等待语义——但监控/告警若依赖 task.progress 事件，将永远收不到数据（task.retry 已由指标采集器订阅，可正常收到）。

7.2 为什么这么设计

问题 答案
为什么等待不直接轮询存储？ Future 通道是内存 asyncio.Event，O(1) 唤醒、零存储压力；等待方在任务终态前只挂起不空转。wait_for_task 在超时/异常后还会二次读状态兜底（lifecycle.py:291-306），防 Future 漏通知
为什么已有 Future 通道还要事件总线？ 事件总线面向外部扩展（用户可订阅任务生命周期做审计/通知），且支持多订阅者；Future 是 1:1 的内部机制。代价是双通道状态必须保持一致——目前 task.progress 仍是唯一未接线的环节
为什么任务进度事件被实现却没接线？ _update_task_progress 已具备"更新存储 + 发事件"的完整逻辑，但 Worker 执行路径从未调用它——进度功能是"预留接口"，需要用户自行在 executor 中通过其他方式实现进度上报

Task.to_dict()（models/task.py）是全部存储与事件共用的序列化通道：data/result 在 to_dict 时 json.dumps 成字符串；from_dict 反向解析。因此：

  • Task 的 progress/progress_message 字段存在，SQLite/Redis 均支持读写，只是执行链路从不更新（7.1 节断链）。

十、故障场景实战

场景 1：节点失联后任务被其他节点接管，出现重复执行 📝

现象：Redis 模式多节点，B 节点因网络抖动超过 20s 未上报心跳（或进程卡死），其 RUNNING 任务被其他节点判为孤儿回收，任务被再次执行——而 B 节点其实还在跑，出现重复执行。

根因链：B 的 node_id 落入 NodeManager.get_active_nodes() 之外 → 其他节点的 Reclaimer 判定 task.node_id not in active_nodes → 复位 PENDING + 重新入队 + 释放锁（reclaimer.py _reclaim_single_task）；同时 HeartbeatManager 判死后也会按 task.node_id == 死亡节点 回收同一批任务。B 若仍存活且持有锁，新执行者 acquire 失败；但若 B 的锁已因抖动过期，则新执行者会真的再跑一遍。

对策：① 业务侧幂等是唯一根治手段（框架只保证"调度层面不双跑"）；② 调大 heartbeat_timeout 与锁 TTL 可降低网络抖动引发的误判概率；③ 不要把本节点任务误判的风险寄托在"回收器不会动本地任务"上——本地跳过只保护同一进程内的回收器，跨节点仍以心跳为准。

场景 2：同步函数把事件循环堵死 📝

现象：默认 executor_type=ASYNC，提交同步函数任务后，全部任务排队不执行，心跳与监控也停止刷新。

根因：ExecutorFactory 对同步函数做静默包装（task_pool.py:223-226 包装为 async def wrapped_executor，但包内是同步调用）——在 ASYNC 模式下该包装协程运行于 TaskPool 的事件循环线程，同步阻塞直接卡死整个循环（包括 DelayedQueue 的 0.1s 调度循环与心跳上报）。

对策：同步函数显式配置 executor_type="thread"（或 “process”），让 ExecutorFactory 交给 ThreadPoolExecutor/进程执行器；异步函数保持默认。判断当前生效执行器：提交一个含 time.sleep(2) 的同步任务，若期间其他任务全部停滞即命中本场景。

场景 3：wait_for_result 永不返回、队列里却堆满 PENDING 📝

现象：调用方捕获/吞掉了入队异常（或使用批量提交未逐条检查），随后拿到一个 task_id 去 wait_for_result 却一直挂起；get_stats() 显示队列积压，任务状态停留 PENDING。

排查顺序：① 先确认任务是否真实入队：队列满时 submit 会抛 QueueFullError 并已把任务置 FAILED（3.4 节），若未捕获该异常需在日志里核对，同时检查 queue_max_size 是否被调小；② 再看 Worker 是否存活：执行器类型与任务函数不匹配（场景 2）时队列只进不出；③ 最后核对 max_retries：重试任务 delay 线性增长 + 转正 score=5（4.2 节），大量重试任务会排在即时任务之后造成"饿死"假象——用 get_stats() 区分 failed 与 pending 的数量比。

场景 4：重启后周期任务全部消失 📝

现象：进程重启后，submit_interval/submit_cron 注册的任务不再触发，也没有任何报错。

根因：周期任务实例只存在于 TaskScheduler 的内存字典，由 1s 扫描循环驱动（6.1 节）；v1.0.2 未做周期任务持久化。延时单次任务（submit_delayed）因走 TaskPool 的存储层，SQLite/Redis 模式下重启后仍在队列中，行为与周期任务不一致。

对策：周期任务用外部配置驱动（启动时重新注册）；或自行持久化周期注册表并在启动时恢复；同时把 next_run 的漂移容忍写进业务（扫描粒度 1s 意味着触发时刻存在 ±1s 抖动）。
