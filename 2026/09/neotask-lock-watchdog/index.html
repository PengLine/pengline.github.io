同一任务被执行两次才是事故：NeoTask 分布式锁与看门狗实战

分布式任务调度系统里，故障分两种：响的和哑的。任务报错是响的——有日志、有告警、有重试，顶多烦人。同一任务被两个节点各执行一次，是哑的——每次执行都完整、自洽、看起来成功，伤害全在业务侧：重复扣款、重复发券、库存超卖。等你从脏数据里发现它，往往已经发生过不止一次。

这就是任务调度的锁与业务锁的区别：业务锁要“互斥”，任务调度的锁还要“自愈”——节点会崩、进程会被 kill -9、网络会抖，锁必须接受“持有者可能永远不回来”。本文以 NeoTask（v1.0.5）为蓝本，把分布式锁与看门狗从设计取舍讲到生产排障。机制细节在官方分布式锁与故障恢复文档里有源码级展开，本文聚焦为什么这么设计、实战里怎么用对。

一、先看朴素方案的破绽

在讲 NeoTask 的答案之前，先把三个"看起来可行"的方案摆出来，它们的破绽各有代表性：

方案 思路 破绽
进程内锁（如 asyncio.Lock） 同一进程内互斥 多节点部署完全失效，节点间照样重复执行
数据库 SELECT ... FOR UPDATE 行锁互斥 每个任务开一个事务，调度吞吐被锁等待和连接池拖垮
单纯 SET NX 不加过期 键存在即互斥 持锁节点崩溃后锁永不释放，系统整体死锁

破绽的共性很清楚：只考虑了"正常时互斥"，没考虑"异常时收敛"。任务调度的锁要同时满足两个目标：正常时绝对互斥，异常时尽快自愈。

顺带回答一个常见选型问题：为什么不选 ZooKeeper 或 etcd？两者的一致性模型更严格（临时节点 + Watch，线性一致），但代价是独立集群的部署运维成本，以及任务调度锁高频抢占下不划算的毫秒级延迟。Redis 与任务队列共用一套基础设施，SET NX EX 原生支持、亚毫秒响应。取舍的核心是：调度锁保护的不是“资金转账”级的强一致，而是防止“同一任务执行两次”——要求正常时互斥、异常时尽快收敛。Redis 主从切换瞬间丢失几毫秒写入，最多造成短暂双执行窗口，随后被状态机与回收器收敛；极端一致性要求的业务仍应在业务侧做幂等。

NeoTask 的答案是三件套组合：SET NX EX 原子获取、Lua 脚本安全释放、看门狗自动续期，再叠加任务状态机与回收器，形成三层防线。

三层不是重复建设，而是互补：锁保证互斥，状态机保证“锁丢了错误路径也被挡住大半”，回收器保证“节点故障后任务有人接管”。调度系统永远不信任单一机制。

二、一条命令的三种语义：SET NX EX

NeoTask 获取锁的真实代码出乎意料地朴素：

SET lock:task:xxx owner NX EX 30 这一条命令同时完成三件事：

  1. NX：键不存在才写入——同一时刻只有一个节点成功；

  2. owner：随机持有者标识——释放/续期前先验身份，防止“释放别人的锁”；

  3. EX 30：到期自动删除——持有者崩溃后锁也能自愈。

Redis 单线程事件循环保证这条命令本身原子，不存在“先检查后设置”的竞态。这里有个值得品的细节：RedisLock 里虽然定义了获取锁的 Lua 脚本常量，但 acquire() 实际走原生 set(nx=True, ex=ttl)——Lua 只在“多条命令需要组合成事务”时才必要。获取一条命令就够，就不写 Lua；释放和续期要“比对 + 删除/续期”两步，才必须 Lua。这个判断标准能帮你在自己的实现里避免“为了 Lua 而 Lua”。

owner 用 uuid4() 而不是“节点 ID + 时间戳”：本地生成、全局唯一、不可伪造、零协调——释放时它是“身份证”，随机化杜绝了“恰好撞值误删他人锁”的极端可能。

三、看门狗：TTL 两难的工程解

锁有了 TTL 就有两难：太短，长任务锁过期，另一个节点可能抢占同一任务；太长，持锁节点崩溃后锁迟迟不释放，恢复慢。看门狗（WatchDog）把这两个诉求解耦：TTL 设短（默认 30s，崩溃后最多 30s 自愈），同时由守护协程在任务执行期间持续续期（长任务不断锁）。WorkerPool 执行任务的真实流程是：校验任务状态 PENDING → 获取锁 → 启动看门狗 → 状态置 RUNNING → 执行业务 → finally 里停看门狗、释放锁。

sequenceDiagram
    participant W as Worker 协程
    participant LM as LockManager
    participant WD as WatchDog
    participant R as Redis

    W->>W: 校验任务状态 == PENDING
    W->>LM: acquire("task:{id}", ttl=30)
    LM->>R: SET lock:task:{id} uuid NX EX 30
    LM-->>W: True
    W->>WD: start("task:{id}", ttl=30)
    Note over WD,R: 每 9s 续期一次（TTL × 0.3）
    W->>W: start_task → RUNNING → 执行业务
    W->>WD: stop()
    W->>LM: release()（Lua 比对 owner 后 DEL）

这个顺序有两处细节：状态校验在加锁之前——任务一旦进入 RUNNING，其他节点即使抢到锁也会因状态不是 PENDING 而跳过；置 RUNNING 在拿锁成功之后——避免“RUNNING 但没有锁保护”的裸奔窗口。锁把“检查-置位-执行”变成临界区，状态机在锁失效时兜住错误路径。

为什么续期间隔取 TTL 的 0.3

看门狗默认 interval_ratio=0.3，即 TTL 30s 时每 9s 续期一次（max(0.5, 30 × 0.3)，🔧 lock/watchdog.py:65）。这个系数不是拍脑袋：

  • 不能太晚（超过 TTL/2）：一次网络抖动或 GC 停顿就可能让锁在两次续期之间过期；

  • 不能太频繁（小于 TTL/10）：每次续期都是一次 Redis 往返；

  • 0.3 的经验依据：续期后 9s 再续，距锁过期还有 21s 余量——允许连续两次续期失败仍不丢锁。

看门狗也不是免费午餐：每把锁每 9 秒一次 Redis 往返，100 把并发长锁约 11 QPS，相对任务调度本身可以忽略；常驻成本是一个活跃锁一个守护协程，worker_concurrency=10 就是 10 个协程。用“每 9 秒一次轻量往返”换“崩溃后 30 秒内自愈 + 长任务不断锁”，这笔交易明显划算。

一个多锁并发的隐藏前提

高并发下同一个 RedisLock 实例会同时持有多个锁（worker_concurrency=10 就是 10 把）。若续期用实例级单一 owner，后 acquire 的锁会覆盖前一把的 owner，先持有的锁就续不上期。NeoTask 在实例内维护“key → owner token”映射，续期按 key 取 owner，配合 Lua 原子比对——多锁各续各的。结论反直觉但重要：长任务 + 高并发这个最需要看门狗的场景，反而是它最稳的场景。

四、锁续期失败以后，任务怎么办

这是生产真正会咬人的问题，值得一层层推演。

第一层：看门狗停了，任务会怎样？ 任务继续跑。看门狗与业务执行是两个独立协程，退出循环只是不再续期，业务协程对锁丢失一无所知，会执行完再在 finally 收尾（release 大概率返回 0）。这是有意的取舍：强制中断可能正写到一半数据库、正在调第三方 API，半截状态更危险。宁可让它跑完，把一致性交给状态机与业务幂等。

第二层：什么情况下会真的造成重复执行？ 锁过期本身不必然出事——任务状态还是 RUNNING，状态机会挡住大部分重入。真正危险的组合是：超时/孤儿回收把任务重新入队（状态重置为 PENDING）之后，原节点还没跑完。此时新老两个节点都在执行同一任务，状态机完全失效。这正是回收器把任务重新入队时必须同时释放旧锁的原因，也是任务处理器必须幂等的根本理由。

第三层：兜底永远是业务幂等。 框架只能保证“调度层面尽量不双跑”，保证不了“任务跑两次副作用相同”——发短信任务重跑一次就是两条短信。业务侧自备幂等键（订单号、request_id），把“调度至多一次”升级为“业务恰好一次”。

"业务幂等"四个字说起来容易，落地时先分清你的任务属于哪一类。常用的是四种模式，成本与适用面各不同：

模式 做法 适用任务 代价
天然幂等 操作本身可重复（如"把状态置为已完成"） 状态置位、缓存刷新 零成本，首选
条件更新 UPDATE ... WHERE status='待处理'，影响行数为 0 即放弃 单实体状态流转 一条 WHERE，几乎零成本
幂等键 业务侧建去重表，以订单号/request_id 做唯一约束 发短信、扣款等外部副作用 一张表 + 一次查询
对账补偿 事后核对副作用记录，重复的做补偿回滚 无法前置幂等的遗留系统 对账任务 + 人工流程

给最常见的外部副作用任务一个最小示例——发短信前先抢幂等键：

注意分支语义：重复执行应返回成功而不是报错——重试机制看到“失败”只会再重试。调度层防重 + 业务层幂等，两层各自正确，“同一任务执行两次”才从事故降级为一次无感的重复调用。选择顺序：天然幂等 → 条件更新 → 幂等键 → 对账补偿，越靠后修复成本越高。

五、出队与加锁为什么要分开

一个容易产生技术误解的设计：NeoTask 的批量抢占并不加锁。Redis 模式下消费端用 Lua 脚本 ZRANGE + ZREM 原子批量弹出任务——只做"取 + 删"。分布式锁发生在 Worker 真正执行任务之前。

"出队 + 加锁"合成一个脚本技术上完全可行，但刻意拆成两步，理由有三：

  1. 节奏不同：出队是批量（一次 pop N 个），执行是逐个。出队即加锁会让预取的 20 个任务同时持有 20 把锁，节点崩溃时 20 把锁一起残留；

  2. 预取缓冲不需要锁：任务还在本地队列、尚未执行，加锁只会提前消耗 TTL；需要保护的是“开始执行”那一刻；

  3. 语义分离：分配的互斥由 ZREM 原子性保证，执行的互斥由锁保证，故障模型更简单。

有人会问：出队已经原子互斥了，为什么执行前还要锁？因为出队互斥只防“同时取出”，防不了“再次取出”——失败重试、孤儿回收、人工补偿都会让同一 task_id 再次入队，在另一个节点上执行。执行锁 + PENDING 检查挡的正是跨轮次的重复。

一句话：队列负责“任务不重”，锁负责“执行不重”，状态机负责“结果不乱”。 连带收益是预取能用 ZRANGE + ZREM 批量原子脚本，不必逐任务加锁——互斥用原子性而非锁实现，性能与正确性在这里同向。

六、锁丢了之后：回收器的兜底链路

异常路径的最后一环是回收器（TaskReclaimer）。NeoTask 属于被动租约派：执行者持有租约（锁 + TTL），过期即可接管，不关心执行者死活。主动检测派靠心跳判死再接管，但心跳会误报（网络抖动）、判死会误杀（GC 停顿）；租约是确定性的，TTL 过期就是过期。检测可以慢、可以错，恢复依然正确，系统因此不依赖故障检测精度。

回收器（TaskReclaimer）只在 Redis 形态初始化（🔧 api/task_pool.py:134-135），每 30s 扫一次 RUNNING 索引：超时回收（执行时长超过任务 ttl）与孤儿回收（执行节点不在活跃集合中）。两个容易误解的口径：

  • 超时口径不是“5 分钟”，而是任务自身的 ttl，默认 3600s。提交时按业务预期显式传 ttl（如视频转码 ttl=600），否则卡死任务会白占 RUNNING 索引一小时；

  • 孤儿回收极其保守：拿不到活跃节点集合就整轮跳过；本节点正在执行的任务绝不回收；节点只是短暂失联也不回收。

回收命中后统一走一个入口：状态重置 PENDING、重试计数 +1、清空执行节点、按 1s、2s、3s 线性递增延迟重新入队，并尝试释放旧锁。注意“尝试”——跨节点回收时回收器不知道原 owner，锁若仍被续期（原节点还活着），release 会因 owner 不匹配失败，锁安然不动，正在执行的任务不会被打断；锁若已过期，release 幂等无害。同一节点内的超时回收走同一个 LockManager，owner 匹配，能释放自己持有的锁。结论要带上范围：跨节点的回收者无权删别人正在续期的活锁，这是回收体系最重要的安全属性：真正决定“任务是否继续执行”的永远是锁。

重试不是无限的：超过 max_retries（默认 3）的任务标记 FAILED 并投递死信队列——Redis 模式默认开启，容量 10000 条（满后淘汰最旧），保留失败原因（超时/孤儿/超限）与完整上下文，保留 7 天。需要人工补偿时，DeadLetterQueue.replay(task_id) 只做一件事：取出条目、从死信队列移除并返回成功（🔧 queue/dead_letter.py:204-225），不会自动重新入队或执行——把任务重新提交回任务池是调用方的事。也正因如此，重新提交的流程没有任何捷径：同一 task_id 仍要重新走 PENDING 校验、执行锁与业务幂等。

把一个节点崩溃的完整时间线串起来：

sequenceDiagram
    participant N as 宕机节点 B
    participant R as Redis
    participant RC as 回收器（其他节点）
    participant W as 新节点接管

    N->>R: 持有 lock:task:A（TTL 30s）任务 RUNNING
    Note over N: 进程被 kill -9
    Note over R: 看门狗消失 30s 后锁自动过期
    RC->>R: 30s 周期扫描 RUNNING 索引
    RC->>RC: 判定孤儿（B 已不在活跃集）
    RC->>R: 置 PENDING + 释放旧锁 + 延迟 1s 重新入队
    W->>R: 出队 → acquire 成功 → 重新执行

全程约 30~60s；调小扫描周期与 TTL 可更快，代价是开销上升。

七、生产故障场景实战

四个真实形态的事故，各给一条排查路径。

场景一：日志刷 Watchdog failed to renew，业务偶发重复

排查：先确认续期失败是“返回 False”还是“抛异常”——前者是锁易主，后者是网络抖动；再查是否有人误删锁、Redis 是否在高负载或主从切换。注意 1.0.5 的口径：Worker 执行锁固定 30 秒、看门狗每 9 秒续期，lock_timeout 不会改变它——长任务不靠调大参数延长锁。最后回到业务幂等。

场景二：节点宕机，任务一小时没恢复

先确认一个前提：回收器只在 Redis 形态存在（🔧 api/task_pool.py:134-135）。memory/SQLite 形态下没有回收器，enable_orphan_reclaim 之类的开关都不会被实例化，卡在 RUNNING 的任务不会自动恢复——SQLite 的任务状态虽然落盘，也没有组件在重启后接管 RUNNING 记录，只能人工重提。确认是多节点 Redis 后，再查四个判据：node_id 是否为空（孤儿回收只认带 node_id 的 RUNNING 任务）、能否拿到活跃节点集合（拿不到就整轮跳过孤儿回收）、节点是否真的被判死（心跳键未过期仍算活跃）、回收循环是否在跑。都正常的话，任务应在一两个扫描周期内被捞回；否则检查回收器与 Redis 连接。手动干预：API 取消后重新提交，或触发一轮手动回收。

场景三：运维清锁清出双执行

运维误判节点死亡、手动删锁，而该节点只是网络分区且仍在续期——锁被删后任务被其他节点抢占，原节点恢复后继续执行，双执行。预防：删锁前三重确认（心跳超时 + 锁空闲超时 + 无进度更新）；优先用 cleanup_stale_locks，而不是指定持有者的 cleanup_by_owner；流程上“先标记死亡 → 等宽限期 → 再清锁”。

场景四：Redis 主从切换后的短暂双主

Redis 主从复制是异步的，failover 瞬间旧主的锁写入可能未同步到新主，两个节点同时 SET NX 成功。这是所有单实例 Redis 锁的固有边界（Redlock 也只是降低概率）。NeoTask 的定位很坦诚：锁是“低成本防重”，不承诺线性一致——调度场景的双执行窗口通常是毫秒级，配合状态机与业务幂等可以消化；严格互斥的业务（如资金操作）应在业务事务内二次校验。

僵尸锁扫描：能跑，但别把它当最后一张网

即使有 TTL 兜底，仍会出现残留锁：时钟漂移、主从切换丢命令、release 未送达。1.0.5 在 Redis 形态下由回收器组合一个 LockScanner（enable_stale_lock_reclaim=True，默认 60s 一轮）。但它当前的实际能力比名字弱：判定函数 _is_stale_lock 只调用 get_ttl / is_locked / exists（🔧 lock/scanner.py:135-166），而 RedisLock 只实现了 is_locked，没有 get_ttl / exists / delete；stale_ttl_threshold（默认 300s）也没有参与判定。扫到的键都还存在，于是被判定为“非僵尸”，自动清理基本不会发生。RedisLock.cleanup_stale_locks(ttl_threshold) 确实实现了按 TTL/空闲阈值删除，但它是手动方法，不在自动循环里。

所以正确的预期是：僵尸锁的最终兜底是 TTL 自动过期，不是扫描器。需要主动清理时，手动调用 cleanup_stale_locks()，或三重确认后用 cleanup_by_owner()；不要把“自动扫描会兜底”写进 runbook。

上线前自检：锁健康的四个观测点

这套机制跑在生产上，日常盯什么？四个指标，分别对应四类故障的早期信号：

  1. 续期失败计数（False/异常分开）：False 非零说明锁在易主，查误删与 TTL；异常突增说明 Redis 网络在恶化；

  2. 锁获取延迟 p95：正常接近一次 Redis 往返；抬升意味着锁竞争或慢查询，比“任务变慢”的感知更早；

  3. 回收计数（超时/孤儿分开）：孤儿非零必然死过节点，该查基础设施；超时持续非零说明有任务的 ttl 短于真实执行时长；

  4. 死信堆积与最老条目年龄：堆积上涨说明某类任务系统性失败；最老条目几天没人处理，说明 replay 流程形同虚设。

这四个点不需要额外组件，Redis 信息和框架计数器就够了。锁故障九成是慢性的，等业务报出重复扣款再查就晚了。把四项指标与排查动作写进 runbook，值班同学不必读完本文也能处理九成告警。

八、配置建议

锁与回收配置大部分在 TaskPoolConfig，但有两个关键参数不在配置对象里，先说边界：

配置项 默认值 实际作用与调优建议
lock_type memory 单机用 memory；多节点部署必须 redis
lock_timeout 30s 1.0.5 的 TaskPool 路径不生效：执行锁硬编码 30s，手动 acquire_lock 自带 ttl。别依赖它调优
看门狗 始终启用 Worker 路径固定 WatchDog(interval_ratio=0.3)；LockConfig.watch_dog_enabled 存在但未使用
max_retries 3 必然失败的任务调小，避免无效重试放大下游压力
reclaimer_interval 30s 崩溃恢复时延的量级；调小提速、增开销
heartbeat_interval / heartbeat_timeout 5s / 20s 节点判活的依据，一般不动
enable_dead_letter True Redis 形态下重试超限自动投递死信
dead_letter_max_size / dead_letter_ttl 10000 / 7 天 按失败量与人工处理节奏调整
任务 ttl 3600s 长任务提交时显式传 ttl，这是回收器的超时判据

多节点生产的典型配置：

注意没有 watch_dog_enabled：1.0.5 的 TaskPoolConfig 不接受这个字段，照抄网上旧示例会抛 TypeError，这是从 1.0.2 升级时容易踩的坑。

TTL 与任务时长的搭配原则：Worker 执行锁固定 30s、看门狗每 9s 续期，长任务不需要调锁 TTL；真正要调的是任务自身的 ttl（回收器的超时判据）和 reclaimer_interval（接管延迟）。Redis Cluster 下，NeoTask 的锁脚本与出队脚本都只操作单键，天然兼容；自行写跨键 Lua 时需要用 hash tag 把相关键钉在同一 slot。

两个高频误用。其一，锁 TTL 与任务超时是两个旋钮：执行锁固定 30s（看门狗续期），卡死任务的回收口径是任务自身的 ttl（默认 3600s）——想更快回收，提交时把 ttl 传小，别动 lock_timeout。其二，不要在业务代码里手动 SET/DEL 锁键：绕过 owner 校验会把“误删他人锁”的竞态请回来；清锁一律走 cleanup_stale_locks，或三重确认后的 cleanup_by_owner。

最后给单机形态一个速查结论：lock_type=memory 时锁是进程内实现（threading.RLock 保护 owner/过期字典，非阻塞获取；🔧 lock/memory.py），跨协程、跨线程有效，但跨进程与跨节点无效；看门狗仍在长任务执行期间续期，避免执行锁在任务结束前过期。单机形态下没有回收器（只有 Redis 形态才初始化），所以“节点崩溃后由别的节点接管”这件事不存在：memory 形态重启后任务状态全部丢失；SQLite 形态的任务记录与队列表虽然落盘，但没有启动扫描接管 RUNNING 记录，已 pop 未执行的任务也不会回灌——重启后能继续的只有仍留在队列表里的 PENDING 行。分布式锁与回收器的复杂度，只在多节点 Redis 部署那天才需要支付，这也是嵌入式任务池“先单机、后分布式”路线的价值。

九、工程结论

  1. 分布式锁的价值不在互斥，在自愈。SET NX EX 一条命令同时拿到互斥与崩溃自愈，owner 随机化 + Lua 原子释放堵住“误删他人锁”，看门狗解耦“短 TTL 快速自愈”与“长任务不断锁”——每一层都在为异常路径设计；

  2. 分层防御，不信任任何单一机制。队列防“任务不重”、锁防“执行不重”、状态机防“结果不乱”、回收器兜节点故障、看门狗保长任务、死信接住彻底失败。任何一层失效，其余层把事故收敛到“业务幂等”这最后一道防线；

  3. 锁丢了不可怕，可怕的是不知道丢了之后系统怎么运行：续期失败停手而不是疯狂重试（别给别人的锁续命）、任务跑完而不是强制中断（半截状态更危险）、跨节点回收器无权删别人正在续期的活锁、超时口径以任务声明的 ttl 为准、回收器只在 Redis 形态存在。这些边界行为比 benchmark 数字更值得考察——把“续期失败后任务去向、回收器的作用范围与权限、崩溃到接管的时延”列成清单，逐项向候选框架求证。
