同一任务被执行两次才是事故：NeoTask 分布式锁与看门狗实战

分布式任务调度系统里，故障分两种：响的和哑的。任务执行报错是响的——有日志、有告警、有重试，顶多烦人。同一任务被两个节点各执行一次，是哑的——每次执行都完整、自洽、看起来成功，伤害全部发生在业务侧：重复扣款、重复发券、库存超卖。等你从脏数据里发现它，往往已经发生了不止一次。

这就是为什么任务调度的锁与普通业务锁不是一回事。业务锁要的是"互斥"，任务调度的锁还要"自愈"——节点会崩、进程会被 kill -9、网络会抖，锁必须接受"持有者可能永远不回来"这一事实。本文以 NeoTask（v1.0.2）的实现为蓝本，把分布式锁与看门狗这对组合从设计取舍讲到生产排障。机制细节在官方分布式锁与故障恢复文档里有源码级展开，本文聚焦为什么这么设计、实战里怎么用对。

一、先看朴素方案的破绽

在讲 NeoTask 的答案之前，先把三个"看起来可行"的方案摆出来，它们的破绽各有代表性：

方案 思路 破绽
进程内 asyncio.Lock 同一进程内互斥 多节点部署完全失效，节点间照样重复执行
数据库 SELECT ... FOR UPDATE 行锁互斥 每个任务开一个事务，调度吞吐被锁等待和连接池拖垮
单纯 SET NX 不加过期 键存在即互斥 持锁节点崩溃后锁永不释放，系统整体死锁

破绽的共性很清楚：只考虑了"正常时互斥"，没考虑"异常时收敛"。任务调度的锁要同时满足两个目标：正常时绝对互斥，异常时尽快自愈。

顺带回答一个常见选型问题：为什么不选 ZooKeeper 或 etcd？两者的一致性模型确实更严格（临时节点 + Watch，线性一致），但代价是独立集群的部署与运维成本、毫秒到十毫秒级的延迟——而任务调度的锁高频抢占，对延迟敏感。Redis 与任务队列共用一套基础设施，SET NX EX 原生支持，亚毫秒级响应。取舍的核心在于：调度锁不是要保护"资金转账"级别的强一致，而是要防止"同一任务执行两次"——后者的诉求是"正常时绝对互斥、异常时尽快收敛"，Redis 主从切换瞬间丢失几毫秒的写入，最多造成短暂的双执行窗口，随后被状态机与回收器收敛。这个取舍是 NeoTask 定位"轻量嵌入式调度库"的必然选择，极端一致性要求的业务仍应在业务侧做幂等。

NeoTask 的答案是三件套组合：SET NX EX 原子获取、Lua 脚本安全释放、看门狗自动续期，再叠加任务状态机与回收器，形成三层防线。

三层不是重复建设，而是互补：锁保证互斥，状态机保证"即使锁因异常丢失，错误的执行路径也会被挡住大半"，回收器保证"节点故障后任务有人接管"。调度系统永远不信任单一机制——这是理解后面所有设计的前提。

二、一条命令的三种语义：SET NX EX

NeoTask 获取锁的真实代码出乎意料地朴素：

SET lock:task:xxx owner NX EX 30 这一条命令同时完成三件事：

  1. NX：键不存在才写入——互斥，同一时刻只有一个节点成功；

  2. owner（锁值）：写入随机持有者标识——身份可校验，后续释放/续期时先验身份，防止"释放别人的锁"；

  3. EX 30：到期自动删除——持有者崩溃后锁也能自愈。

Redis 单线程事件循环保证这条命令本身原子，不存在"先检查后设置"的竞态窗口。这里有一个值得品的设计细节：RedisLock 类里虽然定义了获取锁的 Lua 脚本常量，但 acquire() 实际走的是原生 set(nx=True, ex=ttl)——Lua 不是装饰品，只在"多条命令需要组合成事务"时才必要。获取锁一条命令就够，就不写 Lua；释放和续期需要"比对 + 删除/续期"两步，才必须 Lua。这个判断标准值得记住，它帮你在自己的实现里避免"为了 Lua 而 Lua"。

owner 为什么用 uuid4() 而不是"节点 ID + 时间戳"？UUID 本地生成、全局唯一、不可伪造、零协调——释放时它是"身份证"，随机化杜绝了"恰好撞值误删他人锁"的极端可能。

三、看门狗：TTL 两难的工程解

锁有了 TTL 就有了两难：

  • TTL 太短：任务跑久一点锁就过期，另一个节点可能重新抢占同一任务 → 重复执行；

  • TTL 太长：持锁节点崩溃后，锁要等很久才释放 → 故障恢复慢，任务长时间无人接管。

看门狗（WatchDog）的思路是把这两个诉求解耦：TTL 设短（默认 30s，崩溃后最多 30s 自愈），同时由守护协程在任务执行期间持续续期（长任务不断锁）。WorkerPool 执行任务的真实流程是：校验任务状态 PENDING → 获取锁 → 启动看门狗 → 状态置 RUNNING → 执行业务 → finally 里停看门狗、释放锁。

sequenceDiagram
    participant W as Worker 协程
    participant LM as LockManager
    participant WD as WatchDog
    participant R as Redis

    W->>W: 校验任务状态 == PENDING
    W->>LM: acquire("task:{id}", ttl=30)
    LM->>R: SET lock:task:{id} uuid NX EX 30
    LM-->>W: True
    W->>WD: start("task:{id}", ttl=30)
    Note over WD,R: 每 10s 续期一次（TTL 的 1/3）
    W->>W: start_task → RUNNING → 执行业务
    W->>WD: stop()
    W->>LM: release()（Lua 比对 owner 后 DEL）

注意这个顺序里藏着两处细节：状态校验在加锁之前——任务一旦进入 RUNNING，其他节点即使抢到锁也会因"状态不是 PENDING"而跳过；置 RUNNING 在拿锁成功之后——避免出现"状态是 RUNNING 但没有锁保护"的裸奔窗口。锁与状态机互补而不重复：锁把"检查-置位-执行"变成临界区，状态机在锁失效时兜住大半错误路径。

为什么续期间隔是 TTL 的三分之一

看门狗默认 interval_ratio=0.3，即 TTL 30s 时每 10s 续期一次。这个数字不是拍脑袋：

  • 不能太晚（超过 TTL/2）：一次网络抖动或 GC 停顿就可能让锁在两次续期之间过期，看门狗形同虚设；

  • 不能太频繁（小于 TTL/10）：每次续期都是一次 Redis 往返，任务量大时是纯开销；

  • TTL/3 的经验依据：留出 2/3 的 TTL 作为安全余量——允许大约两次连续续期失败而不丢锁。30s 的锁能扛约 20s 的网络抖动窗口，对生产环境的故障形态足够宽容。

看门狗也不是免费午餐，但账很好算：interval_ratio=0.3 下每把锁每 10 秒一次 Redis 往返，100 把并发长锁也就是 10 QPS 的续期流量——相对任务调度本身的 Redis 交互量可以忽略。真正的常驻成本是协程数量：每把活跃锁一个守护协程，worker_concurrency=10 就是 10 个看门狗协程，内存开销微乎其微。用"每 10 秒一次轻量往返"换"崩溃后 30 秒内自愈 + 长任务不断锁"，这笔交易明显划算。

一个多锁并发的隐藏前提

高并发场景下同一个 RedisLock 实例会同时持有多个锁（worker_concurrency=10 就是 10 把）。如果续期时用"实例级的单一 owner"，后 acquire 的锁覆盖前一把锁的 owner，先持有的锁就续不上期了。NeoTask 的实现是实例内维护「key → owner token」映射，续期按 key 取各自的 owner，配合 Lua 原子比对——多锁各续各的，互不干扰。结论反直觉但重要：长任务 + 高并发这个最需要看门狗的场景，反而是它最稳的场景。

四、锁续期失败以后，任务怎么办

这是生产环境真正会咬人的问题，值得单独一层层推演。

第一层：看门狗停了，任务本身会怎样？ 答案是：任务继续跑。看门狗与业务执行是两个独立协程，看门狗退出循环只是不再续期，业务协程对锁丢失一无所知，会执行到完成，然后在 finally 里照常收尾（release 大概率返回 0，锁已不在自己名下）。这是有意的设计取舍：强制中断执行中的业务逻辑几乎总是更危险——协程可能正写一半数据库、正在调第三方 API，贸然取消造成半截状态。宁可让它跑完，把一致性交给状态机与业务幂等兜底。

第二层：什么情况下会真的造成重复执行？ 锁过期本身不必然出事——任务状态还是 RUNNING，状态机会挡住大部分重入。真正危险的组合是：超时/孤儿回收把任务重新入队（状态重置为 PENDING）之后，原节点还没跑完。此时新老两个节点都在执行同一任务，状态机完全失效。这正是回收器把任务重新入队时必须同时释放旧锁的原因，也是任务处理器必须幂等的根本理由。

第三层：兜底永远是业务幂等。 框架能保证的是"调度层面的幂等"（任务尽量不双跑），保证不了"业务层面的幂等"（任务跑两次副作用相同）——“发短信"任务被重跑一次就是两条短信。业务侧自备幂等键（订单号、request_id），把"调度至多一次"升级为"业务恰好一次”。这一条不在任何框架的能力边界内，是使用者的必修课。

"业务幂等"四个字说起来容易，落地时先分清你的任务属于哪一类。常用的是四种模式，成本与适用面各不同：

模式 做法 适用任务 代价
天然幂等 操作本身可重复（如"把状态置为已完成"） 状态置位、缓存刷新 零成本，首选
条件更新 UPDATE ... WHERE status='待处理'，影响行数为 0 即放弃 单实体状态流转 一条 WHERE，几乎零成本
幂等键 业务侧建去重表，以订单号/request_id 做唯一约束 发短信、扣款等外部副作用 一张表 + 一次查询
对账补偿 事后核对副作用记录，重复的做补偿回滚 无法前置幂等的遗留系统 对账任务 + 人工流程

五、出队与加锁为什么要分开

一个容易产生技术误解的设计：NeoTask 的批量抢占并不加锁。Redis 模式下消费端用 Lua 脚本 ZRANGE + ZREM 原子批量弹出任务——只做"取 + 删"。分布式锁发生在 Worker 真正执行任务之前。

"出队 + 加锁"合成一个脚本技术上完全可行，但刻意拆成两步，理由有三：

  1. 出队与执行的节奏不同：出队是批量动作（一次 pop N 个），执行是逐个动作。若出队即加锁，预取的 20 个任务要同时持有 20 把锁——节点在处理本地队列时崩溃，20 把锁同时残留，放大故障面；

  2. 预取缓冲层不需要锁：预取机制先把任务放进节点本地队列，任务尚未开始执行，此时加锁只会提前消耗 TTL。真正需要锁保护的是"开始执行"这个时刻；

  3. 语义分离：分配（出队）的互斥由 ZREM 原子性保证，执行的互斥由锁保证。各自边界清晰，故障模型也简单。

有人会问：出队已经原子互斥了，为什么执行前还要锁？因为出队互斥只防"同时取出"，防不了"再次取出"——任务失败重试会重新入队、故障恢复会把孤儿任务重新入队、人工补偿可能重复提交。任务在队列里进出多次后，同一 task_id 完全可能在两个节点上"各自执行一轮"。执行锁 + PENDING 状态检查，挡的正是这些跨轮次的重复。

一句话总结这套分工哲学：队列负责"任务不重"，锁负责"执行不重"，状态机负责"结果不乱"。 这套分工还有个连带收益：出队不需要锁，意味着预取可以走 ZRANGE + ZREM 的批量原子脚本（官方基准里批量弹出吞吐是单条的两倍），而不必承受逐任务加锁的往返延迟——互斥用原子性实现而不是用锁实现，性能与正确性在这里难得地同向。

六、锁丢了之后：回收器的兜底链路

前面都在讲"正常路径上的锁"，但异常路径的最后一环是回收器（TaskReclaimer）。理解它的设计，先要知道 NeoTask 属于被动租约派：执行者持有租约（锁 + TTL），租约过期即视为可接管，不关心执行者死活。与之相对的主动检测派靠心跳判死再接管——但心跳可能误报（网络抖动）、判死可能误杀（GC 停顿）。租约是确定性的：Redis 上的 TTL 是硬事实，过期就是过期。检测可以慢、可以错，恢复依然正确，系统因此摆脱了对故障检测精度的依赖。

回收器每 30s 扫描一次 RUNNING 状态索引，做两类回收：超时回收（执行时长超过任务自身 TTL）与孤儿回收（执行节点不在活跃节点集合中）。两个容易误解的口径：

  • 超时判定的默认值不是"5 分钟"，而是任务对象自身的 ttl 字段——默认 3600s（1 小时）。"卡死 5 分钟自动回收"是常见误解；正确姿势是提交任务时按业务预期显式传 ttl（如视频转码 ttl=600），别依赖默认值，否则卡死任务会白占 RUNNING 索引一小时；

  • 孤儿回收的判定极其保守：未配置节点管理器时整轮跳过（宁可晚回收，不可错回收）；本节点自己正在执行的任务绝不参与回收；节点只是短暂失联（心跳键未过期）也不回收。

回收命中后的处置统一走一个入口：状态重置 PENDING、重试计数 +1、清空执行节点、按 1s、2s、3s 线性递增延迟重新入队，并尝试释放旧锁。注意"尝试"两个字——回收器并不知道原持有者的 owner，锁若还在续期（原节点其实活着），release 会因 owner 不匹配而失败，锁安然不动，正在执行的任务不会被回收动作打断；锁若已过期，release 幂等无害。回收者无权删活锁，这是整个回收体系最重要的安全属性：真正决定"任务是否继续被执行"的，永远是锁。

重试不是无限的：超过 max_retries（默认 3）的任务被标记 FAILED 并投递死信队列——Redis 模式下默认开启，容量默认 10000 条（满后淘汰最旧），保留完整上下文与失败原因（超时/孤儿/超限），保留期默认 7 天，支持 replay() 人工重放。状态机回答"它失败了吗"，死信回答"失败细节是什么、要不要人工介入"，两者并存。另外注意 replay() 重放的不是"豁免"：任务仍以同一 task_id 走完整流程——PENDING 校验、执行锁、业务幂等一道不少。人工重放只是把重试的机会还给你，不是绕过防线的后门。

把一个节点崩溃的完整时间线串起来：

sequenceDiagram
    participant N as 宕机节点 B
    participant R as Redis
    participant RC as 回收器（其他节点）
    participant W as 新节点接管

    N->>R: 持有 lock:task:A（TTL 30s）任务 RUNNING
    Note over N: 进程被 kill -9
    Note over R: 看门狗消失 30s 后锁自动过期
    RC->>R: 30s 周期扫描 RUNNING 索引
    RC->>RC: 判定孤儿（B 已不在活跃集）
    RC->>R: 置 PENDING + 释放旧锁 + 延迟 1s 重新入队
    W->>R: 出队 → acquire 成功 → 重新执行

全程约 30~60s。要更快，调小扫描周期与锁 TTL，代价是误回收窗口变小、扫描开销上升——量力而行。

七、生产故障场景实战

四个真实形态的事故，各给一条排查路径。

场景一：日志刷 Watchdog failed to renew，业务偶发重复

排查：先确认续期失败是"返回 False"还是"抛异常"——前者是锁易主/owner 不匹配，后者是网络抖动。然后检查锁 TTL 是否短于任务执行节奏（长任务建议调大 lock_timeout 到 60~120s），确认没有运维脚本误删活锁。最后回到业务幂等这个最后防线。

场景二：节点宕机，任务一小时没恢复

先查孤儿回收的四个判定前提：任务的 node_id 是否为空（孤儿回收只认带 node_id 的 RUNNING 任务）、是否装配了节点管理器（内存/SQLite 形态没有 NodeManager，孤儿回收整轮跳过，只剩 ttl 超时兜底）、节点是否真的被判死（心跳键未过期时短暂仍算活跃）、enable_orphan_reclaim 是否被关。都正常的话，任务应在一两个扫描周期内被捞回；还不恢复，检查回收器是否存活、Redis 连接是否健康。手动干预最快的两条路：API 取消后重新提交，或触发一轮手动回收。

场景三：运维清锁清出双执行

运维判定某节点"死了"，手动批量删除它持有的锁，结果该节点只是网络分区并未宕机——它手里的锁还在被看门狗续期，锁被删后任务被其他节点抢占，原节点恢复后继续执行，双执行。预防原则：删锁前必须三重确认（心跳超时 + 锁空闲超时 + 任务无进度更新）；优先用按空闲阈值自动判断的 cleanup_stale_locks 而不是人工指定持有者的 cleanup_by_owner；流程上遵守"先标记节点死亡 → 等宽限期 → 再清锁"。

场景四：Redis 主从切换后的短暂双主

Redis 主从复制是异步的，failover 瞬间旧主上的锁写入可能未同步到新主，两个节点同时 SET NX 成功。这是 Redis 分布式锁的固有边界（Redlock 也只是降低概率而非消除）。NeoTask 的定位很坦诚：锁是"低成本防重"，不承诺线性一致——调度场景下双执行窗口通常为毫秒级，配合状态机与业务幂等可以完全消化；需要严格互斥的业务（如资金操作）应在业务事务内二次校验。顺带说明：这也是所有基于单实例 Redis 的锁的共同边界——不是某个框架实现得好不好的问题，而是异步复制语义决定的物理上限，选型时应把它算进风险接受度。

僵尸锁扫描：最后一张网

即使有 TTL 兜底，仍会出现残留锁：时钟漂移、主从切换丢命令、release 因网络异常未送达而任务已结束。LockScanner 每 60s 扫一次锁键，对"TTL 异常/空闲超阈值（默认 300s）"的锁做清理。阈值定得比锁 TTL 大一个数量级是刻意的：正常长任务的锁有看门狗续期，可以合法存活几十分钟，只有"持有者失联"的锁才该被扫——清理僵尸锁宁可慢，不可错，反正 TTL 兜底最终会释放，扫描器只是加速收敛。

上线前自检：锁健康的四个观测点

这套机制跑在生产上，日常盯什么？四个指标，分别对应四类故障的早期信号：

  1. 看门狗续期失败计数（False 与异常分开计）：False 持续非零说明锁易主在发生——先查是否有人误删锁、TTL 是否短于任务节奏；异常突增说明 Redis 网络质量在恶化，是更大故障的前兆；

  2. 锁获取延迟分布（p95）：正常应接近一次 Redis 往返。p95 抬升通常意味着锁竞争加剧或 Redis 慢查询，比"任务变慢"这种下游感知早得多；

  3. 回收动作计数（超时/孤儿分开计）：孤儿回收非零必然意味着节点死亡过——哪怕业务无感，也该触发一次基础设施排查；超时回收持续非零则说明有任务的 ttl 定得比真实执行时长短，去修口径而不是放任重试；

  4. 死信队列堆积量与最老条目年龄：堆积上涨说明某类任务在系统性失败；最老条目超过几天没人处理，说明 replay 流程形同虚设——死信队列的价值在"有人看"，不在"有地方放"。

这四个点都不需要额外组件，Redis 已有的信息 + 框架暴露的计数器就够了。锁体系的故障九成是慢性的，等业务报出重复扣款再查， traces 早就凉了。最后一个建议是把这页写进 runbook：四项指标各自的告警阈值、对应的排查动作（对照第七节的四个场景），让值班同学不必读完本文也能处理九成的锁相关告警。

八、配置建议

锁与回收相关配置集中在 TaskPoolConfig，关键项与调优建议：

配置项 默认值 调优建议
lock_type memory 单机用 memory；多节点部署必须 redis
lock_timeout 30s 任务普遍超过 30s 时调大到 60~120s
watch_dog_enabled True 建议保持开启
max_retries 3 必然失败的任务调小，避免无效重试放大下游压力
reclaimer_interval 30s 崩溃恢复时延的量级；调小提速、增开销
watchdog_interval_ratio 0.3 续期节奏系数，一般不动
任务 ttl 3600s 长任务提交时显式传 ttl，别依赖默认值

多节点生产的典型配置：

TTL 与任务时长的搭配原则：大部分任务小于 30s，保持默认，看门狗兜住突发长任务；存在分钟级长任务，把 TTL 调到 60~120s 给续期留更宽窗口；负载不确定，保持默认 + 幂等处理器即可。另外 Redis Cluster 下注意：NeoTask 的锁脚本与出队脚本都只操作单键，天然兼容集群；如果你自行写跨键 Lua 脚本，需要用 hash tag 把相关键钉在同一 slot。

两个高频误用顺手澄清。其一，锁 TTL（lock_timeout，默认 30s）不是任务超时——任务执行时长的回收口径是任务自身的 ttl（默认 3600s），锁 TTL 只约束"执行互斥窗口"，两者是独立的旋钮：把 lock_timeout 调大到 3600 并不会让卡死任务更快被回收，只会让节点崩溃后的锁多占一小时才自愈。其二，不要在业务代码里手动 SET/DEL 锁键——绕过 owner 校验的裸操作等于亲手把"误删他人锁"的竞态请回来，运维清锁一律走按空闲阈值自动判断的 cleanup_stale_locks，或三重确认死节点后的 cleanup_by_owner。

最后给单机形态一个速查结论，避免"拿着分布式的药方治单机的病"：lock_type=memory 时锁是进程内的 asyncio 实现，互斥只在本进程内成立，看门狗同样工作但防的只是"同进程内两个协程重复处理"；内存/SQLite 存储形态没有 NodeManager，孤儿回收整轮跳过，只剩 ttl 超时回收兜底。换句话说，单机形态下本文讨论的"节点崩溃双执行"问题根本不存在——崩溃的是整个进程，任务状态随进程消亡，重启后一切重来。分布式锁的全部复杂性只在多节点部署那天才需要支付，这也是嵌入式任务池"先单机、后分布式"渐进路线的价值所在。

九、工程结论

  1. 分布式锁的价值不在互斥，在自愈。SET NX EX 一条命令同时拿到互斥与崩溃自愈，owner 随机化 + Lua 原子释放堵住"误删他人锁"，看门狗把"短 TTL 快速自愈"与"长任务不断锁"这对矛盾解耦——每一层都在为异常路径设计，而不是只为正常路径；

  2. 分层防御，各司其职，不信任任何单一机制。队列防"任务不重"、锁防"执行不重"、状态机防"结果不乱"、回收器兜节点故障、看门狗保长任务、死信队列接住彻底失败。任何一层失效，其余层把事故收敛到"业务幂等"这最后一道防线上；

  3. 锁丢了不可怕，可怕的是不知道丢了之后系统的行为。续期失败停手而不是疯狂重试（别给别人的锁续命）、任务跑完而不是强制中断（半截状态更危险）、回收器无权删活锁（接管前先证明原执行者已放弃）、超时口径以任务声明的 ttl 为准——这些边界行为才是选型时真正该考察的东西，比 benchmark 数字重要得多。我们建议把"续期失败后任务去向、回收器能否删除活锁、崩溃到接管的时延"列成一张行为清单，逐项向任何候选框架求证——这三问的答案质量，基本决定了它进生产后的表现。
