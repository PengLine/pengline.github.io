剧本分镜智能体（PenShot）性能评测

相关链接：GitHub | 官网 | 文档 （架构设计 · 召回策略 · MCP Server · 一致性策略 · RAG 增强）

评测基线：PenShot v0.3.x（当前发布线）。本文引用的所有数字均来自项目真实运行产物与系列文章中已披露的实测记录，未做估算、模拟压测或人为美化。

一、评测概述与数据来源

1.1 为什么要单独做一次性能评测

PenShot 的主链路是一条“六段式”流水线：

剧本解析 → 镜头拆分 → 视频分段 → 指令转换 → 质量审查 → 连续性守护

它与普通后端服务最大的不同在于：链路中规则处理与 LLM 调用混合。视频分段是确定性规则算法，耗时稳定且极短；而解析、拆分、指令转换都依赖 LLM 调用，耗时具有明显的弹性——同一个剧本运行两次，耗时也可能因模型响应速度、重试与修复回环而产生差异。

因此，性能评测要回答的核心问题不是“PenShot 快不快”，而是：时间都花在了哪里，哪些环节可以通过工程手段优化。

1.2 数据来源

数据组 来源 内容
A 组 项目本地运行产物（数据目录 data/output/{script_id}/{task_id}/） 同一剧本的两次真实任务记录：TSK17807426061109503223（2026-06-11）与 TSK17807426072316085190（2026-07-23）
B 组 系列文章《实战案例》 一次完整运行的阶段级耗时披露（7 片段剧本）
C 组 仓库 docs/README.md 与系列文章（总览 / 集成使用）的输出示例 两个 13 片段、总时长 48 秒示例的端到端耗时记录（≈89s 与 ≈519s）
D 组 系列文章《召回评测》 向量检索与重排序的测试环境与效果数据

说明：A 组运行产物位于本地数据目录（该目录不随源码发布），其中包含执行摘要、质量报告、记忆报告与阶段统计等完整快照；B、C、D 三组数据可在对应文章与仓库文档中直接查证。

二、关键要点拆解

2.1 端到端耗时画像：瓶颈集中在 LLM 阶段

先看一次典型运行的阶段耗时结构。下表是 B 组披露的一次完整运行（7 个片段）的实测数据：

阶段 处理方式 耗时 占比
剧本解析（script_parser） LLM 调用 ≈21s 21.9%
镜头拆分（shot_segmenter） LLM 调用 ≈8s 8.3%
视频分段（video_splitter） 规则算法 ≈1s 1.0%
指令转换（prompt_converter） LLM 调用 ≈66s 68.8%
端到端合计 — ≈96s 100% 
pie title 7 片段剧本的阶段耗时占比（合计 ≈ 96s）
    "指令转换（LLM）" : 66
    "剧本解析（LLM）" : 21
    "镜头拆分（LLM）" : 8
    "视频分段（规则）" : 1

整个链路的耗时结构可以用一个简单的分解式表达：

$$T_{total} \approx T_{parse} + T_{segment} + T_{split} + \sum_{i=1}^{n} T_{convert}^{(i)} + T_{audit}$$

其中 $n$ 为片段数，$T_{convert}^{(i)}$ 为第 $i$ 个片段的指令转换耗时，$T_{audit}$ 为质量审查环节引入的耗时。

核心解读：

  1. 规则与 LLM 的耗时差了两个数量级。视频分段仅需约 1 秒；而三个 LLM 阶段合计约 95 秒，占端到端耗时的 99% 左右。

  2. 指令转换独占约 69%，因为它是按片段逐一调用 LLM 的：每个片段都要生成“视觉提示词 + 音频提示词”，7 个片段意味着至少 7 轮生成。B 组数据显示，该次运行的提示词平均长度约 407 字符、最长约 600 字符。

  3. 平均到每个片段，转换耗时约 $66 / 7 \approx 9.4$ 秒——这个数量级基本就是单次 LLM 调用的往返时延。

需要特别指出的是：端到端耗时不可按片段数线性推算。系列文章与仓库文档中记录的两个 13 片段示例（总时长均为 48 秒），端到端耗时分别约为 519 秒（8.7 分钟）与 89 秒，相差近 6 倍。耗时波动主要来自 LLM 调用的响应差异与修复回环次数——这也是后文“超时余量”排坑提示的直接依据。

适用场景与优化方向：如果要在生产环境压缩耗时，优先级非常明确——指令转换 > 剧本解析 > 镜头拆分。可行手段包括：为转换阶段选择响应更快的模型、控制提示词上下文的长度，以及依托任务级并发配置（max_concurrent）提升多任务场景下的整体吞吐。需要注意，PenShot 支持 ollama 本地推理与 OpenAI/通义千问等云 API 两类 LLM 接入，本地推理的延迟特性与云 API 差异明显，选型时应以实测为准。

2.2 解析质量与置信度画像

性能之外，解析阶段的“质量”同样需要量化。A 组两次运行对同一剧本的解析结果高度一致：

  • 解析出 7 个元素（3 段对话、3 个动作），涉及 1 个场景、2 个角色；

  • 完整度评分 0.87，整体解析置信度 0.76；

  • 解析耗时 19.0 秒，尝试 1 次即成功，存在 1 个问题未触发修复。

把置信度按维度拆开看，信息量更大：

维度 置信度
动作 1.0
角色 0.75
对话 0.67
场景 0.6

核心解读：动作、角色这类“显式、结构化”的信息最容易提取，置信度最高；而场景置信度仅 0.6——场景往往包含隐式信息（时间、光线、氛围、空间关系），需要模型推断，天然更容易出现偏差。这意味着对场景要求高的剧本（如多场景切换的群像剧），应把人工复核的重点放在场景标注上。

另外，《实战案例》中披露了一个值得注意的机制：当系统检测到“历史解析质量评分为 0”时，会自动启用增强验证模式，对解析输出执行更严格的校验。这说明解析质量并非一次性输出，而是可以在后续运行中被反馈修正的。

2.3 质量得分：从 major_issues 到 minor_issues

A 组两次运行的终审结果对比：

指标 2026-06-11 运行 2026-07-23 运行
片段数 7 7
总时长 21.89s 23.91s
镜头数 / 场景数 / 角色数 7 / 1 / 2 7 / 1 / 2
审查状态 major_issues minor_issues
质量得分 5.0 90.0
违规项数量 8 4

核心解读：两次运行的生成规模几乎一致（同为 7 片段、1 场景、2 角色，解析完整度同为 0.87），但终审状态与得分差异显著。这说明质量得分更多取决于审查与修复链路对具体违规项的处理过程，而不是生成规模的差异。

同时这也提示了一个使用要点：质量得分是一个“终审快照”。当得分偏低时，应当结合运行产物中的审查明细（逐项违规记录与修复历史）定位问题，而不是只看总分。PenShot 的质量审查采用“规则 + LLM 双重审查”并支持自动修复——理解这条链路的存在，才能正确解读分数。

2.4 资源与存储开销

除了计算耗时，部署 PenShot 还需要关注存储与依赖组件。A 组运行记录（7 月运行）中的记忆报告如实反映了各层级的资源参数：

记忆层级 存储介质 关键参数 本次运行状态
短期记忆 Redis（localhost:6379/1） max_size=20 条、TTL=3600s 已启用
中期记忆 本地摘要持久化 max_tokens=500 已持久化至 data/memory/{script_id}
长期记忆 Chroma 向量库 检索 k=3 未启用

其它可量化的开销：

  • 端到端时间成本：同为 13 片段、总时长 48 秒的示例，仓库文档记录的耗时为 88,988ms（约 89 秒），而系列文章中另一次记录的耗时为 519,072ms（约 8.7 分钟）。中等规模剧本的端到端耗时落在“1 分钟到 10 分钟”量级，且波动较大（详见 2.1 节）。

  • 向量检索成本：根据 D 组《召回评测》的披露，检索链路采用 BGE-small-en 嵌入模型（768 维），测试环境为 16GB 内存；引入重排序后，top-1 命中率从 68% 提升至 86%。检索质量提升的同时，会额外引入一次重排序模型推理的开销。

  • 工作流持久化：检查点采用 SqliteSaver，按 script_id / task_id 隔离存储，用于中断恢复。

核心解读：PenShot 的依赖组件是“可裁剪”的——长期记忆与 Redis 都不是必需项；但一旦启用记忆系统（enable_memory=True），Redis 就变成强制依赖。资源规划时应当按“LLM 调用（主要成本）+ Redis / 向量库（可选）+ 本地数据目录（必需）”三块分别评估。

三、注意事项与排坑提示

结合上述真实数据，整理三条最容易踩坑的实践提示：

1. 耗时是分钟级，别让同步调用撞上超时墙

单次中等规模剧本的处理耗时实测在 90 秒到 8.7 分钟之间波动（B 组 ≈96s；13 片段示例为 ≈89s 与 ≈519s），长剧本还会进一步放大。如果用同步 HTTP 客户端（常见默认超时 30 秒）直接等待结果，极易误判为失败。实践建议：生产环境使用异步任务接口提交，通过任务轮询或回调获取结果；同时把超时阈值设置在实测耗时的 2~3 倍以上。

2. 记忆系统可选，但开启后 Redis 是硬依赖

记忆系统整体是可选的，但需要注意其边界：仅当 enable_memory=True 时才要求 Redis；短期记忆会写入 Redis（本次实测连接 redis://localhost:6379/1，max_size=20、TTL=3600s）。如果只配置了 Redis 但未启动服务，记忆读写会直接失败。没有 Redis 的环境应保持记忆功能关闭，不要“半启用”。

3. 数据目录不随源码发布，迁移前记得单独备份

运行产物（任务输出、记忆文件、检查点）统一落在数据目录下，该目录不进入版本库。这意味着：更换机器或用容器重新部署时，历史任务、记忆与检查点都需要单独备份与迁移，否则中断恢复能力会静默丢失。同时，产物按 script_id / task_id 分层存储，长期运行后应关注磁盘占用的持续增长。

四、总结与建议

耗时结构一句话：约 99% 的时间花在 LLM 调用上（解析 22% + 拆分 8% + 转换 69%），规则阶段（视频分段）几乎不占时间；中等规模剧本端到端耗时 1~10 分钟且波动明显——优化性能，本质上就是优化 LLM 调用。

质量画像一句话：解析完整度 0.87、置信度 0.76，其中场景维度（0.6）是最薄弱的环节；终审质量得分存在波动，需要结合审查明细解读。

给生产实践的三条建议：

  1. 异步优先：以异步任务模式接入，为 LLM 长耗时链路预留足够的超时余量；

  2. 按需启用记忆：评估 Redis 与向量库的部署收益，无记忆需求时明确关闭，减少依赖面；

  3. 备份数据目录：把数据目录纳入备份策略，避免任务历史与检查点丢失。

版本基线说明：本文实测数据覆盖 2026-06 至 2026-07 的运行记录与当前发布的 v0.3.x 版本线。后续版本（v0.4 及以上的规划项）可能改变耗时结构与资源参数，升级后建议重新实测。
