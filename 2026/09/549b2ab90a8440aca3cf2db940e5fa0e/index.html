PenShot 性能评测：两次真实运行的阶段耗时画像与 LLM 瓶颈拆解

PenShot 性能评测：两次真实运行的阶段耗时画像与 LLM 瓶颈拆解

相关链接：GitHub | 官网 | 文档 （架构设计 · 召回策略 · MCP Server · 一致性策略 · RAG 增强）

评测基线：PenShot v0.3.x（当前发布线）。本文引用的所有数字均来自项目真实运行产物与系列文章中已披露的实测记录，未做估算、模拟压测或人为美化。

一、评测概述与数据来源

1.1 为什么要单独做一次性能评测

PenShot 的主链路是一条六段式流水线：

剧本解析 → 镜头拆分 → 视频分段 → 指令转换 → 质量审查 → 连续性守护

它与普通后端服务最大的不同在于：链路中规则处理与 LLM 调用混合。视频分段是确定性规则算法，耗时稳定且极短；而解析、拆分、指令转换都依赖 LLM 调用，耗时具有明显的弹性——同一个剧本运行两次，耗时也可能因模型响应速度、重试与修复回环而产生差异。

因此，性能评测要回答的核心问题不是快与不快，而是：时间都花在了哪里，哪些环节可以通过工程手段优化。

1.2 数据来源

数据组 来源 内容
A 组 项目本地运行产物（数据目录 data/output/{script_id}/{task_id}/） 同一剧本的两次真实任务记录：TSK17807426061109503223（2026-06-11）与 TSK17807426072316085190（2026-07-23），含各阶段产物的落盘时间戳与阶段级时间戳链
C 组 仓库 docs/README.md 与系列文章（总览 / 集成使用）的输出示例 两个 13 片段、总时长 48 秒示例的端到端耗时记录（≈89s 与 ≈519s）
D 组 系列文章《召回评测》 向量检索与重排序的测试环境与效果数据

说明：A 组运行产物位于本地数据目录（该目录不随源码发布），其中包含执行摘要、质量报告、记忆报告与阶段统计等完整快照，各文件 metadata 中的 saved_at / audited_at 等时间戳字段构成本文的阶段耗时明细，与《实战案例》共用同一数据源；C、D 两组可在对应文章与仓库文档中直接查证。

二、关键要点拆解

2.1 端到端耗时画像：瓶颈集中在 LLM 阶段

先看两次真实运行的阶段耗时结构。A 组的每个阶段产物都会记录落盘时间戳（metadata.saved_at 等字段），相邻两次落盘的时刻差，就是该阶段处理与保存所占用的区间：

区间（相邻产物的落盘时刻差） 运行 1 运行 2 处理内容
解析产物 → 镜头产物 13.3s 11.0s 镜头拆分（LLM）
镜头产物 → 分段产物 5.5s 4.8s 视频分段（规则直通，无 LLM 调用）
分段产物 → 转换产物 39.0s 36.4s 指令转换（逐片段 LLM 调用）
转换产物 → 审计产物 41.3s 37.8s 质量审查（规则 + LLM 合并审查）
审计产物 → 连续性产物 6.5s 11.6s 连续性守护
端到端（解析落盘 → 连续性落盘） ≈106s ≈102s —

口径说明：解析阶段自身的耗时无法从产物时间戳中直接得出（它之前没有可参照的落盘记录），上表覆盖的是解析之后的五个阶段；区间耗时包含阶段处理与产物序列化保存的开销，不进一步拆分。

pie title 运行 1 相邻产物的区间耗时占比（合计 ≈ 105.6s）
    "质量审查（规则+LLM）" : 41.3
    "指令转换（LLM）" : 39.0
    "镜头拆分（LLM）" : 13.3
    "连续性守护" : 6.5
    "视频分段（规则）" : 5.5

整个链路的耗时结构可以用一个简单的分解式表达：

$$T_{total} \approx T_{parse} + T_{shots} + T_{split} + \sum_{i=1}^{n} T_{convert}^{(i)} + T_{audit} + T_{continuity}$$

其中 $n$ 为片段数（本剧本 $n=7$），$T_{convert}^{(i)}$ 为第 $i$ 个片段的指令转换耗时，$T_{audit}$ 为质量审查环节的耗时，$T_{continuity}$ 为连续性守护的耗时。

核心解读：

  1. LLM 密集区段吃掉八成以上的时间。运行 1 中镜头拆分、指令转换、质量审查三段合计 93.6s，占端到端 105.6s 的 88.7%；运行 2 为 85.3s / 101.7s ≈ 83.9%。唯一不含 LLM 调用的视频分段，两次运行都是最轻的一环。

  2. 质量审查与指令转换是并列大头，审查甚至略高：41.3s 对 39.0s（运行 2 为 37.8s 对 36.4s）。审查阶段同样包含逐片段的内容复核与 LLM 检查，这段开销在只盯着生成阶段时最容易被忽略。

  3. 指令转换按片段线性扩展：39.0s / 7 片段 ≈ 5.6s 每片段（运行 2 为 36.4 / 7 ≈ 5.2s）。每个片段要生成视觉与音频两组提示词内容，这个单片段耗时基本就是一次 LLM 往返的实测量级。

需要特别指出的是：端到端耗时不可按片段数线性推算。仓库文档记录的一个 13 片段示例耗时约 89 秒，而系列文章中另一个同为 13 片段、总时长 48 秒的记录耗时约 519 秒（8.7 分钟），相差近 6 倍。耗时波动主要来自 LLM 调用的响应差异与修复回环次数——这也是后文超时余量排坑提示的直接依据。

适用场景与优化方向：如果要在生产环境压缩耗时，优先级是——质量审查与指令转换 > 镜头拆分。可行手段包括：为这两个 LLM 密集阶段选择响应更快的模型、控制参与转换的上下文长度、减少修复回环（审查问题越少，重试轮次越少），以及依托任务级并发配置（max_concurrent）提升多任务场景下的整体吞吐。需要注意，PenShot 支持 ollama 本地推理与 OpenAI/通义千问等云 API 两类 LLM 接入，本地推理的延迟特性与云 API 差异明显，选型时应以实测为准。

2.2 解析质量与置信度画像

性能之外，解析输出的质量同样需要量化。A 组两次运行对同一剧本的解析结果高度一致：

  • 解析出 7 个元素（3 段对话、3 个动作），剧本总时长 19.0 秒，涉及 1 个场景、2 个角色；

  • 完整度评分 0.87，整体解析置信度 0.76；

  • 解析一次成功（parse_attempts = 1），两次运行的 stats 字段逐项一致。

把置信度按维度拆开看，信息量更大：

维度 置信度
动作 1.0
角色 0.75
对话 0.67
场景 0.6

核心解读：动作、角色这类显式且结构化的信息最容易提取，置信度最高；而场景置信度仅 0.6——场景往往包含隐式信息（时间、光线、氛围、空间关系），需要模型推断，天然更容易出现偏差。这意味着对场景要求高的剧本（如多场景切换的群像剧），应把人工复核的重点放在场景标注上。

另外还有一个值得注意的反馈机制：base_repairable_agent.py 会把历史解析质量分级——平均完整度低于 0.6 标记为 poor，低于 0.8 标记为 medium；等级为 poor 时，镜头拆分与视频分段环节会启用增强验证模式，执行更严格的额外校验。这说明解析质量不是一次性输出，而是可以在后续运行中被反馈修正的。本次剧本完整度 0.87，未触发该模式。

2.3 质量得分：从 major_issues 到 minor_issues

A 组两次运行的终审结果对比：

指标 2026-06-11 运行 2026-07-23 运行
片段数 7 7
总时长 21.89s 23.91s
镜头数 / 场景数 / 角色数 7 / 1 / 2 7 / 1 / 2
审查状态 major_issues minor_issues
质量得分 5.0 90.0
违规项数量 8 4

核心解读：两次运行的生成规模几乎一致（同为 7 片段、1 场景、2 角色，解析完整度同为 0.87），但终审状态与得分差异显著。这说明质量得分更多取决于审查与修复链路对具体违规项的处理过程，而不是生成规模的差异。

再看分数是怎么算出来的——源码 quality_auditor_agent.py 中的 _calculate_weighted_score() 从 100 分起扣，各严重级别的扣分权重为 info 0 / warning 5 / moderate 10 / major 25 / critical 40（另有 error 60），下限截断在 0 分。用这套权重反向核算两次运行：

  • 运行 1：2 条 major + 3 条 moderate + 3 条 warning → 100 − (2×25 + 3×10 + 3×5) = 5.0，与产物 score 完全吻合；

  • 运行 2：2 条 warning + 2 条 info → 100 − (2×5 + 2×0) = 90.0，同样吻合。

同时这也提示了一个使用要点：质量得分是一个终审快照。当得分偏低时，应当结合运行产物中的审查明细（逐项违规记录与修复历史）定位问题，而不是只看总分。PenShot 的质量审查采用规则 + LLM 双重审查并支持自动修复——理解这条链路的存在，才能正确解读分数。

2.4 资源与存储开销

除了计算耗时，部署 PenShot 还需要关注存储与依赖组件。A 组运行记录（7 月运行）中的记忆报告如实反映了各层级的资源参数：

记忆层级 存储介质 关键参数 本次运行状态
短期记忆 Redis（localhost:6379/1） max_size=20 条、TTL=3600s 已启用
中期记忆 本地摘要持久化 max_tokens=500 已持久化至 data/memory/{script_id}
长期记忆 Chroma 向量库 检索 k=3 未启用

其它可量化的开销：

  • 端到端时间成本：同为 13 片段、总时长 48 秒的示例，仓库文档记录的耗时为 88,988ms（约 89 秒），而系列文章中另一次记录的耗时为 519,072ms（约 8.7 分钟）；A 组 7 片段小剧本两次运行约 102~106 秒。中等规模剧本的端到端耗时落在 1 分钟到 10 分钟量级，且波动较大（详见 2.1 节）。

  • 向量检索成本：根据 D 组《召回评测》的披露，检索链路采用 BGE-small-en 嵌入模型（768 维），测试环境为 16GB 内存；引入重排序后，top-1 命中率从 68% 提升至 86%。检索质量提升的同时，会额外引入一次重排序模型推理的开销。

  • 工作流持久化：检查点采用 SqliteSaver，按 script_id / task_id 隔离存储，用于中断恢复。

核心解读：PenShot 的依赖组件是可裁剪的——长期记忆、Redis 与记忆整体都是可选项，不会成为启动或运行的硬门槛。需要修正一个常见误读：启用记忆功能（enable_memory=True）并不等于 Redis 变成强制依赖——源码 short_term_memory.py 的 _check_redis_availability() 在未配置 Redis URL 或连接失败时都会降级为内存存储加文件持久化，不阻断任务（详见排坑第 2 条）。资源规划时应当按 LLM 调用（主要成本）+ Redis / 向量库（可选）+ 本地数据目录（必需）三块分别评估。

三、注意事项与排坑提示

结合上述真实数据，整理三条最容易踩坑的实践提示：

1. 耗时是分钟级，别让同步调用撞上超时墙

单次中等规模剧本的处理耗时实测在 89 秒到 8.7 分钟之间波动（A 组 7 片段小剧本两次运行约 106s 与 102s；13 片段示例为 ≈89s 与 ≈519s），长剧本还会进一步放大。如果用同步 HTTP 客户端（常见默认超时 30 秒）直接等待结果，极易误判为失败。实践建议：生产环境使用异步任务接口提交，通过任务轮询或回调获取结果；同时把超时阈值设置在实测耗时的 2~3 倍以上。

2. Redis 是可选依赖，连接失败会静默降级

短期记忆在有 Redis 时写入 Redis（本次实测连接 redis://localhost:6379/1，max_size=20、TTL=3600s），但源码中的可用性探测决定了它并非硬依赖：未配置 URL 时直接使用内存存储，连接失败时打印告警并降级为内存存储，同时把短期记忆落盘到 data/memory/{script_id}/short_term.json 以便重启恢复，任务不会因此失败。坑点在于：运行看似一切正常，实际已经退化为单进程内存态——多实例部署时各实例的记忆互不可见。排查时不要只看 enable_memory=True，而要核对记忆报告中的 redis_enabled 字段与实际连接地址是否与预期一致。

3. 数据目录不随源码发布，迁移前记得单独备份

运行产物（任务输出、记忆文件、检查点）统一落在数据目录下，该目录不进入版本库。这意味着：更换机器或用容器重新部署时，历史任务、记忆与检查点都需要单独备份与迁移，否则中断恢复能力会静默丢失。同时，产物按 script_id / task_id 分层存储，长期运行后应关注磁盘占用的持续增长。

四、总结与建议

耗时结构一句话：LLM 密集区段（镜头拆分、指令转换、质量审查）合计占端到端耗时的 84%~89%，其中质量审查与指令转换贡献最大；中等规模剧本端到端耗时 1~10 分钟且波动明显——优化性能，本质上就是优化这几段 LLM 调用。

质量画像一句话：解析完整度 0.87、置信度 0.76，其中场景维度（0.6）是最薄弱的环节；终审质量得分按违规权重从 100 分起扣，同一剧本两次运行可以拉开 18 倍，解读时必须结合审查明细。

给生产实践的三条建议：

  1. 异步优先：以异步任务模式接入，为 LLM 长耗时链路预留足够的超时余量；

  2. 按需启用记忆：评估 Redis 与向量库的部署收益，无记忆需求时明确关闭，减少依赖面；

  3. 备份数据目录：把数据目录纳入备份策略，避免任务历史与检查点丢失。

版本基线说明：本文实测数据覆盖 2026-06 至 2026-07 的运行记录与当前发布的 v0.3.x 版本线。后续版本（v0.4 及以上的规划项）可能改变耗时结构与资源参数，升级后建议重新实测。
