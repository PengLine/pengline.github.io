AI 网关工具 LiteLLM 的使用指南

发表于2026-08-11|更新于2026-09-08
|ToolsAI
|浏览量:

LiteLLM 是一个开源的 AI 网关（AI Gateway），它通过提供统一的 OpenAI 兼容接口，帮助开发者在不修改业务代码的情况下，同时调用 OpenAI、Azure、Anthropic、Cohere、Ollama、HuggingFace 等数十家大模型供应商的服务。

核心价值：

  • 统一接口：业务侧始终使用 /chat/completions，底层模型可任意切换；
  • 智能路由：根据模型名、价格、延迟、可用性自动选择最优供应商；
  • 高可用：支持 Fallback、重试、熔断、速率限制；
  • 可观测性：内置成本追踪、日志、Guardrails 内容审核。

核心架构

LiteLLM 主要包含两个使用形态：

  1. Python SDK：在代码中直接调用 litellm.completion()，适合脚本或后端服务集成；

  2. LiteLLM Proxy：一个独立的 OpenAI 兼容代理服务，适合多服务共享模型访问、统一鉴权与计费。

  • Router：根据配置策略选择模型，处理 Fallback 与重试；

  • Cache：缓存模型列表、可用性状态与部分响应，降低延迟；

  • Guardrails：在请求/响应阶段进行内容审核、敏感信息过滤；

  • Spend Tracking：按 API Key、用户、模型维度记录调用成本。

LiteLLM Proxy 请求生命周期

下面以一次 /chat/completions 调用为例，说明请求在 LiteLLM Proxy 中的完整流转。

sequenceDiagram
    participant Client as 客户端
    participant Proxy as LiteLLM Proxy
    participant Router as Router
    participant Cache as Cache
    participant Guard as Guardrails
    participant Spend as Spend/Budget
    participant Provider as 上游 LLM

    Client->>Proxy: POST /chat/completions<br/>model=gpt-4o-mini
    Proxy->>Router: 解析 model 与策略
    Router->>Cache: 查询模型可用性/缓存
    Cache-->>Router: 命中/未命中
    Router->>Guard: 前置内容审核
    Guard-->>Router: 通过 / 拦截
    Router->>Spend: 检查预算/额度
    Spend-->>Router: 允许 / 超限
    Router->>Provider: 转发请求
    Provider-->>Router: 返回响应
    Router->>Cache: 更新状态/缓存
    Router->>Spend: 记录成本
    Router->>Guard: 后置内容审核（可选）
    Router-->>Client: 返回 OpenAI 格式响应

注意：所有上游差异（鉴权头、参数格式、流式协议）均由 Proxy 屏蔽，业务侧无需关心具体供应商。

多供应商模型路由决策

LiteLLM 的 Router 支持按 价格、延迟、可用性、RPM/TPS 等多维度进行智能路由。配置 model_list 后，相同 model_name 可映射到多个供应商实例。

    A[收到请求 model=gpt-4o-mini] --> B{存在多个<br/>候选供应商?}
    B -->|否| C[直接转发唯一候选]
    B -->|是| D[检查各候选健康状态]
    D --> E{存在可用候选?}
    E -->|否| F[触发 Fallback 模型]
    E -->|是| G[按策略排序候选]
    G --> H{路由策略?}
    H -->|最低成本| I[选择价格最低]
    H -->|最低延迟| J[选择最近/RTT 最小]
    H -->|负载均衡| K[轮询 / 加权随机]
    H -->|优先级| L[选择权重最高]
    I --> M[转发请求]
    J --> M
    K --> M
    L --> M
    F --> N[返回降级响应或错误]
    M --> O[成功?]
    O -->|是| P[返回响应]

实践中的问题与解决方案

1. 模型调用失败未自动降级

  • 现象：某个上游供应商短暂不可用，请求直接报错，没有切换到备用模型。

  • 根因：router_settings 中未配置 fallbacks，或候选模型 model_name 与主请求不一致。

  • 解决步骤：

    1. 在 config.yaml 中定义 fallbacks：
    2. 确保候选模型在 model_list 中已注册且可用；
    3. 合理设置 allowed_fails 与 cooldown_time，避免误剔除健康节点。

2. 速率限制导致批量任务中断

  • 现象：批量处理任务运行一段时间后，大量请求收到 429 Too Many Requests。

  • 根因：单供应商 RPM/TPM 达到上限，Proxy 未启用限流或路由策略未分散负载。

  • 解决步骤：

    1. 为每个模型配置 rpm_limit 与 tpm_limit；
    2. 使用 routing_strategy: latency-based 或 least-busy 分散流量；
    3. 在客户端侧实现指数退避重试；
    4. 多供应商部署相同模型，利用 Router 自动切换。

3. 密钥管理混乱或泄漏

  • 现象：团队共用同一组 API Key，难以追溯调用来源，一旦发生泄漏只能全部重置。

  • 根因：所有服务直接持有上游供应商 Key，缺少分层授权与审计。

  • 解决步骤：

    1. 使用 LiteLLM 的 master_key 与细粒度 Virtual Key 机制；
    2. 为不同项目/环境分配不同 Virtual Key，并绑定模型白名单与预算；
    3. 定期轮换 Key，并通过 Spend Logs 监控异常调用。

4. 缓存未命中，延迟与成本居高不下

  • 现象：相同或相似的提示词反复调用，响应时间与 Token 消耗没有改善。

  • 根因：未开启响应缓存，或缓存键未包含系统提示与温度等关键参数。

  • 解决步骤：

    1. 在 litellm_settings 中启用 cache: true，并接入 Redis；
    2. 对适合缓存的场景设置 cache_params（如 ttl、相似度阈值）；
    3. 对动态上下文使用 cache_control 跳过缓存。

5. 成本与预算不可控

  • 现象：月底账单远超预期，无法按项目或用户拆分成本。

  • 根因：缺少统一的成本埋点与预算限制。

  • 解决步骤：

    1. 启用 spend_logs 与 budget_alerting；
    2. 为每个 Virtual Key / Team / User 设置 max_budget；
    3. 在 Proxy 层面统一上报到 Prometheus / OpenTelemetry，构建成本看板。

小结

LiteLLM 通过统一的 OpenAI 兼容接口，将多模型调用的复杂度收敛到网关层。生产环境中应重点关注 路由策略、Fallback、速率限制、密钥与成本治理 四个维度，才能在享受多供应商灵活性的同时保证稳定性与可控性。
