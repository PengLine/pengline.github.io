Redis 集群是如何分片的？从哈希槽到扩缩容迁移的完整机制

发表于2026-08-20|更新于2026-09-29
|DBRedis
|浏览量:

本文定位：这不是命令手册，而是围绕一条主线解释集群的分片设计——一个 key 如何被放进某个槽、一个槽如何被搬来搬去、这条链路上每一步的代价与陷阱。内容分三类标注：机制考证（基于官方文档与源码行为）、理论估算（给出推导与前提，未经实测背书）、经验值（业界通行实践，需按业务校准）。

深夜的告警通常是一个固定剧本：先是某个 Redis 实例内存使用率越过 90%，接着主从同步断开重连、RDB 的 fork 耗时飙到几百毫秒，然后接口延迟全面上涨。打开监控，这台实例已经 50 多 GB，写 QPS 稍微冲高，单线程的 CPU 就顶满。加内存只能再撑几个月——内存可以堆，单线程的写能力堆不出来。到这一步，垂直扩展的路就走完了，剩下的选择只有分片：把数据拆到多台机器上。

Redis Cluster 是官方内置的分片方案。它把全部数据映射到 16384 个哈希槽，再把槽分摊给各个主节点，同时内置了路由重定向、在线扩缩容和自动故障转移。本文围绕一个核心问题展开：为什么中间要引入"槽"这一层抽象，以及围绕槽建立的路由、通信、迁移与容错机制各自解决了什么问题、付出了什么代价。

一、概述：分片方案要同时回答三个问题

把单机 Redis 换成分布式，本质上是回答三个问题：数据怎么分、请求发给谁、节点挂了怎么办。三个问题互相咬合，一个方案在任何一个问题上的选择，都会决定另外两个问题的形态。

数据怎么分，决定扩容难度。 最朴素的做法是 hash(key) mod N，N 是节点数。这个方案最大的问题在于 N 是易变的：加一台节点，N 从 3 变 4，几乎所有 key 的映射关系全部失效——要么接受缓存全量失效打穿数据库，要么停机做全量重哈希。扩容从"加一台机器"变成一次全量数据搬家工程。一致性哈希把 N 变化的影响限制在相邻区间，缓解了这个问题，但映射是随机的，你无法精确控制"哪些数据应该在哪台机器上"。

请求发给谁，决定架构形态。 让客户端自己算路由（客户端分片），逻辑分散在每个服务里，规则一改所有使用方都要对齐；加一层代理转发（代理分片），多一跳延迟、多一个要保活的组件；让服务端自己会转发（Redis Cluster 的重定向模式），服务端要维护全局拓扑并把它传播出去。

节点挂了怎么办，决定高可用水位。 客户端分片和代理分片都只管"分数据"，不管高可用，每一台主节点背后还得再挂一套哨兵做主从切换；Redis Cluster 把分片和容错做在同一个体系里，主节点挂了从节点自动顶上，槽的归属跟着主节点走，客户端通过 MOVED 重定向自动收敛到新主。

Redis Cluster 对这三个问题的回答可以浓缩成一句话：在 key 和节点之间加一个固定数量的中间层——16384 个哈希槽。key 到槽的映射永远不变（CRC16 算出来是多少就是多少），槽到节点的映射随时可调。于是：

  • 扩缩容 = 调整一批槽的归属，key 的哈希值永远不用重算；

  • 路由 = 查"槽归哪个节点"这一张表；

  • 故障转移 = 槽跟着主节点整体移交。

后面所有的机制——MOVED/ASK 重定向、gossip 通信、MIGRATING/IMPORTING 状态机、从节点选举——都是围绕这张"槽表"的读、写、传播和一致性展开的。

把三个问题的答案连起来看，会发现集群设计的重心不在"分"，而在"账本的一致性"：分片规则本身极简（一个取模），难的是让所有节点和所有客户端对"账本当前是什么样"达成一致，并且在改写账本（迁移、故障转移）的过程中不丢请求。带着这个视角读后文，每个机制的出现位置都会显得顺理成章。

二、哈希槽：为什么是 16384 个

2.1 槽是怎么算出来的

任何进入集群的 key，按同一个公式定位：

$$\text{slot} = \text{CRC16}(key) \bmod 16384$$

CRC16 产生 16 位校验值，取值空间 $2^{16} = 65536$；对 16384 取模等效于取低 14 位，源码里就是 crc16(key,len) & 0x3FFF。因为 16384 是 2 的幂，取模退化成位运算，没有除法开销；CRC16 在这个模数下的分布均匀性是官方验证过的，不存在明显偏斜。

有一个关键事实必须先立住：槽是逻辑分片，不与节点上的物理数据绑定。节点 A 不是"存了 0~5460 这段数字"，而是"存了所有槽号落在 0~5460 的 key"。槽号只是 key 的分组编号——正因为分组与存储位置解耦，槽的归属才能随时调整，这是第六节在线迁移能成立的前提。

另外注意：向集群 ADD-NODE 一个新节点后，它默认是"空节点"（不负责任何槽），不会自动搬数据。必须显式执行 reshard 或 rebalance，槽才会划过去——这是集群行为与很多"自动负载均衡"存储系统的明确区别，第八节对比时会再提。

还有一层容易被误解的统计口径：槽均分不等于数据均分。--cluster create 把槽按编号轮询分给各节点，槽的数量是绝对均匀的，但每个槽里的 key 数量、value 大小由业务数据决定。CRC16 只保证离散 key 落槽均匀，不保证槽内数据体积均匀——判断是否需要 rebalance 的依据是各节点的 used_memory 与 QPS 分布，而不是槽号表本身。

集群元数据的自身开销也小到可以忽略：每个节点的槽归属表由 16384 个指针（64 位下约 128KB）加 2KB 位图组成，再加上节点列表，百节点规模也就 MB 级内存——这是槽方案除心跳体积之外的另一个存储红利。

2.2 为什么不用一致性哈希

这是高频面试题，但值得从工程角度重新推一遍。一致性哈希把节点散列到环形空间，key 顺时针找最近的节点存储。它和哈希槽解决的是同一个问题——减少扩容时的数据搬移量——但路径完全不同：

  1. 映射的确定性。 一致性哈希里 key 直接映射到节点，节点加入或退出会改变环上相邻节点的负责区间；哈希槽把映射拆成两段：key→槽 永远固定，槽→节点 可变。扩容时搬的是"槽"这个有明确边界的完整单元，而不是按哈希值散落的零散 key。

  2. 迁移的控制粒度。 一致性哈希没有"把某段数据迁走"的操作原语，再平衡是环重算后的被动结果，中途无法暂停、无法只迁一半。哈希槽可以精确指定"把槽 3000 从节点 A 迁到节点 B"，每一步都是显式命令，可以观察、可以暂停、可以修复。

  3. 元数据的紧凑性。 槽有固定编号，"本节点负责哪些槽"可以压成一张 16384 位的位图——这对第五节 gossip 心跳包的体积是决定性的。哈希环没有固定结构，元数据没法这样压缩。

  4. 均衡的确定性。 一致性哈希靠虚拟节点逼近均匀，虚拟节点数、哈希函数质量都会引入倾斜，且倾斜了不容易定向修；哈希槽天然 16384 等分，只要各槽 key 数量接近，分布就均匀，个别槽倾斜也能定向把它挪走。

一句话总结 trade-off：一致性哈希换来的是"无中心、自动再平衡"，代价是失控——数据在哪、迁多少、迁给谁，都不由你决定；哈希槽用一张全局槽表换来完全的可控性，代价是需要一个机制去维护和传播这张表（gossip 协议），客户端也必须感知路由（smart client 或重定向）。

再回答一个衍生问题：槽数为什么固定，而不是随节点数动态伸缩？固定槽数让"槽表"成为一份可以独立传输、校验、修复的数据结构——任何时刻、任何节点对"16384 个槽各归谁"都能给出明确答案，配置传播和一致性判断（比较 epoch）都围绕这份静态结构进行。槽数若随节点数伸缩，每次拓扑变更都要重定义分片边界，等于退回重哈希的老路。固定数目的中间层，是这套设计里最朴素也最关键的决定。

2.3 为什么恰好是 16384

16384 不是拍脑袋定的数字。antirez 在 GitHub issue 里正面回答过这个问题，核心是两个约束的折中。

约束一：心跳包体积。 集群节点定期互发 PING/PONG，消息头里必须携带"本节点负责哪些槽"的完整位图，这是其他节点维护全局槽表的基础。位图大小等于槽数除以 8：

$$16384 \div 8 = 2048 = 2\text{KB}$$

如果把槽数提高到 65536（用满 CRC16 的 16 位输出），位图就是 $65536 \div 8 = 8\text{KB}$。gossip 消息发送频率高、且每个包都要携带，8KB 的心跳在几百上千节点的规模下是实打实的带宽与 CPU 开销。2KB 是"槽表信息完整"与"心跳包体可控"的平衡点。

约束二：集群规模上限。 官方对 Redis Cluster 的定位是支撑约 1000 个主节点。1000 个节点分 16384 个槽，平均每节点 16 个槽，粒度足够细，再做更细的切分（65536 槽）对分配精度没有实质提升，只会白白撑大心跳。反过来，如果集群只有 10 个节点，每节点约 1638 个槽，槽粒度依然够用——槽数往下取（比如 Codis 的 1024）也能工作，但会让大集群下的均衡调整变粗糙：想把 1000 个节点的负载调平，每节点只有十几二十块"可搬动的积木"已经不宽裕，槽数更少时连积木都不够分。

还有两个附带好处：16384 是 $2^{14}$，取模即位运算 & 16383，无除法开销；槽的数量远大于常见集群的节点数，"槽→节点"的分配可以做得均匀，不会出现哈希环上节点稀少时的大段区间倾斜。

适用边界：预估规模在百节点以内，16384 绰绰有余；如果想象中的目标是几千个节点的单一集群，官方会直接告诉你这不是设计目标——正确做法是拆多个集群，而不是嫌槽数太少。

补充一个常见追问：为什么用 CRC16 而不是 CRC32？一是 CRC16 实现极轻、可硬件加速，antirez 明确说过这让集群协议的实现保持简单；二是对 16384 取模后，两者的分布质量差异可以忽略——模数只占 14 位，16 位校验值的信息量已经绰绰有余，换 CRC32 不会更均匀，只会更贵。另外，若目标只是几个节点的迷你集群，更少的槽数（如 256）同样够用且心跳更小；16384 是官方面向"百到千节点"场景的一次性定档，这也是选型要先估规模的原因。

三、hash tag：多 key 操作的逃生门，也是倾斜的源头

集群模式下，涉及多个 key 的命令——MSET、SUNIONSTORE、MULTI/EXEC 事务、Lua 脚本——要求所有 key 落在同一个槽，否则直接报错：

这不是实现偷懒，而是架构必然：不同槽的 key 可能分布在不同节点上，要求跨节点原子执行，等价于要求分布式事务，这与集群"单节点单线程保证原子性"的模型直接冲突。要让多 key 操作可用，只能由业务保证这批 key 同槽——这就是 hash tag 存在的理由。

规则：如果 key 中包含花括号，且第一个 { 与其后第一个 } 之间有非空内容，则 CRC16 只对这段内容计算，key 的其余部分被忽略。

key 参与哈希的部分 结果
{user1000}.following user1000 tag 生效
{user1000}.followers user1000 与上一条同槽，多 key 操作可行
foo{}{bar} 整个 key 花括号内为空，tag 失效
foo{{bar}}zap {bar 只认第一个 { 到其后第一个 }

用法上，hash tag 是把"业务实体"作为原子单元的正规手段：以订单为中心的 key 统一写成 {order:1001}:detail、{order:1001}:items，订单 1001 的所有数据保证同槽，事务和 Lua 脚本就能正常工作。注意 Lua 脚本在集群里同样受同槽约束：脚本入参的所有 key 必须同槽，否则报错。

但代价必须写进团队规范：tag 的粒度直接决定倾斜风险。

  • 粒度太细（每个实体一个 tag）：倾斜风险低，但能同槽一起操作的 key 也少，事务覆盖面小。

  • 粒度太粗（整个模块共用一个 tag）：该模块所有 key 落进同一个槽，而槽只能属于一个节点——等于在模块维度上放弃了分片，热点模块还会把单个节点打满。这是第九节故障场景 2 的直接成因。

正确姿势是按实体 ID 打 tag（订单号、用户 ID），而不是按业务域打 tag。前者天然分散，后者是灾难。

事务与 Lua 在集群下的行为也值得单独强调：Lua 脚本要求所有 key 通过 KEYS 数组传入并落在同一槽，脚本体里直接硬编码 key 名在单机下静默通过，在集群下会报 Lua script attempted to access a non local key——这是单机代码迁往集群时最典型的不兼容点。迁集群之前用真实拓扑回归一遍多 key 链路，比上线后补课便宜得多。

顺带把集群模式的另外两条硬性边界在这里一并交代：只有 db 0（SELECT 不可用，多 DB 隔离方案失效）；SCAN 等遍历命令只作用于当前连接的节点，全量扫描要遍历所有主节点，或用 CLUSTER GETKEYSINSLOT 按槽扫。这两条经常在从单机迁往集群的改造清单里被漏掉。

一个容易争论的边界问题顺带澄清：hot key（单 key 访问过热）能不能靠 hash tag 解决？不能。hash tag 改变的是 key 到槽的映射，单个 key 的所有访问仍指向同一个槽、同一个节点，正解是本地缓存或读写拆分。hash tag 解决的是"多个 key 被迫同槽"的约束问题，不是"单个 key 过热"的容量问题，混为一谈会开出错误的药方。

四、客户端路由：MOVED、ASK 与 smart client

槽表有了，客户端的请求发给谁？集群给了两层答案：不认识拓扑的客户端走重定向（每条请求可能两跳），认识拓扑的客户端走槽表缓存（常态一跳）。

4.1 MOVED：槽的归属已经变了

客户端连上任意节点发命令，节点先算 key 的槽号，再查本地槽表：槽归我，直接执行；不归我，返回重定向：

MOVED 是一个明确信号：槽的归属发生了持久变化（扩缩容、故障转移），客户端应该更新本地槽表，之后同类请求直达新节点，不再绕路。

可以亲手复现：连上集群任意节点，GET 一个不属于它的 key，就能看到 MOVED；改用 redis-cli -c -p 7000 再试一次，redis-cli 会自动跟随重定向并打印转折过程——这是理解集群路由最快的一个小实验。

4.2 ASK：槽正在搬家

麻烦出在迁移过程中。假设槽 3000 正从节点 A 迁往节点 B，此刻一部分 key 在 A、一部分在 B，槽的正式归属尚未切换。客户端拿着"已经迁走的 key"来问 A 时，A 不能回 MOVED——从全局看槽还是 A 的，回 MOVED 会诱导客户端错误地改写槽表，而槽里剩下的 key 仍必须来 A 处理。所以 A 回的是另一种重定向：

ASK 的语义是"这个 key 这次去节点 B 试一下，但槽的归属没变，槽表别动"。客户端收到 ASK 后，向 B 重发命令之前必须先发一条 ASKING 命令。原因：B 此刻对槽 3000 的状态是 IMPORTING（导入中），槽还没正式归它，没有 ASKING 标记的话，B 会按正常规则把请求 MOVED 回 A，形成循环。ASKING 相当于一张一次性通行证：“我知道这个槽还没正式归你，但这条请求是源节点让我来的。”

两种重定向的本质区别：

MOVED ASK
含义 槽归属已永久变化 槽迁移中的临时指引
客户端动作 更新本地槽表，后续直达 先发 ASKING 再重发命令，槽表不动
目标节点校验 正常接收 必须带 ASKING 才接收

迁移期间还有两个补充错误：多 key 命令中所有 key 都不在源节点时回 ASK；部分在、部分已被迁走时回 TRYAGAIN，客户端稍后重试即可。这两个错误的分界在源节点的视角里非常好理解：全不在，说明这批 key 大概率都在目标上，指过去；一部分在，说明槽正在被搬，此刻执行任何多 key 原子操作都不安全，让客户端等一等。

4.3 smart client：把重定向变成例外而非常态

如果每条请求都靠 MOVED 二跳，集群吞吐直接腰斩，没人这么用。主流语言的驱动（Java 的 Jedis/Lettuce、Python 的 redis-py RedisCluster、Go 的 go-redis ClusterClient）都是 smart client，工作方式：

  1. 启动时连任意节点，执行 CLUSTER SLOTS（Redis 7 起推荐 CLUSTER SHARDS）拉全量槽表，建立 slot → node 的本地映射，并为每个主节点维护独立连接池；

  2. 正常请求按槽表直达目标节点，一跳完成；

  3. 收到 MOVED：更新本地槽表；收到 ASK：按规范先发 ASKING 再重定向一次，不更新槽表；

  4. 定期或按需刷新槽表，吸收 gossip 层慢慢传播过来的拓扑变化。

工程上的坑大多在客户端而非服务端：有的封装库把 ASK 当 MOVED 处理、直接改槽表，迁移一开就出现槽表抖动；有的客户端只在连接报错时才刷新槽表，拓扑变了却拿着旧表一跳到底，直到收到 MOVED 才醒。在做任何槽迁移变更前，先确认所依赖客户端版本对 cluster 协议的实现是否规范，这比调服务端参数更有效。

redis-cli -c 是最朴素的"跟随重定向"模式：每条命令都从当前连接发出，收到重定向就换节点重发，不做任何缓存。它适合调试和验证，不适合压测，更不适合业务——用它压出来的吞吐会严重低估真实 smart client 的表现。

槽表的刷新时机各家实现不同：有按固定间隔轮询的，有收到 MOVED 才触发刷新的，也有订阅拓扑事件主动刷新的。判断一个驱动是否成熟，就看它在故障转移场景下的收敛速度——主挂到新主接管之间，客户端能否在重试几次内自动跟上新拓扑，而不是持续报错直到人工介入。

还有两个集群客户端的工程细节常被忽视：其一，seed 节点要配置多个（最好覆盖全部主节点），任意一个能返回 CLUSTER SLOTS 即可完成拓扑发现，只写一个 seed 等于给自己造单点；其二，密码要在所有节点上保持一致，smart client 会按槽表直连每个主节点，部分节点缺 AUTH 会造成零星的 NOAUTH 报错且难以归因。

五、节点间通信：gossip 协议

客户端要维护槽表，服务端节点之间也要维护同一份全局视图：谁负责哪些槽、谁还活着。Redis Cluster 是去中心化架构，没有配置中心，所有节点通过 cluster bus（一个二进制协议通道，端口默认为客户端端口 + 10000）互相 gossip。

四种消息类型：

消息 触发时机 作用
MEET 新节点加入 握手，把新节点纳入集群视图
PING 周期性发送 携带自身槽位图 + 随机节点的状态摘要
PONG 回应 PING 同时用于主动广播自身最新配置
FAIL 判定节点下线 广播"某节点已下线"的最终结论

cluster bus 使用独立端口（客户端端口 + 10000）而不是复用业务端口，既是协议隔离——bus 上跑的是二进制节点间消息，与 RESP 命令协议完全不同——也是安全边界：防火墙只需在节点之间放行 bus 端口，客户端侧完全无需感知它的存在。排障时也别把两类流量混进同一个观测口径。

工作机制拆开看：

  • 覆盖式探活。每个节点的集群定时任务每 100ms 跑一次，挑选"超过半个 cluster-node-timeout 没有收到 PONG"的节点补发 PING，保证任何节点在半个超时窗口内至少被探活一次。

  • 全量槽表 + 增量 gossip。每个 PING/PONG 的消息头带自己完整的槽位图（2KB），消息体带随机抽取的约 1/10 已知节点的状态摘要。于是槽的归属变化靠消息头较快扩散，节点存活状态靠消息体慢速扩散。

  • 两阶段下线判定。节点 A 超过 cluster-node-timeout（默认 15 秒）没收到节点 B 的 PONG，先把 B 标记为 PFAIL（疑似下线）；A 把这个观点随 gossip 扩散，当集群内过半数主节点都报告了同样的 PFAIL，B 被升级为 FAIL，并向全集群广播。用多数派确认而不是单点判定，是防止某台机器自己的网络抖动造成误判。

（故障判定之后的从节点选举时序，见第七节图。）

新节点加入用的是 MEET 而不是 PING：两者消息格式相同，区别在于收到 MEET 的节点会把对方无条件纳入集群视图，并把"集群里有新节点"这件事继续 gossip 出去。redis-cli --cluster add-node 的背后就是这条消息——它只帮你完成 MEET，槽的划走仍要 reshard，两步是解耦的。

给一个理论估算级的数量感（未经实测，仅用于建立直觉）：gossip 的收敛轮次随集群规模是对数级的——一条新配置传遍 N 个节点大致需要 O(log N) 轮，因为每个 PING 都把状态摘要随机带给一批节点；而心跳的带宽开销随节点数线性增长，N 个节点各自周期性发 2KB 量级的小包。这也是 2.3 节"槽数不能无限大"的另一面：槽数决定单包体积，单包体积乘上消息频率和节点数才是真实成本。

为什么用 gossip 而不是中心化的元数据服务（Codis 就把槽表存在 ZooKeeper 里）？trade-off 很清楚：中心化方案元数据一致性强、排障直观，但引入外部依赖和单点风险；gossip 无外部依赖、无单点、随节点数自然扩展，代价是最终一致——拓扑变化需要若干个 gossip 周期才能传遍全集群，期间不同节点看到的槽表可能短暂不一致。重定向机制恰好用来兜住这种不一致：路由错了几跳，MOVED 会把客户端拉回正轨。

cluster-node-timeout 是整个体系里最需要谨慎对待的参数，它同时出现在三个地方：探活节奏（半个超时）、下线判定（一个超时）、failover 触发（依赖下线判定）。调小，故障发现和切换都快，但网络抖动容易被误判成节点下线，触发不必要的主从切换——而异步复制下切换本身可能丢最近几百毫秒的写入；调大，误判少，但真挂了要等更久。生产常见取值 15~30 秒；跨机房部署建议调大，因为抖动概率更高。

六、扩缩容：槽迁移的全流程

集群扩容是三件事：新节点 MEET 进集群、从现有节点划一批槽给它、补从节点。缩容反过来：先把槽迁空，再 DEL-NODE 摘除节点。整个过程的主体是槽迁移——这是集群里最精密、也最容易出事故的流程。

6.2 迁移中的两阶段请求

在第二步与第四步之间，同一个槽的 key 分布在两个节点上，请求路由必须分成两段看。

源节点 A 收到请求时：

  • key 还在本地 → 正常执行；

  • key 不在本地、槽处于 MIGRATING → 回 ASK 指向 B（单 key 场景）；

  • 多 key 命令、部分 key 已迁走 → 回 TRYAGAIN，等迁移窗口过去再重试。

目标节点 B 收到请求时：

  • 请求带 ASKING 标记 → 正常执行；

  • 不带 ASKING → 回 MOVED 指回 A（槽还没正式归它，不能自作主张）。

这套两阶段协议保证迁移过程中不丢请求：无论 key 此刻在源还是目标，客户端总能被正确引导。代价是迁移中的槽的访问会出现一次额外往返（ASK 二跳），并且多 key 操作在迁移期间可能频繁吃 TRYAGAIN——这也是迁移要挑低峰窗口的第二个理由（第一个理由是 MIGRATE 的阻塞，马上讲）。

用一个具体请求序列体会两阶段：客户端 GET order:9001 命中源节点 A，key 还在，正常返回；几秒后同路径的 GET order:9002，key 已被迁走，A 回 ASK 指向 B，客户端带 ASKING 去 B 拿到数据；迁移完成、SETSLOT 广播之后，再来一个 GET order:9004，A 直接回 MOVED，客户端更新槽表，此后该槽请求全部直达 B。三次请求分别对应"执行、临时指引、永久指引"，这就是迁移窗口内线上流量的真实形态。

对业务侧的提示：迁移窗口内，依赖 MULTI 事务和 Lua 的链路要做好 TRYAGAIN 重试（退避后重试，通常一两轮内槽就迁完了）；纯单 key 读写的链路几乎无感，最多多一次 ASK 往返。把"哪些业务用了多 key 原子操作"提前列入迁移评估，是防止线上悄悄报错的最后一道检查。

6.3 大 Key：迁移最大的敌人

MIGRATE 有一个绕不开的特性：它是同步阻塞命令。执行期间源节点与目标节点的主线程都在忙——源要序列化和发送，目标要反序列化和写入——阻塞时长与 key 体积成正比。这不是"可能慢"，而是设计如此：两边都要在主线程上保证这个操作的原子性。

一个几百 MB 的 zset 在迁移时的线上表现：源和目标两个节点同时无响应，以秒甚至十秒计；两个节点上其他槽的请求全部排队，客户端超时、弃用连接、重建连接（又把槽表缓存丢掉），监控上就是一次全集群抖动。redis-cli --cluster reshard 已经做了批量优化（把多个 key 打包进一条 MIGRATE 的 KEYS 参数，减少往返），但这只减少 RTT 次数，单 key 的序列化与传输阻塞无解。

所以迁移前的检查清单里，第一项永远是处理大 Key：

  1. 用 redis-cli --bigkeys 配合 MEMORY USAGE 扫描待迁移槽内的 key，把重点对象列出来；

  2. 单 value 超过 10MB 的字符串、元素数过大的集合，先在业务侧分桶或瘦身（大 Key 治理的具体手段见站内相关文章）；

  3. 迁移一批、观察一批：每迁完一个槽，用 CLUSTER COUNTKEYSINSLOT 确认计数归零、确认延迟无毛刺，再继续下一个；

  4. 绝对不要在业务高峰对含大 key 的槽做迁移。

另一个容易踩的坑是超时的双写状态：MIGRATE 超时返回错误时，目标节点可能已经写入成功，而源节点因为没收到 OK 不删副本——此刻两边各有一份。reshard 工具对此的处理是带 REPLACE 重发迁移，最终以一次成功的迁移为准收敛。但如果自己写迁移脚本，必须显式处理这个中间态，否则会留下两份数据各自演化、最终分叉的事故。

七、主从复制与自动故障转移

分片解决容量与吞吐，高可用靠主从。集群模式下每个主节点应当至少配置一个从节点，从节点异步复制主节点数据。主节点挂掉后的切换流程：

第一步：判定。 故障节点的 PING 超过 cluster-node-timeout 无 PONG，其他主节点标记它为 PFAIL；gossip 把这个观点扩散，过半数主节点确认后升级为 FAIL 并广播全集群。

第二步：选举。 故障主节点的各从节点按复制偏移量排序——数据最新的优先——错开时间发起选举：向所有主节点发送投票请求，携带自己的 epoch；每个主节点在一个 epoch 内只投一票，通常投给数据足够新、最先来拉票的从节点。

第三步：晋升。 拿到过半数主节点选票的从节点晋升为新主，接管原主的全部槽，epoch 加一，通过 PONG 广播自己的新配置。

第四步：收敛。 其他节点收到更高 epoch 的配置后更新槽表；客户端访问旧地址会收到 MOVED，指向新主，槽表刷新后恢复一跳。

    R-->>C: PONG 广播新配置
    Note over B,C: 槽表更新：槽 0~5460 归新主 R

为什么选举要过半数主节点同意，而不是从节点自己切？ 和哨兵同样的理由：防脑裂。旧主可能只是网络分区了并没有死，若没有多数派确认，分区两侧可能各出现一个"新主"，同一个槽就有两个写入点。epoch 单调递增的规则保证了方向唯一：网络恢复后，旧主看到更高 epoch 的配置会自动降级为从节点，配置永远不会回滚到旧的槽表。

几个相关的配置与事实：

  • cluster-require-full-coverage 默认 yes：任何槽失去覆盖（主从全挂且没有备用从节点）时，集群对相关请求返回 CLUSTERDOWN。这是"宁可部分不可用、也不让缺口悄悄吞数据"的取舍；改成 no 可以让剩余槽继续服务，但要清楚这是在放弃一致性兜底。

  • 复制是异步的，failover 瞬间新主可能缺少最后一段写入，这是 CAP 里取 AP 的必然代价。重要链路要在业务层做补偿或降级校验，而不是指望集群替你保证。

  • 滚动升级等场景可以主动执行 CLUSTER FAILOVER 让从节点平滑接管（它会先等主从复制追平再切换），比等超时判定优雅得多，这是日常变更的标准动作。

从节点侧还有两个参数影响选举结果：cluster-replica-validity-factor 控制从节点的数据新鲜度门槛——从节点与主节点断连超过 (node-timeout × validity-factor) + repl-ping-period 仍未恢复，就失去参选资格，防止数据严重落后的从节点当选后造成大面积数据丢失；cluster-migration-barrier 是每个主节点保留的最少从节点数，多余的从节点会被集群自动"迁移"给没有从节点的孤主，避免个别主节点裸奔。

CLUSTER FAILOVER [TAKEOVER] 的两种模式也值得区分：不带 TAKEOVER 是安全切换，从节点先确认复制追平、再走多数派投票；TAKEOVER 跳过多数派直接提升自己，用于大多数主节点都已不可用的极端场景，代价是放弃多数派保证，常规变更不要用它。

八、横向对比：客户端分片、代理分片、一致性哈希

把 Redis Cluster 放回分片方案的全景里，三条路线各有站位：

维度 客户端分片 代理分片（Twemproxy/Codis） Redis Cluster
架构 业务代码内实现路由 独立代理层 + 中心化槽表 去中心化 gossip + smart client
扩容 mod N 几乎全量重哈希 Codis 预分片 1024 槽，支持迁移 槽粒度在线迁移
路由开销 客户端内计算，无额外 RTT 多一跳代理 RTT 常态一跳，重定向才两跳
高可用 不负责，另配哨兵 代理自身要 HA，后端配哨兵 内置故障转移
客户端要求 低 低 必须支持 cluster 协议
多 key/事务 不受限（业务自己兜底） 取决于代理实现 同槽才行，hash tag 解
元数据 无，各端各记 集中存储（如 ZooKeeper） gossip 最终一致

客户端分片的问题不只是扩容痛，而是把路由逻辑复制进了每一个使用方：哈希规则一改（换函数、改节点数），所有服务都要发版对齐，任何一个服务漏改就是路由分裂。代理分片把路由收敛到一个地方，业务零改造，代价是多一跳延迟、一个必须高可用的中间件和一套元数据存储；Codis 的 1024 槽预分片 + 中心槽表 + 后台迁移，本质上就是"带代理和元数据中心的集群方案"，可以对照 Redis Cluster 理解——它缺的是 gossip 去中心化和内置故障转移，多的是运维组件。一致性哈希与哈希槽的对比在 2.2 节已经展开，补一句选型结论：自建系统追求可控、可观察、可修复，预分片（无论 Codis 的 1024 还是 Cluster 的 16384）几乎总是优于纯哈希环；一致性哈希的价值在无中心、难以维护全局槽表的系统里（Dynamo、Cassandra 一类）。顺带补一个量级对照（经验值）：一致性哈希实践里虚拟节点通常要设到每物理节点上百个才能把负载标准差压到可接受范围，这与 16384 槽均分后"每节点千余槽"是同一思路——都用足够多的逻辑分片逼近均匀——区别只在哈希槽的边界静态可枚举、可定向搬运。

反过来，代理分片至今没有消失，因为它在两个场景下仍然占优：一是存量系统里有大量老旧客户端无法统一升级 cluster 支持，代理层一处改动全局生效；二是多云、跨机房拓扑下需要中心化的路由与限流点。选型时先盘点客户端形态，再决定是"改造客户端上集群"还是"引入代理保存量"，顺序反了常常返工。

那什么时候不该用 Redis Cluster？三个场景：

  1. 重度依赖跨 key 事务和 Lua，且 key 无法按实体 ID 归组——hash tag 改造的代价可能超过收益；

  2. 依赖多 DB 隔离——集群只有 db 0；

  3. 数据量和 QPS 用"单主 + 从库读写分离"就能扛住——集群带来的客户端改造、运维心智和翻倍的故障模式，是一笔真实的税。分片方案引入的复杂度是长期税负，不要为想象中的规模提前付费。

九、三个真实故障场景复盘

以下场景取材于社区与生产环境的常见事故模式，按"发生什么 → 为什么 → 如何处理 → 如何恢复"复盘。

9.1 迁移期的重定向风暴

发生什么： 给集群扩容，计划迁移 500 个槽。运维一次性发起大批量 reshard 后十几分钟，业务接口 P99 翻了数倍，客户端错误日志里大量 MOVED 与 TRYAGAIN，连接池频繁重建，部分服务出现超时雪崩苗头。

为什么： 三个因素叠加。其一，部分服务的客户端封装较旧，对 MOVED 只重定向、不更新槽表，每条请求都变成两跳，吞吐腰斩；其二，迁移批次太大，MIGRATE 的同步阻塞让源节点周期性卡顿，堆积请求超时后客户端弃用连接重建——重建又丢掉了槽表缓存，从头再走一轮重定向；其三，迁移中的槽命中 ASK 的请求天然多一次往返，把延迟放大了。

如何处理： 立即把 reshard 批次调小（经验值：每次 10~20 个槽，批次之间留观察间隔）；排查各服务客户端的 ASK/MOVED 处理逻辑——ASK 应先发 ASKING 重定向一次且不更新槽表，MOVED 应更新槽表；把大 key 从迁移批次中剔除，挪到低峰单独处理。

如何恢复： 槽迁移完成、SETSLOT 广播之后，MOVED 会自然归零，客户端槽表在下一次刷新后回到一跳模式。事后用 redis-cli --cluster check 确认所有槽归属一致，并在压测环境验证客户端的重定向处理，再继续剩余迁移量。这个场景的根因多数不在 Redis 而在客户端，把它写进变更前置检查项。监控上的识别特征也值得记下来（经验值）：风暴期 ASK 计数通常显著高于 MOVED——迁移中间态是常态、槽落定是瞬间；如果反过来 MOVED 持续高于 ASK，多半是客户端槽表刷新机制有问题，优先查客户端而不是继续怀疑服务端。

9.2 hash tag 造成的数据倾斜

发生什么： 上线三个月后，集群里一个节点内存 75%，其余节点都在 15% 上下；该节点 CPU 长期是其他节点的数倍，大 key 与慢查询告警频发，而其他节点闲着。

为什么： 某业务模块为图省事，把模块内所有 key 共用了一个 hash tag（形如 {mall_order} 前缀），上千万个 key 全部落进同一个槽，而这个槽恰好分配在某一个节点上。CRC16 没有错，参与哈希的内容从来没有变过——分片在模块的边界被击穿了，这个槽所在的节点实质上退化为单机。

如何处理： 第一步确认倾斜范围：CLUSTER COUNTKEYSINSLOT 找出大槽，CLUSTER GETKEYSINSLOT 抽样观察 key 的命名模式，定位到错误的 tag 用法。第二步改造 key 命名：tag 收紧到实体粒度（如 {order:100861}），新写入自然分散。第三步处理存量：能设 TTL 的等过期；不能过期的写脚本按新命名重写、双跑比对后再切换读取。

如何恢复： 存量重写完成、监控上各节点内存占比回归均衡后，执行一次 redis-cli --cluster rebalance 把槽分布重新摊平。注意一个止血手段的局限：如果业务着急，可以先把热点槽 reshard 到一台高配节点单独扛——但槽内 key 依然挤在一起，CPU 热点依旧，这只是买时间，不是修复。最后把"禁止业务域级 hash tag"写进 code review 清单，这类问题一旦形成惯例，返工成本远高于当初写对。

9.3 迁移中断，槽卡在过渡态

发生什么： reshard 脚本跑到一半网络闪断，进程退出。之后业务开始间歇性报错：有的 key 出现 MOVED 循环（客户端被 A 指到 B、又被 B 指回 A），多 key 命令频繁 TRYAGAIN。CLUSTER NODES 输出里能看到形如 [3000->-] 的迁移标记。

为什么： 迁移只走了一半——MIGRATING/IMPORTING 已设置、部分 key 已搬走，但 SETSLOT NODE 没有执行，两个节点对槽的认知停留在中间态。全局槽表认为槽还是 A 的，A 上的部分 key 却已经在 B 上，"被 ASK 引到 B 的请求"与"仍命中 A 的请求"交替出现，客户端的表现就是路由抖动。

如何处理： 优先用官方修复工具：

fix 会扫描所有槽的迁移状态，把残留的 key 补迁完，再统一执行 SETSLOT 收尾。若只有个别槽想手动处理：先 CLUSTER GETKEYSINSLOT 把源节点残留 key 迁完，然后对源、目标和其余节点补执行 CLUSTER SETSLOT 3000 NODE ；如果确认这个槽本来就不该迁，用 CLUSTER SETSLOT 3000 STABLE 清掉 MIGRATING 状态回到稳态。

如何恢复： 修复后用 redis-cli --cluster check 验证 16384 个槽全部有归属、无过渡态标记，观察 MOVED 错误率归零，再继续后续变更。教训有两条：reshard 工具本身可重复执行，中断后重新跑即可续传，不要在半途用非常规手段"修正"数据；变更平台要把"迁移中断后的检查步骤"固化下来，而不是依赖当事人在深夜凭记忆处理。

十、总结与建议

回到开头的单机瓶颈。Redis Cluster 用"固定槽数 + 可变归属"的两层映射，把扩缩容从全量重哈希变成槽粒度的定向搬迁；用 MOVED/ASK 两级重定向加客户端槽表缓存，把路由成本压到常态一跳；用 gossip 加多数派判定加从节点选举，在不引入外部组件的前提下补齐高可用。理解这套机制的钥匙始终是那个中间层：16384 个槽是数据分布的账本，一切扩容、均衡与故障转移都只是在改写账本。

落地建议按优先级排：

  1. 客户端先行。 选成熟的 smart client 并逐一验证 MOVED/ASK/TRYAGAIN 的处理，这一步做错，后面所有服务端变更都会被放大成线上事故。

  2. 大 key 治理前置。 MIGRATE 同步阻塞源和目标两个主线程，大 key 是迁移流程的单点风险，任何 reshard 计划之前先完成扫描与拆分。

  3. hash tag 立规范。 按实体 ID 打 tag，禁止业务域级 tag；这类问题的返工成本远高于当初写对。

  4. 参数与窗口。 cluster-node-timeout 按网络质量取 15~30 秒，跨机房调大；迁移挑低峰、小批量推进、每批观察。

  5. 接受边界并设计补偿。 单 DB、同槽多 key、异步复制下 failover 可能丢毫秒级写入——这三个边界要在架构评审阶段摊开，业务侧准备好补偿与校验，而不是上线后补救。

工程结论

  • 16384 个槽是心跳位图体积（2KB）与千级节点分配精度的官方折中；key 到槽的映射永远不变，扩缩容只改槽的归属——这是理解集群一切行为的地基。

  • MOVED 是"槽已易主、更新槽表"，ASK 是"搬家途中、ASKING 通行且槽表不动"，多 key 部分缺失回 TRYAGAIN；三者处理混淆是迁移期事故最常见的客户端侧根因。

  • MIGRATE 同步阻塞源与目标两个主线程，大 key 必须迁移前拆解；迁移走低峰、小批量，超时可能留下双写状态，自写脚本要显式处理。

  • gossip 是最终一致的去中心化元数据协议；cluster-node-timeout 同时决定探活节奏、下线判定与 failover 时机，跨机房部署应调大。

  • 集群只有 db 0、多 key 操作依赖 hash tag 同槽、failover 可能丢毫秒级写入，这三条边界要在选型与评审阶段摊开，而非线上补救。
