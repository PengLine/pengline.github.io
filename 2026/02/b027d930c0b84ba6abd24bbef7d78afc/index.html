PenShot MCP 服务源码考证：七工具契约、手写 JSON-RPC 与双传输真相

相关链接：GitHub | 官网 | 文档 （架构设计 · 召回策略 · 一致性策略 · RAG 增强）

一、概述：MCP 核心价值

MCP (Model Context Protocol) 是一个开放协议，用于标准化 LLM 应用与外部数据源、工具的连接方式。可以通俗地理解为 AI 应用的 “USB-C 接口”——让不同模型能统一接入各种工具和数据，避免为每个工具/模型重复编写适配代码。

本文分两部分展开：前三章讲透 MCP 协议本身的架构、通信与选型对比；第四章进入源码层，考证 PenShot MCP Server 的真实实现——环境配置、CLI 启动、七个工具的输入输出契约、stdio 与 HTTP 两条通道的差异，以及接入 Claude Desktop 的完整配置。先给三个源码级结论，后文逐一展开：

  1. mcp_server.py 没有依赖官方 mcp SDK，而是用标准库手写 JSON-RPC over stdio 循环，只实现 initialize / tools/list / tools/call 三个方法；

  2. 同一批工具存在两条通道：stdio 版的工具参数 schema 全部为空对象（{"type": "object", "properties": {}}，客户端看不到参数名），HTTP 联调版的 /tools 则带完整参数描述——接入时要留意这一差异；

  3. 任务成功终态的字面量是 success，不存在 completed：源码里 TaskStatus.SUCCESS 的值为 "success"，不少流传的示例都用错了这个值。

概念延伸：MCP 与 Function Calling、LangChain Tools 最大的区别在于协议中立、生态开放。它定义了 initialize / tools/list / tools/call 等一系列标准 JSON-RPC 方法，让同一个 Server 能被 Claude、Cursor、各类 Agent 框架通用调用。

2.2 核心组件说明

组件 角色 职责
MCP Client LLM应用 (Host) 发起请求、管理会话、处理响应
MCP Server 能力提供方 暴露资源/工具/提示词，处理具体操作
Transport 通信层 Stdio (本地进程) 或 SSE (远程HTTP)
Resources 数据源 文件、数据库记录等只读或订阅型数据
Tools 可执行功能 API调用、计算、数据库写入等操作
Prompts 模板库 预定义的提示词模板，可带参数

Transport 二选一：Stdio 通过子进程标准输入输出通信，适合本地工具（Claude Desktop 常用）；SSE（Server-Sent Events）走 HTTP，适合远程共享部署。PenShot 的 MCP Server 默认走 Stdio 子进程。

四、PenShot MCP Server 源码考证

PenShot MCP Server 支持 Claude Desktop、Cursor 等 MCP 兼容客户端调用，工作方式遵循提交任务 → 轮询状态 → 获取结果三部曲。与泛泛的功能介绍不同，本章以源码为准绳逐节考证真实实现：

  • stdio 版（src/penshot/mcp_server.py）：手写 JSON-RPC 循环，零第三方依赖，是 Claude Desktop 配置的标准入口；

  • HTTP 版（src/penshot/mcp_http_server.py）：基于 FastAPI 的本地联调服务，把同一批工具暴露为 /tools/* 路由，参数 schema 比 stdio 版更完整；

  • 客户端示例（examples/mcp/）：仓库提供 mcp_client.py（stdio）与 mcp_http_client.py（HTTP）两个可运行示例，4.4 / 4.5 节直接引用其真实代码。

4.1 支持的工具

stdio 版与 HTTP 版暴露同一批七个工具，breakdown_script 负责提交剧本（同步 / 异步两种模式），其余六个用于查询与管理：

工具名称 功能描述 必需参数 返回要点
breakdown_script 提交剧本进行分镜拆分 script 异步返回 task_id 与 pending 状态；同步返回完整结果
get_task_status 查询任务状态和进度 task_id 状态 + 当前阶段 + 各阶段进度明细
get_task_result 获取任务结果 task_id success / status / data / error / 耗时
cancel_task 取消正在执行的任务 task_id {task_id, cancelled}
list_tasks 列出所有任务 可选 任务摘要列表（limit 默认 20）
get_queue_status 获取队列状态 无 队列长度、活跃任务数、并发上限等
get_stats 获取服务器统计信息 无 提交 / 完成 / 失败累计计数与队列快照

典型编排：breakdown_script 提交后返回 task_id，随后循环 get_task_status 观察进度，终态为 success 时用 get_task_result 取结果（注意不是 completed，源码枚举里没有这个值）；cancel_task 用于中止异常任务，get_queue_status / get_stats 用于运维监控。

排坑：stdio 版工具参数 schema 全为空。mcp_server.py 的 get_tools_list() 把七个工具的 parameters 统一返回为空对象 {"type": "object", "properties": {}}——客户端（LLM）看不到 script、language、wait 等参数名，只能凭 description 猜测。若工具调用参数不符合预期，可对照各 _handle_* 方法实际读取的键名（script / language / wait / timeout / task_id / limit）在系统提示词中自行约束。HTTP 联调版的 /tools 没有这个问题（见 4.5 节）。

4.3 启动与服务端实现剖析

参数语义：--max-concurrent 控制同时执行的任务数（默认 10），--queue-size 控制队列入队上限（默认 1000）。队列满时 _enqueue_task 打印 warning 并拒绝入队（返回 False）——提交方不会收到明确拒绝信号，高负载场景建议监控 get_queue_status 的 queue_usage_percent 字段提前扩容。

启动后服务内部做了什么？mcp_server.py 的核心循环只有约 60 行，值得逐点拆解：

① 手写 JSON-RPC 循环（核心事实）。整个模块只 import 标准库 json / logging / sys 与项目内部模块，不依赖任何 mcp 包：run() 是一个 while True 循环——逐行读 stdin → json.loads → 按 method 分发 → 把响应逐行写回 stdout。只实现三个方法：

方法 行为
initialize 返回协议版本 0.1.0、serverInfo（name=penshot-mcp-server，version=1.0.0）与 capabilities: {tools: {}}
tools/list 返回七个工具定义（参数 schema 为空对象）
tools/call 按 name 查找 handler 执行，结果 json.dumps 后包进 content[0].text

② 错误码约定：handler 内部抛异常返回 -32000 + 异常消息；工具名或方法名不存在返回 -32601。这两类错误是客户端调试时的第一线索。

③ 日志与协议分流：模块 docstring 直接标注 MCP Server - 所有日志输出到 stderr，setLog() 把 logging 与 langchain / httpx 等第三方日志统一重定向到 stderr 并压到 WARNING 级别，stdout 只保留逐行 JSON-RPC。这是 stdio 传输的基本纪律——任何混入 stdout 的 print 都会破坏协议流，客户端解析会直接失败。

④ 边界：通知不处理。循环对这三个方法之外的一切输入（包括 MCP 规范中的 notifications/initialized 通知）统一回 -32601。规范上通知不应有响应，因此严格校验响应配对的客户端需实测兼容性——这是手写实现换取轻量的直接代价。

设计取舍：为什么不用官方 SDK？这套手写循环让服务保持零第三方依赖、协议行为完全可控（响应结构、错误码、日志走向都是普通源码）；代价是只覆盖 tools 能力的最小集，resources / prompts / 订阅等高级特性不可用，协议版本也停留在写死的 0.1.0。如果只是把工具挂给主流客户端，这条路线足够轻；若要扩展完整 MCP 能力，官方 SDK 是更稳妥的选择。

4.4 Stdio 客户端：基于真实示例的实现剖析

examples/mcp/mcp_client.py 提供了可直接运行的 stdio 客户端 MCPStdioClient（241 行），并通过 mcp_server_demo.py 做端到端自测。它的设计出发点在文件注释里写得很清楚：后台线程持续读取 stdout 并把 JSON 响应放入队列，请求按自增 id 匹配响应，避免阻塞式 readline 在 Windows 上的兼容问题。下面是核心骨架（节选，省略类型标注）：

七个内置工具在示例里都有语义化封装（breakdown_script / get_task_status / get_task_result / cancel_task / list_tasks / get_queue_status / get_stats），结果摘要统一按 data.instructions 契约打印（与 SDK / REST 结果结构一致）。

三个值得抄走的设计点：

  1. stdout 读取必须独立成线程。主线程只负责发请求、按 id 收结果，避免阻塞式 readline 与超时控制互相干扰（这正是真实示例放弃 readline 轮询方案的原因）；
  2. stderr 必须持续排空。server 侧日志全走 stderr，客户端不读就会在管道缓冲区写满后把 server 阻塞在写日志上（_drain_stderr 同时保留最近 50 行供报错展示）；
  3. 终态集合是 {"success", "failed", "cancelled"}。轮询循环只在命中这三个值（或 not_found）时退出——再次强调，没有 completed。

4.5 HTTP 联调服务与客户端

src/penshot/mcp_http_server.py 是产品内置的 HTTP 版 MCP 服务（模块描述直接标注：用于本地联调），把同一批工具暴露为 /tools/* 路由。需要先澄清一个边界：它不是 MCP 标准的 SSE / Streamable HTTP 传输，而是 FastAPI 风格的 REST 封装——不能用 MCP 协议客户端直连，只能用普通 HTTP 调用。

启动方式：

服务默认监听 127.0.0.1:8000，根路径 GET / 会自描述全部端点：

方法 端点 说明
GET / 服务自描述（名称 / 版本 / 端点清单）
GET /tools 工具列表（带完整参数 schema）
POST /tools/breakdown_script 拆分剧本（body：script / language / wait / timeout）
POST /tools/get_task_status 任务状态（任务不存在返回 404）
POST /tools/get_task_result 任务结果（任务不存在返回 404）
POST /tools/cancel_task 取消任务
POST /tools/list_tasks 任务列表（可带 status_filter / limit）
GET /tools/queue_status 队列状态
GET /tools/stats 统计信息

与 stdio 版最重要的差异在 GET /tools：HTTP 版返回的工具定义带完整 parameters 描述（script / language / wait / timeout 的类型与默认值一目了然），不存在 stdio 版空 schema 的排坑问题。两版共用同一个 create_penshot_agent() 任务池，任务状态与结果完全一致。

源码瑕疵提醒：HTTP 版 list_tasks 的 status_filter 参数枚举里写着 ["pending", "processing", "completed", "failed"]，但真实状态机里并不存在 completed（成功为 success）——传 status_filter=completed 永远筛不出任务。业务里按状态筛选请用 success；这一处参数说明与实际枚举不一致，属于当前实现的小瑕疵。

五、总结与建议

5.1 常见问题排查表

现象 可能原因 处理方式
客户端看不到工具 Server 未启动或 python 无法导入 penshot 用 python -m penshot.mcp_server 手动验证；检查 command 是否指向正确解释器
调用返回 Tool not found 工具名拼写不符或方法不支持 对照 4.1 工具清单；错误码 -32601 即方法 / 工具不存在
调用返回 -32000 handler 内部异常（多为未配置 LLM key） 看 stderr 日志定位；先确认 .env 中的密钥已生效
任务一直停在 pending 队列已满被拒入队 用 get_queue_status 查看 queue_usage_percent；必要时调大 --queue-size 或错峰提交
同步等待超时 长剧本 + 慢模型 改用 wait=False 异步模式 + 轮询
状态判断永远不命中 误把 completed 当任务终态 任务终态只有 success / failed / cancelled；completed 仅属于阶段明细
结果为空 剧本内容问题或任务未成功 先看 get_task_result 的 success / error 字段

5.2 使用建议

MCP 接入 PenShot 的核心收益：不用写业务代码、不用关心 Web 界面与私有协议，用一套标准化的提交 - 轮询 - 取结果工具，就能把分镜能力挂进 Claude、Cursor 等任意 MCP 兼容环境。要点总结如下：

  1. 协议层：PenShot 的 stdio 服务是手写 JSON-RPC 最小集（initialize / tools/list / tools/call），零第三方依赖；换来的边界是不支持 notifications、resources 等高级能力，扩展前需评估；

  2. 任务模型：PenShot 走异步任务池——先提交拿 task_id，再轮询 get_task_status（看 current_stage / stage_name / progress），终态 success 后由 get_task_result 取 data.instructions；

  3. 并发与超时：默认并发 10、队列 1000，队列满直接拒绝入队；长剧本优先 wait: false 异步模式，同步模式务必显式设置 timeout；

  4. 两条通道：stdio 对接桌面客户端（工具 schema 为空，需在系统提示词里约束参数）；HTTP 联调版参数描述完整，适合本机联调与多客户端共享（注意与 REST 服务端口冲突）。

踩坑提醒：两个高频误读都有源码级答案——任务终态是 success 而非 completed（completed 只出现在阶段进度明细的 status 里，两套值域不要混用）；HTTP 版 list_tasks 的 status_filter=completed 永远筛不出任务（源码枚举瑕疵，请用 success）。迁移或复用本文示例时，以仓库 examples 目录的源码为准。
