PenShot 节点详解：六大智能体的源码实现与规则逻辑

PenShot 节点详解：六大智能体的源码实现与规则逻辑

相关链接：GitHub | 官网 | 文档 （MCP Server · 召回策略 · 一致性策略 · RAG 增强）

一、预先准备：节点体系概览

PenShot 将一个完整的分镜任务抽象为六个顺序执行的智能体节点，由 LangGraph 负责端到端的协调与调度。理解这套节点体系，是读懂后续 JSON 数据模型与修复机制的前提。每个节点遵循统一的模式：接收输入 → 调用 LLM 或规则实现 → 结果判定（经决策函数路由）→ 进入下一节点或触发修复。

核对说明：本文的节点输入输出、检查项名称、提示词规则、字段名等均与 story-shot-agent v0.3.x 源码逐一核对（agent/script_parser/、agent/shot_segmenter/、agent/video_splitter/、agent/prompt_converter/、agent/quality_auditor/、agent/continuity_guardian/）。示例 JSON 标注为"示例数据"，字段结构对照真实 Pydantic 模型核校；凡属推测或实现不足，都会明确标注。

二、节点输入输出总表

阶段 输入 输出 关键处理
剧本解析 原始文本 结构化剧本 格式自动识别 + LLM 提取场景/角色/元素 + 五维完整性评分
镜头拆分 结构化剧本 镜头序列 元素分组（对话合并规则）+ 三类时长估算器
视频分段 镜头序列 视频片段 超阈值镜头 LLM 语义切分 / 规则均分，保持连续性
指令转换 视频片段 Prompt指令 LLM 生成双语提示词 + 音频提示词 + 负面词
质量审查 Prompt指令 审查报告 五项硬性检查 + 严重度加权扣分
连续性检查 全阶段输出 问题列表 六维关键词规则检查 + 签名去重

上表为 T 型摘要，每一行的真实实现机制都在第三节展开；各节点的输入输出模型（如 ParsedScript、ShotSequence、FragmentSequence、AIVideoInstructions、QualityAuditReport）均为 Pydantic 模型，字段级核对见后文。

决策分支说明：

检查点 通过 不通过
剧本解析 进入镜头拆分 重试/错误处理
镜头拆分 进入视频分段 重试/修复
视频分段 进入指令转换 修复后重试

质量审查 进入连续性检查 返回指令转换（回炉重生成）

关于"修复目标"的两套设计：质量审查失败后的修复确实收敛到指令转换——decide_after_audit 返回 NEEDS_REPAIR 时，图映射把它指向 CONVERT_PROMPT，从最靠后的"可修复层"重生成提示词，比全链重跑更省 Token 与时间。连续性检查则是另一套：节点内部按问题来源把修复路由到解析/拆分/分段/转换四个阶段中最早的命中者，意图"哪错回哪"。注意两套路由的当前实现状态不同——连续性修复的"重试回流"存在未接通的缺口，详见 3.6。

三、核心节点详解

3.1 剧本解析智能体

核心目标：将任意格式剧本转换为统一的结构化中间表示，执行剧本的格式转换和语义提取。这是"六格式分流"的第一道关口。

flowchart LR
    subgraph Input
        A[原始剧本文本]
    end

    subgraph Process[解析流程]
        B[格式识别<br/>正则规则] --> C[匹配对应系统提示词<br/>六种格式分流]
        C --> D[LLM语义解析]
        D --> E[构建Pydantic模型<br/>ID生成/字段补全]
        E --> F[五维完整性评分]
    end

    subgraph Output
        G[结构化剧本<br/>ParsedScript]
    end

    A --> B --> G

格式识别是真实现的，不是概念。script_parser_agent.py 中的 _detect_script_format 用一组正则规则对原文分类，命中即返回对应的 ScriptType：

优先级 判定规则（正则要点） 结果
1 INT. / EXT. / 内景 / 外景 / 场景N： STANDARD_SCRIPT 标准剧本
2 镜头N / shot N / 分镜N / 画面描述： AI_STORYBOARD AI 分镜脚本
3 场景： / 地点： / 时间： / 角色： STRUCTURED_SCENE 结构化场景
4 角色：台词 行数占比 > 70% DIALOGUE_ONLY 纯对话
5 句号/感叹号/问号数量 > 冒号/引号数量 NATURAL_LANGUAGE 自然语言
6 以上均不命中 MIXED_FORMAT 混合格式

为什么先做"格式识别"：LLMScriptParser 为每种格式准备了独立的系统提示词（ScriptType.NATURAL_LANGUAGE / STANDARD_SCRIPT / AI_STORYBOARD / STRUCTURED_SCENE / DIALOGUE_ONLY 各一份，加一个 default 兜底），识别格式后路由到对应提示词，避免"一套提示词硬吃所有格式"。代价是规则法只能识别典型特征——正则漏判时会退回 MIXED_FORMAT 通用提示词，而非报错。

质量评估维度：五维加权评分

解析完成后，_evaluate_completeness 对结果做五维评分（权重为源码真实值）：

维度 权重 评分逻辑（简）
场景完整性 0.25 场景数量（3 个封顶）+ 描述长度 > 10 字符占比，取均值
角色完整性 0.25 角色数量（2 个封顶）+ 描述长度 > 5 字符占比，取均值
对话提取质量 0.20 原文有对话标记但未提取→ 0.3；否则提取数/预期数
动作提取质量 0.20 提取动作数 / (原文动作动词表命中数 × 0.5)
总体覆盖率 0.10 提取内容字符量 / 原文字符量 × 2（封顶 1.0）

评分还带一道"问题惩罚"：completeness_score -= min(0.2, 问题数 × 0.05)——即发现 4 个及以上问题项时，最多额外扣 0.2 分。此外 _calculate_confidence 会分别计算场景/角色/对话/动作置信度与 overall 均值，供下游节点与决策函数参考。

graph TD
    A[原始剧本文本] --> B(LLM解析)
    B --> C{解析成功?}
    C -->|是| D[结构化JSON]
    C -->|否| E[错误处理]
    D --> F[添加元数据]
    F --> G[输出结构化剧本]
    E --> H[返回错误信息]

  1. 自动识别输入格式，根据不同的剧本做不同处理

  2. 使用LLM解析，通过剧本复杂度、类型、解析置信度

  3. 提取语义元素（角色、动作、对话、场景）

  4. 转换为统一数据结构

  5. 保持原始语义，不添加时间信息

设计要点：本节点刻意不添加时间信息（只输出结构化序列），把"时长"这件事完全交给下游的镜头拆分节点处理——职责单一化让每个节点的输入输出更可预期。

    participant User as 用户
    participant API as 流程编排器
    participant Parser as 剧本解析智能体
    participant LLM as LLM服务
    
    User->>API: POST 接口 {text: "剧本文本"}
    API->>Parser: 调用解析任务

输出示例

以下 JSON 为示例数据（结构对照 ParsedScript 模型核校）：顶层为 metadata / title / characters / scenes / global_metadata / stats。每个场景（scene）内含多个 elements，元素类型包括 ACTION（动作）、DIALOGUE（对话）、SCENE（环境交代），并带有 sequence（顺序）、duration（估时）、confidence（置信度）、intensity（强度）、emotion（情绪）等字段：

被低估的 global_metadata：贯穿全剧的"连续性账本"

顶层模型里最容易被忽略的是 global_metadata——它专门存放跨场景必须保持一致的元素，由解析阶段一次性抽取，供后续所有节点引用：

字段 含义 消费方
key_props 关键道具（名称/颜色/出现场景） 拆分、分段、转换（道具一致性约束）
character_outfits 角色服装（颜色/款式/材质） 转换节点（服装描述逐字复用）
key_locations 关键地点（视觉特征） 拆分、转换（场景视觉锚点）
continuity_notes 需要特别注意的连续性要点 全链路
audio_atmosphere / recurring_sounds 全局音频氛围 / 重复出现的声音 音频提示词生成

这不是装饰性字段：分段提示词的【重要约束】会直接引用它（“角色服装必须严格遵循【全剧上下文】中的描述，不可将某个角色的服装特征错误地分配给其他角色”），把一致性要求从"事后检查"前移到"生成时约束"。

顺序与完整性保障：两级事后校验

decide_after_parsing 的决策依据来自解析结果的结构化校验，而不是"位置回溯"。真实的校验手段有两个：

  1. 顺序连续性校验（validate_parsed_result）：汇总所有场景的元素后，检查 sequence 是否构成 1…N 的连续序列——不连续时记录 warning 日志，不阻断流程。

  2. ID 兜底生成：LLM 返回的 id 优先采用；缺失时由 _generate_element_id 按 elem_{场景序号}_{元素序号} 规则补全（如 elem_001_002），保证下游引用链不断。

实现边界（如实标注）：该校验只能发现"编号不连续"，无法发现"编号连续但内容顺序错误"的情况；同样也没有原文偏移量（offset）回溯机制——sequence 的正确性完全依赖 LLM 输出质量。兜底手段是解析结果为空或完整性评分过低时，由 decide_after_parsing 路由回 PARSE_SCRIPT 重试。

3.2 镜头拆分智能体

核心目标：将结构化剧本拆分为视觉上独立的镜头单元，考虑情感节奏和时长合理性。

flowchart LR
    subgraph Input
        A[结构化剧本]
    end

    subgraph Process[拆分流程]
        B[场景遍历] --> C[元素序列分组]
        C --> D{合并判断}
        D -->|连续对话且同角色| E[合并进当前镜头]
        D -->|连续动作(默认不合并)| F[创建新镜头]
        D -->|对话后短动作<3秒| E
        E --> G[镜头类型判定]
        F --> G
        G --> H[时长估算器覆写]
        H --> I[增强器后处理]
    end

    subgraph Output
        J[镜头序列JSON]
    end

    A --> B --> J

拆分规则：两种实现共享同一套输出模型

镜头拆分有 LLM 与规则两种实现（ShotSegmenterFactory 按 config.enable_llm 选择）。规则模式的合并逻辑（RuleShotSegmenter._should_merge_elements）只有三条：

判断 条件 结果
连续对话 两个 DIALOGUE 且角色相同 合并进同一镜头
连续动作 两个 ACTION 且角色相同 默认不合并（merge_consecutive_actions=False）
对话后短动作 DIALOGUE 后紧跟 ❤️.0 秒的 ACTION 合并（视为对话的延续）

镜头类型判定（规则模式）同样只有三条硬规则：组内含对话 → 特写（close_up）；含场景描述 → 全景（wide_shot）；其余 → 中景（medium_shot）。镜头描述优先取组内首元素内容，对话追加说话者前缀（角色: 台词），并支持 max_description_length 配置截断。LLM 模式的拆分粒度由提示词约束（如"避免过度分割，保持镜头的视觉和叙事连贯性"“对话元素必须在镜头描述中完整逐字呈现”），灵活性高于规则，但每次调用都消耗 Token。

镜头类型选择（提示词【镜头选择规则】的真实对应）：

场景 推荐镜头 提示词中的原始定位
对话+情感高潮 特写（close_up / extreme_close_up） 聚焦面部表情，展现情绪变化
对话+环境交代 中景（medium_shot） 最常用的对话和叙事镜头
动作+多人互动 中景 / 双人（two_shot） 展现人物上半身和动作 / 关系展示
场景建立 全景（wide_shot / long_shot） 展现场景全貌，适合开场

为何按类型选镜头：镜头类型（景别）直接决定观众获得的视觉信息量与情绪浓度——情感高潮用特写放大情绪、场景建立用全景交代空间、互动用中景兼顾人物与环境。ShotType 枚举共 13 种（含过肩、主观视角、跟拍、摇摄等），提示词中明确列出 8 种的使用场景，供 LLM 选择。

时长估算：LLM 建议只是草稿，估算器才是最终裁决

提示词中给出的时长建议表（LLM 模式下作为参考；shot_segmenter_prompt.yaml 原文）：

内容类型 建议时长
快节奏动作/突发事件 1.5-2.5秒
对话/表情反应 2.5-4秒
风景/环境建立 3-5秒
情感高潮/重要台词 4-6秒

但更关键的机制是：无论 LLM 还是规则模式，拆分完成后 estimator_factory.estimate_sequence() 都会重新计算每个镜头的时长并覆写 shot.duration——LLM 给出的时长只是"草稿"。估算器按镜头类型分发到三个实现类（CLOSE_UP → DialogueDurationEstimator、WIDE_SHOT → SceneDurationEstimator、其余 → ActionDurationEstimator），以动作估算器为例，计算链路是：

  1. 按镜头类型取基准时长（中景 base=2.8 秒）；

  2. 叠加复杂度因子（描述 >20 字 ×1.3，≤10 字 ×0.8）；

  3. 速度关键词调整（“猛地”"快速"×0.8，"缓缓"×1.3）；

  4. 场景情绪调整（紧张 ×0.9，悲伤 ×1.2）；

  5. 角色特征调整（老幼角色 ×1.2 / ×0.9）；

  6. 与动作时长工具（ActionDurationEstimatorTool）的结果按 0.4 : 0.6 加权平均；

  7. 最后 clamp 回该镜头类型的 [min, max] 区间。

之后集中到增强器 DurationEnhancer 做整体校准：把超范围时长拉回边界（如中景 2.0~5.0 秒）、情感特写至少 3.0 秒、开场/结尾镜头 ×1.2，并防止连续同型镜头时长雷同（差值 <0.3 秒时改为前者 +0.3 秒错开）。

设计取舍：把时长交给独立估算器而不是信任 LLM 输出，换来的是"时长可控、可测试、可复现"——同一份输入，时长结果不受 LLM 随机性影响；代价是估算器本质上仍是关键词匹配 + 固定系数的规则，对"缓慢而有力量地攥紧拳头"这类语义微妙的描述识别能力有限。另需注意：增强器中为 climax / transition 预留的节奏系数（1.3 / 0.8）在 _enhance_shot 中并未被引用——当前只有 opening / ending 两条生效。

每个镜头记录 scene_id（归属场景）、start_time（起始时间）、duration（时长）、shot_type（景别）、main_character（主角色）、element_ids（来源元素引用），并带格式 id 前缀 shot_：

当前实现的局限与工程提示

  • 时长估算不感知语义内容：复杂度因子基于描述字符数（>20 字 → ×1.3），速度/情绪/角色因子均为关键词命中；没有情感分类模型或机器学习校准。估算器与增强器的所有参数都是固定常量，不会从生成反馈中自适应调整——"30% 误差逐步收窄到 10%"之类的演进路线并不存在于当前代码，属于合理的未来方向而非既成事实。

  • 规则模式的镜头类型判定偏保守：含对话即特写、含场景描述即全景，没有"对话+环境交代 → 中景"这类更细的分支；中间景别的选择基本交给 LLM 模式或人工调整。

  • 合并逻辑的适用边界：merge_consecutive_actions=False 意味着"转身 → 走向窗边"这类连续动作会被拆成两个镜头，再交下游分段阶段处理——拆得碎但保真；若希望动作连贯成镜，需改用 LLM 模式或调整 ShotConfig。

为什么是 5 秒，以及"阈值 ≠ 上限"的区别：主流文生视频模型对单段生成时长有硬性上限，而系统里与 5 秒相关的其实是三个不同的值——duration_split_threshold（默认 5.5 秒，超过才触发切分，留出 0.5 秒容差避免临界镜头被无谓切割）、max_fragment_duration（默认 5.0 秒，单片段的目标上限）、min_fragment_duration（默认 1.0 秒，提示词中进一步要求不低于 1.5 秒保证可读性）。"≤5.5 秒直接成段"这个设计让大部分镜头零开销通过，只有真正超长的镜头才进入智能切分。

连续性挑战

把长镜头切开的最大风险是"切断连续性"，系统从四个维度规避：

挑战 示例说明 解决方案（对齐源码实现）
动作中断 在动作中间切分导致视觉跳跃 提示词要求在动作自然停顿处分割
状态不一致 片段边界状态不匹配 continuity_notes 携带主角色/场景/主动作逐段传递
时空不连续 位置、服装、道具突然变化 全剧上下文（global_metadata）约束服装/道具描述
情绪断裂 情绪变化不符合时间逻辑 提示词要求"避免在分割点出现情感突变"

切分选点（提示词原文）：动作分割点＝动作完成后的瞬间 / 转身前 / 视线转移时；对话分割点＝句号、省略号后 / 情绪转折处；情感分割点＝呼吸停顿处 / 表情变化前。切点落在语义自然停顿处，再把边界状态通过 continuity_notes 交给下一片段。

两种实现：规则均分与 LLM 语义切分

分段节点同样有双实现（VideoSplitterFactory 按 AgentMode 选择）：

  • 规则模式（RuleVideoSplitter）：超过阈值即按公式均分——num_segments = min(3, int(时长 / 2.5) + 1)，每段时长 = 总时长 / 段数。纯数学、零 Token、确定性输出；代价是切点"不会读剧本"，可能在动作中途下刀。

  • LLM 模式（LLMVideoSplitter）：超阈值镜头逐镜送给 LLM，按提示词给出语义化的 segments（每段含 description / key_frames / continuity_hints），再由 _validate_and_adjust_fragments 校验并微调时长。

谁负责选路：_should_use_llm_split(shot)——镜头时长 ≤ 阈值直接走规则，超阈值走 LLM：

实现细节（如实指出）：该函数最后一行是无条件 return True，导致上面 complex_shots 与对话关键词两个分支实际上是死代码——只要超过阈值就必然走 LLM。从代码意图看，作者可能想为"复杂镜头才走 LLM、简单超长镜头走规则均分"留余地，但没有实现完整。这不影响结果正确性，但会让读者误以为存在更细的路由策略。

LLM 切分失败怎么办：cut() 主循环把每个镜头包在 try/except 里——LLM 切分抛异常时记录错误日志并自动降级为规则均分（warning("镜头{id}降级到简单规则分割")）。这是一条真实的"优雅降级"路径：宁可切得粗糙，不可卡死整个工作流。

LLM 模式的切分约束来自提示词（video_splitter_prompt.yaml 摘录）：

  • 12 条分割规则：动作连贯性 / 对话完整性 / 场景一致性 / 角色连续性 / 视觉元素连贯性 / 情感连贯性 / 转场合理性 / 叙事连贯性 / 视觉风格一致性 / 节奏控制 / 信息完整性 / 道具一致性；

  • 多片段（>2 段）时长分配：建立状态 30% → 发展变化 40% → 收束情感 30%；

  • 音频同步：台词结束点必须与视频片段结束点对齐，环境音可跨片段延续；

  • 硬约束：对话不可在句子中间分割；分割后各段描述合并必须覆盖原始描述的全部关键信息（含完整台词与道具细节）。

"模型特定"是怎么实现的：源码里并没有"加载模型模板"这种机制——真实做法是把目标模型名注入提示词模板（user_prompt_template.format(dm_model=self.config.video_model, ...)），由 LLM 按该模型的偏好组织描述，最后把 model 字段写入每个 AIVideoPrompt。模型白名单由质量审查节点把关（runway_gen2 / sora / pika），转换阶段本身不做格式强校验——这是一处轻量取舍：适配灵活性交给 LLM，合规性交给下游审查。

输出内容与真实拼装方式：

  • 视频提示词（双语拼装）：LLM 返回 prompt（英文）与 original_prompt（原语言）两个字段，代码拼接为 combined_prompt = f"{english_prompt}\n\n{original_prompt}" 存入 AIVideoPrompt.prompt——即"英文在前、原语言在后"的单字段结构，而非两个独立字段；

  • 负面提示词：取 LLM 返回的 negative_prompt，缺失时回退到配置默认值（模型默认 blurry, distorted, low quality, cartoonish, bad anatomy）；

  • 音频提示词（同批生成）：_build_audio_prompt_from_llm_result() 从同一次 LLM 返回中解析音频字段，构造 AIAudioPrompt（默认模型 XTTSv2 用于台词/旁白，背景声可用 AudioLDM_3），挂载在 AIVideoPrompt.audio 上，并用 previous_audio_id 串联音色连续性；

  • 技术参数：duration 沿用片段时长、model 取配置的 video_model、style 取 LLM 返回的 style_hint；

  • 执行建议：AIVideoInstructions.execution_suggestions 三条默认建议（顺序生成 / 保持种子 / 检查衔接）。

检查 实现方式（源码要点） 触发条件与严重度
角色 对照 ParsedScript.characters 与镜头 main_character；外观对比三类词表——服装（穿/戴/着/衣服/裙子/裤子/衬衫）、发型（长发/短发/马尾/卷发/直发）、配饰（眼镜/帽子/围巾/项链/耳环） 有对话但无镜头 → CHARACTER_MISSING（MAJOR）；同类外观词变化 → CHARACTER_APPEARANCE_CHANGE（WARNING）
场景 相邻镜头 scene_id 变化且前后镜头类型相同 单次跳变 → SCENE_JUMP（WARNING）；跳变计数 > 镜头数 × 30% → SCENE_TOO_FREQUENT（MODERATE）
动作 动作词表（走/跑/跳/转身/坐下/站起/拿起/放下）按角色追踪首个命中词 同角色相邻动作词变化 → ACTION_BREAK（MODERATE）
风格 统计 AIVideoPrompt.style 去重种类数 种类数 > 2 → STYLE_INCONSISTENT（MODERATE）
时间 比对片段 start_time 与"前段起始 + 时长"的差值 差值 > 0.1s：正差 → TIME_GAP（MAJOR）；负差 → TIME_OVERLAP（ERROR）
道具 道具动词表（拿/举/抱/提/端/持/握）按角色统计相邻变化 同角色道具动词变化 → PROP_CHANGE（WARNING）

去重、截断与 auto_fixable

_create_issue() 为每个问题生成去重签名：{type}_{fragment_id}_{scene_id}_{severity}_{position}_{description[:100]}——同一位置、同一级别的同类问题只报一次；超过 500 字符的描述截断为"497 字符 + …“。多数问题带 auto_fixable=True 标记与 suggestion（如"为角色添加镜头”“添加过渡镜头”），供修复流程直接消费；source_stage 记录问题归属阶段（解析 / 拆分 / 分段 / 转换）——由检查器创建问题时按问题类型直接填充，工作流端另有 _infer_issue_source 类型映射表兜底。

局限性与工程提示（如实指出）：关键词规则能低成本兜住"机械性断裂"，但误报/漏报是必然的——“转头"不会被动作词表命中（表里只有"转身”），“拿手机"到"握手机"会被判为道具变化，同义改写与近义动作就是词表法的边界。此外六项检查对 parsed_script / shot_sequence / fragment_sequence / instructions 各类上下文是"有则查、无则跳过”（每个方法开头都有判空返回），上下文喂得不全会直接降低检查覆盖面。需要真正的语义级连贯判定时，仍需 LLM 审查或人工复核补位。

修复路由与"未接通"的缺口（源码考证）

连续性检查发现问题后的"修复回流"设计了三步：① 按 source_stage 把问题分组到四个阶段（_analyze_continuity_issues，字段缺失时用问题类型映射表兜底）；② 用 ContinuityRepairGenerator 为每个阶段生成 QualityRepairParams 并写入 state.domain.repair_params[stage]（8 种问题类型各有对应修复建议文案）；③ _route_to_fix_stage 按"解析 → 拆分 → 分段 → 转换"优先级改写 state.execution.current_node，意图"哪错回哪"。四个上游节点开头也都有配套的消费逻辑——读 repair_params[自己] 并调用 apply_repair_params。

但图边的决策函数 decide_after_continuity 读取的是 state.continuity_issues——这是组合状态重构前的顶层属性写法；WorkflowState 由 input / domain / execution 等子状态组合而成，问题实际写在 state.domain.continuity_issues，顶层属性并不存在，getattr(..., []) 静默取到空列表，决策恒为 SUCCESS，流程直接进入结果生成。净效果：修复参数被生成、路由目标被改写，但本次运行不会回流到上游节点去消费它们（重试超限转人工的分支也因此不可达）。另外，即便修正读取路径，决策返回的是 NEEDS_RETRY，而图映射只声明了 NEEDS_REPAIR 等键——路由键同样需要补齐。这是"连续性修复闭环"当前未真正接通的根因，也是接入前值得优先处理的两处小改动。

四、常见排坑提示

  1. 顺序错乱：解析后如果场景/元素的 sequence 不连续，validate_parsed_result() 会给出警告但不阻断（只记问题项）。因此顺序问题的兜底在于复核 scenes[].elements[].sequence 是否符合预期；确认是解析质量问题时，走解析节点的重试路径（NEEDS_RETRY）。

  2. 时长超标：确认分段节点是否走了降级路径——LLM 切分抛异常时会静默降级为规则均分（日志出现"降级到简单规则分割"）。规则均分最多切 3 段，超长镜头均分后单段仍可能超过 5.5 秒红线；根治手段是在上游把镜头拆得更细（更细的元素分组），而不是在审查环节反复重试。

  3. 连续跳变：提示词生成后仍出现角色服装/道具突变，通常是 continuity_notes 没传对——确认上游片段已填充 main_character / location / main_action / split_type，并且 global_metadata 中的 character_outfits、key_props 已被解析出来（转换节点的提示词模板直接引用它们）。

  4. 检查误报：质量审查与连续性守护都是机械判定（硬性规则 + 词表匹配），"拿手机→握手机"被判道具变化这类误报属于已知边界——不要把它们的结论当语义金标准，高价值内容建议人工复核一次。
