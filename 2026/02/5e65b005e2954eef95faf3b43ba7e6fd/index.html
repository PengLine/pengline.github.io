PenShot 核心实现：LLM 客户端、提示词工程与三层记忆源码拆解

本文从源码层面拆解 PenShot 的关键实现。文中代码标注两类来源：真实源码（节选自 story-shot-agent 公开仓库 v0.3.x，仅省略 import 与版权头）与简化示意（用于说明设计意图的伪代码）。第六至八节的记忆系统以真实实现为准，并明确标注当前版本的工程边界——写清楚"实现了什么"与"还没实现什么"。

相关链接：GitHub | 官网 | 文档 （架构设计 · 召回策略 · 一致性策略 · RAG 增强）

一、LLM 客户端：多厂商可插拔封装

背景：PenShot 需要调用大语言模型做解析、拆分、转换，而不同厂商（OpenAI、本地 Ollama、通义千问）的 API 与 Embedding 接口差异较大，需要统一的封装层。配置分两级：配置文件/环境变量提供默认值，代码参数实时覆盖（优先级更高），厂商类型由 base_url 自动探测。

OpenAI

Ollama

QWen

核心逻辑解释（为什么这么设计）：

  • 统一抽象，差异下沉：所有客户端继承 BaseClient 并只实现 llm_model() 与 llm_embed() 两个方法，上层智能体只依赖 LangChain 的 BaseLanguageModel / Embeddings 抽象，不感知厂商差异；新增厂商只需注册到 CLIENT_REGISTRY。
  • 厂商自动探测：工厂函数 detect_ai_provider_by_url() 根据 base_url 域名路由客户端（openai.com → OpenAI、aliyuncs.com → Qwen、deepseek.com → DeepSeek，其余兜底 Ollama）。配置里只需填 base_url，减少一个必填字段、少一处出错点。
  • 参数语义对齐是真实坑点：同样叫"max tokens"，Ollama 的 num_predict 按生成 token 计数，代码显式乘 4 留出余量；Qwen 的 temperature/timeout 只能经 model_kwargs 透传。切换厂商时这些隐性差异必须逐项确认，否则会出现"配置没变、行为变了"的排查难题。
  • 环境变量是已知副作用：OpenAI/Qwen 客户端在构造时写入 os.environ（部分 LangChain 组件依赖环境变量读取密钥）。这是实现便利与副作用之间的取舍——同进程多客户端实例共存时环境变量会互相覆盖，属于当前实现的边界。

客户端工厂与降级链

配置初始化之外，真正决定"AI 服务挂了系统还能不能跑"的是工厂层的降级设计：

核心逻辑解释：LLM 在 PenShot 中是"增强项"而非"必需项"。初始化链路为 默认配置 → fallback 备用配置 → 返回 None 并打日志，共三级。上层拿到 None 后转入纯规则路径（例如视频切分自动降级为规则切分），任务不会因 AI 服务不可用而整体失败——这是"AI 辅助 + 规则兜底"架构在客户端层的落点。代价是降级后的输出质量只能靠规则保证，且降级发生时只有一条日志，调用方需要自行监控。

二、提示词管理：YAML + 版本化 + 缓存

背景：分镜质量高度依赖提示词质量。PenShot 对提示词做"版本化、分语言、分智能体维护"，避免散落在代码里难以迭代。每个智能体在 prompts/{version}/{language}/ 下拥有独立 YAML，以**镜头拆分智能体（shot_segmenter）**的模板为例（以下为真实 YAML 节选，version: 1.3）。

提示词模板

核心逻辑解释（提示词工程）：

  • 结构化约束驱动：给出"规则 / 拆分 / 衔接 / 转场 / 镜头 / 元素分配"六类规则，把分镜师的专业经验工程化为可执行约束。
  • One-shot 示例（few-shot）：提供输入→输出的完整示例，并要求"直接返回合法的 JSON 结构"，提升结构化输出稳定性。
  • 占位回调：{repair_hint}（修复建议）与 {history_hint}（历史上下文）承接"质量修复"与"记忆系统"，让同一条模板在不同运行态下复用。
  • 注意事项：切勿让 LLM 省略台词——"台词完整性"被反复强调，因为后台词缺失会直接破坏叙事。

与 YAML 模板配套的是加载器 PromptManager（源码文件 prompt_load_manager.py，注意与做"向量化模板复用"的 PromptTemplateManager 是两个不同的类）。以下为真实源码节选：

核心逻辑解释：

  • 懒加载 + 标志位：用 _all_prompts_loaded 保证所有 YAML 只全量加载一次，避免反复 IO。
  • 多策略匹配 & 容量上限：get_prompt() 按"缓存 → 键名 → name 字段 → 去 _prompt 后缀"逐级匹配；缓存超过 1024 条时只保留最新 1024 条，防内存膨胀。
  • 注意事项：模板以 version + language 目录隔离，切换语言/版本即切换目录，便于 A/B 调试。
  • 已知代码缺陷（如实记录）：get_all_prompts() 中"处理旧格式"的 elif isinstance(data, dict) and "name" in data 分支永远不可达——上面的 if isinstance(data, dict) 已捕获全部 dict 情形，这是历史重构的残留；另外 get_prompt() 的 docstring 列出了 5 条匹配策略，实现层实际只落地了其中 2 条。这类"文档与实现漂移"不影响主流程，但会误导二次开发者，属于可以顺手清理的技术债。

提示词组装（带重试的 LLM 调用）

核心逻辑解释：超时/网络抖动导致调用异常时，先 sleep(1) 再重试（默认 max_retries=2）；最后一次仍失败则显式上抛，交由工作流节点层的异常处理与三级循环控制接管（见第四节）。

注意事项（如实记录）：重试间隔是写死的 time.sleep(1)，并未使用 LLMBaseConfig.retry_delay 配置项；也没有区分"可重试错误/不可重试错误"——参数类的 4xx 错误同样会重试 2 次再上抛。这是用增加延迟换取实现简单，属于当前版本可优化的边界。

三、全局一致性保证

背景：拼接视频的致命伤是角色/道具/场景在不同片段间"变样"。PenShot 从源码层面用三种手段保证一致性。

连续性锚点传递

核心逻辑解释：锚点不是简单几个字段，而是带"生效范围"的约束对象——start_time/end_time/fragment_range 限定它只在某个时间区间或片段区间内有效（例如"雨伞"道具从第 3 个片段才出现），priority 用于多条约束冲突时的取舍，is_active_at() 供下游按时间轴查询"此刻哪些约束生效"。设计动因很直接：把一致性从"每处手写描述"升级为"结构化、可查询、有作用域"的约束数据，避免前一个片段还穿米白裙、后一个片段就换了外套。

修复参数反馈

核心逻辑解释：质量审计发现问题后，把"问题类型 + 涉及片段 + 严重程度 + 修复建议"封装成参数，由工作流在节点下一次执行前调用 apply_repair_params() 注入；智能体随后在组装提示词时生成 {repair_hint} 段（呼应第二节 YAML 中的占位符），实现"定向修复"而非盲目重跑。注意语义：修复参数是"下次执行生效"，且 suggestions 由审计阶段生成——这意味着审计若漏检，修复就无从谈起，质量修复能力上限取决于审计规则的覆盖度。

全局设置（真实实现）

核心逻辑解释：真实实现里并没有"全片段写死同一个魔数种子"的做法。PenShot 的一致性走两条路径：① 指令包携带 style_consistency、use_common_negative_prompt 全局开关，并把每个片段的风格收敛到统一的 default_style（默认 cinematic）与公共负面提示词；② 随机种子分两层——LLM 层的 LLMBaseConfig.seed（默认随机生成，仅 Ollama 客户端向下传递，影响文本生成的可复现性）与音频提示词层的 AudioPrompt.seed（默认 None，由 LLM 生成音频参数时可选填充）。

注意事项（如实记录）：LLMBaseConfig.seed 在 OpenAI/Qwen 客户端并未向下传递；视频画面的采样种子最终由下游视频模型决定，PenShot 输出的是提示词包，并不直接控制生成模型的随机性。把"固定种子"说成 PenShot 保证画面风格一致的核心手段并不准确——它保证的是"指令一致性"，画面一致性需要生成侧配合。

四、重试与无限循环控制

背景：多智能体、多阶段工作流极易在某节点卡死或无限自旋。PenShot 用"硬限制 + 软限制 + 全局后备"三套计数器兜底。

机制 计数器 触发条件 重置条件 作用
硬限制 node_current_loops 每次进入节点 永不重置 防止死循环
软限制 stage_current_retries 决策返回 NEEDS_RETRY 成功时重置为0 控制质量重试
全局后备 global_current_loops 每次进入节点 永不重置 最后防线

关键设计原则：

  1. 软限制失败后降级为 NEEDS_REPAIR，不是直接失败
  2. 修复参数会随 NEEDS_REPAIR 传递，指导节点如何修复
  3. 全局限制作为兜底，防止极端情况下的无限循环

全局 80% 预警（真实源码 workflow_decision.py）：全局循环用到 80% 时发出一次 warning 日志——条件为 global_current_loops >= global_max_loops * 0.8 and not loop_warning_issued，由 loop_warning_issued 标志位保证只发一次。这是典型的"软着陆"设计：等到 100% 直接 FAILED 时往往来不及排查，80% 预警给了运维介入的窗口。

默认参数参考（真实源码 workflow_state_types.py）：节点硬限制按节点差异化配置（PARSE_SCRIPT: 3、SEGMENT_SHOT: 5、SPLIT_VIDEO: 5、AUDIT_QUALITY: 3、HUMAN_INTERVENTION: 1）；阶段软限制多为 3（AUDIT_QUALITY、CONTINUITY_CHECK 为 2）；全局上限默认 global_max_loops = 30，工作流启动时按"所有节点最大循环次数之和 × 2"推导（workflow_pipeline.py 的 2 倍安全系数）。

决策状态流转图

stateDiagram-v2
    [*] --> 节点执行
    
    节点执行 --> 成功: 业务逻辑成功
    节点执行 --> 异常: 抛出异常
    
    成功 --> 决策函数
    异常 --> 错误处理
    
    决策函数 --> SUCCESS: 无质量问题
    决策函数 --> VALID: 轻微问题，可接受
    决策函数 --> NEEDS_RETRY: 有问题，可重试
    决策函数 --> NEEDS_REPAIR: 需修复后重试
    决策函数 --> NEEDS_HUMAN: 需人工干预
    决策函数 --> FAILED: 严重失败
    
    NEEDS_RETRY --> 检查软限制
    
    检查软限制 --> 节点执行: 未超限 (current < max)
    检查软限制 --> NEEDS_REPAIR: 已超限
    
    NEEDS_REPAIR --> 节点执行: 应用修复参数后重试
    
    SUCCESS --> [*]: 重置软限制，继续流程
    VALID --> [*]: 重置软限制，继续流程
    NEEDS_HUMAN --> [*]: 等待人工决策
    FAILED --> [*]: 进入错误处理
    
    错误处理 --> 节点执行: 可恢复错误，重新开始
    错误处理 --> NEEDS_HUMAN: 不可恢复
    错误处理 --> [*]: 中止流程

核心逻辑解释：状态机把"执行结果"和"质量评估"解耦——业务逻辑成功 ≠ 质量合格，是否重试由决策函数 + 软限制共同决定；无法恢复的错误才走到 NEEDS_HUMAN 或 FAILED。

注意事项：硬/全局计数器"永不重置"，是进程级防失控的最终闸门；因此排查瓶颈时应优先看软限制（质量重试）而不是硬限制。

TaskManager 状态持久化 Redis/内存双后端、TTL 过期

优先级管理

核心逻辑解释（为什么不用 heapq）：heapq 能做到 O(log n) 入队，但 PenShot 选择 list.insert 有序插入（最坏 O(n)）。原因在于队列还要支持按 task_id 遍历与移除——cancel_task() 的实现就是 for i, queued in enumerate(self._queue) 找到后 del；用堆实现这种操作反而更绕且需要延迟删除。队列上限 1000 的量级也不构成性能瓶颈。这是"数据结构选型服从业务操作集合"的典型例子；若队列规模升到数万级，才值得考虑堆 + 懒删除方案。

使用示例

核心逻辑解释：接入层（API/MCP/Python 库）统一走 TaskFactory 进入队列，AsyncTaskProcessor 按并发从 Worker Pool 调度执行；任务状态由 TaskManager 写 Redis 或内存，因此同一 task_id 可被不同回调随时查询。

故障恢复设计：recover_pending_tasks(max_age_hours=2) 会在进程重启后把两小时内状态仍未完成的任务重新放回队列——这是任务层面对"Worker 宕机 / 进程崩溃"的恢复手段。边界也很明显：恢复后一律以 NORMAL 优先级重新入队（原优先级丢失），且超过 2 小时的任务不会自动恢复，需要人工介入。

1. 短期记忆：滑动窗口 + Redis 双通道

真实实现不是 ConversationBufferMemory，而是"自维护 deque 滑动窗口 + LangChain 会话历史"的双通道结构：

flowchart LR
    subgraph 输入流
        I1[交互1] --> I2[交互2] --> I3[...] --> I4[交互19] --> I5[交互20] --> I6[交互21]
    end

    subgraph 滑动窗口[deque maxlen 20]
        W1[交互19] --> W2[交互20] --> W3[交互21]
    end

    I1 -.->|超出自动丢弃| W1
    I4 & I5 & I6 --> W1 & W2 & W3
    W1 & W2 & W3 --> O[get_recent 当前上下文]

核心逻辑解释（三条通道各司其职）：

  • deque 滑动窗口：deque(maxlen=20) 在添加时自动丢弃最旧条目，O(1) 且不可能溢出——比"判断超限再裁剪 list"的写法更难出错。get_recent(n) 优先读内存 deque（快），为空时回查 Redis（进程重启后的恢复路径）。
  • Redis 会话历史：跨请求可见，ttl=3600 让单次任务周期内的记忆自动过期，不需要额外清理任务。
  • 文件降级：Redis 不可用时每次 add() 同步写 short_term.json，重启后 _load_from_file() 恢复窗口。

故障实战（Redis 挂掉会发生什么）：降级决策发生在实例构造时——_check_redis_availability() 用 3 秒超时连接并 ping()，失败则整体切换到"内存 + 文件"模式并打 warning 日志，这是设计好的路径。运行中途 Redis 才挂的情况更微妙：add() 会走异常分支（error 日志），且由于缓冲区追加与 Redis 写入在同一 try 块内，本次交互既写不进 Redis 也不会进入内存窗口；后续 add() 持续失败，直到 Redis 恢复。也就是说，当前版本没有运行期重连与补偿机制，中途故障不会自动切通道。影响面可控的原因在于：单次记忆丢失不会中断主流程，且工作流有质量审计与检查点兜底；想彻底解决需引入重连探活与本地补偿队列，属于 Roadmap 级别的工作。

2. 中期记忆：LLM 摘要融合 + 双重截断保护

真实实现用 RunnableWithMessageHistory 包装自定义摘要函数（也不是 ConversationSummaryMemory），默认摘要是"逐步融合式"的滚动摘要（rolling summary）：

核心逻辑解释（为什么是"融合式"而不是"重新总结"）：每次摘要把"已有摘要 + 新内容"一起交给 LLM 做增量融合，而不是把全部历史重读一遍——摘要成本与内容总量呈线性关系，而不是随历史长度平方级增长。两处硬截断（输入 ≤ max_token_limit*4 字符、输出 ≤ max_token_limit*2 字符）是防"摘要越滚越大"的保险丝；代价是超长内容会被静默砍掉尾部（没有告警日志），排查"摘要信息缺失"类问题时要意识到这一点。

持久化与恢复：中期记忆写入 data/memory/{script_id}/ 下的 JSON（按小时归档），实例化时 _load_from_file() 恢复 _stage_summaries（阶段摘要字典）。注意滚动摘要本体不在恢复范围内，进程重启后需要从新的交互重新积累——这是当前实现的边界之一。

需要验证的疑点（如实记录）：similarity_search_with_score() 在 Chroma 默认 L2 距离度量下返回的是距离（越小越相似），而过滤条件是 score >= threshold（0.7）——方向与"保留更相似结果"的直觉相反，疑似"按余弦相似度习惯写过滤条件"的遗留。这里不下结论，建议使用方打印分数分布验证：如果命中的都是距离偏大的条目，应改为 score <= threshold。

故障实战（历史上下文没清干净会怎样）：clear_historical_context() 约定在"节点成功完成后"调用。若某条成功路径忘记调用（或新增节点未接入），历史问题会持续影响后续提示词——表现为"已经修好的问题，LLM 仍在小心翼翼地规避"，输出越来越保守。排查方法是看提示词日志里【历史参考信息】是否含过时条目；这也是为什么基类把它设计成显式的一对方法（apply / clear），而不是隐式状态。

三层记忆不是并列被调用的，而是由 ScriptMemory 统一组合。它有一个值得注意的设计——add 时的自动流转规则：

核心逻辑解释（这里的"融合"是组装，不是加权）：recall() 的真实语义是"按层查询、原样组装进 MemoryContext"，没有 0.6/0.3/0.1 之类的加权融合，也不存在 MemoryFusion 类——网上把"设计意图"当成了实现。三层信息的取舍发生在两个地方：MemoryContext.to_prompt() 的格式化（短期最多 10 条、长期最多 5 条、逐条截断）和调用方传入的 level 参数（指定只查某一层）。

一个值得讨论的设计点：触发"短期→中期"流转的人数阈值判断发生在每次 add() 末尾，且没有水位线/已压缩标记——窗口达到 80% 后每次 add 都会再触发一次摘要融合（多一次 LLM 调用），直到窗口被清空才会停。由于 deque maxlen=20、阈值为 16，窗口饱满后这条路径几乎每轮都执行；且在近满载时每次摘取的"最近 5 条"高度重叠。要修的话加一个 last_summarized_count 水位线即可——这属于读源码才能发现的优化点。

七、文本压缩：真实机制与边界

针对长剧本场景，PenShot 的"压缩"分散在三个层次，而不是一个独立的摘要模块。这里如实拆解每一层实际做了什么、没做什么。

真实存在的压缩机制

层次 机制 压缩对象 真实参数
记忆层 MediumTermMemory 的 LLM 滚动摘要 阶段交互内容 输入 ≤ max_tokens*4、输出 ≤ max_tokens*2 字符
记忆层 ScriptMemory 80% 水位自动摘要 短期窗口最近 5 条 short_term_size=20
提示词层 MemoryContext.to_prompt() 截断 组装后的记忆上下文 短期限 10 条/条 500 字符；长期限 5 条/条 800 字符
提示词层 指令长度约束 生成的视频提示词 max_prompt_length=200（单词），警告阈值 +20

核心逻辑解释（为什么用"字符估算"而不是精确分词）：_truncate 用"1 token ≈ 2 字符"的保守估算。为什么不上 tiktoken 等精确分词器？因为这里只需要一个"不超窗"的安全上界，而非精确计费——引入分词器会给每次提示词组装增加计算与依赖成本，而截断点本身已有冗余。这是一次典型的"精度换简洁"取舍；未来若做精确 token 计费或硬限流，才需要替换。

边界与不足（重要）：当前版本没有一个独立的"长剧本分块摘要器"类。网上流传的 ScriptSummarizer、按场景/对话/动作三级摘要以及 70%/80%/60%/50% 压缩比在源码中均不存在，属拟造内容。实际的长文本处理是"分而治之"：shot_segmenter 按场景（scene）逐个处理、video_splitter 按镜头（shot）逐个处理，每个单元的提示词只携带本场景信息 + 元素列表 + global_context（角色服装/关键道具等跨场景一致性汇总）。也就是说，长剧本的"分块"发生在场景/镜头拆分阶段，而非文本摘要阶段；真正的"全剧摘要压缩"属于 Roadmap 方向。

八、上下文窗口管理的真实边界

"上下文窗口管理"很容易被写成一套漂亮的分层机制，但真实源码里能落地的是四条朴素规则：

    end

核心逻辑解释（为什么锁定"窗口 + 约束"，不做"动态重要性淘汰"）：真实的取舍是把有限的工程预算放在"确定性"上——滑动窗口与 TTL 的行为可预测、调试成本低；而"按重要度动态淘汰"需要引入评分模型，且可能淘汰掉关键约束，反而增加不可控性。对应的质量兜底交给审计规则：提示词过长/过短都会被标记并进入修复循环，而不是在窗口层做文章。

当前实现边界（如实记录）：不存在 ContextWindowManager 类的"动态窗口 / 重要度评分 / 相似度去重"机制（源码中无对应类）。跨场景一致性信息通过 shot_segmenter 提示词的 global_context 占位符注入每次镜头拆分调用；把完整剧本一次性塞进单次提示词的做法只在短视频剧本下可接受，超长剧本的分块与逐块上下文重构属于 Roadmap 规划，不当作现状。

九、实现要点小结

  • 多 LLM 可插拔 + 三级降级：OpenAI / Ollama / Qwen 统一封装与厂商自动探测；默认配置失败退备用配置，再失败返回 None 走规则引擎模式。

  • 提示词工程是质量瓶颈：规则化约束 + one-shot 示例 + 版本化 YAML + {repair_hint}/{history_hint} 占位回传；加载器中存在不可达分支与文档漂移（已在第二节标注）。

  • 一致性保障：连续性锚点（带生效范围的结构化约束）、修复参数反馈（审计 → 注入 → 定向重试）、全局风格开关（style_consistency / use_common_negative_prompt）——而非"固定种子"这类被误传的说法。

  • 防御性循环控制：硬限制 / 软限制 / 全局后备三级计数器 + 80% 预警，节点级参数差异化配置，2 倍安全系数推导全局上限。

  • 三层记忆 + 分层存储：deque/Redis（短期）、LLM 滚动摘要/文件（中期）、Chroma（长期），recall() 按层组装而非加权融合；workflow_memory 的"历史参考信息"闭环让记忆真正影响下一轮输出。

  • 工程边界（如实记录）：无独立长剧本摘要器、无运行期 Redis 重连、长期记忆阈值过滤方向存疑、LLMBaseConfig.seed 仅 Ollama 透传——这些都在正文标注，供读者评估与向社区反馈。
