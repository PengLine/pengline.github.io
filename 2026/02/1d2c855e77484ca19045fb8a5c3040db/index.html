剧本分镜智能体（PenShot）技术架构

发表于2026-02-12|更新于2026-09-14
|AIAgentPenShot
|浏览量:

PenShot 技术架构

相关链接：GitHub | 官网 | 文档 （MCP Server · 召回策略 · 一致性策略 · RAG 增强）

一、概述：系统核心价值

PenShot（Pen & Shot）是一个基于 LangGraph 的多智能体协作系统，目标是把「自然语言剧本」端到端转化为「可直接投喂给 AI 视频模型（Sora / Veo / Runway / 可灵 / SVD）的指令序列」。它将「分镜」这一复杂任务拆解为解析、拆分、分段、转换、审查、守护六个相互衔接的专业节点，每个节点只专注一项职责，再通过工作流编排器统一调度。

这种架构带来的核心收益有三点：

  • 职责清晰：单一 Agent 的 prompt 与数据结构可各自优化，避免「一个 LLM 干所有事」导致的指令冲突与质量漂移。

  • 可控可重试：每个节点都能独立判定成功/失败，配合修复参数实现精准的局部重试，而非整条链路推倒重来。

  • 错误兜底：内置重试、错误处理与人工干预三重机制，保证长链路任务的鲁棒性。

概念澄清：LangGraph 是 LangChain 官方推出的图状态机框架，通过 StateGraph 描述节点（Node）与边（Edge）、条件分支（Conditional Edge），天然支持循环、路由与状态持久化，是多智能体流程编排的主流选择。

二、关键要点拆解

2.1 整体架构

智能体框架：LangGraph（专为多智能体状态机设计）

整个系统可分为 输入层 → LangGraph 多智能体核心工作流 → 记忆层 → 输出层 → 下游渲染 五个区块。核心工作流包含六个业务智能体与一个「辅助生成智能体」（三视图 / 背景图 / 关键帧），并通过控制节点（循环检查 → 错误处理 → 人工干预 → 结果生成）提供重试/修复/路由决策支持。记忆层用「短期 / 中期 / 长期 + 向量数据库 Chroma」四路供给上下文。输出端经 Workflow Output Fixer 修复与格式化后，以 JSON / SDK / MCP / A2A 对外暴露；下游经多模型适配器对接 Sora / Veo / Runway / 可灵 / SVD，由 FFmpeg 合成成片。

技术栈

组件 技术
智能体框架 LangGraph（状态图 + 条件分支）、LangChain
LLM支持 OpenAI、Ollama、通义千问、DeepSeek
任务管理 异步队列 + Redis
记忆系统 三层记忆 + 向量检索
错误处理 重试机制 + 人工干预

选型解读：LLM 层同时兼容云端 API 与本地部署（Ollama），便于在私有化与成本之间权衡；任务管理采用异步队列 + Redis，天然支持高并发与崩溃恢复，是面向「长任务」AI 服务的标配方案。

智能体职责

智能体 职责 输入 → 输出
1. 剧本解析智能体 将任意格式剧本统一解析为结构化叙事单元，提取场景、角色、动作、对话、道具、情绪等 原始文本 → 结构化序列（场景、角色、对话等）
2. 镜头拆分智能体 基于情感强度、节奏变化等，将剧本划分为最小可独立表达的镜头单元，并分配合理时长 结构化对象 → 带时间戳的镜头序列
3. 视频分段智能体 将镜头按5秒粒度切分，优先在动作静止点切割，输出符合AI视频模型要求的片段序列 镜头序列 → 符合AI视频长度限制的片段序列
4. 指令转换智能体 为每个AI片段生成模型适配的文生视频提示词（Prompt），包含构图、光线、运动等 片段内容 + 连续性锚点 → 可直接用于AI视频生成指令
5. 质量审查智能体 对全序列进行连贯性、时长合规性、角色漂移等检查，输出修正建议 AI片段序列 → 审查报告 （通过 / 修正建议列表）
6. 连续性守护节点 跨阶段连续性检查，识别角色、场景、动作、风格等连续性问题 所有阶段输出 → 连续性检查结果

设计说明：这六个节点呈「细化 → 拆分 → 合规化 → 转译 → 校验 → 兜底」的流水线逻辑。「按 5 秒切分」适配主流文生视频模型的单段时长硬上限；「优先在动作静止点切割」则可避免动作半途被截断造成的视觉跳变。

2.2 工作流编排

采用 LangGraph 实现多智能体协作流程，支持状态管理、循环控制和错误恢复。每个业务节点后都有一个决策判断，根据结果进入不同后续路径：

flowchart TD
    Start([开始/剧本输入]) --> Parse[剧本解析节点]

    Parse --> Decision1{解析结果判断}
    Decision1 -->|成功| Split[镜头拆分节点]
    Decision1 -->|严重失败| Error[错误处理节点]
    Decision1 -->|需要人工干预| Human[人工干预节点]

    Split --> Decision2{拆分结果判断}
    Decision2 -->|成功| Fragment[视频分段节点]
    Decision2 -->|需要重试/修复| Split
    Decision2 -->|严重失败| Error

    Fragment --> Decision3{分段结果判断}
    Decision3 -->|成功| Prompt[提示词生成节点]
    Decision3 -->|需要重试/修复| Fragment
    Decision3 -->|严重失败| Error

    Prompt --> DecisionP{生成结果判断}
    DecisionP -->|通过| Audit[质量审查节点]
    DecisionP -->|需要重试/修复| Prompt
    DecisionP -->|严重失败| Error

    Audit --> Decision4{审查结果判断}
    Decision4 -->|通过| Continuity[连续性守护节点]
    Decision4 -->|需要重试/修复| Prompt
    Decision4 -->|需要人工干预| Human
    Decision4 -->|失败| Error

    Continuity --> Decision5{连续性判断}
    Decision5 -->|通过| Output[生成输出节点]
    Decision5 -->|需要修复| Prompt
    Decision5 -->|需要人工干预| Human
    Decision5 -->|严重失败| Error

    Output --> End([工作流完成])

    Error --> DecisionE{错误处理判断}
    DecisionE -->|可恢复| Parse
    DecisionE -->|需要人工干预| Human
    DecisionE -->|中止流程| End

    Human --> DecisionH{人工决策判断}
    DecisionH -->|继续流程| Output
    DecisionH -->|重新开始| Parse
    DecisionH -->|调整提示词| Prompt
    DecisionH -->|中止流程| End

决策状态

每个节点的执行结果统一收敛为一组判定状态，由决策函数解释并路由，这是 LangGraph 条件分支的落地形态：

状态 含义 后续动作
SUCCESS 执行成功 进入下一节点
VALID 有轻微问题 继续执行
NEEDS_RETRY 需要重试 重新执行当前节点
NEEDS_REPAIR 需要修复 应用修复参数后重试
NEEDS_HUMAN 需要人工干预 进入人工干预节点
FAILED 执行失败 进入错误处理

状态机设计要点：SUCCESS 与 VALID 都「放行」，但语义不同——VALID 表示有轻微瑕疵、可带病继续；只有 NEEDS_REPAIR 才携带修复参数回退。这样既保证质量，又避免因轻微问题反复重试拖垮吞吐。

    Continuity -->|NEEDS_REPAIR| Prompt

    Human -->|SUCCESS| Output

    QA->>QA: 47. 生成修复参数

    CG->>CG: 51. 角色连续性检查

    CG->>CG: 53. 动作连续性检查

    WP-->>TF: 65. 任务完成

重试配置

智能体 最大重试次数 修复策略
剧本解析 3次 修复参数重试
镜头拆分 3次 时长调整重试
视频分段 3次 切分点优化重试
指令转换 3次 提示词优化重试
质量审查 2次 参数调整重试
连续性守护 3次 问题溯源修复

重试语义：每个节点拥有独立的修复策略——解析重试侧重「修复参数」，分段重试侧重「切分点优化」，连续性守护则采用「问题溯源」定位回退到哪个上游节点，避免盲目整链重跑。

    participant System as 流程编排器
    participant Parser as 剧本解析智能体
    participant Splitter as 镜头拆分智能体
    participant Fragmenter as 视频分段智能体
    participant Converter as 指令转换智能体
    participant Auditor as 质量审查智能体
    participant Guardian as 连续性守护节点
    participant Error as 错误处理节点
    participant Human as 人工干预节点

    %% 正常流程
    User->>System: 提交剧本
    System->>Parser: 开始解析

    %% 剧本解析 + 重试循环
    loop 最多3次重试
        Parser->>Parser: 解析剧本
        Parser-->>System: 返回结构化剧本
        System->>System: 决策:解析结果判断
        
        alt 解析成功
            System->>Splitter: 开始镜头拆分
        else 需要重试/修复
            System->>Parser: 应用修复参数后重试
        else 严重失败
            System->>Error: 进入错误处理
        end
    end

    %% 镜头拆分 + 重试循环
    loop 最多3次重试
        Splitter->>Splitter: 拆分镜头
        Splitter-->>System: 返回镜头序列
        System->>System: 决策:拆分结果判断
        
        alt 拆分成功
            System->>Fragmenter: 开始视频分段
        else 需要重试/修复
            System->>Splitter: 应用修复参数后重试
        else 严重失败
            System->>Error: 进入错误处理
        end
    end

    %% 视频分段 + 重试循环
    loop 最多3次重试
        Fragmenter->>Fragmenter: 5秒智能分段
        Fragmenter-->>System: 返回片段序列
        System->>System: 决策:分段结果判断
        
        alt 分段成功
            System->>Converter: 生成AI指令
        else 需要修复(时长问题)
            System->>Fragmenter: 应用修复参数后重试
        else 严重失败
            System->>Error: 进入错误处理
        end
    end

    %% 指令转换 + 重试循环
    loop 最多3次重试
        Converter->>Converter: 生成提示词
        Converter-->>System: 返回Prompt序列
        System->>System: 决策:生成结果判断
        
        alt 生成通过
            System->>Auditor: 开始质量审查
        else 需要重试/修复
            System->>Converter: 应用修复参数后重试
        else 严重失败
            System->>Error: 进入错误处理
        end
    end

    %% 质量审查 + 修复决策
    Auditor->>Auditor: 规则审查
    Auditor->>Auditor: LLM深度审查
    Auditor->>Auditor: 问题分类+生成修复参数
    Auditor-->>System: 返回审查报告
    System->>System: 决策:审查结果判断

    alt 审查通过
        System->>Guardian: 开始连续性检查
        
    else 轻微问题(≤3个)
        System->>System: 自动修复
        System->>Guardian: 继续连续性检查
        
    else 中等问题
        System->>System: 标记需要修复
        System-->>Converter: 返回到指令转换修复
        
    else 严重问题
        System->>Error: 进入错误处理
        
    else 需要人工干预
        System->>Human: 请求人工决策
        Human-->>System: 返回人工决策
    end

    %% 连续性检查 + 修复循环
    loop 最多3次连续性修复
        Guardian->>Guardian: 角色连续性检查
        Guardian->>Guardian: 场景连续性检查
        Guardian->>Guardian: 动作连续性检查
        Guardian->>Guardian: 风格连续性检查
        Guardian->>Guardian: 时间连续性检查
        Guardian->>Guardian: 道具连续性检查
        Guardian-->>System: 返回连续性问题列表
        System->>System: 决策:连续性判断

        alt 检查通过
            System->>User: 返回完整AI指令
            
        else 发现连续性问题
            System->>System: 问题溯源分析
            
            alt 剧本解析问题
                System-->>Parser: 返回到剧本解析修复
            else 镜头拆分问题
                System-->>Splitter: 返回到镜头拆分修复
            else 视频分段问题
                System-->>Fragmenter: 返回到视频分段修复
            else 指令转换问题
                System-->>Converter: 返回到指令转换修复
            end
            
        else 修复次数超限
            System->>Human: 请求人工干预
            Human-->>System: 返回人工决策
            
            alt 人工确认继续
                System->>User: 返回AI指令(带警告)
            else 人工要求中止
                System->>User: 返回失败信息
            end
        end
    end

    %% 错误处理流程
    System->>Error: 进入错误处理
    Error->>Error: 错误分类分析
    Error->>Error: 制定恢复策略

    alt 网络/超时错误
        Error->>Error: 延迟后重试
        Error-->>Parser: 重新开始流程
        
    else 验证/数据错误
        Error->>Error: 生成修复参数
        Error-->>System: 返回需要修复
        
    else 配置错误
        Error->>Error: 调整配置参数
        Error-->>Parser: 重新开始流程
        
    else 多次重试失败
        Error->>Human: 请求人工干预
        Human-->>Error: 返回人工决策
        
        alt 人工继续
            Error-->>System: 继续执行
        else 人工中止
            Error->>User: 返回失败信息
        end
        
    else 不可恢复错误
        Error->>User: 返回失败信息
    end

审查策略说明：质量审查采用「轻微问题（≤3 个）自动修复」的灰度策略——代价低的小问题内部消化，避免频繁打断流程；只有达到中等或严重程度才触发回退修复或人工介入。

并发任务流程

任务提交后统一进入优先级队列（CRITICAL > HIGH > NORMAL），由工作线程池按优先级拉取执行，空闲 Worker 逐级补位，最大化并发吞吐：

sequenceDiagram
    autonumber
    participant C1 as 客户端1
    participant C2 as 客户端2
    participant TF as TaskFactory
    participant Q as 优先级队列
    participant P as Processor
    participant W1 as Worker 1
    participant W2 as Worker 2
    participant W3 as Worker N

    C1->>TF: 1. 提交任务A(优先级HIGH)
    C2->>TF: 2. 提交任务B(优先级NORMAL)
    C1->>TF: 3. 提交任务C(优先级CRITICAL)

    TF->>Q: 4. 任务C入队(CRITICAL)
    TF->>Q: 5. 任务A入队(HIGH)
    TF->>Q: 6. 任务B入队(NORMAL)

    Note over Q: 队列按优先级排序: C → A → B

    loop 并发调度
        P->>Q: 7. 获取任务
        Q-->>P: 8. 返回最高优先级任务
        
        alt Worker空闲
            P->>W1: 9. 分配任务C
            W1->>W1: 10. 执行任务
            
            P->>Q: 11. 获取下一个任务
            Q-->>P: 12. 返回任务A
            P->>W2: 13. 分配任务A
            W2->>W2: 14. 执行任务
        end
    end

    W1-->>P: 15. 任务C完成
    P-->>TF: 16. 回调通知
    TF-->>C1: 17. 返回结果

    W2-->>P: 18. 任务A完成
    P-->>TF: 19. 回调通知
    TF-->>C1: 20. 返回结果

适用场景：当多个客户端同时提交分镜任务时，优先级队列确保「重要/紧急」任务优先调度，而不会因先来先服务导致关键任务长时间排队。

状态持久化流程

状态通过「内存缓存 → Redis → 持久化存储」三级联动落地，并内置崩溃恢复逻辑——扫描未完成任务时，2 小时内的任务恢复重处理，超过 2 小时标记为过期：

sequenceDiagram
    autonumber
    participant Agent as 智能体
    participant TM as TaskManager
    participant Cache as 内存缓存
    participant Redis as Redis
    participant DB as 持久化存储

    Agent->>TM: 1. 更新任务进度
    TM->>Cache: 2. 更新内存状态
    TM->>Redis: 3. 同步到Redis
    Redis-->>TM: 4. 同步成功
    TM-->>Agent: 5. 更新完成

    Note over Redis: 任务状态定期同步

    alt Redis不可用
        TM->>Cache: 6. 仅内存存储
        TM->>DB: 7. 异步持久化
    end

    Note over Agent,Redis: 任务恢复场景

    TM->>Redis: 8. 扫描未完成任务
    Redis-->>TM: 9. 返回任务列表
    
    loop 恢复每个任务
        TM->>TM: 10. 检查任务年龄
        alt 2小时内
            TM->>Cache: 11. 恢复任务状态
            TM->>Agent: 12. 重新入队处理
        else 超过2小时
            TM->>TM: 13. 标记为过期
        end
    end

降级要点：Redis 不可用时任务仍可「仅内存 + 异步落库」运行，保证服务不至于完全不可用；2 小时恢复窗口可看作「半衰期」——超出即认定失败或无人等待，直接过期回收。

双重保护机制

为避免 LLM 反复失败导致无限循环拖垮系统，架构设置了三级计数器防护：

机制 计数器 作用
硬限制 node_current_loops 防止死循环
软限制 stage_current_retries 控制质量重试
全局后备 global_current_loops 最后防线

防死循环原理：node_current_loops 限制单节点内循环次数，stage_current_retries 限制阶段级质量重试，global_current_loops 作为全局兜底。任一触顶都会把流程强制导向错误处理或人工干预，避免无限消耗 token 与时间。

2.5 质量保障体系

检测修复策略

采用 “轻前置检测 + 重最终检测” 的策略：每个节点后只做轻量基础检测（格式 / 时长 / 空值，随手即修），只有在全流程结束后才做统一的深度检测（连贯性 / 一致性 / 语义），并根据问题溯源到相应上游节点修复：

flowchart TD
    A[剧本输入] --> B[剧本解析]
    B --> C[剧本基础检测]
    C --格式问题--> B

    C --> D[镜头分割]
    D --> E[镜头基础检测]
    E --时长/格式--> D

    E --> F[视频分割]
    F --> G[片段基础检测]
    G --时长/格式--> F

    G --> H[指令转换]
    H --> I[指令基础检测]
    I --格式/空值--> H

    I --> J[统一质量检测]
    J --全局问题分类--> K{问题溯源}

    K --剧本语义--> B
    K --镜头连贯--> D
    K --片段分割--> F
    K --指令质量--> H

    J --> L[最终输出]
检测类型 检测时机 检测内容 修复方式
基础检测 每个节点后 格式、时长、空值等基础问题 立即修复
统一检测 所有节点后 连贯性、一致性、语义等深度问题 分类修复
跨层检测 统一检测中 角色、道具、场景等跨节点问题 多节点协同

设计价值：把「昂贵的深度 LLM 校验」集中在一次而非每节点各来一遍，可显著节省成本；基础检测前置，让格式类低级错误尽早暴露。

修复参数机制

质量审查发现问题后，不直接改数据，而是**按来源分类生成「修复参数」**并写入工作流状态，节点重试时读取并应用——形成「检测 → 分类 → 生成修复 → 保存 → 重试应用」的闭环：

flowchart LR
    subgraph Audit[质量审查]
        A[检测问题] --> B[按来源分类]
        B --> C[生成修复参数]
    end

    subgraph Apply[修复应用]
        D[保存到状态] --> E[节点重试时传入]
        E --> F[智能体调整策略]
    end

    subgraph Result[修复结果]
        G[避免问题重现]
    end

    Audit --> Apply --> Result

详细参数传递流程：

sequenceDiagram
    autonumber
    participant QA as 质量审查智能体
    participant Report as 审查报告
    participant State as 工作流状态
    participant Node as 工作流节点
    participant Agent as 业务智能体

    QA->>QA: 1. 检测问题
    QA->>QA: 2. 按来源分类
    QA->>Report: 3. 生成修复参数
    Report-->>QA: 4. 返回RepairParams

    QA->>State: 5. 保存到state.repair_params
    State-->>QA: 6. 保存成功

    Note over State,Node: 节点重试时

    Node->>State: 7. 读取修复参数
    State-->>Node: 8. 返回repair_params

    alt 有修复参数
        Node->>Agent: 9. apply_repair_params()
        Agent->>Agent: 10. 更新内部策略
        
        Node->>Agent: 11. process(repair_params)
        Agent->>Agent: 12. 使用修复参数生成
        Agent-->>Node: 13. 返回优化结果
        
        Node->>State: 14. 清除修复参数
    else 无修复参数
        Node->>Agent: 15. process()
        Agent-->>Node: 16. 返回正常结果
    end

关键细节：修复参数在应用成功后会被主动清除（第 14 步），防止被执行过的修复参数在下游节点再次被误应用，避免「二次修理」引发副作用。

错误处理与重试

sequenceDiagram
    autonumber
    participant Node as 工作流节点
    participant Decision as 决策函数
    participant Error as 错误处理节点
    participant Human as 人工干预节点
    participant Retry as 重试机制

    Node->>Decision: 1. 节点执行完成
    Decision->>Decision: 2. 判断执行结果

    alt 执行成功
        Decision-->>Node: 3. 返回SUCCESS
        Note over Node: 继续下一节点

    else 需要重试
        Decision->>Decision: 4. 检查重试次数
        alt 未超限
            Decision->>Retry: 5. 增加重试计数
            Retry-->>Decision: 6. 返回NEEDS_RETRY
            Decision-->>Node: 7. 返回NEEDS_RETRY
            Note over Node: 重新执行当前节点
        else 已超限
            Decision->>Error: 8. 返回FAILED
        end

    else 需要修复
        Decision->>Decision: 9. 生成修复参数
        Decision-->>Node: 10. 返回NEEDS_REPAIR
        Note over Node: 应用修复参数后重试

    else 严重错误
        Decision->>Error: 11. 返回FAILED
    end

    Error->>Error: 12. 错误分类分析
    Error->>Error: 13. 制定恢复策略

    alt 可恢复错误
        Error->>Retry: 14. 重置重试计数
        Retry-->>Error: 15. 返回原节点
        Error-->>Node: 16. 返回NEEDS_RETRY

    else 需要人工干预
        Error->>Human: 17. 请求人工干预
        Human->>Human: 18. 等待用户决策
        
        alt 用户选择继续
            Human-->>Error: 19. 返回CONTINUE
            Error-->>Node: 20. 返回SUCCESS
        else 用户选择重试
            Human-->>Error: 21. 返回NEEDS_RETRY
            Error-->>Node: 22. 返回NEEDS_RETRY
        else 用户选择中止
            Human-->>Error: 23. 返回ABORT
            Error-->>Node: 24. 终止流程
        end

    else 不可恢复错误
        Error->>Error: 25. 记录失败
        Error-->>Node: 26. 返回ABORT
    end

错误分类观：错误处理区分「网络 / 超时、验证 / 数据、配置、不可恢复」四类——网络类延迟后整链重跑，验证类生成修复参数局部重试，配置类调参后重跑，不可恢复类直接 ABORT。

状态清理分析

flowchart TD
    subgraph Task[任务执行]
        A[节点开始] --> B{是否有历史上下文?}
        B -->|有| C[apply_historical_context]
        B -->|无| D[跳过]
        C --> E{是否有修复参数?}
        D --> E
        E -->|有| F[apply_repair_params]
        E -->|无| G[执行节点逻辑]
        F --> G
        G --> H{执行成功?}
        H -->|是| I[节点结束]
        H -->|否| J[进入错误处理]
    end

    subgraph Cleanup[清理时机]
        I --> K{是否还有后续节点?}
        K -->|是| L[保留状态供下游使用]
        K -->|否| M[任务完成，清理所有状态]
        J --> N[保留状态供重试]
    end
场景 是否需要清理 原因
节点正常完成 需要 避免影响后续任务
节点异常/重试 不需要 重试时需要保留修复参数
节点被跳过 不需要 未执行，无状态
整个任务完成 需要 任务结束，释放资源

清理策略：状态清理遵循「按需保留、用毕即删」——重试路径必须保留修复参数，正常推进则清理避免污染下游，整任务完成后整体释放资源。这样在「可恢复性」与「存储占用」之间取得平衡。

三、总结与建议

PenShot 的技术架构体现了多智能体系统设计的几个通行范式：

  1. 以 LangGraph 为骨架：用图状态机承载「分支、循环、重试、路由」，让复杂的创作流程可编排、可观测、可恢复。

  2. 六节点流水线 + 控制节点：业务节点各司其职，控制节点统一负责循环检查、错误处理、人工干预，分工清晰。

  3. 多级容错：决策状态机（RETRY / REPAIR / HUMAN / ABORT）+ 双重防死循环计数器 + 状态持久化恢复，三层保障鲁棒性。

  4. 「轻前置 + 重最终」质检：基础检测随做随修，深度检测集中于收尾，兼顾成本与质量。

落地建议：接入时先从最小的「两到三个节点」流水线起步验证效果，再逐步扩展节点与修复参数机制；并务必配置好双重防死循环计数器的阈值与人工干预的触发条件，避免长任务在无监督环境下「打转」或「白跑」。
