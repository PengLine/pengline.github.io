PenShot 召回评测：三层记忆的真实接线与静默失效

版本基线：本文以 PenShot 0.3.9（2026-10-13）源码为复核基线。文中的真机数据来自 2026-05 至 2026-07 的本地运行快照，仅代表当时的环境；长期记忆检索的阈值问题已在 0.3.8 修复，本文会单独标注。

相关链接：PenShot 官网 | GitHub | 记忆与检索文档

召回系统是 PenShot 智能增强层的核心：它从历史成功案例和知识库中检索信息，用来增强提示词与连续性检查。三层记忆、向量检索、重排序、混合检索——这些词放在一起，很容易让人以为系统已经“全副武装”。

把源码逐条打开后，结论要克制得多：写入侧持续运转，读取侧只有部分接线；一些能力已经实现，但没有生产调用方。 这类系统最危险的不是报错，而是安静地少做事。

本文按 0.3.9 的调用链，把“已接线”“已实现未接线”“静默失效”分开说清楚。

一、真实接线图

先看生产链路里真实发生的事情：

graph TB
    subgraph Prod["生产链路（已接线）"]
        N[工作流节点] --> WM[WorkflowMemory.after_stage_completion]
        WM --> MM[MemoryManager → ScriptMemory.add]
        MM --> ST[短期记忆<br/>Redis · 20 条滑动窗口]
        MM --> MT[中期记忆<br/>LLM 摘要 + JSON 持久化]
        MM --> LT[长期记忆<br/>Chroma · score ≥ 0.7]
        N --> PTM[PromptTemplateManager]
        PTM --> SS[search_similar / get_best_match<br/>SimpleVectorStore 余弦检索]
        PTM --> EP[enhance_prompt<br/>模板增强]
    end

    subgraph Stand["已实现 · 未接线（无生产调用方）"]
        KR[KnowledgeRouter._hybrid_search<br/>三源合并去重]
        CR[create_retriever_for_script<br/>BGE 重排序装配]
        MR[MemoryManager.get_context_for_llm<br/>记忆语义读取]
    end

    KR -.-> CR
    SS -.->|生产路径无重排序| CR
    MM -.-> MR

三条事实：

  • 记忆链路是三套存储分工：短期走 Redis（不可用时降级内存 + 文件），中期走 LLM 摘要 + JSON，长期走 Chroma；

  • 脚本知识库检索不经过 Chroma：search_similar 直接用 LlamaIndex 的 SimpleVectorStore 做余弦检索，Chroma 只服务长期记忆；

  • KnowledgeRouter 的工厂函数在 llama_index_router.py:546，但全仓库没有生产代码导入它——混合检索、重排序装配、文档检索器都处于“已实现、未接线”状态。

二、短期记忆：Redis 优先，内存兜底

短期记忆的真实结构是“Redis 优先、内存降级”的双轨制（short_term_memory.py:25）：

  • 窗口机制：deque(maxlen=config.short_term_size)，默认 20 条，超过自动淘汰最旧消息；

  • 存储选择：初始化时尝试 Redis，key 为 penshot:memory:{session_id}，TTL 默认 3600 秒；Redis 不可用时降级为带文件持久化的进程内消息历史；

  • 会话隔离：session_id 按剧本粒度生成，而不是项目级共享；

  • 降级判定发生在构造时：_check_redis_availability() 在初始化阶段 ping 一次，运行中途 Redis 挂掉不会触发重新选择存储。

这带来一个容易忽略的边界：构造时 Redis 可用、运行中挂掉，缓冲追加与 Redis 写入在同一个 try 块里，异常被吞掉，本次交互静默丢失，也没有重连补偿。任务看起来还在跑，只是记忆少了一截。

短期记忆没有“任务完成即清空”的钩子，只靠两个机制自然滚动：20 条上限与 1 小时 TTL。一小时内连续跑多个剧本时，会话残留属于设计内行为；隔离依赖 session_id 的剧本粒度，而不是“用完即清”。

三、中期记忆：摘要正常写，重启读不回

中期记忆基于 LangChain 的摘要链：每次写入时，新内容超过 max_token_limit * 4（默认 500 → 2000 字符）先截断，再调用 LLM 把新内容并入既有摘要；摘要自身超过 max_token_limit * 2（1000 字符）时再截断。

设计之外，有一个值得单独记录的静默失效：读写文件名不一致。

  • 写入：medium_term_memory.py:161 调用 save_json_result(..., f"medium_summary_{YYYYMMDDHH}.json")，按小时分文件；

  • 读取：medium_term_memory.py:172 读取固定名 medium_summary.json；

  • clear 操作同样指向固定名。

写入与读取指向两个不同的路径。后果是：中期摘要每次进程重启后都加载不回来，历史摘要永远在磁盘上“沉睡”。真机数据恰好印证了两面：data/memory/ 下堆积着 2026-05 至 07 的多份按小时快照（写入一直在跑），但没有一份会被读取逻辑认领。

这里还有一个语义偏差：max_token_limit 的名字是 token，代码里实际按字符长度截断。中文里 1 个汉字通常不止 1 个 token，所以“500 token 上限”在中文场景下会低估实际长度。功能上无害（照样压缩），但参数含义与名字并不完全一致。

四、长期记忆：靠成功样本喂养

长期记忆基于 Chroma，每个剧本一个 collection。写入路径是：工作流每个阶段完成后，WorkflowMemory.after_stage_completion 评估该阶段是否构成“成功案例”，通过才生成条目写入。

workflow_memory.py:632 的门槛按阶段不同：

阶段 成功条件
parse_script completeness_score >= 0.8
segment_shot 镜头数 ≥ 1 且总时长 > 0
split_video 片段数 ≥ 1
convert_prompt 有提示词，且音频覆盖率 ≥ 50%

长期记忆是一个“全靠成功样本喂养”的冷启动系统：样本不够成功，它就一直是空的。空库状态下的检索不会报错——它安静地返回零条结果，任何依赖“历史经验”增强的逻辑都会静默退化为“没有经验可用”。

0.3.8 修复了一个关键问题。 2026-09-19 的提交“修复长期记忆检索用距离与相关度阈值比较导致结果恒为空问题”，把 Chroma 返回的距离换算成相关度：

然后在 long_term_memory.py:185-186 用相关度与 long_term_score_threshold（默认 0.7）比较。修复前，距离直接和 0.7 比，结果几乎恒为空；修复后，检索至少能在非空集合里正常工作。

但“能检索”和“有东西可检索”是两件事。如果成功样本尚未积累，集合仍然是空的。给长期记忆加一个“集合文档数”监控，比任何检索日志都更能提前暴露问题。

五、重排序与混合检索：装配完整，生产没接

这是最容易被“功能列表”误导的部分。

create_retriever_for_script 里的重排序装配是完整的（llama_index_knowledge.py:577-630）：

  • 支持从配置读取 rerank_model_local_path，相对路径自动拼到项目根目录；

  • 路径不存在时输出 warning，降级为模型名，可能触发从 HuggingFace 联网下载；

  • 用 SentenceTransformerRerank(model=..., top_n=min(3, similarity_top_k)) 挂入 node_postprocessors；

  • 成功与失败都有日志埋点。

但是，生产路径中的 query() 并没有走这套装配。query() 的实现是手动余弦相似度（llama_index_knowledge.py:481-565）：查询文本嵌入后，遍历向量存储内的全部文档向量逐一计算、排序、截取 Top-K。函数签名里有 search_type 与 use_rerank，函数体却从未读取它们。

所以会出现这样的组合：

参数传了 use_rerank=True，但 query() 不读，重排序不会发生。prompt_template_manager.py:511 的 search_similar_scene 也是同样情况。真正能走重排序的 create_retriever_for_script 只在 KnowledgeRouter 里被调用，而 KnowledgeRouter 没有生产调用方。

MMR 分支同理：search_type == "mmr" 的装配存在，但 query() 不读 search_type，生产路径也到不了 create_retriever_for_script。混合检索的 _hybrid_search 也只在未接线的路由器里。

一句话总结：“支持重排序”在代码层面是真的，“生产链路启用了重排序”在当前版本里不是。

六、真正影响输出的两条链

召回结果以什么路径影响最终输出？逐条复核后，答案是“两通、一断”。

链路一：提示词增强（已接线）。 convert_prompt 节点对每个片段调用 enhance_prompt(fragment.prompt, enhancement_mode="append")（workflow_nodes.py:576），内部走 get_best_match → search_similar，top_k=1、min_score=0.7、仅模板类型。命中就把匹配模板拼接进原提示词。这是“召回质量直接影响生成输入”的实链路，只有一个质量闸门。

链路二：连续性检查（已接线）。 search_similar_scene 为每个连续性问题检索历史场景方案（workflow_nodes.py:971），top_k=2，填充 historical_solutions。这条链没有分数门槛——低质结果也可能被当作“历史方案”。

断点：记忆语义读取未接线。 MemoryManager.recall → MemoryContext.to_prompt（对外封装为 get_context_for_llm，memory_manager.py:295）与 WorkflowMemory.restore_context_for_stage（workflow_memory.py:97），这两条“把记忆读回来注入上下文”的设计链路，全仓库没有生产调用方。记忆的语义检索能力完整实现，却从未接上消费端。

这意味着“三层记忆影响生成质量”在真机上尚未完全成立：写入侧持续运转，读取侧只有键值查询，语义读取是断的。

七、一套最小可复现的召回评测

既然系统里没有现成的评测数据，就把评测做起来。不需要新框架，用项目内现成能力即可。

第一步：构造最小评测集。 按查询类型分层取样：角色查询（“主角是谁”）、场景查询（“雨夜街道”）、模板查询（“愤怒情绪的提示词”），每类 10 条，人工标注期望命中的文档。小索引的价值不在于统计显著性，而在于建立可重复的回归基线——更换嵌入模型或阈值后，同一套评测跑出的差异才是可解释的。

第二步：指标分“健康度”与“效果”两层。 健康度优先：空结果率、长期记忆集合文档数、嵌入维度一致性断言——这三项能第一时间暴露静默失效。效果层再跟上：命中率@K、MRR、首条命中分数分布。

第三步：先验证开关，再做对照。 本文最大的教训是“哑参数”——use_rerank、search_type 传了等于没传。任何 A/B 实验开始前，先跑一次“开关有效性验证”：变更参数后打印最终生效的配置，或断言参数被读取，确认旋钮真的连着线。

第四步：从小索引的现实出发设计结论。 2–12 条文档的召回实验只能回答“链路是否通”，回答不了“准确率多少”。要得到有价值的数字，需要先灌入几十上百条剧本构建有统计意义的索引——这是评测的前置工程量，无法绕过。

八、把结论压成三张清单

已接线（真实生产行为）

  • 相似度检索两条路径：search_similar（0.7 及格线 + 模板类型过滤，经 enhance_prompt 进入生成）与 query()（手写余弦、无分数门槛，用于连续性检查）；

  • 三层记忆写入：短期 Redis（20 条窗口 + 3600s TTL，剧本级 session）、中期 JSON 摘要（写入正常但重启读不回）、长期 Chroma（受成功门槛约束）；

  • 提示词增强与连续性检查均在 convert_prompt / 连续性检查节点中真实执行。

已实现未接线（代码完整、无生产调用方）

  • 重排序装配（BGE-reranker-large）、MMR 分支、KnowledgeRouter 混合检索、记忆语义读取（get_context_for_llm / restore_context_for_stage）。

静默失效清单（不报错但行为偏离预期）

  • 中期摘要读写文件名不一致：重启即“失忆”；

  • 长期记忆空库：检索安静返回零结果；

  • 嵌入维度偏差：配置维度与实际落盘维度不一致时，按配置硬编码的处理代码会错位（这是环境配置问题，不是当前版本的默认行为）；

  • 哑参数与无分数门槛：传了不生效、查了不过滤。

三条工程建议

  1. 先建测量，再谈指标。 上召回系统前，先给延迟、空结果率、命中率留好埋点；

  2. 把静默失效当一等公民。 空库、文件名不一致、哑参数都不抛异常，为它们建监控的收益远超调参；

  3. 接一根线、验一根线。 重排序、MMR、混合检索、记忆读取都是“看起来有、实际没有”的能力，每次声称“已支持”，用一条端到端调用链测试来证明它。
