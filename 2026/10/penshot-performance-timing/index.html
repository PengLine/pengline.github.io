PenShot 性能评测：LLM 阶段吃掉了多少时间

版本基线：本文实测数据来自 v0.3.x 在 2026-06 至 2026-07 的两次真实运行，环境为本机部署的 PenShot 服务。升级版本、更换模型供应商或调整并发后，耗时会变化，建议重新实测。

相关链接：PenShot 官网 | GitHub | Docker 部署

PenShot 的主链路是一条六段式流水线：

剧本解析 → 镜头拆分 → 视频分段 → 指令转换 → 质量审查 → 连续性守护

它和普通后端服务最大的不同在于：链路中规则处理与 LLM 调用混合。视频分段是确定性规则算法，耗时稳定且极短；解析、拆分、指令转换都依赖 LLM，耗时带有明显弹性。同一个剧本运行两次，耗时也可能因模型响应速度、重试与修复回环而不同。

所以性能评测要回答的不是“快不快”，而是：时间花在了哪里，哪些环节可以通过工程手段优化。

一、数据口径

本文使用同一剧本的两次真实任务记录：

数据组 来源 内容
A 组 本地运行产物 data/output/{script_id}/{task_id}/ TSK17807426061109503223（06-11）与 TSK17807426072316085190（07-23），含各阶段落盘时间戳
B 组 仓库文档与系列文章 13 片段、48 秒示例的端到端耗时记录（约 89 秒与约 519 秒）

A 组产物不随源码发布，但字段结构可对照源码核验。每个阶段产物会记录 metadata.saved_at 等时间戳，相邻两次落盘的时刻差，就是该阶段处理与保存所占用的区间。

需要说明：解析阶段自身的耗时无法从产物时间戳直接得出，因为它之前没有可参照的落盘记录。下面的分段耗时覆盖解析之后的五个阶段，区间包含阶段处理与产物序列化保存的开销，不进一步拆分。

二、耗时画像：八成以上时间在 LLM

区间（相邻产物落盘时刻差） 运行 1 运行 2 处理内容
解析产物 → 镜头产物 13.3s 11.0s 镜头拆分（LLM）
镜头产物 → 分段产物 5.5s 4.8s 视频分段（规则直通）
分段产物 → 转换产物 39.0s 36.4s 指令转换（逐片段 LLM）
转换产物 → 审计产物 41.3s 37.8s 质量审查（规则 + LLM）
审计产物 → 连续性产物 6.5s 11.6s 连续性守护
端到端（解析落盘 → 连续性落盘） ≈106s ≈102s —

把整条链路写成一个分解式：

$$
T_{total} \approx T_{parse} + T_{shots} + T_{split} + \sum_{i=1}^{n} T_{convert}^{(i)} + T_{audit} + T_{continuity}
$$

其中 $n$ 为片段数（本剧本 $n=7$），$T_{convert}^{(i)}$ 为第 $i$ 个片段的指令转换耗时。

三个直接结论：

  1. LLM 密集区段吃掉八成以上时间。 运行 1 的镜头拆分、指令转换、质量审查合计 93.6 秒，占端到端 105.6 秒的 88.7%；运行 2 为 83.9%。唯一不含 LLM 调用的视频分段，两次都是最轻的一环。

  2. 质量审查与指令转换是并列大头，审查甚至略高。 41.3 秒对 39.0 秒（运行 2 为 37.8 秒对 36.4 秒）。审查阶段同样包含逐片段的内容复核与 LLM 检查，只盯生成阶段时最容易被忽略。

  3. 指令转换按片段线性扩展。 39.0 秒 ÷ 7 片段 ≈ 5.6 秒/片段（运行 2 为 5.2 秒/片段）。每个片段要生成视觉与音频两组提示词，这个单片段耗时基本就是一次 LLM 往返的实测量级。

但端到端耗时不能按片段数线性推算。同为 13 片段、48 秒的示例，仓库文档记录约 89 秒，另一份记录约 519 秒，相差近 6 倍。波动主要来自 LLM 响应差异与修复回环次数。

pie title 运行 1 相邻产物的区间耗时占比（合计 ≈ 105.6s）
    "质量审查（规则+LLM）" : 41.3
    "指令转换（LLM）" : 39.0
    "镜头拆分（LLM）" : 13.3
    "连续性守护" : 6.5
    "视频分段（规则）" : 5.5

如果要在生产环境压缩耗时，优先级是：质量审查与指令转换 > 镜头拆分。可行手段包括：为这两个阶段选择响应更快的模型、控制参与转换的上下文长度、减少修复回环、用任务级并发配置提升多任务吞吐。PenShot 支持本地 Ollama 与 OpenAI 兼容云 API 两类接入，本地推理的延迟特性与云 API 差异明显，选型应以实测为准。

三、解析质量：场景是最薄弱的一维

两次运行对同一剧本的解析结果高度一致：

  • 7 个元素（3 段对话、3 个动作），总时长 19.0 秒，1 个场景、2 个角色；

  • 完整度 0.87，综合置信度 0.76；

  • 解析一次成功（parse_attempts = 1），两次运行的 stats 字段逐项一致。

把置信度拆开看：

维度 置信度
动作 1.0
角色 0.75
对话 0.67
场景 0.6

动作、角色这类显式且结构化的信息最容易提取；场景往往包含时间、光线、氛围、空间关系等隐式信息，需要模型推断，天然更容易偏。对场景要求高的剧本（如多场景切换的群像剧），人工复核应重点放在场景标注上。

base_repairable_agent.py 还会把历史解析质量分级：平均完整度低于 0.6 标记为 poor，低于 0.8 标记为 medium；poor 时，镜头拆分与视频分段会启用增强验证模式，执行更严格的额外校验。本次完整度 0.87，未触发该模式。

四、质量分：同一剧本可以拉开 18 倍

指标 06-11 运行 07-23 运行
片段数 7 7
总时长 21.89s 23.91s
镜头数 / 场景数 / 角色数 7 / 1 / 2 7 / 1 / 2
审查状态 major_issues minor_issues
质量得分 5.0 90.0
违规项数量 8 4

两次运行的生成规模几乎一致，终审状态与得分却差异显著。这说明质量分更多取决于审查与修复链路对具体违规项的处理，而不是生成规模。

分数怎么算？quality_auditor_agent.py:77-84 的权重表从 100 分起扣：info 0、warning 5、moderate 10、major 25、critical 40、error 60，下限 0。代入两次运行：

  • 运行 1：2 条 major + 3 条 moderate + 3 条 warning → 100 − (2×25 + 3×10 + 3×5) = 5.0

  • 运行 2：2 条 warning + 2 条 info → 100 − (2×5 + 2×0) = 90.0

与产物中的 score 完全吻合。质量得分是一个终审快照；得分偏低时，应结合逐项违规记录与修复历史定位问题，而不是只看总分。

五、资源与存储开销

7 月运行的记忆报告反映了各层级的资源参数：

记忆层级 存储介质 关键参数 本次运行状态
短期记忆 Redis（localhost:6379/1） max_size=20 条、TTL=3600s 已启用
中期记忆 本地摘要持久化 max_tokens=500 已持久化至 data/memory/{script_id}
长期记忆 Chroma 向量库 检索 k=3 已启用

其它可量化的开销：

  • 时间成本：7 片段小剧本两次运行约 102–106 秒；13 片段示例在 89 秒到 8.7 分钟之间波动。中等规模剧本的端到端耗时落在 1 分钟到 10 分钟量级，波动较大。

  • 向量检索：嵌入与检索会引入额外的网络往返或本地推理开销；长期记忆与 RAG 都是可选项，不启用时不会成为启动门槛。

  • 工作流持久化：检查点采用 SqliteSaver，按 script_id / task_id 隔离存储，用于中断恢复。

一个常见误读需要纠正：启用记忆功能（enable_memory=True）不等于 Redis 变成强制依赖。源码 short_term_memory.py 的 _check_redis_availability() 在未配置 Redis URL 或连接失败时都会降级为内存存储加文件持久化，不阻断任务。资源规划应按“LLM 调用（主要成本）+ Redis / 向量库（可选）+ 本地数据目录（必需）”三块分别评估。

六、三条排坑提示

1. 耗时是分钟级，别让同步调用撞上超时墙。 单次中等规模剧本实测在 89 秒到 8.7 分钟之间；长剧本还会放大。同步 HTTP 客户端常见默认超时 30 秒，直接等待结果极易误判为失败。生产环境应使用异步任务接口提交，通过轮询或回调获取结果，并把超时阈值设在实测耗时的 2–3 倍以上。

2. Redis 是可选依赖，连接失败会静默降级。 短期记忆在有 Redis 时写入 Redis（本次实测 redis://localhost:6379/1，max_size=20、TTL=3600s）；未配置 URL 时直接使用内存存储，连接失败时打印告警并降级为内存存储，同时把短期记忆落盘到 data/memory/{script_id}/short_term.json 以便重启恢复。坑点在于：运行看似正常，实际已退化为单进程内存态，多实例部署时各实例的记忆互不可见。排查时不要只看 enable_memory=True，要核对记忆报告中的 redis_enabled 字段与实际连接地址。

3. 数据目录不随源码发布，迁移前记得单独备份。 任务输出、记忆文件、检查点统一落在数据目录下，该目录不进入版本库。更换机器或用容器重新部署时，历史任务、记忆与检查点都需要单独备份与迁移，否则中断恢复能力会静默丢失。

七、结论

耗时结构一句话：LLM 密集区段（镜头拆分、指令转换、质量审查）合计占端到端耗时的 84%–89%，其中质量审查与指令转换贡献最大；中等规模剧本端到端耗时 1–10 分钟且波动明显——优化性能，本质上就是优化这几段 LLM 调用。

质量画像一句话：解析完整度 0.87、置信度 0.76，场景维度（0.6）最薄弱；终审质量分按违规权重从 100 分起扣，同一剧本两次运行可以拉开 18 倍，解读时必须结合审查明细。

给生产实践的三条建议：

  1. 异步优先：以异步任务模式接入，为 LLM 长耗时链路预留足够的超时余量；

  2. 按需启用记忆：评估 Redis 与向量库的部署收益，无记忆需求时明确关闭，减少依赖面；

  3. 备份数据目录：把数据目录纳入备份策略，避免任务历史与检查点丢失。
