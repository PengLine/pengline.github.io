SQLite 多 Worker 为什么会 database is locked：一次 NeoTask 存储边界实测

SQLite 做本地持久化很方便，但在任务队列里，它有一个很明确的边界：单写入者可以，多 Worker 并发写同一个库文件就会撞锁。

NeoTask 1.0.5 的 SQLite 探针把这个问题暴露得很直接：2 个 Worker 从第 37 次提交开始报 database is locked，4 个 Worker 从第 36 次开始。

一、实测结果

测试任务为 noop，每个用例独立重建数据库文件。SQLite 探针是单轮测量，只用于确认边界。

模式 Workers 结果
串行提交 100 条 1 30.1 tasks/s，P50 31.31 ms，P95 66.34 ms，100/100 成功
突发提交 100 条 1 25.5 tasks/s，100/100 成功，0 错误
突发提交 100 条 2 第 37 次提交起 database is locked，33/37 完成，耗时 66.9 s
突发提交 100 条 4 第 36 次提交起 database is locked，34/36 完成，耗时 61.5 s

单 Worker 能跑完，2 个和 4 个 Worker 反而在 36～37 次提交附近卡住。Worker 越多，锁冲突来得越早。

二、锁从哪来

NeoTask 1.0.5 的 SQLite 存储有两个关键实现细节：

  1. SQLiteTaskRepository 和 SQLiteQueueRepository 各自持有一个连接，都指向同一个库文件。

  2. save / push / pop / remove 每次执行后都会 commit()。

再加一条：当前版本没有启用 WAL、busy_timeout 等写并发优化。

于是多个 Worker 同时推进任务时，会出现这样的竞争：

SQLite 同一时刻只允许一个写事务。一个连接拿着写锁提交时，另一个连接的写入只能等待；等不到就抛出 database is locked。任务提交流程被这个异常打断，后面的任务也就无法继续。

注意，这不是“SQLite 的 SQL 太慢”。单条 SQL 并不慢，真正的问题是每次状态变更都要落盘并提交，而且两个连接会反复争抢同一把写锁。

2.1 锁等待只有 5 秒

database is locked 不是“永久死锁”，而是等待超时。Python 的 sqlite3.connect() 默认 timeout=5.0，NeoTask 的 sqlite_compat.create_connection() 没有覆盖这个参数（🔧 utils/sqlite_compat.py:229-242），也没有设置 PRAGMA busy_timeout。所以一个连接拿不到写锁时，最多等 5 秒；5 秒内等不到就抛 OperationalError。

这解释了探针为什么在 36～37 次提交附近“突然”失败：前面的提交还能在 5 秒窗口内轮到自己，积压到一定程度后，单个事务的持锁时间加上排队长度超过 5 秒，异常就开始出现。

2.2 报错之后，已提交的任务也可能卡住

更麻烦的是异常之后的现场。2 Worker 用例里，探针成功提交了 37 条，但在 60 秒等待窗口内只完成 33 条；4 Worker 用例提交 36 条、完成 34 条。也就是说，一次 database is locked 不只让当次提交失败，还会让一部分已经入队的任务迟迟走不完状态写回——队列 pop、状态置 RUNNING、结果写回，每一步都要抢同一把写锁。

所以监控上不能只盯“提交错误数”。提交接口报错只是最外层症状，真正的恢复往往要把积压任务跑完或重建库文件；探针里 66.9 秒、61.5 秒的墙钟时间，大部分花在等这批残留任务上，而不是提交本身。

三、为什么 1 个 Worker 反而稳定

单 Worker 时，任务状态写入和队列操作基本被串行化，写锁不会同时被两个执行流争抢。代价是吞吐低：

  • 串行提交约 30.1 tasks/s；

  • 突发提交约 25.5 tasks/s；

  • P50 约 31 ms，P95 约 66 ms。

这个数字要和 Memory 后端分开看：

口径 Memory SQLite 差距
串行往返 64.3 tasks/s，P50 15.50 ms 30.1 tasks/s，P50 31.31 ms 约 2.1×
noop 完成吞吐 2,433 tasks/s 30.1 tasks/s 约 81×

串行口径下只慢约 2 倍，是因为两边都在“提交一个、等一个”。但一到批量完成场景，SQLite 每次状态变更都落盘的代价就被放大到约 81 倍。这不是调 prefetch_size 能解决的问题。

四、应该怎么选

场景 后端 配置
可丢、追求吞吐 Memory storage_type="memory"
本地持久化、低频写入 SQLite worker_concurrency=1，低提交频率，不突发
高并发、分布式、多进程 Redis storage_type="redis" + neotask[redis]

SQLite 本地持久化的起点配置：

无论哪个平台都建议显式传绝对路径。1.0.5 的 sqlite_path 默认值是 /data/neotask.db（🔧 models/config.py:167、:227）；在 Windows 上它会被解析到当前盘符根目录（通常是 C:\data\neotask.db），既不在项目目录，也可能受目录权限影响。排查时发现"数据没写进去"，先看这个路径。

如果你的业务确实需要高并发写入，正确做法是换后端，而不是在 SQLite 上继续叠 Worker。需要分布式或多进程时，用 Redis；只需要本地持久化且写入频率不高时，SQLite 单 Worker 足够。配置方式见官网《持久化存储》与《配置参考》。

顺带澄清一个常见误区：想通过配置打开 WAL 或调大 busy_timeout。1.0.5 的 TaskPoolConfig 没有暴露这类 SQLite PRAGMA 选项，create_connection() 也不额外传 timeout（🔧 utils/sqlite_compat.py:229-242）。即便在进程启动时自己对同一个库文件执行 PRAGMA journal_mode=WAL，也只是缓解读写互斥，改变不了“两个连接、逐次 commit”的写入结构，而且不在 NeoTask 的支持契约里——升级或换机器后都要重新验证。

如果你在生产日志里看到同样的异常，先记录四个字段：Worker 数、失败时的提交序号、已提交但未完成的任务数、从开始到放弃的墙钟时间。这四个字段能区分“偶发冲突”和“结构性写锁瓶颈”——前者重试可能过去，后者只能换后端或降并发。

需要明确的边界：

  • 这是单轮探针，不是稳定吞吐测试；数字用来确认“会不会锁”，不是容量规划依据。

  • 任务体是 noop，测的是存储写入链路，不包含真实业务执行时间。

  • 结论针对 NeoTask 1.0.5 当前的 SQLite 实现与默认设置；如果未来版本启用 WAL、busy_timeout 或批量提交，边界会变化，应以当时源码和实测为准。
