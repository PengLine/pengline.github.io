3000 个 waiter 只剩 31% 吞吐：NeoTask 结果回收的隐藏成本

任务提交得很快、执行也不慢，为什么整体吞吐还是上不去？

有一种很容易被忽略的原因：结果回收方式本身有成本。 在 NeoTask 1.0.5 的实测里，同样 3,000 个任务，改用 3,000 个并发 waiter 之后，完成吞吐只剩事件口径的约 31%。

一、同一批任务，两种回收方式

测试条件：3,000 个 noop 任务，10 个 Worker，Memory 后端。

结果回收方式 速率 P50 P95 P99
订阅 task.completed 事件 2,433/s 790.21 ms 869.05 ms 881.74 ms
3,000 个并发 wait_for_result_async 759.6/s 3,249.06 ms 3,680.70 ms 3,700.06 ms

事件口径能跑到 2,433 tasks/s，waiter 口径只有 759.6 tasks/s。P50 从 790 毫秒变成 3.2 秒，P99 从 882 毫秒变成 3.7 秒。

任务还是那批任务，执行器也没有变慢。变慢的是“等结果”这件事。

二、waiter 的成本结构

TaskFuture.wait 本身是事件驱动的，不是轮询：1.0.5 为每个等待循环创建一个 asyncio.Future，登记在 (loop, future) 列表里；任务完成时由 FutureManager 在锁内 set_result，再通过 loop.call_soon_threadsafe 唤醒对应循环（🔧 core/future.py:20-117）。这一段明确不用 asyncio.Event，就是为了修复跨事件循环的唤醒丢失。

但 wait_for_task 在 Future 之上又套了一层存储回查：它按 0.2 秒的时间片调用 future.wait(0.2)，每次超时后直接读仓储确认任务是否已在别的节点完成，直到终态或总超时（🔧 core/lifecycle.py:351-406）。于是每个 waiter 的完整路径是：

  1. wait_for_task 先查一次任务状态，确认还没完成；

  2. 在 FutureManager 字典里获取或创建一个 TaskFuture；

  3. future.wait(0.2) 挂起；0.2 秒内没完成就醒来，回查一次仓储，再挂起，循环往复；

  4. 任务完成时，FutureManager.complete() 在锁内 set_result，并通过 call_soon_threadsafe 唤醒对应循环；

  5. asyncio.gather 负责调度这几千个等待协程。

3,000 个 waiter 意味着：

  • 3,000 次初始状态查询；

  • 每秒约 15,000 次 0.2 秒回查（3,000 ÷ 0.2），直到任务完成；

  • 3,000 个等待协程同时挂起；

  • 3,000 份 Future 注册、查找和唤醒；

  • 3,000 个超时定时器；

  • 一次 gather 同时管理 3,000 个任务。

单个操作都不重，但回查是按 waiter 数量线性放大的：任务完成得越慢，回查次数越多。这正是"等待方式本身有成本"的具体来源——不是任务执行变慢，而是几千个等待者把调度器和存储读接口一起拖进了忙循环。

要特别区分两件事：

  • 任务执行吞吐下降：执行器或 Worker 不够；

  • 结果回收吞吐下降：等待方式本身开销过大。

这里的 759.6 tasks/s 属于后者。把 waiter 换成事件，任务执行能力并没有变化，变化的是结果回收路径。

2.1 本地 Future 之外，为什么还要回查仓储

FutureManager 的唤醒只发生在执行任务的节点：任务完成时，执行节点调用 complete()，本节点登记的 Future 才会被唤醒。跨节点部署时，等待方根本没有执行这个任务，本地 Future 收不到任何通知。wait_for_task 因此保留 0.2 秒时间片回查，并且绕过生命周期缓存直接读仓储——源码注释写得很直白：“跨节点执行时本地缓存可能仍是 PENDING”（🔧 core/lifecycle.py:355-406）。

这道回查是跨节点正确性的代价，不是实现偷懒。它也解释了为什么在单机、全内存的基准里 waiter 仍然每 0.2 秒查一次存储：代码路径不会因为“同节点”而跳过回查。

2.2 换成 SQLite 会更糟

上面算出的每秒约 15,000 次回查，在 Memory 后端只是字典查找；换成 SQLite，每次都是走同一条数据库连接的 SELECT。而 Worker 的状态写回也走这条连接（SQLiteTaskRepository 单连接，所有操作投递到专用 loop 串行执行，🔧 utils/sqlite_compat.py:125-145），读得越多，写状态排在后面的机会越大。

这也是为什么“大量 waiter + SQLite”是个应该避开的组合：SQLite 本身在几十次并发提交内就会撞 database is locked（见 SQLite 边界实测），再叠加每秒上万次结果回查，等待方会实打实地和 Worker 抢同一条连接。要么换 Memory/Redis，要么把等待方式改成事件或分片。

三、什么时候用事件，什么时候用 waiter

需求 推荐方式 原因
观测、计数、统计、日志 on_completed / task.completed 不需要逐个结果，事件回调最轻
批量编排，只关心全部完成 事件 + 计数器 避免为每个任务创建 waiter
必须逐个拿返回值 有界分片 gather 控制同时挂起的 waiter 数量
任务量很小（几十个） wait_for_result_async 开销可接受，代码更直观

判断标准不是“能不能等”，而是同时挂起多少个 waiter。几十个没问题，几千个就要换方式。

四、推荐写法

4.1 观测和统计：用事件

事件回调运行在 TaskPool 的事件循环上，所以只做计数、入队、标记这类轻量操作。不要在回调里做重 IO，也不要 await 长任务，否则会直接拖慢完成管线。

4.2 必须逐个取结果：用有界分片

分片大小从 100～300 起测。它的目标不是让等待“更快”，而是把同时挂起的 waiter 数量控制在可接受范围。

4.3 不要做的三件事

  1. 不要一次挂起数千个 waiter。 这是本组数据里吞吐掉到 31% 的直接原因。

  2. 不要在事件回调里做重活。 回调在 TaskPool 的事件循环里执行，会阻塞其他事件。

  3. 不要指望 submit_batch_async / wait_all_async 并行。 它们内部是顺序 for 循环；wait_all_async 在超时时还会逐个等待，长尾会被放大。大批量请用上面的分片 gather。

五、怎么验证

用同一批任务、同一组 Worker，分别跑两种回收方式：

  • A：只订阅 task.completed，用计数器判断全部完成；

  • B：把 3,000 个 wait_for_result_async 一次性交给 gather。

对比完成吞吐和 P95/P99。如果 B 的吞吐明显下降、但任务执行时间没变，基本就是等待方式的开销。

六、边界

  • 数据来自单台 Windows 10 笔记本，Memory 后端、noop 任务、10 个 Worker；绝对值不能直接外推。

  • 759.6 tasks/s 是“3,000 个并发 waiter”这一种回收方式的结果，不代表 NeoTask 的任务执行上限。

  • 任务执行时间变长后，waiter 的相对开销会下降；但“不要一次挂几千个 waiter”这个原则仍然成立。
