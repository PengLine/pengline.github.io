1697 ops/s 与 2,433 tasks/s 为什么不能直接比：任务队列性能口径拆解

看到两个性能数字，第一反应通常是“哪个快”。但在任务队列里，这个问题经常是错的。

官网旧版 benchmarks 页面出现过 1697 ops/s 和持续负载 64.6 ops/s；NeoTask 1.0.5 的新基准里，完成吞吐是 2,433 tasks/s，持续负载是 2,565 tasks/s。把它们放在一起说“快了 1.4 倍”或“快了 40 倍”，都不严谨。

原因不是谁测错了，而是它们回答的不是同一个问题。

一、先看两组数字分别是什么

项目 旧版 benchmarks 页面 NeoTask 1.0.5 新基准
版本 v1.0.2 / v0.3.0 1.0.5
场景规模 12 项基准 15 个主套件场景 + 1 组队列微基准 + 4 个 SQLite 边界用例
存储 SQLite 未测 Memory 主套件 + SQLite 独立探针
计时方式 旧版脚本采用过 0.5 秒垫时、0.00 ms 埋点等做法 实际壁钟为分母，多轮取中位数
典型数字 1697 ops/s、64.6 ops/s 提交 14,657/s、完成 2,433/s、持续 2,565/s

仅看这张表就能发现：版本、场景数量、存储后端和计时方式都变了。此时直接比较两个数字，等于把不同实验条件下的结果混在一起。

二、五个不可比因素

1. 版本不同

v1.0.2 / v0.3.0 与 1.0.5 之间经历过多次实现调整。调度、存储、预取、结果回收中的任何一处变化，都会影响吞吐。跨版本比较只能说明“新版本在某场景下更快或更慢”，不能说明“旧数字是错的”。

2. 统计对象不同

任务队列至少有四种口径：

口径 计时起点 计时终点 回答的问题
提交吞吐 第一个 submit_async 第 N 个 submit_async 返回 创建、落库、入队有多快
完成吞吐 第一个提交 第 N 个 task.completed 事件 排队、执行、状态写回、事件通知的整体能力
单任务延迟 单任务提交前 该任务完成 无积压时一次往返要多久
等待吞吐 N 个 waiter 开始等待 N 个 wait_for_result_async 返回 结果回收方式本身的开销

旧页面的 1697 ops/s 是被固定 0.5 秒垫时稀释过的提交端速率：分子是已提交任务数，分母含脚本里的 0.5 秒等待，既不统计执行完成，也没有真实的延迟埋点（那一列恒为 0.00 ms）。新页面的 2,433 tasks/s 则是“完成事件口径”。一个只到提交返回，一个到任务完成，中间还混着固定垫时，起点和终点都不同。

3. 负载与配置不同

新基准关闭了 metrics、health check、reporter、reclaimer、heartbeat、dead letter 和 retry，避免旁路组件污染结果；任务体是 noop，Worker 数为 10。旧版页面的测试配置、任务体、预热方式和并发上限不一定相同。

哪怕只改一个 prefetch_size，短任务吞吐就可能差一个数量级：关闭预取 2,382 tasks/s，默认预取 181 tasks/s。配置不写清楚，数字就没有可比性。

4. 计时方式不同

新基准强调“所有速率以实际壁钟为分母，不写死名义时长”，并且主套件重复 2～3 轮取中位数。旧版脚本采用过 0.5 秒垫时、0.00 ms 埋点这类做法；这些做法在旧场景下有其原因，但不能和新口径直接拼接。

5. 环境与存储不同

新数据来自 Windows 10 笔记本、Python 3.13.15、i7-1165G7；主套件用 Memory 后端，SQLite 另做边界探针。旧页面的机器、Python 版本和存储配置未必相同。SQLite 与 Memory 的差距本身就可能达到两个数量级，混在一起比较没有意义。

三、正确的比较方式

如果你确实想比较两版性能，至少固定这些条件：

  1. 同一版本：不要拿 v1.0.2 的数字和 1.0.5 的数字直接比。

  2. 同一台机器：CPU、OS、Python 版本、磁盘类型都记录清楚。

  3. 同一份配置：Worker 数、预取、存储后端、旁路组件开关全部固定。

  4. 同一种口径：提交就比提交，完成就比完成，不要拿提交吞吐打完成吞吐。

  5. 同样的预热与轮次：预热 ≥ 1 秒，重复 2～3 轮取中位数。

  6. 保留原始数据：每轮结果、失败数、P50/P95/P99 都要留下。

只有这六项对齐，数字才有比较价值。

四、旧数字不是“错”，只是“回答了另一个问题”

旧版 benchmarks 页面在它对应的版本、环境和脚本下，仍然是有信息量的：

  • 它说明了当时队列微基准与提交端速率的量级差异（1697 是被 0.5 秒垫时稀释的提交端口径，不度量执行）；

  • 它暴露过 Worker 扩展性、Windows 定时器粒度等问题；

  • 它帮助读者理解“队列很快”不等于“端到端很快”。

新版 1.0.5 基准做的是另一件事：把提交、完成、延迟、等待四种口径拆开，补充 SQLite 边界，并用多轮中位数降低单轮波动影响。

所以更准确的表述是：

旧数据回答的是“v1.0.2 / v0.3.0 在旧脚本下表现如何”；新数据回答的是“1.0.5 在当前四类口径下表现如何”。
两者可以对照阅读，但不能直接换算成倍数。

五、读性能数字的检查清单

下次看到任务队列的性能宣传，先问五个问题：

  1. 这是提交吞吐、完成吞吐，还是等待吞吐？

  2. 计时从哪里开始，到哪里结束？

  3. 任务体是什么？noop、20 ms IO，还是真实业务？

  4. 存储后端是什么？Memory、SQLite，还是 Redis？

  5. 版本、机器、配置和轮次是否写清楚？

如果这五个问题答不上来，那个数字就只适合当背景信息，不适合做选型依据。

六、一个可复用的记录模板

与其争论“哪个数字更真”，不如把每次压测的环境固定成一张表。下面这份字段清单可以直接抄进 README 或发布说明：

类别 必须记录
版本 包版本 + commit；是否与文档基线一致
环境 CPU 型号、内存、OS、Python 版本、磁盘类型
配置 Worker 数、prefetch_size、存储后端、metrics/health/reporter/reclaimer/heartbeat/dead letter 开关
负载 任务体（noop / 固定 IO / 真实业务）、优先级分布、是否重试
规模 N、预热条数、轮次、每轮时长
口径 计时起点、计时终点、速率分母（壁钟还是名义时长）
结果 吞吐、P50/P95/P99、失败数、错误类型
原始数据 每轮 JSON 或 CSV 的存放位置

这张表的价值在于：它让“不可比”变成可检查的项。下次有人拿两个数字做对比，逐项对一遍，哪一项不同、差多少，一眼就能看出来。比起在评论区争论“你这测试不准”，把差异摊开是更有效也更体面的做法。
