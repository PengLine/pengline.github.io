PenShot 省 Token 指南：哪些优化真的生效了

版本基线：本文以 PenShot 0.3.9（2026-10-13）源码为核对基线。文中只陈述代码里能追到的行为；没有实测数据的比例数字一律不写。

相关链接：PenShot 官网 | GitHub | 核心实现

做长剧本分镜，Token 成本很容易失控：解析要读整段剧本，提示词转换要按片段逐个调用，质量审查还要再读一遍。一个中等长度的电影剧本走完整条链路，调用次数和输入长度都不小。

于是“省 Token”成了很自然的目标。但工程文章里最常见的问题，是把“计划做”写成“已经做”，再配一个看起来很精确的百分比。本文换一种写法：只按源码核对，哪些机制真的在跑、哪些只是装配好了但没接线、哪些还停留在路线图上。

一、Token 花在哪：三个放大器

PenShot 的主链路是：

剧本解析 → 镜头拆分 → 视频分段 → 指令转换 → 质量审查 → 连续性守护

Token 消耗集中在三个环节：

  1. 剧本解析：整段剧本作为输入，是单次输入最大的一环；

  2. 指令转换：每个片段生成视觉与音频两组提示词，调用次数随片段数线性增长；

  3. 质量审查：规则审查之外还有 LLM 审查，每个片段都要进入审查上下文；一旦触发修复回环，还会产生额外调用。

flowchart TD
    A[原始剧本] --> P1[剧本解析]
    P1 --> P2[镜头拆分]
    P2 --> P3[视频分段]
    P3 --> P4[提示词转换]
    P4 --> P5[质量审查]
    P5 -->|发现问题| R[修复 / 重试]
    R --> P4
    P5 -->|通过| O[输出分镜]

真正的“放大器”是重试循环：一次审查失败可能触发多轮 LLM 调用。所以省 Token 的关键不只是压输入，更是减少无效重复调用。

二、已经在跑的机制

1. 逐片段审查时截断提示词

质量审查不会把完整提示词原样塞进 LLM。llm_quality_auditor.py:66-70 对每个片段只保留前 300 个字符：

这是实打实的输入裁剪。代价是审查器看不到提示词后半段；如果关键信息恰好被截掉，语义审查会失真。它省的是审查阶段的 Token，不是生成阶段的。

2. 质量审查结果的短期复用

LLMQualityAuditor._should_run_llm_audit()（llm_quality_auditor.py:178-186）有三个条件：从未审过、距上次超过 300 秒、片段数量变化。三者都不满足时，直接复用上一次的 LLM 审查结果。

这不是跨任务缓存，而是同一个 auditor 实例内的短期复用。它减少的是“同一批片段反复审查”的重复调用，不会减少首次审查的成本。

3. 规则检查与条件分支

视频分段有一条明确的分流：只有时长超过 5.5 秒的镜头才交给 LLM 做语义分割，其余按规则直通（rule_video_splitter.py:29）。小剧本的 7 个镜头全部落在直通区间，整个分段阶段没有 LLM 调用。

工作流还有条件边：质量审查通过就继续，不通过才进入修复；连续性检查无问题就输出，有问题才重试。能由确定性代码判定的分支，不再额外调用 LLM。

4. 短期记忆的滑动窗口

短期记忆用 deque(maxlen=20) 维护最近 20 条消息（short_term_memory.py:54），Redis 侧 TTL 默认 3600 秒。超过窗口的记录自动淘汰，不会无限膨胀。

5. 中期摘要与长期检索

中期记忆每次写入都会更新摘要：新内容先按 max_token_limit * 4 截断，摘要再按 max_token_limit * 2 截断，max_token_limit 默认 500（memory_models.py:40）。长期记忆检索默认取前 3 条（memory_models.py:45）。

但要看清一个边界：长期记忆的语义读取链路在生产中没有调用方。get_context_for_llm 与 restore_context_for_stage 只有定义，没有生产调用（详见《召回评测》）。所以“三层记忆把上下文压到 2000 Token 以内”这类说法，在当前版本里不能当作已实现事实——摘要确实在写，语义读取并没有接上消费端。

6. 提示词模板复用

convert_prompt 节点会对每个片段调用 enhance_prompt（workflow_nodes.py:576），在模板库中检索相似模板，命中后把模板追加到原提示词后面。参数是 top_k=1、min_score=0.7。

注意：append 模式会把模板拼进去，输入 Token 是增加而不是减少。它解决的是“复用成功经验、提升稳定性”，不是“省 Token”。如果模板本身很长，反而会推高单片段成本。把它归到“质量优化”比归到“成本优化”更准确。

三、已实现但没接线

1. 长剧本分块

LongScriptChunker 已经实现（long_script_chunker.py:43）：按场景数（默认 30）、总时长（默认 180 秒）分块，块间保留 3 个重叠场景，用于连续性检查。

但全仓库没有生产调用方。当前工作流仍然假设剧本能一次性进入解析链路。这意味着超长剧本的 Token 峰值问题还没有被这个分块器解决——能力在仓库里，链路没接。

2. 重排序与 MMR

create_retriever_for_script 支持 BGE 重排序与 MMR 分支，use_rerank=True 的调用也出现在 knowledge_manager.py:81 和 prompt_template_manager.py:511。但生产路径的 query() 是手写余弦检索，函数体不读取 use_rerank / search_type。参数传了，重排序不会发生。

所以“重排序把候选从 15–20 条压到 3–5 条，从而省上下文”这条链路，在 0.3.9 的生产路径里不成立。

3. LLM 缓存

base_llm_agent.py:98 有缓存判断，但 client_config.py:101 把 enable_llm_cache 默认设为 False，注释是“LLM 输出不稳定”。也就是说，默认配置下相同提示词不会命中缓存。

想用缓存省 Token，需要显式开启，并接受“相同提示词复用旧输出”的语义风险。对创作类任务，这个取舍要谨慎。

四、还在路线图上的

以下方向在项目文档或 CHANGELOG 的 Unreleased 里出现过，但当前代码没有完整实现，不能计入“已生效”：

  • 批量调用：把解析、拆分等独立调用合并成批量请求；

  • 模型路由：按任务难度分派大小模型；

  • 增量处理：只重跑剧本变更部分；

  • 输出长度自适应：按目标视频模型的偏好动态调整提示词长度；

  • 解析结果缓存：对相同或相似剧本复用历史解析。

这些方向都合理，但在落地前，文章里不应给出“减少 30%–40%”之类的确定数字。没有测量就没有比例。

五、怎么测量，而不是怎么宣称

想认真做成本优化，先补三件事：

  1. 记录每次 LLM 调用的输入/输出 Token 与阶段归属。 没有这个埋点，所有优化都是感觉；

  2. 统计每个阶段的调用次数。 指令转换阶段的理论调用次数≈片段数×2（视觉 + 音频），实际次数与理论值的差额就是重试与修复的成本；

  3. 记录缓存命中与审查复用次数。 否则无法判断“缓存到底省了多少”。

有了这三组数据，优化顺序会很清晰：

  • 先看重试回环：一次失败触发的额外调用，往往比压缩提示词更贵；

  • 再看指令转换的上下文长度：是否把不必要的全量剧本/历史都带进了每个片段；

  • 然后看审查阶段：300 字符截断是否足够，是否需要分级审查；

  • 最后才考虑记忆与检索：在语义读取接线之前，不要指望它显著降低上下文。

六、结论

把“省 Token”拆成三句话：

  1. 已生效的：审查提示词截断、审查结果 300 秒复用、规则分流跳过 LLM、短期 20 条窗口、中期摘要、模板复用（质量向，不是成本向）；

  2. 未生效的：长剧本分块、重排序/MMR、默认关闭的 LLM 缓存；

  3. 别提前记账的：批量调用、模型路由、增量处理、解析缓存。

成本优化不是单一手段的胜利，而是“输入端压缩 + 调用端去重 + 模型端分级”的组合拳。但在 PenShot 当前版本里，最值得先做的不是加新策略，而是把重试回环和调用次数测清楚——先知道钱花在哪，再谈怎么省。
