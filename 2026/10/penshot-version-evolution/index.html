PenShot 版本演进：从 MVP 到 0.3.x 的五次转向

版本基线：本文以仓库 pyproject.toml 的 0.3.9 为当前安装包版本，结合 Git 提交记录、Release 标签与 CHANGELOG.md 还原演进过程。仓库另有 v0.3.10 的 release 提交，版本号请以实际安装包与 Release 页为准。

相关链接：PenShot 官网 | GitHub | CHANGELOG

开源项目的版本演进很容易被写成一条平滑上升的曲线：v0.1 打基础，v0.2 加功能，v1.0 走向成熟。真实的 Git 历史通常不是这样。

PenShot 从 2025 年 10 月 23 日的第一个提交开始，到 2026 年 10 月的 0.3.9，经历了五次比较明显的转向。有的来自能力扩展，有的来自线上问题倒逼，有的来自部署形态变化。本文按可核对的记录，把“已发布”“已实现未接线”“仍在路线图”分开讲。

一、时间线：一年内的五次转向

时间 阶段 关键变化
2025-10 项目启动 创建“剧本分镜”项目，搭建智能体与提示词骨架
2025-11 连续性与状态机 引入 Chroma 向量记忆、状态机，增强连续性守护
2026-04 0.3.0 发布线 六节点流水线、任务层拆分、RAG 知识库逐步成形
2026-05 记忆与知识库 剧本级数据隔离、三层记忆、短期记忆文件持久化
2026-09 稳定性补课 规则解析兜底、长期记忆阈值修复、OpenAI 兼容客户端
2026-10 部署收敛 Docker 镜像精简、0.3.9 / 0.3.10 发布提交

下面按转向拆开。

二、第一次转向：先跑通流水线

项目最早的提交集中在“把剧本变成结构化数据”：统一提示词、引入 LlamaIndex、增加剧本语法解析器、定义动作/情绪/角色等字段。

这一阶段最重要的决策不是某个模型，而是强类型数据契约：节点之间传 Pydantic 模型，而不是自由文本。解析结果、镜头、片段、提示词指令各有明确结构，后续的校验、修复、落盘才有抓手。

到 0.1.0，MVP 已经具备：

  • 剧本解析、镜头拆分、5 秒级片段切割、提示词生成；

  • REST API、MCP Server、Python SDK、CLI 四条接入路径；

  • 质量审查与连续性守护的雏形。

这也是后来所有能力的地基：先让链路跑通，再谈智能增强。

三、第二次转向：质量与连续性

流水线跑通后，问题很快从“能不能拆”变成“拆得对不对”。

2025 年 11 月的提交“新增向量记忆（chromadb）+ 状态机，增强连续性守护智能体功能”，标志着系统开始处理跨片段一致性：角色、场景、道具不能在每个片段里重新发明一遍。

随后补上的是质量审查与检查点：

  • 质量审查从单一规则检查扩展为规则 + LLM 的合并审查，按严重度扣分；

  • 连续性检查从“看一眼”变成带问题分类、修复参数与重试上限的独立阶段；

  • 工作流检查点用 SqliteSaver 按 script_id / task_id 落盘，支持中断恢复。

这一阶段的核心认知是：多智能体系统的质量，取决于失败路径设计，而不只是主路径。 修复参数、重试次数、人工干预阈值，和提示词本身一样重要。

四、第三次转向：RAG 与三层记忆

2026 年 4 月至 5 月，项目进入“知识增强”阶段。提交记录里可以清楚看到几条线：

  • 剧本知识库按剧本 ID 做目录隔离、索引隔离、向量存储隔离和查询隔离；

  • 提示词模板库支持相似模板检索，命中后增强当前提示词；

  • 三层记忆成形：短期 Redis（或内存降级）、中期 LLM 摘要 + JSON、长期 Chroma；

  • 短期记忆增加文件持久化，用于 Redis 不可用时重启恢复。

这一阶段也留下了后面要补的坑：长期记忆的距离/相关度阈值比较错误、中期摘要读写文件名不一致、重排序装配没有接入生产查询路径。这些不是“设计失败”，而是“能力先落地、接线后补”的典型代价。

五、第四次转向：稳定性补课

2026 年 9 月是一次明显的“补课期”，Release 0.3.8 与 0.3.9 集中处理稳定性与兼容性：

  • 规则解析兜底：LLM 连接失败或解析异常时，自动回退到本地规则解析。效果会打折扣，但任务不再直接失败；

  • 长期记忆修复：把 Chroma 返回的距离换算成相关度，再与阈值比较，修复“结果恒为空”的问题；

  • 记忆会话维护：移除已弃用的 RunnableWithMessageHistory，改为直接维护会话历史；

  • 模型兼容：LLM 客户端支持 OpenAI 兼容的 Chat 接口，默认配置与超时时间同步调整；

  • Redis 配置修正：连接地址与超时配置在 9 月中旬的多笔提交中修正。

这一阶段的主题不是“加能力”，而是“让已有能力在真实环境里稳定工作”。对开源项目来说，这类提交往往比新功能更重要。

六、第五次转向：部署形态收敛

2026 年 8 月底到 10 月，部署链路快速收敛：

  • GitHub Actions 增加 Docker 构建与推送；

  • 镜像从 GHCR 扩展到 Docker Hub，提供 neotems/penshot 与 ghcr.io/neopen/penshot 两个来源；

  • 镜像基于 python:3.11-slim，以非 root 用户运行，缩减体积；

  • 文档补齐 .env、命令行 -e、Compose 三种配置方式，以及 Redis 可选依赖的说明。

这一步让 PenShot 从“能 pip 安装的库”变成“能直接起服务的应用”。对使用者来说，部署成本往往比模型能力更早决定是否试用。

七、哪些是已发布，哪些还没接线

版本文章最容易犯的错误，是把仓库里存在的代码当成已发布能力。按 0.3.9 复核，边界大致如下：

已发布且在链路中生效

  • 六节点流水线与条件分支；

  • 规则 + LLM 质量审查、连续性检查、检查点恢复；

  • 提示词模板检索与增强；

  • 三层记忆写入（短期 / 中期 / 长期）；

  • REST、MCP、SDK、CLI、Docker。

代码已实现，但生产链路未接线

  • LongScriptChunker 长剧本分块：默认 30 场景 / 180 秒 / 3 场景重叠，但工作流没有调用；

  • create_retriever_for_script 的 BGE 重排序与 MMR 分支：只在未接线的 KnowledgeRouter 中使用；

  • get_context_for_llm / restore_context_for_stage 记忆语义读取：只有定义，没有生产调用。

仍在路线图 / Unreleased

  • Redis 任务持久化的进一步增强、批量处理接口；

  • Web UI 演示界面；

  • 多智能体流水线中的独立“质量审查智能体”形态；

  • 批量调用、模型路由、增量处理等成本优化方向。

这些方向在 CHANGELOG.md 的 Unreleased 或项目文档里出现过，但在落地并接线之前，不应写进“已支持”。

八、三次架构决策的复盘

回看这一年，真正影响后续形态的决策有三个。

1. 用 LangGraph 承载状态机，而不是手写循环。 分支、重试、路由、检查点都交给图引擎，节点只关心自己的输入输出。代价是要理解条件边与状态合并，收益是失败路径可以被显式表达。

2. 用强类型模型做节点契约。 解析、镜头、片段、提示词都有结构，校验和修复才有抓手。代价是模型演进时要维护兼容性，收益是“自由文本智能体”常见的不稳定被大幅收敛。

3. 把增强能力做成可裁剪模块。 RAG、三层记忆、Redis、重排序都不是启动硬依赖；没有它们，主链路仍能跑。代价是“能力存在但未接线”的状态会长期存在，收益是部署门槛低、故障面可控。

九、结论

PenShot 的版本演进可以概括为：

  1. 先跑通：强类型契约 + 六节点流水线；

  2. 再补质量：审查、连续性、检查点；

  3. 再加知识：RAG、三层记忆、模板复用；

  4. 然后补稳定性：规则兜底、记忆修复、模型兼容；

  5. 最后收敛部署：Docker、镜像、配置方式。

版本号会继续增长，但这五次转向留下的结构不会轻易改变。判断一个新能力是否真的“支持”，不要看功能列表，去看它有没有生产调用方、有没有端到端测试、有没有在真实产物里留下痕迹。
