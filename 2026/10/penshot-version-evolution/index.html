PenShot 版本演进：从 MVP 到 0.4.x 的七次转向

PenShot 版本演进：从 MVP 到 0.4.x 的七次转向

版本基线（2026-11-17 更新）：本文初版以 0.3.9 为基线，现按当前最新补丁版 v0.4.5（2026-11-14）复核，并结合 v0.4.0–v0.4.5 的 Release 与提交记录补全演进过程。版本号请以实际安装包与 Release 页为准。

相关链接：GitHub | CHANGELOG

开源项目的版本演进很容易被写成一条平滑上升的曲线：v0.1 打基础，v0.2 加功能，v1.0 走向成熟。真实的 Git 历史通常不是这样。

PenShot 从 2025 年 10 月 23 日的第一个提交开始，到 2026 年 11 月的 v0.4.5，经历了七次比较明显的转向。有的来自能力扩展，有的来自线上问题倒逼，有的来自部署形态变化。本文按可核对的记录，把“已发布”“已实现未接线”“仍在路线图”分开讲。

一、时间线：一年内的七次转向

时间 阶段 关键变化
2025-10 项目启动 创建“剧本分镜”项目，搭建智能体与提示词骨架
2025-11 连续性与状态机 引入 Chroma 向量记忆、状态机，增强连续性守护
2026-04 0.3.0 发布线 六节点流水线、任务层拆分、RAG 知识库逐步成形
2026-05 记忆与知识库 剧本级数据隔离、三层记忆、短期记忆文件持久化
2026-09 稳定性补课 规则解析兜底、长期记忆阈值修复、OpenAI 兼容客户端
2026-10 部署收敛 Docker 镜像精简、0.3.9 / 0.3.10 发布提交
2026-11 目标模型适配 0.4.0 适配层、0.4.1 连续性约束、0.4.2 资产计划
2026-11 路由与质量收口 0.4.3 模型路由、0.4.4 连续性闭环、0.4.5 分镜缺陷修复

下面按转向拆开。

二、第一次转向：先跑通流水线

项目最早的提交集中在“把剧本变成结构化数据”：统一提示词、引入 LlamaIndex、增加剧本语法解析器、定义动作/情绪/角色等字段。

这一阶段最重要的决策不是某个模型，而是强类型数据契约：节点之间传 Pydantic 模型，而不是自由文本。解析结果、镜头、片段、提示词指令各有明确结构，后续的校验、修复、落盘才有抓手。

到 0.1.0，MVP 已经具备：

  • 剧本解析、镜头拆分、5 秒级片段切割、提示词生成；

  • REST API、MCP Server、Python SDK、CLI 四条接入路径；

  • 质量审查与连续性守护的雏形。

这也是后来所有能力的地基：先让链路跑通，再谈智能增强。

三、第二次转向：质量与连续性

流水线跑通后，问题很快从“能不能拆”变成“拆得对不对”。

2025 年 11 月的提交“新增向量记忆（chromadb）+ 状态机，增强连续性守护智能体功能”，标志着系统开始处理跨片段一致性：角色、场景、道具不能在每个片段里重新发明一遍。

随后补上的是质量审查与检查点：

  • 质量审查从单一规则检查扩展为规则 + LLM 的合并审查，按严重度扣分；

  • 连续性检查从“看一眼”变成带问题分类、修复参数与重试上限的独立阶段；

  • 工作流检查点用 SqliteSaver 按 script_id / task_id 落盘；但恢复入口与稳定 thread_id 直到 v0.4.5 仍未接通，"支持中断恢复"的目标没有兑现。

这一阶段的核心认知是：多智能体系统的质量，取决于失败路径设计，而不只是主路径。 修复参数、重试次数、人工干预阈值，和提示词本身一样重要。

四、第三次转向：RAG 与三层记忆

2026 年 4 月至 5 月，项目进入“知识增强”阶段。提交记录里可以清楚看到几条线：

  • 剧本知识库按剧本 ID 做目录隔离、索引隔离、向量存储隔离和查询隔离；

  • 提示词模板库支持相似模板检索，命中后增强当前提示词；

  • 三层记忆成形：短期 Redis（或内存降级）、中期 LLM 摘要 + JSON、长期 Chroma；

  • 短期记忆增加文件持久化，用于 Redis 不可用时重启恢复。

这一阶段也留下了后面要补的坑：长期记忆的距离/相关度阈值比较错误、中期摘要读写文件名不一致、重排序装配没有接入生产查询路径。这些不是“设计失败”，而是“能力先落地、接线后补”的典型代价。

五、第四次转向：稳定性补课

2026 年 9 月是一次明显的“补课期”，Release 0.3.8 与 0.3.9 集中处理稳定性与兼容性：

  • 规则解析兜底：LLM 连接失败或解析异常时，自动回退到本地规则解析。效果会打折扣，但任务不再直接失败；

  • 长期记忆修复：把 Chroma 返回的距离换算成相关度，再与阈值比较，修复“结果恒为空”的问题；

  • 记忆会话维护：移除已弃用的 RunnableWithMessageHistory，改为直接维护会话历史；

  • 模型兼容：LLM 客户端支持 OpenAI 兼容的 Chat 接口，默认配置与超时时间同步调整；

  • Redis 配置修正：连接地址与超时配置在 9 月中旬的多笔提交中修正。

这一阶段的主题不是“加能力”，而是“让已有能力在真实环境里稳定工作”。对开源项目来说，这类提交往往比新功能更重要。

六、第五次转向：部署形态收敛

2026 年 8 月底到 10 月，部署链路快速收敛：

  • GitHub Actions 增加 Docker 构建与推送；

  • 镜像从 GHCR 扩展到 Docker Hub，提供 neotems/penshot 与 ghcr.io/neopen/penshot 两个来源；

  • 镜像基于 python:3.11-slim，以非 root 用户运行，缩减体积；

  • 文档补齐 .env、命令行 -e、Compose 三种配置方式，以及 Redis 可选依赖的说明。

这一步让 PenShot 从“能 pip 安装的库”变成“能直接起服务的应用”。对使用者来说，部署成本往往比模型能力更早决定是否试用。

七、第六次转向：从提示词包到交接包（0.4.0–0.4.2）

0.3.x 的输出以“每个片段一段提示词”为中心。0.4.0 起，这个中心开始外移：系统不只生成提示词，还要说明交给哪个模型、需要哪些资产、下游怎么回填。

v0.4.0：目标模型适配层。 提示词转换结果统一为 AIVideoInstructions，再由适配层按目标模型重写风格前缀、负向词、镜头字段、分辨率与运动参数。提示词生成与模型适配解耦，为后续“按片段自动选型”留出了接口。

v0.4.1：连续性前置约束。 外观锚点注入、一致性契约校验器与阶段回退进入主链路，修复回路与 continuity_report.json、repair_history.json 落盘。连续性不再只是最后一道检查，而是提前约束生成。

v0.4.2：声明式资产计划。 新增 generate_assets 节点，输出 asset_plan：角色三视图（character_sheet）、关键道具（prop）与场景锚点（scene）的提示词、负向词、尺寸、视角与状态。片段通过 references 复用资产，usage.fragments 标明每个资产被哪些片段使用；下游生成资产后可回传 asset_manifest，把真实引用接回 PenShot。人工干预节点新增 [7] EDIT_ASSET，可修改资产提示词并回到资产节点重建。

这一步把“资产一致性”从一句设计目标变成了可交付的契约。需要强调的是：PenShot 默认不调用任何文生图接口，资产节点只声明“要生成什么”，落图由下游负责；如果下游不消费 asset_plan，资产链不会自动生效。

八、第七次转向：路由与质量收口（0.4.3–0.4.5）

v0.4.3：模型路由。 新增 route_model 节点，登记 runway_gen4、kling_3、luma_dream、sora_2、pika_2 五个模型的时长上限、图生视频、镜头控制、一致性与风格倾向。路由按可读文字、动作复杂度、角色一致性需求、风格倾向与时长做确定性规则匹配，输出 instructions.route_plan，并为每个片段生成模型专属提示词包。关键文字或高一致性片段可以走“静态首帧 + 动作驱动”的两段式图生视频；路由失败只记录告警，route_plan 置空，不阻断主流程。

v0.4.4：连续性闭环。 跨场景切换改为确定性插入过渡镜头，修复 scene_jump 重试仍反复重跑分镜的问题；外观比较改为主体服装集合，配饰与鞋履增删不再误报；角色三视图与道具静帧不再作为首帧，asset_ref 只代表片段首帧；模板索引修复了“零命中”和“单文档覆盖”两个问题，并新增外观锚点污染、景别不一致、互斥打光、资产使用范围缺失四条质量规则。CONTRACT_SCHEMA_VERSION 升至 0.4.4，0.4.3 入库的缺陷模板需要执行一次迁移。

v0.4.5：分镜缺陷收口。 片段时长改为按动作节点确定性推算，并输出 duration_report；新增同镜头重复片段的检测、合并与超长重切；首帧提示词清洗中文镜头词与广播/音效标记；新增剧本语言推断与 dialogue_language；质量门禁在 below_threshold 放行时写入 quality_gate 标记，资产生成不足时输出 degraded_assets。这一版没有破坏性 API 变更，新增字段均为可选。

至此，主链路从六节点扩展为八节点（新增资产计划与模型路由），输出也从“提示词包”变成了“片段提示词 + 资产计划 + 路由结果 + 质量标记”的交接包。

九、哪些是已发布，哪些还没接线

版本文章最容易犯的错误，是把仓库里存在的代码当成已发布能力。按 v0.4.5 复核，边界大致如下：

已发布且在链路中生效

  • 八节点流水线与条件分支；

  • 规则 + LLM 质量审查（11 项规则）、连续性检查与按来源回退修复；检查点状态落盘（恢复/续传入口未接通）；

  • 声明式资产计划、asset_manifest 回填与人工资产编辑；

  • 目标模型适配与五模型规则路由、两段式图生视频；

  • 提示词模板检索与增强（v0.4.4 修复索引与迁移）；

  • 三层记忆写入（短期 / 中期 / 长期）；

  • REST、MCP、SDK、CLI、Docker。

代码已实现，但生产链路未接线

  • LongScriptChunker 长剧本分块：默认 30 场景 / 180 秒 / 3 场景重叠，但工作流没有调用；

  • create_retriever_for_script 的 BGE 重排序与 MMR 分支：只在未接线的 KnowledgeRouter 中使用；

  • get_context_for_llm / restore_context_for_stage 记忆语义读取：只有定义，没有生产调用；

  • StateSnapshot 状态快照：检查器能生成快照，但工作流没有调用 take_snapshot。

仍在路线图 / Unreleased

  • 超长剧本分块接入主链路、节点内批量调用与增量处理；

  • LLM 缓存默认开启（当前 enable_llm_cache=False）；

  • Web UI 演示界面、可观测性与成本报表；

  • 更多视频模型的能力注册与图片执行器落盘。

这些方向在 CHANGELOG.md 的 Unreleased 或项目文档里出现过，但在落地并接线之前，不应写进“已支持”。

十、三次架构决策的复盘

回看这一年，真正影响后续形态的决策有三个。

1. 用 LangGraph 承载状态机，而不是手写循环。 分支、重试、路由、检查点都交给图引擎，节点只关心自己的输入输出。代价是要理解条件边与状态合并，收益是失败路径可以被显式表达。

2. 用强类型模型做节点契约。 解析、镜头、片段、提示词都有结构，校验和修复才有抓手。代价是模型演进时要维护兼容性，收益是“自由文本智能体”常见的不稳定被大幅收敛。

3. 把增强能力做成可裁剪模块。 RAG、三层记忆、Redis、重排序都不是启动硬依赖；没有它们，主链路仍能跑。代价是“能力存在但未接线”的状态会长期存在，收益是部署门槛低、故障面可控。

十一、结论

PenShot 的版本演进可以概括为七次转向：

  1. 先跑通：强类型契约 + 最初的六节点流水线；

  2. 再补质量：审查、连续性、检查点；

  3. 再加知识：RAG、三层记忆、模板复用；

  4. 然后补稳定性：规则兜底、记忆修复、模型兼容；

  5. 收敛部署：Docker、镜像、配置方式；

  6. 接入下游：目标模型适配层，提示词从“能用”变成“可交接”；

  7. 补齐生产语义：声明式资产计划、按片段模型路由、质量门禁与首帧语义，八节点流水线成型。

版本号还会继续增长，但前五次转向定下的骨架——强类型契约、可裁剪模块、显式失败路径——没有变。最后两次转向（0.4.x）做的是另一件事：把“生成提示词”这一步，延伸成一条可被下游视频平台消费的交接链。判断一个新能力是否真的“支持”，不要看功能列表，去看它有没有生产调用方、有没有端到端测试、有没有在真实产物里留下痕迹。
