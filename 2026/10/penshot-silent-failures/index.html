PenShot 四类静默故障：超时、Redis 与循环路由

PenShot 四类静默故障：超时、Redis、Worker 崩溃与循环路由

版本基线：本文以 PenShot 0.3.9（2026-10-13）源码为复核基线。以下内容是对代码路径的分析，不代表每个故障都已在生产环境复现；升级版本后请重新核对。

相关链接：PenShot 官网 | GitHub | 检查点文档

系统出故障时，最怕的不是抛异常，而是“看起来一切正常”：

  • 任务卡住了，超时定时器却没有触发；

  • Redis 挂了，任务还在跑，只是状态不再更新；

  • 进程重启了，任务恢复了，但从头开始跑；

  • 某个节点反复失败，循环计数器在涨，路由却走进了没有定义的边。

这四类问题共同点是：不报错、不告警、结果偏离预期。本文按 0.3.9 的源码逐条拆开。

一、超时：同步调用让 async 定时器失效

代码路径：workflow_pipeline.py:662-663 用 asyncio.wait_for 包裹 enhanced_workflow_invoke，默认超时 1800 秒；超时后返回 workflow_status: "timeout"。

问题：enhanced_workflow_invoke 内部调用的是同步 workflow.invoke()（workflow_output_fixer.py:47-49）。源码注释写着“注意：这里需要 await workflow.ainvoke”，但下一行仍然是同步调用。

同步调用会阻塞事件循环，asyncio.wait_for 的超时回调没有机会执行。工作流不主动让出控制权，超时定时器就形同虚设。

后果：任务卡在某个 LLM 调用上时，外层超时可能不生效，进程一直挂着，直到节点内部的 LLM 超时或循环上限把它打断。

应对：

  • 依赖节点内部的 LLMBaseConfig.timeout（默认 60 秒）与循环上限作为第一道防线；

  • 生产环境加进程级看门狗，超过阈值直接重启 worker；

  • 如果你在二次开发，把同步 invoke() 改成 await workflow.ainvoke() 是根治方向，但要同时确认所有节点与回调都支持异步。

二、Redis 宕机：任务层与记忆层，两种命运

代码路径：任务记录通过 TaskRepository.write_task 写入 Redis（task_repository.py:89-105）；短期记忆通过 Redis 会话历史写入（short_term_memory.py）。

任务层：Redis 写入失败时，write_task 捕获异常、打 error 日志并返回 False。任务主流程不会因此中断，但状态更新开始丢失。如果 Redis 一直不可用，崩溃恢复能力也随之丧失——内存字典会随进程消失。

记忆层：短期记忆的降级决策发生在构造时（_check_redis_availability()，初始化阶段 ping 一次）。构造时 Redis 可用、运行中途挂掉的情况下，追加消息时 history.add_user_message 抛异常，被 add_to_memory 的 try/except 捕获（short_term_memory.py:145-168），当前这条交互不会进入缓冲区，也不会写进 Redis。

后果：任务看起来还在跑，只是记忆少了一截；多实例部署时，各实例的记忆互不可见。没有告警，也没有重连补偿。

应对：

  • 不要只看 enable_memory=True，核对记忆报告里的 redis_enabled 与实际连接地址；

  • 给 Redis 写入失败加计数与告警，而不是只打日志；

  • 对状态更新失败做重试或降级落盘，避免“任务在跑、状态不动”。

三、Worker 崩溃：恢复窗口与优先级

代码路径：服务启动时调用 recover_pending_tasks(max_age_hours=2)（task_factory.py:641、task_init.py:46），把 2 小时内的未完成任务重新入队。

三个容易忽略的行为：

  1. 超过 2 小时的任务不标记、不清理，只是不再恢复，等待 Redis TTL 自然过期；没有告警；

  2. 恢复的任务优先级统一为 NORMAL（task_processor.py:553 附近），原本的高优先级任务复活后与普通任务同权；

  3. 入队不是简单追加：_insert_queued_task 会按优先级插入（task_processor.py:188-202），同优先级才追加到末尾。恢复任务都是 NORMAL，所以会排在 HIGH 之后、LOW 之前。

更关键的是检查点与恢复路径没有直接衔接。 检查点管理器自身的 get_config() 返回 thread_id = {script_id}_{task_id}（workflow_checkpointer.py:175-186），但实际执行工作流时，workflow_output_fixer.py:49-51 使用的是 thread_id = process_{id(initial_state)}。这是进程内对象地址，每次运行都不同。恢复后的任务即使复用 task_id，也找不到上一次的检查点。

后果：任务会重新执行，进度回退到起点。对分钟级的小剧本影响有限，对长剧本就是实打实的成本。

应对：

  • 把恢复窗口、优先级策略、队列容量写进运维文档；

  • 如果依赖断点续传，先验证检查点 thread_id 是否与恢复路径一致；

  • 对超过恢复窗口的任务做显式标记与告警，不要让它“安静地过期”。

四、循环失控：预警共用标记，路由缺一条边

代码路径：工作流有节点级、阶段级、全局级三层循环计数，任一触顶即熔断。80% 水位会打 Warning 日志（workflow_decision.py:862-863、workflow_nodes.py:1246-1247）。

缺口一：预警标记共用。 节点级与全局级检查都读写同一个 loop_warning_issued 标记，只有先触发的那一级会报警，后触发的那一级不会再提示。排查时容易误以为“只接近了一次上限”。

缺口二：连续性重试的路由缺键。 decide_after_continuity() 在存在 critical 或 moderate 问题且仍可重试时返回 PipelineState.NEEDS_RETRY（workflow_decision.py:534-548），但 workflow_pipeline.py:228-238 为 CONTINUITY_CHECK 注册的条件边只有：

  • SUCCESS → GENERATE_OUTPUT

  • VALID → GENERATE_OUTPUT

  • NEEDS_REPAIR → CONVERT_PROMPT

  • NEEDS_HUMAN → HUMAN_INTERVENTION

  • FAILED → ERROR_HANDLER

没有 NEEDS_RETRY。命中这条路径时，不是“优雅降级”，而可能是框架级路由错误。建议部署前用单元测试覆盖这条路径，确认所用 LangGraph 版本的实际行为。

应对：

  • 为连续性重试补上条件边，或让决策函数统一返回已注册的状态；

  • 把预警标记拆成节点级与全局级两个，避免互相吞掉；

  • 对循环计数、熔断次数、人工干预次数做监控。

五、一张排查清单

把四类故障压成一张表：

故障 表面现象 静默点 优先检查
工作流超时 任务长时间不结束 async 超时被同步调用阻塞 节点 LLM 超时、进程看门狗
Redis 宕机 任务仍在跑 状态写入失败只打日志；记忆当前条目丢失 redis_enabled、写入失败计数
Worker 崩溃 任务恢复后从头跑 2 小时外不告警；优先级降为 NORMAL；检查点 thread_id 不一致 恢复窗口、thread_id、任务耗时
循环失控 节点反复失败 预警标记共用；连续性重试边缺失 循环计数、条件边覆盖

三条工程建议：

  1. 把静默失效当一等公民。 为写入失败、空结果、恢复、熔断建监控，比事后看日志有效得多；

  2. 每条恢复路径都要端到端演练。 杀进程、断 Redis、制造超时，确认系统真的按设计恢复，而不是“看起来恢复了”；

  3. 不要假设框架会兜底。 LangGraph 的条件边、检查点 thread_id、asyncio 超时，都有明确的使用前提；前提不满足时，框架不会替你报错。
